第十一章　并行度、广播变量与累加器

阶段 13 · 大数据处理与分布式检索技术　|　|　难度 ★★★☆
这一章在解决什么问题

程序能跑、逻辑也对，但慢。慢的第一个原因是并行度没配好：分区太少，八核机器只有一个核在工作；第二个原因是闭包陷阱：你在 Driver 定义了一个大维表/配置文件，Task 每次都要把它序列化一遍发给 Executor，几万 Task 就复制几万份——内存和网络全废。前者靠并行度解决，后者靠广播变量（Broadcast）解决；再加一个累加器（Accumulator）处理"跨节点计数/求和"这个看似简单却处处是坑的需求。

这三个是 Spark 内核调优的"老三样"，也是面试必考。学完你能：为程序正确设置并行度、用广播变量替代闭包变量、用累加器做分布式计数，并避开计数翻倍这种隐蔽 bug。

这一章在整个知识库里的位置 上一章：内核第二块（pipeline、缓存、checkpoint） 本章 ← 你在这里：内核第三块——并行度调控 + 共享变量三件套 下一章：实战项目——UV/PV 统计、二次排序、卡口统计（把前 11 章全用上） 再往后：SparkSQL（DataFrame/SQL 更高效的表达） 阶段终点：Spark 分布式计算从原理到实战的完整闭环
1① 并行度：你的集群"同时能干多少活"
要解决什么

集群有 4 台机器、每台 4 核，你的程序却一次只跑 2 个任务——20 分钟变 2 小时。并行度（Parallelism） 就是"同时执行的 Task 数"，它决定了集群资源用满没有。这是性能优化的第一道门槛。

核心思路

并行度 = 某个 Stage 同时运行的 Task 数量 = 该 Stage 输入 RDD 的分区数（每个分区一个 Task，由 Executor 的空闲核并行执行）。

40 个分区 ÷ 16 个核 = 2.5 批
→ 16 个 Task 并行跑，2 批多一点跑完
40 个分区 ÷ 4  个核（只配了 4 个核）
→ 4 个并行，要 10 批跑完 ← 并行度严重浪费

并行度从哪来（4 个决定者，按作用顺序）：

  1. 读取算子：textFile(path, minPartitions) 指定的分区数 / HDFS 分块数
  2. 并行度配置：spark.default.parallelism（shuffle 后默认分区数的来源）
  3. 转换算子参数：reduceByKey(func, numPartitions) / join( ..., numPartitions) 的第二个参数
  4. 显式重分区：repartition(n) / coalesce(n)

盯住一个点：shuffle 之后分区数会变——reduceByKey 不写分区数时用 spark.default.parallelism（没设过则是上游分区数）。要控制 shuffle 后的并行度，就在那个算子上传分区数参数。

坑在哪
现象原因 / 怎么办
集群 16 核但 UI 上只有 4 个 Task 并行spark.default.parallelism 没设或被覆盖。显式给 shuffle 算子传分区数，或设 --conf spark.default.parallelism=<核数×2~3>
并行度拉满反而变慢分区太多 → 每个分区数据太少 → Task 调度开销 > 计算收益。经验：每个分区 100MB 左右数据，或"核数×2~3"起步再微调
一个 Executor 上的 Task 数超过核数Task 排队等核，白启动。Task 并发数 ≤ ④Executor×核数 才有意义；同时注意给每 Executor 留内存（多 Task 共享 Executor 内存）
修改spark.default.parallelism 没生效它在 shuffle 后才作为默认分区数；读取阶段的并行度由输入文件分块/参数决定。两处要分开调
2② 调整分区：repartition 与 coalesce 怎么选
要解决什么

并行度不合适就要改分区数。Spark 给了两个改分区的算子：repartition(n)（增/减都行，但必 shuffle）和 coalesce(n)（减分区，尽量不 shuffle）。用错场景，一次简单"减分区"就白吃一次全量网络搬运。

核心思路 
rdd.repartition(100)    // 重分布到 100 个分区：全程 shuffle，数据跨节点重排
rdd.coalesce(4)         // 减到 4 个分区：尽量本地合并，不 shuffle
rdd.coalesce(4, shuffle = true)  // 强制 shuffle 版（=repartition(4)）
repartitioncoalesce
方向增/减皆可通常减（增分区会退化）
shuffle总是默认不 shuffle
数据分布均匀重排尽量合并不搬移
场景数据倾斜重分布、提并行度输出前减文件数、降并行度

两个经典用法：

// ① save 前减文件数（少 shuffle，最常用）
result.coalesce(1).saveAsTextFile("out/")   // 只出 1 个 part 文件

// ② 减完并行度不够再 repartition 提回去
rdd.coalesce(2).repartition(50)             // 先粗并再细分，两段走

要点：coalesce 不 shuffle 的前提是"目标分区数 < 当前"且数据能在原位合并；增分区必须 shuffle（coalesce 传大数反而没意义）。

坑在哪
现象原因 / 怎么办
coalesce 没生效/结果还是原来分区数减分区时它可能只在 Executor 内本地合并，跨 Executor 合并需要 shuffle=true。数据要跨节点时明确 coalesce(n, true)
用 repartition 减分区能减但吃一次全量 shuffle，明显浪费——减分区一律先想 coalesce
输出 100 个文件嫌多coalesce(1) 出一份，但注意：大量数据 coalesce(1) 会让单分区内存爆炸 + 单 Task 慢，宁可 coalesce 到"核数×2"份
频繁 repartition每次 shuffle 都全量搬运。链路里尽量一次性定好分区数，别算一步 repartition 一步
3③ 分区与资源的匹配：核数、内存、数据量的三角平衡
要解决什么

光知道"并行度要高"不够——分区数要和 Executor 资源匹配，多了调度浪费、少了资源闲置。本点给出从业界实践总结的配比经验，让你一次设置就八九不离十，而不是靠玄学调参。

核心思路

核心关系式：

手动设分区数（shuffle 算子参数 / repartition）优先于默认配置
建议起步值：总核数（executor个数 × 每executor核数）× 2~3

Executor 内存建议：每个 Executor 2~4GB 起步（spark.executor.memory），
                   大 shuffle/大数据量给 4~8GB
分区数据量经验：100MB/分区 左右为佳
  ┌──────────────────────────────┐
  │ 分区太少 → 并行度不足，资源闲置│
  │ 分区太多 → 调度开销大、碎片化  │
  │ 单分区内存爆 → 分区数据量太大  │
  └──────────────────────────────┘

配比经验表（8 核×4 台=32 核为例）：

数据量建议分区数建议每 Executor 内存
1~5GB64~962~4GB
5~20GB96~2004~8GB
20GB+数据量/100MB8GB+ 或加大 Executor 数

调优动作的顺序：先看 UI 的"任务执行时长分布" → 若有 Task 长时间 0 数据空跑 = 分区过多；若有分区数据超大/长 Task = 数据倾斜或分区过少。以 UI 为依据调，不要拍脑袋。

坑在哪
现象原因 / 怎么办
无脑"核数×2"还是慢2~3 倍只是起步，shuffle 密集的任务要多给分区（数据量大更要加）。以实际 Task 空闲率调整
一调大 Executor 内存就"内存超配额"YARN 上每 Executor 内存+overhead 不能超节点内存/可分配数。核数与内存要配成整数倍数（如 2 核 4G）
单个分区几 GB 直接 OOM分区数据量过大（聚合到单 key 也可能）。加大分区数 + 检查是否有倾斜 key
UI Tasks 都是"秒完"但总时长长调度开销占比高，典型的分区过多。减少 repartition 的目标分区数即可
4④ 闭包陷阱：Task 为什么要"背"着整个环境跑
要解决什么

你在 map 里用了 Driver 定义的一个 200MB 的规则表——很多人以为"每个 Executor 一份就行"，实际上每个 Task 都会序列化一份完整闭包！几千个 Task 就是几千份 200MB，网络和内存直接炸。理解闭包机制，是理解广播变量价值的钥匙。

核心思路

闭包（Closure）：你在转换算子的 lambda 里引用的外部变量（Driver 端定义的），会被 Spark 捕获，随 Task 一起序列化后发给 Executor。

// Driver 里定义
val rules: Map[String, String] = loadBigRules()   // 200MB 维表

// 在算子里引用 → 闭包捕获
val result = data.map(row => rules(row.key))      // rules 被包进闭包

悲剧就在这里：

每个 Task = 一份完整闭包（含 rules）→ 序列化 → 网络传输 → Executor 反序列化
200MB × 1000 个 Task = 200GB 网络流量 + 每个 Executor 内存里 N 份 rules

量级测算：8 个 Executor × 每 Executor 32 个 Task = 256 份闭包，都带上 200MB 维表 = 51GB 传输。而维表只有 8 份就够了（每 Executor 一份，进程内共享）。

验证方法：UI 上每个 Task 的"Shuffle Write"不大，但作业很慢、GC 频繁——多半是闭包在作祟；Spark 日志会提示序列化大小。

坑在哪
现象原因 / 怎么办
Task 序列化报 NotSerializableException闭包里塞了不可序列化的对象（如数据库连接）。连接应放 mapPartitions 里按分区创建，不要放 Driver 变量里
大对象每次 Task 都复制，内存暴涨大只读数据用广播变量（下一知识点），每 Executor 只有一份，Task 之间共享
闭包里有个 Random/Date 每次结果不同闭包变量在 Driver 捕获后是固定的。想要每 Task/每元素变化的值，要在算子内部创建
以为闭包变量修改能传回 Driver不能！Executor 上改的是副本。想回传用累加器（本知识点后面）
5⑤ 广播变量：大只读数据"每 Executor 只有一份"
要解决什么

闭包陷阱的直接解药：广播变量（Broadcast）。它让 Driver 只把大只读数据发一次，每个 Executor 上维护一份，所有 Task 共享同一份副本，从"每 Task 一份 200MB"变成"每 Executor 一份 200MB"，数量级直接除以 Task 数。维表关联、白名单过滤、配置字典全用它。

核心思路 
// ① 广播：Driver 把 rules 只发一次给所有 Executor
val bcRules = sc.broadcast(rules)          // Broadcast[Map[String,String]]

// ② 算子内使用：执行时从广播变量取（本地读取，无网络）
val result = data.map(row => bcRules.value(row.key))

执行原理：

Driver ──(发一次, 各 Executor 一份)──→ Executor1: [rules 一份]
                                        Executor2: [rules 一份]
每个 Executor 上的所有 Task 共享这一份 rules（同进程内存复用）

对比闭包变量的量级：

闭包变量广播变量
传输次数Task 数份Executor 数份
200MB×1000 Task200GB200MB×8=1.6GB
每 Executor 占用多份1 份

撒手锏细节：广播用的是序列化存储 + 懒加载——Executor 第一次用到时才反序列化，且数据不会随每个 Task 走网络。Spark 会自动广播闭包中 ≤10MB（spark.sql.autoBroadcastJoinThreshold）的变量，大对象必须手动 broadcast。

坑在哪
现象原因 / 怎么办
广播了还是慢检查是否真的用了 bc.value（对标闭包写法）。写了 .value 但对象本身在 Driver 里又被引用，闭包还是捕获到，双重浪费
广播变量是"不可变"的含义数据在任务执行期不可变。想改？重新 broadcast 一份新的，别尝试原地修改（会引发不一致）
广播 2GB 数据爆内存广播数据存在每 Executor 内存里，太大照爆。先缩小数据（只广播需要的字段）或换 JOIN 方案
忘了清理广播bc.unpersist() 释放。长作业频繁换广播对象时记得回收，否则内存泄漏式增长
6⑥ 累加器：跨节点"数数"的正确姿势
要解决什么

需求很朴素："统计处理了多少条""过滤掉多少脏数据""累加了多少钱"。但在 Executor 上改 Driver 变量是无效的（副本机制），用 collect 又太重。累加器（Accumulator）就是 Spark 提供的跨 Executor 对 Driver 端变量做加法的专用工具——最后的和会准确回到 Driver。

核心思路 
// ① 创建累加器
val total = sc.longAccumulator("total")       // 长整型计数
val skipped = sc.longAccumulator("skipped")   // 可以建多个

// ② 在算子内累加（同时 role 计数 + 脏数据计数）
data.foreach { line =>
  total.add(1)
  if (line.isEmpty) skipped.add(1)
}

// ③ 行动算子结束后，在 Driver 读数（在行动算子**执行完**之前读不到最终值）
println(total.value, skipped.value)

关键机制：

  1. 只能做 add（加），Executor 上累加到本地副本，只有 Driver 能看到完整 value（汇总各 Executor）
  2. 类似"只写不读"通道：Executor 读不到别的 Executor 的中间结果（设计如此，保证一致性）
  3. 容易踩的雷：累加器在转换算子里累加时，如果该 RDD 被缓存后多次行动算子使用 / Task 重试，累加会重复执行（重新跑一遍就多加一遍）
累加器放在 foreach 里（行动算子）→ 只跑一遍，安全
累加器放在 map 里（转换算子）  → 每行动算子触发都再累加一次 → 翻倍！
坑在哪
现象原因 / 怎么办
数字对不上（翻倍/多倍）累加器在转换算子里且该 RDD 被多个 Job/缓存复用 → 每 Job 重放一遍。放行动算子（foreach/count 前）里，或接受"执行一次加一次"的语义
Driver 里在算子执行完前读 value读到的是旧值/0。累加器最终值只有所有 Task 完成后才可靠。要拿最终统计结果 → 放在行动算子之后读
Task 失败重试，累加重复重试的 Task 会重跑累加逻辑。在意精确性就别在转换算子内累加；或在行动算子阶段统一做
想用累加器统计"最大值/复杂对象"累加器做不了——只有数字加和（可自定义累加器但复杂）。求 max/自定义统计用 reduce/aggregate
7⑦ 共享变量三件套：何时用什么，一张表看清
要解决什么

闭包、广播、累加器三者都讲完，容易混。本点把三者放进同一张决策表："我要从 Driver 往 Executor 传数据"用前两个（按数据量选）；"我要从 Executor 往 Driver 收数据"用第三个。从此不再犹豫。

核心思路 
问题 1：Executor 需要 Driver 的什么数据？
  ├─ 小数据（几 KB~几 MB）→ 闭包变量直接用（Spark 自动处理）
  └─ 大数据（几 MB~几百 MB 只读）→ 广播变量（手动 sc.broadcast）

问题 2：Executor 算出来的东西要回 Driver？
  └─ 只是数字累加/计数 → 累加器
  └─ 需要复杂聚合结果 → reduce/collect（行动算子）
工具方向典型场景必须知道
闭包变量Driver→Executor小配置、小字典每 Task 一份，大对象会炸
广播变量Driver→Executor维表、白名单、规则库每 Executor 一份，不可变
累加器Executor→Driver计数、过滤统计、累加总和只加不减；转换算子内会用重

同一场景组合用法（日志清洗想想看）：

val bcDict = sc.broadcast(dict)          // 大字典广播 → Executor 读
val cnt    = sc.longAccumulator("cnt")   // 过滤掉的数量 → Driver 读

clean.foreach { row =>
  if (!bcDict.value.contains(row.key)) cnt.add(1)
}
坑在哪
现象原因 / 怎么办
小数据也手动 broadcast没坏处但没必要（10MB 以下 Spark 自动处理）。写代码时小变量直接闭包即可，减少干扰
混用"广播+闭包"两个引用广播对象必须在 Lambda 里通过 bc.value 取；如果又在 Lambda 外引用原变量，闭包还是会捕获原对象（双份）。统一用 bc.value
想传"可变的大数据"用广播广播不可变。数据会变就每次变更后重新 broadcast（开销=重发一次），或用外部服务读
累加器计数和 UI 上的输入行数对不上先排除 Task 重试/多 Job 复用因素，再看累加器放的位置（转换 vs 行动）
8⑧ 实战套路：一个"慢任务"的并行度调优路径
要解决什么

前面讲了并行度的概念，但真的拿到一个慢任务，从哪下手、按什么顺序调？本点给一条可复制的四步调优路径——照着走，别瞎调。

核心思路

四步调优法（按代价从低到高）：

① 先看资源：Executors 总核数够吗？
     spark-submit --executor-cores 4 --num-executors 8 → 总核 32
     活跃分区数 > 总核数 → 排队串行（多数任务的真相）

② 再看分区：数据分区数和核数匹配吗？
     默认 partition = 文件块数，可能远小于核数 → 并行度上不去
     repartition(分区数 ≥ 核数×2~3) 摊开计算

③ shuffle 分区：宽依赖的分区数单独控
     spark.sql.shuffle.partitions（SQL 场景默认 200）
     reduceByKey 的并行度由 shuffle 分区数决定，别和输入分区混淆

④ 最后看倾斜：有没有一个分区吃掉 90% 时间？
     看 Stage 长尾 Task → 数据倾斜 → 加盐/重分区

实测口诀："分区太少加分区，核数不够加核，单个 Task 长尾查倾斜"。

验证调优是否有效：UI 上看该 Stage 的总耗时/最长 Task 耗时；调一次看一次，别一次调三个参数（无法归因）。

坑在哪
现象原因 / 怎么办
分区调大后反而更慢并行度超过核数=任务排队+调度开销。分区数 ≈ 核数×2~3 是经验甜区，过多过少都慢
只调并行度不加核并行度是"能同时跑的任务数"，核数是"能跑几个"，两头要同时看
SQL 慢和 RDD 慢用一样的调法SQL 的 shuffle 分区归 spark.sql.shuffle.partitions，RDD 的归算子参数。两套别串
调完不看 UI 凭感觉UI 是唯一裁判：调一个参数→跑→看 Stage 耗时→再调下一个

本章小结

这一章你实际拿到的是三样东西：

拿到了什么为什么要紧
并行度方法论：分区数来源、repartition/coalesce 选择、资源配比经验性能优化第一步——让集群真正"转起来"，不空转不浪费
闭包→广播的思维升级：同是大对象，一份/份数差百倍维表和规则库关联类作业的性能命根子，也是面试高频考点
累加器纪律：只加不减、行动算子内累加、Task 重试会重复计数类统计不翻倍、不乱跳，生产可交付
