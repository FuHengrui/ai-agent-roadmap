1① 项目全景：需求、数据、架构图
要解决什么

动手前先画作战地图：需求是什么（口径！）、数据长什么样（字段！）、批与流两条线的架构。口径先定死再写码——这是本实战教学最重要的一个习惯（也是上一章强调的）。

核心思路

需求（口径固定）：

指标口径输出
PV每天页面访问总次数(日期, 总次数)
UV每天去重用户数（按 user_id）(日期, 独立用户数)
热门页面 Top10每天各页面访问量排序前 10(日期, 页面, 次数) 列表
地区分布按地区聚合访问量(地区, 次数)

数据（样例一行）：

2026-10-01 08:12:33  u_1001  /home  北京  Chrome 119
时间戳 | user_id | 页面 | 地区 | 浏览器

两条线的架构：

【批线】（T+1 报表）
HDFS 日志 → SparkSQL 清洗成宽表 → 指标 SQL → 分区表落数仓（dt 分区）

【流线】（实时大屏）
Kafka(topic: user_events) → Structured Streaming/DStream
   → 窗口聚合（每分钟 PV/UV/地区流量）→ Redis/MySQL 供前端大屏

数据库设计（输出目标）：

-- 数仓表
CREATE TABLE dwd.log_clean (dt STRING, ts STRING, user_id STRING, page STRING, region STRING, ua STRING) PARTITIONED BY (dt);
CREATE TABLE ads.daily_metric (dt STRING, pv BIGINT, uv BIGINT) PARTITIONED BY (dt);
坑在哪
现象原因 / 怎么办
需求没定就写代码先把四张"口径表"给业务确认。口径错=白算，这是数据项目的头号返工原因
表和目录没有规划先建库建表（ODS/DWD/ADS），代码跟着结构走，别边写边发明表
样例数据手算过一遍了吗拿 5 行样例手算 PV/UV 期望值，程序跑完对答案——这是验证"语义对不对"最便宜的方法
批流两条线各自为政两条线跑同一口径（复用 SQL 口径文档），实时结果定期和批结果对账（能对上=两条线都可信）
2② 批线第 1 段：SparkSQL 清洗成宽表
要解决什么

第一条流水线开工：原始日志 → 清清洗洗 → 可用宽表。复用前面所有清洗知识：schema 校验、脏行过滤、字段规整、写分区表。这段代码是"数仓分层"的第一层（ODS→DWD）。

核心思路 
// 读原始日志（CSV 风格，header=false）
val raw = spark.read.option("sep", "	").schema(schema)
  .csv("hdfs://.../raw_logs/")

// 清洗：解析时间、过滤坏行、去查询串
val clean = raw
  .filter(col("ts_str").isNotNull && col("user_id").isNotNull)
  .withColumn("dt", to_date(col("ts_str"), "yyyy-MM-dd HH:mm:ss"))
  .withColumn("page", regexp_replace(col("page"), "\?.*$", ""))
  .drop("ts_str").filter(col("dt").isNotNull)

// 写 DWD 分区表（按 dt 分区）
clean.write.mode("overwrite").partitionBy("dt").saveAsTable("dwd.log_clean")

两个要点：

  1. 解析与兜底成对出现：to_date 解析失败返回 null → 用 isNotNull 过滤；时间格式先 dt 探一列确认格式串
  2. 写分区表自动建目录：partitionBy("dt") + saveAsTable 一步到位；Hive/BI 直接能查
坑在哪
现象原因 / 怎么办
to_date 格式写错全 null格式串要和真实数据一致（有 T 还是空格、毫秒有没有）。先 select to_date(col,"<格式>") 试一行
双写（文件+表）重复只 saveAsTable（元数据+数据都在 Hive 注册）。不要再手动写 parquet 又建表
脏行"悄悄消失"有意为之（清洗）。想看消了多少：累加器 count 或对比 raw 行数——写进监控
spark.sql 查不到 dwd 表没 enableHiveSupport 或临时表 vs 正式表混淆。先 SHOW TABLES 验证注册成功
3③ 批线第 2 段：指标计算（PV / UV / Top10 / 地区）
要解决什么

宽表就绪，指标怎么算？——全是前面学的 SQL/DSL 基本功：count、countDistinct、开窗 TopN、groupBy 地区。本点给出四段完整 SQL + 输出到 ADS 表，这就是"数仓报表层"的标准动作。

核心思路 
// 复用宽表
val clean = spark.table("dwd.log_clean")

// ① PV：总行数
clean.agg(count("*").as("pv"))

// ② UV：去重用户数
clean.agg(countDistinct("user_id").as("uv"))

// ③ 热门页面 Top10（窗口函数！）
val topPages = clean
  .groupBy("dt", "page").count()           // (dt, page, cnt)
  .withColumn("rn", row_number().over(
    Window.partitionBy("dt").orderBy(desc("count"))))
  .filter(col("rn") <= 10)                 // 每组 Top10

// ④ 地区分布
clean.groupBy("region").agg(count("*").as("cnt")).orderBy(desc("cnt"))

输出策略（ADS 层）：指标结果合并成"一张指标宽表"落数仓，报表/BI 直接查：

val daily = clean.groupBy("dt")
  .agg(count("*").as("pv"),
       countDistinct("user_id").as("uv"),
       countDistinct("page").as("page_uv"))
daily.write.mode("overwrite").partitionBy("dt").saveAsTable("ads.daily_metric")

至此批线闭环：raw → ODS 读 → DWD 宽表 → ADS 指标 → 报表工具消费。

坑在哪
现象原因 / 怎么办
Top10 排序有 null 列orderBy 默认 null 行为：desc 时 null 在前！orderBy(desc_nulls_last(col("count"))) 或清洗时去 null
指标 SQL 里列名拼错countDistinct("user_id") 写错字段运行时才报。先用 .columns / printSchema 对字段
每天一个任务的指标重跑翻倍saveAsTable mode 选错：用 overwrite（今天覆盖）或 insertInto 指定分区（append 分区级）。重跑要"只重算当日分区"
PV/UV 都写在两张表里不好对账同一天 PV、UV 汇总在一行（daily_metric），报表侧 join 简单；对账也快：用 count(*) 交叉验证
4④ 流线版本：同一口径的实时实现
要解决什么

批线算的是"昨天"，业务大屏要"当前"——同一套口径换流式实现：Kafka 进 → 每批解析 → 窗口聚合 → 每分钟输出指标。本点给出 Structured Streaming 版（推荐生产）+ DStream 版要点，关键在口径对齐（和批线用同一份 SQL 口径文档）。

核心思路 
// Structured Streaming：DF API 写流
val parsed = spark.readStream.format("kafka")
  .option("kafka.bootstrap.servers", "kafka:9092")
  .option("subscribe", "user_events").load()
  .selectExpr("CAST(value AS STRING) AS json")
  .select(from_json(col("json"), schema).as("d")).select("d.*")

// 按事件时间窗口聚合：每分钟 PV/UV
val metric = parsed
  .groupBy(window(col("ts"), "1 minute"), col("region"))
  .agg(count("*").as("pv"), countDistinct("user_id").as("uv"))

// 输出：写 Redis/MySQL（foreachBatch 批量写）
metric.writeStream.outputMode("update")
  .trigger(Trigger.ProcessingTime("10 seconds"))
  .foreachBatch(...).start()

批流对账（口径一致性验证）：

实时口径：t+1 分钟窗口 PV = 批口径：该分钟在 dwd 里 count(*) PV
对不上 → 查口径差异（时区！过滤规则！）再调

DStream 版思路（如果要沿用）： KafkaUtils.createDirectStream → map(_.value) → updateStateByKey/窗口（见第 17 章第③④⑥点），输出 foreachRDD 写 Redis。

坑在哪
现象原因 / 怎么办
实时和批对不上账第一疑犯：时区（to_date 按服务器时区）→ 统一用 Asia/Shanghai；第二：过滤规则不一致（实时没滤的脏行批滤了）
window 用时间列没排序流里事件时间要按 ts 为准（不是到达时间）。window(col("ts"),"1 minute") 按事件时间；迟到数据用 watermark（高级点）
foreachBatch 里建连接批次内每分区建连接或复用池，别在 Driver 建（老坑重现）
Redis/MySQL 没装也能跑通？本地演示输出到 console（format("console")）验证逻辑，再接存储。先 console 后存储，两段解耦
5⑤ 数据倾斜实战：热点 key 的"加盐"解法
要解决什么

实战压轴坑：某个 key 数据量爆炸（如"北京"地区占 60% 流量），导致对应 reduce 分区巨慢、其它分区空转——数据倾斜（Skew）。解决思路本质是"把大 key 拆分后合并"：加盐（两阶段聚合）。这是调优面试必问的实战题。

核心思路

问题图解：

reduceByKey 后：北京分区 6000 万行，其它分区几十万 → 北京那个 Task 是全场最长尾

加盐两阶段聚合：

// ① 第一阶段：给 key 加随机盐，把"大 key"拆成多份
val salted = rdd.keyBy(_._1).map { case (k, v) =>
  val salt = scala.util.Random.nextInt(10)   // 10 份盐
  ((k, salt), v._2)                           // key 变成 (原key, 盐)
}
// ② 第一层聚合：盐内先合（每份盐各自 reduce）→ 分而治之
val partial = salted.reduceByKey(_ + _)
// ③ 去掉盐，第二层聚合：把 10 份盐的结果合并成最终值
val result = partial.map { case ((k, _), v) => (k, v) }
                    .reduceByKey(_ + _)

两阶段聚合原理：

不加盐：  北京 → [1 个巨石分区]，6000 万行单点扛
加盐后：  北京+盐0 .. 北京+盐9 → 10 个分区各 600 万行 → 并行聚合
         再合并 10 份结果 → 最终北京值

适用与代价：对 key 数量多、单个 key 数据量大的聚合最有效；代价是多一次 shuffle（两轮聚合）。skew 严重才值得。

其它手段（列个清单）：过滤无关热点、广播小表 join、调整分区数、AQE 自动优化（Spark 3 的 spark.sql.adaptive.skewJoin.enabled）。

坑在哪
现象原因 / 怎么办
加盐后结果不正确/翻倍盐粒度和合并逻辑要对称：第一层 reduceByKey 聚合的是 (key,盐) 粒度，第二层去掉盐再聚——中间少任何一层都会错
join 也倾斜加盐对 join 更复杂：要"大表加盐 + 小表复制盐份广播"。可先试 AQE 自动处理，不行再手动
以为加盐包治小数据加盐反而慢（多一次 shuffle）。先确认真倾斜（UI 长尾 Task）再动手
窗口内加盐盐要加在窗口聚合之前的 key 上，别忘了窗口的粒度与盐无关
