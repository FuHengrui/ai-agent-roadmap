第八章　Cursor 精准上下文与 Rule 规则体系：让 AI 答得准

阶段 16 · Vibe Coding 实践　|　工具实操　|　难度 ★★☆
这一章在解决什么问题

为什么 Cursor 有时候"答非所问"？ 根本原因往往是：上下文给错了。Cursor 的 AI 不是"通灵"，它答得准不准，取决于你喂给它的上下文准不准、你立的规矩清不清楚。

这一章解决两件事：① 精准上下文——用 @ 方式把"文档、网页、代码文件"钉进对话，让 AI 在正确的资料上回答；② 规则体系（Cursor Rules）——把"你希望 AI 怎么干活"写进规则文件，让它每次自动遵守，不用重复交代。

学完这一章，你能回答：@Docs 和 @Web 分别解决什么问题、Cursor Rules 的本质和优先级、四种规则类型（Team/Project/User 及 .cursor/rules 下的项目规则文件）分别在哪生效、规则仓库有哪些可用的提示词资源。这些是 Cursor 从"会用"到"用精"的分水岭。

开始之前

不用装新东西，用之前的 Cursor；上一章的模式先分清，这章讲怎么问得准。

1① 精准上下文总览：@ 符号体系
要解决什么

Cursor 里到处是 @ 符号，它到底是干什么的？

核心思路

精准上下文是 Cursor 的核心功能，允许通过 @（打招呼符号）方式将特定文件、文件夹、文档、网页等内容添加到 AI 的上下文中，让 AI 能"看向"指定的资料来回答。

核心效果：

  • AI 的回答基于你指定的资料，而不是泛泛而谈；
  • 与选中的代码/文件联动，上下文自动跟上；
  • 上下文随对话保留，同一话题连续追问不失忆。
@ 的基本用法（输入框里输入 @ 即弹出选择菜单）
@某个文件     → 把文件内容喂给 AI
@某个文件夹   → 把整个目录喂给 AI
@Docs (文档) → 喂官方文档/知识文档
@Web (网页)  → 喂指定网页/在线资料

注意：@ 选中的资料占用上下文窗口额度，别把所有文件都 @ 进去——只钉需要的资料。

坑在哪
现象原因 / 怎么办
输入 @ 没反应确认焦点在输入框且版本支持；@ 是 Cursor 的上下文引用入口不是普通字符
把整个项目 @ 进去上下文会爆；按需选关键文件/模块即可
忘记 @ 资料就问没 @ 资料时 AI 只能凭通用知识回答，自然"答非所问"；先 @ 再问
2② @Docs：把文档变成 AI 的"参考资料"
要解决什么

问 AI"这个库的 API 怎么用"，它常答旧版本或瞎编——怎么让它基于最新官方文档回答？

核心思路

@Docs 让你把官方文档、开发者文档、知识文档等加入上下文，作为 AI 的"参考资料"。

使用方式（把文档喂给 AI）：

  1. 在输入框中输入 @Docs；
  2. 从弹窗中选择要引入的文档（可搜索）；
  3. 选中后即可在对话中针对该文档提问。

把文档加入 @Docs 列表（首次配置）：

  1. 点击 @Docs 下方的"自定义文档（Custom docs）"入口；
  2. 填写文档名称与文档网址（URL）；
  3. 保存后可在 @Docs 中搜索并引用。

典型场景：问 "React 19 的新 API 怎么用？"——先 @ 官方 React 文档，AI 就会基于文档回答而不是凭旧记忆扯淡。

提醒：文档内容也会占用上下文额度，按需引入；Ask 模式下照样可以 @ 文档，问答体验专门为此优化过。

坑在哪
现象原因 / 怎么办
@Docs 里搜不到某文档先用 Custom docs 添加（填名称+URL）；索引需缓存时间，稍后再试
文档内容太大导致上下文爆文档按需选；可只 @ 相关章节（如能分页引入的话）
以为 @Docs 会实时更新加入的是索引时的快照；文档更新后需重新添加/刷新索引
3③ @Web：让 AI 上网找最新答案
要解决什么

问"最新的框架教程"或事实类问题——AI 的知识可能有截止时间，怎么让它实时联网？

核心思路

@Web 允许将网页内容作为上下文引入（相当于给 AI 开"网页浏览"权限），AI 可访问指定的网页 URL 或在线资料，回答更有时效性。

典型用法：

  • 输入 @Web 后给出网址，AI 直接读取该网页内容；
  • 结合自然语言提问："@Web 帮我总结这个网页的要点"；
  • 用于查找最新文档、教程、技术文章。

注意：@Web 也需要网络可用；它帮你"引用网页"，不代表"随便上网乱搜"——你需要明确给 URL 或可检索的关键信息。

坑在哪
现象原因 / 怎么办
@Web 后 AI 说访问不到URL 可能需登录/反爬；换公开可访问的来源，或把内容复制成文字喂进去
问"最新技术趋势"但没给 URL给出 URL 或用可定位的资料；@Web 是"带 AI 访问指定网页"而非无限搜索引擎
和 @Docs 混淆@Docs 喂文档类资料（索引化）、@Web 喂网页 URL（实时抓取）；按资料形态选
4④ 什么是 Cursor Rules：写进文件的行为准则
要解决什么

每次对话都要重新交代"用中文注释、别用 alert、测试要覆盖边界"……太累。能不能让 AI 每次都自动遵守？

核心思路

Cursor Rules（规则）是指导 AI 行为的提示词（Prompt）文件——把"AI 应该怎么工作"的规范写成文件，Cursor 会在合适时机自动加载这些规则，让 AI 严格遵守。

Rules 的本质：一段文本（Markdown/纯文本），描述"如何编程、何时使用何种模型、注意什么"等行为约束。

重要澄清：Rules 是提示词文件，不是插件，也不是代码库——它塑造 AI 的行为，不改变 Cursor 的机制本身。

使用价值：

价值说明
一致性每次 AI 行为稳定，风格统一
效率不用重复交代偏好，一次写入处处生效
质量强制约束代码风格、测试要求、命名规范

优先级（重要）：Team > Project > User（Team 规则优先级最高，User 规则兜底；没有 Notebook/System 这两级）。

坑在哪
现象原因 / 怎么办
把 Rules 当插件装Rules 是提示词文本文件；装"插件"是另一回事（扩展/扩展市场）
规则写太啰嗦互相打架优先级是 Team > Project > User；冲突时高优先级胜出，别靠"全写上"解决
写完规则 AI 没生效检查文件位置/类型是否正确（User 在用户级目录、Project 在 .cursor 目录），并重启/重载
5⑤ 四种规则类型：Team / Project / User / 目录内规则
要解决什么

Rules 有四种，各自管哪一层？放哪个文件？什么时候生效？

核心思路
类型作用范围存放位置说明
User Rules（用户规则）全局（所有项目）用户设置目录你最通用的偏好，如"默认使用中文注释"
Project Rules（项目规则）单个项目.cursor/rules/ 目录该项目专属规范，如组件风格、目录约定
Team Rules（团队规则）Team / Enterprise 套餐，在 Dashboard 配置全团队共享团队统一规范，优先级最高
System Rules（系统规则）系统内置/兜底Cursor 内部厂商预设，优先级最低，一般不感知

Team > Project > User：记住越"贴近你"的规则优先级越高——你的习惯 > 项目的约定 > 笔记场景 > 系统兜底。

在 .cursor/rules 下用 .mdc 文件：Cursor 的规则文件支持 .mdc（带 YAML frontmatter 的 Markdown 规则文件），frontmatter 支持 description / globs / alwaysApply 三个字段——只是 Markdown 加 YAML 头，没有"函数"能力——比纯 md 多一层"结构化约束"。规则文件通常会在对话中被自动加载，无需每次手动引用。

一个 Project Rules 示例（.cursor/rules/summary.mdc）：

---
description: 代码风格约束
globs: "**/*.ts"     # 注意是复数，配合 alwaysApply 用
---
写 TypeScript 必须：
1. 使用 interface 而非 type 定义对象
2. 注释使用中文
3. 所有函数必须写 JSDoc
坑在哪
现象原因 / 怎么办
把全局偏好写进项目规则项目规则只对该项目生效；全局偏好写 User Rules
.mdc 里写了 JS 代码执行.mdc 支持的函数是给 AI 用的约束/动作描述，不是自动执行脚本；照格式写，别当代码库
glob 写错导致规则张冠李戴glob 如 **/*.ts 限定文件范围；写错会该生效不生效，核实后重写
6⑥ 规则仓库：现成的提示词资源
要解决什么

自己写规则没头绪？有没有别人验证过的现成规则可以抄？

核心思路

规则仓库（Rules Repository） 是社区/官方整理的现成可复用提示词资源——用户可从中查找与项目匹配的规则直接使用，或参考改写。

用途：

  • 快速获取"别人写好的、验证过的"规则；
  • 主题覆盖广（代码风格、框架规范、安全要求等）；
  • 拿来即用，省去从零编写调试的时间。

使用建议：先看规则覆盖的场景与 glob 范围是否匹配你的项目，再决定直接引用或本地化改写；引用前通读一遍，确认没有与你项目冲突的约束。

坑在哪
现象原因 / 怎么办
从仓库拉规则不审就用规则"直接用"风险在冲突（别人的规范和你的项目冲突）；先通读再审用
以为规则仓库=官方唯一来源规则仓库是资源集合，入口可能在 Cursor 设置/社区；来源不同质量参差，择优
拉一大堆规则把上下文塞满规则会自动加载进上下文；只保留必要规则，避免浪费 token
7⑦ Chrome 插件开发的技术积累：进入实战前的剩余概念
要解决什么

下一章要用 Cursor 实战开发 Chrome 插件，这里先把"离线安装、权限、文件的 MIME 映射"等前置概念补完，避免下一章被细节卡住。

核心思路

本章末尾为实战做了铺垫，三个技术细节提前讲清：

1. 加载已解压的扩展程序（开发者模式）

Chrome 地址栏输入 chrome://extensions/ → 右上角开启"开发者模式" → 点"加载已解压的扩展程序" → 选择插件目录。这是开发期加载未打包插件的标准方式（对应打包后的 .crx 安装）。

2. 插件权限（permissions）

manifest 清单文件里声明插件需要的权限列表（如 storage、activeTab、scripting、tabs 等），Chrome 安装时向用户展示并索取授权。最小权限原则：只申请实际用到的权限，避免过度索权导致审核/信任问题。

3. 文件 MIME 类型映射

开发时如遇文件类型不被识别（例如用 fetch 读取离线资源的类型问题），需要配置 MIME 类型映射，让 Chrome 正确识别资源类型。例如服务器或本地测试服务需配置 .json → application/json、.js → text/javascript 等。

这三个点分别对应下一章的：加载插件（开发者模式）、写 manifest（权限）、调资源（MIME）。

坑在哪
现象原因 / 怎么办
加载插件按钮灰色确认已开启开发者模式；未开启时按钮不可用
权限写太多被拒绝遵循最小权限原则，manifest 只声明用到的权限
扩展读取本地文件类型报错检查 MIME 映射配置（开发期尤常见于 json/js 资源）
8⑧ 规则触发类型与 User Rule 配置入口
要解决什么

第 ④ 点讲了规则的四种"级别"（User/Project/Notebook/System），但 .mdc 规则文件还有四种"触发类型"——它们是什么？User Rule 在哪里配置？

核心思路

① .mdc 规则文件的四种触发类型（决定规则"什么时候生效"）：

类型触发时机适合
Always始终应用想让规则一直生效
Auto Attached匹配 globs 模式的文件被引用时自动附加想让规则自动触发
Agent Requested由 AI 代理判断是否应用（需提供规则说明）想让 AI 自己决定
Manual仅在提示中显式使用 @规则名 时附加想手动调用规则

② User Rule 的配置入口：Cursor 的全局设置——Cursor Settings → Rules 里设置，对所有项目生效。用户级规则示例（回复语言与风格类）：

所有输出和建议必须基于确认无误的信息，严禁臆测或无依据的猜测
按文件逐一修改，便于审阅和排查问题
除非明确要求，禁止添加任何第三方或新增依赖
仅修改用户明确指定的内容，不影响其他区域或功能
只做指定改动，不增加任何未被请求的功能或逻辑

③ 快速生成规则文件：在 Chat 窗口输入 / 并选择 Generate Cursor Rules，Cursor 自动生成 .cursor/rules/ 目录及默认规则文件；也可手动 mkdir -p .cursor/rules + touch xxx.mdc。

两个分类维度别混：第 ④ 点的 User/Project/Notebook/System 是"作用范围/级别"；本点的 Always/Auto Attached 等是"触发时机"——一个规则文件既有级别又有触发类型。

坑在哪
现象原因 / 怎么办
把"级别"和"触发类型"混为一谈级别=管多大范围（全局/项目），触发类型=什么时候生效（始终/自动/手动）；两个维度叠加使用
Manual 规则一直不生效Manual 需要显式 @规则名才附加；想省事选 Always/Auto Attached
User Rule 写太激进全局翻车User Rule 全局生效，保守稳健为先；项目特有约束写 Project Rules

拿到了什么为什么要紧
