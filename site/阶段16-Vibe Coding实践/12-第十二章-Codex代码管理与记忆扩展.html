第十二章　Codex 代码管理与记忆扩展：Git 集成的工程化 Agent

阶段 16 · Vibe Coding 实践　|　工具实操　|　难度 ★★★
这一章在解决什么问题

Vibe Coding 的终极问题：AI 改错了一堆代码，怎么无损回到"改之前"？AI 每次都要重新交代的偏好，能不能写成"长期记忆"让它永远记得？ 这一章是 Codex 的"工程化双件套"：Git 代码管理（初始化、提交、回滚、分叉、工作树）和记忆扩展（AGENTS.md、插件、Skills、MCP）。

Git 是回滚的底气：AI 放手干，错了 git checkout 一条命令回到解放前——没有 Git 兜底的 Vibe Coding 是裸奔。AGENTS.md 是记忆的载体：把项目规则写进去，Codex 每次开工自动读取，你就不用重复交代。

学完这一章，你能回答：Codex 怎么初始化 Git、代码回滚的三种姿势（checkout/reset/分叉）、工作树 worktree 与回滚的关系、AGENTS.md 是什么怎么用、插件能扩什么、Skills 与 MCP 分别是什么。

这一章在整个知识库里的位置 上一章：你掌握了 Codex 功能模块 + 权限沙箱——它怎么干活、怎么防乱来。 本章 ← 你在这里：Codex 工程化的最后两块拼图——Git 管"改错了怎么办"，AGENTS.md/插件/Skills/MCP 管"怎么越用越顺手" 阶段终点：Codex 收官，阶段 16 三款 Vibe Coding 工具全部闭环
学习提示

本章 4 个模块：Git（回滚/分叉/worktree）、AGENTS.md（记忆文件）、插件与 Skills（能力扩展）、MCP（生态接入）。优先级：Git 回滚 ≥ AGENTS.md > 其余。动手时每改一轮就 git commit 一次，形成"无提交不实验"的肌肉记忆。

1① Git 初始化：一切回滚的前提
要解决什么

"AI 改错能回滚"的第一步是什么？——先把项目交给 Git 管起来。

核心思路

在 Codex 中初始化 Git：让 Codex 项目进入版本控制状态，后续所有"提交/回滚/分叉"才有地基。

# 概念示例：在项目目录初始化 Git 仓库
git init

# 提交当前基线（"实验前快照"）
git add .
git commit -m "baseline: 开始 AI 改造前的基线"

为什么必须做：没有 Git 时的 AI 改动是"不可逆的赌注"；有 Git 后，每一次实验都有检查点可回。

建议节奏（Vibe Coding 铁律）：

开工前 → 初始化 + 提交基线
每完成一个小里程碑 → 提交一次
AI 要动大手术前 → 再提交一次（保平安）

和权限沙箱的分工：沙箱防"危险操作偷偷执行"，Git 救"改错了想反悔"——一个管入口，一个管出口。

坑在哪
现象原因 / 怎么办
开始实验前没初始化没基线就无法干净回滚；先 init+commit 再让 AI 动手
一个大任务完成后才提交里程碑粒度提交才有用；"完成才提交"=只有一个检查点
把 .git 目录删除当回滚删 .git 丢全部历史；回滚用的是 checkout/reset（下一点）
2② 代码回滚：实验失败的后悔药
要解决什么

AI 改崩了怎么回到之前？Codex/Git 提供的回滚姿势有哪些？

核心思路

Git 回滚的三种常用姿势：

姿势命令（概念）用途
丢弃工作区改动git checkout -- <file> 或 git restore <file>放弃未提交的修改，回到最后一次提交
软回退指针git reset --soft HEAD~1回退提交记录但保留改动在暂存区（改主意了想重做）
硬回退git reset --hard <commit>彻底回到某提交，之后改动全部丢弃（慎用）

在 Codex 中操作：直接对话命令让 Codex 执行回滚（或手动在终端执行）；回滚类命令属于权限沙箱内需授权的操作，确认后再执行。

使用原则：

  • 只想丢掉"最近的烂活" → checkout/restore；
  • 想重做最近一次提交 → reset --soft；
  • 想彻底抛弃一段时间内的所有改动 → reset --hard（先确认没有要留的东西）。
坑在哪
现象原因 / 怎么办
reset --hard 后"我的修改没了"hard 会丢弃未提交/后续提交；用前三次确认（要留的先 commit/stash）
回滚了但 AI 再次执行同样操作回滚≠防复发；把"别那么做"的约束写进 AGENTS.md
对公共分支乱 resetreset 改历史，共享分支上慎用；自己实验分支随便，公共分支用 commit 修复
3③ 分叉与工作树：平行实验不打架
要解决什么

想让 AI 同时试两条方案（A 方案、B 方案），互不影响、可随时切换——怎么办？

核心思路

分叉（Fork/Branch）：从当前状态分出一个独立分支，让 AI 在一个分支上实验，原分支保持不动。

# 概念示例：开分支做危险实验
git branch experiment/refactor-v2
git switch experiment/refactor-v2
# ……AI 在分支上随便改……
git switch main        # 随时切回主线

工作树（Worktree）：更彻底的平行——同一个仓库开出多个工作目录，各自独立 checkout 不同分支：

git worktree add ../proj-exp experiment/refactor-v2

两种方式的定位：

方式特点适合
分叉（branch）同一目录切换分支快速实验、切换查看
工作树（worktree）多目录并行，互不干扰多方案同时进行、需要并排对比

和 Codex 的关系：外接 VSCode 打开的就是工作树（上一章）；"新方案开新 worktree"让 AI 的实验与主线物理隔离，是最安全的探索姿势。

坑在哪
现象原因 / 怎么办
分支切来切去丢了现场切分支前 commit 或 stash；未提交改动会跟着你走，容易乱
多个 worktree 改同一个依赖各自独立工作树但依赖（node_modules）可能共享/冲突；按项目实际处理
实验分支永不合并也不清理实验完要么 merge、要么删分支，别让分支长杂草
4④ AGENTS.md：Codex 的长期记忆
要解决什么

每次开新对话都要重新交代"用中文注释、别动 utils 里那个函数、测试必写"——能不能写进文件一劳永逸？

核心思路

AGENTS.md 是 Codex 的项目记忆文件——把项目的规则、约定、注意事项写进这个 Markdown 文件，Codex 在（重新）开始任务时自动读取，作为行为准则。

在项目根目录放置 AGENTS.md，内容示例：

# 项目约定
- 代码注释使用中文
- 不要修改 utils/legacy.js（历史遗留，改动风险高）
- 所有新功能必须附带测试
- 变量命名使用 camelCase

为什么它这么好用：

  • 自动加载：新会话无需重复交代；
  • 上下文省 token：规则常驻、对话不用反复粘贴；
  • 团队共享：所有用 Codex 的人共享同一套约定。

善用三招：①把"AI 常犯的错"写进去（防复发）；②把"本项目特殊约定"写进去（保一致性）；③把"危险区（别碰什么）"写进去（护底线）。

坑在哪
现象原因 / 怎么办
AGENTS.md 写太长塞爆上下文写要点别写论文；长规则拆成"路径+条目"，能省则省
改了 AGENTS.md 但 Codex 没反应新会话才会重新读取；改完开新对话验证生效
把所有通用偏好写进项目级 AGENTS.md通用偏好（全程中文等）可放用户级规则，项目级专注本项目专属约定
5⑤ 插件与自动化：给 Codex 加装技能
要解决什么

Codex 默认能力不够用、重复流程每次手写——怎么扩展？

核心思路

插件（Plugin）/自动化扩展：给 Codex 增加工具与自动化能力的机制。

典型用途（讲义思路）：

  • 扩展命令集：为 Codex 增加自定义命令（工作流类操作一键触发）；
  • 自动化流程：把"构建→测试→提交"这类固定流程封装，Codex 一键执行；
  • 集成外部工具：接入代码分析、部署脚本等第三方工具。

插件形态的提示（重要）：Codex 的插件通过在其环境中注册/配置使用；安装前看清来源与权限——插件可能包含执行能力，别装来源不明的。

示例（概念）：定义一条自定义流程
build → test → lint → git commit
之后一句 "跑一遍流程" 即可触发
坑在哪
现象原因 / 怎么办
装了来路不明的插件插件的执行能力=代码执行；选官方/可信来源，安装前看权限说明
插件和现有环境冲突先备份配置再装；冲突时逐个排查/禁用
以为必须装插件才能用 Codex插件是"增强项"；基础能力（对话/搜索/计划）开箱即用
6⑥ Skills 与 MCP：能力包与生态接入
要解决什么

Codex 的扩展生态里还有两个高频词：Skills 和 MCP。它们分别是什么？

核心思路

Skills（技能包）

  • 把特定领域的工作流/知识打包成可复用的技能文件（类似"招式"），Codex 按需调用；
  • 与 AGENTS.md 的"规则"区别：Skills 更像"做某类事的完整方法"（如"帮我审查代码"按固定步骤来），规则是"行为约束"。

MCP（Model Context Protocol，模型上下文协议）

  • 一套开放协议，让 AI 应用（如 Codex）标准化地接入外部工具和数据源（数据库、API、内部系统……）；
  • 价值：生态互联——写一次适配，多个 AI 工具都能用；不再每个工具各写各的对接。

三者的分工（本阶段理解到这一层即可）：

机制管什么
AGENTS.md项目"规矩"（行为约束）
Skills某类任务的"招式"（方法流程）
MCP对外部工具/数据的"接口"（生态通道）

和阶段前文的呼应：第 5 章 Trae 讲过 MCP 概念（三组件、两传输）——MCP 是行业通用协议，Trae、Codex 等都在用它接外部世界，这正是"知识库前后呼应"的点。

坑在哪
现象原因 / 怎么办
AGENTS.md / Skills / MCP 三者混淆记忆口诀：规矩（AGENTS.md）、招式（Skills）、通道（MCP）
以为 MCP 是 Codex 独有MCP 是开放标准协议，多家 AI 工具支持；第 5 章 Trae 已涉及
一上来就追求全套扩展先跑通基础闭环，再按需加 Skills/MCP；扩展是手段不是目的
7⑦ AGENTS.md 写作清单：该写什么、别写什么
要解决什么

AGENTS.md 到底写什么？写太多是"长篇文档"、太少又约束不住 AI——讲义给了一份明确的"适合/不适合"清单。

核心思路

讲义第 19 页对 AGENTS.md 的内容边界给了权威说明：

适合写进去的内容：

  • 项目使用的包管理器、测试命令、构建命令；
  • 修改代码后必须执行的验证步骤；
  • 不能触碰的目录、密钥、生成文件或外部系统（风险边界）；
  • 团队约定的代码风格和提交前检查；
  • 特定子目录的例外规则（如后端/前端/脚本目录各自的验证命令）。

不适合写进去的内容：

  • 大段产品背景、历史会议纪要、完整 API 文档；
  • 会频繁变化的临时任务列表；
  • 密钥、账号、Token 或只能给人看的内部凭证（红线：密钥绝不进规则文件）；
  • 可以通过命令自动发现的信息（例如完整文件树）。

还可以让 AI 帮你写：让 Codex"通读当前项目，把学到的项目信息保存到 AGENTS.md 文件里，用中文、格式清晰"——AI 自动沉淀项目知识（讲义第 19 页演示了这一步）。

核心判断标准：AGENTS.md 不是越长越好，它该写"Codex 做事前必须知道的规则"，而不是把所有项目文档复制进去。

坑在哪
现象原因 / 怎么办
把密钥/Token 写进 AGENTS.md绝对禁止；密钥用环境变量/凭证管理，规则文件只写"不要触碰密钥文件"
AGENTS.md 越写越长定期瘦身：超过"做事前必知"范围的移出；长文档放项目 docs，规则只做索引
写完发现 Codex 不守规则检查是否新会话（AGENTS.md 在新对话自动读取）、内容是否具体可执行（"别乱改"这种空话无效）
8⑧ 插件与自动化实例：GitHub + Gmail 组合拳
要解决什么

插件和自动化到底怎么用？讲义给了一个完整的组合实战——让 Codex 自动"查 GitHub 项目 + 发邮件给自己"。

核心思路

讲义第 21 页的完整实例：

插件是什么（讲义定义）：插件是第三方服务器为 Codex 编写的软件包，第三方把自己的能力用插件形式注入 Codex；目前 Codex 的插件市场已经非常丰富。连接 GitHub、Gmail 等第三方服务时，需要进行授权操作。

组合实战流程：

1. 安装/连接 GitHub 插件（授权）
2. 安装/连接 Gmail 插件（授权）
3. 指令："用 /github 看本周关于 AI Agent 一个月内 star 数
   前 10 的开源项目，用 /gmail 把列表发邮件给我"
4. 追加自动化："把上述任务做成自动化，每周五下午 5 点半
   都发邮件给我"
  • 第一步：插件提供能力（查 GitHub / 发 Gmail）；
  • 第三步：一条指令同时驱动两个插件完成"查 + 发"；
  • 第四步：定期对话实现自动化——把任务设为周期执行，无需手动触发。

学习要点：插件的价值=把外部服务能力注入 Codex；自动化的价值=把固定任务交给定期对话。两者配合，Codex 从"回答工具"变成"常驻自动化助手"。

坑在哪
现象原因 / 怎么办
插件连接第三方服务时拒授权授权是必要步骤（OAuth 类）；先明白"插件要读取什么、能干什么"再授权
自动化任务频率设错定期对话先确认触发时机（周五 17:30 等）再落地；别用错周期造成骚扰
把"能查 GitHub"当成"能改你仓库"插件权限按授权范围；只授任务所需的最小权限，别图省事全给
