第十一章　Codex 功能模块与权限沙箱：Agent 怎么干活、怎么保证安全

阶段 16 · Vibe Coding 实践　|　工具实操　|　难度 ★★★
这一章在解决什么问题

Codex 作为一个能在你电脑上"动手"的 Agent，最核心的两个问题是：①它会干什么；②它乱来怎么办。 这一章正面回答这两问：前半讲功能模块（搜索、重命名、归档、Steer 方向控制、计划模式、批注模式、外接 VSCode、上下文压缩），后半讲权限沙箱（三层权限限制模型，Codex 自我防护的底座）。

这一章是全阶段的最难点，也是 Codex 相对 Trae/Cursor 最独特的一部分——它把"AI 能不能动某类操作"做成了可视化的三层许可模型。理解它，你就理解"为什么 Agent 时代需要新的安全范式"。

学完这一章，你能回答：Codex 六个核心功能模块分别干什么、Steer 怎么给 AI 纠方向、计划模式与批注模式的区别、外接 VSCode 如何使用、上下文压缩解决了什么、三层权限沙箱（watch/plan/auto）每一层放行什么、越界操作如何拒绝与上报。

这一章在整个知识库里的位置 上一章：你完成 Codex 安装，有了工作空间概念——"桌子"摆好了。 本章 ← 你在这里：Codex 的"手"（功能模块）和"刹车"（权限沙箱）——这是 Codex 干活与防乱来的核心机制 下一章：Codex 代码管理与记忆扩展（Git 集成、AGENTS.md）——把工程管理也交给 AI 阶段终点：三款 Vibe Coding 工具的能力与安全模型全部掌握

本章分两半记忆：上半"功能"按"找（搜索）、改（重命名）、整（归档）、控（Steer）、算（计划）、批（批注）"串；下半"沙箱"是重中之重——把三层权限（watch/plan/auto）与"越界怎么办"背成条件反射。

1① 功能模块总览：Codex 的六只手
要解决什么

Codex 具体会做哪些操作？先看清功能全景，避免"只会对话不会用功能"。

核心思路

Codex 的核心功能模块（讲义归纳）：

模块干什么类比
搜索（Search）在项目中搜代码/文件，支持语义搜索项目内的"百度"
重命名（Rename）批量重命名文件、变量、符号全局改名手术
归档（Archive）把文件/代码块归档整理项目"收纳箱"
Steer对话中给 AI 纠方向、改策略开车时的方向盘
计划模式（Plan Mode）先出执行计划再动手，重在"想清楚"施工前的图纸
批注模式（Annotate Mode）在代码上做批注式修改说明评审时的批注笔

功能之间可叠加使用：比如"先搜索定位 → 再计划改法 → Steer 修正策略 → 重命名落地"。会叠加，才是 Codex 的高级用法。

坑在哪
现象原因 / 怎么办
只知道"对话干事"，不知道有搜索/计划等模块功能模块让 Codex 更可控、更可查询；翻上表逐项实操一次
重命名直接整个项目改名重命名要先确认范围（文件/符号/全局）；必要时切 Steer 或计划模式先看方案
归档功能用成"删除"归档是收纳整理（可恢复语义），删除是另一回事；确认操作类型再执行
2② 搜索与重命名：找得准、改得稳
要解决什么

大项目里"找一个函数"和"全局改名"是高频操作。Codex 怎么做这两件事？

核心思路

搜索（Search）

  • 支持按文件内容、文件名检索；
  • 支持语义搜索（用自然语言描述"找登录逻辑"类意图）；
  • 搜索范围遵循当前工作空间与权限沙箱约束。

重命名（Rename）

  • 可重命名文件、变量、函数/符号；
  • 通常带引用联动：改一处，相关引用一并更新（依赖 Codex 对代码关系的理解）；
  • 强调"安全重命名"：先预览影响面，再批量执行。
示例对话
codex：把 utils.js 里的 getData 重命名为 fetchUserList，并联动更新所有引用

协作姿势：先 Search 确认位置（哪儿在用），再 Rename 动手（改什么），改完人工抽查引用，避免漏网。

坑在哪
现象原因 / 怎么办
重命名只改了定义没改引用检查重命名是否联动引用；确认后把它当"改前必查"项
语义搜索返回不相关结果搜索是辅助定位，结果仍需人工判断；用更精确的查询词
重命名动到生成物/第三方代码限定范围（排除 node_modules、构建产物），避免误改依赖
3③ 归档：给项目做收纳
要解决什么

项目里一批"暂时不用但不想删"的文件/代码怎么处理？

核心思路

归档（Archive） 模块把选中的文件或代码块归档整理——"眼不见但数据还在"。

使用场景：

  • 旧模块暂时下线但保留备用；
  • 多版本代码并存时整理归类；
  • 项目目录太乱，把"历史遗留"归到归档区。

与删除的本质区别：删除 = 移除（通常不可逆）；归档 = 收纳（可找回）。别把归档当删除用，也别怕归档——它不是损失数据。

与 Git 的关系：归档更多是"项目布局整理"；要真正的历史版本管理，走 Git（下一章）。

坑在哪
现象原因 / 怎么办
归档后找不到文件归档有去向标识（归档区/标记）；先查归档位置再问为什么"消失"
把归档当 Git 分支/历史归档≠版本管理；版本回滚看 Git，归档只是整理收纳
归档范围太大影响构建归档前确认是否被引用；被引用文件归档可能导致构建报错
4④ Steer：对话里的方向盘
要解决什么

AI 干着干着跑偏了（方案不对、风格不符），怎么即时纠偏？

核心思路

Steer 是 Codex 的方向控制机制——对话中随时给 AI 纠方向，而不必重开对话。

用法：在对话流中发出一条"方向指令"，Codex 会修正后续行为。和"重新描述需求"的区别是——Steer 不推翻当前上下文，只调方向，效率更高。

典型 Steer 指令：

别用 TypeScript，保持 JavaScript
走测试驱动，先写测试再实现
优先可读性，不要过度优化
换个思路：用事件驱动而不是轮询

原理：Steer 本质是把"约束/偏好"注入当前对话上下文，比"重开一局"省 token、省时间。

坑在哪
现象原因 / 怎么办
Steer 没生效（AI 还是原来方向）指令要具体可执行（"用 X 不用 Y"），别用"你注意点"这类空话；必要时用计划模式重审
频繁 Steer 打断节奏开工前把关键约束一次说清（可写进 AGENTS.md，下一章）；Steer 用于中途纠偏
把 Steer 当"回滚"Steer 只管调方向；已经改坏的代码要靠 Git 回滚（下一章）
5⑤ 计划模式：先出图纸再施工
要解决什么

希望 AI"先说怎么做、我再批准"，而不是直接改代码——这是对 Agent 的信任管理基础。

核心思路

计划模式（Plan Mode）：Codex 先输出执行计划（步骤、要改哪些文件、影响什么），不动手改代码，等用户确认后才执行。

核心价值：把"AI 的意图"前置可见，用户批准 = 授权，拒绝 = 保护。它是"计划先行"的开发习惯与 Agent 的结合。

典型流：

你：用计划模式，重构这个模块
Codex：计划如下——
  1. 新建 hooks/useUser.ts …
  2. 修改 UserCard.tsx 引用 …
  3. 删除旧 fetchUser 函数 …
  请确认是否执行
你：批准（或：第 2 步不用做）

批注模式（Annotate Mode）：与计划模式配套——在代码上做批注式说明（标记修改点、说明改动意图），代码本体暂不改动，供你逐处审阅。类似"评审者在代码上写批注"。

一句话区分：计划模式管"整体怎么走"（计划层），批注模式管"每处怎么改"（代码层）——两者都强调"先可见、后执行"。

坑在哪
现象原因 / 怎么办
计划模式也直接改代码确认当前处于计划模式而非执行态；批准后才动手
计划看着对就全批计划要逐条审：文件对不对、范围对不对、风险项有没有；偷懒全批=放弃把关
批注模式和普通注释混淆批注是"给 AI/人看的改动说明"，不进入最终逻辑；普通注释是代码注释，两者不同
6⑥ 外接 VSCode：把 Codex 的活接到编辑器里
要解决什么

Codex 改的文件在"另一个环境"里看不到，怎么让修改直接落在熟悉的编辑器里？

核心思路

Codex 支持外接 VSCode：把 Codex 的执行区/worktree 链接到 VSCode 打开，让 AI 的改动直接在编辑器中可见可改。

使用方式（讲义路线）：

  1. 在 Codex 会话中发起"在 VSCode 中打开"（或对应命令/按钮）；
  2. Codex 的工作空间/工作树被 VSCode 打开；
  3. 在 VSCode 里查看 AI 改动的文件、继续人工编辑；
  4. 编辑完成后回到 Codex 继续对话（或提交 Git）。

价值：VSCode 的查看/编辑/调试体验 + Codex 的自动执行，"编辑器供人看、Agent 供人使"——尤其适合 Codex 改完、人还要精修的混合协作。

注意：外接 VSCode 打开的是 Codex 的工作树，和人本地通用项目目录的关系取决于工作空间类型（临时/持久），别在两边各改各的造成冲突。

坑在哪
现象原因 / 怎么办
VSCode 里改了，Codex 没感知两边顺序要清晰：AI 改→你审改→回来继续对话；别同时双向写同一文件
外接后找不到文件认准打开的是工作树根目录（worktree/folder），文件路径以它为基准
没装 VSCode 点外接没反应前置软件里的 VSCode 没装/没在 PATH；装好后再外接
7⑦ 上下文压缩：对话越长越贵，怎么办
要解决什么

对话一长，上下文窗口挤爆、费用飙升、AI"忘事"——Codex 怎么解决？

核心思路

上下文压缩（Context Compression）：当对话长度超过阈值时，Codex 自动压缩早期对话，保留关键信息，释放上下文空间——让长任务不断线。

效果：

  • 对话可继续更长（不会被硬截断）；
  • 节省 token（压缩后成本更低）；
  • 关键信息（当前任务、已做改动、约束）尽力保留。

用户侧该做什么：

  • 别以为"压缩了=没丢"，关键结论/待办自己心里有数；
  • 重要的约束（规则）写进 AGENTS.md（下一章），压缩后依然在；
  • 对极长任务，分阶段/分任务推进优于一个超长对话。

一句话：压缩是"自动整理记忆"，但它不保证零丢失——把重要的事交给文件和 Git，别只放在对话里。

坑在哪
现象原因 / 怎么办
压缩后 AI 忘了一些细节压缩是有损摘要；长任务中重要事实主动再确认
不想被压缩把会话拆短/拆任务；约束写进 AGENTS.md 最稳
以为压缩=永久保留压缩目的是继续对话；要永久记录用 Git 提交/AGENTS.md
8⑧ 权限沙箱总览：三层许可模型
要解决什么

Codex 能在你电脑上执行命令、改文件——它凭什么"不乱来"？答案：权限沙箱——Codex 的安全底座。

核心思路

权限沙箱（Permission Sandbox）：Codex 的三层权限控制模型，把 AI 能执行的操作按危险程度分级，低危自动放行、中危可授权放行、高危必须明确确认。

层级名称行为控制典型操作
Watch（观察层）低危，自动放行只读类操作无需确认读文件、搜索、查看代码
Plan（计划层）中危，需授权修改类操作需用户批准修改文件、执行某些命令
Auto（自动层）高危/自动执行高风险操作严格确认/禁止删除、执行任意命令等

设计思想：最小权限原则——AI 默认只能"看"（Watch），要"改"先问你（Plan），要"干危险事"基本不放行（Auto 严格管控）。

你与沙箱的协作：每次 Codex 请求权限，看清楚再点；不确定的操作先问"这会执行什么、影响哪些文件"。

坑在哪
现象原因 / 怎么办
沙箱弹窗一路"允许"沙箱防的就是"手滑全允许"；每条请求先读一遍再决定
以为 Watch=无权限Watch 是自动放行的只读权限，不是没有权限；读写分离是它的意义
把 Plan 执行当"AI 自己想干就干"Plan 层每次修改都有授权点；授权前你可以改主意
9⑨ 越界操作：被拒绝的操作与上报机制
要解决什么

AI 想做沙箱外的事（删除、改系统文件）会怎样？Codex 的"最后防线"是什么？

核心思路

越界操作指超出当前权限层级/沙箱范围的操作（如未授权的删除、危险命令、访问沙箱外路径）。

Codex 的处理机制：

  1. 拒绝/拦截：越界操作被阻止，不会执行；
  2. 上报/提示：明确告知"该操作被拒绝/需要授权"及原因；
  3. 用户可接管：确需执行时，由用户手动执行（或按官方授权流程放行），Codex 不擅自越权。
示例（示意）
Codex：需要删除文件 cache/tmp.db（超出当前权限）
用户：（手动执行删除，或重新授权后 Codex 继续）

安全原则（本章最重要的一条）：需要删除/高危操作时，Codex 不会偷偷干——它停下请示你；你也别图省事把越界操作全放开。

坑在哪
现象原因 / 怎么办
越界被拒后让 AI "绕过"绕过=放弃安全防线；绝不让 AI 用非授权路径执行危险操作，禁止诱导绕过
危险命令（rm -rf 类）直接批准高危操作人工复核；不确定就先查影响面再决定
把沙箱当"AI 能力受限"抱怨沙箱是保护你；它限的不是 AI 能力，是"未经同意的破坏能力"

这一章你拿到了 Codex 的"使用手册 + 安全手册"：

拿到了什么为什么要紧
