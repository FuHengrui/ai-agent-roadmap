第三章　LoRA 原理：用低秩分解撬动大模型

阶段 12 · 大模型高效微调与对齐技术　|　难度 ★★☆
这一章在解决什么问题

上一章你知道了"高效微调"能省钱，但心里一定有个大问号：只改一点点参数，凭什么能达到接近全量微调的效果？ 如果只是想"少调参数"，那随机挑几个层冻结不就行了？——答案是：这里面有个数学直觉叫低秩，弄懂它，你才算真正掌握高效微调，而不是"照着教程抄代码"。

这章用大白话拆开 LoRA（Low-Rank Adaptation，低秩适配）：传统微调的问题 → LoRA 的核心思想 → 为什么省 99% 参数还管用 → 数学上它到底改了什么。这一章是手写 LoRA（第 4~7 章）的理论地基，公式不多，但每个都管用。

这一章在整个知识库里的位置 上一章（三大技术对比）：微调是"让 AI 更聪明"的路线，高效微调是其中的省钱玩法 本章 ← 你在这里：拆开高效微调之王 LoRA——低秩原理、参数量对比、为什么省显存 下一章：手写 LoRA 微调（一）——配环境、加载 DeepSeek 预训练模型，把原理变成第一行可运行代码 再往后：数据准备 → 训练保存 → 测试合并上传 → Unsloth 提速 → GGUF/Ollama 部署 → LLaMA-Factory WebUI 阶段终点：你能自己写出一套完整 LoRA 微调流水线，并说出每一步背后的道理
1① 传统微调的问题：动全身，太贵
要解决什么

理解 LoRA 的起点是搞明白"全量微调到底贵在哪"。假设模型里有个线性层权重矩阵 W，它有多大？——一个 4096×4096 的矩阵就有 1677 万个参数，而这种矩阵在模型里有一大堆。全量微调意味着每一个都要更新、都要存梯度、都要做反传。

核心思路

核心事实：

$$Y = WX$$

  • W 是形状为 d×k 的权重矩阵（如 4096×4096）；
  • 全量微调意味着要训练并更新整个 W，1677 万个参数只是一个层；
  • 模型有几十上百个层，全更新 = 显存里除了模型还要存梯度、优化器状态（Adam 再翻几倍）→ 一张普通显卡根本装不下。

于是自然的问题：我们真的需要更新 W 的每一个数吗？ 还是只更新"它的某个缩略版本"就够了？——这就是 LoRA 切入的破绽。

坑在哪
现象原因 / 怎么办
以为"微调开销=模型参数×2"就够算全量微调的显存大头是优化器状态：AdamW 每参数还要存一阶/二阶动量，约等于再翻 2 倍多的参数空间。这也是 7B 全量微调动辄 60GB 显存的原因
以为 W 全是 4096×4096 这种大矩阵真实模型里也有小矩阵（如注意力 K/V 投影），但 LoRA 是按"作用模块"整体处理的，原理不因矩阵大小改变
2② LoRA 的核心思想：不碰 W，挂两个小矩阵
要解决什么

既然不更新整个 W，那 LoRA 到底"调"什么？答案是：它不动 W 本身，而是给 W 旁边挂两个很小的新矩阵，用它们的乘积模拟"W 应该发生的改变"。

核心思路

拆解一下：

> LoRA 不直接学习 W'，而是引入两个小矩阵： > - A 矩阵（形状 d×r） > - B 矩阵（形状 r×k）

让权重的变化 ΔW 由两个小矩阵相乘得到：

$$\Delta W = A \times B$$

于是模型的输出变成：

$$Y = (W + \Delta W)X = (W + AB)X$$

通俗理解：W 是"原老师"，A×B 是"一个小补丁"。训练时只训补丁（A、B），老师 W 全程冻结。推理时把补丁合回去（W + AB），模型就用上了新本领。

这个"补丁"为什么能管用？——因为实验发现：大模型在下游任务上的参数变化，其实集中在一个很低维的空间里；AB 这种低秩乘积恰好能表达这个低维变化。这是 LoRA 成立的根本直觉。

坑在哪
现象原因 / 怎么办
以为 AB 乘积能 100% 表达任意 ΔW数学上低秩乘积表达不了"全秩"变化，所以 LoRA 是近似。但实践中大模型任务适配的变化就集中在低维方向，近似够用，且这种"限制"反而自带正则化、不易过拟合
混淆"A 直接加在权重上"A、B 不是直接加到 W 上参与前向，而是先乘出 AB 再和 W 相加（W+AB）；训练时保存的是 A、B 两个小权重的文件，而不是改写后的 W
3③ 为什么省参数：算一笔账就懂
要解决什么

"两个小矩阵"到底有多小？光说"参数少"没感觉——用具体数字算一遍，你才会有"哇，真的少 99.6%"的实感。

核心思路

具体算一遍：

对象形状参数量
原始 W4096×409616,777,216（约 1677 万）
A 矩阵（秩 r=8）4096×832,768（约 3.2 万）
B 矩阵8×409632,768（约 3.2 万）
LoRA 总参数A+B65,536（约 6.4 万）

减少比例：1677 万 → 6.4 万，减少了 99.6%。

把账目换成直觉：原来要更新 100 个箱子里的所有东西，现在只更新其中 0.4 个箱子的量——而且效果还接近。这就是"低秩"的杠杆：用一个很窄的中间维度 r，把"大变化"压扁在"小矩阵"里。

坑在哪
现象原因 / 怎么办
以为"r 越小越好，反正省显存"r 是"表达能力的宽度"：r 太小（如 1、2）补丁能力不足，效果下降；r 太大（如 512+）又接近全量、不省。实践常用 r=8/16/32，从 8 起步试
拿"99.6%"直接算显存节省参数少 ≠ 显存等比例省：显存里还有激活值（前向中间结果）、梯度、以及基础模型的权重。LoRA 省的是"训练侧的可训练参数/优化器状态"，不是全部显存，别把账算太满
4④ 前向公式：训练时和推理时有什么不同
要解决什么

教程代码里一会儿 get_peft_model 挂 LoRA，一会儿 merge_and_unload 合并——这两个阶段背后就是"W+AB"的两种存在形式。搞清楚"训练时怎么算、部署时怎么合"，代码才不是玄学。

核心思路

分两个阶段看：

1. 训练阶段（挂 LoRA）：前向走

$$Y = (W + \frac{\alpha}{r} \cdot AB)X$$

注意这里隐藏了一个缩放因子 α/r（lora_alpha 与秩 r 的比），控制补丁强度——这就是 LoraConfig(r=8, lora_alpha=32) 里两个数字的意义。训练只更新 A、B，W 冻结，梯度反传也只在 A、B 上算。

2. 推理/部署阶段（合并）：事先算好

$$W_{merged} = W + \frac{\alpha}{r} \cdot AB$$

把补丁"焊死"进原权重（merge_and_unload），得到一个正常的、无 LoRA 痕迹的模型文件——可以直接导出成 GGUF、上传 Hugging Face、跑 Ollama（第 10 章正好用上）。

两个阶段转换，就是代码里 PeftModel.from_pretrained(...) + merge_and_unload() 干的事（第 7 章实战）。

坑在哪
现象原因 / 怎么办
忘记 α 的存在，以为 LoRA 只能靠 r 控制强度r 控制"低秩宽度"，α 控制"补丁缩放"。实际生效强度 ≈ α/r：r=r、α 越大越用力。调参时两个一起看，别只盯 r
以为"合并后还能继续微调"merge 后 LoRA 痕迹消失，想再微调得重新挂 PEFT（或保留未合并副本）。所以训练产物要保留 lora 权重文件（小），合并产物（大）用于部署，两条线别混
5⑤ 显存优化：LoRA 的钱省在哪
要解决什么

前面说"参数少了显存省"，但这句太笼统。面试或自检时，别人追问"到底省了哪块显存"，你得能说清是省了训练参数、梯度和优化器状态，而不是省了模型本身。

核心思路

训练一份模型，显存大致装四样东西：

显存占用全量微调LoRA省不省
模型权重 W要训练冻结不减（W 还在）
训练参数梯度W 的梯度只有 A、B 的梯度大省
优化器状态（Adam 动量×2）按 W 大小×3 倍按 A、B 大小算大省
激活值（前向中间结果）全量可用梯度检查点再省部分可省

所以 Lora 省的是"训练负担"：要更新、要存梯度和动量的东西从 1677 万降到 6.4 万，显卡压力断崖式下降——这就是 4GB 显存也能跑 LoRA 微调的原因。一句话总结：显存优化（只需调整少量参数）+ 计算效率（训练负担更轻）+ 灵活性（与各种预训练模型轻松结合）。

坑在哪
现象原因 / 怎么办
以为"LoRA 微调不需要好显卡"模型本身 W 还是得放进显存（可量化到 4bit 再省，见第 4 章 QLoRA）。LoRA 省的是"训得动"，不是"装得下"——装不下照样要量化
把"省显存"说成"省内存/省磁盘"三样东西分开记：显存=训练时 GPU 上放得下；内存=加载推理；磁盘=模型文件大小。LoRA 主要省显存，磁盘上模型文件（合并后）一样大
6⑥ target_modules 与 bias：LoRA 挂在哪、动哪些
要解决什么

代码里 target_modules=["q_proj", "v_proj"] 这种参数是干嘛的？为什么有的教程挂 q/v，有的挂全部线性层？——不搞清楚，你连"调哪些模块"都无法自定义。

核心思路

LoRA 不是全自动的，得告诉它"给模型的哪些线性层挂补丁"：

配置项含义常见做法
target_modules作用模块列表（挂 A、B 的层）["q_proj","v_proj"]（轻）或 [...all]（重，如 LLaMA-Factory 填 all）
bias是否训练偏置"none"（默认不动 bias，最省）
lora_dropout补丁层随机失活率常用 0.05~0.1，防过拟合
task_type任务类型TaskType.CAUSAL_LM（因果语言模型）

参考资料：注意力里的 q_proj/k_proj/v_proj/o_proj 是微调的主战场，挂它们就能明显改行为；MLP 的 gate/up/down 挂了信息量更大但负担更重。教学版通常只挂 q/v（本书示例即如此），追求上限时挂全线性层（Unsloth 默认更全）。

坑在哪
现象原因 / 怎么办
以为 target_modules 是 LoRA 的"全部作用范围"LoRA 挂住的模块才被调整；没挂的层 W 完全冻结。语音/视觉/表格等多模态模型的模块名不同，直接套文本模型的 q_proj 会报错找不到
忽略 prepare_model_for_kbit_training 这类前置调用量化模型（QLoRA）训练前要先"准备"：解冻某些层、禁用缓存、必要时用 gradient checkpointing。跳过它，量化微调可能直接不收敛或报错（第 6 章会真实遇到）
7⑦ 一张图看懂 LoRA 在模型里的位置
要解决什么

文字讲再多不如一张结构图：LoRA 的 A、B 矩阵到底"长"在模型的哪里？为什么说它"不改变原始模型参数"？

核心思路

把 LoRA 画在 Transformer 的一个注意力层旁边：

  输入 X
    │
    ▼
┌───────────────────────────────┐
│ Q/K/V/O 投影层                 │
│ W (冻结，d×k)     ← 模型本体   │
│                              │
│  LoRA 补丁（只训这个）          │
│   A (d×r) ──► B (r×k)         │
│   ΔW = A×B                    │
│   Y = (W + ΔW)X               │
└───────────────────────────────┘
    │
    ▼
  输出 Y

几个关键点：

  • W 冻结：requires_grad=False，不参与更新；
  • A、B 是新增的独立参数：初始 A 随机、B 为 0（保证开始时 ΔW=0，模型输出不变，训练平滑起步）；
  • 训练完成存下的是 A、B 两个小文件（几十~几百 MB 内，远小于模型本体），换任务只需换"补丁包"，底座可复用。

这解释了高效微调的"灵活"：一个底座，N 个任务的 LoRA 补丁，随时切换。

坑在哪
现象原因 / 怎么办
以为 B 初始也随机B 必须初始化为 0（否则一开始模型输出就被带偏）。看到源码里 zero-init 的 B 别奇怪，这是 LoRA 训练的稳定性设计
以为"存 LoRA 权重 = 存整个模型"保存的 peft_model 目录里是适配器配置 + A/B 权重 + 少量元数据，不是完整模型；加载时才用 base_model_name_or_path 把底座拉回来组合（第 7 章代码可见）
8⑧ LoRA 的边界：什么场景别指望它
要解决什么

前面吹了一路的省，现在浇一盆冷水：LoRA 不是万能的。知道它的三个边界，你才不会在错误场景里白折腾——这也是"懂原理"和"会抄教程"的分水岭。

核心思路

三个边界，实践中最常撞到：

边界说明规避
能力上限受底座约束LoRA 调整的是"行为/风格/任务适配"，底座不会的推理，补丁也变不出来先确认底座能力足够，再微调
低秩表达有极限任务适配方向若真的"高秩"（变化铺满整个参数空间），r 不够就学不动效果差且排除了数据问题后，把 r 加大试（64/128），再不行考虑全量
数据仍要足够且干净参数少不代表"垃圾数据也能学出好效果"数据清洗、格式、量仍是决定成败的第一位

一句话心法：LoRA 是"高效"，不是"万能"；它放大数据与底座的价值，而不是创造价值。 学完这一章，你已经具备手写 LoRA 的全部理论前提，下一章就真正开始敲代码。

坑在哪
现象原因 / 怎么办
"LoRA 效果不如全量，一定是我配置错了"数据/超参因素排除后，任务可能确实需要更高秩甚至全量。先做对照：同数据下 r=8/16/32 都试一遍，再给结论
把"LoRA 省显存"当"可以无视显存直接选大模型"装不下=跑不了，LoRA、QLoRA、梯度检查点都是"省训练开销"的手段，模型的装载大小问题依然存在（4bit 量化能再救一把）

拿到了什么为什么要紧

为什么省 99.6% 参数低秩表达能力 + 只存梯度/优化器（A、B），显存负担断崖式下降，单卡也能微调
