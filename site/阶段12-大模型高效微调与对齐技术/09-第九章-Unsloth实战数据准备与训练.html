第九章　Unsloth 实战：加载模型、数据与训练

阶段 12 · 大模型高效微调与对齐技术　|　2 课时　|　难度 ★★★
这一章在解决什么问题

环境就绪了，现在真刀真枪：用 Unsloth 完整跑一遍 DeepSeek-R1-1.5B 的 LoRA 微调——加载模型、配 LoRA 参数、准备 Alpaca 数据、SFTTrainer 训练、和手写基线对比。

1① FastLanguageModel：Unsloth 的加载入口
要解决什么

手写时用 AutoModelForCausalLM 加载，Unsloth 用 FastLanguageModel——它比 Auto 版多做了什么事？加载时 4bit 量化、max_seq_length 怎么设？

核心思路

讲义代码（整理为可运行版）：

from unsloth import FastLanguageModel
import torch

max_seq_length = 2048   # 输入输出最大长度（token 数）

# 加载模型 + 自动套用 Unsloth 优化内核，并做 4bit 量化
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/DeepSeek-R1-Distill-Qwen-1.5B",
    max_seq_length=max_seq_length,
    dtype=None,              # None=自动选择（fp16/bf16）
    load_in_4bit=True,       # 4bit 量化：显存降到约 1.8GB
)

与 Auto 加载的差异：

维度AutoModelForCausalLMFastLanguageModel
内核标准 PyTorchUnsloth 优化（第 8 章原理）
量化需另配 bitsandbytesload_in_4bit=True 一步到位
max_seq_length默认模型内定显式参数，配合 RoPE 缩放
显存标准量化 + 内核优化，整体大幅下降

max_seq_length=2048 的含义：训练时最长输入+输出合起来的 token 数。超长的样本会被截断。按你的数据最长长度设，设太大费显存、太小截断丢信息。

坑在哪
现象原因 / 怎么办
model_name 填错/找不到检查是否带 unsloth/ 前缀、名字是否拼对；网络问题用 HF 镜像（第 10 章更多）。先试官方给的 unsloth/ 镜像名，它已处理好格式
max_seq_length 设 8192 显存爆长度直接决定显存（注意力与长度平方相关）。先 2048 跑通，再按需加大
load_in_4bit=True 报 bitsandbytes 错误缺库或环境不支持。pip install bitsandbytes；Windows 原生请回第 8 章换 WSL2/Colab
2② Unsloth 的 LoraConfig：target_modules 全线性
要解决什么

手写时 target_modules 只挂 q_proj/v_proj。Unsloth 加载后，讲义用了一套"更狠"的配置：r=16 且 target_modules='all-linear'——什么意思？为什么这样反而更省显存？

核心思路

讲义代码（整理为可运行版）：

from peft import LoraConfig

model = FastLanguageModel.get_peft_model(
    model,
    r=16,                        # 秩：比手写 8 翻倍，补丁更有容量
    target_modules=["q_proj","k_proj","v_proj","o_proj",
                    "gate_proj","up_proj","down_proj"],
    # ↑ 即 'all-linear'：所有线性层全挂
    lora_alpha=16,
    lora_dropout=0,              # Unsloth 建议：dropout 设为 0
    bias="none",
    use_gradient_checkpointing="unsloth",  # 高级显存省法
    random_state=3407,           # 复现种子
)

对比要点：

  • 'all-linear'（=把所有线性层列全）：全部线性层都挂 LoRA = 补丁覆盖面大、自由度更高。看起来显存该更大？——不，量化+梯度检查点把省下来的显存补回来了，反而总占用略低于只挂 q/v 的手写方案；
  • lora_alpha=16：α=r，强度=1（不放大也不缩小），配 r=16 常用；
  • lora_dropout=0：Unsloth 官方建议 dropout=0——量化环境下 dropout 收益低还增加开销；
  • random_state：固定种子，保证"换模型/换参数"对比时结果可复现。
坑在哪
现象原因 / 怎么办
'all-linear' 报错（很老版本的 PEFT 不认识）该字符串是 PEFT 新特性。升级 peft 或升级代码里把 7 个模块名写全（讲义同时给了展开写法）
担心"全线性层都挂 = 显存爆炸"实测结论：结合 4bit + 梯度检查点，总显存并不上升——这正是 Unsloth 省显存的表现，别凭直觉放弃
dropout=0 心里发虚讲义和官方都这么建议；过拟合用"早停/数据集质量"管，别在 Unsloth 场景硬加 dropout。跟随官方推荐再谈自定义
3③ 数据集格式：Alpaca 长这样
要解决什么

第 5 章手写版用了 LaMini 数据，这一章出现新面孔：Alpaca 格式（instruction/input/output 三字段）。它长什么样、怎么构造对话/提示模板、和手写版有什么区别？

核心思路

Alpaca 数据三条记录示例（讲义风格）：

example = {
    "instruction": "请解释什么是机器学习",
    "input": "",
    "output": "机器学习是让计算机从数据中自动学习规律……"
}
  • instruction：指令（必填）；
  • input：额外上下文，可为空字符串（很多库里是可选）；
  • output：期望回答（监督标签）。

Alpaca 与 LaMini 的异同：

  • 都是"指令-回答"监督对——本质一样；
  • Alpaca 显式区分 instruction/input 两字段；LaMini 常直接给整句 QA；
  • 训练时把 instruction(+input) 拼成 prompt（系统+用户），output 是标签——模板和训练一致这条纪律不变（第 5 章 trap 依然有效）。

构造 prompt 时注意：DeepSeek-R1 系模型带特殊系统提示（让模型先想再答），需要用数据集的模板原样拼接，否则训练风格错乱。具体模板字符串以讲义/模型卡为准。

坑在哪
现象原因 / 怎么办
数据只有两列（Q/A），套 Alpaca 报错Alpaca 结构要求三字段。两列数据改成 LaMini/ShareGPT 路线（第 11 章有 ShareGPT），别硬套模板
input 字段全填了长文本，token 超长input 是"附加上下文"，别把整篇资料塞进去。短 input（或不填），长文档走 RAG 路线
拼接 prompt 时漏掉系统提示R1 系模型没系统提示会"答非所问/风格漂移"。用模型卡的 System Prompt 模板拼接（讲义里有现成常量）
4④ 复制 5 条数据做起跑：小数据先验证链路
要解决什么

上来就全量数据训练，错一个 bug 要等一小时。正确姿势：先取几十条数据跑通全链路，再放开全量。这一节讲这招和它的判断标准。

核心思路

讲义做法（整理）：

# 数据集已有 dataset["train"] 后，先小样跑通
dataset_tiny = dataset["train"].select(range(50))

# 同一套 Trainer 配置去训练
trainer = SFTTrainer(... )  # 见下一节
trainer.train()

小样验证三件事：

  1. 数据管道通：字段名、模板拼接、length 设置没报错；
  2. 训练能收敛：小样本下 loss 快速下降，说明优化器/学习率没配错；
  3. 生成能产出：训完用第 7 章的 generate 法问问它，能看到"有点样子"。

通过后再全量训：把 select(range(50)) 换回完整数据集，其余代码原样重跑。小样跑通 = 全量 90% 安全，这 10 分钟值得花。

坑在哪
现象原因 / 怎么办
小样跑通就放开全量，结果全量报 OOM全量数据更长/更多，batch 撑爆。全量首次用更小 batch 起步，平稳后再上调
小样 50 条训 1 轮看不出收敛样本太少 loss 波动大正常。先看"能生成有意义的回复"，别指望小样本 loss 平滑
小样能跑但一换数据就报错换的是脏数据（空行/超长/字段缺失）。加数据清洗（第 5 章 filter/length 检查）再全量
5⑤ SFTTrainer：一键训练 + 学习率/批次
要解决什么

数据准备好了，Unsloth 版的训练器叫 SFTTrainer（trl 库），比手写 Trainer 更省事——数据集格式、长度截断、模板拼接它大半自动处理。这一节把训练参数配置讲清楚。

核心思路

讲义典型配置（整理为可运行版）：

from trl import SFTTrainer
from transformers import TrainingArguments

trainer = SFTTrainer(
    model=model,
    tokenizer=tokenizer,
    train_dataset=train_dataset,       # 已按模板拼好 prompt 的数据
    dataset_text_field="text",         # 告诉它哪个字段是"拼接后文本"
    max_seq_length=max_seq_length,     # 自动截断
    dataset_num_proc=2,                # 多进程预处理
    args=TrainingArguments(
        per_device_train_batch_size=2,
        gradient_accumulation_steps=4,
        warmup_steps=5,                # 学习率预热
        num_train_epochs=1,
        learning_rate=2e-4,
        logging_steps=1,               # 每步打日志
        optim="adamw_8bit",            # 8bit 优化器：省显存
        seed=3407,
        output_dir="outputs",
    ),
)
trainer.train()

几个关键参数人话翻译：

  • dataset_text_field="text"：数据预处理时把 instruction/input/output 拼成 text 列，SFTTrainer 按它训练（不用再手写 preprocess 函数——这是比手写版省事的地方）；
  • optim="adamw_8bit"：8bit 优化器降显存（需要 bitsandbytes）；
  • warmup_steps=5：前 5 步学习率从小升到大，训练更稳。
坑在哪
现象原因 / 怎么办
忘了拼 text 列，报 "no text field"SFTTrainer 要整条文本。预处理时把三字段拼成 text（含系统提示模板），再喂数据集
optim adamw_8bit 报 bitsandbytes 缺失pip install bitsandbytes；或换 optim="adamw_torch"（显存略升但能跑）
logging_steps=1 日志刷屏训练轮数多时每 step 都打。改 10~50，观测平滑曲线即可
6⑥ 训练过程观察：loss 怎么看、中途怎么停
要解决什么

训练真的开跑了：进度条、loss 数字、每步日志。这一节教你看懂这些输出：loss 降到多少算正常？中途想停怎么安全停？日志里哪些信号是"坏了"？

核心思路

训练开始的输出长这样：

{'loss': 2.83, 'learning_rate': ..., 'epoch': 0.0}
{'loss': 1.96, 'learning_rate': ..., 'epoch': 0.0}
{'loss': 1.55, ...}

判读规则：

  • loss 应逐 step 下降，前几十步降得快（学习率预热+拟合开始），随后放缓；
  • 最终 loss 落在数据集语言混乱度的合理范围（参考：指令数据常见 0.5~2.5，取决于数据量/长度）；
  • epoch 数值从 0 涨到 1 = 训练完一轮。

中途停的三种方式：

方式适用
Ctrl+C（前台）想立即停，检查点已按 save_strategy 存好
等 step 结束停加 KeyboardInterrupt/脚本里手动 break 逻辑
提前结束调 num_train_epochs 低于当前轮次 + resume

注意：显存/磁盘满比"loss 不降"更常见也更危险——边跑边看磁盘余量，别让 checkpoint 写爆盘。

坑在哪
现象原因 / 怎么办
loss 先降后回升学习率冲到最优点之后震荡。降学习率/加 warmup；回升持续 = 过拟合，配合 eval 判断
loss 从第 1 步就是 NaN学习率爆表 / 数据有空样本 / 精度问题。学习率降到 1e-5 试，再查数据
磁盘被 checkpoint 写满每 epoch 存一份很快爆盘。调大 save_steps 或清理旧 checkpoint，保存策略要按磁盘量配
