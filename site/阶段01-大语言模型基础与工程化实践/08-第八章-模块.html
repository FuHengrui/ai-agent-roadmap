第八章　模块

阶段 1 · 大语言模型基础与工程化实践　|　难度 ★★★
这一章在解决什么问题

到上一章为止，你的代码全在一个 .py 文件里。但一个真实的项目不可能这样。

想一想：配置从哪读？提示词写在哪？调用大模型的代码放哪？怎么保证换个模型不用改一百个地方？

如果全塞在一个文件里，那个文件会长到 2000 行——改一个功能得滚动半天，两个人同时改必然冲突。

这一章解决最后一个层次的组织问题：把代码拆成多个文件，并且让它们互相调用。

而且这一章不只是讲语法——最后一大块是一个完整的项目（Novel 自动化生成系统）。你会看到一个真实的 AI 应用是怎么搭起来的：配置、Schema、提示词、LLM 客户端、导出、pipeline、入口。

这是阶段 1 的收官，也是你从"会写 Python"走到"能搭 AI 应用"的那一步。

1① 为什么要模块化
要解决什么

一个文件写到 1000 行，改一处要翻半天，还容易改错。怎么把代码拆开、又不拆乱？

核心思路

模块化的三层好处：

好处具体表现
职责清晰一个文件只干一类事——config.py 管配置、llm_client.py 管模型调用
能复用这个项目写的 llm_client.py，下个项目直接拷过去
改一处不惊动全局换模型只改 llm_client.py，业务代码一动不动

所谓的"设计和实现分离"就是这个意思：

# ✗ 设计和实现混在一起 # main.py 里既写着&quot;用哪个模型&quot;（设计）， # 又写着&quot;怎么发请求&quot;（实现） # # ✓ 分开 # config.py ← 设计：用哪个模型、温度多少、超时几秒 # llm_client.py ← 实现：怎么发 HTTP 请求、怎么解析响应 # main.py ← 组装：把两者接起来

判断一个模块好坏的标准：能不能用一句话说清它管什么。 说不清就说明它管太多了。

拆太碎的代价

不是越细越好。 一个 10 行的工具函数单独占一个文件，反而增加了跳转成本。

经验法则：

  • 单文件 200–500 行比较舒服
  • 超过 800 行就该考虑拆
  • 相关的功能放一起，不相关的分开
2② 模块导入：import 与 from ... import
要解决什么

"我写了 utils.py，怎么在 main.py 里用它的函数？"——四种导入方式，各有各的场合。

核心思路 
# ① import 模块名 —— 用的时候要带模块名（推荐）
import utils
utils.clean_salary("8-15K")

# ② from 模块 import 名字 —— 直接用
from utils import clean_salary
clean_salary("8-15K")

# ③ from 模块 import * —— 导入所有公开名字（不推荐）
from utils import *
clean_salary("8-15K")

# ④ import 模块 as 别名 —— 起个短名
import numpy as np
import pandas as pd

①和②怎么选？

写法好处什么时候用
import utils
utils.clean()		看得出这是谁家的函数默认用这个——尤其名字比较通用时
from utils import clean → clean()写得短名字够独特、不会撞名时

为什么 import * 不推荐？ 三个问题：

  • 不知道名字从哪来——读到 process() 完全猜不出是哪个模块的
  • 会覆盖你的变量——如果 utils 里也有个 data，你的 data 被顶掉了
  • IDE 提示会变差——静态分析不知道有哪些名字
几个必踩的坑
坑说明
文件名不能和标准库重名建一个 json.py 会让 import json 导到你自己那个，标准库就用不了了
模块名不能有中文/横线my-utils.py 导不进来（横线在 Python 里是减号）。用下划线 my_utils.py
导入是"执行整个文件"import a 会把 a.py 从头到尾跑一遍（函数定义只是"定义"，但顶层代码会执行）
循环导入a.py 导入 b.py，b.py 又导入 a.py → 报错。解法：把公共部分抽到第三个模块
3③ 导入的底层原理
要解决什么

"为什么改了模块里的代码，重跑有时候不生效？"——搞懂导入做了什么，你就能解释这类怪现象。

核心思路

import a 时 Python 做了四件事：

# 1. 在 sys.modules 缓存里找 &#x27;a&#x27; ← 找到就直接用，不重新加载 # 2. 找不到 → 按 sys.path 的顺序找 a.py # 3. 找到文件 → 执行整个文件，把里面的定义装进一个模块对象 # 4. 把模块对象放进 sys.modules 缓存，并在当前命名空间绑定名字 a

关键点：模块只会被执行一次，之后走缓存。

import utils        # 第一次：找到文件、执行、放进缓存
import utils        # 第二次：直接拿缓存，不执行

这解释了几个现象：

# 1. 为什么改模块的代码不生效？
#    因为在同一个进程里模块只加载一次。
#    交互式环境里要 importlib.reload(utils)

# 2. 为什么模块里的顶层 print 只出现一次？
#    因为只执行一次

# 3. 循环导入为什么报错？
#    因为 a 还没加载完，b 就想用 a 里的东西

if __name__ == "__main__": 为什么有用？

# utils.py
def clean(s):
    ...

if __name__ == "__main__":
    # 只有【直接运行 python utils.py】时才执行
    # 被别人 import 时不执行
    print(clean("8-15K"))

原因：

情况__name__ 是什么
直接运行 python utils.py"__main__"
被导入 import utils"utils"

这让你能"既当模块用、又能单独测试"——是 Python 项目里的标准写法，几乎每个文件都有这一段。

动态导入（用 importlib）——按字符串导入模块：

import importlib
mod = importlib.import_module("collectors.zhaopin")
klass = getattr(mod, "ZhaopinCollector")

实战用途：插件式架构——把所有平台适配器放在 collectors/ 目录，运行时按名字动态加载，加新平台不用改主程序。

相对导入的坑 
from . import utils          # 相对导入：当前包内的 utils
from .. import config        # 上一级包

相对导入只能在"包内部"用。如果你直接 python mypackage/utils.py 运行这个文件，会报：

ImportError: attempted relative import with no known parent package

原因：直接运行一个文件时，它不属于任何包。所以包内的文件不要直接跑，用 python -m mypackage.utils 或从包外面导入。

4④ 包：把模块组织成目录
要解决什么

项目大了，模块几十个，全堆在一个目录里也是一团乱。需要再上一层组织：目录。

核心思路

包 = 带 __init__.py 的目录（Python 3.3+ 严格来说可以没有，但建议加上）。

# 项目结构 # novel/ # ├── __init__.py ← 有它才算&quot;包&quot; # ├── config.py # ├── llm_client.py # ├── prompts/ # │ ├── __init__.py # │ └── templates.py # └── exporters/ # ├── __init__.py # └── txt_exporter.py

导入包里的模块：

from novel.llm_client import LLMClient
from novel.exporters.txt_exporter import TxtExporter

__init__.py 是干什么的？

它在你 import novel 时被执行，可以用来：

  • 把子模块"提"到包这一层，让导入更短
  • 声明这个包对外暴露什么（__all__）
  • 放包的版本号、初始化代码
# novel/__init__.py
"""Novel 自动化生成系统。"""

__version__ = "0.1.0"

from .llm_client import LLMClient        # 现在可以 from novel import LLMClient
from .config import load_config

__all__ = ["LLMClient", "load_config"]

为什么要"提"上来？ 用起来舒服：

# 不提：导入路径很长
from novel.llm_client import LLMClient

# 提了：短，而且以后换文件位置不影响调用方
from novel import LLMClient
模糊导入与包的注意事项

模糊导入（from novel import *）在包里更危险——它会把 __init__.py 里所有不以下划线开头的东西都拉进来。

建议：

  • 明确写 __all__，控制 import * 到底导出什么
  • 调用方尽量别用 import *
  • 目录名同样别和标准库重名（别建 json/、types/）
5⑤ pip 与第三方库
要解决什么

① Schema：用数据类定义结构

from dataclasses import dataclass, field
from typing import List, Optional


@dataclass
class Character:
    """一个角色。"""
    name: str
    role: str                      # 主角 / 配角 / 反派
    traits: List[str] = field(default_factory=list)
    background: str = ""


@dataclass
class Chapter:
    """一个章节。"""
    index: int
    title: str
    outline: str                   # 这一章要写什么
    content: str = ""              # 生成出来的正文
    word_count: int = 0


@dataclass
class Novel:
    """整部小说。"""
    title: str
    genre: str                     # 题材
    synopsis: str = ""             # 梗概
    characters: List[Character] = field(default_factory=list)
    chapters: List[Chapter] = field(default_factory=list)

为什么用 @dataclass 而不是手写 __init__？ 它自动帮你生成 __init__、__repr__、__eq__——写起来短，调试时打印还好看。

关键细节：field(default_factory=list)

# ✗ 错：所有实例共享同一个列表（第六章讲过的类属性陷阱）
traits: List[str] = []

# ✓ 对：每个实例单独创建
traits: List[str] = field(default_factory=list)

default_factory=list 就是"每次创建实例时调一次 list()"，等价于在 __init__ 里写 self.traits = []。

② LLM 客户端：把"怎么调模型"封起来

# src/llm_client.py
import time
import logging
import requests


class LLMError(Exception):
    """模型调用相关错误。"""


class LLMClient:
    """把"和大模型说话"这件事封成一个类。"""

    def __init__(self, cfg: dict):
        self.model     = cfg["llm"]["model"]
        self.api_key   = cfg["llm"]["api_key"]
        self.temperature = cfg["llm"].get("temperature", 0.7)
        self.timeout   = cfg["llm"].get("timeout", 60)
        self.base_url  = cfg["llm"].get("base_url", "https://api.deepseek.com")
        self.log = logging.getLogger(__name__)
        self.usage = {"prompt_tokens": 0, "completion_tokens": 0}

    def chat(self, prompt: str, system: str = "", retries: int = 3) -> str:
        """发一次对话请求，失败自动重试。"""
        messages = []
        if system:
            messages.append({"role": "system", "content": system})
        messages.append({"role": "user", "content": prompt})

        for attempt in range(1, retries + 1):
            try:
                resp = requests.post(
                    f"{self.base_url}/chat/completions",
                    headers={"Authorization": f"Bearer {self.api_key}"},
                    json={
                        "model": self.model,
                        "messages": messages,
                        "temperature": self.temperature,
                        "stream": False,
                    },
                    timeout=self.timeout,
                )
                resp.raise_for_status()
                data = resp.json()
                self._track(data.get("usage", {}))
                return data["choices"][0]["message"]["content"]

            except requests.RequestException as e:
                self.log.warning("第 %d 次请求失败：%s", attempt, e)
                if attempt == retries:
                    raise LLMError(f"重试 {retries} 次仍失败：{e}") from e
                time.sleep(2 ** attempt)          # 指数退避：2s → 4s → 8s

    def _track(self, usage: dict) -> None:
        self.usage["prompt_tokens"]     += usage.get("prompt_tokens", 0)
        self.usage["completion_tokens"] += usage.get("completion_tokens", 0)

这段代码里有四个值得注意的设计：

设计为什么
封成类配置、会话、统计都挂在实例上，不用到处传
失败重试 + 指数退避网络抖动很常见。2 ** attempt 让重试间隔越来越长，避免把对方打挂
raise ... from e保留原始异常链，方便定位根因
统计 token 用量AI 应用的成本就藏在这里，必须能算出来

"把模型调用封成一个类"的最大价值：将来换供应商（DeepSeek → 通义 → 本地 Ollama），只改这一个文件。 业务代码一行都不用动。

提示词与客户端的三个常见错
坑说明
把 API Key 硬编码一旦提交到 GitHub 就泄露。永远从环境变量读
不重试网络类应用不重试，等于把偶发故障变成必然失败
不统计用量跑一晚上账单出来才发现超了。要么统计，要么设置上限
10⑩ Novel 项目：导出模块
要解决什么

"生成完的东西怎么交出去？"——输出格式可能是 txt、markdown、json，而且以后可能还要加 PDF。

核心思路

用"基类定接口、子类做实现"的结构（第六章的继承用法）：

# src/exporters/base.py
from abc import ABC, abstractmethod


class BaseExporter(ABC):
    """所有导出器的父类——规定必须实现 export。"""

    @abstractmethod
    def export(self, novel, path: str) -> str:
        """把 novel 写到 path，返回实际写入的文件路径。"""
        raise NotImplementedError
# src/exporters/txt_exporter.py
from pathlib import Path
from .base import BaseExporter


class TxtExporter(BaseExporter):
    def export(self, novel, path: str) -> str:
        p = Path(path)
        p.parent.mkdir(parents=True, exist_ok=True)
        with open(p, "w", encoding="utf-8") as f:
            f.write(f"《{novel.title}》\n")
            f.write(f"题材：{novel.genre}\n")
            f.write("=" * 40 + "\n\n")
            for ch in novel.chapters:
                f.write(f"第{ch.index}章　{ch.title}\n\n")
                f.write(ch.content + "\n\n")
        return str(p)
# src/exporters/json_exporter.py
import json
from dataclasses import asdict
from pathlib import Path
from .base import BaseExporter


class JsonExporter(BaseExporter):
    def export(self, novel, path: str) -> str:
        p = Path(path)
        p.parent.mkdir(parents=True, exist_ok=True)
        with open(p, "w", encoding="utf-8") as f:
            json.dump(asdict(novel), f, ensure_ascii=False, indent=2)
        return str(p)

asdict(novel) 是 dataclasses 提供的——直接把数据类转成字典，一行搞定。

"加一种格式"要改多少代码？ 只加一个文件，其它地方一行不动。这就是"封装变化"的价值。

导出模块的三个细节
细节为什么
encoding="utf-8"不写，中文在 Windows 上会乱码
parents=True, exist_ok=True目录不存在时自动创建；已存在也不报错
返回文件路径调用方可以据此记日志、显示"已保存到 xxx"
11⑪ Novel 项目：pipeline 流程编排
要解决什么

所有零件都有了。谁先跑、谁后跑、每一步的产物给谁？——这是 pipeline 要解决的。

核心思路 
# src/pipeline.py
import logging

from .llm_client import LLMClient, LLMError
from . import prompts
from .schemas import Novel, Chapter
from .exporters.txt_exporter import TxtExporter
from .exporters.json_exporter import JsonExporter


class NovelPipeline:
    """把整个生成流程串起来。"""

    def __init__(self, cfg: dict):
        self.cfg = cfg
        self.llm = LLMClient(cfg)
        self.log = logging.getLogger(__name__)

    def run(self, idea: dict) -> Novel:
        novel = Novel(title=idea["title"], genre=idea["genre"],
                      synopsis=idea.get("synopsis", ""))

        # 第一步：生成人物设定
        self.log.info("① 生成人物设定……")
        self._build_characters(novel, idea)

        # 第二步：生成章节大纲
        self.log.info("② 生成章节大纲……")
        self._build_outline(novel, idea.get("chapters", 3))

        # 第三步：逐章生成正文（关键：单章失败不影响整体）
        self.log.info("③ 逐章生成正文……")
        self._write_chapters(novel)

        return novel

    def _build_characters(self, novel, idea):
        text = self.llm.chat(
            prompts.CHARACTER_PROMPT.format(**idea),
            system=prompts.SYSTEM_WRITER,
        )
        novel.characters = parse_characters(text)      # 解析成 Character 列表

    def _build_outline(self, novel, n):
        text = self.llm.chat(
            prompts.OUTLINE_PROMPT.format(
                n=n, genre=novel.genre, synopsis=novel.synopsis,
                characters=format_characters(novel.characters),
            ),
            system=prompts.SYSTEM_WRITER,
        )
        novel.chapters = parse_outline(text)           # 解析成 Chapter 列表

    def _write_chapters(self, novel):
        for ch in novel.chapters:
            try:
                ch.content = self.llm.chat(
                    prompts.build_chapter_prompt(ch, novel, self.cfg),
                    system=prompts.SYSTEM_WRITER,
                )
                ch.word_count = len(ch.content)
                self.log.info("   第 %d 章完成（%d 字）", ch.index, ch.word_count)
            except LLMError as e:
                # ★ 关键：单章失败【不中断】整体流程
                self.log.error("   第 %d 章生成失败：%s", ch.index, e)
                ch.content = ""
                ch.word_count = 0

    def save(self, novel, out_dir: str = "output") -> list:
        results = []
        results.append(TxtExporter().export(novel, f"{out_dir}/{novel.title}.txt"))
        results.append(JsonExporter().export(novel, f"{out_dir}/{novel.title}.json"))
        return results

pipeline 里最值得学的设计：

设计为什么
每一步单独一个方法_build_characters / _build_outline / _write_chapters——能单独测试，也能单独重跑
单章失败不中断try/except 只包住一章。这是"能跑一整晚"的关键（第七章讲的东西在这里用上了）
中间产物挂在 novel 上人物、大纲、正文都在一个对象里，随时能存成 JSON 断点续跑
日志打在关键节点明天看日志就知道跑到第几章了
导出和流程分开run() 只管生成，save() 只管落盘——职责清晰
流程编排的三个经验

① 每一步都要有"可观察的产物"——不要一口气跑到底才输出。人物生成了存一下、大纲生成了存一下。中途崩了不用从头来。

② 把"贵"的操作放后面——人物设定和大纲很便宜（几百 token），正文很贵。先跑便宜的，确认没问题再跑贵的。

③ 长流程必须能断点续跑——300 章的小说，跑到第 200 章断电了怎么办？把中间状态存盘，重启时读回来接着跑。

12⑫ Novel 项目：程序入口与测试
要解决什么

所有模块都写好了，从哪开始跑？ 入口文件要把"读配置 → 建流程 → 跑 → 存 → 报错"这套完整流程串起来。

核心思路 
# main.py
import sys
import logging
from pathlib import Path

from src.config import load_config
from src.pipeline import NovelPipeline
from src.llm_client import LLMError


def setup_logging(cfg):
    """日志同时输出到屏幕和文件。"""
    log_dir = Path(cfg["paths"]["logs"])
    log_dir.mkdir(parents=True, exist_ok=True)

    logging.basicConfig(
        level=logging.INFO,
        format="%(asctime)s [%(levelname)s] %(message)s",
        handlers=[
            logging.StreamHandler(),                                  # 屏幕
            logging.FileHandler(log_dir / "novel.log", encoding="utf-8"),  # 文件
        ],
    )


def main() -> int:
    cfg = load_config()
    setup_logging(cfg)
    log = logging.getLogger("main")

    # 输入：想写什么样的故事
    idea = {
        "title": "星海拾荒者",
        "genre": "科幻",
        "synopsis": "在废弃空间站里捡垃圾的少女，意外唤醒了旧时代的战舰 AI。",
        "chapters": 3,
    }

    log.info("开始生成《%s》", idea["title"])
    log.info("模型：%s", cfg["llm"]["model"])

    try:
        pipeline = NovelPipeline(cfg)
        novel = pipeline.run(idea)
    except LLMError as e:
        log.error("生成失败：%s", e)
        return 1
    except KeyboardInterrupt:
        log.warning("用户中断")
        return 130                     # Ctrl+C 的标准退出码

    files = pipeline.save(novel, cfg["paths"]["output"])
    u = pipeline.llm.usage
    total = u["prompt_tokens"] + u["completion_tokens"]

    log.info("完成！共 %d 章", len(novel.chapters))
    for f in files:
        log.info("  已保存：%s", f)
    log.info("Token 用量：输入 %d / 输出 %d / 合计 %d",
             u["prompt_tokens"], u["completion_tokens"], total)
    return 0


if __name__ == "__main__":
    sys.exit(main())

入口文件的五件事，缺一不可：

做什么为什么
读配置参数不该写死在代码里
配日志出问题要有据可查
准备好输入明确"要生成什么"
捕获顶层异常别让用户看到一屏 Traceback
汇报结果和成本生成了几章、花了多少 token——用户想知道这个

注意 main() 返回退出码，sys.exit(main()) 把它传给操作系统：

退出码含义
0成功
1出错（脚本可以据此判断）
130被 Ctrl+C 中断（Linux 惯例）

这个约定在自动化里很重要——定时任务、CI/CD 都靠退出码判断成功失败。

__main__ 守护——让 main.py 既可以直接跑，也能被别的脚本导入：

if __name__ == "__main__":
    sys.exit(main())
测试与调试的三条经验

① 先跑最小规模——先生成 1 章，确认流程通了，再跑 3 章、10 章。别一上来就跑 100 章。（这个项目的费用是按 token 算的）

② 每一步的产物都存下来——人物、大纲、正文都写文件。出问题时能看是哪一步的产物不对。

③ 先用假数据测流程——把 LLMClient.chat 临时替换成返回固定字符串的函数，能在不花钱的情况下把流程跑通：

class FakeLLM:
    def chat(self, prompt, system="", retries=3):
        return "第1章 测试\n\n这是测试正文。"

pipeline.llm = FakeLLM()          # 注入假客户端，零成本调试

这个技巧叫「依赖注入」——把"用哪个客户端"从外部传进来，测试时就能换成假的。这是单元测试的基础，也是写可测代码的关键。
