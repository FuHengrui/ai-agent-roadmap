第九章　GRU与双向RNN

阶段 22 · 自然语言处理与Transformer架构　|　RNN演进　|　难度 ★★★
这一章在解决什么问题

LSTM 效果好但参数多：三个门四套矩阵，训练又慢又容易过拟合。能不能"减配不减效"？另外，一句话的意思往往后面的词也能帮我们理解前面的词——"我在河边遛狗"里，读完才知道"bank"应该是河岸。这一章两手抓：GRU 把门砍到两个、双向 RNN 让每个位置同时看前后文，两个都是 RNN 家族里的"高性价比"升级。

开始之前

沿用前面的 PyTorch 环境，不用装新东西；上一章 LSTM 的三个门要能说出来。

学到这儿就够了

能说清 GRU 比 LSTM 少哪个门、双向 RNN 怎么拼前后文，能判断什么任务该用双向，这章就算过了。

上一章→本章→下一章 上一章 LSTM 解决了记忆问题但代价是参数多、只能单向。本章做两道减法与一道加法：GRU 精简门控、双向 RNN 引入后文信息。下一章进入模型级升级：Seq2Seq 把 RNN 组装成"编码器-解码器"，正式开启机器翻译这条线，再往后就是注意力机制登场。
1① GRU 的动机：LSTM 的三个门是不是有点多？
要解决什么

LSTM 效果好但参数多，能不能用更少的结构达到接近的效果？

核心思路

GRU（Gated Recurrent Unit，门控循环单元，2014） 是 LSTM 的精简版，核心思想：把"遗忘门 + 输入门"合并成"更新门"，砍掉细胞状态 C，只用隐藏状态 h 一条通道。

两个门：

  • 更新门 z_t：决定隐藏状态"保留多少旧记忆 + 吸收多少新信息"（一扇门同时管遗忘和写入）。
  • 重置门 r_t：决定"旧记忆多大程度参与候选值的计算"。

计算：

z_t = σ(W_z·[h_{t-1}, x_t])
r_t = σ(W_r·[h_{t-1}, x_t])
h_cand = tanh(W·[r_t * h_{t-1}, x_t])   # 候选新状态
h_t = (1 - z_t) * h_{t-1} + z_t * h_cand  # 旧新加权

效果：参数量约为 LSTM 的 3/4，训练更快、更不容易过拟合，而任务效果通常持平或接近——是"性价比"极高的 RNN 单元。

坑在哪
现象原因 / 怎么办
以为 GRU 一定不如 LSTM实测两者在多数任务上接近，GRU 更省资源；效果优先时两个都试，选验证集好的
把 z 和 r 的作用记反z 管"旧新各占多少"（合并遗忘+写入），r 管"旧记忆是否参与候选计算"
2② 更新门与重置门的直觉
要解决什么

"更新"和"重置"在实际语义操作上分别是什么？

核心思路

用"读小说记笔记"打比方：

  • 更新门 z 大：新信息重要，隐藏状态大幅更新（旧笔记退后，新笔记上前）。
  • 更新门 z 小：话题没变，保持旧状态为主（"他继续说……"）。
  • 重置门 r 小：当前句与上下文无关（新段落开始），候选状态"清零重来"。
  • 重置门 r 大：完全基于旧记忆 + 当前输入合成候选。

正是"一扇门管全局更新、一扇门管候选生成",GRU 才能在两个门里完成 LSTM 三个门九成的活。

坑在哪
现象原因 / 怎么办
以为 GRU 门更"弱"门数少但耦合设计精巧，局部信息流依靠两门配合，理解"配合"而非"各自为政"
写代码时把两门权重混用每个门有自己的 W_z/W_r，别复用同一套参数
3③ GRU vs LSTM：一张表选型
要解决什么

实战中 GRU 和 LSTM 到底怎么选？

核心思路
维度LSTMGRU
门数量3（遗忘/输入/输出）2（更新/重置）
状态通道C（细胞）+ h（隐藏）仅 h
参数量多（约 4 组矩阵）少（约 3 组矩阵）
训练速度慢快
过拟合风险略高（小数据明显）略低
效果长依赖更强一点多数任务持平
推荐场景超长文本、复杂时序数据量中等、资源有限、快速迭代

选型口诀：资源紧或数据小优先 GRU；序列超长、任务复杂且资源充足时可上 LSTM；纠结的话两者各跑一版，用验证集分数说话。

坑在哪
现象原因 / 怎么办
迷信"LSTM 一定更强"论文与工程都显示多数任务差距很小，GRU 的省资源优势在工业界更常用
不跑实验直接拍板单元选择是典型的"试了才知道"，固定其他条件只换单元对比 loss 与指标
4④ 双向 RNN 的动机：只看前文不够
要解决什么

"我在银行工作"要理解 bank，其实后面的"工作"同样关键——单向 RNN 漏了什么？

核心思路

单向 RNN 每个位置只能看到左侧（过去）的信息，但很多语义判定依赖右侧（未来）：

  • 词性："I bank the boat"（动词）vs "the bank of the river"（名词），后文决定词性。
  • 命名实体："Apple" 后面跟 "company" 才知道是公司而非水果。
  • 句法：主谓一致、指代消解常需后文佐证。

双向 RNN（Bi-directional RNN, BiRNN） 的做法：跑两个 RNN——一个从左往右、一个从右往左，每个位置把两个方向的隐藏状态拼接：

h_t = [h_t^forward ; h_t^backward]

这样每个位置的表示就同时携带了全句上下文（前向看过去、后向看未来）。

坑在哪
现象原因 / 怎么办
以为双向=模型看到"未来答案"训练时全句已知所以双向合法；但注意：自回归生成（如翻译逐词输出）不能双向，因为生成时未来还不存在
忘了两个方向参数独立前向/后向是两套独立权重，拼接 h 而非相加
5⑤ 双向 RNN 的结构细节
要解决什么

双向 RNN 的具体网络怎么搭？输出怎么组织？

核心思路

结构分三层看：

  1. 前向 RNN（forward）：按 t=1→T 处理，得 h_t→。
  2. 后向 RNN（backward）：按 t=T→1 处理，得 h_t←。
  3. 拼接：每个位置 h_t = concat(h_t→, h_t←)，维度翻倍（hidden*2）。
import torch.nn as nn

rnn = nn.LSTM(
    input_size=64,
    hidden_size=96,
    bidirectional=True,   # 关键开关
    batch_first=True,
)
import torch                        # 本节的 torch.randn 要用
x = torch.randn(8, 20, 64)          # [batch, seq, embed]
out, (h_n, c_n) = rnn(x)
print(out.shape)  # [8, 20, 192] = 96*2，双向拼接

bidirectional=True 一个参数搞定；注意输出最后一维 = hidden × 2，接 Linear 层时要对齐维度。

坑在哪
现象原因 / 怎么办
忘记输出维度翻倍拼接后最后一维是 hidden*2，后面 fc 层输入维度必须写对，否则 shape 报错
用双向 LSTM 做生成生成/自回归任务（逐词产出且未来未知）只能用单向；理解类任务（标注、分类）才能双向
6⑥ 双向 RNN 的两个正确用法（以及为什么不能用来生成）
要解决什么

读句子时"后面的词能反过来帮前面"——双向 RNN 吃的是整句；但这也决定了它不能用于逐词生成。

核心思路

一个经典案例：用双向 RNN 辅助生成。办法是"先生成后一半，再回头生成前一半"：

  1. 给定歌词的后半句骨架（如"……意绵绵"），后向 RNN 从右往左"倒着写"前半句。
  2. 再或反向：前向给出前半句，让模型续后半句时可参考后向已生成内容。

核心洞察：歌词的押韵与对仗是"双向约束"——"举头望明月"后面能接"低头思故乡"，因为要照顾前后呼应。双向结构让"我的今日子、都要配你的明样子"这类约束可被建模。

代码演示维度：双向拼接后最后一维翻倍，接一个 Linear 输出词表概率即可，训练目标仍是"预测下一个字符"，只是每个位置的上下文变全了。

坑在哪
现象原因 / 怎么办
以为双向能"提前看到答案"用于生成生成时看不到未来，双向的收益是用在"给已有序列补全"或理解类任务上；纯自回归生成仍单向前向
双向生成左右拼接口不齐工程上要约定"生成到句中央对接"的策略（停符检测、长度约束），否则两半对不上
7⑦ 实战：把 RNN 歌词生成升级成双向
要解决什么

上一章的歌词生成器，怎么改造成双向版本？

核心思路

改动极小，核心就两处：

import torch.nn as nn

# 1) 单向 -> 双向
self.rnn = nn.LSTM(
    embed_dim, hidden_dim,
    batch_first=True,
    bidirectional=True,   # 加这一行
)
# 2) 输出维度对齐：hidden*2
self.fc = nn.Linear(hidden_dim * 2, vocab_size)

注意 bidirectional=True 后 LSTM 返回的 out 维度是 [batch, seq, hidden*2]，所以 Linear 输入要写 hidden*2；h_n/c_n 形状变成 [num_layers*2, batch, hidden]（前向+后向各一组）。

但别拿它做歌词生成：双向的 out[t] 里混进了 x[t+1] 以后的信息，而那正是要预测的目标——训练 loss 会假性趋零，推理时又拿不到未来，分布完全对不上。双向只用于「整句已知」的任务：分类、序列标注、给候选句打分/排序。

所以正确用法是这两类：情感分类/序列标注（整句已知，要每个位置都有上下文），以及候选打分（先生成若干句，再用双向模型给它们排序）。生成模型本身保持单向。

坑在哪
现象原因 / 怎么办
fc 输入维度仍写 hidden双向后最后一维翻倍，忘了改就 shape mismatch
初始化 h0/c0 形状写错双向层数按 num_layers*2 算，手动初始化状态时别搞错
8⑧ 从 RNN 到注意力：这一条线的终点
要解决什么

GRU、双向 RNN 都学了，为什么这条线最后要走向"注意力"？

核心思路

把 RNN 家族的问题收敛一下：

  • 顺序计算 → 无法并行，长文本慢。
  • 信息压缩 → 无论多长，最后都得"塞进一个向量"，信息必然损失（这就是编码器瓶颈）。
  • 距离衰减 → 即便 LSTM/GRU，超长依赖依然吃力。

注意力机制（第十一章）让每个词直接"看到"所有其他词：不需要顺序传递、不需要压缩进单一向量、一步直达任意远距离——同时解决三个问题。这正是一个范式转变：从"一步步传递记忆"到"全位置直接互联"。学完 GRU 与双向 RNN，你已经站在 RNN 这条线的终点，接下来就换引擎了。

坑在哪
现象原因 / 怎么办
以为注意力要淘汰所有 RNN 知识编码器的"位置/顺序"概念、掩码思想在 Transformer 里全保留，只是实现方式换了
跳过本阶段直接看 Transformer先理解"RNN 有什么做不到的"，才能理解"注意力为什么好"，顺序学习效果最佳

本章小结

本章完成 RNN 家族的最后两块拼图：

问题答案
GRULSTM 精简版：合并门为更新/重置两个门，去掉 C
GRU vs LSTM参数更少更快，效果接近；小数据优先 GRU
双向 RNN 动机后文影响前文理解（词性/实体/句法）
双向结构前向+后向两个 RNN，每位置拼接 h
维度变化输出最后一维 hidden*2，fc 要对齐
适用边界理解类任务可双向；自回归生成只能单向
最终走向顺序/压缩/距离三大短板 → 注意力机制

一句话记住本章：GRU 把三个门精简成两个、去掉细胞状态，快省而不失手；双向 RNN 让每个词同时吃到前后文，理解类任务明显受益（生成任务除外）；它们把 RNN 的能力打磨到极限后，也把"顺序计算、压缩失真、距离衰减"三大天花板摆到了台面上——下一章注意力机制就是来拆天花板的。
