第一章　项目全景与技术选型

阶段 9 · 智能运营平台　|　实践　|　难度 ★★★
这一章在解决什么问题

做内容运营的人每天卡在四件事上：选题靠刷（刷热搜刷到眼花）、文案靠憋（憋一小时写出三百字）、配图靠找（图库翻半天还怕侵权）、发布靠手动（一个个平台复制粘贴）。一天最多两三篇，还容易撞选题、踩敏感词、被限流。

本章要做的「智能运营平台」，把这四道手工关卡收进一条流水线：你输入一个主题或一句灵感，AI 帮你出选题、写文案、配图，最后点一下发布——原本一下午的活压到十几分钟。

学完这一章，你手里会有一张完整系统蓝图：这个平台由哪几个模块组成、为什么这么选技术、数据在哪些表之间流动。后面十一章做的都是这张图上的一块拼图。

这一章在整个知识库里的位置 上一章（阶段 8 · AI Agent 智能体与多模态应用）：你已经会用 LangChain / LangGraph 搭 Agent、接工具、管记忆 本章 ← 你在这里：看清「AI 运营平台」的全景——四个模块、八张表、一条 Agent 流水线 下一章：数据库设计与初始化——八张表怎么建、字典表怎么填、连接怎么配 再往后：后端骨架（uv + FastAPI）→ 数据模型与 Aerich 迁移 → JWT 登录 → 前端联调 → 接 Coze → 选题落库 → 文案创作 → 配图与发布 阶段终点：跑通「输入主题 → 选题 → 文案 → 配图 → 发布记录」的整条闭环
1① 真实痛点：内容运营的四道手工关卡
要解决什么

先弄清楚「为什么要做这个系统」，后面的技术选型才有着落——技术是给痛点买单的。

核心思路

一个运营同学每天的动作，拆开看是四段，每段都在耗人：

关卡手工做法痛在哪
选题刷热搜、翻同行、凭感觉不知道哪个题能火；同一个题反复做，自己先腻了
文案对着空白文档憋风格不稳定；一不小心写了敏感词，被限流还不知道为什么
配图图库翻找 + 自己拼找图慢、风格不统一、版权有风险
发布各平台手动上传重复劳动；发完就忘，数据也不回看

这四段的共同点：每段都要人从头做一遍，下一篇文章还是从零开始。系统的价值不是"替人写一篇文章"，而是把经验沉淀下来——上一次的选题、文案、图、发布数据都留在库里，下一次可以复用、可以对比、可以迭代。

坑在哪
现象原因 / 怎么办
一上来就想"全自动无人值守"发布这一步涉及账号风控，全自动风险高；先做半自动（AI 出稿 + 人工确认 + 一键发布），跑顺了再谈提效
把系统做成"AI 聊天框"聊天框不解决问题；运营要的是结构化的产物（选题列表、文案、配图、发布记录），所以核心是表结构和流程，不是对话
2② 四大功能模块拆解
要解决什么

一个完整产品不可能一把梭，先把「这个系统到底有哪些能力」列成清单，后面开发才有验收依据。

核心思路

按用户的使用顺序，平台分四块：

模块具体能力落在哪一层
热搜灵感与选题实时热搜检索与推荐、已有主题复用、行业热点采集、标题灵感生成Coze 选题智能体 + 后端 API 落库
文案编导一键生成平台风格文案、控制情绪/语气/长度、敏感词与限流词检测、历史文案复用大模型调用（DashScope）+ 敏感词规则
图片生成与排版多风格配图一键生成、封面图与内文图批量产出、尺寸与用途区分文生图模型 + 阿里云 OSS 存储
发布与历史管理一键发布、多账号管理、发布记录追踪、历史笔记复用、素材库后端发布记录表 + 前端管理页

记住这张表的作用：它是需求地图。后面每章做完一件事，你都能回到这里打勾——不会写着写着忘了"我在做哪个功能"。

3③ 技术选型：十四项，分四类看
要解决什么

技术栈要在动手前一次定清楚，避免中途换框架导致返工。

核心思路

把十四项按"干什么用"分四类，比平铺更能记住：

类别技术用途
语言与工程Windows 11、Cursor / VSCode、Python 3.12、uv开发环境与依赖管理（uv 比 pip + venv 快得多）
Web 与数据FastAPI、Uvicorn、Tortoise-ORM、MySQL 8 + Navicat、Aerich接口、服务、异步 ORM、数据库、表结构迁移
平台能力Coze（Agent 编排）、DashScope（模型调用）、阿里云 OSS + python-multipart（文件上传）把这几个"重能力"外包出去，不自己造
安全与调试JWT（登录鉴权）、Postman（接口调试）认证与联调

一句话概括选型逻辑：自己写业务和表结构，把大模型能力外包给平台。

现象原因 / 怎么办

Python 版本不对，异步驱动装不上3.12 是硬要求；uv python pin 3.12 固定解释器版本
4④ 架构：三层结构 + 一个"外挂大脑"
要解决什么

动手前心里得有一张静态结构图：知道哪段代码摆在哪一层，出问题去哪找。

核心思路

                    │ HTTP /api（JWT 鉴权）

关键认知：Agent 不在你的 Python 代码里，而在 Coze 平台上。后端负责"收请求、存结果、管权限"，生成类的活交给平台，通过 API 调。这样模型换代、提示词调整都不用改后端。

坑在哪
现象原因 / 怎么办
前端直接调 Coze，绕过自己的后端会丢掉鉴权、丢掉落库、留不住历史记录；所有调用必须经后端中转
把 OSS 的 AccessKey 写进前端等于把存储桶公开；密钥只放后端 .env，前端只拿后端返回的临时 URL
5⑤ 为什么接 Coze，而不是自己写一套 Agent
要解决什么

你上一阶段已经会写 LangGraph 了，那为什么这里要用平台？想清楚这个问题，才知道这套架构的取舍。

核心思路

两条路的对比：

维度自己写（LangGraph）用 Coze 平台
上手速度慢，要处理重试、超时、上下文快，可视化拖节点，提示词即改即用
迭代成本改逻辑要改代码、重启服务平台上改完直接生效，不碰代码
可观测要自己接日志与追踪平台自带运行记录与调试面板
灵活性高，任何逻辑都能写受平台能力约束（自定义代码块有限）
适合谁需要深度定制、要嵌入自有系统运营同学自己就能调提示词、换模型

本阶段的定位是"业务系统 + 外挂 Agent"：业务流程（落库、权限、发布记录）自己写，创作能力（选题、文案、配图）交给平台。所以选 Coze。

坑在哪
现象原因 / 怎么办
Agent 返回的 JSON 解析失败平台输出是"自然语言 + 可能夹代码块"，后端要容错解析（去围栏、找第一个 { 到最后一个 }），并在失败时返回可读错误
同一请求调两次，结果完全不同生成类接口本来就不幂等；需要落库的操作用任务 ID 去重，别让前端重试把库写脏
6⑥ 数据流：一篇内容在八张表之间怎么走
要解决什么

这套系统的骨架不是代码，是表之间的一条链。先把链路想清楚，第二章建表才不会乱。

核心思路

一条内容从灵感到发布，经过五步、落到八张表：

① 用户提主题        → t_sections（选题组：原始主题 + 分类）
② AI 出标题列表     → t_titles（标题、排序、状态）
③ 生成正文          → t_titles.content + status
④ 生成/上传配图     → t_title_images（正文图 / 封面图 / 缩略图）
⑤ 发布并记录        → t_publish_records + t_publish_images
                      t_style / t_models 是字典表，全程被引用

两个要点：

  1. 选题与标题是两层：t_sections 是"一个方向"，下面挂多个 t_titles。"AI 减肥"是 section，"我靠这三个动作瘦了十斤"是 title。
  2. 发布是独立的一层：同一篇内容可以发多个平台，所以发布数据不能塞进 t_titles，要单开 t_publish_records（一个 title 对多条记录）。
坑在哪
现象原因 / 怎么办
把图片 URL 直接塞进 t_titles一篇内容有封面 + 多张正文图，塞一个字段必然不够；图片单独成表，用 title_id 关联
发布状态和内容状态混成一个字段内容状态（未生成/已生成/已发布/已废弃）与发布状态（待发/发布中/成功/失败）是两件事，混用后无法区分"发布失败"和"还没写"
7⑦ 十二章路线图：哪些在复用、哪些是新东西
要解决什么

先盘点"哪些我会、哪些我不会"，把精力花在增量上，别把时间浪费在重复劳动里。

核心思路
章做什么性质

Aerich 和手写 SQL 混着用一旦用 Aerich 管版本，表结构变更就走迁移命令（aerich migrate / upgrade），不要两边都改
8⑧ 交付物与验收标准
要解决什么

知道"做完长什么样、怎么算跑通"，避免闷头写完发现方向偏了。

核心思路

阶段结束时应能演示这条链路：

验收项标准
