1① 文案 Bot 的人设：小红书笔记正文生成器
要解决什么

文案不能"泛泛而写"，要符合小红书调性：口语化、有情绪、有 emoji、带引导互动。人设就是这条标准的定义。

核心思路

文案 Bot（BOT_ID_CONTENT）人设核心（提炼版）：

你是一位拥有10年小红书运营经验的爆款笔记作者。
根据给出的标题，生成一篇 220-420 字的小红书笔记正文，要求：
- 语言口语化、亲和有网感；
- 适度使用 emoji 与表情符号，增加视觉节奏；
- 结构：开头吸引 → 正文干货/故事 → 结尾引导点赞收藏关注；
- 禁止广告法违禁词（最、第一、绝对等），禁止夸大功效。

设计要点：

  • 字数区间（220-420）硬约束：太短没干货，太长读者流失，区间承载了平台对"内容规格"的定义；
  • 网感要素可枚举（emoji、对话感、punchline），让人设可执行而非空话；
  • 输出也是纯正文（方便直接存 content 字段），结构与第 8 章选题 Bot"JSON 收口"不同——按任务性质定制输出协议。
坑在哪
现象原因
文案带"标题：xxx"前缀或开头复述标题人设没写"直接输出正文，不要标题、不要编号"；补一条输出约束
生成正文超 420 字很多只说了"220-420 字"但没强调"严格"，模型倾向写长；写"超长会被截断，务必控制在区间内"
文案出现"作为AI模型我无法…"文案人设语气不到位；用"你是有10年经验的小红书作者"身份压制 AI 自述
2② /copy 接口：按标题生成文案
要解决什么

前端素材页点某标题的"生成文案"，后端要调文案 Bot 并把结果存回 t_titles.content。

核心思路 
@router.post("/copy")
async def copy_content(title_id: int, user_id: int = Depends(get_current_user_id)):
    title = await Title.filter(id=title_id, user_id=user_id).first()  # 先确认归属
    if not title:
        raise HTTPException(404, "标题不存在")
    text = await content_creation(title.title)     # agent 层调文案 Bot
    if not text or not text.strip():
        raise HTTPException(500, "文案生成失败，请重试")
    title.content = text
    title.status = "1"                             # 1=已生成
    await title.save()
    return {"code": 200, "data": {"id": title.id, "content": title.content}}

三个要点：

  1. 归属校验：filter(id, user_id=user_id) —— 防越权改别人的标题（一石二鸟：404 vs 403 语义，本项目用 404 防"枚举探测"）；
  2. 状态机推进：生成成功才把 status 从 0 置 1；
  3. 返回 id+content 让前端直接渲染新文案。
坑在哪
现象原因
用 title_id 直接查，改到了别人数据查询必须带 user_id 归属条件，否则越权（IDOR 漏洞）
文案 Bot 返回空/失败但 status 已置 1必须先验证 text 非空再改状态；顺序写反会留下"已生成但没正文"的记录
不清楚该用 /copy 还是别的路径文案生成统一走 /copy，与 /start（选题）职责分开，别复用
3③ title 详情与重置：编辑管理的基本盘
要解决什么

用户要看这条标题的现状、要重新生成（覆盖）——详情与重置两个接口。

核心思路 
# 详情：单条标题的完整信息
@router.get("/title/{title_id}")
async def title_detail(title_id: int, user_id: int = Depends(...)):
    title = await Title.filter(id=title_id, user_id=user_id).first()
    if not title: raise HTTPException(404, "标题不存在")
    return {"code": 200, "data": {
        "id": title.id, "title": title.title,
        "content": title.content, "status": title.status,
        "view_count": title.view_count, "like_count": title.like_count,
    }}

# 重置：清空文案回到"未生成"
@router.post("/title/{title_id}/reset")
async def title_reset(title_id: int, user_id: int = Depends(...)):
    title = await Title.filter(id=title_id, user_id=user_id).first()
    if not title: raise HTTPException(404, "标题不存在")
    title.content = None
    title.status = "0"
    await title.save()
    return {"code": 200, "message": "已重置"}

细节：重置是"软操作"——不删记录只清字段+回状态，保留标题本身（可选/重置类比第 2 章状态机 3=已废弃，重置 = 回到 0）。

4④ 保存编辑：用户手改的文案怎么落库
要解决什么

AI 文案通常要人工微调，"save-copy"提供保存入口：用户把改好的正文存回数据库。

核心思路 
@router.post("/save-copy")
async def save_copy(title_id: int, content: str, user_id: int = Depends(...)):
    title = await Title.filter(id=title_id, user_id=user_id).first()
    if not title: raise HTTPException(404, "标题不存在")
    if not content or not content.strip():
        raise HTTPException(400, "正文不能为空")
    title.content = content
    title.status = "1"                # 手工保存也视为"已生成"
    await title.save()
    return {"code": 200, "message": "保存成功"}

与前一个拷贝接口共享同一落库逻辑——提取一个 _update_content(title, text) 工具函数，重置/生成/保存三处复用，避免"三份差不多的代码三个不同 bug"。

坑在哪
现象原因
保存接口允许空正文参数校验（strip 后非空）必须在服务端做，前端校验可绕过
生成/保存/重置三处状态逻辑不一致状态转移收敛到一个函数处理（set_status 帮助函数），统一"0→1"规则
手改的内容没保存就刷新属前端 UX 责任——切换标题/刷新前未保存提示（Element Plus 的 beforeunload/路由守卫）
5⑤ 风格列表接口：配图的风格从哪来
要解决什么

下一章配图要选"风格"（第 2 章 t_style 种子数据），先做一个只读接口把风格列表供给前端下拉。

核心思路 
@router.get("/styles")
async def styles():
    rows = await Style.all().order_by("id")
    return {"code": 200, "data": [
        {"id": s.id, "name": s.name, "fengge": s.fengge} for s in rows
    ]}

说明：

  • 风格是全平台共享配置（不是按用户隔离的），所以不加 user 过滤——与 /themes 形成对照；
  • fengge 字段就是文生图提示词片段，前端不直接展示给用户选（用户选 name，后端拼 fengge）。

⚠️ 注意与第 5 章 GET /v1/test/styles 的区别：那是"测试路由"，这里是"业务路由"。同一数据源，两个入口的场景不同（测试 vs 实际使用），别在业务代码里调用 test 接口。

6⑥ 状态机的完整流转
要解决什么

status 字段从 0 到 3 的每一步谁在改？梳理清楚，前端徽标才能准确。

核心思路 
0 未生成  --(/copy 生成成功/ save-copy 保存)-->  1 已生成
1 已生成  --(reset)--> 0 未生成
1 已生成  --(发布成功, 第 12 章)--> 2 已发布
1/2 已生成  --(人工废弃)--> 3 已废弃

规则：

  • 顺向流转靠业务动作（生成/保存/发布/废弃）；
  • reset 只能从 1 回 0（未生成不能 reset，已发布不能 reset）；
  • 已发布（2）后内容冻结——再改文案应新开一条或先废弃。

把这张表写进后端"状态变更守卫"（一个函数里 switch 校验），前端与后端各持一份一致枚举。

坑在哪

状态守卫只做"校验"不做"隐式转换"：非法的流转（如已发布回 1、未生成 reset）直接抛 400，而不是静默吞掉或顺手帮他改状态。隐式转换会让前端看到的状态永远对不上，排查时最坑；后端枚举跟前端各持一份还要配注释说明谁在什么时候改 status。

7⑦ 联调验收：文案模块的完整动作流
要解决什么

文案功能好不好用，用一条"真实用户路径"验收：从选标题到改稿保存。

核心思路

验收剧本：

  1. 素材页点某标题 → GET /v1/create/title/{id} 返回细节；
  2. 点"生成文案" → POST /v1/copy（等待 10-30s，显示 loading）→ content 出现、status=1；
  3. 点"重新生成"→ 再次 /copy → content 被覆盖；
  4. 手动改正文 → POST /v1/save-copy → 刷新页面内容仍在；
  5. 点"重置" → content 清空、status=0；
  6. 下拉风格列表 → GET /v1/create/styles 有条目。

判定通过 = 六步全部符合预期且刷新后数据一致。任一步异常，按接口顺序排查：路径 → 鉴权 → 归属校验 → agent 调用 → 落库。

本章小结

  • 文案 Bot 人设：220-420 字、口语化、emoji、引导互动、禁违禁词——内容是"规格化"产物
  • /copy 接口：归属校验（防 IDOR）→ 调 AI → 验证非空 → 更新 content + status=1
  • 详情 /title/{id} 与 重置 reset：软操作（清字段回状态），不删记录
  • save-copy：人工改稿落库，服务端强制非空校验
  • 风格接口 /styles：平台共享配置，不加用户过滤；与测试接口区别使用
  • 状态机：0↔1 可逆、1→2 发布冻结、可弃为 3；变更收敛到统一守卫函数
  • 联调剧本六步：详情/生成/重试/保存/重置/风格，刷新校验一致性
  • 编辑态与保存态分离：脏标记 + 显式保存 + 离开拦截，保存成功才清脏

8⑧ 编辑态与保存态的边界：脏标记与未保存提示
要解决什么

用户手动改了文案，没保存就切走/刷新——改的内容全丢，是最伤体验的坑。前端需要一个"编辑态"机制。

核心思路

关键设计（前端职责，与后端 save-copy 配合）：

  1. 脏标记（dirty flag）：进入编辑后，对原文做一次深比较，发生差异即标记"已修改"；
  2. 保存动作显式化：只有点"保存"才调 POST /v1/save-copy，编辑中不自动提交——避免每次敲键盘都打接口；
  3. 离开拦截：有脏标记时，切标题/刷新/跳路由前先提示"有未保存的修改，确定离开？"（路由守卫或 beforeunload）；
  4. 保存成功清脏：save-copy 返回成功后才清除脏标记，防止"以为存了其实失败"。

边界："重置"与"未保存修改"是两件事——重置清的是数据库里的 content（后端操作），脏标记管的是前端编辑框里的临时状态。前端先确认是否丢弃本地修改，再决定是否调 reset。

坑在哪
现象原因
改完没保存切走，内容丢了没有脏标记 + 离开拦截；改多少丢多少
每次输入都发请求把"编辑"当"保存"；保存必须由显式按钮触发
save-copy 失败但页面显示已保存不清脏标记、不提示失败；保存返回才更新 UI 状态
