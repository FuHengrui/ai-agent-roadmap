第十一章　定时任务、Web 仪表板与常用命令

阶段 15 · Hermes-Agent 自我进化的超级智能体　|　平台实操　|　难度 ★★★
这一章在解决什么问题

前面十章，Agent 都是"被召唤才干活"：你发消息它才动。但一个"自我进化的超级智能体"，凭什么不能主动干活？ 每天早上自动给你推今日待办、每周五自动汇总本周项目进展、监控某个网页变化就提醒你——这些"没人盯着也会发生"的能力，来自定时任务（Cron）。

同时，Agent 的"后台状态"你一直靠命令猜：它在忙什么？服务器在线吗？日志有没有异常？Web 仪表板给你一块可视化控制屏，浏览器打开就能看。最后把散落的命令收个总——这一章是 Hermes 的"自动化 + 可视化 + 命令大全"收官章。

学完这一章，你能回答：三种 Cron 调度模式怎么选、/cron 命令怎么用、网关的 60 秒轮询机制怎么回事、Web 仪表板怎么打开、以及 20+ 常用命令的分类使用。学完这一章，Hermes 从"你指挥的助手"晋级为"会自己上班的伙伴"。

这一章在整个知识库里的位置 上一章（第十章）：MCP——能力外接，底座无限。 本章 ← 你在这里：定时任务（自动化）+ Web 仪表板（可视化）+ 常用命令（操作大全），闭环收官 阶段终点：人格（SOUL）→ 行动（工具）→ 流程（技能）→ 记忆 → 外观 → 扩展 → 自动化。第 12 章进入强化学习与对齐（如课程有）或毕业实操
学习提示

本章是三合一，容易散。抓住主线："主动"两字——Cron 让 Agent 主动开工，仪表板让你主动掌握状态，命令让你主动操控一切。三个都是"从被动到主动"的进阶。

1① 定时任务：把"提醒我"变成"自动执行"
要解决什么

"每天早上 8 点给我推送今日摘要""每周末汇总本周进展"——这种周期性需求，靠手发消息会被遗忘，靠记忆不靠谱。定时任务就是为"无人值守的周期执行"而生的。

核心思路

定时任务（Cron Job） 让 Hermes 在指定时间自动执行任务并（可选）推送结果。它与"对话"的本质区别：

维度对话定时任务
触发你发消息时间到（cron 表达式）自动触发
交互实时多轮无人值守，执行+（可选）投递
场景一切即时需求周期性/计划性需求

典型用例：每日摘要、周报汇总、监控提醒（配合 MCP 查 API）、内容定时发布。它把"人力盯守"转换成"配置一次，永久生效"——这正是"主动型伙伴"的第一块基石。

坑在哪
现象原因 / 怎么办
以为定时任务要"每次对话里设置"一次 /cron 配置即持久；除非删除/禁用，否则周期一直生效
以为定时任务=提醒闹钟它是执行任务（Agent 真实干活）不只提醒；"推送结果"只是可选项
任务不跑先怀疑 Agent 坏了先查 Cron 是否启用/网关是否运行（第 ④ 点网关轮询）；大概率是运行条件没满足
2② 三种调度模式：秒速/计划/条件
要解决什么

"定时"不只是"每个小时一次"——讲义给了三种调度模式，它们适用场景完全不同。需要一次分清。

核心思路

讲义第 48 页界定三种调度模式：

模式机理适用
基于时间的调度按 cron 表达式在指定时刻触发每日/每周/每月定点任务（最常见）
基于间隔的调度按固定间隔（如每 30 分钟）触发轮询类、频率稳定的任务
基于条件的调度满足某条件时才触发（如某工具返回特定结果）监控类：网页变化、API 状态、阈值报警

选型口诀："定点用时间，均匀用间隔，看情况触发用条件"。本阶段教材重点演示"基于时间的调度"（cron 表达式），后两种知道存在即可，需要时再查。

坑在哪
现象原因 / 怎么办
所有任务都塞"基于时间"轮询类任务用间隔更合理；条件类任务用时间调度会空跑，三种模式各有位置
调度模式与"立即执行"混淆"立即跑一次"是手动触发（/cron run），与周期调度是两回事
学完只记模式名不记场景背场景口诀：时间=定点、间隔=均匀、条件=看情况
3③ /cron 命令：创建与管理的入口
要解决什么

怎么创建定时任务？命令长什么样？创建后还能改吗？

核心思路

对话内斜杠命令 /cron 是定时任务的创建与管理入口（讲义第 49 页示例环境是一条用内网工具创建的 cronjob）：

/cron                      # 进入任务创建/管理向导
# 创建时通常要提供：
#   触发方式：cron 表达式（如 0 8 * * * = 每天 08:00）
#   任务内容：要 Agent 执行的消息/指令
#   可选投递：是否把结果推送到某个会话
操作途径
创建/cron 向导，或 hermes 配置/命令（以实际支持为准）
查看已有任务/cron list 类子命令
管理（暂停/删除/手动触发）/cron 向导对应操作

cron 表达式速记（5 段：分 时 日 月 周）：

  • 0 8 * * * = 每天 8:00
  • */30 * * * * = 每 30 分钟
  • 0 9 * * 1 = 每周一 9:00
坑在哪
现象原因 / 怎么办
cron 表达式写错（6 段/7 段）Hermes 用 5 段（分时日月周）；秒级用间隔模式，别往 cron 里塞秒
创建任务不带时间只看效果先给表达式，再让向导生成；拿不准就先手动触发试跑再定周期
忘记"可投递结果"配置不投递=执行了就完，你看不到结果；要"推送"就配置投递目标会话
4④ 网关 60 秒轮询：定时任务"醒来"的机制
要解决什么

定时任务不是凭空执行的——总有个"闹钟"在看表。讲义说"网关每 60 秒检查一次"，这段机制怎么理解？跟定时任务的准确度什么关系？

核心思路

讲义原话要点：线程在 60 秒间隔检查已调度的 cronjob 并触发它们（讲义第 49 页："同样会在每 60 秒的网关线程中检查并触发"）。

机制图解：

网关持续运行（后台线程）
   └─ 每 60 秒扫描一次定时任务表
        ├─ 时间到了 → 触发对应任务执行
        └─ 没到     → 继续等下一个 60 秒

两个推论：① 网关必须保持运行，定时任务才会被执行——关掉网关=任务全部休眠；② 触发精度是分钟级（60 秒轮询粒度），要求"秒级准时"的场景不适用，计划精度到分钟即可。

坑在哪
现象原因 / 怎么办
关掉网关后任务不跑，以为删了任务还在，只是"闹钟没电"；重启网关即恢复（第 3 章重启铁律的又一应用）
期望"8:00:00 整点执行"60 秒轮询会有秒级抖动；当作"8 点前后一分钟内"理解
多个任务同时到点互相挤同一轮询周期内按序触发，密集任务建议错开分钟，避免排队延迟
5⑤ 任务执行+结果投递：闭环的最后一环
要解决什么

任务执行完了，结果去哪？"跑完了没人看见"和"跑完自动送到手里"是两种体验，需要把投递配明白。

核心思路

定时任务 = 到点执行 + （可选）结果投递：

环节说明
任务内容你给 Agent 的一段指令（执行什么）
执行到点 Agent 真实干活（搜索/生成/调 MCP...）
投递（可选）把产出推送到目标会话（如你的微信群/QQ/飞书/CLI）

典型配置思路（示例）：每日 8 点 → "汇总昨天 GitHub 仓库的 issues → 推送到我的微信群"。任务不带投递=执行完沉默；要"自动报告"就必须在创建时指定投递目标（呼应第 3 章各平台的会话）。

坑在哪
现象原因 / 怎么办
任务执行了但"什么都没发生"大概率没配投递/投递目标失效；确认任务配置里的 delivery 目标
投递目标写错平台投递走已接入的平台会话（第 3 章）；平台没接好，投递自然失败
忘了投递可含"文件/链接"部分平台支持富推送；产物型任务可以推文件或链接而非纯文本
6⑥ 定时任务的调试：先手动触发，再等周期
要解决什么

定时任务配置完，最怕"等到天荒地老才发现任务本身就有 bug"。怎么调试定时任务？

核心思路

调试铁律：先手动触发验证，再交给周期调度：

① 手动触发   /cron run <任务>（或向导里"立即执行"）
② 检查结果   任务内容对不对？投递到没到？
③ 修正      有 bug 就改任务内容/表达式/投递
④ 才启用周期 → 让 cron 按表达式接管

理由很直观：手动跑一次=所见即所得，把"任务本身的问题"与"调度的时机问题"分开排查。千万不要"配完就等"——等到点才发现任务内容错的，白白浪费一个周期。

坑在哪
现象原因 / 怎么办
配完 cron 就等第二天看结果先手动触发：10 秒内确认任务逻辑，而不是 24 小时后才发现错
手动跑成功但到点没跑那就是调度环节问题：查网关运行、cron 表达式、时区
手动触发和周期触发结果不一样周期触发时的环境（网关负载、平台状态）可能不同；以日志为准复盘
7⑦ Web 仪表板：浏览器里的"控制面板"
要解决什么

命令行再好，"可视化总览"仍有不可替代的价值：任务、状态、日志一眼扫过去。Web 仪表板就是这块"玻璃窗"。

核心思路

Hermes 提供 Web 仪表板，默认地址 http://localhost:9119（讲义第 49 页提到 "dashboard" 可视化查看任务/logs 等；默认端口 9119）。

能力说明
浏览器访问打开 localhost:9119 即可（无需登录/简单鉴权，以实际版本为准）
看什么定时任务状态、运行日志、服务器状态等

价值：诊断"任务到底跑没跑"的图形化入口——比翻终端日志直观。用途与 hermes mcp list//cron list 互补：命令是精确定位，仪表板是全局视野。

坑在哪

打开 localhost:9119 空白/拒绝连接服务没启动（仪表板随网关运行）；先确认网关活着再开页面
端口被占用看一下 config.yaml/日志确认实际端口；被占用可在配置里改端口
只依赖仪表板不看命令输出仪表板适合总览，深挖细节（具体报错）要回终端日志；两手都要
8⑧ 常用命令全景：四大类收个总
要解决什么

十一个章节下来，命令散落各处。最后把它们收进"一张全景图"，随用随查。

核心思路

把全书命令按用途分四大类（合并讲义第 50 页常用命令与各章已学）：

① 配置与信息类

9⑨ URL 与端口的"本地服务观"
要解决什么

第 4 章的 localhost:8080、本章的 localhost:9119——漫游期间反复出现端口号。它们背后的"本地服务观"值得统一理解。

核心思路

这一切都是 WSL 里的本地服务通过端口暴露、Windows 浏览器可访问（第 2/4 章铺垫过）：

服务地址谁在用
案例前端页面http://localhost:8080你（浏览器）
Hermes Web 仪表板http://localhost:9119你（浏览器）
其它本地工具服务各自端口视工具而定

三条规律：① 默认只在本地（localhost）监听，外部机器访问不到——这是安全默认；② 端口被封/占用就改配置换端口；③ 服务没起=地址打不开，先保服务再谈页面。以后遇到任何"本地端口打不开"，先按这三条排查。

坑在哪
现象原因 / 怎么办
想从手机访问 localhost:9119localhost 只在本机；要跨设备访问需配置端口转发/机地址（进阶操作，默认不做）
端口冲突打不开换端口 + 重启对应服务，别死磕同一端口
打不开先怀疑"防火墙"本地 localhost 一般与防火墙无关；先查服务是否真的在跑（ps / 端口占用）
10⑩ 自动化红线：无人值守不等于无人审查
要解决什么

定时任务让 Agent 无人值守地执行命令、推送消息——这份"自主权"怎么给才安全？需要建立自动化场景的安全边界。

核心思路

"无人值守"解放了你，也意味着脚本化的权限授予。安全边界三原则：

原则实践
任务内容只给"本来就会手动授权"的事不会手动批准/approve 的活，别写进 cron
危险操作留审批/避险机制涉及删除、支付、发送的操作，任务设计成"先产出待办→等你确认"而非直接执行
投递目标可信结果只推到可信会话；不把敏感结果推到公开群

核心判断：定时任务相当于"预先批准的授权书"——你批准的是"到点自动执行"，而不是把安全审查全部豁免。宁可任务产出"草稿"由你拍板，也不要全自动一把梭。

坑在哪
现象原因 / 怎么办
把 100% 自动的"删旧文件"写进 cron没人审批的破坏性操作风险巨大；自动任务以"只读/生成/提醒"为先，破坏性动作留人工
全自动任务跑出奇怪结果后追责 Agent先追任务设计：内容、投递、权限三处总有设计缺陷；改动前先手动验证
敏感内容推到公共群投递目标选择小心翼翼；只读结论进群、完整数据留本地
11⑪ 从"会用"到"会养"：日常运维四件套
要解决什么

阶段接近尾声，Hermes 不再只是"学完的软件"，而是"要长期养的伙伴"。日常怎么保养？

核心思路

日常运维四件套（频率由低到高）：

周期动作命令/入口
每会话确认网关在跑、平台消息正常发条消息自测
每周技能/记忆体检：删过时、补缺失hermes skills list / memory list
每月MCP 与 Token 审计：不用的下线、过期的更新hermes mcp list + 平台后台
每季度版本升级：跟进 hermes 更新，顺带回归官方更新渠道

"养"的本质：把第一阶段学的每样能力，变成定期维护的习惯。进化不是装完就完，是"用+检+修"的循环——这正呼应"自我进化的超级智能体"里的"进化"二字。

坑在哪
现象原因 / 怎么办
装完新鲜劲过了就再也不管Agent 与你的"关系"靠运维维持；四件套哪怕只做"每会话自测+每周体检"也好
升级前不看 changelog 直接更新大版本可能有破坏性变更（路径/命令/配置）；先备份配置再升级
出问题不记录把"踩坑+解法"沉淀进记忆/技能（第 7/8 章），下次同类问题秒解——这才是真"进化"
12⑫ 阶段收官：Hermes 的"完整画像"
要解决什么

最后一节给整个阶段 15 画一张"完整画像"——十一个章节学到的东西，怎么变成一个整体？

核心思路

把全书串成一条"伙伴养成线"：

认识它      （第 1 章）Hermes 是什么：开放、可成长、定位"共同成长"
装好它      （第 2 章）环境+安装+模型：Git/WSL2/一键脚本/镜像补救
接上它      （第 3 章）微信/QQ/飞书：扫码+配对+授权，聊天即操作
指挥它      （第 4 章）提示词案例：五要素指令 → 七环节完整交付
塑造它      （第 5 章）SOUL.md：它是谁、怎么说话
武装它      （第 6 章）工具与工具集：八大类能力地图
教学它      （第 7 章）技能系统：把流程固化成手册
赋能它      （第 8 章）持久记忆：记住你、记住事、会翻旧账
美化它      （第 9 章）皮肤：外观有辨识度
扩展它      （第 10 章）MCP：能力无限外接
自动化它    （第 11 章）Cron+仪表板：会自己上班、可视可查

一句总结：先认识、再安装接入，然后用"人格+工具+技能+记忆"塑造核心，用皮肤和 MCP 扩展体验与能力，最后用定时任务和仪表板让它主动运转——这就是"与你共同成长"的完整闭环。

坑在哪
现象原因 / 怎么办
学完各章但串不成整体用上面 11 步"养成线"回顾每章位置，缺哪步回哪章
拿"全部记住了"当验收验收是实操闭环：建一个定时任务+接一个 MCP+写一条记忆，全跑通才算毕业
毕业就停更能力会随版本演进；常回官方文档和社区，保持更新（运维四件套的季度项）
