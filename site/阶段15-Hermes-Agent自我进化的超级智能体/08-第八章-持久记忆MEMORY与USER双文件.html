第八章　持久记忆：MEMORY 与 USER 双文件

阶段 15 · Hermes-Agent 自我进化的超级智能体　|　平台实操　|　难度 ★★☆
这一章在解决什么问题

前面七章读下来，一个灵魂拷问挥之不去："自我进化"到底进化在哪？ Agent 有性格（SOUL）、有动作（工具）、有手册（技能）——但它不记事：今天聊完，明天它就忘了你是谁、你做过什么、你偏好什么。这样的 Agent 和"一年前认识的陌生人"没区别。

记忆就是"自我进化"的硬盘。Hermes 用两个文件承载长期记忆：MEMORY.md（关于 Agent 指挥者的事实）和 USER.md（关于用户的事实），再加上一个会话搜索数据库，构成"长期记忆 + 情景记忆"的双层结构。记不住，一切沉淀都是空谈。

学完这一章，你能回答：MEMORY.md 和 USER.md 分别记什么、它们的规模配额（2200/1375 字符）从哪来、memory 工具有哪四个操作、session_search 是什么、记忆文件增长到爆了怎么办。学完你就能真正开始"打磨"你的 Agent 记忆。

这一章在整个知识库里的位置 上一章（第七章）：技能系统——Agent 会"按流程做"了。 本章 ← 你在这里：持久记忆——Agent 开始"记事"，跨会话认识你、记住事 下一章：皮肤主题——外表个性化 再往后：MCP 扩展（第 10 章）→ 定时任务与仪表板（第 11 章） 阶段终点：性格（SOUL）+ 动作（工具）+ 手册（技能）+ 记忆（MEMORY/USER）四件套齐备，"自我进化"闭环成型
学习提示

记忆这章最容易被"文件内容"带偏，值得抓住的是机制：两个文件各记什么、配额从哪来、memory 工具怎么动它们、session_search 又搜什么。文件只是表象，配额与分工才是管理记忆的思维框架。

1① 记忆的双层结构：长期记忆 + 情景回忆
要解决什么

"记忆"在 Hermes 里不是一个东西，而是一个系统。先建立全局观：它有哪几层？各管什么？

核心思路

HerMes 记忆系统分两层：

层载体管什么
长期记忆MEMORY.md + USER.md（持久文件）稳定的、跨会话的事实与偏好
情景记忆/回忆state.db（SQLite + FTS5，存可传承上下文）历史会话的全文检索

类比人脑：

  • MEMORY.md/USER.md = 记事本：重要的、整理好的、长期有效的；
  • state.db + session_search = 日记本：完整的、原始的、可翻找的。

两者互补：记事本精而短（靠手工 memory 写入维护），日记本全而杂（靠 session_search 搜索）。理解了这层结构，后面所有命令都是对这两个载体的操作。

坑在哪
现象原因 / 怎么办
以为"记忆"只有一个文件是两个文件+一个 DB 的三件套（MEMORY/USER/state.db），分工不同
以为会话内容会自动进 MEMORY.md不会！MEMORY.md 只由记忆工具显式写入（第 ④ 点）；会话原文进的是 state.db
分不清"长期"与"情景"长期=整理好的事实文件；情景=可检索的原始历史；一个精一个全
2② MEMORY.md：关于"你（指挥者）"的事实
要解决什么

MEMORY.md 到底记什么？它和 USER.md 有什么本质区别？这是记忆系统最容易记混的核心分界。

核心思路

定义：MEMORY.md：关于你（指挥者）的希望、目标和事实。

也就是——MEMORY.md 记的是"关于 Agent 的指挥者/使用者"的事：

该记示例
用户希望"用户希望回答简洁有力"
用户目标"用户正在构建个人 AI 知识库"
用户事实"用户使用 Windows 的 WSL2 环境"

注意：它和 USER.md 的"分界"不像名字看起来那么清楚（USER.md 也记用户）——差异在哪个工具往哪里写、以及习惯用法（第 ③、④ 点细讲）。先记住纲领：MEMORY.md 是关于"你"（指挥者）的事实集合。

坑在哪
现象原因 / 怎么办
把"项目背景知识"写进 MEMORY.md项目背景属于 AGENTS.md 或技能；MEMORY 只收"关于人的希望/目标/事实"
把一次性任务细节写进去记忆文件是长期档案，临时事项进 state.db 靠搜索，别污染长期记忆
担心 MEMORY.md 里记的用户信息太敏感记"偏好/目标"即可，密钥密码绝不进记忆文件（呼应各章安全线）
3③ USER.md：同样关于"你"，为什么还要一个文件
要解决什么

MEMORY.md 已经记"关于你的事实"了，USER.md 又记一遍，两个文件怕不是重复？它们到底怎么分工？

核心思路

定义：USER.md：关于你（用户）的偏好和细节。

两者都关于"你"，但分工在侧重点：

文件侧重点例子
MEMORY.md希望、目标、事实（较宏观）目标：做知识库；期望：回答直接
USER.md偏好、细节（较微观）喜欢表格；讨厌长篇大论；常驻城市

记忆工具会把"你明确告诉它的"拆到对应文件（示例：关于用户的信息进 USER.md，关于目标/期望的进 MEMORY.md）。对使用者来说，你不需要记住"哪条该进哪个文件"——用 memory 工具写入，框架自动归类；你只需要记住"记忆由两个文件共同承载"。

坑在哪
现象原因 / 怎么办
试图严格区分"哪条事件进 MEMORY 哪条进 USER"归框架自动处理（memory 工具按语境落盘）；手工维护才需要关心归类
以为 USER.md 是"用户手册"给 Agent 看的教程它是用户画像：关于用户的偏好和细节，不是操作说明书
两个文件都空着也没啥记忆空=Agent 每次从零认识你；长期不用记忆，体验和"无记忆 Agent"没区别
4④ memory 工具：四个操作管两个文件
要解决什么

记忆文件不是手写的，是通过 memory 工具操作。它有哪些动作？每个动作具体做什么？

核心思路

memory 工具支持增、查、改、删四类操作：

操作作用类比
add向记忆文件添加一条新的事实记事本新写一行
search在记忆文件中搜索已有条目翻记事本找内容
replace用新内容替换已有的记忆条目撕掉旧页写新页
delete从记忆文件中删除一条记忆划掉过时条目

典型用法（对话中自然发生）：

"记住：用户喜欢在回答前先给结论"
→ memory add → MEMORY.md 或 USER.md

自动 vs 手动：Agent 会在合适时机主动调用 memory 工具沉淀信息；你也可以明确说"记住XX"触发它。这是"自我进化"的写盘动作。

坑在哪
现象原因 / 怎么办
用"记性不好"评价 Agent 不主动写记忆检查记忆工具是否可用/开启；也可能模型策略保守，明确说"记住XX"即可触发
满屏 add 把文件塞爆记忆有配额管理（第 ⑤ 点）；写多了要清理/合并，别无限往里塞
想改记忆却找不到"编辑命令"就是 memory replace：先 search 定位旧条目 → replace 成新表述
5⑤ 配额与基准：2200 和 1375 是"让你注意"的信号
要解决什么

有两个数字：MEMORY.md 2200 字符、USER.md 1375 字符——这代表什么？是硬性上限吗？

核心思路

这两个数字是实例中记忆文件的实际大小（界面上写着"约占上限的 %"，表示还有多少空间），说明：

  • 记忆文件有大小管理逻辑：不能无限膨胀（否则每轮都占大量上下文 token）；
  • 2200/1375 这类数值提示"到量后该清理了"。

两个含义：① 记忆是有配额的资源（类似 SOUL 截断机制）；② 配额提示你定期 review 记忆，合并冗余、删除过时。Hermes 文档常见指引"如果达到上限，重新组织和删除陈旧条目"。

动作怎么做
检查占用查看记忆文件字符数 / 用 memory search 列全部
清理删除过时条目、合并相似条目
重写用 replace 重写条目，让表达更紧凑
坑在哪
现象原因 / 怎么办
把 2200/1375 当死上限，到数就恐慌它们是实例参考值，提示"该整理了"，不是程序崩溃线
记忆文件超大也不管超配额会挤占上下文、降低遵循度；定期整理记忆应是使用习惯
清理时手抖全删先备份 MEMORY.md/USER.md 再动手；删了过时条目留核心事实
6⑥ 记忆文件的落盘位置与文件形态
要解决什么

一目了然地知道记忆文件存哪、长什么样，方便直接查看和备份。

核心思路

关键信息：

项值
目录~/.hermes/memories/
MEMORY 文件MEMORY.md
USER 文件USER.md
会话数据库state.db（SQLite + FTS5，存可传承上下文）

实操查看：

cat ~/.hermes/memories/MEMORY.md
cat ~/.hermes/memories/USER.md

文件就是普通 Markdown，可以直接手改，但更推荐用 memory 工具改（工具会处理好归类与格式）。state.db 是二进制库，不手改，靠 session_search 查询。

坑在哪
现象原因 / 怎么办
手改记忆文件后格式错乱skill/tool 改写比手工安全；手改也要保持原有 Markdown 结构
找不到 state.db在 ~/.hermes/ 下（默认）；它是数据库文件不是文本，别用文本编辑器看
想备份记忆直接复制 memories/ 目录即可（纯文本文件，便携）
7⑦ session_search：在"日记本"里翻旧账
要解决什么

MEMORY.md 记得精但记得少；想找回"两个月前那次对话里说过的一个细节"，靠什么？这就是 session_search 的舞台。

核心思路

session_search 检索历史会话（存在 state.db 里），让你和 Agent 都能"翻旧账"。

维度MEMORY.mdsession_search
内容整理好的事实全部历史会话原文
检索方式memory search（文件内）session_search（数据库全文）
适合回答"我记得你偏好X"回答"那次我们讨论过X吗"

用法：Agent 遇到"以前聊过但我忘了"的提问，会自动调 session_search 查历史；你也可以直接说"搜一下我们上次聊 XX 的内容"。两者配合 = "总结知识"+"原始回忆"双保险。

坑在哪
现象原因 / 怎么办
用 session_search 查不到"偏好"偏好是长期事实，该在 MEMORY.md（memory search），历史会话里未必有
搜历史没结果就判定"记忆坏了"检查 session_search 工具是否开启（第六章工具集）；state.db 是否有数据
希望"所有对话都自动可搜"Hermes 在对话中进行可传承上下文的存储，默认可用；极端隐私场景可关注配置
8⑧ 记忆与 SOUL/USER 的协同：三份"你"别打架
要解决什么

第 5 章有 USER.md（用户画像），本章 USER.md 又出现了，还多了 MEMORY.md——三个文件都涉及"用户"，怎么协同不冲突？

核心思路

这其实是同一个 USER.md 的两个视角：第 5 章在"配置文件三件套"框架里讲它（AGENTS/SOUL/USER 分工），本章在"记忆机制"框架里讲它（记忆的落盘位置与维护方式）。

文件第 5 章视角本章视角
USER.md用户是谁（画像）记忆文件之一，偏好与细节的长期落盘
MEMORY.md（未细讲）关于指挥者的希望/目标/事实
SOUL.mdAgent 是谁（人格）（不参与记忆）

协同原则：人格在 SOUL、用户画像在 USER、目标事实在 MEMORY、干活规范在 AGENTS。四份文件的"边界"用一句话记：它是谁 / 你是谁 / 你的目标 / 怎么干活。

坑在哪
现象原因 / 怎么办
用户偏好写进 SOUL 又写进 USER，两边重复偏好只应放 USER.md；SOUL 里出现用户偏好会污染人格身份
MEMORY 和 USER 都写"用户喜欢简洁"重复条目浪费配额；用 memory 工具管理时留意合并
AGENTS.md 里写人格员工手册不写性格；各文件各司其职，混用会稀释各自权重
9⑨ 记忆是"进化"的写盘动作：一次完整链路
要解决什么

把"进化"这个词落到实处：一次对话中，记忆是怎么被写入、被读回、被更新的？走一遍完整链路。

核心思路

记忆的完整生命周期（从学到用）：

① 获取     对话中你说了"我喜欢表格回答"
② 写盘     Agent 调 memory add → 进入 USER.md（或 MEMORY.md）
③ 持久     文件保存于 ~/.hermes/memories/，跨会话存活
④ 读取     下次会话启动，记忆文件注入系统提示词（渐进披露式）
⑤ 运用     新对话中 Agent 主动用表格回答——"它记得你"
⑥ 更新     你改口了 → memory replace / delete 更新旧条目

前 5 步构成"记忆→行为"闭环，第 6 步保证记忆可修正。看懂了这条链，"自我进化"就不再是营销词：每次有价值的对话，都在给下一次对话提供更好的起点。

坑在哪
现象原因 / 怎么办
写盘后当场对话没变化记忆大多在后续会话生效（新会话注入）；当前会话未必即时体现
记忆写错想撤销用 memory search 定位该条 → delete 删除，或 replace 改掉
以为记忆只增不减有 delete/replace 就有"遗忘"能力；定期维护=主动遗忘过时项
10⑩ 记忆配额管理：从"塞爆"到"三档整理法"
要解决什么

记忆文件迟早会涨到配额附近。到时候怎么整理？给一套可执行的三档整理法。

核心思路

按"价值密度"分三档处理：

档位内容举例处理
必留（核心）用户姓名、环境、核心偏好保留并压缩表达（合并同类项）
可留（有价值）进行中项目的关键事实精炼后保留，砍掉细节
该删（过时/临时）已结束任务的细节delete 删除，或挪到 AGENTS.md/技能里

实操命令：

# 查看全部记忆
hermes memory list            # 或对话内 memory search 全量
# 定位过时条目 → 删除
hermes memory delete <id>     # 按返回的条目 ID 删除

整理周期建议：每次达到配额提醒时做一轮；平时多按 topic 合并，别堆积到爆。

坑在哪
现象原因 / 怎么办
整理时把"可能有用"的全都留这是记忆文件膨胀主因；"可能有用"→ 靠 session_search 兜底，别占长期记忆配额
删除凭印象不动文件删除的是记忆文件里的条目，不是聊天记录；先在 list/search 里确认目标
整理完没验证新会话里抽查一条整理后的记忆，确认 Agent 读到的是新版本
11⑪ 记忆的"该进/不该进"清单
要解决什么

记忆写到什么程度算好、什么内容根本不该进记忆？给一张黑白名单，避免记忆文件变质。

核心思路
该进（白名单）不该进（黑名单）
用户的稳定偏好（表格、语气）密钥、Token、密码（永远不进任何文件）
正在进行的长期目标一次性任务的临时细节
关键个人事实（名字、环境）会话原文/长对话转储（那是 state.db 的活）
重大决策与结论未经验证的推测/流言
用户的成长记录与边界情绪化片段、隐私数据

判断一句话："半年后这条还对吗？"——对则进，不对则不该占长期记忆。

坑在哪
现象原因 / 怎么办
把 API Key 写进记忆"方便使用"绝对红线：密钥走环境变量，记忆文件进密钥=泄漏定时炸弹（呼应技能的 API Key 规则）
记忆里塞对话全文那是 session_search 的分内事；长期文件塞全文=配额爆炸+检索稀释
一条记忆长达几十字尽量一句话：主谓宾+限定词；长内容转移给 AGENTS/技能
12⑫ 记忆系统五问自检：你的 Agent"记得住"了吗
要解决什么

学完本章如何验收？给五个自检问题，逐个回答就知道你的记忆系统是否健康。

核心思路

记忆系统健康自检五问：

#问题通过标准
1两个文件有内容吗cat ~/.hermes/memories/MEMORY.md 和 USER.md 有有效条目
2跨会话验证了吗新会话问一个已沉淀的偏好，Agent 能答上来
3会主动写吗说"记住XX"后文件里出现新条目（memory add 生效）
4会主动搜吗问"我们上次说过X吗"能触发 session_search 找到原文
5配额在管吗记忆超过配额阈值时知道怎么整理（三档法）

五问全过，记忆系统就真正"活"了——这是"自我进化"在数据层的最终验收。

坑在哪
现象原因 / 怎么办
只验"文件有内容"不问"跨会话生效"文件是原料，跨会话读取才是目的；第 2 问是核心验收
自检失败就怀疑框架坏了按顺序查：工具集开启？会话重启？文件位置对？大概率是配置环节
做完本章不验收直接往下记忆是后面所有"进化"的底盘；先让五问全过再学皮肤/MCP 不迟

本章小结

这一章你装上了 Agent 的"硬盘"：

拿到了什么为什么要紧
双层记忆结构：MEMORY/USER 文件（长期）+ state.db（情景）记事本与日记本分工——精而短 + 全而杂，互补不替代
MEMORY.md：关于指挥者的希望、目标、事实长期记忆的主文件之一，知道它记什么
USER.md：关于用户的偏好与细节用户画像的持久落盘，跨会话"懂你"的数据源
memory 四操作：add / search / replace / delete记忆的写、查、改、删——进化的"写盘动作"
配额意识：2200/1375 是提示不是死线记忆有成本，定期 Review+合并+删除才是健康用法
session_search：在历史里翻旧账大量原始信息的兜底检索，与长期记忆互补
三档整理法 + 五问自检记忆可维护、可验收，"进化"能落地检查

一句话记住本章：MEMORY.md 管"你的目标与事实"、USER.md 管"你的偏好细节"，memory 工具增查改删、session_search 翻旧账；定期清理配额，新会话验生效——记得住，才谈得上进化。
