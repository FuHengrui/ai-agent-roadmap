第七章　文本向量化与向量数据库

阶段 11 · LegalMind 法律咨询系统　|　难度 ★★★
这一章在解决什么问题

上一章 LLM 会说话了，但它是"无记忆的百科全书"——你问它"和我情况最像的判例"，它只能背书，因为它没有检索能力。法律咨询真正的价值在"检索到对的案例"这一步。 裁判文书是非结构化长文本，不能靠 SQL 的 LIKE 模糊匹配（"该案是离婚纠纷赔偿多少多少"这种语义根本对不上关键词）。本章用 BGE 嵌入模型把文本变成向量 + ChromaDB 向量库存取：语义相近的案例在向量空间里距离近，一查一个准。学完本章，build_index.py 跑完，法律语料就变成"可被语义检索的向量库"。

第 6 章能调模型就能开始；这章要下 BGE 中文嵌入模型（约 90MB）建向量库。

学到这儿就够了

1① 为什么文本要变成向量
要解决什么

SQL 的 LIKE 匹配是"字面匹配"：LIKE '%离婚%' 只能命中查到"离婚"二字的文本。可用户问"我俩过不下去了想分开，财产怎么分"，这文本里没有"离婚"两字，却和离婚案高度相关——字面匹配对此束手无策，必须用语义匹配。

核心思路

嵌入（Embedding）模型把一段文本映射成一个固定维度的向量（本项目 BGE-small-zh 产出 512 维），语义相近的文本向量在空间里距离近：

"我想离婚，财产怎么分割"  →  [0.12, -0.35, 0.78, ...] 512个浮点数
"离婚财产分割裁判案例"    →  [0.11, -0.34, 0.77, ...]  ← 距离近 = 语义相关
"今天天气不错"            →  [0.89, 0.21, -0.44, ...]  ← 距离远
  • 相似度用余弦相似度（cosine）衡量：越接近 1 越相关。
  • 检索时：把用户问题也转成向量 → 在库里找余弦距离最近的 N 条。
  • 效果：写法和说法不同，但意思一样也能命中——这正是 RAG 相对传统搜索的根本优势。
坑在哪
现象原因 / 怎么办
以为向量检索能自动纠错、理解所有同义改写嵌入模型不是万能的，专有名词、数字、法条号照样召回差；向量检索解决的是"语义相近"，精确匹配还得配关键词路（见混合检索）
2② BGE 嵌入模型与本地加载
要解决什么

嵌入模型选哪家？在线 API 每次调用按量计费且依赖网络；本地跑一个开源模型，免费、离线、快。法律场景数据敏感（案情内容），本地化处理更稳妥。

核心思路

本项目选用 BAAI/bge-small-zh（智源开源中文嵌入模型，512 维，轻量）：

# app/rag/embeddings.py
from langchain_huggingface import HuggingFaceEmbeddings

def get_embeddings():
    return HuggingFaceEmbeddings(
        model_name=str(settings.MODEL_DIR / settings.EMBEDDING_MODEL),   # 指到本地目录，别写 HF 仓库名
        cache_folder=str(settings.MODEL_DIR),
        model_kwargs={"device": "cpu"},        # 低配机器 CPU 推理
        encode_kwargs={"normalize_embeddings": True},  # 归一化=余弦相似度变点积
    )

关键点：

  • 权重放 models/bge-small-zh/，model_name 直接指这个目录；写 "BAAI/bge-small-zh" 会走 HF 缓存，没网/没缓存时启动就卡在下载。
  • normalize_embeddings=True：向量归一化后，余弦相似度 = 点积，计算更快且数值范围稳定。
  • 启动时不应触发下载——第 3 章 init_vector_store() 从本地加载，若日志出现 "HuggingFace download" 说明本地模型缺失，先手动放好权重。
坑在哪
现象原因 / 怎么办
首次加载卡在下载网络问题；手动去 HF 下载权重放进 models/bge-small-zh/ 再重启
内存占用高BGE 模型约 300MB；低配机器缩 batch 或用 cpu + 小 batch
向量维度与库不一致换模型后旧库要重建；EMBEDDING_DIM 与模型输出必须一致（512）
中文效果差必须用中文预训练模型（bge-small-zh），通用英文模型中文向量很差
3③ ChromaDB：轻量向量库怎么用
要解决什么

向量算出来要存哪里？自己写个数组存内存，重启就丢；上 Milvus/ES 又太重。ChromaDB 是"嵌入式向量库"，轻量、本地文件持久化、天然支持向量检索 + metadata 过滤，与 LangChain 集成成熟。

        # 数据存本地 chroma_data 目录
        self.db = Chroma(
            collection_name="legal_cases",
            embedding_function=self.embeddings,
            persist_directory=str(settings.CHROMA_DIR),   # 落盘目录
            collection_metadata={"hnsw:space": "cosine"},   # 默认是 L2，别让阈值口径含糊
        )

    def build_index(self, cases: list[dict]) -> None:
        docs = [
            Document(
                page_content=c["title"] + "\n" + c["content"],   # 标题也进正文，检索更容易命中
                metadata={"case_number": c["case_number"], "title": c["title"],
                          "court": c["court"], "type": c["type"]},   # 去重与展示都要用
            )
            for c in cases
        ]
        self.db.add_documents(docs)

    async def similarity_search(self, query: str, top_k: int = 5, filters: dict | None = None):
        return self.db.similarity_search_with_score(
            query, k=top_k, filter=filters or None
        )
  • 持久化：persist_directory 落盘，向量库不占内存常驻。
  • page_content vs metadata：可检索文本（title+summary）和结构化字段（court/type/laws）分开存——检索命中后还能按 metadata 过滤。
  • add_documents 要幂等：重复跑 build_index 会重复插入，本项目用"按 case_number 去重跳过"策略（见第 4 点）。
坑在哪
现象原因 / 怎么办
重复执行建库脚本报 "collection already exists"create_collection 对已存在的集合会报错；用 get_or_create_collection，或用 delete_collection 重置
报维度不一致（dimension mismatch）向量维度由嵌入模型决定（如 768/1024），换了模型或重建索引维度就变；集合创建后维度锁定，换模型要重新建集合
4④ 建索引脚本：从 cases 表到向量库
要解决什么

前面都是组装，真正让向量库"有货"靠 scripts/build_index.py：读 cases 表 → 逐条嵌入 → 存 ChromaDB。这个脚本必须在种子数据（第四章）之后跑。

核心思路 
# scripts/build_index.py
import asyncio
from app.models.case import Case
from app.rag.vector_store import VectorStore

async def main():
    store = VectorStore()
    # 从 Postgres 拉全部案例
    cases = await Case.all()
    # 已有 index 的 case_number 跳过（幂等）
    existing = store.get_existing_case_numbers()   # VectorStore 里要有这个方法（读 metadata 的 case_number 去重）
    new_cases = [c for c in cases if c.case_number not in existing]

    print(f"待索引 {len(new_cases)} 条（跳过 {len(cases) - len(new_cases)} 条已索引）")
    await store.add_cases([c.to_dict() for c in new_cases])
    print(f"✅ 索引完成，向量库共 {store.count()} 条")

asyncio.run(main())

执行流程：python scripts/seed_cases.py（灌数据）→ python scripts/build_index.py（建索引）。顺序反了会得到"有数据但库里空"的假象。

坑在哪
现象原因 / 怎么办
把整篇判决书当成一条文本直接 embed检索粒度过大，用户问"利息怎么算"匹配到整篇文章，相关度被稀释；先按段落/语义切块（chunk）再逐块向量化
5⑤ 混合检索的必要性
要解决什么

纯向量检索有个弱点：专有名词、案号、法条编号（如"（2024）京01民终1024号""民法典第一千零八十七条"）——这种短而精确的 token，向量模型往往编码得不好。关键词检索（BM25）反而是它的强项。两者结合才能全场景覆盖。

核心思路 
用户查询 "民法典第一千零八十七条 离婚 房产"
    │
    ├─► 向量检索（ChromaDB）：语义召回   → 与"离婚财产分割"语义相近的案例
    │
    └─► BM25 关键词检索（rank-bm25）：字面召回 → 法条编号精确命中的案例
    │
    ▼
合并候选集（去重） → 重排序 → 取 Top-K（第 8 章）
  • 向量负责"语义"，BM25 负责"精确"。
  • 候选池放大：top_k * 3（本项目 15 条）保证重排序有足够弹药。
  • 第 8 章 HybridRetriever 是这套合并逻辑的实现，本章先把"向量侧"（ChromaDB + embeddings）这一半打牢。
坑在哪
现象原因 / 怎么办
只有向量路，搜"民法典第 1043 条"这种精确编号完全失灵向量擅长语义、不擅长精确串匹配；BM25 关键词路专门兜这种，两路合并再重排才是完整方案
6⑥ 相似度分数与阈值
要解决什么

检索出的结果"多相关算相关"？没有阈值，垃圾结果也进 prompt 白白占 token，还可能让 LLM 引用错误案例。要给相似度设一个准入线。

核心思路

Chroma 的 similarity_search_with_score 返回 (doc, score)，本项目 .env 里有阈值配置：

RAG_SCORE_THRESHOLD=0.7
RAG_TOP_K=5

用法（RetrievalAgent 里）：

docs = await store.similarity_search(query, top_k=top_k * 3)
filtered = [d for d in docs if d[1] <= settings.RAG_SCORE_THRESHOLD]   # Chroma 返回的是距离，越小越像
  • 阈值 0.7（距离，越小越像）：宁可少召回，不把"不相关"硬塞给 LLM——法律场景错误引用的代价高。
  • RAG_TOP_K=5：最终送入 prompt 的案例数。多了 token 爆炸且模型抓不住重点。
  • 调参顺序：先看相似度分数分布，再定阈值——盲设阈值容易"全过"或"全滤"。
7⑦ 初始化与关闭：向量库的生命周期
要解决什么

向量库也要跟 app 一起初始化/关闭，否则会出现"启动即要连模型加载 10 秒"或"句柄泄漏"。第 3 章 lifespan 里的 init_vector_store 就是干这个的。

核心思路 
_store: VectorStore | None = None

async def init_vector_store():
    """lifespan 启动时调用，全局缓存单例"""
    global _store
    if _store is None:
        _store = VectorStore()     # 首次调用加载嵌入模型 + 连 Chroma
    return _store

def get_vector_store() -> VectorStore:
    if _store is None:
        raise RuntimeError("VectorStore 尚未初始化")
    return _store
  • 单例缓存：模型只加载一次，避免每次请求都重新嵌入（每次都加载要等 10 秒+）。
  • 懒加载 + 启动预热：lifespan 里提前 init，首个请求不再被模型加载拖慢。
坑在哪
现象原因 / 怎么办
开发期反复启动后报 lock / 无法写入Chroma 持久化目录被占用或上次异常没释放；确认 lifespan 里正确 close，必要时清掉 lock 文件重来
8⑧ 验证：向量检索的冒烟测试
要解决什么

索引建完，用一句话查询验证"语义检索真的有效"——这是回归防线：以后改了嵌入配置、换了模型，跑一遍就知道有没有退化。

核心思路 
# scripts/retrieval_smoke_test.py
import asyncio
from app.rag.vector_store import get_vector_store, init_vector_store

async def main():
    store = await init_vector_store()
    # 用"语义近但字面不同"的查询测试
    results = await store.similarity_search("夫妻闹离婚，房子归谁", top_k=3)
    for doc, score in results:
        print(f"[{score:.2f}] {doc.metadata['title']}")

asyncio.run(main())

期望输出：返回离婚相关案例，且距离 < 0.7（similarity_search_with_score 给的是距离，越小越像）。若返回空或距离很大：

  1. 查 build_index 是否真的跑过（向量库 count）。
  2. 查 seed_cases 是否先跑（数据源）。
  3. 换更直白的词测试，定位是"模型问题"还是"链路问题"。
