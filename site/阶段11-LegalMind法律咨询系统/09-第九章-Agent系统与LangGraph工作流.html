第九章　Agent 系统与 LangGraph 工作流

阶段 11 · LegalMind 法律咨询系统　|　2 课时　|　难度 ★★★
这一章在解决什么问题

前几章攒了一堆零件：意图识别、案例检索、法律问答、文书生成——但谁来决定先用哪个、怎么串起来？写死 if-else 只能处理"能预测的顺序"，可用户的真实请求千变万化：有人问问题（问答）、有人要写诉状（文书）、有人想查判例（检索）。顺序是运行时由意图决定的。 正好可以用 LangGraph 来解决：这种"按条件分叉的多步任务"正是有向状态图的强项。LegalMind 用 LangGraph 把所有能力编排成一张图——总是先走意图识别，再按识别结果条件路由到检索/文书，工作流完成一次完整协作。学完本章，你的 AI 系统从"单打独斗的工具集合"升级为"会自己排兵布阵的 Agent 系统"。

这一章在整个知识库里的位置 上一章（第八章 RAG 检索）：RetrievalAgent 已可用，检索质量可调 本章 你在这里：把四个 Agent 装进 LangGraph 状态机——分工、路由、记忆，一次编排 下一章：聊天与文书生成 API——工作流实例直接挂在 FastAPI 路由后面，SSE 推流 再往后：前端联调、检索页面 阶段终点：一个"会自动选路"的完整 AI 律师大脑
1① Agent 的拆解：四个单一职责模块
要解决什么

LLM 调用场景各不相同，全塞一个类会膨胀到没法维护。按职责拆成四个 Agent，各自只干一件事，可单独测试、可替换升级。

核心思路

LegalMind 的四枚 Agent 与职责：

Agent输入输出依赖
IntentAgent用户 queryqa / document / searchLLM + 意图 prompt
RetrievalAgentquery、filters案例列表（已重排）HybridRetriever + Reranker
QAAgent案例 + 消息历史流式回答文本LLM + QA prompt
DocumentAgent文书类型 + 参数文书全文LLM + 文书模板

协作关系一句话：IntentAgent 决定方向 → RetrievalAgent 找弹药 → QAAgent 组织回答（或 DocumentAgent 生成文书）。四者互不 import 对方（各自只依赖 rag/llm 层），替换任一 Agent 不影响他人——这就是"单一职责"在 Agent 架构里的落地。

坑在哪
现象原因 / 怎么办
把 LLM 调用、检索、写库全塞进一个"万能函数"一个函数耦合四件事，改一处全崩；先按职责拆四个模块，图才有清晰的节点边界
2② LangGraph 核心概念：State/Node/Edge
要解决什么

用过的都说 LangGraph 是"给 LLM 应用写流程图"。先搞懂它的三个核心概念，再看 LegalMind 的图就一目了然。

核心思路

对比关系（把 Agent 工作流想象成工厂流水线）：

概念类比本项目实例
State传送带上的"料盒"（所有节点共用）AgentState：query / intent / retrieved_cases / response / messages
Node（节点）工位的"工人"intent_recognition / case_retrieval / qa_generation / document_generation / final_output
Edge（边）工位间的"传送带"普通边（顺序）与条件边（按 State 分叉）

State 定义（TypedDict）：

class AgentState(TypedDict):
    query: str                       # 用户问题
    intent: str                      # 意图（qa/document/search）
    retrieved_cases: list            # 检索结果
    document_type: str               # 文书类型
    document_params: dict            # 文书参数
    response: str                    # 最终回答
    sources: list                    # 引用来源
    messages: Annotated[list[BaseMessage], add_messages]  # 对话历史（自动合并）

add_messages 是 LangGraph 对 messages 字段的归约器（reducer）：多节点往里加消息时自动 append 合并，而不是覆盖。

坑在哪
现象原因 / 怎么办
Node 直接在函数里改入参 State 对象，期望图内共享图节点要返回"要更新的 state 片段"，不是原地改外部变量；否则并发/检查点恢复时状态全乱
3③ 建图：五节点 + 三条件边的完整结构
要解决什么

四个 Agent 怎么编排成图？从"入口在哪、节点叫什么、按什么条件分叉"三个问题入手，把图的结构一次搭对。

4④ 各节点实现：如何改 State
要解决什么

5⑤ 条件路由函数：_router_by_intent 的写法
要解决什么

条件边需要一个"路由函数"：读 State，返回 key 字符串，LangGraph 拿 key 查映射表决定下一节点。写这个函数要把"默认行为"想清楚。

核心思路 
def _router_by_intent(self, state: AgentState) -> str:
    intent = state["intent"]
    if intent == "document":
        return "document"
    elif intent == "search":
        return "search"
    return "qa"          # 默认兜底：未知意图一律走问答

def _route_after_retrieval(self, state: AgentState) -> str:
    if state["intent"] == "search":
        return "search"
    return "qa"

两个防呆设计：

  • 兜底分支：意图识别输出不在 {qa, document, search} 时，_router_by_intent 返回 "qa"——宁可多答，不能路由崩（对应第 6 章 agent 的 output 净化）。
  • search 意图的"双节点接力"：先走检索拿结果，再到 final_output 把结果 JSON 化直接返回——检索页的接口可以复用这条链路。
6⑥ checkpointer：对话记忆持久化到 Postgres
要解决什么

聊天要"记得上一轮"。LangGraph 的 checkpointer 可以把状态（含 messages）按 thread_id 存起来；本项目用 AsyncPostgresSaver 存进 Postgres——跨请求、跨进程重启都不丢。

7⑦ 懒编译 get_graph：图的加载时机
要解决什么

图编译是重活（要连接 checkpointer、构建状态机），不能每次请求都编译。项目用懒加载 + 单例缓存：第一次调用时编译一次，之后复用。

核心思路 
class LegalMindWorkflow:
    def __init__(self):
        self.intent_agent = IntentAgent()
        self.qa_agent = QAAgent()
        self.document_agent = DocumentAgent()
        self.retrieval_agent = RetrievalAgent()
        self._graph = None

    def get_graph(self):
        """懒加载编译图。首次调用时编译并缓存。"""
        if self._graph is None:
            self._graph = self._build_graph()
        return self._graph

注意：__init__ 里只是实例化四个 Agent，不编译图——这样 import 模块时零副作用（不会触发 get_checkpointer()）。图编译推迟到第一次"真实使用时"（lifespan 已完成 checkpointer 初始化），时序天然正确。模块末尾 workflow = LegalMindWorkflow() 提供全局单例，API 路由直接 from app.agents.workflow import workflow。

坑在哪
现象原因 / 怎么办
每次请求都重新编译整张图，响应慢一截图结构不变就不要每次重建；get_graph 缓存复用，只在线程安全的编译一次
8⑧ astream 流式：stream_mode="messages"
要解决什么

聊天体验要"打字机效果"（逐字输出），LangGraph 怎么把内部节点的输出流出来？用 astream(..., stream_mode="messages") 只流 LLM 的 token，节点元信息（在哪个节点）一并给出。

核心思路 
async def astream(self, query: str, thread_id: str):
    config = {"configurable": {"thread_id": thread_id}}
    init_state = {"query": query, "messages": [HumanMessage(content=query)]}
    async for chunk, metadata in self.get_graph().astream(
        init_state, config=config, stream_mode="messages"
    ):
        yield chunk, metadata     # metadata 含 langgraph_node 字段

第 10 章 chat API 会用它做 SSE：

async for chunk, metadata in workflow.astream(query=query, thread_id=session_id):
    node = metadata.get("langgraph_node") if metadata else None
    if node == "qa_generation" and chunk.content:
        # 只把问答节点的 token 推给前端
        yield f"data: {json.dumps({'content': chunk.content}, ensure_ascii=False)}\n\n"

要点：

  • stream_mode="messages" 流的是 LLM 层消息 token（细粒度），不是节点级结果。
  • 按节点过滤：node == "qa_generation" 才推流——检索节点没有 token 输出，文书节点走一次性返回。
  • 流结束后单独 graph.aget_state(config) 读最终 state 取 sources——流式模式不暴露最终 state，这是本项目踩过的坑（第 10 章展开）。
坑在哪
现象原因 / 怎么办
stream_mode=messages 和默认模式的事件结构弄混，解析不到内容不同 stream_mode 的 event 结构不同；先用一个回显脚本打印原始事件，再写解析，别猜结构
