开发时手动起 Postgres/Redis/后端/前端——生产谁干这活？docker-compose.yml 定义全部服务 + 依赖顺序 + 数据持久化，一条命令全家启动。

坑在哪
现象原因 / 怎么办
后端容器反复重启（depends_on 不生效）depends_on 默认只等"启动"，不等"健康"；要加 healthcheck + condition: service_healthy 才能等 PG 真就绪
容器重建后数据全丢了没挂 volume；Postgres/Redis 数据目录必须挂到命名卷（postgres_data/redis_data），否则容器一删数据也没了
POSTGRES_PASSWORD 直接写进仓库compose 文件会被提交；用环境变量引用 .env（compose 自动读同名 .env），仓库里只留占位符
8⑧ 部署验证与排障：三查三板斧
要解决什么

部署完怎么知道"成了"？三个检查点 + 三个常见故障定位法，让你的首次上云不翻车。

核心思路

验证三板斧：

# 1. 服务状态：8 个容器都 UP 且无 RESTARTING
docker compose ps

# 2. 后端健康：API 响应正常（会返回 401，说明鉴权活着）
curl -i http://localhost:8000/api/chat/sessions

# 3. 前端入口：首页 200，JS 能加载
curl -I http://localhost/

# 4. 日志排障：看后端实时日志
docker compose logs -f backend

排障口诀（对照现象查因）：

现象排查路径
前端白屏 / API 404检查 Nginx proxy_pass 路径与 router base 是否一致
SSE 一整块才出来（不逐字）关 Nginx 缓冲：proxy_buffering off;
后端一直重启docker compose logs backend 看报错；确认 .env 变量齐全
数据重启就丢确认 volume 挂载正确；postgres 目录必须是 /var/lib/postgresql/data

收尾动作：docker compose down 停服、docker compose up -d --build 重新构建——这 8 个 point 走完，LegalMind 系统就完成了从源码到产品的全部旅程。

坑在哪
现象原因 / 怎么办
SSE 不逐字推，一大坨一起出来Nginx 默认缓冲响应；/api 的 proxy 块加 proxy_buffering off; 并保持 X-Accel-Buffering: no
前端白屏但 API 正常多半是 Nginx proxy_pass 路径没带 api 前缀或 router base 不一致；先在浏览器 Network 里看 404 的是谁
