第八章　RAG 检索与重排序

阶段 11 · LegalMind 法律咨询系统　|　难度 ★★★
这一章在解决什么问题

第 7 章向量库建好了，但"检索"远不止"向量搜一下"这么简单。法律场景有两个硬需求：案号和法条编号要能精确命中（向量检索在这上面会漏），命中结果要按相关度排好序（向量分高的未必是最该引用的）。 LegalMind 的 RetrievalAgent 用 "多路召回 + 重排序" 的组合拳：向量检索（语义）+ BM25 关键词检索（字面）双路召回 15 条候选，再用词重叠打分重排，截取最相关的 5 条进 prompt。这条路就是当下 RAG 系统的标准骨架。学完本章，你掌握的不只是"查案例"，而是一套可以复用到任何垂直领域的检索范式。

这一章在整个知识库里的位置 上一章（第七章 向量库）：ChromaDB 里已有案例向量，similarity_search 可用了 本章 你在这里：把检索升级为完整 RAG——向量+BM25 双路召回、重排序、过滤、阈值筛选 下一章：Agent 系统与 LangGraph——RetrievalAgent 成为工作流里的"case_retrieval 节点" 再往后：第 9 章聊天/文书 API 用上 QAAgent 这套 RAG 链路 阶段终点：检索质量可调可验，QA 回答有据可依
1① RAG 的完整链路回顾
要解决什么

7 章讲完，RAG 的各个零件都齐了，但"它们怎么串起来"需要一次收拢——否则容易只见树木不见森林。

核心思路

RAG（Retrieval-Augmented Generation，检索增强生成）标准五步：

① 建库：语料切片 → 嵌入 → 存向量库（第 7 章已完成）
② 召回：用户 query → 向量检索 + BM25 双路召回 → 合并去重（本章重点）
③ 重排：对候选按相关度打分排序，截取 Top-K（本章重点）
④ 增强：检索结果拼进 prompt（第 6 章 QA_PROMPT 的 {cases}）
⑤ 生成：LLM 依据案例 + 法条生成回答（第 6 章）

为什么检索质量决定生成质量：LLM 再聪明，喂进去的是垃圾案例，输出就是引用错误案例的"专业胡说"。RAG 系统的性能上限由检索端决定，这是行业内公认的"Garbage in, garbage out"。

坑在哪
现象原因 / 怎么办
以为 RAG = 向量检索一步完整链路是 拆块→向量化→双路召回→重排→拼 prompt→生成；漏掉重排或检索质量调试，答案相关性全靠运气
2② HybridRetriever：向量 + BM25 双路召回
要解决什么

第 7 章讲过纯向量在案号/法条上的短板。HybridRetriever 把两路检索合并，用"召回广度"换"查全率"——先多捞，再精筛。

现象原因 / 怎么办

3③ Reranker：词重叠启发式重排
要解决什么

合并后的候选顺序是"先向量后 BM25"，不一定按相关度排。重排序器要用一个更准的信号重新打分——本项目用词重叠（query 与文档共同词数），简单高效、可解释。

核心思路

app/rag/reranker.py：

class Reranker:
    async def rerank(self, query: str, documents: list[dict], top_k: int = 5) -> list[dict]:
        scored_docs = []
        query_terms = set(query.lower().split())     # 简化：英文按空格，中文可结合分词

        for doc in documents:
            content = doc.get("content", "")
            title = doc.get("title", "")
            # 打分：query 的词在文档标题/正文中出现越多分越高
            score = sum(1 for term in query_terms if term in content or term in title)
            scored_docs.append((score, doc))

        scored_docs.sort(key=lambda x: x[0], reverse=True)   # 降序
        return [doc for _, doc in scored_docs[:top_k]]       # 截取 Top-K

定位与局限要说透：

  • 这是轻量启发式重排（词频/词重叠），不是模型重排（如 cross-encoder/BGE-Reranker）——好处是零依赖秒算，坏处是信号粗糙。
  • 项目用 RERANK_ENABLED=True 开关控制；生产环境想提精度，把这里的打分函数换成 BGE-reranker 或 cohere rerank，接口完全兼容。
  • 重排的价值：向量分高的"语义像"，重排后的"字面更像"——法律场景用户问法往往带关键词，词重叠信号很有效。
坑在哪
现象原因 / 怎么办
重排分数和相似度分数混为一谈相似度是"像不像"，重排是"符不符合问题意图"；调试时两列分开看，别用一个阈值同时卡
4④ RetrievalAgent：把三件事包装成一个接口
要解决什么

召回、重排、过滤逻辑不能散在调用方。RetrievalAgent 作为"检索门面"，对外只有 retrieve(query, top_k, filters) 一个方法，Agent 层和 API 层调它就好。

5⑤ 检索结果怎么进 prompt
要解决什么

检索出 5 条案例，不能直接把 dict 丢给 LLM——要格式化成"案例清单"文本，让模型一眼看懂每个案例的标题、案号、法院、要旨、法条。

核心思路

QAAgent（第 8 章）+ 第 6 章 QA_SYSTEM_PROMPT 的组装（_format_cases）：

def _format_cases(self, cases: list[dict]) -> str:
    if not cases:
        return "暂无相关案例参考。"
    formatted = []
    for i, case in enumerate(cases, 1):
        formatted.append(
            f"【案例{i}】\n"
            f"标题：{case.get('title', '未知')}\n"
            f"案号：{case.get('case_number', '未知')}\n"
            f"法院：{case.get('court', '未知')}\n"
            f"裁判要旨：{case.get('summary', '未知')}\n"
            f"相关法条：{case.get('laws', '未知')}\n"
        )
    return "\n".join(formatted)
  • 案号/法院/要旨/法条四项全给——这是"引用依据"原则的原料（第 6 章回答原则 3）。
  • 无案例时给"暂无相关案例参考"——LLM 会老老实实说没查到，而不是编一个。
  • 案例是当轮 system 注入，绝不进长期 messages（第 8 章 Agent 部分详述，防上下文膨胀）。
坑在哪
现象原因 / 怎么办
检索结果全是 0 分的垃圾向量库没建好或过滤条件太严；先查 add 成功没、阈值是否过狠
案例重复出现合并去重没生效；检查 case_number 是否一致（空值会导致去重失败）
BM25 结果为空中文没分词（jieba 没装/没调用），BM25 对整句中文不敏感
prompt 里案例太多/token 超限TOP_K 调小；案例文本截断（summary 只取前 500 字）
6⑥ 检索质量调试：参数从哪调
要解决什么

检索不准时，90% 的修复调的不是模型，而是几个配置参数。把"调什么、往哪调"列成清单，别瞎改代码。

核心思路

.env 里的检索参数就是调试面板：

参数调大调小场景
RAG_TOP_K更多案例、更全更快、更聚焦综合问答 5，文书参考 3
RAG_SCORE_THRESHOLD更严、更精准更松、更多召回语料质量高调高，语料少调低
RERANK_ENABLED开重排关重排保速度精度优先开，耗时敏感关
候选池倍数 top_k*3重排选择更多更快语料库大时可以调 5 倍

调试流程：先跑检索冒烟测试 → 看分数分布 → 调阈值 → 看漏召回 → 调 TOP_K。一次只调一个参数，记录效果。

坑在哪
现象原因 / 怎么办
召回条数一改（top_k）就发现答案质量跳变别只顾 top_k，先看召回内容本身对不对；问题往往在 chunk 切分和阈值，不在最后的条数旋钮
7⑦ 过滤条件的透传设计
要解决什么

案例搜索页要"只看北京的案例""只看劳动争议"，聊天里可能也要"按法条限定"。过滤逻辑不能写死在检索函数里，做成可透传的参数。

核心思路

过滤参数从 API → Agent → Retriever → Chroma 一路透传：

# API 层（case 搜索接口）
filters = {}
if court:     filters["court"] = court
if case_type: filters["case_type"] = case_type
if article:   filters["laws"] = {"$contains": article}

results = await agent.retrieve(query=q, top_k=limit, filters=filters or None)

Chroma 的 metadata 过滤语法（$contains 是数组字段的包含判断）：

filter={"court": "北京市第一中级人民法院"}          # 等值过滤
filter={"laws": {"$contains": "民法典第一千零八十七条"}}  # 数组包含
  • API 层拿 query 参数 → 组 filters → 透传，检索内部逻辑完全不变。
  • 向量检索支持 metadata 过滤（查得快），BM25 侧在合并时一并对齐过滤即可。
坑在哪
现象原因 / 怎么办
过滤字段名前端传 camelCase、后端收 snake_case，静默过滤空跨端字段约定必须一致（文档里约死并且联调时对照），过滤条件透传前做一层字段映射
8⑧ 检索链路验证：端到端冒烟
要解决什么

全链路写完后，用一个能覆盖"向量 + BM25 + 重排 + 过滤"四个特性的测试查询，确认检索质量没退化。
