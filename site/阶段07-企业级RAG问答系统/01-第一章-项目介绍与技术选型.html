第一章　项目介绍与技术选型

阶段 7 · 企业级RAG问答系统　|　理论　|　难度 ★★☆
这一章在解决什么问题

上一阶段你跑通了端到端 RAG 演示，但那是一个"玩具"：单文件脚本、用自己的文档就要改代码、问了问题没有来源可查。企业里的 RAG 不是这样——员工要能自己上传文档、系统要同时服务几十个人、回答必须能追溯"这句话出自哪份文件"。

这一章是这个阶段的立项书：企业级 RAG 问答系统到底要解决谁的什么问题、第一版做什么不做什么、整个系统的骨架长什么样，以及最重要的——向量库、嵌入模型、大模型三家供应商怎么选。先想清楚再动手，后面的每一章都在落实这里的决策。

这一章在整个知识库里的位置 上一章（阶段6）：RAG 端到端快速演示——用脚本把一个 RAG 系统跑通，先见森林 本章 ← 你在这里：项目介绍与技术选型——从"能跑"升级到"能上生产"，先定目标和框架 下一章：项目搭建与文档解析——把工程骨架立起来，解决"各种格式的文档怎么读进来" 阶段终点：一个完整的企业级 RAG 问答系统——上传文档、解析入库、检索问答、可追溯来源
这一章你要达到什么程度

8 个知识点，不写代码。学完你能回答三件事：这个系统为谁解决什么问题、MVP 该砍掉什么、以及"向量库/嵌入/大模型"这三样核心组件各自有哪些候选、为什么这么选。后面的代码全部围绕这里的架构图展开。

1① 立项：企业文档明明有，为什么还要专门做个问答系统
要解决什么

企业里最常见的两个抱怨：一是文档找不到——制度、手册、FAQ 散落在几十个共享目录里，员工根本不知道"该去哪查年假规定"；二是找到了也读不完——一份 200 页的验收规范，谁有耐心从头看到尾找一条标准？

核心思路

企业级 RAG 问答系统的目标不是"做一个聊天机器人"，而是把散落的文档变成"会说话的数据库"：

现状痛点系统要带来的变化
文档散落在共享盘、网盘、Wiki，没人知道在哪统一入库，按内容语义检索，不看文件名也能找到
找到文档还要一页页翻直接问，答案定位到"出自哪一段"
制度更新后，旧版本还在流传入库即最新，回答永远基于库里的现行版本
新员工要花几周熟悉业务资料上手就能问，几分钟获得老员工一个月的经验

它和普通客服机器人的差别在"私有"：语料是公司自己的文档，数据不出内网，回答必须可溯源——这就决定了下面的每一层都要为"私有、可溯源"服务。

2② 用户画像与 MVP：第一版先服务谁、砍掉什么
要解决什么

立项最怕"什么都要"。如果第一版就做权限管理、多租户、知识库自动更新、千人千面，半年都交不了货。不知道砍什么，就不知道先做什么。

核心思路

这个项目把第一版（MVP）的用户定得很窄：企业内部员工，用自然语言查询公司制度/技术文档/FAQ。 对应的功能边界：

MVP 要做的（围绕"能问答"）                 MVP 明确不做的（留到以后）
┌─────────────────────────────┐         ┌─────────────────────────────┐
│ ① 上传文档（PDF/Word/MD/HTML）│         │ ① 细粒度权限（谁可以看哪篇）  │
│ ② 自动解析、分块、向量化入库  │         │ ② 多租户（多个部门独立知识库） │
│ ③ 自然语言提问，返回答案+出处 │         │ ③ 文档自动同步/增量更新       │
│ ④ 支持多文档批量检索          │         │ ④ 用户反馈与答案纠错闭环       │
│ ⑤ 可配置的大模型提供商        │         │ ⑤ 移动端 App                 │
└─────────────────────────────┘         └─────────────────────────────┘

判断标准一句话：用户能不能"上传→提问→拿到有出处的答案"走过完整闭环。能，就是 MVP 合格；不能，说明功能砍得不对。这里反复强调的也是这个闭环——先让一条链路走通，再谈锦上添花。

坑在哪
现象原因
以为"多文档上传"必须配"权限管理"，否则不敢上线权限是运营问题不是技术问题：MVP 阶段可以先把文档人工审核后入库，权限留在二期。把权限塞进 MVP 会拖垮进度
以为 MVP 就要"支持所有格式"MVP 只做 4 种格式（PDF/Word/MD/HTML），Excel、图片等排在以后。格式覆盖广 = 解析工作量爆炸，先把最常用的做透
把"回答质量"当 MVP 验收标准第一版验收的是链路通：解析入库成功、检索能命中、答案有出处。质量优化是持续迭代的事，不是第一版的完工线
3③ 系统骨架：企业级 RAG 的五层架构
要解决什么

阶段6的演示是 7 个脚本一溜排开。但企业版要面对：多种格式、海量文档、多用户并发、可配置的模型供应商。没有清晰的层次划分，代码会随着需求膨胀成一坨。

核心思路

项目把系统分成 5 个相对独立的模块，每一层只干一件事、只对上一层负责：

┌────────────────────────────────────────────────────────┐
│  前端（Vue3 + Element Plus 网页界面）                    │
│  上传文档 / 提问 / 展示答案与来源                         │
└──────────────────────────┬─────────────────────────────┘
                           │ HTTP 请求
┌──────────────────────────▼─────────────────────────────┐
│  API 层（FastAPI 路由）                                 │
│  /api/chat 问答  /api/document 上传  /api/health 健康检查│
└──┬──────────┬──────────┬──────────┬────────────────────┘
   │          │          │          │
┌──▼───┐ ┌───▼────┐ ┌───▼────┐ ┌──▼────────┐
│ 解析层 │ │ 嵌入层 │ │ 检索层 │ │ LLM 层     │
│ PDF/Word│ │ 在线/本地│ │ 向量库  │ │ 智谱/通义  │
│ MD/HTML│ │ 模型    │ │ 查topK │ │ 生成回答   │
└───────┘ └────────┘ └────────┘ └───────────┘
       共享的数据库层：文档元数据（你在哪）+ 向量数据（你像什么）

记住两个流向：

  • 入库方向：文档 → 解析 → 清洗 → 分块 → 嵌入成向量 → 存进向量库（离线，做一次）
  • 问答方向：提问 → 嵌入成向量 → 向量库检索 topK → 拼进 Prompt → 大模型生成答案（在线，每次）

后面的五章，正好一章覆盖一层（解析、清洗分块、嵌入存储、检索生成、API 前端）。

坑在哪
现象原因
以为"向量库就够存了，为什么还要数据库层"向量库只管"哪些向量离我近"，但文档本身、标题、来源文件、上传时间这些元数据也要管理，否则"答案出自哪份文档"无法回答。项目里 DocumentStore 就是干这个的
以为 5 层必须一次全部建好分层是逻辑边界不是物理分工：MVP 里解析层和嵌入层可以是同一个服务进程。先把层分清楚，别急着拆微服务
把"前端"当可有可无企业用户不是程序员，没有网页界面系统就"不存在"。工程里 frontend 单独成一个目录，前端也是交付物之一
4④ 向量数据库选型：四个候选怎么权衡
要解决什么

RAG 的核心是"海量向量里找近邻"。市面上向量数据库一抓一大把，选错了要么过度设计（部署复杂、维护成本高），要么性能翻车（几万条就卡）。选型不是选"最强的"，是选"匹配当前规模的"。

核心思路

先对比四类主流方案，看各自定位：

方案本质适合场景代价
Milvus分布式向量数据库，独立集群千万级向量、高并发生产环境组件多（etcd/MinIO/Pulsar），部署运维重
QdrantRust 写的高性能向量库百万级、要快又要轻是独立服务，仍需多部署一个进程
PGVectorPostgres 的向量扩展公司已有 PG，向量量不大大规模检索性能一般，索引调参有门槛
FAISSMeta 出的算法库（不是数据库！）研究、离线批量算相似度无服务、无持久化方案，需自己包

本项目最终选了轻量嵌入式方案（ChromaDB），而不是上面四个。理由很清楚：MVP 阶段文档量是几万到几十万条向量，单机嵌入式足够；先求"装得进、跑得动、改得快"，等量级上来再换 Milvus。而"换"之所以可行，正因为它屏蔽在抽象接口后面（第⑦点讲）。

坑在哪
现象原因
以为"选 Milvus 更专业、一步到位"项目还没上线先背一套分布式集群，运维复杂度直接把团队拖垮。选型和业务量级强相关：先轻后重，接口留好替换余地
把 FAISS 当"数据库"用FAISS 是算法库，不负责持久化——进程一退数据全没。生产落地必须自己补存储，这正是它排在这类项目之后的原因
看性能评测只比"查询多快"还要比易用性、部署成本、生态。Chroma 胜在"pip 装完就能用 + 自带持久化"，对 MVP 这才是关键指标
5⑤ 嵌入模型选型：在线 API vs 本地模型
要解决什么

文本要变成向量才能进向量库。但"用哪个模型来变"是个要命的选择：在线 API 接入简单、效果稳定，但数据要发给第三方且按量计费；本地模型离线私密、可定制，但要在自己的机器上推理，慢且占资源。 对"企业私有文档"这个场景，两者都是真实需求。

核心思路

项目干脆两种都支持，用一个接口统一起来（第⑥点的抽象），配置里选一种：

维度在线嵌入（OpenAI 兼容接口）本地嵌入（sentence-transformers）
代表智谱 embedding-2、通义 text-embedding-v4BAAI/bge-small-zh-v1.5 等
接通成本申请 Key、填 base_url 就行下模型权重，可能要按 GPU
数据隐私文本出内网完全离线，私有文档不出内网
性能快、吞吐高取决于本机，小模型可 CPU 跑
成本按 token 计费一次性部署，之后免费
中文效果好BGE 系列中文效果好，社区公认

选型结论：对"企业私有文档"，本地嵌入是长期正解（数据不出内网是大前提），但直接上手本地模型有门槛，所以 MVP 阶段可以先用在线 API 跑通链路，接口留好，随时能切。

坑在哪
现象原因
以为"嵌入模型必须和大模型同厂商"不需要。嵌入是独立的模型，和回答用的大模型没有任何绑定——你可以用智谱的嵌入 + 通义的大模型，接口层都兼容
以为"本地模型一定比 API 慢到不能用"bge-small-zh 这样的小模型在 CPU 上也能跑，几十毫秒级。慢的是大语言模型推理，不是嵌入
只顾模型效果不管向量维度更换嵌入模型后向量维度可能变了（如 1024→768），旧库里的向量和新向量对不上，检索直接失效。换模型 = 全库重嵌，这是最容易被忽略的坑
6⑥ LLM 大模型选型：为什么是"智谱 + 通义"双提供商
要解决什么

大模型的 API 各家协议不统一：有的叫 chat/completions，有的走自家 SDK。如果代码里写死某一家，将来换供应商就得改业务代码——这对"要能选型、要能切换"的企业项目是不可接受的。

核心思路

关键决策：选"OpenAI 兼容接口"的模型厂商，用一个统一客户端调用。

比对结论：

候选特点本项目判断
智谱 GLM（zhipu）中文好、glm-4 系列支持 OpenAI 兼容接口✅ 入选
通义千问（qwen）阿里系、qwen-plus 等支持 OpenAI 兼容✅ 入选（备选/切换）
其他（如 DeepSeek 等）同样兼容 OpenAI 协议架构上随时可加
  • 为什么两个都配：企业怕供应商单点故障，也想要价格/效果的比价空间——配置里换个 provider 字段就切换，业务代码一行不用改。
  • 为什么"兼容 OpenAI 协议"是关键：意味着项目里只要保留一个 OpenAI 风格客户端（base_url + api_key + chat/completions），就能同时接两家，不需要为每家写一套 SDK 适配。
# 项目里统一这样接（示意，真实 Key 从环境变量读）：
client = OpenAI(
    api_key=os.environ["LLM_API_KEY"],          # 绝不写死
    base_url=os.environ["LLM_BASE_URL"],        # 指向智谱或通义的兼容端点
)
# 换供应商 = 改两个环境变量，代码不动
坑在哪
现象原因
以为"同时接两家 = 写两套代码"正因为两家都兼容 OpenAI 协议，一套客户端够用。不兼容的模型才需要写适配层
把 API Key 写死在代码或配置仓库里Key 泄露 = 别人拿你的 Key 花你的钱。项目做法：Key 放 .env 环境变量，代码用 os.getenv() 读，.env 不进 git（教程里的真实 Key 全部换成 os.environ[...] 占位）
以为"模型越强大越好，直接上旗舰"论效果旗舰当然好，但成本、延迟、限流都是企业要算的账。项目把模型名做进配置可调，方便按场景权衡
7⑦ 贯穿全项目的设计主心骨：接口抽象，一切可替换
要解决什么

选型最大的风险不是"选错"，而是"选错了代价巨大"。今天用 Chroma，明天要换 Milvus；今天用 API 嵌入，明天要换本地模型。如果代码直接调具体实现，任何一次替换都是伤筋动骨的重构。

核心思路

项目从第一行代码就贯彻一个原则：面向接口编程，具体实现藏在接口后面。 每个核心组件都先定义抽象基类：

组件抽象基类它锁定的"能力契约"
文档解析BaseParserparse(path) -> 清洗后的文本
嵌入模型BaseEmbeddingembed_text() / embed_batch() / get_dimension()
向量存储BaseVectorStoreadd() / search() / stats() / clear()
大模型LLMgenerate() / generate_stream()

业务代码只认接口，不认实现。于是：

  • 换向量库 = 新写一个 MilvusStore(BaseVectorStore)，业务零改动；
  • 加一家 LLM = 配置里加一条 LLM_PROVIDERS，代码零改动。

这就是为什么刚才选型可以"先轻后重、先贵后本地"——试错成本被抽象接口压到了最低。

8⑧ 本章决策汇总：一个表记住所有选型
要解决什么

讲了三页选型，落地前需要一张"拍了板的清单"，后面每章写代码都对照它，不再纠结。

核心思路
决策点拍板结果一句话理由
系统形态前后端分离的网页应用企业用户要能浏览器直接访问
后端框架FastAPI异步性能好、自动文档，阶段2已验证
前端Vue3 + Element Plus组件全、中文生态好
文档格式PDF / Word / Markdown / HTMLMVP 最常用的 4 种
向量库ChromaDB（轻量嵌入式）小规模够用、自带持久化、换得起
嵌入模型在线 API + 本地模型双支持先跑通再私有化，接口统一
大模型智谱 GLM + 通义千问双提供商都兼容 OpenAI 协议，一个客户端切换
配置方式.env 环境变量密钥不入库、供应商可切换
代码组织按"能力"分模块 + 接口抽象每层可独立替换，试错成本最低

这张表就是整个阶段的"宪法"——后面每一章的实现，都能在这一行里找到依据。
