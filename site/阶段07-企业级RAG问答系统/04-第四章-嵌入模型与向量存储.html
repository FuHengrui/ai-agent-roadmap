第四章　嵌入模型与向量存储

阶段 7 · 企业级RAG问答系统　|　实操　|　难度 ★★★
这一章在解决什么问题

上一章的分块还只是文本。文本不能直接"检索相关性"——你得先把它变成计算机能手拉手的"向量"，再存进一个能"按相似度找邻居"的仓库。这两件事，就是这个 RAG 项目里最核心、最"AI"的一段：嵌入模型负责"翻译"，向量库负责"存储和找近邻"。

这一章解决三个问题：文本怎么变成向量（嵌入）、谁来变（在线 API vs 本地模型）、变完之后存哪、怎么按相似度查（向量存储）。它会引出贯穿全项目的两条抽象接口：BaseEmbedding 和 BaseVectorStore。

这一章在整个知识库里的位置 上一章：文本清洗与智能分块——把文档变成了干净的小块文本 本章 ← 你在这里：嵌入模型与向量存储——把小块变成向量、存进向量库 下一章：检索与 LLM 生成——用户提问时去向量库找最近的块，拼成提示词生成答案 阶段终点：企业级 RAG 问答系统——入库链路到此完整，下一半是问答链路
这一章你要达到什么程度

8 个知识点，动手跑代码。学完你能：说清 embedding 是什么、为什么语义相近的文本向量相近；能区分在线嵌入和本地嵌入怎么选；能讲出 BaseVectorStore 背后的设计意图，以及 Chroma 里存了哪些字段、检索时怎么用 metadata 过滤。

1① 嵌入（Embedding）：把"意思"翻译成"数字"
要解决什么

计算机不认识"年假 15 天"和"带薪休假时长"，只认数字。你要让机器判断"这个问题和哪段文档相关"，必须先把两边都变成它能算的数字。光靠关键词匹配是假的相似——"假期"和"休假"字不一样，但意思一样。

核心思路

嵌入就是"把一段文本变成一个向量（一串数字）"的模型能力：

"公司年假是几天"  →  [0.021, -0.314, 0.117, ..., 0.008]   （比如 768 维）
"年休假天数规定"  →  [0.019, -0.298, 0.125, ..., 0.011]   （语义相近 → 向量也相近）

关键性质：语义越接近的文本，向量在多维空间里离得越近。所以"找相关文档"就变成了"找最近的向量"——这就把语义检索变成了数学运算，向量库专干这个。

为什么"翻译"质量重要：嵌入模型决定了"相似"判断的基准。同一个问题，中文领域用中文语料训练过的模型（如 BGE 系列）判定"年假≈休假"，错位的模型可能判成完全不相关。

坑在哪
现象原因
以为向量是"加密后的原文"，能反解出来看向量是不可逆的语义投影——两个向量相近说明语义相近，但你不能从向量还原出原文。所以原始文本必须另外存，检索后才有得拼提示词
以为"向量维度越大越准、价格越便宜越好"维度大更占存储、更慢，且不是线性的精度收益；维度小可能丢语义细节。按实际场景选，标注模型名称+维度，别拍脑袋
2② 为什么要抽象嵌入接口：BaseEmbedding
要解决什么

嵌入模型有两种完全不同的来源：在线 API（调接口拿向量）和本地模型（自己跑推理）。如果业务代码直接调某个具体的 SDK，将来"从在线切到本地"就要改所有调用处。这里需要一个统一的"向量翻译官"接口。

核心思路

项目定义 BaseEmbedding 抽象类，锁三个能力：

class BaseEmbedding(ABC):
    @abstractmethod
    def embed_text(self, text: str) -> list[float]:
        """单个文本 → 向量"""

    @abstractmethod
    def embed_batch(self, texts: list[str]) -> list[list[float]]:
        """一批文本 → 一批向量（分块后一次全嵌）"""

    @abstractmethod
    def get_dimension(self) -> int:
        """向量维度（入库前要校验，见坑位）"""

两个具体实现都实现这套接口：

实现底层特点
OpenAIEmbedding（在线）OpenAI 兼容接口（智谱/通义）配置 base_url + key 即用
LocalEmbedding（本地）sentence-transformers + BGE离线、私密，维度等可自选

上层（向量存储、检索）只知道 BaseEmbedding，换实现只改配置。这正是第1章"一切可替换"的又一次落地。

坑在哪
现象原因
维度不校验就混存换模型后维度变了（768→1024），新旧向量没法比相似度。入库前必须 get_dimension() 校验并记录模型版本
一条条调用 embed_text慢且费网络请求。批量 embed_batch 一次送几十条，分块入库就是这么玩的
在线嵌入不处理失败API 会限流/超时。项目里要加重试（tenacity 这类），否则入库跑到一半断掉
3③ 在线嵌入：OpenAI 兼容接口的"一鱼两吃"
要解决什么

在线嵌入的接入方式和第1章大模型一样，有个免费的午餐：智谱、通义等厂商的 embedding 接口都兼容 OpenAI 协议——意味着你不需要每家学一套 SDK，一个客户端全搞定。

核心思路

看项目 OpenAIEmbedding 的做法：

from openai import OpenAI

class OpenAIEmbedding(BaseEmbedding):
    def __init__(self):
        # 示例：智谱 embedding-2；通义 text-embedding-v4 同理换 base_url/model
        self.client = OpenAI(
            api_key=os.getenv("ZHIPU_API_KEY"),            # 密钥只从环境变量来
            base_url=os.getenv("ZHIPU_BASE_URL"),
        )
        self.model = "embedding-2"                          # 模型名可配置

    def embed_batch(self, texts):
        resp = self.client.embeddings.create(model=self.model, input=texts)
        return [d.embedding for d in resp.data]

三个要点：base_url 可配（换厂商只改配置）、api_key 走环境变量（绝不写死）、embedding API 和 chat API 是两码事（同一家平台里两个端点，别混）。

在线嵌入的取舍（接第1章）：接得快、效果好、按量计费；代价是文本要出内网。所以它适合"先跑通"，不适合"私有文档长期居住"。

坑在哪
现象原因
批量嵌入时偶发失败/限流，入库跑一半断掉在线 API 有 QPS 和超时限制，没有重试机制就会中断。项目里用 tenacity 这类库加重试，失败重试而不是整体重来
模型名填错（如写成"embedding"而不是"embedding-2"）各家模型名不是通用的，填错直接 4xx。模型名来自你开通平台的模型列表，且和 chat 模型名是两码事
4④ 本地嵌入：sentence-transformers + BGE，数据不出内网
要解决什么

企业文档最敏感的就是"不想出内网"。在线嵌入把每段文本都发给第三方，再好的效果也过不了合规关。本地嵌入把模型装在自己机器上，推理全程离线——这是企业私有化部署的基本盘。

核心思路

项目 LocalEmbedding：

from sentence_transformers import SentenceTransformer

class LocalEmbedding(BaseEmbedding):
    def __init__(self, model_name: str = "BAAI/bge-small-zh-v1.5"):
        self.model = SentenceTransformer(model_name)   # 首次会下载权重

    def embed_batch(self, texts):
        return self.model.encode(texts, normalize_embeddings=True).tolist()

选择要点：

  • BGE 系列（BAAI/bge-small-zh-v1.5 等）是中文场景的社区主流，效果好、体积小（small 版几百 MB），CPU 也能跑，不需要 GPU 就能起步；
  • normalize_embeddings=True：把向量归一化成单位长度——这样"余弦相似度"可以直接用向量点积算，检索时保持一致。

本地嵌入的取舍：离线、私密、一次部署终身免费；代价是首次下载模型、推理吃本机资源。和在线版共用 BaseEmbedding，配置里挑一个。

坑在哪
现象原因
BGE 模型 encode 的结果不归一化后续用点积算相似度会失准。要么归一化，要么检索时用余弦，两头要一致
首次运行卡在"下载模型"权重在 HuggingFace，网络受限时下载失败。生产环境要预下载/镜像/离线打包
以为 small 模型效果肯定差中文 RAG 场景 small 版往往够用且快；先用小模型跑通，效果不够再换大的，这是省钱节奏
5⑤ 向量存储解决什么问题：从"暴力扫描"到"近邻索引"
要解决什么

向量有了，存哪？朴素做法：存个列表，检索时挨个算相似度。几万条没关系，几百万条就是灾难——每次提问都把全库算一遍，响应要按秒甚至分钟计。向量存储的本质是给"找近邻"这件事做的优化。

核心思路

向量数据库（或带索引的向量存储）解决的问题：在大规模向量集合里快速找到与查询向量最相似的前 K 个。

做法原理规模上限速度
暴力扫描全库算一遍相似度~10 万级慢
近邻索引（HNSW 等）建图/树结构，快速剪枝逼近最近邻百万-千万级亚毫秒-毫秒级

项目选用的 Chroma：轻量、嵌入式、自带持久化（上一阶段已用过），索引和暴力都支持，小规模起步完全够。它在企业版里被封装在 BaseVectorStore 后面，将来要换 Milvus 等大规模方案，换实现不换接口。

坑在哪
现象原因
以为"向量库都要先部署一个服务，好重"只有 Milvus/Qdrant 那种才要独立部署。Chroma 是嵌入式库，pip install 完直接嵌进进程用，还能持久化到磁盘——这就是 MVP 阶段不碰服务编排的原因
检索时拿到一堆向量，但拼不出给大模型的文本向量库里只存向量+id 不够，必须连原文一起存（Chroma 的 documents 字段）。检索结果要能直接拿 text 去拼 Prompt
6⑥ 向量存储接口与数据模型：存什么、怎么查
要解决什么

"存向量"听上去简单，但落地要回答一堆问题：除了向量还存什么？查询时除了向量还要带什么条件？搜出来怎么排序？ 先定好数据模型和接口，存储实现才不会五花八门。

核心思路

一是数据模型，一个块（chunk）入库时带全信息：

@dataclass
class Document:
    text: str                    # 块原文（供大模型引用）
    embedding: list[float]       # 向量
    metadata: dict               # 来源文档、块序号、页等
    doc_id: str                  # 文档/块唯一 ID

@dataclass
class SearchResult:
    document: Document
    score: float                 # 相似度得分

二是抽象接口 BaseVectorStore，锁四个能力：

class BaseVectorStore(ABC):
    @abstractmethod
    def add(self, documents: list[Document]): ...
    @abstractmethod
    def search(self, query_embedding: list[float], top_k: int,
               metadata_filter: dict | None = None) -> list[SearchResult]: ...
    @abstractmethod
    def stats(self) -> dict: ...        # 有多少条、占多少
    @abstractmethod
    def clear(self) -> None: ...        # 清库（测试/重建用）

「按相似度查前 K 个」是核心，但 metadata_filter 告诉你：检索可以叠加条件（比如只要某个 namespace 或某类文档）——这为第5章的检索模块留了接口。

7⑦ Chroma 实现：持久化、距离函数与 metadata 过滤
要解决什么

抽象定了，具体实现要落地一堆细节：向量存哪（内存还是磁盘）、相似度怎么算、metadata 怎么查到。Chroma 把这些都提供好了，你要做的是正确的姿势接起来。

核心思路

项目 ChromaStore：

import chromadb

class ChromaStore(BaseVectorStore):
    def __init__(self, path: str = "./chroma_data", collection: str = "documents"):
        self.client = chromadb.PersistentClient(path=path)   # 持久化到磁盘
        self.collection = self.client.get_or_create_collection(
            name=collection,
            metadata={"hnsw:space": "cosine"},               # 距离函数
        )

    def add(self, documents):
        self.collection.add(
            ids=[d.doc_id for d in documents],
            embeddings=[d.embedding for d in documents],
            documents=[d.text for d in documents],
            metadatas=[d.metadata for d in documents],
        )

四个关键决策：

  • PersistentClient：数据落磁盘，进程重启不丢（FAISS 之类的纯内存方案做不到）；
  • hnsw:space=cosine：相似度用余弦——和本地嵌入的归一化搭配，语义匹配最稳；
  • search 时带 metadata_filter：Chroma 支持 where 条件，比如只搜某个 namespace；
  • collection 概念：不同知识库/文档集可拆成不同 collection，互不干扰。
8⑧ DocumentStore：把整条入库链路焊成一个服务
要解决什么

到这儿，解析、清洗、分块、嵌入、存储每个零件都有了，但用户上传一个文档，系统要一气呵成走完整条流水线。没人把装配线搭好，这些零件还是散的。

核心思路

DocumentStore 就是这条装配线的总调度（database 层），它干三件事：

① 入库 add_document(file)：
   解析 → 清洗 → 分块 → 嵌入 → 存入向量库 → 登记文档元数据表

② 查询 search(query)：           ③ 元数据管理 / stats / delete
   嵌入查询 → 向量库检索 topK    文档表里记录了"哪些文档已入库、
   → 返回带来源的结果            每个文档多少块"，支持按文档删库

它同时管理两个存储：向量库（存的向量，管"像不像"）+ 文档元数据表（存的文档清单，管"是谁"）。namespace/collection 隔离让"上传多份文档、按文档检索"成为可能。这也是为什么第2章的目录里 database 单独一层——它把"解析+嵌入+存储"的编排集中在这一个服务里。

坑在哪
现象原因
重复上传同一个文档，库里出现两套一样的向量add_document 没先按 doc_id 去重/更新。入库前查重，同一文档重复上传要么跳过要么覆盖旧块
只清向量库不清元数据表（或反过来）两个存储不同步，"库里有 10 块但文档表说没有"这类脏状态会咬人。增删文档要同时操作两处（这正是 DocumentStore 统一编排的价值所在）
