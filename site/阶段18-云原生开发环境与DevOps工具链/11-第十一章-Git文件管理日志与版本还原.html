第十一章　Git 文件管理、日志与版本还原

阶段 18 · 云原生开发环境与 DevOps 工具链　|　版本控制　|　难度 ★★★
这一章在解决什么问题

上一章你学会了"改 → add → commit"。这一章解决三个高频痛点：怎么翻历史（log）、怎么看改动（diff）、怎么反悔（reset / checkout）。

写代码最贵的是"改坏了恢复不回来"——这一章的还原能力就是你的后悔药，同时它也是面试爱问的 git reset 三模式。另外，"哪些文件不该进版本库"（.gitignore）也是在这一章解决。

这一章在整个知识库里的位置 上一章：本地仓库基础——init / status / add / commit 本章 ← 你在这里：本地仓库的"查看"与"回退"——历史、差异、还原、忽略 下一章：本地玩熟练了，接远程仓库和多人协作（push / pull / 冲突）
1① git log：翻开项目的"岁月史书"
要解决什么

commit 提交了几十次之后，你想知道：项目从哪来的？每一步改了什么？哪个版本是"昨天还能用的"？没历史记录只能靠记忆，而 Git 把这一切记在日志里。

核心思路 
git log              # 完整日志：每次提交的作者、日期、说明、提交号
git log --oneline    # 精简模式：每次提交压缩成一行（提交号 + 说明），最常用
git log --graph      # 显示分支合并图，看分支怎么汇合的（第十三章会用到）

--oneline 输出的每一行就是一个版本，最左边是提交号（一个很长的哈希，通常看前几位就够引用）。

坑在哪
现象原因 / 怎么办
git log 输出很长，卡在冒号界面退不出来这是分页查看器，按 q 退出；想要直接输出，用 --oneline
日志里看不到刚做的 commit先确认是否真的 commit 成功（git status）；仓库从未 commit 过时 git log 会报 "does not have any commits yet"
提交号太长记不住用前几位即可，如 git show a1b2c3d，Git 能自动补全
2② git reflog：连"后悔"都能后悔
要解决什么

git log 只能看到当前分支的历史。如果一次 reset / checkout 把分支退回了旧版本，那些新提交在 log 里就"消失"了——难道真的找不回了吗？Git 留了后门：reflog 记录了你在本地仓库做过的每一次移动。

核心思路 
git reflog     # 列出 HEAD 的历史移动记录（每次操作一条）

输出里能看到你执行过的 reset、checkout、commit 等操作，以及每次操作前后的提交号。它相当于"操作流水账"：哪怕分支被回退、被误删，只要操作发生过，就能从 reflog 里找到目标提交号，再把它捡回来。

坑在哪
现象原因 / 怎么办
reflog 找不到很久以前的记录reflog 有保留期限，而且只记本地操作；想长期留住历史，靠 git log 和标签（第十四章）
以为新克隆的仓库有完整 reflogreflog 是本地的，新克隆的仓库 reflog 几乎是空的——远程历史要用 git log 看
3③ git diff：看清"到底改了什么"
要解决什么

"我记得改了 a.txt，但改了啥来着？" commit 之前想核对一下改动，或者想确认这次提交动了哪些行——肉眼看不出差异，需要 Git 给出"差异报告"。

核心思路

git diff 有两种常见用法，比较对象不一样：

git diff                # 工作区 vs 暂存区：你改了什么还没 add
git diff --cached       # 暂存区 vs 版本库：你已经 add 了，这次提交会带什么进去

diff 输出里的符号含义：

符号含义
--- / +++前面的代表原始文件，后面的代表新文件
- 开头行原始文件中被删除的行
+ 开头行新文件中增加的行
@@ ... @@这次改动所处的行号上下文
坑在哪
现象原因 / 怎么办
add 之后再 git diff 没输出正常！add 后工作区和暂存区一致了；要看已暂存差异得用 git diff --cached
diff 输出中文乱码终端编码问题；换 Git Bash 或把终端编码调成 UTF-8——不影响文件本身
4④ 还原情况一：改了但没 add → checkout 丢掉修改
要解决什么

改着改着发现思路全错，文件被改得面目全非，想把工作区恢复成和版本库一致的干净状态。

核心思路 
git checkout -- aaa.txt   # 用仓库里的版本覆盖工作区，丢弃对 aaa.txt 的修改
git checkout -- .         # 丢弃当前所有文件的未提交修改（危险，先确认）

这条命令只作用于工作区：把文件"拉回"未修改的状态。这里有个关键点：这些改动没有 add 过、也没有 commit 过，丢弃之后无法找回——用之前务必想清楚。

坑在哪
现象原因 / 怎么办
以为这里 checkout 是"切换分支"后面跟路径就是还原文件，跟分支名才是切换分支（第十三章）——搞混会做错事
执行前没确认，改了半天全没了先 git status / git diff 看清楚要丢什么，确认要丢再 checkout
5⑤ 还原情况二：add 了但没 commit → 取消暂存再还原
要解决什么

改完顺手 git add 了，现在发现改错了想整体放弃。此时直接用 checkout -- 还原的是暂存区的版本（等于把暂存内容拷回工作区，改错的内容还在），不彻底。

核心思路

两步走：先取消暂存，再丢弃修改：

git reset HEAD            # 把所有文件移出暂存区（回到 modified 状态），不影响文件内容
git checkout -- aaa.txt   # 再把 aaa.txt 还原成仓库版本，丢掉所有改动

逻辑上等于：先让暂存区"忘记"这次 add，然后走情况一的还原。注意这里的 git reset HEAD 不带 --hard，不会丢文件内容。

坑在哪
现象原因 / 怎么办
只用 git reset HEAD，发现文件内容没变回原样正常！reset 只取消暂存；要还原内容还得加 checkout --
把 HEAD 写成小写 headHEAD 要大写（Git 的内部标记）；写错会报错或当成普通分支名处理
6⑥ 还原情况三：已经 commit → reset 回到上一个版本
要解决什么

已经 commit 了，提交后发现这个版本是错的，想回到上一个提交的干净状态。这时工作区、暂存区、仓库里都有记录，还原意味着"三个房间一起回退"。

核心思路 
git log --oneline        # 先看历史，确定要回到哪个版本
git reset HEAD^          # 回到上一个提交（当前 commit 作废）
git checkout -- aaa.txt  # 把文件内容也还原成仓库版本

HEAD 的几种写法：

写法含义
HEAD当前版本
HEAD^上一个版本
HEAD^^上上一个版本（几个 ^ 就是往前几步）

git reset 版本号 可以回退到 git log 里显示的任意一个提交——HEAD^ 只是"上一个"的快捷写法。

坑在哪
现象原因 / 怎么办
reset 之后新提交在 log 里消失了，以为代码丢了提交对象还在，只是分支指针移走了；用 git reflog 找到原提交号可以再回来
以为 reset 一定会丢工作区的修改不带 --hard 的 reset 只动暂存区/分支指针，工作区文件不动；会不会丢，取决于你用哪种模式（下一点）
7⑦ git reset 的三种模式：soft / mixed / hard
要解决什么

同一个 git reset，为什么有人说是"安全"的、有人说"会丢代码"？因为 reset 有三种模式，回退的彻底程度不一样——这是面试高频，也是新手最容易翻车的地方。

核心思路 
git reset --soft HEAD^     # ① 只把分支指针回退；暂存区、工作区都不动
git reset --mixed HEAD^    # ② 分支指针回退 + 暂存区清空；工作区不动（默认模式，不加参数就是这个）
git reset --hard HEAD^     # ③ 三个房间全回退：分支指针、暂存区、工作区全部变成旧版本
模式分支指针暂存区工作区风险
--soft回退保持保持最低，改动都能找回
--mixed（默认）回退清空保持低，文件内容没丢，只是变回"未暂存"
--hard回退清空覆盖还原高：未提交的改动直接丢失

--hard 是核弹按钮——用之前务必确认工作区没有你要留的东西；一旦用了，想反悔只能靠 reflog 找提交号。

坑在哪
现象原因 / 怎么办
reset --hard 后发现有文件忘了备份先 git reflog 找之前的提交号，git reset --hard 那个提交号 还能救；如果改动从没 commit 过，救不回来
不记得 reset 默认是什么模式默认 --mixed：只清暂存区，工作区文件不动——所以"reset 会丢代码"多半是用了 --hard
8⑧ 删除文件：git rm 与"直接删"的区别
要解决什么

项目里某个文件不要了，直接右键删除就行——那 Git 干嘛还要专门教 git rm？区别在于：git rm 会把这个"删除动作"也纳入版本管理。

核心思路 
git rm 文件名        # 删除工作区文件，并把这个删除放进暂存区（等着和提交一起落库）

关键点：

  • git rm 删掉的只是工作目录里的文件，版本库里的历史快照还在——删掉的内容仍然可以从历史中恢复；
  • 直接在资源管理器里删除（或 rm 文件），对 Git 来说只是文件变成了 deleted 状态，仍然需要提交这个"删除"，commit 后删除才会真正落库（此时 status 里它从"已跟踪"变为待提交的删除）。
坑在哪
现象原因 / 怎么办
手动删了文件，status 显示 deleted正常！在 Git 眼里这算一次"修改"；用 git rm（或 git add）把它提交掉
以为 git rm 后文件彻底没了只是工作区没了；版本库历史里还留着，用 checkout 能救回来（下一点）
9⑨ 挽救误删/改坏的文件：git checkout 兜底
要解决什么

"人有失手，马有失蹄"：不小心把项目中所有 .html 删了、或者把文件改坏想恢复……Git 的还原能力是使用版本控制最主要的理由之一，这里就是现场。

核心思路 
git checkout aaa.txt    # 把 aaa.txt 从版本库拉回工作区（覆盖当前内容）
git checkout .          # 把当前目录下所有被删/被改的文件恢复成仓库版本

原理：git checkout 接文件名时，会把暂存区或版本库中的内容复制到工作区，覆盖现有文件——删掉的回来了，改坏的也复原了（前提是它之前 commit 过）。这个小技巧不仅能救删除，改某个文件后反悔了，也可以用它恢复。

大前提：整个 Git 记录都在根目录的 .git 目录里。要是 .git 被删了，历史就没了，文件也就救不回来了。

坑在哪
现象原因 / 怎么办
checkout 一个从未 commit 过的新文件报错 "did not match any file(s)"——版本库没存过它，救不回来；新文件尽快 commit 才安全
误删 .git 目录这是唯一"历史彻底没了"的操作；删前先备份，别手滑
10⑩ .gitignore：把不想管的文件挡在门外
要解决什么

每次 git status 都刷出一堆你根本不想提交的文件：编译产物（target/、*.class）、日志、本地配置……它们不该出现在版本库里，也不该天天在 status 里刷存在感。Git 给了黑名单机制。

核心思路

在项目根目录创建固定文件名 .gitignore，把要忽略的模式写进去：

# 忽略规则示例
target/          # 忽略名为 target 的整个目录（斜杠结尾 = 目录）
*.class          # 忽略所有 .class 文件（* 通配任意多个字符）
index.class      # 忽略指定文件
[ab].class       # 忽略 a.class 和 b.class（[] 匹配列表中的单个字符）
?.log            # 忽略 a.log、b.log 这类单个字符开头 + .log（? 通配单个字符）
/public/*        # 忽略 public 目录下的所有内容
!/public/assets  # 但 public/assets 特例放行（! 表示不忽略）

规则速记：* 通配多个字符、? 通配单个、[] 匹配字符列表、! 取反放行、结尾 / 表示目录、开头 / 表示相对当前目录。至于 .gitignore 本身要不要提交？——要！它是团队共用的"物业公约"，应该进版本库。

坑在哪
现象原因 / 怎么办
忽略规则不生效，文件还是 untracked先看是不是已经被跟踪了（下一点）——忽略只对"还没被 Git 管理"的文件有效
规则写得太宽，.gitignore 自己也被忽略了常见坑：* 之类的宽泛规则把 .gitignore 也吞了；检查规则别匹配到它自己
分不清 target/ 和 target带斜杠明确表示"目录"，不带斜杠也匹配同名文件——按需选择
11⑪ 已经跟踪的文件，再写忽略规则不生效
要解决什么

你以为写完 .gitignore，那些文件就会"自动消失"？不会。 忽略规则只管"还没进版本库的文件"；已经被 add/commit 过的文件，加规则无效——这是新手第一大翻车点。

核心思路

Git 的规矩：已被跟踪（tracked）的文件，.gitignore 管不了它。要"解除跟踪但保留文件"，需要先把它从 Git 管理里移除：

git rm --cached target/   # 把 target/ 从 Git 跟踪里移除（文件还在磁盘上）
git commit -m "移除 target 目录的跟踪"   # 提交这次移除

之后 .gitignore 里的规则才对它生效，新克隆的人也不会再拉到它。

坑在哪
现象原因 / 怎么办
写了 .gitignore，但已提交的文件还是出现在提交里已跟踪文件不受忽略规则影响；先 git rm --cached 解除跟踪再提交
执行 git rm --cached 后以为文件被删了文件还在本地磁盘，只是不再被 Git 跟踪；"文件不见了"是常见误解
