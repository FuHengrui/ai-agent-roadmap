第二十章　镜像仓库与 Docker 架构

阶段 18 · 云原生开发环境与 DevOps 工具链　|　容器化　|　难度 ★★★★
这一章在解决什么问题

你辛苦自建的 Tomcat 镜像，只躺在自己电脑里，同事怎么拿到？换台服务器怎么用？——得有个"货架"把镜像放上去，别人随时取。 同时，学了一路 Docker 命令，也该在架构层面搞明白：你敲的命令到底是谁在执行？镜像为什么是一层一层的？ 本章收官三件事：① 官方仓库 Docker Hub 与阿里云 ACR；② 发布镜像全流程（login/tag/push/pull）；③ C/S 架构与镜像分层原理。

这一章在整个知识库里的位置 上一章：容器网络与联动——容器之间互通 本章 ← 你在这里：镜像的"分发货架" + Docker 的底层架构 阶段终点：能造、能跑、能联网、能发布——Docker 全链路闭环，收官
学习提示

本章有两个小操作环节（注册仓库账号、阿里云控制台开通 ACR），涉及真实账号/密码的地方全部用占位符代替： 真实凭证只在你自己的终端/控制台里操作，永远不要写进笔记、代码或文档。

1① 为什么要把镜像推向远程仓库
要解决什么

镜像在本地，只有你自己能用。想象三个真实诉求：同事要用、换台新服务器要用、团队版本要一致。没仓库怎么办？

核心思路

把镜像推到远程仓库，别人从仓库拉取即可——这就是"货架"逻辑：

诉求没远程仓库有远程仓库
给同事用拷 U 盘/传文件，版本混乱一条 pull，永远最新
换服务器部署重做镜像docker pull 即可
团队统一各改各的以仓库为准
备份/回滚本地误删全没了仓库里还有旧 tag

为什么用仓库而不直接发文件：仓库带版本（tag）、带权限、全世界可达、天然支持团队协作——和代码仓库 Git 一个逻辑。

坑在哪
现象原因 / 怎么办
以为远程仓库就是"网盘备份"仓库是带版本和权限的分发中心，不是备份盘；它不解决"本地跑不起来"的问题，只解决"镜像怎么给别人"
本地镜像删了以为就完了如果推过仓库，随时 docker pull 找回；这正是"推送"常被当作备份手段的原因
2② Docker Hub：全世界最大的镜像货架
要解决什么

先认识最大的一个"货架"长什么样、怎么用。

核心思路

Docker Hub（hub.docker.com）是 Docker 官方 + 社区共享镜像的网站/存储库：

  • 你前面 docker pull openjdk:11 默认就是从它拉的（不指定仓库地址时默认 Docker Hub）；
  • 可浏览、可搜索、可上传自己的镜像；
  • 官方镜像（OFFICIAL）有质量背书，优先用它。
docker pull openjdk:11
        └── 没写仓库地址 ──► 默认去 Docker Hub 找

国内使用常常较慢，所以实践中常用国内镜像加速或国内仓库（下一个知识点）——但概念上它们都是"镜像的货架"。

坑在哪
现象原因 / 怎么办
Docker Hub 上同名镜像很多，不知道怎么选认准 OFFICIAL 标记 + 看星级；第三方镜像的内容不受监管，可能有坑
拉取很慢或超时配置国内镜像加速器（形如 https://xxxx.mirror.aliyuncs.com，xxxx 换成你自己的专属地址）；它只负责加速拉取，不改变镜像本体
3③ 阿里云容器镜像服务 ACR：国内的"货架"
要解决什么

Docker Hub 在海外，国内拉镜像慢、发布也不稳。需要国内可托管的镜像仓库——阿里云 ACR 就是官方答案。

核心思路

ACR（阿里云容器镜像服务） 是云上托管容器镜像、Helm Chart 等制品的地方：

  • 支持全球同步加速、大镜像分发加速、多代码源构建加速；
  • 与阿里云容器服务 ACK 无缝集成（云原生部署的默认搭档）；
  • 对个人/团队开源/内部使用都很友好。

用它的完整链路（后面知识点细讲）：

开通服务 → 建命名空间 → 建镜像仓库 → docker login → docker tag → docker push → 别人 docker pull

命名空间（Namespace）相当于"租户分区"，仓库名是具体镜像的名字。 镜像地址形如：registry.cn-hangzhou.aliyuncs.com/你的命名空间/你的仓库名:版本。

坑在哪
现象原因 / 怎么办
本地拉镜像还是慢配置镜像加速器（上面的形如 https://xxxx.mirror.aliyuncs.com）；它只负责"拉得快"，不改变拉到的内容
分不清"镜像加速"和"ACR"加速器 = 加速拉取 Docker Hub 镜像；ACR = 把你做好的镜像托管/分发的国内仓库，是两码事
4④ 发布到 Docker Hub：login → commit/tag → push
要解决什么

认识了货架，现在把镜像放上去。以官方 Docker Hub 为例走一遍"注册 → 登录 → 打标 → 推送"。

核心思路
# 1. 注册账号（hub.docker.com/signup，邮箱用占位符 yourname@gmail.com 那种，别用真实邮箱） # 登录用户名假设为 yourname # 2. 登录（提示输入密码时不回显，是正常的，别以为卡住了） docker login --username=yourname # 3. 方式A：把&quot;容器&quot;固化成镜像（老式做法） # docker commit -m &quot;镜像描述&quot; -a &quot;作者&quot; 容器id 仓库名:版本 docker commit -m &quot;my tomcat image&quot; -a &quot;yourname&quot; mytomcat yourname/mytomcat:1.0 # 描述 ↑ 作者 ↑ 容器 仓库名:版本 ↑ # 4. 方式B（推荐）：为已有镜像打出&quot;远程库标识&quot; docker tag 镜像id yourname/mytomcat:1.0 # 5. 推送 docker push yourname/mytomcat:1.0

前缀规则：推送到 Docker Hub 的镜像名，要带你的账号名作前缀（账号名/仓库名:版本），仓库才知道放在谁名下。 commit 的定位：docker commit 能把改过的容器快照成镜像（-m 描述、-a 作者），适合临时应急； 正规范式是 Dockerfile + build（第 18 章）——commit 出来的镜像"黑盒"、不可复现，别当常规手段。

坑在哪
现象原因 / 怎么办
登录连不上 hub.docker.com网络问题；换镜像加速/代理，或改用国内 ACR
push 报 "denied: requested access to the resource is denied"镜像名前缀不是你的账号名（如忘了加 yourname/），重新 tag 再 push
密码在终端里被看到/记录docker login 的密码输入不回显，别把密码写进命令行参数，更别写进任何文档
5⑤ 发布到阿里云 ACR：从开通到 push 全流程
要解决什么

国内场景更常用 ACR。把"开通 → 命名空间 → 仓库 → 登录 → 打标 → 推送 → 拉取"整条路走一遍，这是操作型章节的核心练手点。

核心思路
步骤 1：控制台准备（全部用你自己的账号，文档中用占位词）
  1. 登录阿里云控制台 → 搜索容器镜像服务 ACR → 开通（个人版即可练手）；
  2. 创建命名空间：如 mynamespace（一个账号可建多个命名空间，区分项目/部门）；
  3. 在命名空间下创建镜像仓库：填仓库名（如 mytomcat），选地域（如杭州）。
步骤 2：命令行操作
# 1. 登录 Registry（用户名=阿里云账号全名；密码=访问凭证里设置的，用你自己的） docker login --username=你的阿里云账号 registry.cn-hangzhou.aliyuncs.com # 2. 给本地镜像打上&quot;远程库地址&quot;标签 # docker tag [镜像ID] registry.cn-hangzhou.aliyuncs.com/命名空间/仓库名:[版本] docker tag &lt;镜像ID&gt; registry.cn-hangzhou.aliyuncs.com/mynamespace/mytomcat:1.0 # 3. 推送 docker push registry.cn-hangzhou.aliyuncs.com/mynamespace/mytomcat:1.0 # 4. 别人/其他机器拉取（一条命令取回镜像） docker pull registry.cn-hangzhou.aliyuncs.com/mynamespace/mytomcat:1.0
步骤 3：自检
检查项说明
控制台仓库页出现同名镜像push 成功了
tag 里的"地域/命名空间/仓库名"和创建时一致不一致就是 404 / denied
登录成功但 push 失败访问凭证密码没设/过期，去"访问凭证"页重置

整套口诀：开通 → 2 个创建（命名空间、仓库）→ login → tag → push → pull。

坑在哪
现象原因 / 怎么办
push 提示 401 / denied登录凭证不对：用户名是阿里云账号全名，密码用访问凭证（不是登录密码）；按控制台提示重新 login
pull 的地址 404tag 里地域/命名空间/仓库名/版本号和创建时不一致；去控制台复制"推送命令"对照
镜像太大 push 超时大镜像首次全量传输慢；可先 push 小镜像验证链路，或选地域近的节点
6⑥ C/S 架构：你敲的命令，其实发给了"守护进程"
要解决什么

用了这么多 docker 命令，你有没有想过：docker run 到底是谁在干活？搞懂这一点，报错都更看得懂。

核心思路

Docker 是标准 C/S（客户端/服务端）架构：

┌─────────────┐   命令行/API   ┌──────────────────────────┐
│ Docker 客户端 │ ────────────► │ Docker daemon（服务端）     │
│ docker run 等│   socket/HTTP  │ 在宿主机后台跑，真正干活的  │
└─────────────┘                └──────────────────────────┘
部分角色说明
客户端你敲的命令docker xxx 系列命令都在这边，负责把你的意图翻译成请求
服务端Docker daemon（dockerd）宿主机后台常驻，负责创建、运行、分发容器这些脏活累活
通信socket / RESTful API客户端和服务端可在一台机器（默认本地 socket），也可跨机器（-H 指定远端）
# 查看客户端+服务端版本信息（也验证 C/S 连通） docker version # 指定连到另一台机器的 Docker 服务端（把 127.0.0.1:1234 换成实际地址） docker -H tcp://127.0.0.1:1234 ps

认知升级：你敲 docker ps 时，客户端把请求发给 daemon，daemon 查完把结果回传——"docker 命令"本身不干活，干活的是 daemon。

坑在哪
现象原因 / 怎么办
docker 命令全报 "cannot connect to the Docker daemon"daemon 没起来/没权限：先 systemctl start docker，或检查当前用户有没有 docker 组权限
本机能连、远程连不上默认只监听本地 socket；远程访问要配置 daemon 监听 tcp + 证书（生产慎开，裸连不安全）
以为每个 docker 命令都独立干活都是"请求 → daemon 执行 → 返回"；理解这点，daemon 停了 = 所有命令都瘫
7⑦ 联合文件系统 UnionFS：镜像为什么是一层一层的
要解决什么

第 15 章说"容器 = 镜像 + 可读写层"，第 18 章说"每条 RUN 加一层"——"层"到底是什么技术支撑的？答案在 UnionFS。

核心思路

联合文件系统（UnionFS）：一种轻量级、高性能的分层文件系统——把多个目录"叠加"挂载成同一个虚拟文件系统，修改作为"一次提交"层层往上摞。

镜像（只读层，从下往上）
┌───────────────────────┐
│ 层4  CMD/ENV 等         │  ← 越往上越"应用层"
│ 层3  RUN 装 Tomcat     │
│ 层2  RUN 装 JDK        │
│ 层1  基础系统           │  ← 最底下是基础镜像
└───────────────────────┘
       │ 启动容器时，最上面再叠一层可读写层
       ▼
容器视角 = 所有这些层"糊"成一个完整文件系统

关键点：

  • Dockerfile 的每一条指令都生成一个独立镜像层；
  • 容器看到的是"分层叠加后"的完整文件系统，读写发生在最上层可读写层；
  • 镜像层只读、共享：多个容器共用底层，内存里相同内容只加载一份。
坑在哪
现象原因 / 怎么办
以为容器里看到的是"某一个层"容器看到的是所有层叠加后的合并视图，不是某一层；改文件只写最上层
以为"分层"是分区/分文件夹分层是版本化叠加（像 git 提交历史），不是把磁盘切成几块
8⑧ 镜像分层的好处：改底层，全家受益
要解决什么

分层是个"工程决定"，它到底好在哪？三个实打实的好处，理解了就不怕"层"了。

核心思路
好处说明例子
① 底层一改，全体受益基础环境出问题，只需改底层镜像，基于它的所有镜像跟着修复底层 JDK 有漏洞，重建基础镜像，所有应用镜像随之更新
② 资源共享相同环境共用同一底层，不用每个镜像重新造一份10 个镜像都基于 centos，底层只存一份
③ 复用省空间、构建快相同内容只加载一份；改 Dockerfile 后只有变动层重建只改 CMD 那层，前面 3 层直接复用缓存

这解释了第 18 章"合并 RUN"为什么重要：层数越少，镜像越小、构建越快、传输越省。 也解释了"FROM 选好基础镜像"为什么重要：它是所有层的地基，选小了全家都瘦。

坑在哪
现象原因 / 怎么办
改了一行 Dockerfile，构建却还是慢只有从改动那条指令开始往后的层会重建，前面的层"复用缓存"——这正是分层的好处，别误以为卡住
误以为层可以随便加，反正能共享层越多镜像越大（数据不会因为共享而消失）；"少层瘦身"依然是铁律
9⑨ 全链路收官：从构建到分发的完整闭环
要解决什么

最后一站，把阶段 18 的 Docker 能力从头到尾串一遍——形成一个你可以照着做的"生产线"。

核心思路 
第 18 章          第 19-20 章           第 20 章
写 Dockerfile ─► docker build ─► docker login（仓库）
      └─────────► 本地镜像 ─► tag 成远程标识 ─► docker push 上架
                                              │
                      第 16-17 章             ▼
                docker run + 卷 + 网络   ◄── docker pull 部署到任何机器

一条完整生产线（自检清单）：

  1. 造：Dockerfile 定制镜像，docker build -t myapp:1.0 .（配合少层优化）；
  2. 跑：docker run -d --name myapp -p 8080:8080 -v ... myapp:1.0（卷保数据、网络联动）；
  3. 传：docker tag 打上仓库地址 → docker push 上架；
  4. 用：任何机器 docker pull 拉下来直接跑——环境一致达成。

到这里，你已集齐云原生交付的核心闭环：镜像即产物、容器即运行时、仓库即分发。 "Build once, Run anywhere"不再是口号，是你亲手走完的路。
