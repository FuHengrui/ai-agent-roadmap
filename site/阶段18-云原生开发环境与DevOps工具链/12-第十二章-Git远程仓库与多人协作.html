第十二章　Git 远程仓库与多人协作

阶段 18 · 云原生开发环境与 DevOps 工具链　|　版本控制　|　难度 ★★★
这一章在解决什么问题

前面三章你都在自己电脑上玩 Git。现在问题来了：代码在本地仓库里，队友怎么拿到？换台电脑怎么继续工作？怎么备份到云端？

答案是远程仓库：一个放在服务器上的公共仓库，所有队友通过它交换代码。这一章解决：怎么建远程仓库、怎么推送/拉取、冲突到底是怎么回事、怎么解，以及 HTTPS 和 SSH 到底选哪个。

这一章在整个知识库里的位置 上一章：本地仓库的日志、diff、还原——单人开发全流程 本章 ← 你在这里：把本地仓库连上远程（GitHub / Gitee / GitLab），学会 push / pull 和解决冲突 下一章：多人协作的场景再升级——分支，让"并行开发互不干扰"成为可能
1① 代码托管平台：GitHub / Gitee / GitLab 怎么选
要解决什么

Git 只是工具，远程仓库得有个"服务器"来放。自己搭一台服务器又贵又麻烦，直接使用现成的托管平台是绝大多数项目的选择——但平台那么多，选哪个？

核心思路
平台特点适合谁
GitHub全球最大开源社区，生态最全，面向开源及私有项目开源项目、求职作品集、国际化协作
Gitee（码云）服务器在国内，访问快、中文界面国内团队、学校作业、网络不稳定的场景
GitLab开源、可私有部署公司内部自建、需要强管控的场景

选择逻辑：图快选 Gitee，图生态选 GitHub，公司自建选 GitLab。这里用 Gitee 或 GitHub 都行，命令完全一样。

坑在哪
现象原因 / 怎么办
访问 GitHub 经常超时/失败服务器在境外，网络问题不是 Git 问题；换 Gitee，或用代理/加速手段
以为平台之间不兼容三个平台都支持标准 Git 协议，换个 remote 地址就能迁移代码
2② 创建远程仓库 + git remote add：给远程仓库起个外号
要解决什么

在平台上建好了一个空仓库，平台会甩给你一串地址（HTTPS 或 SSH）。本地怎么"认识"这个远程仓库？靠 git remote add——把它登记进来，并起个简称方便以后引用。

核心思路 
git remote add origin https://gitee.com/yourname/my-project.git
#                ↑简称    ↑远程仓库地址（换成你自己的，这里是占位示例）
  • origin 是远程仓库的别名（惯例叫 origin，也可以叫别的）；
  • 以后推拉代码不用敲一长串地址，直接 git push origin 就行；
  • 平台新建仓库一般会给出提示命令，复制 remote add 这一行即可。
坑在哪
现象原因 / 怎么办
直接照抄网上教程里的地址那是别人的仓库！改成你自己平台的仓库地址再执行
配错地址想改git remote set-url origin 新地址 覆盖；或 git remote rm origin 删掉重加
remote add 报 "already exists"已经配过 origin 了；用 git remote -v 查看，再决定改还是删
3③ 查看与移除远程仓库记录
要解决什么

"我到底配了哪些远程？地址对不对？"——查一下就知道。配错了、不要了，怎么移除？

核心思路 
git remote            # 列出所有远程仓库别名（通常只有一个 origin）
git remote -v         # 详细模式：显示别名对应的完整地址（fetch / push 两条）
git remote rm origin  # 移除名为 origin 的远程仓库记录

注意：git remote rm 只是删掉本地这条"远程地址记录"，不会影响远程仓库本身——远程那边的代码还在。

坑在哪
现象原因 / 怎么办
以为 remote rm 就把云端仓库删了不会！它删的只是本地配置；要删云端仓库必须登录平台网页操作
git remote -v 显示两个一样的地址正常：一条是 fetch（拉取用）、一条是 push（推送用），通常相同
4④ git push：把本地提交推上远程
要解决什么

本地 commit 了一堆版本，队友还看不到。把本地仓库的提交同步到远程仓库，让团队都能拉取——这就是 push。

核心思路 
git push origin master       # 把本地 master 分支推送到远程 origin
git push -u origin master    # -u：首次推送时绑定"上游分支"，以后直接 git push 即可
git push                     # 绑定上游之后，可以省略参数直接推送

push 的本质：把本地领先远程的那些提交传过去，不是把整个目录复制一遍。首次推送建议带 -u，绑定一次之后就能简写成 git push。

坑在哪
现象原因 / 怎么办
push 报错 "rejected（被拒绝）"远程有你本地没有的提交 → 需要先 pull 合并后再 push（第⑥⑨点）
push 时一直要输账号密码HTTPS 协议每次都要认证；要么配置凭据缓存，要么换 SSH 免密（第⑪点）
push 上去发现提交作者是别人还是第十章那句话：先检查 git config user.name / user.email 配没配对
5⑤ git clone：把远程仓库"复制"到本地
要解决什么

你不是仓库的创建者，而是新加入的队友；或者换了台电脑要接着干活——本地还没有这个仓库，怎么开始？clone（克隆）：把远程仓库连同全部历史记录原样拉一份到本地。

核心思路 
git clone https://gitee.com/yourname/my-project.git   # 在当前目录克隆下来
git clone https://gitee.com/yourname/my-project.git myapp   # 克隆后本地目录叫 myapp

要点：

  • clone 拉下来的不只是当前文件，还包括全部提交历史（所以克隆大项目会比较久）；
  • clone 后会自动配置好 origin，并且本地分支已和远程关联——不需要再手动 remote add；
  • 克隆的就是"一份完整的库"，这正是分布式的含义。
坑在哪
现象原因 / 怎么办
克隆私有仓库失败仓库是私有的，需要认证：HTTPS 输账号（或令牌），SSH 需要配好密钥
克隆到带空格的目录名命令里给路径加引号，如 git clone <url> "my app"
克隆后直接改代码就 push，被拒别慌，远程可能已有人提交了新内容，先 pull（下一点）
6⑥ fetch 与 pull：拉取代码的两个档位
要解决什么

队友 push 了新东西，你要拿到本地。Git 给了两条命令：git fetch 和 git pull——看起来差不多，但一个是"只下载"，一个是"下载并合并"，用错会有"惊喜"。

核心思路 
git fetch              # 把远程的最新提交下载到本地，但【不合并】进你的工作区
git pull               # fetch + 自动合并（merge）一步到位
  • fetch：只更新"远程分支在本地镜像"（origin/master），你的工作区文件不变；想看内容需要手动合并，比如 git merge origin/master；
  • pull：下载并自动合并，一步到位，日常最常用。

场景建议：想"先看看远程改了什么再决定" → fetch；想"赶紧跟上最新" → pull。

坑在哪
现象原因 / 怎么办
fetch 后文件没变化，以为没拉到fetch 本来就不改工作区；用 git merge origin/master 合并，或直接改用 pull
pull 时本地有未提交的修改可能被拒绝合并；先 commit 本地改动，或先把改动收起来再 pull
以为 fetch 和 pull 可以随便混用记住口诀：fetch 是"看"，pull 是"取并合"
7⑦ 为什么会冲突：两个人改了同一个地方
要解决什么

"我 push 的时候明明没报错，队友 push 就被拒绝：rejected (fetch first)"——然后你就慌了。先理解冲突为什么必然存在：你俩基于同一个旧版本，改了同一处，Git 不知道该保留谁的。

核心思路

两种典型冲突场景：

  1. 不同人改同一文件的同一位置（各自 commit 或 push 后，后 push 的人被拒）；
  2. 同一个分支上：你 pull 了但没立刻 push，同时队友又 push 了一版——两边都动了同样的行。

用生活打比方：两个人都拿"初稿.docx"改第 3 段，一个改成 A 版、一个改成 B 版；合并时到底用谁的？Git 无法替你判断，只能请你裁决——这就是冲突的本质：不是 Git 坏了，是语义上有分歧，机器做不了主。

坑在哪
现象原因 / 怎么办
见到 "rejected / fetch first" 就以为仓库坏了这是最常见的正常流程：按提示 pull → 解决冲突 → 再 push 即可
以为只有 push 会冲突merge（第十三章）也会冲突；凡是"两处改动要合一"，都可能冲突
8⑧ 冲突长什么样：<<<<<<< ======= >>>>>>>
要解决什么

pull 提示 "CONFLICT" 之后，文件里凭空多出一堆奇怪的符号——这文件现在长什么样？这些符号是干什么的？看不懂就别乱删。

核心思路

冲突时，Git 会把双方内容都写进文件，用冲突标记分隔：

<<<<<<< HEAD
# 你自己写的部分
this is my version
=======
# 别人写的部分
public class HelloWorld {}
>>>>>>> 0b8b926   # 对方的提交号（示例）
  • <<<<<<< HEAD：上面是你这一侧（你的本地内容 / 当前分支）；
  • =======：分界线；
  • >>>>>>> 提交号：下面是对方那一侧（拉下来的内容）。

你的任务：把标记符号全部删掉，手动保留（或改写）真正想要的最终内容，然后重新提交。

坑在哪
现象原因 / 怎么办
直接把冲突文件提交了（带着 <<<<<<< 符号）一等一的低级事故，代码根本编译不过；解决完冲突后，全文搜一下确认没有残留标记再提交
不知道哪边"对"冲突要靠人判断：和对方沟通、看业务逻辑，不能无脑选一边
9⑨ 解决冲突：手动合并 → 重新提交
要解决什么

知道了冲突标记，接下来是完整流程：怎么从"冲突中"走回"正常"？顺序错了会反复报错。

核心思路 
git pull                    # 1. 拉取最新代码，触发冲突
# …编辑冲突文件，删掉标记，保留想要的最终内容…
git add 冲突文件            # 2. 把解决好的文件加入暂存区（对 Git 说"我裁决好了"）
git commit -m "解决冲突：保留双方逻辑"   # 3. 提交这次合并结果
git push                    # 4. 推送到远程

关键理解：解决冲突 = 手动改文件 + add + commit。Git 不会自动替你选，但只要你完成这三步，冲突就正式结束了。

坑在哪
现象原因 / 怎么办
add 之后马上 push 又被拒冲突解决后必须先 commit 再 push；只 add 不 commit，状态还是"合并中"
解决到一半想放弃git merge --abort 可以撤销当前合并，回到冲突前状态重来
图形工具里点"全部接受某一边"慎用一键接受；复杂冲突建议逐段手动合并，避免漏掉另一边逻辑
10⑩ 传输协议：HTTPS 和 SSH 怎么选
要解决什么

复制远程仓库地址时，平台给两种地址：https://... 和 git@...。选哪个？各自有什么坑？这直接决定你每次 push 要不要输密码。

核心思路

Git 远程传输支持多种协议：本地（Local）、HTTPS、SSH、Git 专用协议。日常就是 HTTPS vs SSH 二选一：

协议认证方式push 时适合
HTTPS用户名 + 密码/令牌每次可能需要输入临时使用、只拉取不推送
SSH密钥对（公钥 + 私钥）免密长期开发的个人电脑 ✅

结论：想省事就配 SSH——配一次，之后 push / pull 全部免密。SSH 本身是加密协议，能有效防止远程管理过程中信息泄露。

坑在哪
现象原因 / 怎么办
HTTPS 地址能用，换成 SSH 地址不能 pullSSH 地址需要先配好密钥；没配就用 HTTPS 地址（两者可以随时切换）
HTTPS push 老输密码还输错现在很多平台已不支持密码 push，要用个人访问令牌（Token）当密码；或干脆换 SSH
以为 SSH 是"更快的协议"SSH 解决的是安全与免密，速度上两者差别不大
11⑪ SSH key：一次性配置，终身免密
要解决什么

SSH 免密的原理：用一对密钥——公钥（公开，放到平台）和私钥（保密，留在本机）做身份认证。配置共三步：生成密钥 → 把公钥贴到平台 → 验证连通。

核心思路 
ssh-keygen -t rsa          # 1. 生成密钥对（一路回车即可，也可以顺手设个口令）

生成后会在用户目录 .ssh（Windows 是 C:\Users\你的用户名\.ssh）下出现两个文件：id_rsa（私钥，绝对不要泄露/提交）和 id_rsa.pub（公钥，可以公开）。

cat ~/.ssh/id_rsa.pub      # 2. 查看公钥内容，全选复制
  1. 打开托管平台（GitHub / Gitee）→ 设置 → SSH 公钥 → 粘贴保存；
  2. 验证连通：
ssh -T git@gitee.com       # 显示欢迎语（如 "Hi yourname!"）即成功

之后用 git@... 形式的 SSH 地址 clone / push，全部免密。

坑在哪
现象原因 / 怎么办
把 id_rsa（私钥）提交进仓库或被分享出去私钥泄露 = 别人能冒充你 push；立即在平台删除旧公钥并重新生成密钥对
ssh -T 提示 Permission denied公钥没粘对/没保存；先确认 ~/.ssh/id_rsa.pub 内容是否完整复制
换了电脑/重装系统后免密失效新机器没有你原来的私钥；在新机器重新生成并把新公钥加到平台

本章小结

问题答案
远程仓库放哪托管平台：GitHub（生态）/ Gitee（快）/ GitLab（自建）
怎么登记远程git remote add origin 地址；git remote -v 查看，git remote rm 移除（不影响云端）
怎么把提交送上去git push（首次 -u 绑定上游）
怎么从零拿下一份仓库git clone 地址（含全部历史，自动配好 origin）
fetch 和 pull 什么区别fetch 只下载不合并；pull 下载 + 自动合并
冲突为什么发生双方基于同一旧版改了同一处，机器无法裁决
冲突怎么解决删标记 → 保留最终内容 → add → commit → push
HTTPS 和 SSH想免密长期用 → SSH 配密钥对；临时用 → HTTPS

一句话记住本章：远程仓库 = 团队的公共交换站；push 上交、pull 取回、clone 全量搬新家；冲突不是 bug 而是"双方改了同一处"的信号——删掉冲突标记、手动合并再提交；SSH 配一次密钥，从此免密。
