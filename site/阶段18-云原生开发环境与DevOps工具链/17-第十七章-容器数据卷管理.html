第十七章　容器数据卷管理

阶段 18 · 云原生开发环境与 DevOps 工具链　|　容器化　|　难度 ★★★★
这一章在解决什么问题

上一章结尾你跑了 Tomcat，但只要执行一条 docker rm -f mytomcat，容器里存的东西——你部署的网页、写的文件、MySQL 的数据库——全没了。 这就是容器最大的"原罪"：它的可读写层跟着容器走，容器一删，数据灰飞烟灭。 数据库总不能每次重启容器都重新建库吧？本章用数据卷（Volume）解决三件事： ① 数据持久化（容器删了数据还在）；② 宿主机和容器互相传文件；③ 多个容器共享同一份数据。

这一章在整个知识库里的位置 上一章：镜像与容器基本操作——能跑起容器，但数据是"一次性"的 本章 ← 你在这里：数据卷——把数据从容器里"摘出来"挂到宿主机上 下一章：Dockerfile 镜像定制——把环境做成可复用的镜像 阶段终点：数据活了，镜像才会"活"；这是走向生产部署的关键一环
1① 灵魂拷问：容器删了，数据还在吗
要解决什么

先把痛处摊开：你辛苦往 MySQL 容器里存的数据，容器一删就没了，这个后果你能接受吗？ 想清楚"数据为什么跟着容器死"，才能理解后面所有命令的意义。

核心思路

答：不在。原因是第 15/16 章的公式——「容器 = 只读镜像层 + 可读写层」。 你写的任何文件都落在可读写层里，这层像草稿纸一样属于容器本身： 容器被 docker rm 删除时，草稿纸也跟着撕掉。docker stop 不会删数据（只是熄火），但删容器就是连根拔。

三个随之而来的问题（本章逐一解决）：

  1. 持久化：容器删了，数据能不能留在宿主机上？
  2. 交换：容器和宿主机能不能直接互相传文件？（不用 docker cp 一条条拷）
  3. 共享：两个容器能不能共用一套数据？
坑在哪
现象原因 / 怎么办
以为 stop 了数据就丢stop 只停进程，可读写层还在，start 后数据原样回来；只有 rm/rm -f 才销毁数据
以为跑 docker commit 就能保数据commit 把容器文件系统固化成镜像，但不是正经备份手段（镜像会越做越大）；正规做法是数据卷
2② 数据卷是什么：宿主机上的一个目录/文件
要解决什么

要让数据"跳出容器"，得有一个容器之外、宿主机之上的落脚点。

核心思路

数据卷（Data Volume）就是宿主机中的一个目录或文件。 用 -v 把它和容器内的某个目录绑定，绑定之后两边就是"一个东西"： 容器里写文件 → 宿主机目录实时出现；宿主机改文件 → 容器里实时同步。

宿主机                                    容器
/opt/webapps   ◄─────── -v 绑定 ────────►  /usr/local/tomcat/webapps
（数据卷/真身）      双向实时同步             （容器内的"镜子"）

因为数据存在宿主机上，所以：容器删了，宿主机目录里数据还好好的；再开一个容器绑定同一个目录，数据立刻"复活"。

坑在哪
现象原因 / 怎么办
以为数据卷是"容器里的一块特殊磁盘"数据卷物理上就在宿主机，容器只是"借用"它；把它理解成"容器目录开了一扇通向宿主机的门"更准确
容器删了以为数据卷也删了数据卷默认不随容器删除；只有 docker rm -v 或显式删卷才会清掉
3③ 数据卷的三大用途：持久化 / 传文件 / 容器间共享
要解决什么

"为什么要有卷"的完整答案：卷技术就是为了实现数据的持久化和同步，顺带解决了传文件和共享。

核心思路

三个场景一一对应三个价值：

场景没数据卷时有数据卷后
数据库重启/重建容器数据随容器湮灭卷在宿主机，新容器挂上即恢复
宿主机改配置文件要 docker cp 进进出出直接改宿主机文件，容器内立即生效
两个服务读同一份数据各存各的，不同步同时挂载同一个卷，天然共享

特性：一个数据卷可同时被多个容器挂载；一个容器也能挂多个数据卷（多对一、一对多都行）。 特别留意场景 2：改配置不需要重建容器——改宿主机上挂的配置文件，容器内立刻生效，这是日常调试的救命特性。

4④ -v 挂载：把宿主机目录"焊"进容器
要解决什么

知道了卷的用处，上手第一步：怎么在创建容器时把目录绑起来？绑定有哪些讲究？

核心思路
# 语法：-v 宿主机目录:容器内目录 # \ 是命令续行符（Linux 多行命令写法），抄的时候别漏 docker run -d --name mytomcat -p 8080:8080 \ -v /opt/webapps:/usr/local/tomcat/webapps docker.io/tomee # └ 宿主机目录 └ 容器内目录

三条规矩（直接决定成败）：

  1. 目录必须写绝对路径（如 /opt/webapps），相对路径不认；
  2. 宿主机那边目录不存在会自动创建，你不用先 mkdir；
  3. 一个容器可以挂多个卷：多写几个 -v 即可，如 -v A:B -v C:D。
坑在哪
现象原因 / 怎么办
用相对路径挂载报错-v 的宿主机路径必须是绝对路径；容器内路径也建议绝对路径
挂载后容器内目录变成空的了正常：挂载后容器内该目录完全跟随宿主机；镜像里原来这个目录的内容会被"盖住"（首次挂载时一次性初始化）
复制多行命令时提前回车命令报"参数不完整"；多行命令用 \ 续行，别提前按回车
5⑤ 三种挂载方式：匿名 / 具名 / 指定路径
要解决什么

-v 后面到底写什么？"卷名:路径"和"绝对路径:路径"有什么区别？面试常问，操作时也经常懵。

核心思路

三种写法，本质区别是"卷由谁管理"：

写法例子特点
匿名挂载-v 容器内路径只写容器路径，docker 自动生成一串乱码卷名；不指定名字，难复用
具名挂载-v 卷名:容器内路径卷名由你起（如 edc-tomcat-vol），可反复用、可管理
指定路径挂载-v /宿主机绝对路径:容器内路径精确指定宿主机目录，位置完全由你掌握
# 匿名挂载：只写容器内路径 docker run -d -P --name tomcat1 -v /usr/local/tomcat/webapps docker.io/tomee # 具名挂载：卷名字在前 docker run -d --name edc-tomcat -p 8080:8080 \ -v edc-tomcat-vol:/usr/local/tomcat/webapps docker.io/tomee # 指定路径挂载：宿主机绝对路径在前（上面第 ④ 点的就是这种）

补充说明：run 时没写 -v、但镜像里声明了 VOLUME（第 18 章讲）时，Docker 会默认创建匿名卷——这也是有的容器没挂卷也有卷的原因。

坑在哪
现象原因 / 怎么办
具名挂载后找不到数据在宿主机哪里具名卷由 docker 管理，实际路径在 /var/lib/docker/volumes/卷名/_data；用 docker volume inspect 卷名 一查便知
搞不清"哪个是宿主机哪个是容器"分隔符是冒号 :，冒号左边永远在宿主机/卷层，右边在容器内
匿名卷一堆乱码不知道干什么用 docker volume ls 看，无用的用 docker volume prune 清理
6⑥ 读写权限：ro 只读 / rw 可读写
要解决什么

有些配置文件你希望容器只能读、不能改（防止程序乱写改坏它）。默认是能读能写，怎么锁死？

核心思路

在 -v 后面追加权限后缀：

  • rw（read-write）：可读可写，默认就是它；
  • ro（read-only）：只读，容器只能看不能改。
# 只读挂载：容器里改这个目录会报 &quot;read-only file system&quot; docker run -d -P --name nginx-ro -v my-nginx:/etc/nginx:ro nginx # 可读可写（写不写 :rw 效果一样） docker run -d -P --name nginx-rw -v my-nginx:/etc/nginx:rw nginx

使用思路：配置目录挂上只读，程序想篡改配置时直接失败、暴露问题，而不是悄悄改掉；数据目录（要写的）保持 rw。

坑在哪
现象原因 / 怎么办
-v 卷:路径:ro 后容器写文件没报错多数情况会报只读错误，但有些程序会"吞掉"错误继续跑——查容器日志确认，别只看有没有报错
权限后缀写错（:r / :w）只认 ro / rw 两个，:r 会被当成路径的一部分导致挂载失败
7⑦ volume 命令族：create / ls / inspect / rm / prune
要解决什么

卷多了、乱了，怎么统一管理？Docker 把"卷"当成了一等公民，给了一整套命令。

核心思路
docker volume create edc-tomcat-vol # 1. 手动创建一个具名卷 docker volume ls # 2. 列出所有卷 docker volume inspect edc-tomcat-vol # 3. 看某个卷的详情（挂载点等） docker volume rm edc-tomcat-vol # 4. 删除指定卷 docker volume prune # 5. 删除所有&quot;没被任何容器使用&quot;的卷

其中 inspect 输出的 Mountpoint 字段最有价值——它告诉你这个卷在宿主机上的真实路径（/var/lib/docker/volumes/edc-tomcat-vol/_data），想手动进去看数据就靠它。 注意：有容器正在用的卷，rm/prune 会拦着不让删（这是保护机制，别用 -f 硬刚，先停容器）。

坑在哪
现象原因 / 怎么办
volume rm 报 "volume is in use"还有容器挂着它；先停/删那些容器再删卷
prune 把想留的卷也删了prune 只删"无人使用"的卷；确认不再用的容器先停掉，再统一 prune
inspect 里的挂载路径在容器里找不到那是宿主机路径，容器里看不到；在宿主机上用 ls 检查
8⑧ 实战：MySQL 数据卷挂载——数据库"永不丢失"
要解决什么

把前面所有知识落在最真实的场景：MySQL 容器化 + 数据卷。以后容器怎么删怎么换，库都在。

核心思路
# 1. 搜索并拉取 MySQL 5.7 镜像 docker search mysql:5.7 docker pull mysql:5.7 # 2. 运行 MySQL：-e 设置 root 密码（这里用占位符，别用真密码）， # 同时挂两个卷：配置目录 + 数据目录 docker run -d -p 3306:3306 \ -v /opt/mysql/conf:/etc/mysql/conf.d \ -v /opt/mysql/data:/var/lib/mysql \ -e MYSQL_ROOT_PASSWORD=你的密码 \ --name my-mysql mysql:5.7 # 3. 验证容器起来，再验证可登录 docker ps

要点：

  • -v /opt/mysql/data:/var/lib/mysql 是命根子：MySQL 的所有库表文件都在 /var/lib/mysql，挂到宿主机后，删容器重建一个挂同一目录，数据原封不动；
  • -e MYSQL_ROOT_PASSWORD=你的密码：容器第一次启动时读这个环境变量来初始化 root 密码（只生效一次，初始化完成后改它没用）；
  • 数据和配置分开挂：想换配置只改 /opt/mysql/conf，不用碰数据。
坑在哪
现象原因 / 怎么办
容器起来了但连不上底层还没就绪（docker logs 看初始化日志）；或宿主机 3306 已被别的 MySQL 占用，换宿主端口
改了 -e 密码却连不上新密码MYSQL_ROOT_PASSWORD 只在首次初始化生效；之后要改密码请在容器内用 SQL（ALTER USER），不是改 -e 重启
以为有了数据卷就能随便删数据目录卷目录里的数据文件是唯一真本，误删 = 库没了；定期备份 /opt/mysql/data
9⑨ 容器间数据共享：一卷多挂
要解决什么

两个服务要读同一份数据（比如：A 服务生成报表、B 服务读报表做展示）。方案就是前面提过的"一个卷挂多个容器"。

核心思路
# 1. 先建一个具名卷 docker volume create shared-vol # 2. 两个容器同时挂载同一个卷的同一个目录 docker run -d --name app-a -v shared-vol:/data busybox sleep 3600 docker run -d --name app-b -v shared-vol:/data busybox sleep 3600 # 3. 验证：A 里写文件，B 里能读到 docker exec app-a sh -c &quot;echo hello &gt; /data/msg.txt&quot; docker exec app-b cat /data/msg.txt # 输出 hello =&gt; 共享成功

原理就一句话：两个容器里的 /data 都指向宿主机上同一个卷目录，物理上是同一个文件夹，自然实时共享。 这和"指定路径挂载 + 两个容器挂同一个宿主机路径"是等价的——共享的本质是落在宿主机同一处。

坑在哪
现象原因 / 怎么办
两个容器挂同名卷但数据不同步检查卷名是否一字不差（拼错一个字符就是两个卷）；用 docker volume ls 对一遍
并发写同一个文件互相覆盖卷解决"共享"，不解决"并发写冲突"——文件锁、数据库事务是你自己的事，卷不负责
10⑩ 数据卷 vs 容器：分清四个"会不会丢"
要解决什么

学完一堆命令，最后容易乱。用一张表把"什么情况数据会丢、什么情况不会"钉死。

核心思路
操作容器里的普通文件数据卷里的数据
docker stop / start还在还在
docker rm 容器❌ 没了✅ 还在宿主机
重建容器并挂同一卷新容器重新初始化✅ 原样恢复
单独删数据卷无关❌ 数据真的没了

两条铁律：

  1. 想留数据 → 一开始就用卷；想丢数据 → 直接 rm（务必连 -v 一起想清楚）；
  2. 删卷 = 删数据，没有后悔药（rm、rmi 同理，都是永久操作）。

真正生产上会更激进：连数据目录本身也做备份（mysqldump / 文件拷贝），卷只是"防容器删除"，不防磁盘损坏。

坑在哪
现象原因 / 怎么办
删容器时顺手加 -v，把数据卷也删了还奇怪rm -v 会连容器挂的数据卷一起删；重要数据别用 -v 删，先备份
以为卷"在容器里"卷是宿主机资源，docker ps -a 看不到它，要看 docker volume ls

本章小结

问题答案
为什么必须有数据卷容器可读写层随容器删除而消失，数据会"陪葬"
数据卷是什么宿主机上的目录/文件，与容器目录绑定后双向实时同步
数据卷三大作用持久化、宿主机与容器传文件、容器间共享
怎么挂-v 宿主机目录:容器内目录，必须绝对路径，可挂多个
三种挂载匿名 / 具名 / 指定路径；冒号左边在宿主机
读写控制:ro 只读 / :rw 可读写（默认）
卷的命令create / ls / inspect / rm / prune
MySQL 实战数据目录 /opt/mysql/data 挂卷，配合 -e 设密码
容器间共享一个具名卷挂多个容器，物理同源
什么会丢rm -v 会连卷一起删；stop 永不丢数据
