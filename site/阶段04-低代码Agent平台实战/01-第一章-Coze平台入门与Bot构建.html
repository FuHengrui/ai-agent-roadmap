第一章　Coze 平台入门与 Bot 构建

阶段 4 · 低代码 Agent 平台实战　|　平台实操　|　难度 ★★☆
这一章在解决什么问题

前面几章，你一直在写代码：Python、FastAPI、数据库……每造一个功能都要自己搭环境、调接口、处理异常。

但你有没有想过：很多 AI 应用，其实不该从零写。

一个能查天气的助手、一个懂你产品的客服、一个记得你喜好的健康教练——这些应用的核心逻辑八九不离十：*大模型 + 记忆 + 工具 + 知识*。组装它们比发明它们更重要。

Coze（扣子）就是干这个的：字节跳动出品的一站式 AI 应用开发平台。它把大模型的接入、工具的调用、知识的注入全部做成可视化配置，让你不写后端也能做出能上线使用的 AI 助手。

这一章解决的就是：怎么用 Coze 把一个"会聊天的模型"变成一个"有身份、有工具、有知识、有记忆"的 Bot。

在全局框架里的位置 上一章：你亲手写了一个完整的会议系统项目——理解了 Agent 的工程全貌 本章 ← 你在这里：登上低代码平台，用配置代替代码，快速搭出可用的 Bot 下一章：工作流与多 Agent——当单个 Bot 搞不定复杂任务时，把它升级成流水线
这一章你要达到什么程度

学完这一章，你手里有 9 个知识点：先说清 Coze 是什么，再把搭 Bot 的五个核心模块（人设、插件、知识库、记忆、对话体验）挨个过一遍。每个模块配一个能跟着做的案例。

不用记 API，不用背参数——你要带走的是"一个 Bot 由哪些部分组成"这张地图。

1① Coze 是什么：把 AI 应用从"写出来"变成"搭出来"
要解决什么

如果让你从零开发一个"能陪用户聊星座"的助手，你需要：接一个大模型 API、写后端逻辑、处理上下文、部署上线……至少一两个月。

但这个需求其实不特殊——大量 AI 应用都是"模型 + 提示词 + 几个外部能力"的排列组合。为它们重复造轮子，纯属浪费。

核心思路

Coze 把 AI 应用的公共部分（模型接入、对话管理、工具生态、发布渠道）全部平台化了。你只需要关注自己的业务：这个助手是什么人设、要调用什么能力、吃什么知识。

几个关键概念：

  • Bot（智能体）：Coze 里的 AI Agent 就叫 Bot，是一个*基于对话*的 AI 项目。用户跟它聊，它自动调用插件、工作流等能力完成任务。
  • 应用：和 Bot 相对，是*有界面、有表单*的 AI 项目（比如 AI 翻译工具），这一章先不展开，第二章讲。
  • 版本之分：国内版 coze.cn（默认豆包，还有 DeepSeek、Kimi，国内网络直接用）；国际版 coze.com（GPT 系列等，需要代理）。两边账号、插件库、模型互不相通，选对版本很重要。

零代码/低代码是它的招牌：会拖拽就能起步，会点代码就能进阶（比如在插件里写 Python）。

2② 人设与回复逻辑：从"通用助手"到"专属角色"
要解决什么

直接把大模型丢给用户，它是个"四平八稳的通用助手"——没有性格、没有边界、不主动引导。一个星座 App 的助手和一家银行的客服，回答风格不该一样。

你希望 Bot 有身份、有技能、有底线，且这些约束不需要每次都跟用户重复。

核心思路

人设与回复逻辑，就是系统提示词（System Prompt）。它在每次对话前悄悄"告诉"模型：你是谁、什么能做、什么不能做、按什么格式回。

以"星座运势解读助手"为例，一段好的人设包含四层：

# 核心人设
你是专业的星座运势解读师"星语"，拥有10年占星研究经验。

# 我能做什么
1. 每日/每周/每月星座运势解读
2. 星座性格特征分析
3. 星座配对兼容性分析

# 我不能做什么（伦理边界）
1. 不预测具体事件（如"你会中彩票"）
2. 不做医疗/财务决策建议

# 回复模板结构
1. 开场：问候 + 确认星座
2. 主体：运势分析（分爱情/事业/健康）
3. 结尾：鼓励话语 + 小贴士 + 免责声明

三个事半功倍的手段：

  • 用 Markdown 写：分节、加粗、列表，模型对结构化的提示词理解更好。
  • 用提示词模板：Coze 内置模板（角色/目标/技能/工作流/输出格式/限制），填空即可，也可以让 AI 照着模板帮你生成。
  • 对比优化：写了两版提示词不知道哪个好？用"提示词对比优化"让平台帮你评；写好的还能存进个人提示词库，跨 Bot 复用。
坑在哪
现象原因
Bot 回得很"官方"、没特点人设里没写语气和回复结构，模型只能自由发挥
Bot 回答越界（预测彩票、给医疗建议）没写"我不能做什么"，伦理边界缺失
人设一段话写完，效果差应分「人设/能力/边界/模板」多块组织，信息密度高才稳
3③ 插件：给 Bot 装上"手"和"眼"
要解决什么

大模型的短板是只能处理文本：你让它查北京的实时天气，它答不上来——它根本不知道今天几号、北京有没有下雨。

但现实中 AI 助手必须触达真实世界：查天气、读新闻、发邮件、订机票。

核心思路

插件 = Coze 平台预置的功能模块，相当于智能体里的 Function Call：模型在对话中识别用户意图，把参数提取出来传给插件，再把插件的返回结果整理成自然语言回答。

平台集成了上百款插件：新闻阅读、便利生活、图像、网页搜索、音视频……直接用，不用自己写。

以"天气助手"为例，步骤很清晰：

  1. 建一个 Bot，写好"你是天气助手"的人设；
  2. 添加墨迹天气插件（DayWeather）；
  3. 告诉模型"查天气时调用 DayWeather 插件"。

第一次测试翻车了——查询不到天气数据。原因很微妙：查天气需要传"日期"参数，但模型不知道今天是几号。

解决：再加一个查当前时间的插件 get_current_datetime，让人设同时声明"查询日期时使用 get_current_datetime 插件"。模型会先拿到日期，再带着日期去查天气——两个插件按顺序协作。

坑在哪
现象原因
插件返回了数据，Bot 却答非所问人设里没写"什么时候调用哪个插件"，模型不知道该用
天气插件报缺参数模型没有当前时间/位置信息，需要先用时间插件或让用户提供
插件很多不会选按"我的 Bot 要做什么事"选，而不是按"平台有什么"选
4④ 自定义插件：商店里没有的，自己写
要解决什么

平台插件再多，也覆盖不了你自己系统的功能：查自家订单、调企业内部接口、做公司专属的格式转换……商店里永远不会有"我家公司的接口"这种插件。

核心思路

Coze 提供三种自定义插件方式：

  • 云端插件：插件运行在 Coze 服务器上，零部署；
  • 基于已有服务创建：你已有一个在线 API，把它描述给 Coze 即可（下一知识点展开）；
  • Coze IDE 中创建：没有现成服务，让 Coze 帮你运行代码。

一个插件里可以有多个工具（Tool），但每个工具只能有一种功能——这是元数据的价值：明确的输入输出描述让模型知道"这个工具什么时候能用、怎么用"。

以"获取当前日期"插件为例，核心是一段 Python：

from datetime import datetime

def handler(args: Args[Input]) -> Output:
    """获取当前日期和星期几"""
    now = datetime.now()
    # 1. 日期
    date = now.strftime("%Y/%m/%d")
    # 2. 星期几
    weekdays = ["星期一", "星期二", "星期三",
                "星期四", "星期五", "星期六", "星期日"]
    weekday = weekdays[now.weekday()]
    # 3. 返回结果
    return {"date": date, "weekday": weekday}

三步收尾：在元数据里配置输入/输出参数（让模型认识这个工具）→ 测试代码 → 发布插件。之后就能像用官方插件一样，在任意 Bot 里引用它了。

坑在哪
现象原因
模型识别不了你的插件元数据里的输入/输出描述太含糊，模型不知道何时调用
一个插件塞了多个功能违背"一个工具一种功能"，模型调错工具
改了代码但 Bot 行为没变发布新版本后，Bot 里要重新选择该插件版本
5⑤ 基于已有服务创建插件：把自己写的 API 接进 Coze
要解决什么

云端插件适合小工具，但企业里最常用的是另一种：你的团队已经有大量 API 服务（订单查询、物流跟踪……），希望 AI 客服直接调用它们——这能复用现有系统，还保证数据在自己服务器上。

问题来了：你本地能访问的服务，Coze 在云端访问不到。 怎么把"内网的一个接口"变成"Coze 能调的插件"？

核心思路

两步：把本地服务暴露到公网（ngrok）→ 把公网 API 配置成 Coze 插件。

以"获取当前时间"服务为例，先用 Flask 写一个简单 API（支持时区参数，返回日期、时间、星期、农历）：

from flask import Flask, request, jsonify
import pytz
from datetime import datetime
from lunardate import LunarDate

app = Flask(__name__)

@app.route('/get_time', methods=['GET'])
def get_time():
    # 时区参数可选，默认上海
    timezone_str = request.args.get('timezone', 'Asia/Shanghai')
    tz = pytz.timezone(timezone_str)
    now = datetime.now(tz)
    lunar = LunarDate.fromSolarDate(now.year, now.month, now.day)
    return jsonify({
        "date": now.strftime("%Y/%m/%d"),
        "time": now.strftime("%H:%M:%S"),
        "weekday": ["星期一", "星期二", "星期三",
                    "星期四", "星期五", "星期六", "星期日"][now.weekday()],
        "lunar": f"农历{lunar.year}年{lunar.month}月{lunar.day}日",
        "timezone": timezone_str
    })

if __name__ == '__main__':
    app.run(port=8000)

本地跑起来后，用 ngrok 做内网穿透（把本地端口映射成公网 HTTPS 地址，且自动带 https——Coze 插件只允许访问 https 的 API）：

# 1. 配置令牌（第一次使用） ngrok config add-authtoken 你的token # 2. 暴露本地端口 ngrok http 8000

拿到公网地址后（形如 https://xxx.ngrok-free.dev），就能访问 https://xxx.ngrok-free.dev/get_time?timezone=Asia/Tokyo 测通了。最后在 Coze 资源库里基于已有服务创建插件：填 API 地址、配置工具参数、试运行、发布。本地的一个接口，就此变成 Bot 的"手"。

坑在哪
现象原因
Coze 调用本地接口失败没做内网穿透，或公网地址不是 https
ngrok 地址经常变免费版每次重启地址会变，插件里要同步更新
接口通了但参数报错工具元数据里的参数名要和 API 实际接收的参数名一致
6⑥ 通过插件调用外部模型：用上平台没有的模型
要解决什么

Coze 主要用的是豆包，但有些任务其他模型更合适：比如生成 LOGO 图——豆包不做文生图大模型平台，而你恰好有阿里百炼（通义万象）的 API 额度。

难道要用别的平台？不用。 插件机制本身就是"把任意 API 包装给模型用"——那外部模型 API 为什么不呢？

核心思路

创建一个基于已有服务的插件，插件内部调用阿里百炼通义万象的文生图 API，然后把"生成一张 LOGO 图"这件能力暴露给 Bot。

具体做法：

  1. 参照[阿里百炼通义万象文档](https://bailian.console.aliyun.com/cn-beijing/?tab=api#/api/?type=model&url=2975126)，在插件里创建一个名为 generation 的工具：输入写"prompt"（生成要求），输出写"图片 URL"；
  2. 试运行工具，确认能出图；
  3. 发布插件；
  4. 创建"LOGO 生成助手"Bot，人设里写清调用规则：识别到"生成 LOGO/设计标志"意图时，立即调用该插件，并允许助手自动优化 prompt（追加"高清、简约、矢量、无背景"等词）。

到这里你应该发现了："通过插件调用外部模型"和"基于已有服务创建插件"是同一件事。区别只是被包装的 API 是个模型而已。这个思路统一了 Coze 的扩展方式：凡是能调 API 的能力，都能变成 Bot 的能力。

坑在哪
现象原因
调用外部模型失败没配置目标平台的 API Key / 授权
Bot 认不出"生成 LOGO"的意图人设里没写清触发条件，模型不知道何时调插件
prompt 太短，出的图质量差在插件调用前先让模型优化 prompt，而不是用户说什么传什么
7⑦ 知识库：让 Bot 学会你的私有资料
要解决什么

让大模型回答"英雄联盟新英雄不落魔锋怎么玩"——它大概率会一本正经地编，因为训练数据里还没有这位新英雄。

任何专业场景都会撞上同一堵墙：模型不知道你的私藏资料（产品手册、课程问答、新品介绍）。直接问，就会幻觉。

核心思路

知识库就是 Coze 的 RAG（检索增强生成）：回答前，先从你上传的文档库里检索相关段落，再把段落作为上下文交给模型生成答案。模型不再靠猜，而是"读完资料再回答"。

创建知识库要过三关：

  • 选类型：文本（PDF/Doc/TXT，适合攻略、教程）、表格（Excel/CSV，适合结构化数据）、照片（适合图像生成场景）；
  • 传文档：上传前先清理无关内容、按主题分类、文件名带关键信息；
  • 切片：长文档会自动切成 200-500 字的小段。切太大，无关信息多、干扰判断；切太小，上下文不完整、检索不准。

案例：做一个"英雄联盟游戏助手"，上传《不落魔锋·亚恒》《焰峰凰姬》两份新英雄介绍文档，再写好人设——包括技能的问答机制：

# 角色
你是一个英雄联盟游戏助手
## 技能1：问题理解与回复分析
1. 理解知识库召回的内容与用户问题，判断召回内容是否真是答案
2. 问题信息不足时，追问用户
## 技能2：回答用户问题
1. 知识库没召回内容时，老实说"我学习的知识中不包含相关内容"
2. 召回了相关内容时，只提取和问题相关的部分，总结优化后再回答
## 限制
1. 不回答隐私、违法内容
2. 回答长度不超过300字，用 Markdown 格式

这样问"不落魔锋的大招是什么"，Bot 会先从知识库里检索到对应段落再回答——有据可依，不再胡编。

坑在哪
现象原因
上传了文档，Bot 还是乱答人设里没约束"必须基于知识库内容回答"
检索命中垃圾内容文档没清理，广告、水印、无关段落一起被召回
答案太碎、不连贯切片太小（每段几十字），上下文不完整
没说清资料出处人设里没让模型判断"问题是哪个文档的内容"
8⑧ 记忆模块：Bot 不再是"每次都是第一次见面"
要解决什么

默认情况下，Bot 每次对话都"失忆"：你上周告诉它"我讨厌西兰花、想减重 5 公斤"，今天再问，它一脸茫然。

一个健康教练、一个私人助理，必须记住用户，否则所有建议都是 E 话，用户不会用第二次。

核心思路

定制记忆模块包含四个功能，先把它们的作用分清楚：

功能存什么特点
变量用户基本信息（姓名、目标、作息、禁忌食物）会话内读写，个性化回复
数据库结构化数据（体重记录、习惯打卡表）表格存储，可查询、可统计
长期记忆自动总结对话历史中的用户长期偏好靠模型总结，提升连续对话体验
文件盒子用户上传的文件，Bot 可读取引用目前平台已关闭该功能

以"个人健康生活教练"为例，人设里对记忆的使用写得很讲究：

# 记忆系统使用指南
## 变量（存储用户基本信息）
- user_name：每次对话亲切称呼用户
- health_goal：所有建议围绕此目标展开
- disliked_foods：绝对不推荐这些食物
- 更新时机：用户明确说出新信息时立即更新

## 数据库（结构化记录）
有两张表：daily_records（体重/睡眠/心情/喝水）、habit_logs（习惯完成情况）
- 说"记录体重/睡眠/喝水/心情" → 更新 daily_records
- 说"完成了[习惯]" → 插入 habit_logs
- 一句话含多种数据 → 分成多条 SQL 依次执行，不合并

## 长期记忆
- 每10次对话左右总结用户模式
- 自然引用："我注意到你通常周三比较疲惫…"

注意那个"一句话含多种数据"的规则（"今天完成了晨跑，喝了 8 杯水"→ 先插 habit_logs 再更新 daily_records）——这正是人设里把"模型如何用记忆"写清楚的价值，模型按规则办事，数据才不会乱。

坑在哪
现象原因
长期记忆积累垃圾，干扰当前对话长期记忆会自动积累，过时信息没被清理（如用户早说"讨厌红色"，几周后买中式礼服时 Bot 还过滤掉红色款）
变量改了但 Bot 记不住变量是会话级的，跨会话持久要靠长期记忆
数据表写乱了没有在提示词里规定"何时写、写哪张表、怎么拆 SQL"
9⑨ 对话体验：让 Bot 从"能用"到"好用"
要解决什么

功能全做完了，但用户一打开是干巴巴的输入框——不知道这个 Bot 能干嘛、从哪句开始问。用户从"想用"到"会用"之间隔着一道门槛。

对话体验模块不改变 Bot 的核心能力，但极大影响用户会不会留下来。

核心思路

六个可配置项，各自解决一个使用门槛：

配置作用什么时候开
开场白首次对话自动发送的欢迎语，定下对话基调推荐配置
用户问题建议根据当前对话自动推荐后续问题推荐配置
快捷指令输入框上方的预设按钮，一键发起特定对话推荐配置
背景图片给对话界面设置背景，增强沉浸感视觉要求高的场景
音视频给智能体加语音或虚拟形象需要拟人化/无障碍的场景
用户输入方式默认打字、语音输入或语音通话用户不方便打字的场景

案例是"智能旅行规划助手"，它的开场白和预置问题长这样：

🌴 嗨！我是你的旅行伙伴小百！
我可以帮你：
• 📍 规划国内外旅行路线
• 🏨 推荐特色住宿和餐厅
• 🎫 提醒旅行注意事项
• 🗺️ 生成每日行程安排

告诉我你的旅行想法吧！比如：
- 我想去云南玩5天，预算5000元
- 推荐一些适合带孩子的海边城市

配合人设里写好的"信息收集流程"（目的地 → 时间 → 同行人 → 预算 → 兴趣）和"每日行程模板"，用户点一下预置问题，Bot 就引导着把需求问全、给出结构化行程——用户从"需要学习如何使用"变成"直觉操作"。

坑在哪
现象原因
开场白写了等于没写长度超出"3 句话"，用户没耐心读完
预置问题和 Bot 人设脱节快捷指令提的事，Bot 人设里根本没这能力
界面花哨但答非所问背景/音视频是锦上添花，核心还是人设和知识库

本章小结

这一章你把"搭一个对话型 Bot"的地图拿到了手：

  • Coze 是怎么回事：一站式 AI 应用开发平台，Bot（智能体）= 基于对话的 AI 项目，分国内/国际版；
  • 人设与回复逻辑 = 系统提示词，决定了 Bot 的身份、能力、边界和回复风格（用 Markdown 写、用模板生成、可对比优化）；
  • 插件 = Function Call，让 Bot 触达真实世界；商店没有的就自己写（云端 IDE、基于已有服务、包外部模型）；
  • 知识库 = RAG，让 Bot 基于你的资料回答，专治幻觉；
  • 记忆模块 = 变量 + 数据库 + 长期记忆，让 Bot 记住用户；
  • 对话体验 = 开场白、问题建议、快捷指令等，把使用门槛降到直觉操作。

一套*「一个 Bot = 人设 + 工具 + 知识 + 记忆」*的心智模型，够你搭出 80% 的对话型助手。
