第一章　项目全景与技术选型

阶段 10 · 安康智慧健康管理平台（糖尿病AI健康助手）　|　|　难度 ★★☆
这一章在解决什么问题

一个糖尿病患者要管住四件事：测血糖、管住嘴、按时吃药、坚持运动。传统的做法是记在本子上、凭感觉吃饭、等到复诊才被医生"教育"一顿，中间三周的异常根本没人管。本章要做的系统，就是把患者的血糖、饮食、用药、运动数据全部收进一套系统里，再用 AI（大模型 + RAG + LangGraph）给出个性化的管理建议——你说"我今天早饭喝了粥血糖升到 9"它会结合你的饮食记录和医学知识库告诉你该怎么调整，而不是丢一句正确的废话。

学完这一章，你手里会有一张完整信息系统蓝图：知道这个"AI 健康助手"由哪些模块组成、每个模块用什么技术、整个项目怎么分层。后面每章做的都是这张图上的一块拼图。

这一章在整个知识库里的位置 上一章（阶段 9 · 智能运营平台）：FastAPI + Tortoise + Vue3 的完整全栈实战——你已经掌握了 CRUD、联调、OSS、自动发布的套路 本章 ← 你在这里：为"AI 健康助手"画全景图——功能模块 + 技术栈 + 架构分层 下一章：数据库设计与初始化——7 张业务表怎么建，外键怎么挂 再往后：后端 CRUD → AI 引擎（DietAdvisor / HealthAnalyzer / RAG）→ LangGraph 工作流 → 前端联调 阶段终点：交付一个能跑通"问诊-检索-生成-预警"全链路的糖尿病 AI 健康助手
1① 这个项目解决的真实痛点
要解决什么

先搞清楚"为什么要做这个系统"，后面的技术选型才有着落——技术是为痛点服务的。

核心思路

糖尿病是典型的数据密集型慢性病：患者每天要监测血糖、记录三餐、按时用药、保持运动，但这些数据散落在不同的 App、小本子和脑子里。四大痛点：

痛点具体表现
数据碎片化血糖、饮食、用药、运动记录分散在不同 App 或纸质记录中，医生看不到全貌
缺乏个性化指导通用建议（"少吃多动"）无法针对个人血糖波动规律给出精准方案
就医频次有限复诊间隔数周或数月，中间的血糖异常难以及时干预
患者依从性差缺乏持续的督促和反馈机制，坚持不下去

系统的解法：AI Agent 技术整合多维数据 + RAG 挂载医学指南知识库 + LangGraph 编排多步 Agent 流程，为每位患者生成个性化健康管理方案和实时咨询。

要解决什么

一个完整产品不可能一把梭，先把"这个系统到底有哪些能力"列清楚，后面开发才有清单。

核心思路

功能模块清单，就是这套系统的需求地图：

模块负载技术落点
📊 血糖监测与分析记录血糖、趋势分析、高/低血糖异常预警BloodSugar 模型 + 统计引擎
🍽️ 智能饮食管理根据血糖推荐食谱、计算碳水与 GI 值DietAdvisor 引擎

4④ 技术亮点：这套系统"新"在哪
要解决什么

讲清楚 AI 健康助手与普通 CRUD 系统的分水岭，也是面试/答辩最值得讲的点。

核心思路

四大技术亮点：

  1. LangGraph Agent 工作流：把健康管理拆解为「症状分析 → 知识检索 → 方案生成 → 风险评估」多步节点，用状态机编排，每一步的输出都是下一步的输入，可观测、可干预。
  2. RAG 医学知识增强：结合糖尿病医学指南、营养学知识库回答患者问题，避免 LLM 幻觉——模型不会凭空编造医学建议。
  3. 个性化推荐：基于患者历史血糖、饮食数据生成个性化饮食/运动/用药方案，不是通用模板。
  4. 实时预警：血糖异常自动触发预警通知（高/低血糖风险等级）。

价值点：普通问答机器人是"一问一答"，这个系统是"问诊工作流"——它先判断你问的是血糖还是饮食，再带上你的档案和数据去回答案。

5⑤ 项目架构图：三层一脑
要解决什么

动手前心里要有"系统长什么样"的静态结构图，知道每段代码摆在哪个层。

核心思路

项目的总体分层（架构图的文字化）：

┌──────────────────────────────────────────────┐
│  Vue3 + TypeScript 前端（Element Plus + ECharts）│
│  血糖图表 / 饮食管理 / AI 对话 / 报告页        │
└─────────────────────┬────────────────────────┘
                      │ HTTP /api
┌─────────────────────▼────────────────────────┐
│            FastAPI 应用层（routers）            │
│  patient / blood_sugar / diet / medication    │
│  exercise / health_report / chat              │
└───────┬──────────────────────────┬───────────┘
        │ Tortoise-ORM              │ 业务引擎
┌───────▼────────┐   ┌─────────────▼───────────┐
│   MySQL 8      │   │  AI 引擎层                │
│  7 张业务表     │   │  DietAdvisor（饮食推荐）   │
└────────────────┘   │  HealthAnalyzer（统计）    │
                     │  LLMClient（大模型封装）    │
                     │  RAGEngine（知识检索）      │
                     │  LangGraph Agent（编排）   │
                     └───────┬──────────────────┘

6⑥ Agent 工作流：一图看懂问诊流程
要解决什么

系统的"大脑"是一套 LangGraph 工作流，必须先理解它的节点顺序，后面第十三章才能照着写。

核心思路

Agent 工作流是一条流水线（Agent 工作流程图 / 时序图的文字化）：

用户消息
  │
  ▼
① classify（意图识别）→ 血糖 / 饮食 / 用药 / 其他
  │
  ▼
② load_context（患者档案）→ 姓名/年龄/BMI/病史 + 近7天血糖统计
  │
  ▼
③ retrieve（知识检索）→ 按意图去 ChromaDB 检索糖尿病医学知识
  │
  ▼
④ generate（方案生成）→ 患者档案 + 医学知识拼成 prompt，调 LLM 生成建议
  │
  ▼
⑤ assess_risk（风险评估）→ 根据血糖统计判断高风险/中风险，追加警告
  │
  ▼
最终回复 = AI 建议 + 风险警告

这套编排正是 LangGraph 的 StateGraph：五个节点 + 一个共享状态对象（AgentState），串成有向图。现在只要有印象，第十二章会逐行实现。

坑在哪
现象原因 / 怎么办
"Agent"听起来很玄，不知道代码写在哪它就是一个 StateGraph 图对象，节点是普通 async 函数，靠共享 state 字典传数据，第十二章见真身
把 AI 逻辑写进路由函数里会变成一坨不可测试的代码；所有 AI 相关逻辑放 app/core/

要解决什么

核心思路
能力来源本阶段用法
FastAPI 路由 + Schema阶段 9 已掌握7 个业务路由照搬套路
