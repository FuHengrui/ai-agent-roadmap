第一章　向量数据库基础

阶段 6 · 企业级RAG系统架构与实现　|　理论实操　|　难度 ★★☆
这一章在解决什么问题

上一阶段你已经会写提示词、会调大模型了。但你可能已经撞上一堵墙：大模型只会它"背过"的东西——你公司内部的制度、你自己整理的笔记、最新上线的产品文档，它一概不知道。

解决方案叫 RAG（检索增强生成）：先让系统"查资料"再让模型"回答"。查资料就得有个专门的仓库，这个仓库就是向量数据库：它能让"意思相近"的内容（比如"养老金要交几年"和"养老保险缴费年限"）在千万条文档里被秒速捞出来。

这一章把向量数据库讲透：它凭什么能搜"意思"、市面上 FAISS / Milvus / Chroma 这些该怎么选，并且每个主流产品都带你跑一遍真实代码。

这一章在整个知识库里的位置 上一章（阶段 5）：你掌握了模型原理与提示词工程——有了"会讲话的大脑" 本章 ← 你在这里：给大脑装一个"自己的资料库"——向量数据库 下一章：Elasticsearch——全文检索的另一半，和向量库互补构成企业级检索 再下一章：RAG 理论——把"查资料 + 生成"串成完整架构 阶段终点：你能独立搭出企业级 RAG 系统（向量库 + ES + RAG + 端到端 Demo）

1① 传统数据库为什么搜不了"意思相近"
要解决什么

你有一张员工表，想查"名字里带'张'的人"，MySQL 一条 LIKE '%张%' 就搞定。但换成这种问题呢："把和'社保能报销什么'意思相近的文档找出来"——文档里写的是"门诊、住院费用可按比例报销"，一个字都不匹配。

LIKE 匹配字符，而你要找的是意思。这在传统数据库（B+树、哈希索引）的眼里是做不到的，因为它的索引都是为"精确相等"和"有序范围"设计的。

核心思路

把"意思"也变成一个可以比较的数字，让数据库走"数字越接近 = 意思越接近"的检索。这就是向量数据库做的事：它存储的不是文字，而是每个内容对应的"语义坐标"，检索时比坐标远近。

传统数据库：  找字符相同 → LIKE '关键词'      → 搜不到同义词、口语化表达
向量数据库：  找语义相近 → 比"坐标"距离       → "报销啥" 和 "医保能报门诊住院" 能匹配上

所以向量数据库是 RAG 的第一块地基：没有它，"查资料"这一步就查不到对味的资料。

坑在哪
现象原因
以为"上了向量库就能替掉 MySQL"它不替代关系库。两者互补：用户、订单、权限这些业务数据还在 MySQL；向量库只负责"语义检索"这一件事。硬用它存业务数据，事务、约束、关联查询全都没有
以为"有了向量检索，关键词搜索就不需要了"精确词、编号、型号、代码恰恰是向量的弱项（搜 "iPhone16 512GB" 可能召回 "iPhone15 128GB"）。真实系统常常两个都上
以为向量库是"更高级的搜索引擎"它解决的是语义相似，不解决"相关度排序、高亮、聚合统计"这些搜索工程问题——那些还是全文检索的活
2② Embedding：把"意思"变成数字
要解决什么

上一节说要"比坐标远近"，可文字是文字、数字是数字，怎么把一句话变成一串数字？ 而且这串数字还得保住语义——"苹果好吃"和"苹果手机贵"不能变成同一个坐标。

这个变换步骤有个专门的名字：Embedding（嵌入/向量化），由大模型的 Embedding 模型完成，比如 BGE（BAAI/bge-small-zh）、OpenAI 的 text-embedding 系列。

核心思路

Embedding 模型也是用海量文本"喂"出来的：它学会了把"语义相近的句子"映射到向量空间中距离近的位置。输入一段文字，输出一个几百上千维的浮点数组（向量）：

输入输出（示意，真实是 384~3072 维的数组）
"养老保险要交几年"[0.12, -0.34, 0.87, 0.01, ...]
"社保缴费年限是多久"[0.13, -0.31, 0.85, 0.02, ...] ← 和上面很接近
"今天天气不错"[-0.52, 0.41, -0.08, 0.93, ...] ← 离得远远的

三个关键事实：

  1. 同样的模型才能比：比距离必须用同一个 Embedding 模型生成，跨模型比毫无意义
  2. 维度必须一致：向量库索引对维度有要求，"写入时 384 维、查询时用 512 维"直接报错
  3. 一次对全库做向量化是个大工程：所以流程永远是"入库前批量算好存进去"而不是"查询时现算"

这一节对应的真实代码（后面每个产品都会用到）：

from sentence_transformers import SentenceTransformer
model = SentenceTransformer("BAAI/bge-small-zh")   # 一个国产开源小模型，几百MB
embs = model.encode(["养老保险要交几年", "今天天气不错"], normalize_embeddings=True)
坑在哪
现象原因
以为可以混用不同模型生成的向量不同模型把文字映到完全不同的向量空间，混在一起算距离等于随机。而且换模型 = 整个库作废重灌——这是 RAG 最贵的一次返工
忘了 normalize_embeddings=True很多库（Chroma / FAISS）默认用点积。向量不归一化时，"长文本"的向量天然更长、点积更大，会压过真正语义更近的短文本。用余弦就该显式归一化
以为维度越高效果越好维度高确实更精细，但内存和计算量随之上涨、检索更慢。384~1024 维对中文场景通常够用，别盲目追高维大模型
拿"模型排行榜第一名"直接上榜单多测英文通用任务。中文、垂直领域（法律/医疗）要在自己的数据上试，小模型常常不输大模型
3③ 相似度怎么算：三种距离
要解决什么

坐标有了，问题变成"多远算近"。同样两个向量，用不同算法量出来的远近还不一样——该用哪个？用错会捞回一堆"看起来近其实不相关"的结果。

三个主流算法各有脾气：

  • 欧氏距离（L2）：勾股定理意义上的直线距离，数值小 = 越近。

直观，但向量维度很大时，所有距离都会"糊"成一团（维度灾难）。

  • 余弦相似度：只看方向不在乎长度（两句话长短差 10 倍，语义相同就相似度高）。文本场景的默认首选。
  • 点积（内积）：方向一致又都比较"大"才算近；常用于向量的长度本身携带信息时（部分向量库默认用点积加速）。
核心思路

选算法的口诀：

场景推荐原因
文本/语义检索（RAG）余弦相似度语义只看方向，且实现简单、效果稳
数值型数据最近邻（手机号、坐标）欧氏距离数字相近就是物理上"挨得近"
带权重/长度的向量（部分推荐系统）点积同时考虑方向与强度

注意：不少向量库（Chroma、FAISS）用点积 + 向量归一化来等价实现余弦相似度（归一化后三者可互相换算），所以不用纠结库的默认值，明白语义就够了。

坑在哪
现象原因
归一化没做，可比性就没保证余弦要求归一化；点积不要求。同一批没归一化的向量，用余弦和用点积排出来的"最近邻"可能不一样。换库/换算法时结果变了，八成是这里
库的默认 metric 和你的预期不一致有的库默认 L2、有的默认点积。建索引时显式声明 metric_type，别用默认值赌
以为调距离算法能救效果距离算法的影响远小于 Embedding 模型和分块策略。效果不好先查那两样，别在这里调参
维度很高时用欧氏距离高维下所有点距离趋同（维度灾难），L2 会失去区分度。文本检索优先余弦
4④ ANN：百万级数据怎么"秒查"
要解决什么

精确算距离的做法是：拿查询向量和库里每一条向量挨个比距离，再排序取前 K 个（暴力搜索）。100 条数据无所谓，1000 万条就是 1000 万次距离计算，一次查询几百毫秒甚至秒级——企业级系统扛不住。

而且向量维度经常是 384~1536 维，暴力比对的计算量再乘一个巨大系数。

核心思路

答案是用近似最近邻（ANN，Approximate Nearest Neighbor）：不追求 100% 找到最相似的，只要求"极大概率找到那批最相似的"——换来的是百倍千倍的速度提升。主流索引算法有三大流派：

索引思路（人话）适合
HNSW跳表式"小世界图"：从粗到精层层逼近大规模、要速度，当下最主流
IVF先聚类分桶，只在最近的几个桶里找中等规模、省内存
PQ把高维向量压缩成短码再比数据超大、内存吃紧

打个比方：HNSW 像"先翻目录看城市，再进小区找楼"，而不是把全国每栋楼都扫一遍。召回率通常在 95%+，但速度提升两个数量级。

暴力搜索：  扫全库  → 100% 准确，但 O(N) 太慢
ANN(HNSW)：粗筛+精排 → ~95% 准确，O(log N) 极快
坑在哪
现象原因
以为 ANN 的结果和暴力搜索一样准ANN 是近似，天生有召回损失——"该找到的没找到"是常态。关键业务必须自己做召回率评测（构造问题→期望资料测试集），不能默认 95% 就够用
数据才几千条就上 HNSW小数据量下精确搜索（Flat）又快又准，索引反而增加复杂度。别过早优化
以为索引建完就一劳永逸数据持续写入后，HNSW 的删除只是标记删除，图会越来越"虚"、查询越来越慢。要定期重建/压缩索引
只调 efSearch / nprobe 追精度调大能提召回，但延迟和内存跟着涨。这是和 QPS/延迟的取舍，不是免费的
5⑤ 向量数据库的完整使用流程
要解决什么

很多人第一次接触向量库时一头雾水：到底先做哪步、后做哪步？是先把整本书塞进去吗？数据是从数据库读还是从文件读？

其实向量数据库的使用是一个固定套路，四步走，和"上架商品"一模一样：

核心思路 
① 数据准备   文档 → 清洗 → 切块(chunk) → 每块单独成为一条记录
② 向量化入库  每条记录调用 Embedding 模型 → 得到向量 → 连同原文和元数据一起写入
③ 查询向量化  用户问题 → 同一个 Embedding 模型 → 得到查询向量
④ 检索返回    在库里做 ANN → 返回最像的 Top-K 条（原文 + 相似度 + 元数据）

三个必须记住的细节：

  • 只入库存原文不够，只存向量也不行：向量用来"找"，原文用来"给模型看"，元数据（来源、页码、时间）用来"溯源展示"——三者一起存
  • 查询和入库必须用同一个模型：换模型 = 整个库作废重灌
  • 以后知识更新就再走①→②：这就是 RAG"实时更新知识"的底气所在
坑在哪
现象原因
以为"更新知识"就是改掉原来的文档改完源文档必须重新分块 → 重新向量化 → 重新入库。只改文件不重灌，用户看到的还是旧答案——这是最容易被忽略的一步
只存向量、不存原文检索出来只有一串数字，模型没东西可看、也没法溯源。原文和元数据必须一起存
用固定字数硬切分块会把一句话、一张表格从中间劈开，捞出来是半截。要按文档结构（标题/段落）切，并留重叠
以为"入库一次就完事"知识库是要持续维护的：文档增删改、分块策略调整、Embedding 模型升级，每一步都可能要重灌全库。要提前设计好这套流程
6⑥ 选型五大因素：别一上来就问"哪个最好"
要解决什么

网上搜"向量数据库推荐"，能搜出一堆产品名：FAISS、Milvus、Pinecone、Chroma、Qdrant、Weaviate、Elasticsearch……新人容易犯两个错：一是跟风选"最火的"，二是硬套"最重的"。选型的对错，取决于你的场景在五个维度上的取值。

核心思路

选型就是在这五张牌里做取舍：

因素人话解释关键指标
性能扛得住多大并发？多快出结果？准不准？QPS（每秒查询数）、P99 延迟、Recall@K（召回率）
成本开源白嫖 vs 云服务付费；吃多少内存/GPU每百万向量的资源消耗
易用性装起来麻不麻烦？API 好不好写？团队熟不熟部署复杂度、文档质量
扩展性数据涨 100 倍怎么办？单机能变集群吗分布式、水平扩容能力
功能特性能否混着全文检索？支持元数据过滤吗混合检索、Filter、实时更新

三个指标是面试常客，用生活化方式理解：

  • QPS = 收银台一秒钟能结多少个顾客的账，衡量"吞吐"
  • P99 = 100 个顾客里排第 99 慢的那个等了多久，衡量"响应快不快"（比平均值更能反映卡顿）
  • Recall@K = 我想要的 100 个答案，Top-K 里捞回来了几个，衡量"准不准"

它们互相牵制：QPS 冲高 → 延迟变大；硬要 Recall 高 → 搜索变细 → 延迟和 QPS 都劣化。所以企业级里这叫"调参三角"，没有免费午餐。

坑在哪
现象原因
跟风选"最火的"或"最重的"个人项目上 Milvus Cluster → 运维压垮你；生产环境用 FAISS → 无持久化无并发，出事兜不住。选型取决于你的场景，不取决于热度
只盯平均值，不看 P99平均 20ms 但 P99 是 2s，用户体验就是"偶尔卡死"。对外服务必须看 P99/P999
以为 QPS 越高越好QPS、延迟、召回率是互相牵制的三角，提一个必牺牲另一个。先定业务优先级（是求快、求准、还是求省），再调
忽略"运维成本"这一项团队熟不熟、有没有人能维护，往往比性能更决定成败。选一个没人会运维的明星产品 = 给自己埋雷
7⑦ FAISS：本地轻量级的默认选择
要解决什么

你只是个人项目、课程作业，或者公司数据不能出内网——不想为检索专门起一个服务、不想交云费、就想在 Python 里直接 import 一个库把事办了。FAISS 就是为这个场景生的。

FAISS（Facebook AI Similarity Search）是 Meta 开源的高性能相似度搜索库，不是数据库服务，而是一个 Python/C++ 库：数据在内存里，索引你说了算。

核心思路 
pip install faiss-cpu        # CPU 版，Windows 可用
# pip install faiss-gpu     # GPU 版需 Linux + CUDA，速度可提升 10~100 倍

上手极简：建索引 → 塞向量 → 查询。下面用讲义同款"数字向量"（手机号/订单号）演示全流程——数字一样能做向量检索，这比上来就上文本模型更好理解核心机制：

import numpy as np, faiss

items = [{"type": "phone", "id": "用户A", "number": 13800001234},
         {"type": "order", "id": "订单1001", "number": 203011010001}]
numbers = np.array([r["number"] for r in items], dtype="float32")

index = faiss.IndexFlatL2(1)      # 1 维索引，L2 欧氏距离（数字挨得近=相似）
index.add(numbers.reshape(-1, 1)) # 塞向量

k = 2
distances, indices = index.search(np.array([[205001020500]], dtype="float32"), k)
print(distances, indices)          # 距离小 = 数字接近

实战约定：

数据量用什么索引
<10 万IndexFlatL2（精确搜索）
10 万~100 万IndexIVFFlat（倒排分桶）
>100 万IndexHNSW（图索引）或 IndexIVFPQ（压缩省内存）
坑在哪
现象原因 / 怎么办
以为 FAISS 能当数据库用FAISS 无持久化、无元数据管理、单机内存——重启就丢，要自己落盘（pickle/文件）
GPU 版装不上faiss-gpu 在 Windows 不支持，换 faiss-cpu 或上云/容器
维度很大时查询变慢数据量大就该换 HNSW 而不是 Flat
8⑧ Milvus：企业级分布式的答案
要解决什么

FAISS 的路走到头了：数据量过亿、要多人并发、要高可用、要权限管理——FAISS 一样都没有。这时候需要真正的"数据库"，而不是"库"。

Milvus 是专为 AI 场景设计的开源向量数据库：云原生架构、分布式部署、水平扩展，生产环境的高可用、多租户、权限管理都是原生能力。

核心思路

三种部署方式按需取用：

方式适合特点
Milvus Lite入门/教学/原型单文件、零运维，一条连接串搞定
Standalone个人/小项目docker-compose 拉起来，持久化
Cluster生产级K8s + Helm，多租户、自动扩容

性能参考：单节点数万 QPS、P99 < 50ms、单集合可支持万亿级向量（前提是索引与机器到位）。

上手示例（和 FAISS 同一个"数字向量"案例，但走正规数据库流程：先定义 Schema 再入库再检索）：

from pymilvus import connections, FieldSchema, CollectionSchema, DataType, Collection
import numpy as np

connections.connect(host="localhost", port="19530")

# ① 定义集合结构（注意：Milvus 要求向量维度 ≥ 2）
fields = [
    FieldSchema(name="id", dtype=DataType.INT64, is_primary=True, auto_id=True),
    FieldSchema(name="type",   dtype=DataType.VARCHAR, max_length=50),
    FieldSchema(name="number", dtype=DataType.INT64),
    FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=2),
]
schema = CollectionSchema(fields, "数字向量集合")
collection = Collection("numbers_collection", schema)

# ② 建索引 → 加载到内存 → 检索
collection.create_index("embedding", {"metric_type": "L2", "index_type": "FLAT"})
collection.load()
results = collection.search(
    data=[query_vec.tolist()], anns_field="embedding",
    param={"metric_type": "L2"}, limit=5,
    output_fields=["type", "item_id", "number"],
)
坑在哪
现象原因 / 怎么办
报错 invalid dimension: 1. should be in range 2 ~ 32768Milvus 不接受 1 维向量，维度必须 2~32768；把数字"复制成两列"即可绕过
部署了很久没起来Cluster 模式依赖 K8s 生态，个人先用 Standalone（docker-compose）体验
9⑨ Elasticsearch 也做向量检索：混合检索王者
要解决什么

向量检索擅长"语义"，但对精确词、数字、代码不敏感：搜"iPhone16 512GB"，它可能把"iPhone15 128GB"当最像的。而全文检索擅长精确匹配，却听不懂"同义改写"。

很多企业两个都要：既按关键词搜，又按语义搜，最后合并结果。这时候"一个平台全搞定"就是刚需——Elasticsearch（ES）就是那个同时能打的选手：它本来就是分布式搜索引擎，7.3 版本起原生支持向量检索（kNN）。

核心思路

ES 的向量检索三板斧：

  1. dense_vector 字段：在索引里定义一个向量字段，写入时按维度声明
  2. HNSW 索引：默认用 HNSW 算法做 ANN，和专用向量库同级
  3. script_score / kNN 查询：查询时把向量相似度转成"相关度分数"参与排序

典型"混合检索"姿势：BM25 关键词打分 + 向量相似度打分加权合并，既懂精确匹配又懂语义。这也是下一章 ES 的重头戏，这一节先记住一句话：

FAISS / Milvus  → 专业向量检索，术业有专攻
Elasticsearch  → 全文 + 向量一把抓，企业统一平台

选了 ES 就意味着：团队只要维护一套集群，日志搜索、站内搜索、语义检索全都能跑，运维成本摊薄。

坑在哪
现象原因
以为 ES 装上就能做向量检索要 7.3 以上版本，而且必须显式定义 dense_vector 字段并声明维度——不是自动就有的能力
以为 ES 的向量性能等同专用向量库ES 的 kNN 是"够用"级别，亿级以上还是 Milvus 更合适。ES 的价值在"一个平台全搞定"，不在极致性能
混合检索时把两路分数直接相加BM25 分数无界、余弦是 0~1，直接相加会让 BM25 完全压过向量路。必须先归一化再加权（下一章细讲）
10⑩ Pinecone：零运维的云服务
要解决什么

公司没有专门运维、项目要一周上线，不想关心部署、扩容、备份——只想 pip install 然后调用。这就是托管云服务 Pinecone 的定位：完全托管的向量数据库 SaaS。

核心思路 
from pinecone import Pinecone
import os
pc = Pinecone(api_key=os.environ["PINECONE_API_KEY"])   # 从环境变量读，绝不写死在代码里
index = pc.Index("demo")
index.upsert(vectors=[("doc-1", [0.1, 0.2, 0.3], {"source": "faq.pdf"})])   # id + 向量 + 元数据
print(index.query(vector=[0.1, 0.2, 0.3], top_k=5, include_metadata=True))

优势：开箱即用、自动扩容、免运维，适合快速原型验证。 代价：闭源云服务，数据要出公司，且按量计费——对数据敏感的企业直接出局。另外免费额度紧、不可自建，长期大流量成本不低。

核心思路

一句话决策：要"快"且能接受数据上云 → Pinecone；要"控"（开源/内网/自建）→ 回到前面的开源方案。

坑在哪
现象原因
把 API Key 写死在代码里云端 Key 泄露 = 别人拿你的账号花钱。上面示例里那行 os.environ["PINECONE_API_KEY"] 不是装饰——永远从环境变量读，也别提交进 Git
选型时没做合规评估数据要出公司。金融、医疗、政务这类在选型之前就该否掉，不是上线后才发现
以为免费额度够撑到上线免费额度通常只够验证。长期大流量成本不低，要算 TCO 而不是只看起步价
没设预算告警按量计费 + 没有告警 = 某天收到一张意外账单。开用量上限
11⑪ 轻量级三剑客：Chroma / Qdrant / Weaviate
要解决什么

FAISS 太"裸"（没元数据、没持久化），Milvus 又太重（要装服务）。中间地带：小型项目想要"装起来就忘掉、自带持久化和过滤"的数据库。Chroma、Qdrant、Weaviate 就是为这个生的轻量级选手。

核心思路
产品一句话定位部署特点
Chroma最容易上手的"Pythonic"向量库pip install chromadbAPI 像写字典，自带持久化，教程生态最好，RAG 新手首选
Qdrant性能至上的 Rust 向量库docker 一条命令单机性能强、延迟低、支持丰富过滤；要"极致性能"选它
Weaviate带图关系的向量库docker-compose自带 GraphQL 查询、类图数据库的关系能力，复杂关系场景适用

它们都能做元数据过滤（比如"只看这个来源的"），这是 FAISS 没有的。三个都是 docker 或 pip 就能跑：

# Chroma
pip install chromadb
# Qdrant
docker run -p 6333:6333 qdrant/qdrant
pip install qdrant-client
# Weaviate
docker compose up -d weaviate
pip install weaviate-client

以 Chroma 为例（下一章端到端 Demo 的主角，这里先混个脸熟）：

import chromadb
client = chromadb.PersistentClient(path="chroma_db")     # 持久化到本地目录
collection = client.get_or_create_collection("demo")
collection.upsert(
    ids=["doc-0"], documents=["养老保险要交满15年"],
    embeddings=[[0.1, 0.2, 0.3]], metadatas=[{"source": "faq.pdf"}],
)
print(collection.query(query_embeddings=[[0.1, 0.2, 0.3]], n_results=1))
坑在哪
现象原因
以为"轻量"就等于"能上生产"这三家的定位是"装起来就忘掉"，高并发、大规模、高可用不是它们的强项。Chroma 尤其适合原型和教学，真上生产要评估 Qdrant 或 Milvus
用 docker 跑却没挂数据卷容器一删、一重建，数据全没。上面那条 docker run -p 6333:6333 qdrant/qdrant 只是最小示例，生产必须挂 -v 到宿主机
以为三家的"过滤"能力一样各家 filter 的语法、支持的操作符、过滤后是否仍走索引都不同。量大时过滤会显著影响性能，选型要压测
以为 pip install 就不用起服务了Chroma 可以纯本地，但 Qdrant 和 Weaviate 是需要独立服务进程的（docker）。别以为都是"一个库"
12⑫ 选型决策树：照着场景对号入座
要解决什么

五张牌、七个产品都认识了，最后的问题是我到底该用哪个？ 纠结本身就是在浪费时间——记住下面这张决策树，半分钟出答案。

核心思路 
你的场景 →
├─ 个人学习 / 小项目 / 预算为 0
│    └─ FAISS（本地库） 或 Chroma（要持久化+过滤）
├─ 快速原型 / 不想运维 / 数据可上云
│    └─ Pinecone
├─ 企业生产 / 大规模 / 要高可用
│    ├─ Milvus（纯向量检索为主）
│    └─ Elasticsearch（要全文+向量混合或用它家全家桶）
├─ 极致性能 / 低延迟要求
│    └─ Qdrant 或 FAISS（GPU）
└─ 复杂关系 / 图结构场景
     └─ Weaviate

三条补充经验：

  1. 别在生产环境玩 FAISS：无持久化、无元数据、无并发管理，出事兜不住
  2. ES 不是"向量库里的第二名"：当你有全文检索需求时它是一号位，二者是"用不用混合检索"的问题
  3. 架构上随时可换：向量库 API 大同小异（upsert/query），前期选错代价没想象中大——先跑通，再演进

本章小结

这一章你拿到了 RAG 的第一块地基：

  • 明白向量数据库解决的是"语义相似搜索"——传统 SQL 的 LIKE 做不到
  • 掌握 Embedding、相似度算法（余弦/L2/点积）、ANN（HNSW/IVF/PQ）三大底层概念
  • 能背出七大产品定位：FAISS=本地轻量 / Milvus=企业分布式 / ES=混合检索 / Pinecone=零运维云 / Chroma=最易上手 / Qdrant=高性能 / Weaviate=带关系
  • 会按"选型决策树"对号入座，而不是听别人推荐

下一章把这些能力叠到 Elasticsearch 上——企业级 RAG 的另一半（全文检索）。
