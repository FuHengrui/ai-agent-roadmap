第一章　模型压缩的目的与评估指标

阶段 23 · 模型压缩与高性能推理优化　|　压缩入门　|　难度 ★★☆
这一章在解决什么问题

大模型越训越大，参数动辄几十亿上百亿，直接部署的结果是"模型文件塞不进显存、推理慢到没法用、单个请求耗电惊人"。模型压缩要回答三个问题：为什么要压、压到什么程度算好、怎么量化"压得好不好"。这一章先把目的和两把评估尺子讲清楚——压缩率（Compression Ratio）和理论加速比（Theoretical Speedup），它们是后续所有压缩技术的"验收标准"。

上一章→本章→下一章 上一章（阶段22）学完了 Transformer 与大模型的基础架构。本章从"目标与度量"切入模型压缩，建立"压缩多少、快多少、准度掉多少"的坐标系。下一章总览四大压缩路线（剪枝/量化/知识蒸馏/紧凑网络）与主流框架生态，随后分章展开。
1① 模型压缩的目的：两个核心诉求
要解决什么

大模型部署时最头疼的问题是什么？压缩到底图什么？

核心思路

模型压缩的目的可以浓缩成两句话：

  1. 让模型体积更小——文件从几 GB 降到几百 MB，显存/内存才放得下，带宽才扛得住。
  2. 让推理速度更快——同样一次预测，延迟更低、吞吐更高，才能支撑线上服务。

这两件事不是附赠品，而是部署的硬前提：模型再准，如果塞不进目标硬件、响应慢到用户流失，就是不可用的。压缩的全部分支（剪枝、量化、蒸馏…）都服务于这两个目标，只是手段和代价不同。

坑在哪
现象原因 / 怎么办
以为压缩只图体积体积与速度是两个维度，有的技术（如 float16 量化）体积减半但不一定显著提速
压缩过头只看准度压缩的收益必须和精度损失、推理延迟一起看，单看某一项没有意义
2② 压缩率：衡量"体积缩小多少"
要解决什么

"压得好不好"第一个尺子是什么？怎么算？

核心思路

压缩率（Compression Ratio） 的定义：

压缩率 = 总参数量 / 非0参数量
  • 总参数量：原始网络的全部参数个数。
  • 非0参数量：优化后模型中非 0 的参数个数（剪枝把大量参数置 0，压缩后只需存非 0 部分与其索引）。

直观理解：如果原模型有 1 亿个参数，剪枝后有 2000 万个非 0，压缩率就是 5——理论上模型文件（在合适的稀疏存储下）可以缩到原来的 1/5。这个指标直接回答"体积小了多少"。

坑在哪
现象原因 / 怎么办
用参数量代替压缩率压缩率是比值（原参数/非0参数），不是绝对参数量，别把"还剩多少"当"压缩了多少"
以为参数变 0 文件自动变小要配合稀疏矩阵存储（只存非0+索引），否则文件里还是满的 0
3③ 理论加速比：衡量"推理快多少"
要解决什么

光体积小了还不够，推理速度怎么估？

核心思路

理论加速比（Theoretical Speedup） 的定义：

速度 = 总FLOPS / 非0 FLOPS
  • 总FLOPS：原始网络全部浮点运算量。
  • 非0 FLOPS：优化后网络中非 0 参数对应的运算量。

FLOPS（每秒浮点运算次数）在这里代表"完成一次推理要算多少次乘加"——运算量越低，理论上越快。把被剪掉的参数计算量从分母里去掉，比值就是"快了 X 倍"的理论上限。

要强调"理论"二字：实际加速还取决于硬件、稀疏算子是否优化、内存带宽等，理论值只是方向性判断。

坑在哪
现象原因 / 怎么办
把 FLOPS 与参数个数混为一谈参数量衡量存储，FLOPS 衡量计算；速度看 FLOPS 的减少
把理论加速比当实测值理论值不含带宽/算子开销，实测通常低于理论值，只能做预算
4④ 为什么用"非0"来算：稀疏性的红利
要解决什么

压缩率与加速比公式里反复出现"非0"，背后是什么道理？

核心思路

剪枝的本质是把不重要的连接参数置为 0，让密集张量变稀疏。用"非0"计数的原因：

  • 存储红利：文件里 0 不占有效信息（稀疏格式只存非0值与索引），所以"非0越少，文件越小"。
  • 计算红利：理论上乘 0 可以跳过，所以"非0运算越少，理论上越快"。
  • 显存红利：稀疏张量占用内存带宽更少，大模型部署更容易。

因此，"非0参数量/非0FLOPS"是最能反映压缩真实收益的口径——它天然把三种红利统一在两根尺子里。

坑在哪
现象原因 / 怎么办
忽略稀疏存储的前提数字上的 0 只有配了稀疏表示/稀疏算子才真有收益，密集存储下 0 也占空间
以为稀疏度可以无穷大稀疏度过高精度崩坏（见剪枝章节），压缩率与精度是 trade-off
5⑤ 两个指标怎么配合使用
要解决什么

压缩率和理论加速比是两把尺子，实际怎么一起用？

核心思路

两把尺子各管一段：

  • 压缩率回答部署问题：模型装得下吗？传输快吗？→ 看存储。
  • 理论加速比回答服务问题：线上延迟顶得住吗？吞吐够吗？→ 看计算。

实际压缩项目的验收流程：

1. 记录原模型参数总量与总FLOPS
2. 压缩后统计非0参数与非0FLOPS
3. 分别计算压缩率与理论加速比
4. 评估精度损失（在测试集上的表现）
5. 综合判断：收益是否值回准确率代价

没有万能的单一指标——体积与速度可能与精度冲突，"最优"取决于具体部署场景。

只报压缩率不报准度一个"压了10倍但精度掉光"的模型没有意义，指标必须配套精度评估
用同一指标套所有场景移动端更在意体积，云端服务更在意延迟/吞吐，验收标准跟着场景走
6⑥ 压缩是"全能"还是"有代价"
要解决什么

既然压缩能让模型又小又快，为什么不无脑压到底？

核心思路

压缩的本质是信息取舍：把不那么重要的冗余参数去掉或换低精度表示，代价是精度损失与不确定性增加。

  • 剪枝过头 → 表达能力不足，准确率骤降。
  • 量化过狠（如 int2）→ 数值误差累积，输出质量下降。
  • 蒸馏的学生太小 → 学不到老师的全部知识。

所以"压多少"永远在三个变量里找平衡：体积、速度、精度。后面每一章的技术（剪枝粒度、量化位宽、蒸馏温度…）本质上都是在调这个平衡点。

坑在哪
现象原因 / 怎么办
只看压缩红利忽视代价每次压缩后都必须做精度验证，不能"压完就上线"
以为所有技术可以无脑叠加剪枝+量化+蒸馏叠加时相互作用复杂，需要协同设计与调试
7⑦ 大模型时代压缩为什么更重要
要解决什么

小模型时代压缩是"锦上添花"，为什么到了大模型反而成了必选项？

核心思路

大模型的三重压力把压缩从"优化项"推成了"必经项"：

  1. 显存墙：几十亿参数的权重动辄十几 GB，单卡放不下（8bit 量化能省 4 倍）。
  2. 成本墙：推理按 token 计费，模型的每一点冗余都会放大到运营成本上。
  3. 延迟墙：长上下文下逐个生成 token，KV 缓存暴涨，吞吐与延迟互相挤压。

这正是工业界几乎每个上线的大模型都在做量化和剪枝的原因——模型强不强是一回事，能不能经济地跑起来是另一回事。

坑在哪
现象原因 / 怎么办
认为压缩只属于"边缘设备"云端大模型同样重度使用量化/蒸馏（如 vLLM 支持的 AWQ/GPTQ/FP8），是全局刚需
忽略 KV 缓存等额外开销大模型推理的显存大头常被 KV 缓存占据，压缩技术还要考虑激活与缓存的优化
8⑧ 本章小结：从"为什么压"到"怎么量"
要解决什么

模型压缩这门课的整体框架该怎么建立？

核心思路

以"目的-尺子-路线"三层建立认知骨架：

目的：体积更小、速度更快
尺子：压缩率（存储）、理论加速比（计算）
路线：剪枝 / 量化 / 知识蒸馏 / 紧凑网络（下一章展开）
约束：全程评估精度损失，寻找体积-速度-精度平衡

学完本章，你应该能回答："压缩是在做什么？用什么指标衡量？有什么代价？"——这三问是所有压缩技术的共同地基，后面的每一个章节都是在这块地基上盖楼。

坑在哪
现象原因 / 怎么办
跳过概念直接看具体技术没有"目的+尺子"的坐标系，看剪枝/量化会迷失在各式细节里
不记公式含义压缩率与加速比的公式很简单，但含义（非0计数/理论值）才是考试与实战的关键

本章小结

这一章建立了模型压缩的"目的-度量"坐标系：

要点内容
两大目的体积更小、推理更快
压缩率总参数 / 非0参数，衡量存储收益
理论加速比总FLOPS / 非0FLOPS，衡量计算收益
非0计数逻辑稀疏表示才带来真实收益（存储/计算/带宽）
代价精度损失与不确定性，"体积-速度-精度"三方平衡
大模型时代显存墙/成本墙/延迟墙使压缩成为必经项

一句话记住本章：模型压缩的核心目的只有两个——体积更小、速度更快；验收靠两根尺子——压缩率（总参数/非0参数）和理论加速比（总FLOPS/非0FLOPS），但任何压缩都逃不开"体积-速度-精度"三方权衡，这是全书所有技术共同的地基。
