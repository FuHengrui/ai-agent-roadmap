## 这是什么

一套**按需求重新整理的 AI 笔记**，面向从零开始的初学者。

写法只有一条规矩：

> **每个知识点都先回答「它要解决什么问题」，再讲怎么用，最后说哪里会踩坑。**

因为**知识是学不完的，但需求是有限的**——你把需求搞清楚了，知识就是顺着藤摸瓜。

## 它有什么不一样

### ① 需求驱动：先让你"痛"，再给解药

**❌ 一般的写法**

```markdown
## 列表
列表是 Python 中最常用的数据结构，用方括号表示……
```

**✅ 这里的写法**

```markdown
@@point ① 列表：一次装很多数据
@@need 要解决什么
上一章你学会了处理【一个】数据。但真实世界不会一次只给你一个——
你要处理 100 条招聘信息、一张成绩表。
如果只用上一章的知识，你得写 job1、job2……job100 一百个变量。

@@idea 核心思路
列表就是解决这个的：一个变量装一串数据……
```

**判断标准只有一句：读完这段，一个不懂的人能不能说出「哦，原来是为了解决这个」。**

### ② 每条"坑"都是真踩过的

2,070 条避坑记录，分两类：

| 类型 | 例子 |
|---|---|
| **操作坑** | `EXPOSE 8080` 写了但外面连不上 → **`EXPOSE` 不是开门，`-p` 才是** |
| **认知坑** ★ | 以为 `RAG` 就是向量检索 → **向量只是检索的一种实现，RAG 是架构** |

**认知坑更值钱**——操作坑你搜一下能搜到，**但"我以为是这样、其实是那样"，没人会主动告诉你。**

### ③ 结构化成数据，而不是散文

正文用的是自定义的 `@@` 指令，每个知识点被强制拆成三格：

```
@@need   它要解决什么问题
@@idea   核心思路
@@trap   坑在哪
```

**这是整套东西的关键**：散文写起来舒服，但**读者抓不住重点，AI 也写不稳**。

## 跑起来

**只需要 Python 3.10+，没有任何第三方依赖**（流水线是纯标准库）。

```bash
# 生成 HTML（输出到 site/）
python tools/build_site.py

# 同步首页侧边栏
python tools/sync_index.py

# 自检：结构完整性 + 死链 + 样式
python tools/verify_site.py

# 内容质检：六块结构 / need 覆盖率 / 密钥泄露 / 个人信息
python tools/check_content.py
```

**看效果**：双击 `site/index.html`。

## 方法论（这部分可能比正文更有用）

如果你也想用 AI 生产长内容，这几条是花了两个星期、翻过三次车换来的。

### 1. 规格先行，别让 AI 自由发挥

`docs/写作规格.md` 有 692 行，规定了三套章法：

| 章法 | 什么时候用 |
|---|---|
| **知识型** | 有教材、讲概念 |
| **项目型** | 只给需求书 + 成品代码，要反推设计 |
| **操作型** | 装软件 / 点后台 / 配界面 |

**不给规格，AI 会写成流水账；给了规格，它才知道"什么算合格"。**

### 2. ⚠️ 该给数字的地方必须给数字

**这是最反直觉、也最贵的一条教训。**

有一次我觉得「`@@trap` 覆盖率要 60–80%」这个指标太死板，就把它改成了：

> 「不要按百分比写，覆盖率是结果不是目标」

**结果下一批内容的质量直接崩了——覆盖率从 100% 掉到 15%。**

**教训：**

> 想表达"别死守这个数字"，要写清「**在什么情况下可以低于它**」，
> **而不是把数字删掉**。删掉数字 = 告诉对方"这条不作数了"。

### 3. 质量要能自动检查，否则没法规模化

`check_content.py` 每次跑都检查：

- 六块结构齐不齐
- **每个知识点有没有写「要解决什么」**（覆盖率必须 100%）
- **有没有 API Key 泄露** ← 这条救命
- 有没有个人信息、视频链接

推上去之后 CI 还会再拦四道：

- **`check_publish.py`** —— 扫整个仓库（不只是正文）里的违禁词、密钥、不该提交的文件类型
- **`check_consistency.py`** —— 目录说的和正文写的必须一致：不能两个阶段挂同一个源文件，每章 `@@sub` 的阶段号、`@@h1` 的章号都要跟 `site_config.py` 对得上
- **`stats.py --check`** —— README 上那几个数字（章节 / 知识点 / 坑 / 自测题）跟实际算出来的比，不一致就报红
- **`site/` 一致性** —— CI 重建一遍，和仓库里的 `site/` 有差就报红，逼你先把站点重新构建再提交

**为什么要有「一致性」这一道**：真出过事故 —— 阶段 9 的前两章和阶段 10 共用了一个源文件，页面副标题写着「阶段 10」、正文在讲另一个项目，目录里它却属于阶段 9。页面本身看不出错，人眼发现不了。

**为什么要查密钥**：让 AI 写代码示例，**它真的会把参考材料里的真 Key 抄进去**。我在自己整理的材料里就抓到过 4 个真实的 API Key。

### 4. 没有图的时候，用「说清在哪 + 让读者自查 + 把迷路写进坑」来补

有些章节讲的是可视化后台操作（建机器人、配通道），但截图有版权不能用。

**解法三条：**

1. **开头挑明**："本章全是后台操作，代码不到 20 行，建议开浏览器跟着点"
2. **给检查项表**："账号权限：普通成员**看不到**这个菜单" ← 让读者自己确认走对了
3. **把"找不到入口"写进坑**："手机 App 里翻不到 → 在**官网管理后台**，不是手机端"
