@@h1 第七章　饮食、用药、运动三大记录模块
@@sub 阶段 10 · 安康智慧健康管理平台（糖尿病AI健康助手）　|　2 课时　|　难度 ★★★

@@why 这一章在解决什么问题
糖尿病管理"五驾马车"里，除了血糖监测，还有饮食、用药、运动。上一章学会了血糖模块，本章一口气拿下三个记录型模块——它们**骨架高度相似但各有增量**：饮食带 GI 语义、用药带 active 状态、运动带血糖变化属性。本章解决三件事：**一是识破"三个 CRUD 其实是同一个模板"**，**二是掌握每个模块的独门字段与接口**（营养/剂量/运动前后血糖），**三是学到 active_only 筛选等实用查询模式**。

关键认知：**先复制骨架、再叠加差异**——三个模块 80% 代码同构，剩下 20% 才是理解重点。会写一个就能秒懂另外两个。

@@map 这一章在整个知识库里的位置
上一章：血糖模块——CRUD + 统计引擎
**本章** ← 你在这里：饮食/用药/运动——三大记录模块，前缀 /diet /medication /exercise
再往后：健康报告与 LLM 客户端（跨模块聚合）
再往后：RAG → LangGraph
阶段终点：三类日常行为数据都能录入、查询，为 AI 引擎备好数据源

@@point ① 三个模块的地图：同构与差异一眼看清
@@need 要解决什么
面对三个看起来一样的模块，怎么快速抓住学习重点？

@@idea 核心思路
把三个模块对齐看，差异一目了然：

| 维度 | 饮食 /diet | 用药 /medication | 运动 /exercise |
|---|---|---|---|
| 创建 | DietRecord.create | Medication.create | Exercise.create |
| 列表 | 最近50条按 eaten_at 倒序 | active_only 可选 | 最近30条按 performed_at 倒序 |
| 更新 | exclude_unset + refresh | exclude_unset + refresh | update_from_dict |
| 删除 | delete + 404 | delete + 404 | delete + 404 |
| **独有** | gi_level 计算属性 | is_active 筛选 | bs_change 计算属性 |
| **引擎** | diet_advisor（营养+推荐） | 无 | 无 |

学习策略：**先通读饮食模块（最全），用药/运动只看差异**。三个模块的"共性部分"（创建前验患者、404 兜底、exclude_unset 更新）和血糖模块完全一致——同一套纪律。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把三个模块当三个新知识 | 它们是同一模板的三次复制；抓住差异学，共性直接复用 |
| 模块间 prefix 搞混 | 一个 /diet 一个 /medication 一个 /exercise，URL 前缀必须各归各 |

@@point ② 饮食记录：食物营养四要素 + GI
@@need 要解决什么
一条饮食记录要记录哪些营养信息？前端怎么提交？

@@idea 核心思路
DietRecord 模型的核心字段（营养学四件套）：
- `food_name`：食物名称；
- `calories / carbs / protein / fat`：热量、碳水、蛋白质、脂肪（克或千卡）；
- `gi_value`：升糖指数，**决定 gi_level 计算属性**（低GI ≤55 / 中GI ≤70 / 高GI）；
- `meal_type`：餐次（早餐/午餐/晚餐/加餐）；
- `eaten_at`：进食时间。

创建路由与其他模块一样：先查患者 → `DietRecord.create(**data.model_dump())` → 构造响应时带 `gi_level=record.gi_level`。

**记录的是"吃进嘴的东西"，而计算属性 gi_level 让这条记录带上健康语义**——前端列表直接显示"低GI/高GI"，不用自己算。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 只填热量不填三大营养素 | carbs/protein/fat 是 diet_advisor 做营养汇总的输入，漏填汇总全是 0 |
| gi_value 填了但 gi_level 为 null | Response 构造时没带 gi_level 字段，或 gi_value 为 None 时返回"未知" |

@@point ③ 用药记录：is_active 与用药周期
@@need 要解决什么
患者可能停药、换药，列表怎么只显示"正在吃的药"？

@@idea 核心思路
Medication 模型两处关键：
- **周期字段**：`start_date` / `end_date` 标明用药起止；
- **状态字段**：`is_active`（默认 True）标记"当前有效"；

列表接口的差异化查询：
```python
@router.get("/patient/{patient_id}", response_model=List[MedicationResponse])
async def get_records(patient_id: int, active_only: bool = True):
    await Patient.get_or_none(id=patient_id)
    query = Medication.filter(patient_id=patient_id)
    if active_only:                      # 前端可传 active_only=false 看全部
        query = query.filter(is_active=True)
    records = await query.order_by("-start_date").all()
    return [...]
```

模式拆解：
- **条件组装**：先建 `query`，按参数决定是否追加过滤条件——"Filter 链可续写"，比写死两种查询优雅；
- **默认 True**：前端默认只看正在吃的药，符合业务直觉；
- **倒序起止日期**：新开的药排前面。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| active_only 传 false 还是只看到 active | 布尔类型默认真，传 false 会被忽略成"没传"？——用 Query 显式声明 `active_only: bool = True` 并配 `Query()` 传参才能正确覆盖 |
| 停药了列表还显示 | 只停 end_date 不改 is_active 没用；两个字段要联动（业务层处理） |

@@point ④ 运动记录：bs_change 的价值
@@need 要解决什么
"这运动降糖吗"不能靠感觉——运动前后的血糖差就是证据。

@@idea 核心思路
Exercise 模型特有字段：
- `exercise_type`：运动类型；`duration_min`：时长（分）；`intensity`：强度；`calories_burned`：消耗热量；
- `blood_sugar_before` / `blood_sugar_after`：**运动前后血糖值**——这两个字段喂给 `bs_change` 计算属性：

```python
@property
def bs_change(self):
    if self.blood_sugar_before and self.blood_sugar_after:
        return round(self.blood_sugar_after - self.blood_sugar_before, 1)
    return 0.0
```

如果运动后血糖 5.8、运动前 6.9，`bs_change = -1.1`——前端显示"血糖下降 1.1"，AI 引擎可据此提示"运动有效，注意低血糖"。**差值当负数看：负值 = 降糖成功**。

接口差异：运动更新用的是 `update_from_dict(data.model_dump())`，与前面模块的 setattr 循环等价但更简洁——Tortoise 提供的批量赋值外壳。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 只测了运动后血糖没测前 | bs_change 判空返回 0.0，不会崩但没意义；录入端应引导补测 |
| 忘了 round 导致 -1.1000000001 | 计算属性里 round(..., 1)，展示清爽也避免浮点噪声 |

@@point ⑤ 每日营养统计：diet_advisor 首秀
@@need 要解决什么
"今天吃了多少热量？碳水平衡吗？"——需要按天聚合营养数据。

@@idea 核心思路
路由很小，业务在引擎：
```python
@router.get("/patient/{patient_id}/daily")
async def get_daily_nutrition(patient_id: int, date: Optional[str] = Query(default=None)):
    patient = await Patient.get_or_none(id=patient_id)
    if not patient:
        raise HTTPException(status_code=404, detail="患者不存在")
    return await diet_advisor.get_daily_nutrition(patient_id, date)
```

diet_advisor 内部做的三件事：
1. **圈定当天**：把 date 转成 [当天0点, 次日0点) 半开区间，`eaten_at__gte=start` 且 `eaten_at__lt=end`；
2. **四维汇总**：`total_calories/protein/fat/carbs` 逐个 `sum(record.x or 0)`——**用 `or 0` 防 None**；
3. **语义化评判**：热量 <1200"偏低"、≤1800"适中"、>1800"偏高"；碳水 <100"偏低"、≤200"适中"、>200"偏高"。

返回结构含 `meal_count`（餐次）、`avg_gi`（当日平均 GI）、`records`（精简列表给前端展示）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| sum 遇到 None 报错 | `record.calories or 0`；模型字段可空，累加前必须兜底 |
| 日期边界不对 | 区间必须是 [start, end)，用 __lt 而不是 __lte 取结束端，避免第二天数据混入 |

@@point ⑥ 平均 GI：升糖负荷的当日画像
@@need 要解决什么
营养只算热量不够，"升糖快不快"要用 GI 衡量——一天的平均 GI 怎么算？

@@idea 核心思路
```python
gi_vals = [record.gi_value for record in records if record.gi_value is not None]
avg_gi = statistics.mean(gi_vals) if gi_vals else 0.0
```
两个细节：
- **过滤 None**：不是所有食物都录了 GI 值，先滤掉再求均值，避免 `statistics.mean` 炸；
- **空列表兜底**：当天没记录或全无 GI 时返回 0.0，不抛 `StatisticsError`。

这个"过滤空值 + 空列表兜底"的小模式会反复出现——health_analyzer、diet_advisor、RAG 里都是同一招，形成肌肉记忆。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| mean([]) 抛 StatisticsError | 必须 `if gi_vals else 0.0` 兜底 |
| 把 None 混进列表 | 先 `if x is not None` 过滤；上一步的 or 0 在这里不适用（0 会拉低均值） |

@@point ⑦ consume 的存在性检查模式复用
@@need 要解决什么
三个模块的"创建前验患者"与血糖一模一样——这个模式有什么统一写法？

@@idea 核心思路
三个模块创建接口的开头都是同一行：
```python
await Patient.get_or_none(id=data.patient_id)
```
含义拆解：**存在性副作用检查**——查一次患者，只为确认"这个 patient_id 真实存在"。返回值不用于业务，纯粹防止外键悬空（创建出无主记录）。

工程进阶（讲义未做，值得知道）：正式项目应改成显式判空抛 404：
```python
patient = await Patient.get_or_none(id=data.patient_id)
if not patient:
    raise HTTPException(status_code=404, detail="患者不存在")
```
这样语义更明确、前端能看到友好错误而非静默成功。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| get_or_none 结果丢弃但没判空 | 悬空外键照样入库；至少要在关键场景升级为 404 |
| 想"无副作用"查库存 | 存在性检查本身会读库，高频接口注意性能；量级小时忽略 |

@@point ⑧ 三大模块与 AI 引擎的衔接预告
@@need 要解决什么
记录模块存的数据，后面哪些 AI 功能会用到？

@@idea 核心思路
提前画好数据流向，学后面的章节就不迷路：

| 数据 | 消费方 | 用途 |
|---|---|---|
| DietRecord | diet_advisor.recommend_meal | 结合最近血糖推荐食谱 |
| DietRecord | get_daily_nutrition | 营养汇总 → 前端今日饮食卡片 |
| BloodSugar | health_analyzer | 周报/月报/仪表盘/对话上下文 |
| Medication/Exercise | 对话工作流 | 患者档案展示（`load_patient_context`） |

**对话智能体的"患者上下文"就是这几张表拼出来的**——姓名/年龄/BMI + 近7天血糖概况，全是记录模块的存量数据。所以第七章写扎实，第十二章的 AI 对话才有话可说。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 觉得记录模块没用直接跳过 | 后面 AI 对话/RAG 都依赖这些数据；数据质量决定 AI 质量 |
| 录入数据不规范（meal_type 乱填） | 餐次枚举（早餐/午餐/晚餐/加餐）要固定取值，diet_advisor 才分得清 |
