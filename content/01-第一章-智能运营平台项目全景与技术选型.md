@@h1 第一章　项目全景与技术选型
@@sub 阶段 9 · 智能运营平台　|　实践　|　难度 ★★★

@@why 这一章在解决什么问题
做内容运营的人每天卡在四件事上：**选题靠刷**（刷热搜刷到眼花）、**文案靠憋**（憋一小时写出三百字）、**配图靠找**（图库翻半天还怕侵权）、**发布靠手动**（一个个平台复制粘贴）。一天最多两三篇，还容易撞选题、踩敏感词、被限流。

本章要做的「智能运营平台」，把这四道手工关卡收进一条流水线：**你输入一个主题或一句灵感，AI 帮你出选题、写文案、配图，最后点一下发布**——原本一下午的活压到十几分钟。

学完这一章，你手里会有一张**完整系统蓝图**：这个平台由哪几个模块组成、为什么这么选技术、数据在哪些表之间流动。后面十一章做的都是这张图上的一块拼图。

@@prep 开始之前
纯看蓝图的章，不用装环境；阶段 8 的 LangChain / LangGraph 建议先过一遍。

@@goal 学到这儿就够了
能说出四个模块、八张表在系统里的位置和为什么这么选技术，这一章就算过了。

@@map 这一章在整个知识库里的位置
上一章（阶段 8 · AI Agent 智能体与多模态应用）：你已经会用 LangChain / LangGraph 搭 Agent、接工具、管记忆
**本章** ← 你在这里：看清「AI 运营平台」的全景——四个模块、八张表、一条 Agent 流水线
下一章：数据库设计与初始化——八张表怎么建、字典表怎么填、连接怎么配
再往后：后端骨架（uv + FastAPI）→ 数据模型与 Aerich 迁移 → JWT 登录 → 前端联调 → 接 Coze → 选题落库 → 文案创作 → 配图与发布
阶段终点：跑通「输入主题 → 选题 → 文案 → 配图 → 发布记录」的整条闭环

@@point ① 真实痛点：内容运营的四道手工关卡
@@need 要解决什么
先弄清楚「为什么要做这个系统」，后面的技术选型才有着落——技术是给痛点买单的。

@@idea 核心思路
一个运营同学每天的动作，拆开看是四段，每段都在耗人：

| 关卡 | 手工做法 | 痛在哪 |
|---|---|---|
| 选题 | 刷热搜、翻同行、凭感觉 | 不知道哪个题能火；同一个题反复做，自己先腻了 |
| 文案 | 对着空白文档憋 | 风格不稳定；一不小心写了敏感词，被限流还不知道为什么 |
| 配图 | 图库翻找 + 自己拼 | 找图慢、风格不统一、版权有风险 |
| 发布 | 各平台手动上传 | 重复劳动；发完就忘，数据也不回看 |

这四段的共同点：**每段都要人从头做一遍，下一篇文章还是从零开始**。系统的价值不是"替人写一篇文章"，而是**把经验沉淀下来**——上一次的选题、文案、图、发布数据都留在库里，下一次可以复用、可以对比、可以迭代。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 一上来就想"全自动无人值守" | 发布这一步涉及账号风控，全自动风险高；先做**半自动**（AI 出稿 + 人工确认 + 一键发布），跑顺了再谈提效 |
| 把系统做成"AI 聊天框" | 聊天框不解决问题；运营要的是**结构化的产物**（选题列表、文案、配图、发布记录），所以核心是表结构和流程，不是对话 |

@@point ② 四大功能模块拆解
@@need 要解决什么
一个完整产品不可能一把梭，先把「这个系统到底有哪些能力」列成清单，后面开发才有验收依据。

@@idea 核心思路
按用户的使用顺序，平台分四块：

| 模块 | 具体能力 | 落在哪一层 |
|---|---|---|
| 热搜灵感与选题 | 实时热搜检索与推荐、已有主题复用、行业热点采集、标题灵感生成 | Coze 选题智能体 + 后端 API 落库 |
| 文案编导 | 一键生成平台风格文案、控制情绪/语气/长度、敏感词与限流词检测、历史文案复用 | 大模型调用（DashScope）+ 敏感词规则 |
| 图片生成与排版 | 多风格配图一键生成、封面图与内文图批量产出、尺寸与用途区分 | 文生图模型 + 阿里云 OSS 存储 |
| 发布与历史管理 | 一键发布、多账号管理、发布记录追踪、历史笔记复用、素材库 | 后端发布记录表 + 前端管理页 |

记住这张表的作用：**它是需求地图**。后面每章做完一件事，你都能回到这里打勾——不会写着写着忘了"我在做哪个功能"。

@@point ③ 技术选型：十四项，分四类看
@@need 要解决什么
技术栈要在动手前一次定清楚，避免中途换框架导致返工。

@@idea 核心思路
把十四项按"干什么用"分四类，比平铺更能记住：

| 类别 | 技术 | 用途 |
|---|---|---|
| 语言与工程 | Windows 11、Cursor / VSCode、Python 3.12、uv | 开发环境与依赖管理（uv 比 pip + venv 快得多） |
| Web 与数据 | FastAPI、Uvicorn、Tortoise-ORM、MySQL 8 + Navicat、Aerich | 接口、服务、异步 ORM、数据库、表结构迁移 |
| 平台能力 | Coze（Agent 编排）、DashScope（模型调用）、阿里云 OSS + python-multipart（文件上传） | 把这几个"重能力"外包出去，不自己造 |
| 安全与调试 | JWT（登录鉴权）、Postman（接口调试） | 认证与联调 |

一句话概括选型逻辑：**自己写业务和表结构，把大模型能力外包给平台**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 依赖装了但 `uv run` 找不到 | 依赖必须用 `uv add` 写进 `pyproject.toml`；`pip install` 装的东西不在 uv 的环境里 |
| Python 版本不对，异步驱动装不上 | 3.12 是硬要求；`uv python pin 3.12` 固定解释器版本 |

@@point ④ 架构：三层结构 + 一个"外挂大脑"
@@need 要解决什么
动手前心里得有一张静态结构图：知道哪段代码摆在哪一层，出问题去哪找。

@@idea 核心思路
```
┌─────────────────────────────────────────────┐
│  Vue 3 前端：选题页 / 文案页 / 配图页 / 发布页 │
└───────────────────┬─────────────────────────┘
                    │ HTTP /api（JWT 鉴权）
┌───────────────────▼─────────────────────────┐
│  FastAPI 应用层（routers）                    │
│  users / sections / titles / images / publish│
└──────┬──────────────────────────┬───────────┘
       │ Tortoise-ORM              │ 业务编排
┌──────▼─────────┐   ┌────────────▼──────────┐
│  MySQL 8       │   │  Agent 层（Coze 平台）  │
│  8 张业务表     │   │  选题智能体 / 工作流    │
└────────────────┘   │  文案生成 / 配图生成    │
                     └────────────┬──────────┘
                                  │ DashScope 模型
                                  │ + OSS 存图
```

关键认知：**Agent 不在你的 Python 代码里，而在 Coze 平台上**。后端负责"收请求、存结果、管权限"，生成类的活交给平台，通过 API 调。这样模型换代、提示词调整都不用改后端。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 前端直接调 Coze，绕过自己的后端 | 会丢掉鉴权、丢掉落库、留不住历史记录；**所有调用必须经后端中转** |
| 把 OSS 的 AccessKey 写进前端 | 等于把存储桶公开；密钥只放后端 `.env`，前端只拿后端返回的临时 URL |

@@point ⑤ 为什么接 Coze，而不是自己写一套 Agent
@@need 要解决什么
你上一阶段已经会写 LangGraph 了，那为什么这里要用平台？想清楚这个问题，才知道这套架构的取舍。

@@idea 核心思路
两条路的对比：

| 维度 | 自己写（LangGraph） | 用 Coze 平台 |
|---|---|---|
| 上手速度 | 慢，要处理重试、超时、上下文 | 快，可视化拖节点，提示词即改即用 |
| 迭代成本 | 改逻辑要改代码、重启服务 | 平台上改完直接生效，不碰代码 |
| 可观测 | 要自己接日志与追踪 | 平台自带运行记录与调试面板 |
| 灵活性 | 高，任何逻辑都能写 | 受平台能力约束（自定义代码块有限） |
| 适合谁 | 需要深度定制、要嵌入自有系统 | 运营同学自己就能调提示词、换模型 |

本阶段的定位是**"业务系统 + 外挂 Agent"**：业务流程（落库、权限、发布记录）自己写，创作能力（选题、文案、配图）交给平台。所以选 Coze。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| Agent 返回的 JSON 解析失败 | 平台输出是"自然语言 + 可能夹代码块"，后端要**容错解析**（去围栏、找第一个 `{` 到最后一个 `}`），并在失败时返回可读错误 |
| 同一请求调两次，结果完全不同 | 生成类接口本来就不幂等；需要落库的操作用**任务 ID 去重**，别让前端重试把库写脏 |

@@point ⑥ 数据流：一篇内容在八张表之间怎么走
@@need 要解决什么
这套系统的骨架不是代码，是**表之间的一条链**。先把链路想清楚，第二章建表才不会乱。

@@idea 核心思路
一条内容从灵感到发布，经过五步、落到八张表：

```
① 用户提主题        → t_sections（选题组：原始主题 + 分类）
② AI 出标题列表     → t_titles（标题、排序、状态）
③ 生成正文          → t_titles.content + status
④ 生成/上传配图     → t_title_images（正文图 / 封面图 / 缩略图）
⑤ 发布并记录        → t_publish_records + t_publish_images
                      t_style / t_models 是字典表，全程被引用
```

两个要点：

1. **选题与标题是两层**：`t_sections` 是"一个方向"，下面挂多个 `t_titles`。"AI 减肥"是 section，"我靠这三个动作瘦了十斤"是 title。
2. **发布是独立的一层**：同一篇内容可以发多个平台，所以发布数据不能塞进 `t_titles`，要单开 `t_publish_records`（一个 title 对多条记录）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把图片 URL 直接塞进 `t_titles` | 一篇内容有封面 + 多张正文图，塞一个字段必然不够；图片单独成表，用 `title_id` 关联 |
| 发布状态和内容状态混成一个字段 | 内容状态（未生成/已生成/已发布/已废弃）与发布状态（待发/发布中/成功/失败）是**两件事**，混用后无法区分"发布失败"和"还没写" |

@@need 要解决什么
先盘点"哪些我会、哪些我不会"，把精力花在增量上，别把时间浪费在重复劳动里。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 跳过第 2 章的建表，直接写接口 | 没有表就没有模型，接口只能返回假数据；顺序不能换 |
| Aerich 和手写 SQL 混着用 | 一旦用 Aerich 管版本，表结构变更就走迁移命令（`aerich migrate` / `upgrade`），不要两边都改 |

@@point ⑧ 交付物与验收标准
@@need 要解决什么
知道"做完长什么样、怎么算跑通"，避免闷头写完发现方向偏了。

@@idea 核心思路
阶段结束时应能演示这条链路：

| 验收项 | 标准 |
|---|---|
| 后端服务 | `uv run uvicorn main:app --reload` 起来，`/docs` 能看到接口文档 |
| 登录鉴权 | 未登录取不到数据，登录后拿到 token 才能调业务接口 |
| 数据库 | MySQL 里 8 张表齐全，字典表（风格、模型）有种子数据 |
| 选题链路 | 输入主题 → 返回标题列表 → 选中的标题写进库，刷新还在 |
| 文案与配图 | 能对指定标题生成文案与配图，图片存在 OSS 上、库里只存 URL |
| 发布记录 | 发布后能在列表页看到记录与状态，能按状态筛选 |
| 前端 | 选题、文案、配图、发布四个页面可交互，不再是 Postman 里点 |

难度系数：★★★（★★ 来自要串起"平台 + 后端 + 存储"三处外部依赖，★ 来自它的业务链条比纯 CRUD 长）。
