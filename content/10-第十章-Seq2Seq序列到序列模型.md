@@h1 第十章　Seq2Seq序列到序列模型
@@sub 阶段 22 · 自然语言处理与Transformer架构　|　Seq2Seq　|　难度 ★★★

@@why 这一章在解决什么问题
前面的模型都是"一条文本进，一个标签/一串标签出"。机器翻译、文本摘要、对话生成要的是**变长的输入变成另一个变长的输出**："我爱你" → "I love you"。这一章引入 **Seq2Seq（序列到序列）模型**：一个 RNN 把输入"读"成状态（编码器），另一个 RNN 把状态"写"成输出（解码器），并介绍开始符、停止符这些让它能"知道何时说完整句"的机制。

@@map 上一章→本章→下一章
上一章把 RNN 家族学完了。**本章第一次组装"两个网络"：编码器把源序列压成状态向量，解码器据此逐词吐目标序列**——这是机器翻译/摘要/对话的通用骨架。下一章解决它的致命弱点：编码器把整句压成一个向量信息不够，需要"注意力机制"按需翻看原文。

@@point ① 序列转换任务：什么输入对应什么输出
@@need 要解决什么
机器翻译这种"输入输出都是文本且长度不同"的任务，和之前的分类任务本质区别在哪？

@@idea 核心思路
**序列转换（Sequence-to-Sequence）** 任务的模型输入和输出都是**长度不定的序列**：

- 机器翻译：中文句 → 英文句。
- 文本摘要：长文 → 短摘要。
- 对话生成：上文 → 回复。
- 文本改写：原句 → 改写句。

与分类任务的区别：分类输出是**固定集合里的一个标签**；序列转换输出是**可变长度的 token 序列**，长度都可能和输入不同。为了处理这种"变长到变长"，需要"先读懂全部 → 再从头说出"的两段式结构——这就是编码器-解码器。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把翻译当"查词典替换" | 真正的翻译要理解语义后组织目标语言，词对齐只是副产品，不是字典映射 |
| 以为输入输出必须等长 | Seq2Seq 正是为"不等长"设计：编码与解码长度彼此独立 |

@@point ② 编码器-解码器：读进来，写出去
@@need 要解决什么
一个网络怎么能"既读又写"？为什么要拆成两半？

@@idea 核心思路
**编码器（Encoder）** 与 **解码器（Decoder）** 是两套独立的 RNN：

```
中文:  "我 爱 你" 
        ↓
编码器: [RNN] → 状态向量 z（浓缩全句语义）
        ↓
解码器: [RNN] → "I" → "love" → "you"
        ↓
英文:  "I love you"
```

- **编码器**：从头到尾读源句子，最后时刻的隐藏状态作为**状态向量 z**，承担"把整个源句语义装进去"的职责。
- **解码器**：以 z 作为初始状态，**逐词生成**目标序列，每步输出一个词并把它作为下一步输入（自回归）。

拆成两个的收益：**分工清晰**——编码器只管"理解"，解码器只管"表达"，两者可以分别选型（如编码器双向、解码器单向）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 只用一个 RNN 完成两段 | 编码方向与生成方向信息流不同（读全句 vs 逐词产出），两套权重才能各司其职 |
| 以为 z 只取最后时刻 | 早期做法取最后 h；LSTM 场景常把最后 h 与 c 一起传；注意力时代改为"全时刻都传"（下章） |

@@point ③ 状态向量：整句语义的"压缩包"
@@need 要解决什么
"我爱你"三个字，编码器把它变成了什么？信息怎么装进去？

@@idea 核心思路
状态向量 z 就是**编码器最后时刻的隐藏状态**（LSTM 时往往是 h_T 和 c_T 一起传）：

- z 是一个固定长度向量（如 256 维），**不管源句多长，最后都压成这一个向量**。
- 它的物理含义：源句中每个词的信息，经过一层层 RNN 传递，被逐级融合进 z。

```python
import torch.nn as nn

encoder = nn.LSTM(embed_dim, hidden_dim, batch_first=True)
# encoder 读完整句
_, (h_T, c_T) = encoder(src_embeddings)
# h_T: [1, batch, hidden]  —— 这就是状态向量 z
```

解码器初始化时把 z 传进去：`decoder_rnn(h0=z)`。就这样，"我爱你"的语义被压缩进 256 个数字，交给解码器"解码"成英文。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为 z 保留全部原文 | 压缩必然有损——长句信息塞不进固定向量，这正是上章说的"压缩失真"，也是注意力的动机 |
| LSTM 时只传 h 不传 c | 解码器要同时有 h0 和 c0 才完整，忘传 c 会导致解码状态失真 |

@@point ④ 开始符与停止符：让解码器知道"从哪开始、到哪结束"
@@need 要解决什么
解码器逐词生成时，第一个词从哪来？什么时候停下来？目标序列长度不一怎么办？

@@idea 核心思路
引入两个特殊标记：

- **开始符 `<sos>`（start of sequence）**：作为解码器第一步的输入，告诉它"现在开始输出"。
- **停止符 `<eos>`（end of sequence）**：解码器一旦输出 `<eos>`，生成立即终止——目标多长由模型自己决定。

训练目标序列也加标记（`<sos> I love you <eos>`），模型学到"该收尾时说 `<eos>`"。这样解码器的生成循环就是：

```
输入: <sos> → 预测 "I" → 预测 "love" → 预测 "you" → 预测 <eos> → 停止
```

开始/停止符在词表里各占一个 token 位，与正常词一起训练，是 Seq2Seq 系列的"标准配件"。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 忘了在词表里加 sos/eos | 它们是特殊 token，词表构建时要显式加入，否则无法参与映射与损失 |
| 生成循环没有停止条件 | 不设 eos 停止或 max_len 上限，模型会无限生成直至内存爆掉 |

@@point ⑤ 解码器训练：Teacher Forcing
@@need 要解决什么
训练解码器时，每一步的输入该用"真实的目标词"还是"模型自己刚生成的词"？

@@idea 核心思路
训练采用 **Teacher Forcing（教师强制）**：每步输入用**真实目标词**（来自训练数据），而不是模型上一步的猜测：

```
step1: 输入 <sos>     → 目标 I
step2: 输入 I(真实)   → 目标 love
step3: 输入 love(真实)→ 目标 you
step4: 输入 you(真实) → 目标 <eos>
```

好处：**训练快、稳定**——模型不会因为一个错词导致后续一串都错（误差累积推迟）。代价：训练/推理不一致（推理时只能喂自己的预测），属于"暴露偏差"问题，可用 schedule sampling（部分用预测词）缓解。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 训练用 Teacher Forcing、推理也强行喂真实词 | 推理时没有参考答案，必须改成"上一步输出作为下一步输入"，否则无法上线 |
| 完全不用 Teacher Forcing | 训练初期全自回归会让误差传播爆炸、难收敛；渐进混合才是稳妥做法 |

@@point ⑥ 解码器推理：自回归一步一步生成
@@need 要解决什么
模型训练完，翻译一句新句子时，解码器怎么一步步"说"出来？

@@idea 核心思路
推理（翻译）阶段：

```python
def translate(model, src_tokens, max_len=50):
    # 1. 编码器读入源句，得到状态 z
    z = model.encode(src_tokens)
    # 2. 解码器自回归生成
    step_input = SOS_ID           # 从开始符起步
    result = []
    for _ in range(max_len):
        logits, z = model.decode_step(step_input, z)
        word = logits.argmax(dim=-1)   # 或按概率采样
        if word == EOS_ID:             # 遇到停止符
            break
        result.append(word)
        step_input = word              # 上一步输出 → 下一步输入
    return result
```

要点：**每步只取最大概率词（或采一个词）喂回模型**；直到输出 `<eos>` 或达到 max_len 上限才停。推理不能并行（必须逐词），这也是解码端比编码端慢的天然原因。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| max_len 不设上限 | 卡死风险：异常时永远不输出 eos，设 50-100 兜底 |
| 用 argmax 生成太平庸 | 翻译常用 beam search（保留 Top-k 候选）提升质量；贪心 argmax 只是 baseline |

@@point ⑦ 瓶颈：一个向量装不下整个句子
@@need 要解决什么
翻译长句子时，Seq2Seq 效果会大幅下降——问题出在哪？

@@idea 核心思路
核心瓶颈：**编码器必须把整个源句压进**一个**固定长度**的状态向量 z，再由解码器"凭空"还原。句子越长：

- 信息塞不进 → 开头内容被"挤掉"（长句前面的词记不住）。
- 解码器每一步都得从同一个 z 里"捞信息"，**缺少"按需查找"能力**——译到第 3 个词时，不知道该重点看原文的哪个词。

数学上这就是**信息瓶颈**与**对齐缺失**。缓解尝试：编码器双向、增大 hidden 维度——但都是治标。**注意力机制（下一章）让解码器每一步"回头翻看源句每个词的相关程度"，彻底打破单向量瓶颈**，这是 2015 年后 NMT 最大的进步。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 看到长句翻译变差就加层数 | 堆层不解决"压缩瓶颈"本质，换注意力/transformers 才是正道 |
| 以为 Seq2Seq 已过时不用学 | 它的"编码-解码""sos/eos""teacher forcing"概念全部延续到 Transformer/LSTM 翻译模型，是必学底盘 |

@@point ⑧ Seq2Seq 的工程实现要点
@@need 要解决什么
自己动手写一个最小翻译系统，工程上有哪些必须注意的点？

@@idea 核心思路
最小可跑的实现清单：

1. **词表**：源/目标各建一份，分别预留 `pad/sos/eos/unk`。
2. **编码器**：双向 LSTM 读源句，取最后 h（/c）作为 z。
3. **解码器**:单向 LSTM，初始状态=z，每步输入=上一步输出。
4. **损失**：目标序列右移一位、pad 位置 `ignore_index` 忽略。
5. **Teacher Forcing**：训练时喂真实词，推理时喂预测词。
6. **推理**：argmax 或 beam search + max_len 兜底。
7. **批次**：源/目标分别 pad 到本批最长并附 `lengths` 排序处理。

```python
criterion = nn.CrossEntropyLoss(ignore_index=PAD_ID)
```

这套骨架与 Hugging Face 翻译示例、fairseq 等框架的核心逻辑一致——理解了它，读任何 NMT/生成框架源码都不再陌生。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 一个词表通吃源和目标 | 源/目标语言词表应分开建，训练目标按各自词表索引 |
| 忘记 pad ignore | 不忽略 pad 会造成大量无意义损失，loss 虚高 |
| batch 内长短不一不排序 | RNN 需要按长度降序排 + pack_padded_sequence，否则效率低甚至报错 |

@@summary
本章建立 Seq2Seq 的完整认知：

| 概念 | 要点 |
|---|---|
| 序列转换 | 变长输入 → 变长输出（翻译/摘要/对话） |
| 编码器 | 读全句 → 状态向量 z |
| 解码器 | 以 z 为初始状态逐词生成 |
| 状态向量 | 整句语义压缩包（信息瓶颈所在） |
| sos/eos | 决定从哪开始、何时停止 |
| Teacher Forcing | 训练喂真实词，推理喂自预测 |
| 推理 | 自回归 + eos 停止 + max_len 兜底 |
| 瓶颈 | 单向量装不下长句 → 注意力登场 |

一句话记住本章：**Seq2Seq = 编码器"读"成状态向量 + 解码器"写"成目标序列，靠 sos/eos 控制起止、Teacher Forcing 稳定训练；但它把整句压进一个向量，长句必失真——下一章的注意力机制，就是给解码器配一副"按需翻原文"的眼镜。**
