@@why 这一章在解决什么问题
前面的章节搭好了"平台的身体"（数据库、后端、前端），现在要给平台装"大脑"。本章解决：**在扣子（Coze）平台上打造"热搜选题智能体"**——让一个 Bot 拿到用户的运营主题后，结合全网热点，一次性产出 5 大板块 × 10 个共 50 个爆款标题，而且输出格式严格可解析（否则后端没法落库）。

为什么单独一章讲"平台上的 Bot 搭建"？因为 AI 应用的核心早已不在模型本身，而在**提示词工程 + 工具编排 + 输出约束**。这章的知识，比多背几个 API 都值钱。

@@point ① Coze 平台是什么、解决什么
@@need 要解决什么
"调用大模型"不等于"调一个 API"——真实业务需要人设、联网、多步编排。Coze 把这三件事产品化。

@@idea 核心思路
扣子（Coze）是字节的 AI Bot 开发平台，核心能力三件套：
1. **Bot（智能体）**：带人设的系统提示词 + 温度等参数 + 可选模型，一个 Bot 就是一套"会说话的专家"。
2. **插件/工具**：内置搜索、图片、知识库、工作流等能力——**热搜数据就来自搜索类插件**。
3. **工作流（Workflow）**：把"开始 → 插件 → 大模型 → 结束"编排成可视化流水线（下一章细讲）。

对我们项目的意义：**选题 Bot 需要实时热搜，但大模型本身不联网**——答案在"给 Bot 配一个搜索插件"，让 Bot 先搜热点再写标题。这是平台能否"结合全网热点"的技术根基。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| Bot 生成的标题没有时效性、不蹭热点 | 没配搜索插件，模型只凭训练知识"编热点"；人设里写"请搜索"也不可控 |
| 插件搜索失败时 Bot 报错不回答 | 插件异常要有人设兜底（"搜索失败则说明你无法获取最新热点"），避免整轮对话报废 |

@@point ② 创建选题 Bot：从空 Bot 到"选题专家"
@@need 要解决什么
Bot 怎么建？人设怎么写才能产出"爆款标题"而不是"AI 味文案"？

@@idea 核心思路
在扣子平台新建 Bot 的完整流程：
1. 登录扣子 → 创建 Bot（命名如"热搜选题机器人"）；
2. **添加插件**：给 Bot 挂上联网搜索类插件（如"头条搜索"/"必应搜索"），让它可以查实时热点；
3. **编写人设与回复逻辑**（下一点）；
4. **调试**：右侧对话区直接测试，逐轮校准输出；
5. **发布**：作为 API/应用发布，拿到 Bot ID（BOT_ID_TOPIC）。

⚠️ 关键认知：**Bot 发布后才可被 API 调用**。开发期在对话区测试只是"Bot 内部行为"，后端要能调，必须走到"发布"一步。

@@point ③ 人设 Prompt：五板块 × 10 标题的输出契约
@@need 要解决什么
AI 输出是松散的，选题模块却要"严格 5 板块、每板块 10 条、每条≤20字、JSON 格式"。人设 Prompt 就是这份契约的制定现场。

@@idea 核心思路
选题 Bot 的人设核心（精炼版）：
```
你是一位拥有10年互联网运营经验、擅长打造爆款内容的热搜分析专家。
你的任务：根据用户给的运营主题，结合当下全网热搜，输出 5 大板块各 10 个爆款标题。
5 大板块：
①每日行业热点：今天的行业大事件
②热点榜单：当天全网热榜话题
③专业知识榜单：主题相关专业干货
④人设共鸣：引发目标用户情感共鸣
⑤灵感广场：与主题相关的创意脑暴

格式规范（严格遵守）：
1. 标题字数限制在20字以内；
2. 用 "一、二、三、四、五"输出板块，每个板块输出 10 个标题；
3. 只输出标题，不要输出解释；
4. 生成结束后，将 5 个板块标题内容保存为 JSON 格式输出，供系统直接解析入库。
```

设计要点：**"格式规范"不是装饰，是系统接口**——后端按"一、二、三、四、五"分段 + JSON 提取，任何一条不遵守就会解析失败。所以人设里宁可重复强调，不可省略。这就是"提示词即接口"。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 统计只有 43 个标题（缺板块/缺条数） | 人设没强调"必须满 5×10、缺一不可"；生成后要对数量做校验，不足自动重发 |
| 标题超 20 字 | 人设只说"限制"不够，要写"20字以内，越短越好"并给示例 |
| JSON 混在正文里、被解释文字包裹 | 人设要写死"JSON 单独一段，其余位置不得出现任何其他文字" |

@@point ④ JSON 输出规范：给后端一个"好解析"的结果
@@need 要解决什么
50 个标题最终要进数据库，格式必须机器可读。JSON 的结构怎么定，直接影响后端 create.py 的解析代码。

@@idea 核心思路
约定 JSON 结构（与后端 create.py 的解析一一对应）：
```json
{
  "每日行业热点": [
    {"title": "xxx", "sort_order": 1},
    ...
  ],
  "热点榜单": [...] ,
  "专业知识榜单": [...],
  "人设共鸣": [...],
  "灵感广场": [...]
}
```
后端配合逻辑（下一章展开）：
- 遍历 `data.items()`：板块名 → Section；板块内列表 → 每条 Title（含 sort_order 1-10）。
- **板块名就是 t_sections.name**，顺序即板块顺序。

这等于把"数据库表结构"提前映射进了"提示词输出契约"——**AI 输出从一开始就是为落库设计的**。

@@point ⑤ 温度与模型参数：稳定性 vs 创造性
@@need 要解决什么
同一个 Bot 为什么有时生成很好、有时重复？温度参数在调什么？

@@idea 核心思路
- **温度（temperature）低（0.3 以下）**：输出更确定、更守格式，适合"严格 JSON/数量固定"的选题任务。
- **温度高（0.8+）**：更有创造性但格式容易放飞，适合文案创意，不适合结构解析。

选题 Bot 建议**低温度**——宁可标题稍"平"，也要保证 5×10 齐全、JSON 可解析。格式违约的成本远高于创意损失。文案 Bot 可以适当调高。这是"按任务性质配参数"而非统一默认值。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 温度太高，标题板块混排、数量不满 | 降温度 + 人设强约束双管齐下；先降温度再改提示词，一次只动一个变量 |
| 连续两次生成高度雷同 | 低温度正常现象；需要多样性可加"每个板块主题词不同"约束而不是盲目升温度 |

@@point ⑥ 调试方法论：人设怎么"三次迭代"
@@need 要解决什么
提示词不可能一次写好。有一个可复用的调试循环：测 → 归类失败 → 针对性改 → 复测。

@@idea 核心思路
调试循环（示例）：
1. **第一轮**：输入"新能源汽车" —— 输出只有 40 个标题、JSON 格式对 → 改人设补"每板块必须 10 个，共 50 个"。
2. **第二轮**：输出 50 个但一个标题 35 字 → 补"≤20 字，数字、地名类长词也要拆分"。
3. **第三轮**：格式数量都对，但"人设共鸣"板块像知识清单 → 给该板块补示例："从车主焦虑、家庭出行、通勤场景切入"。

迭代原则：**一次只改一个约束，用对话记录对比**——否则永远不知道是哪句 Prompt 起作用了。Bot 的人设是"代码"，要版本管理。

@@point ⑦ 发布与获取 Bot ID：后端调用的门票
@@need 要解决什么
Bot 做好只是"内部可用"，后端要通过 API 调它，必须发布并拿到 Bot ID。

@@idea 核心思路
发布路径：Bot 编辑页 → 发布 → 选择渠道（本场景走 **API/应用** 方式或复制的 BOT_ID）→ 发布成功后得到该 Bot 的 ID（形如 76xxxxxxxxxxxx72）。

回到项目的 .env：
```
BOT_ID_TOPIC=你的选题机器人ID       # 即将在 coze_agent.py 里使用的
COZE_TOKEN=你的扣子个人令牌（pat_开头）
USER_ID=ops_demo
```
- BOT_ID_TOPIC 就是本章建的"热搜选题机器人"。
- COZE_TOKEN 是开发者令牌（个人访问令牌，pat_ 开头），**等同账号权限，绝不入库**。
- USER_ID 是业务自定的用户标识（如 ops_demo），传给 Coze 用于会话追踪。

⚠️ 拿到 Bot ID 后验证是否可调：在"扣子 API"或调试面板里用测试请求跑一次，能返回 50 标题 JSON 才算"发布成功可调用"。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| API 调用报"Bot not found" | Bot 未发布或 BOT_ID 抄错；发布要在每次改完人设后重新发布 |
| 用他人的 COZE_TOKEN | token 与账号绑定，菜单/工具权限不同；用自己的 token + 自己的 Bot |
| 改完人设不重新发布，调用还是旧行为 | 发布动作才让改动生效，编辑页保存 ≠ 发布 |

@@point ⑧ 双子 Bot 架构：选题与文案各管一摊
@@need 要解决什么
平台有两类 AI 任务：选题（结构化 50 标题）与文案（220-420 字自由正文）。它们人设、输出规范、温度要求都不同——塞进同一个 Bot 会互相干扰。

@@idea 核心思路
项目拆成两个独立 Bot（.env 里两个 ID 一一对应）：
| Bot | 人设 | 输出 | 温度倾向 | 配置键 |
|---|---|---|---|---|
| 热搜选题机器人 | 热点分析专家 | 5 板块×10 标题 + JSON | 低（保格式） | BOT_ID_TOPIC |
| 小红书文案机器人 | 爆款笔记作者 | 220-420 字正文 | 中高（保创意） | BOT_ID_CONTENT |

**互不干扰的价值**：改选题人设不影响文案输出；选题要严格 JSON、文案要自然流畅，两套约束不会打架；Cozepy 调用时按接口各取各的 BOT_ID，代码上只差一个参数。

教训：不要"一个 Bot 打天下"。AI 任务按"输出形态"拆分 Bot，是提示词工程里的模块化思维——**单个 Bot 的人设越聚焦，输出越稳定**。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 把两个任务塞进一个 Bot，格式时好时坏 | 双人设互相稀释；拆两个 Bot 各管一摊 |
| BOT_ID_TOPIC 与 CONTENT 填反 | 选题接口返回文案、文案接口返回标题；核对 .env 两个 ID 的用途标签 |
| 只发布了其中一个 | 另一个接口 404/Bot not found；两个 Bot 都要各自发布 |


@@summary 这一章你学到了什么
- Coze 三件套：Bot 人设、插件（联网搜索）、工作流编排
- 选题 Bot 使命：输入运营主题 → 结合实时热搜 → 5 板块 × 10 = 50 个标题
- 人设 Prompt = 代码：板块结构、条数、字数、JSON 输出全是硬约束
- 输出契约先行：JSON 的 key 直接映射数据库表字段，AI 输出生来就能落库
- 温度策略：选题低温度保格式，文案高温度保创意，按任务调参
- 调试循环：一轮一变量，记录对比，人设要版本管理
- 发布与 BOT_ID：发布后才可 API 调用，除人设改动记得重发
- 双子 Bot 架构：选题与文案各管一摊，人设聚焦输出才稳定
