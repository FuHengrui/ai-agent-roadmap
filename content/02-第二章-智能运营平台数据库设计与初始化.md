@@h1 第二章　数据库设计与初始化
@@sub 阶段 9 · 智能运营平台　|　实践　|　难度 ★★★

@@why 这一章在解决什么问题
后端的一切都长在表上：接口是"读写表"，权限是"谁能读哪张表"，发布记录是"往表里追加一行"。表设计错了，后面每章都要跟着改——所以**动手写代码之前，先把表定死**。

本章要拿到的东西很具体：八张表的字段清单、它们之间的关联、建库脚本、以及让程序连上库的那一段配置。做完这章，你的 MySQL 里就该有一个能跑业务的空壳库，后面的接口全往里灌数据。

@@prep 开始之前
要先装 MySQL 8 并用 Navicat 连上；第一章那张八张表的蓝图先看过，字段才看得懂。

@@goal 学到这儿就够了
能说清八张表各存什么、外键怎么连，并把建库 SQL 跑进 MySQL，这一章就算过了。

@@map 这一章在整个知识库里的位置
上一章：项目全景与技术选型——四模块、三层架构、八张表的数据链
**本章** ← 你在这里：把八张表真正建出来，并让程序连上
下一章：后端工程搭建——uv 初始化项目、FastAPI 骨架、把本章的配置接进去
再往后：模型与 Aerich 迁移（用代码定义表）→ 启动测试 → JWT → 前端联调

一个顺序上的提醒：本章是**先建表再写模型**，第 4 章才用 Aerich 把表结构搬到代码里管理。别把两件事混在一起。

@@point ① 为什么先定表：数据模型是后端的骨架
@@need 要解决什么
搞清楚"表"在整套系统里的地位，才愿意花时间把字段想清楚。

@@idea 核心思路
一条判断标准：**如果一个东西需要"以后还能查回来"，它就该进表**。

- 用户输入的原始主题 → 要能复用，进表（`t_sections`）
- AI 生成的一堆标题 → 要能挑、能排序、能看状态，进表（`t_titles`）
- 生成的正文 → 要能编辑、能再发，进表（`t_titles.content`）
- 配图 → 要能区分封面/正文、能排序，进表（`t_title_images`）
- 发布结果 → 要能复盘数据，进表（`t_publish_records`）

反过来，**提示词、模型参数、临时对话**这些不需要长期留存的东西，就别进表——它们属于配置和运行时。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 表建得太"扁平"，一个字段塞一坨 JSON | 后面按状态筛选、统计数量时全都得全表扫描再解析；**常用筛选项必须是独立字段**（`status`、`platform`） |

@@point ② 八张表的关系：一条主链 + 两张字典
@@need 要解决什么
先把表之间的关系画出来，再一张张看字段，否则容易"建完八张表还是不知道谁连谁"。

@@idea 核心思路
```
t_users ──┬─< t_sections ──< t_titles ──┬─< t_title_images
          │                              └─< t_publish_records ──< t_publish_images
          └─< t_title_images                       （引用 t_title_images）

字典表：t_style（配图风格）、t_models（可用模型）
```

读法：**`1 : N` 用"一的一方主键 → 多的一方外键"**。

| 关系 | 含义 |
|---|---|
| users → sections | 一个用户建多个选题组 |
| users → title_images | 一个用户可以上传/生成多张图（图片表另存 `user_id`） |
| users → publish_records | 发布记录记下是谁发的（可为空） |
| sections → titles | 一个选题组下挂多个标题 |
| titles → title_images | 一个标题有多张图（封面 + 正文） |
| titles → publish_records | 一篇内容可发多个平台，产生多条记录 |
| publish_records → publish_images | 一次发布实际用了哪些图、什么顺序 |
| style / models | 被配图与文案生成引用，本身不挂在主链上 |

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 发布记录挂在 section 上 | 发布的对象是"某一篇内容"（title），不是"某个方向"；挂错层会导致一条记录对应不清 |

@@point ③ 三张主表：users / sections / titles
@@need 要解决什么
主链上的前三个节点，决定了"谁、做什么方向、具体哪篇"，字段必须一次想全。

@@idea 核心思路
| 表 | 关键字段 | 设计要点 |
|---|---|---|
| `t_users` | id、username、password、name、department、created_at | `username` 全局唯一；`password` 存**哈希**不存明文；`department` 可空（个人用户没有部门） |
| `t_sections` | id、user_id、source_name、name、created_at、updated_at | `source_name` 是用户输入的原始主题，`name` 是整理后的选题名——两者分开存，才能回溯"当初那句话是什么" |
| `t_titles` | id、section_id、title、sort_order、content、status、view_count、like_count、created_at、updated_at | `sort_order` 越小越靠前（AI 推荐的排前面）；`content` 可空（还没生成正文）；`status` 用数字码（见第 ⑥ 点） |

三个细节值得单独说：

1. **`source_name` 与 `name` 分开**：用户输入"AI 减肥"，你整理成"AI+健康"分类，但半年后你想知道当初他到底打了什么字——原始输入必须留。
2. **`sort_order` 而不是"按创建时间倒序"**：AI 出的标题有推荐顺序，这个顺序必须能被人工调整，所以要有独立字段。
3. **统计字段（view_count / like_count）先留着**：现在没用，但要发数据的时候就有了；空着不影响。

@@point ④ 图片表与风格表：t_title_images 与 t_style
@@need 要解决什么
图片是这套系统里最"重"的资源（体积大、种类多、要排序），单独建表才撑得住。

@@idea 核心思路
`t_title_images` 的字段设计围绕三件事：**属于谁、干什么用、多大**。

| 字段 | 作用 |
|---|---|
| user_id / title_id | 归属：谁传的、挂在哪篇内容下 |
| image_url | 只存 URL（图片本体在 OSS 上，见第 12 章） |
| image_type | 0=正文图、1=封面图、2=缩略图 |
| sort_order | 同一篇内容里多张图的顺序（越小越靠前） |
| file_size / width / height | 上传时顺手记下，前端做占位图、做比例校验都要用 |
| created_at | 只记创建时间（图片不改，不需要 updated_at） |

`t_style` 是字典表，只有四个字段：`name`（展示名，如"扁平化海报"）、`fengge`（给模型看的完整提示词）、`create_time`。**注意 `fengge` 这一列**：它就是提示词模板，运营改风格 = 改这一列，不用改代码。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把图片二进制存进 MySQL | 数据库会被撑爆、备份变慢；**图存 OSS，库里只存 URL** |
| `width`/`height` 用字符串存 | 后续算比例、做裁剪都得转类型；直接 `int` |

@@point ⑤ 三张辅助表：t_models / t_publish_records / t_publish_images
@@need 要解决什么
这一组解决"用哪个模型生成"和"发到哪里、效果如何"两个问题。

@@idea 核心思路
| 表 | 关键字段 | 用途 |
|---|---|---|
| `t_models` | id、name、type、version、description、status、created_at、updated_at | 模型字典：`type` 区分 text / image；`status` 1=可用、0=停用。切换模型 = 改 `status`，不改代码 |
| `t_publish_records` | id、user_id、title_id、platform、publish_status、publish_time、content、view_count、like_count、comment_count、share_count、created_at、updated_at | 一次发布一行；`platform` 1=小红书 / 2=抖音 / 3=快手 / 4=公众号；数据回填后就更新统计列 |
| `t_publish_images` | id、publish_id、image_id、image_type、sort_order、created_at | 记录"这次发布实际用了哪几张图、什么顺序"——因为发布时可能删掉某张图，不能只看 `t_title_images` |

为什么要多一张 `t_publish_images`？因为**素材是"可变的"，发布结果是"已定格的"**。素材表里删了一张图，历史发布记录不能跟着变，所以发布那一刻用哪几张图，要单独存一份快照。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 发布统计列跟 `t_titles` 里的统计列搞混 | `t_titles.view_count` 是"内容维度的汇总"，`t_publish_records.view_count` 是"这一条平台发布的数据"；同一条内容发三个平台、三条记录，彼此数据不能互相覆盖 |

@@point ⑥ 枚举值约定：数字码要配一张对照表
@@need 要解决什么
状态、平台、图片类型都用数字存，省空间也快，但**没人记得住 2 是成功还是失败**。

@@idea 核心思路
八张表里一共三组枚举，先把对照关系定下来：

| 字段 | 取值 |
|---|---|
| `t_titles.status` | 0=未生成、1=已生成、2=已发布、3=已废弃 |
| `t_publish_records.platform` | 1=小红书、2=抖音、3=快手、4=微信公众号 |
| `t_publish_records.publish_status` | 0=待发布、1=发布中、2=成功、3=失败、4=已删除 |
| `t_title_images.image_type` | 0=正文图、1=封面图、2=缩略图 |
| `t_publish_images.image_type` | 1=正文图、2=封面图、3=详情图（注意与上面**不是同一套编号**） |

两个工程习惯：

1. **对照表写进代码注释 / 前端常量**，别让前后端各自猜。
2. **枚举值只增不改**：已经上线的值不要改含义，否则历史数据会集体"变义"。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 两张图片表的 `image_type` 编号不一致，直接复用同一套常量 | `t_title_images` 里 0=正文、`t_publish_images` 里 1=正文——**复用会错位**，必须分开定义 |
| 用 `status=0` 同时表示"未生成"和"已废弃" | 状态混淆后无法区分"还没做"和"不做了"；废弃要单独一个值 |

@@point ⑦ 建库与初始化：utf8mb4、库名一致、种子数据
@@need 要解决什么
把表真正落地到一个能连的库里，并且保证后面三处配置不打架。

@@idea 核心思路
四步：

1. **装 MySQL 8**（Windows 上可用集成环境一键起服务），用 Navicat 连上。
2. **建库**，字符集必须 `utf8mb4`：

```sql
CREATE DATABASE ai_operation
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
```

3. **导入建表脚本**（八张表 + 索引）。导入后核对表数量：`SHOW TABLES;` 应该是 8 行。
4. **填种子数据**：`t_style` 里放两三种风格、`t_models` 里放一个文本模型 + 一个图像模型、`t_users` 里放一个管理员。**种子数据不是可选项**——第 11、12 章配图要读 `t_style`，空了就选不出风格；`t_models` 目前是预留，后文还没用到。

库名建议统一用 `ai_operation`：**建库、`.env`、`config.py` 三处必须是同一个字符串**，这是最常见的"明明启动了却连不上库"的原因。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 表建好了，插中文/emoji 报错 | 字符集用了 `utf8`（三字节老字符集）；建库建表都要 `utf8mb4` |
| 本地能连、换台机器就连不上 | `.env` 里 `DB_HOST` 写了 `127.0.0.1` 但 MySQL 只监听了 localhost，或端口不是 3306；先在 Navicat 里验证同一套参数能连 |

@@point ⑧ 连接配置：.env + config.py + Tortoise
@@need 要解决什么
让"凭据"和"代码"分开，同时把连接串拼成 Tortoise 认识的格式。

@@idea 核心思路
第一步，凭据进 `.env`（**不进仓库**）：

```
DB_HOST=localhost
DB_PORT=3306
DB_USER=root
DB_PASSWORD=你的密码
DB_NAME=ai_operation
```

第二步，`app/config.py` 读取并拼连接串：

```python
import os
from urllib.parse import quote_plus
from dotenv import load_dotenv

load_dotenv()
DB_PASSWORD = os.getenv("DB_PASSWORD", "")
_encoded = quote_plus(DB_PASSWORD)          # 密码含 @ # : 必须先编码
DATABASE_URL = (
    f"mysql://{os.getenv('DB_USER')}:{_encoded}"
    f"@{os.getenv('DB_HOST')}:{os.getenv('DB_PORT')}/{os.getenv('DB_NAME')}"
    f"?charset=utf8mb4"
)

TORTOISE_ORM = {
    "connections": {"default": DATABASE_URL},
    "apps": {"models": {"models": ["app.models", "aerich.models"],
                        "default_connection": "default"}},
}
```

三个关键点：

- **`quote_plus` 不能省**：密码里有 `@`、`#`、`:` 时，不编码会把 URL 截断，报的错还特别像"密码错误"。
- **`aerich.models` 必须先写进列表**：第 4 章用 Aerich 迁移时它要建自己的版本表，现在不写，到时候还得回头改配置。
- **`charset=utf8mb4`**：和建库时的字符集对齐，否则中文在某些连接下变成问号。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 报 `Access denied`，但 Navicat 能连 | 九成是密码里的特殊字符没 URL 编码；用 `quote_plus` 包一层 |
| `.env` 提交进了 git | 凭据泄露；`.env` 必须在 `.gitignore` 里，仓库里只留 `.env.example` |

@@summary
这一章你实际拿到的是**三样东西**：

| 拿到了什么 | 为什么要紧 |
|---|---|
| **八张表 + 一条主链** | 「选题组 → 标题 → 图片 → 发布」的落点定了，后面接口照着表写就有 |
| **三组枚举对照表** | 前后端不会再各猜一套数字；尤其是两张图片表的编号不同这点 |
| **能连上的库 + 配置骨架** | `.env`、`config.py`、`TORTOISE_ORM` 三件套齐了，第 3 章直接拿来用 |
