@@why 这一章在解决什么问题
上一章配置好了数据库连接，但代码里还没有"患者""血糖记录"这样的对象——ORM 层就是**把 7 张 SQL 表翻译成 Python 类**，让你能写 `Patient.get(id=1)` 而不是手拼 `SELECT * FROM patients`。本章解决三件事：**一是掌握 Tortoise 模型的标准写法**（字段、外键、Meta），**二是把这套系统里最有教学价值的计算属性讲透**（BMI、血糖状态、GI 等级、血糖变化），**三是理解 models/__init__.py 统一导出的机制**。

关键认知：**模型是"静态的，像表结构"，计算属性（@property）是"动态的，不落库"**——属性在读取时即时计算，比如 blood_sugar 的 status 是"算"出来的（value 小于 3.9 是低血糖），不占数据库列。这是 AI 引擎能直接拿到"语义化状态"（而不是一串数字）的关键。

@@point ① Tortoise 模型标准写法：字段类型对照
@@need 要解决什么
SQL 类型要正确翻译成 Tortoise 字段类型，这是模型层的核心语法。

@@idea 核心思路
一个标准模型长这样（以患者表为例）：

```python
from tortoise import fields, models

class Patient(models.Model):
    """患者基础信息表"""
    id = fields.IntField(pk=True, description="主键ID")
    name = fields.CharField(max_length=50, description="患者姓名")
    age = fields.IntField(description="年龄")
    gender = fields.CharField(max_length=10, default="未知", description="性别")
    diabetes_type = fields.CharField(max_length=20, default="2型", description="糖尿病类型")
    diagnosis_date = fields.DateField(null=True, description="确诊日期")
    height = fields.FloatField(null=True, description="身高(cm)")
    weight = fields.FloatField(null=True, description="体重(kg)")
    phone = fields.CharField(max_length=20, null=True, description="联系电话")
    emergency_contact = fields.CharField(max_length=50, null=True, description="紧急联系人")
    emergency_phone = fields.CharField(max_length=20, null=True, description="紧急联系人电话")
    medical_history = fields.TextField(null=True, description="既往病史")
    allergies = fields.TextField(null=True, description="过敏史")
    created_at = fields.DatetimeField(auto_now_add=True, description="创建时间")
    updated_at = fields.DatetimeField(auto_now=True, description="更新时间")

    class Meta:
        table = "patients"
```

SQL ↔ Tortoise 对照（本项目用到的完整清单）：

| SQL 类型 | Tortoise 字段 | 说明 |
|---|---|---|
| INT 主键 | fields.IntField(pk=True) | 自增主键 |
| VARCHAR(n) | fields.CharField(max_length=n) | 必须显式给 max_length |
| TEXT | fields.TextField(null=True) | 长文本，可空 |
| FLOAT | fields.FloatField(null=True) | 浮点数（血糖、身高体重） |
| DATE | fields.DateField(null=True) | 日期（确诊日） |
| DATETIME | fields.DatetimeField(auto_now_add=True) | 创建时间自动填充 |
| 更新时间 | fields.DatetimeField(auto_now=True) | 每次 save 自动更新 |
| BOOLEAN | fields.BooleanField(default=True) | 布尔（is_active） |

规则：**可空字段必须 null=True**，否则 Tortoise 建表时默认 NOT NULL，插入缺值报错。`description=` 虽不影响数据库，但在 FastAPI 自动文档里很有用。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| CharField 忘写 max_length 报错 | Tortoise 的 CharField 强校验 max_length，不给就抛异常 |
| 表名没写 Meta.table | 默认表名 = 模型名（如 patient），与 SQL 的 patients 不一致，查询报表不存在 |
| 加了字段没加 null=True | 表里没默认值时，插入缺该字段的记录直接 NOT NULL 报错 |

@@point ② 外键：一对多关系建模
@@need 要解决什么
一个患者有无数条血糖记录、饮食记录，模型上怎么表达"属于谁"？

@@idea 核心思路
Tortoise 用 `fields.ForeignKeyField` 声明外键：

```python
class BloodSugar(models.Model):
    """血糖记录模型"""
    id = fields.IntField(pk=True, description="主键ID")
    # 关联患者表，一对多关系
    patient = fields.ForeignKeyField(
        'models.Patient',
        related_name='blood_sugars',
        description="关联患者"
    )
    value = fields.FloatField(description="血糖值(mmol/L)")
    measure_type = fields.CharField(max_length=20, description="测量类型")
    measured_at = fields.DatetimeField(description="测量时间")
    note = fields.TextField(null=True, description="备注")
    created_at = fields.DatetimeField(auto_now_add=True, description="录入时间")

    class Meta:
        table = "blood_sugar"
```

关键参数：
- `'models.Patient'`：**字符串引用**而不是直接传类——避免循环导入（Patient 和 BloodSugar 互相引用时）；
- `related_name='blood_sugars'`：反向查询名——`await patient.blood_sugars.all()` 就能拿到这个患者的全部血糖记录；
- 数据库层面自动生成 `patient_id` 列（`patient` 字段的 `_id` 后缀）。

外键在查询时非常强大：`BloodSugar.filter(patient_id=1)` 或 `patient.blood_sugars.all()` 两种写法等价。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 循环导入报 ImportError | 外键用字符串 `'models.Patient'` 而非类对象；模型间互相 import 容易炸 |
| 查询报"patient_id 不存在" | 外键字段在 ORM 里叫 `patient`，数据库列才叫 `patient_id`；Filter 时 `patient_id=` 和 `patient=` 都能用，但要认清语义 |

@@point ③ BMI 计算属性：@property 不落库
@@need 要解决什么
患者的 BMI 和 BMI 分类（偏瘦/正常/肥胖）不存数据库，但要随时算出来给 AI 和前端用——怎么办？

@@idea 核心思路
用 Python 的 `@property` 装饰器，读取时即时计算：

```python
@property
def bmi(self) -> float:
    """计算BMI：体重(kg)/身高(m)的平方"""
    if self.weight and self.height:
        return round(self.weight / (self.height / 100) ** 2, 1)
    return 0.0

@property
def bmi_category(self) -> str:
    """计算BMI分类"""
    bmi_val = self.bmi
    if bmi_val < 18.5:
        return "偏瘦"
    if bmi_val < 24:
        return "正常"
    return "肥胖"
```

设计要点：
- **不占数据库列**：BMI 是"身高、体重的函数"，存两个原始值即可，BMI 随体重变化自动更新——存冗余值反而容易脏；
- **防护空值**：height/weight 可能为 null，先判空再计算，否则报 TypeError；
- **返回值语义化**：bmi 是数字，bmi_category 是"偏瘦/正常/肥胖"——AI 提示词可以直接拼"患者 BMI 24.3（正常）"。

这是本阶段模型层的核心模式：**原始数据落库，派生状态用 property 现算**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 没判空直接算 BMI 报错 | `if self.weight and self.height:` 先判空；否则 None 参与运算 |
| 想存 BMI 算出结果 | 别存！原始值变了 BMI 就过期；property 永远与原始数据一致 |

@@point ④ 血糖状态：status 的阈值逻辑
@@need 要解决什么
血糖值 5.6 和 9.2 在界面上要显示"正常""偏高"，AI 判断也要用语义。阈值规则放哪？

@@idea 核心思路
放在模型层的 status property 里，阈值一目了然：

```python
@property
def status(self) -> str:
    """根据血糖值判断健康状态"""
    if self.value < 3.9:
        return "低血糖"
    if self.value <= 7.0:
        return "正常"
    if self.value <= 10.0:
        return "偏高"
    return "高血糖"
```

阈值表（本项目的核心医学常量）：

| 区间 | 状态 |
|---|---|
| value < 3.9 | 低血糖 |
| 3.9 ≤ value ≤ 7.0 | 正常 |
| 7.0 < value ≤ 10.0 | 偏高 |
| value > 10.0 | 高血糖 |

注意**边界归属**：3.9 属于正常（`< 3.9` 才是低），7.0 属于正常（`<= 7.0`），10.0 属于偏高（`<= 10.0`）——区间是**左闭右闭**衔接的，写错一个等号就会把 7.0 误判成偏高。这与 .env 里的 BG_LOW_THRESHOLD / BG_HIGH_THRESHOLD（3.9 / 10.0）遥相呼应。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 边界值误判（7.0 显示偏高） | 检查区间是否"左闭右闭"：`<= 7.0` 是正常，`< 3.9` 才是低 |
| 阈值写死两处不一样 | .env 与代码里必须同一口径；本项目模型用常量，HealthAnalyzer 用 .env，注意别漂移 |

@@point ⑤ 饮食 GI 等级：gi_level 三级判定
@@need 要解决什么
AI 推荐食谱时要判断食物"升糖快不快"。GI 值怎么映射成"低/中/高"三档？

@@idea 核心思路
与血糖状态同一模式，安装在 DietRecord 上：

```python
@property
def gi_level(self) -> str:
    """判断食物的GI等级"""
    if self.gi_value is None:
        return "未知"
    if self.gi_value <= 55:
        return "低GI"
    if self.gi_value <= 70:
        return "中GI"
    return "高GI"
```

| 区间 | 等级 | 含义 |
|---|---|---|
| gi ≤ 55 | 低GI | 升糖慢，推荐（燕麦 55、苹果 36、豆腐 15） |
| 55 < gi ≤ 70 | 中GI | 适量（糙米 56、全麦面包 51） |
| gi > 70 | 高GI | 升糖快，避免（白米饭 83、西瓜 72） |

特例处理：`gi_value is None` 返回"未知"而不是直接走进判断——很多食物没录 GI 值，直接参与比较会报错。掌握这个"先判 None 再判阈值"的防御模式，后面多处复用。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| gi_value 为 None 时比较报错 | 先 `if self.gi_value is None: return "未知"` 兜底 |
| 把 55 归进中GI | 低GI 是 `<= 55`，等于 55 算低（燕麦 GI 55 是低GI 代表） |

@@point ⑥ 运动血糖变化：bs_change 差值属性
@@need 要解决什么
"运动有没有效"要用数据说话——运动前后血糖差了多少？

@@idea 核心思路
Exercise 模型上的计算属性，把运动前后的血糖差值算出来：

```python
@property
def bs_change(self) -> float:
    """计算血糖变化"""
    if self.blood_sugar_before and self.blood_sugar_after:
        return round(self.blood_sugar_after - self.blood_sugar_before, 1)
    return 0.0
```

用途链：
- 前端运动记录列表显示"−1.3"，一眼看出这运动降糖效果好；
- AI 引擎可解读"血糖下降较多，注意预防低血糖"；
- 无前后值（如忘了测）返回 0.0，展示层不报错。

写法要点：**round(..., 1) 保留一位小数**保持展示清爽；前后有人没填时返回 0.0 兜底。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 只有 after 没 before，差值错 | 判空时用 `and`，两者都有才算；否则返回 0.0 |
| 直接相减没 round | 浮点误差（0.1+0.2=0.30000000000000004）；round 保留 1 位 |

@@point ⑦ models/__init__.py：统一导出机制
@@need 要解决什么
models 目录下 7 个文件，Tortoise 和外部 import 怎么知道"有哪些模型"？

@@idea 核心思路
`app/models/__init__.py` 承担"模型注册中心"职责：

```python
"""
模型包初始化：统一导出所有模型，便于 Tortoise ORM 发现并建立映射
"""
from app.models.patient import Patient
from app.models.blood_sugar import BloodSugar
from app.models.diet_record import DietRecord
from app.models.medication import Medication
from app.models.exercise import Exercise
from app.models.health_report import HealthReport
from app.models.chat_history import ChatHistory

# 供外部导入和 Tortoise 配置引用
__all__ = [
    "Patient", "BloodSugar", "DietRecord",
    "Medication", "Exercise", "HealthReport", "ChatHistory",
]
```

机制解析：
- TORTOISE_ORM 里配了 `"models": ["app.models"]`——Tortoise 扫描 app/models 包，**只认 __init__.py 里导出的类**；
- 外部代码 `from app.models import BloodSugar` 一行拿到全部模型；
- 新增模块时**必须手动加进 __init__.py**，否则 Tortoise 或路由都找不到它。

这是极易踩坑的点：写好了 medication.py 但忘在 __init__.py 导出，启动不报错、查询却报"模型不存在"。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 新模型查不到"模型不存在" | 忘了在 models/__init__.py 里导出该类；新增模块必改 __init__ |
| 重复 import 导致循环依赖 | __init__.py 里统一导入，各模块内部用字符串外键 `'models.XX'` 避免循环 |

@@point ⑧ 模型层设计原则：本项目 vs 阶段9 对比
@@need 要解决什么
很多同学在阶段 9 已经写过模型（Aerich 迁移），本项目的模型写法与之有何异同？要不要迁移？

@@idea 核心思路
| 维度 | 阶段 9（智能运营平台） | 本项目（糖尿病助手） |
|---|---|---|
| ORM | Tortoise-ORM | Tortoise-ORM（复用） |
| 表管理 | Aerich 迁移 | 直接建库 SQL（无 Aerich） |
| 外键 | IntField + 手动关联 | ForeignKeyField + related_name（更"ORM化"） |
| 派生属性 | 少 | **多且关键**：bmi/bmi_category/status/gi_level/bs_change |
| 核心增量 | JWT 认证 | **计算属性 + AI 引擎读语义状态** |

本项目值得特别注意的设计取向：**把"业务判定"（血糖状态、GI 等级、BMI 分类）放到模型 property，让 AI 引擎直接消费语义字符串**——而不是让 AI 引擎自己拿数字再算一遍。这样判定逻辑只有一份，可单测、可复用。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 阶段9 的代码直接拷过来跑 | 表名/字段不同（t_ 前缀在本项目没有）；模型必须与本项目 SQL 对齐 |
| 把判定逻辑散在路由里 | 多处写"if value<3.9"迟早漂移；统一收进模型 property |
