@@sub 阶段 18 · 云原生开发环境与 DevOps 工具链　|　容器化　|　难度 ★★★★

@@why 这一章在解决什么问题
一个 Web 应用要连 MySQL：你写了 `database url=192.168.0.5:3306`。结果 MySQL 容器重启后 IP 变了，**程序还得改代码重发**。
容器网络要解决的正是这种事：① 容器之间怎么互相访问；② 怎么不写死 IP、用名字访问；③ 网桥、网络模式到底是什么。
学完本章，你能让 Tomcat 容器直接按名字找到 MySQL 容器，IP 再怎么变都不影响——**这就是容器网络的"联动"价值**。

@@point ① 为什么需要网络：每个容器都有自己的 IP
@@need 要解决什么
容器是隔离的，你凭直觉也知道"它俩不能互相看见"。但实际跑起来你会发现它们**有 IP、能互相 ping**——这套机制从哪来的？

@@idea 核心思路
只要装了 Docker，宿主机上就会自动多出一块虚拟网卡 **docker0**（一个内置的网桥）。
每启动一个容器：
1. Docker 从 docker0 的网段里挑一个 IP 分给容器（容器拥有专属 IP）；
2. 容器和宿主机、容器和容器之间通过 docker0 互通。

```
宿主机
┌──────────────────────────────────────┐
│  docker0（虚拟网桥，也是默认网关）      │
│   IP 172.17.0.1                      │
│   ├───── veth ── 容器A  172.17.0.2   │
│   └───── veth ── 容器B  172.17.0.3   │
└──────────────────────────────────────┘
```

**容器**删除重建**后 IP 才可能变；`docker restart` 沿用原网络、IP 不变（Docker 按顺序分配）**——这就是网络的第一课：IP 不可靠，可靠的是"名字"。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 在容器里 ping 不通外网 | 默认 bridge 模式可出外网；检查宿主机防火墙/网络，或容器被设成了 none 模式 |
| 容器 IP 和宿主机 IP 看着像"两个世界" | 172.17.x.x 是 Docker 内部地址，只在宿主机内可达；对外访问还得 -p 端口映射 |
| 以为每个容器 IP 固定 | 默认每次创建容器 IP 都可能变；要固定用自定义网络（本章最后） |

@@point ② veth pair：一对"连体"虚拟网卡
@@need 要解决什么
docker0 和容器之间靠什么连？为什么容器一删、对应"网线"也没了？——认识底层元件 veth pair。

@@idea 核心思路
**veth pair（虚拟以太网对）是一对成对出现的虚拟网卡**，像一根网线：一头插容器、一头插 docker0。
- 一头发送的数据，另一头**原封不动收到**，天生一对；
- 正因为成对出现，Docker 才能把千千万万个网络设备"桥"在一起；
- **容器删除时，它那半"网线"自动消失**——隔离做到"连网线都不留"。

```
容器A          宿主机                容器B
eth0 ◄──veth──► docker0 ◄──veth──► eth0
```

这也是"虚拟转发效率高"的原因：**所有接口都是虚拟的**，不走真实网卡硬件，纯内存转发。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 宿主机 ip addr 看到一堆 veth?xxx 看不懂 | 每对 veth 对应一个正在运行的容器，?xxx 是随机名；容器停了这截"网线"也会消失 |
| 以为容器之间直接连、不经过 docker0 | 默认 bridge 模式下流量都要过 docker0 这个"交换机"中转，不是直连 |

@@point ③ 用名字访问：--link 容器联动
@@need 要解决什么
回到开头那个场景：Web 容器里写的数据库地址是 IP，MySQL IP 一变程序就瞎了。
能不能**按容器名访问**，IP 随便变都不影响？

@@idea 核心思路
```cmd
# --link 源容器名字:别名 —— 在"本容器"里给"对方容器"起个别名
docker run --name tomcat01 --link tomcat02   # 注意：tomcat02 必须先 docker run 起来，--link 不能链一个不存在的容器 -d -P docker.io/tomee
#                  └本容器   └ 源容器：以后 tomcat01 里访问 tomcat02 就找到它
```

- 语法：`--link <name or id>:alias`，name/id 是**源容器**（被链接方），alias 是你在本容器里称呼它的别名；
- 效果：tomcat01 里可以直接 `ping tomcat02`（或用别名），**不用关心它的 IP**；
- 本质：Docker 把源容器的 IP 登记进本容器的 `/etc/hosts`，等于做了一次"IP → 名字"的动态翻译。

应用场景：数据库容器 IP 变了 → web 容器里写的 `mysql:3306` 依然有效，程序不用改。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 反向 --link 不通 | link 是**单向**的：A 链 B，A 能访问 B；B 里并不能访问 A。要对等就两边各链一次 |
| mysql:3306 连不上 | link 只解决"名字→IP"，不解决"源容器应用没就绪"；先确认源容器起来了（docker logs） |
| 新版本 Docker 里 link 变弱了 | link 是旧时代的做法，官方推荐用**自定义网络**（本章最后），理念更干净：同一网络内默认按名字互通 |

@@point ④ 四种网络模式：先看全景图
@@need 要解决什么
Docker 网络不是只有"默认"，有 host / container / none / bridge 四种。它们解决"容器网络要跟谁共享"的问题，先建立全局概念。

@@idea 核心思路
| 模式 | 参数 | 一句话 | 隔离度 |
|---|---|---|---|
| **host** | `--net=host` | 和宿主机共用网络，没有独立 IP | 最开放 |
| **container** | `--net=container:名字` | 和另一个容器共用网络 | 相对 |
| **none** | `--net=none` | 只有回环，啥网络都不配 | 最封闭 |
| **bridge** | `--net=bridge` | 默认，docker0 网桥分配 IP | 标准隔离 |

一句话记忆：**host = 跟宿主机一体；container = 跟别人一体；none = 谁也不理；bridge = 各发一张身份证（IP）但都在一个小区（docker0）。**
默认不写 `--net` 就是 bridge。

@@point ⑤ host 模式：住进宿主机"家里"
@@need 要解决什么
有些容器想直接用宿主机的 IP 和端口（比如性能敏感、要多容器抢同一端口），不想做端口映射。那就和宿主机合体。

@@idea 核心思路
```cmd
docker run -d --net=host --name web docker.io/tomee
```

- 容器**不获得独立 IP、不虚拟网卡**，而是和宿主机**共享网络空间（Network Namespace）**；
- 容器里监听的端口 = 宿主机端口，**不用 -p 映射**：容器 Tomcat 听 8080，宿主机 8080 直接就能访问；
- 代价：**没有隔离**，端口冲突风险大——宿主机已有服务占 8080 就起不来。

**适用场景**：性能敏感、端口要直接暴露、调试临时用。
**不适用**：要跑一堆同类容器（端口不够分）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| --net=host 后 -p 映射没效果 | host 模式下容器直接用宿主机网络，-p 映射无效（也没必要）；直接访问宿主机端口即可 |
| host 模式多个容器抢同一端口 | host 容器间不隔离端口；要并存就把端口错开，或用 bridge + 映射 |

@@point ⑥ container 模式：和指定容器"共用一根天线"
@@need 要解决什么
两个容器关系密切（比如日志收集器贴着应用容器跑），希望它们的网络视角完全一致。container 模式让他们"共享网络身份"。

@@idea 核心思路
```cmd
# 新容器和已有容器 myapp 共享网络空间
docker run -d --net=container:myapp --name logger busybox sleep 3600
```

- 新容器**不自己配 IP**，而是完全复用 myapp 的网络（IP、端口、网卡都一样）；
- 两者对外的网络身份**像一个容器**，端口共用；
- 常用于 sidecar 模式（监控/日志容器贴着主应用跑，靠 127.0.0.1 就能访问主应用）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 被共享的容器停了，这个容器也跟着断网 | 共享的对象没了，网络自然没得共享；确保被共享的容器常驻 |
| 两个容器端口都想用同一个 | container 模式端口共用，再监听同端口会冲突；职责分明的 sidecar 场景才合适 |

@@point ⑦ none 模式：与世隔绝
@@need 要解决什么
有些容器就是"算数、离线任务"，根本不需要联网，还想保证绝对安全——连 Docker 分发 IP 的多余动作都不要。这就是 none。

@@idea 核心思路
```cmd
docker run -d --net=none --name offline busybox sleep 3600
```

- 容器有独立的网络空间，但**不做任何网络设置**：不分配 veth、不接网桥、不配 IP；
- 只有回环接口（127.0.0.1），**无法联网**；
- 好处：**最安全**（封闭网络，想被攻击都没入口）；坏处：当然也出不去。

适合：纯计算、批处理、一次性脚本这类"不需要网络"的任务。
面试考点：**四种模式里最安全的是 none，不是 host。**

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| none 容器里 yum/apt 装东西失败 | 正常，none 模式无外网；要装软件换 bridge 模式 |
| 用 none 的容器还想被外部访问 | 不可能；none 专为"不需要网络"设计，需要网络时别选它 |

@@point ⑧ bridge 模式（默认）：小区里的"一户一地址"
@@need 要解决什么
绝大多数容器走的就是默认的 bridge。搞懂它，才算真正理解 Docker 默认网络的工作方式。

@@idea 核心思路
```cmd
# 默认模式，写不写 --net=bridge 都一样
docker run -d --name web docker.io/tomee
```

- Docker 在宿主机虚拟出**网桥 docker0**；
- 每个 bridge 容器从网桥网段分得一个 IP，**docker0 是它的默认网关**；
- 容器进出外网都经 docker0 转发；对外暴露靠 `-p` 端口映射（第 16 章）；
- 容器间默认可以互通（同网段），但**靠 IP 互访不可靠**——下一部分的自定义网络升级它。

**bridge 模式的画像**：隔离合理、自动分配地址、映射端口对外——普通应用的首选。

@@point ⑨ 自定义网络：docker network 命令族
@@need 要解决什么
默认 bridge 有你想要但给不了的：**同一网络内的容器之间用名字直接互访**（可替代 link）、**自定义网段**（避开冲突）。自己建一个网络就有了。

@@idea 核心思路
```cmd
# 网络管理命令全家桶
docker network --help            # 查看所有网络子命令
docker network ls                # 列出网络
docker network create ...        # 创建网络（重点）
docker network inspect 网络名     # 看网络详情/成员
docker network connect 网络名 容器名   # 把已有容器接入网络
docker network disconnect 网络名 容器名 # 从网络断开
docker network rm 网络名          # 删除网络（要先清空成员）
docker network prune             # 清理未使用的网络
```

创建自定义网络，指定网段和网关：

```cmd
# --driver bridge 指定用桥接模式
# --subnet 192.168.0.0/16 指定网段（/16 表示前 16 位固定，后面 192.168.*.* 可用）
# --gateway 192.168.0.1 指定网关
docker network create --driver bridge \
  --subnet 192.168.0.0/16 \
  --gateway 192.168.0.1 \
  mynet
```

**网段常识**（考试爱考）：`/24` 表示前 24 位固定，可用 192.168.200.1~254 这样的几百个地址；`/16` 前 16 位固定，可用范围大得多（192.168.0.1~192.168.255.254）。**掩码位数越小，地址池越大。**

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 自定义网络网段和现有网络撞车 | 容器网络会混乱；创建前先看下现有网段，选个不冲突的 |
| rm 网络报 "network has active endpoints" | 网络里还挂着容器；先 disconnect 或删容器再 rm |
| --subnet 写成 192.168.0.0.16 报格式错 | 网段的写法是"IP/掩码位数"，中间是斜杠，不是小数点；这是很常见的笔误写法，正确是 192.168.0.0/16 |

@@point ⑩ 把容器放进自定义网络：按名字互访
@@need 要解决什么
自定义网络建好了，怎么用？关键福利是：**同一网络里的容器，可以直接用容器名互相 ping，IP 再变也不怕。**

@@idea 核心思路
```cmd
# 方式一：创建容器时直接指定网络
docker run -d -P --name tomcat01 --net mynet docker.io/tomee
docker run -d -P --name tomcat02 --net mynet docker.io/tomee

# 方式二：已存在的容器，动态接入网络
docker network connect mynet 某个已存在容器

# 验证：在 tomcat01 里按名字 ping tomcat02（无需 IP）
docker exec -it tomcat01 ping tomcat02

# 查看网络里有哪些成员
docker network inspect mynet
```

对比 `--link`：link 是"手动在 hosts 里登记对方"，自定义网络是"整个网络内置名字解析"——
**同一网络内所有容器默认支持按名字互访，双向、可动态增减**，这才是官方推荐的正路子。
实战配方：把 Web 容器和 MySQL 容器放进同一个自定义网络，Web 里写 `mysql:3306` 就行了。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 两个容器在不同网络里 ping 名字不通 | 名字解析只在**同一自定义网络内**有效；跨网络要把容器 connect 到同一个网络 |
| connect 之后还是 ping 不通 | connect 只是"加网"，容器里要确认真的多了一块网卡（ip addr）；名字解析生效偶尔有延迟，稍等重试 |
| ping 通名字但应用连不上 | 通了网络还要通应用：源容器监听端口、服务真正就绪（如 MySQL 初始化完成） |

@@summary 本章小结
| 问题 | 答案 |
|---|---|
| 容器有 IP 吗 | 有，docker0 网桥自动分配；但 IP 不固定，不可靠 |
| 容器怎么和网桥连 | veth pair 成对虚拟网卡，容器删了半边网线自动消失 |
| IP 会变怎么办 | --link 按名字访问，或直接用自定义网络 |
| 四种网络模式 | host（共用宿主机）/ container（共用别的容器）/ none（封闭）/ bridge（默认） |
| 哪个最安全 | none（与世隔绝）；host 最开放 |
| 怎么自己建网 | docker network create --driver bridge --subnet 网段 --gateway 网关 名字 |
| 自定义网络的最大好处 | 同网络内容器按名字互访，双向、动态 |
| 网段怎么理解 | /24 比 /16 地址池小；掩码位数越小可用地址越多 |

一句话总结：**容器网络 = docker0 网桥 + veth 网线 + 四种模式选边界；IP 会变所以用名字——旧招 --link 单向登记，正路建自定义网络让同网容器按名互访。**
