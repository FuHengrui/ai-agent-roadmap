@@point ① MCP：AI 世界的"USB-C"接口标准
@@need 要解决什么
"MCP"三个字母听着像又一个黑话。到底什么是 Model Context Protocol？为什么说它是"无限工具"的关键？

@@idea 核心思路
**MCP = Model Context Protocol（模型上下文协议）**——一个开放标准，定义了"AI 应用如何连接外部数据源和工具"的通用方式。

用"USB-C"类比最好懂：

| 项 | USB-C | MCP |
|---|---|---|
| 解决的问题 | 一个口接所有外设（充电/数据/显示） | 一个协议接所有外部工具（搜索/数据库/API） |
| 好处 | 不用每换设备换一种线 | 不用给每个服务写专属集成 |
| 生态 | 任何厂商都能造 USB-C 设备 | 任何服务商都能提供 MCP 服务器 |

对 Hermes：**内置工具是"出厂自带外设"，MCP 是"即插即用的外设接口"**——只要对方提供 MCP 服务器，不用改框架代码就能新增能力。这就是"无限扩展"的技术底座。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把 MCP 当"一个工具" | 它是**协议/标准**，允许接入无数 MCP 服务器提供的工具 |
| 以为接 MCP 要改 Hermes 源码 | 改配置文件注册即可，框架零改动；这正是协议的价值 |
| 把 MCP 和 API 直连混为一谈 | MCP 是**标准化封装**：服务方写一个 MCP 服务器，所有 MCP 客户端通用；API 直连每家用一套 |

@@point ② 为什么要搞协议：从"每家用一套"到"一次接接口"
@@need 要解决什么
没有 MCP 的年代，AI 要接外部服务是怎样一幅混乱图景？协议的"经济学价值"在哪？

@@idea 核心思路
对比"无协议 vs 有协议"：

**无协议（各写各的）**：

```text
Agent A 接 GitHub → 写专属集成
Agent B 接 GitHub → 再写一套专属集成
Agent C 接数据库 → 又一套……
```

**有协议（MCP）**：

```text
GitHub 团队写一次 MCP 服务器
→ 所有 MCP 客户端（Hermes、其他框架）通用
→ 数据库/企微/任何服务同样"一次开发、处处可用"
```

核心收益两条：**① 集成成本从"写代码"降到"写配置"；② 生态复用——一个服务接入一次，全行业受益**。理解这点，你就明白为什么 MCP 被当作 Agent 生态的"基础设施级"标准，而不是某个框架的私有功能。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 觉得"接一个服务也没多难，没必要学 MCP" | 单看一个服务确实不难；几十个服务+换框架迁移时才见分晓——协议省的是**长期和规模化**的成本 |
| 以为 MCP 只适合大厂服务 | 自己写个 MCP 服务器（几十行）也能接私有系统，个人开发者同样受益 |
| 混淆 MCP 与"插件商店" | 插件是框架内的分发机制；MCP 是跨框架的**开放标准**，权限更大参照系更宽 |

@@point ③ 两种传输方式：Stdio 与 HTTP(S)
@@need 要解决什么
接入 MCP 服务器时，配置里要选"传输方式"——Stdio 和 HTTP(S) 是什么区别？什么时候该用哪个？

@@idea 核心思路
两种官方支持的传输方式：

| 维度 | **Stdio** | **HTTP(S)** |
|---|---|---|
| 通信方式 | **标准输入/输出**（本地进程间管道） | **远程 HTTP 请求**（网络） |
| 服务器在哪 | 本地子进程（随 Hermes 启动） | 远程服务器（独立部署/共享） |
| 典型场景 | 本地 CLI 工具、本机服务 | 云服务、团队共享、跨机器 |
| 配置要点 | command+args（启动命令） | url（端点）+ 可选 headers |

选择口诀：**"本地跑得动就用 Stdio（简单直连），要远程/共享就用 HTTP(S)"**。GitHub MCP 工人官方包里一般以 Stdio 方式启动本地服务器进程。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| Stdio 配置里试图填 url | Stdio 是 command+args（本地命令）；填 url 是 HTTP 的用法，写错位置必然失败 |
| HTTP 服务器不可达先怀疑配置 | 先 curl 端点确认服务活着；网络问题与配置问题分开排查 |
| 混用"本地工具必须 Stdio" | 本地也可走 HTTP（本地起服务端）；选择看部署形态不看是否本机 |

@@point ④ 配置总览：MCP 服务器注册在 config.yaml
@@need 要解决什么
知道了协议和传输，落地第一步：MCP 服务器在哪里注册？配置块长什么样？

@@idea 核心思路
MCP 服务器在 `~/.hermes/config.yaml` 中注册，结构（示意）：

```yaml
mcpServers:
  github:                       # 服务器名（自己起，唯一）
    command: "npx"              # Stdio 方式：启动命令
    args:
      - "-y"
      - "@modelcontextprotocol/server-github"
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "<你的GitHubToken>"   # 见第 ⑥ 点安全提醒
```

| 字段 | 作用 |
|---|---|
| `mcpServers` | 顶层配置块，可注册多个服务器 |
| 服务器名（如上例 `github`） | 唯一标识，`hermes mcp xxx` 命令引用它 |
| command / args | Stdio 启动命令与参数 |
| env | 传给服务器的环境变量（如 Token） |

注册完成后，Hermes 会在启动时拉起这些服务器，把它们的工具并入可用工具集。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 多个服务器重名 | 名字唯一，重名后注册的会覆盖/冲突；起名带服务特征 |
| 改完 config.yaml 不重启 | MCP 服务器在**启动时拉起**；改配置后重启会话/网关才生效（配置驱动铁律） |
| 忘了 mcpServers 顶层键名 | 键名就是 `mcpServers`，不是 servers/mcp；写错键名静默不加载 |

@@point ⑤ 注册后工具去哪了："并入可用工具集"
@@need 要解决什么
MCP 服务器注册完，它的工具在哪能看见？"并入可用工具集"具体指什么？

@@idea 核心思路
MCP 服务器的工具**作为可用工具并入 Hermes 的工具集**。验证入口：

```bash
hermes tools            # 查看所有可用工具
hermes tools list       # （如支持）列出含 MCP 工具在内的完整清单
```

对照第六章：内置工具 + MCP 工具在**同一个工具管理界面**里出现，Agent 调用时不分"内置/外接"——**对 Agent 而言都是"工具"**。所以 MCP 工具也能被启用/禁用、也会出现在 /tools list，和内置工具平起平坐。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 在工具列表里找不到 MCP 工具 | 先查注册（mcpServers 配置）+ 重启未生效；再看启动日志有没有报错 |
| 以为 MCP 工具要单独开"工具集" | 并入既有工具体系，按工具管理统一查看/开关 |
| 服务器没启动却去工具列表找 | 启动失败的工具不会出现在列表；先解决服务器拉起的报错 |

@@point ⑥ GitHub MCP 接入：从零到验证的完整链路
@@need 要解决什么
讲概念不如带一遍真流程。GitHub MCP 是官方最常见的例子，把它从创建 Token 到验证工具完整走一遍。

@@idea 核心思路
接入 GitHub MCP 的完整链路（整合成一条完整流程）：

**第一步——准备 Token**：在 GitHub 生成一个 Personal Access Token（Fine-grained PAT：仓库读权限等按需勾选）。**Token 只用于配置，不进任何代码/记忆文件**（红线！）。

**第二步——注册服务器**：

```yaml
mcpServers:
  github:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "<你的GitHubToken>"   # 用真实 token 替换占位
```

**第三步——重启生效**：重启 Hermes 会话/网关，让服务器被拉起。

**第四步——验证**：

```bash
hermes mcp list             # 查看已连接的服务器（github 应在线）
hermes tools                # 或用 hermes tools list，找到 github_* 工具
```

**第五步——真实调用**：让 Agent "列出我的某个仓库的 issues"，看它是否调 GitHub 工具成功。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| Token 权限不足导致 API 403 | Fine-grained PAT 要勾选对应仓库/资源权限；报错先看 GitHub 返回的权限提示 |
| npx 首次拉包慢/失败 | 国内网络可能需要 npm 镜像（呼应第 2 章镜像天坑）；先单独跑一次 npx 命令验证 |
| 验证时"没有 github 工具" | 回查：注册了吗？重启了吗？启动日志有没有 Token 配置缺失的报错？ |

@@point ⑦ Token 安全：配置里的密钥红线
@@need 要解决什么
第 ⑥ 步里把 Token 写进了 config.yaml——这和"密钥不进文件"的红线冲突吗？需要把规则划清楚。

@@idea 核心思路
**分清两件事：① 密钥可以进"本地配置"用于启动服务；② 密钥绝不进"代码/记忆/技能/分享出去的文件"**。

| 场景 | 密钥可以吗 |
|---|---|
| `~/.hermes/config.yaml` 本地配置（供 MCP 服务器进程读取） | ✅ 可以（本机私有，配置即运行时） |
| 记忆文件 MEMORY/USER、技能 SKILL.md | ❌ 绝对不行（会被分享/检索） |
| 聊天记录、日志、贴出来的代码片段 | ❌ 不行 |
| 分享/打包任何配置 | ❌ 先脱敏（Token 换成 <占位>） |

实操建议：**如果方便，Token 走环境变量引用**（启动前 export），配置文件里写 `${GITHUB_PERSONAL_ACCESS_TOKEN}` 之类引用，最大限度避免明文落盘；不能则保持配置本地化，**备份/分享前必脱敏**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 觉得"配置里写 token 也没人看见" | 本地文件也会被打包/备份/同步；脱敏习惯要养成，泄漏一次就是全量泄露 |
| Token 明文写进 SKILL.md 教别人接入 | 技能文件是可分享的，token 进去=见证泄漏；技能里只写 <占位符> |
| 把含 token 的整份 config.yaml 发到群里求助 | 先 grep 检查 token 再发；**分享前扫描是全书通用铁律** |

@@point ⑧ hermes mcp 命令族：查看与管理服务器
@@need 要解决什么
注册完服务器，日常怎么查状态、管服务器？有没有专门的命令入口？

@@idea 核心思路
关键命令：

```bash
hermes mcp list        # 查看已连接的 MCP 服务器及状态
hermes mcp             # （带子命令）管理 MCP 服务器
```

| 命令 | 用途 |
|---|---|
| `hermes mcp list` | 确认各服务器在线/离线、工具数 |
| `hermes mcp <子命令>` | 按需连接/断开/查看详情（以实际 help 为准） |

配合工具管理：`hermes tools` / `/tools list` 看 MCP 工具有没有并入。**管理顺序：注册（config.yaml）→ 重启 → mcp list 查在线 → tools 查工具 → 实际调用验证**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 找不到 hermes mcp 子命令 | 版本较老/未安装 MCP 支持时命令缺失；确认 Hermes 版本支持 MCP（0.10.0+） |
| 只查 mcp list 不查 tools | list 管服务器存活，tools 管工具可见；两步都要 |
| 服务器状态 in 但工具没并入 | 部分服务器的工具注册失败（启动报错）；看 hermes 启动日志抓原因 |

@@point ⑨ 多个服务器：MCP 的"叠加态"
@@need 要解决什么
接完 GitHub 还想接别的（数据库、企微、自建服务）？多个 MCP 服务器怎么共存？

@@idea 核心思路
**mcpServers 是一个映射，可同时注册多个服务器**（第 ④ 点结构）：

```yaml
mcpServers:
  github:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "<你的GitHubToken>"
  my-company-db:            # 第二个服务器
    command: "python"
    args: ["/opt/mcp/my-db-server.py"]
  # enterprise-im:          # 更多同理
  #   ...
```

所有服务器启动后**工具全部合并进可用工具集**。管理要领：**每个服务器独立命名、独立 env、独立排查**——一个挂掉不影响其它（除非资源冲突）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 一个服务器挂了拖垮全部工具 | 正常设计下服务器相互独立；逐一查各自启动日志即可，别全盘重来 |
| env 变量名冲突（两个服务器都要 TOKEN） | 每个服务器有自己的 env 块，各自定义；Hermes 按服务器隔离传递 |
| 追加新服务器后旧工具"消失" | 多半是 YAML 缩进破坏；改完用 `hermes` 启动验证语法再继续 |

@@point ⑩ MCP 出问题时的排查路径
@@need 要解决什么
MCP 接入失败的常见场景五花八门，需要一条"由浅入深"的排查路径，避免瞎折腾。

@@idea 核心思路
MCP 排查路径（按顺序）：

```text
① 配置文件       mcpServers 键名、YAML 缩进、command/args 拼写
② 服务器本身     单独手动跑一遍 command（如直接 npx 启动），看能不能起来
③ 依赖与网络     npx 包能否下载（镜像）、Python 依赖是否安装、HTTP 端点可达性
④ env 与权限     Token 是否缺失/过期、权限是否覆盖目标资源
⑤ 重启与状态     hermes 重启 → hermes mcp list → hermes tools 查看注册成功
⑥ 日志           hermes 启动日志里服务器报错信息（最有力的线索）
```

**核心思想：每层先自证"我这一层没问题"，再往下一层走**——不跳过前面直接怀疑框架。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 一路"重启重启重启" | 重启前先做②③④（服务器本身能否独立跑通）；基础没通重启多少次都没用 |
| 报错信息一眼看不懂就放弃 | 报错里往往带社区链接/明确提示（如 GitHub 403 权限）；先读报错再改 |
| 排查到一半全删配置重来 | 日志和 mcp list 会告诉你具体挂在哪；精准修一处胜过推倒重来 |

@@point ⑪ MCP 与技能的关系：工具 vs 手册，再划一次
@@need 要解决什么
第 7 章划了"工具集 vs 技能"，现在又多了 MCP——三者边界要重新立一遍，防止记串。

@@idea 核心思路
三者的关系一句话：**MCP 是"新工具"，技能是"新手册"，工具集是"开关"**。

| 概念 | 本质 | 例子 |
|---|---|---|
| 工具集 | 工具的开关组合 | web/terminal 开关 |
| 内置工具 | 出厂自带动作 | web_search |
| MCP 工具 | 外接的新动作 | github_get_issue |
| 技能（SKILL.md） | 怎么用动作的流程手册 | 天气查询手册 |

配合逻辑：**MCP 给 Agent 更多"手脚"（新动作），技能教它"按什么流程编排手脚"（手册）**。典型组合：装 GitHub MCP（获得工具）+ 写"周报生成"技能（规定用 GitHub 工具取数据→汇总→输出的流程）。工具决定**能不能**，技能决定**怎么用**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为装了 MCP 服务器=会自动干活 | MCP 只提供工具；会不会**用**、怎么编排，取决于 Agent 能力与技能支持 |
| 想在 MCP 服务器里"装流程" | 流程是技能的活（SKILL.md）；MCP 服务器只管暴露服务接口 |
| 排查技能不生效却去查 MCP | 技能不生效查技能链路（目录/描述/工具集开关）；只有技能依赖的 MCP 工具缺失才涉及 MCP |

@@point ⑫ MCP 的"能力观"：无限，但要有节制
@@need 要解决什么
最后给一个冷静的提醒：MCP 带来"无限"，但也要求"节制"。盲目堆服务器会怎样？

@@idea 核心思路
**"无限扩展"是指天花板无限，不是让你把每个服务器的工具都同时开满**。参考三原则：

| 原则 | 解释 |
|---|---|
| 按需接入 | 只为实际任务接服务器（接 GitHub 是因为你要管仓库，不是因为它出名） |
| 最小权限 | Token 权限只给够用的（只读就给只读）；服务器只开要用的 |
| 定期体检 | 不用的服务器注销/停用；留着的检查 Token 是否过期、是否还被需要 |

潜在代价：**每接入一个服务器=多一组启动进程+多一点攻击面+工具列表更拥挤**。无限能力的前提是"你掌控着开关"。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 一次接 10 个服务器"提前备着" | 启动慢、噪音大、万一有漏洞全暴露；备着=都开着，风险不备存 |
| Token 全给最高权限"省心" | 泄漏时损失最大化；最小权限是安全底线 |
| 装了 MCP 就再也不回看 | Token 会过期、服务器会失效；纳入日常体检（第 11 章仪表板也是监控视角） |

@@summary
这一章你的 Agent 拿到了"外接一切"的能力：

| 拿到了什么 | 为什么要紧 |
|---|---|
| **MCP=协议标准**（USB-C 类比） | 看清 MCP 的本质：不是工具，是"接所有工具"的统一接口 |
| **Stdio vs HTTP(S)**：本地子进程 / 远程端点 | 传输选型一眼定：本地 command+args，远程 url+headers |
| **config.yaml 注册**：mcpServers 块 | 新增能力从"写代码"降为"写配置"，一行一个服务器 |
| **GitHub 全流程**：Token→注册→重启→mcp list→真实调用 | 一条完整样板，其它服务器照着套 |
| **Token 安全红线**：本地配置可放、分享必脱敏、绝进记忆/技能 | 能力越强越要注意凭据卫生——泄漏一次损失一次 |
| **排查路径**：配置→服务器→依赖→env→重启→日志 | MCP 出问题不再瞎重启，逐层自证定位 |
| **三概念边界**：MCP=新工具、技能=新手册、工具集=开关 | 什么时候调 MCP、什么时候写技能，一清二楚 |

一句话记住本章：**MCP 是能力外接的 USB-C 口——config.yaml 注册一个服务器、重启、mcp list 验证，GitHub 是样板；工具无限但接入要有节制，Token 只在本地、出必脱敏。**
