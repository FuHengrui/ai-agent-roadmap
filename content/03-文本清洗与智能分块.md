@@why 这一章在解决什么问题
上一章把 PDF 解析成了文本，但你先别急着入库——**刚解析出来的文本根本不能直接喂给大模型**：页眉页脚一页一页重复、页码混在正文中间、Word 转换出来一堆空行、英文单词被断行切开……这些噪音会让向量检索"精准命中垃圾"。

@@point ① 清洗的必要性：解析出来的文本到底有多脏
@@need 要解决什么
你以为 PDF 解析完就是干净文章？实际输出长这样（真实例子）：

```text
第 1 页
绩效考核管理办法
第一章 总则
第 2 页
第一条 为规范公司绩效考核工作，特制定本办法。
                                                                                                              （转下页）
第 3 页 第二条 ……
```

问题清单：**页眉/页脚每页重复**（检索"第 2 页"会命中一堆废话）、**页码混在正文里**、**大段空白**、**"转下页"这种排版垃圾**。如果直接入库：检索词"绩效考核"可能命中的是页脚"第 1 页绩效考核"而不是正文条款。

@@idea 核心思路
清洗的目标是**把带排版噪音的文本还原成"连续、干净、可读"的正文**，分两类处理：

| 噪音类型 | 例子 | 处理动作 |
|---|---|---|
| 无意义行 | 页码、页眉页脚、分隔线、空行、"转下页" | **直接删除**（正则匹配） |
| 排版残留 | 行尾多余空格、行间多个换行处残留空白 | **合并空白**，恢复一个自然的段落 |

项目里对应两个工具：`TextCleaner`（专门删无意义行 + 合并空白）和 `normalize_whitespace`（把各种空白规整成一个空格）。清洗顺序讲究：**先删"行级噪音"再规整"空白"**，删完的空行正好被规整吞掉。

@@point ② 文本清洗器：正则怎么精准"处决"噪音
@@need 要解决什么
删噪音最容易两个极端：**删得太粗**（把正文里含数字的行都删了）或**删得太细**（漏掉一半垃圾行）。要靠**针对性的正则**精准命中噪音的"长相"。

@@idea 核心思路
项目里 `TextCleaner` 处理的几类 regex 模式（示意）：

```python
class TextCleaner:
    def clean(self, text: str) -> str:
        # 1. 孤立的页码行："12" 或 "第 12 页"（只有数字/页码词的短行）
        # 2. 分隔线：================ 或 ------------  或 *****
        # 3. 常见页眉页脚：转下页 / 第X页 / 公司名+页数 这类模板行
        # 4. 连续空行/空白过多的行
        ...
        return text
```

**判据是"这一行的长相"**：`^第?\s*\d+\s*页?$` 匹配"纯页码行"，`^\s*[-=*]{3,}\s*$` 匹配"分隔线"，`^\s*$` 匹配"纯空行"。清洗器**靠一个 `matches` 列表**：它维护一组"判死规则"，每一行逐个过规则，命中即删。

注意：**规则必须保守**。`matches` 里是"确定是噪音"的模式，宁可漏删也不误删正文——因为正文删错一条就是知识丢失，而噪音漏几条，分块检索时影响有限。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 用一个"万能正则"清洗所有文档 | 不同来源的 PDF 噪音形态不同。**规则集是配置化的、可增补的**；直接改 `matches` 列表，而不是重写清洗逻辑 |
| 把"数字开头的行"当作噪音删掉 | 条款正文常常以`第一条`、`2026年第3号`开头！**判据是"整行只有页码形态"而不是"含数字"** |
| 清洗顺序反了（先合并空白再删行） | 合并后"空格+换行"被吞掉，删行规则就失配了。**必须先行后空** |

@@point ③ 为什么必须分块：整篇文档一个向量是废的
@@need 要解决什么
为什么不把整份 PDF 变成一个向量存了拉倒？因为**检索粒度决定了回答质量**：用户问"年假几天"，你希望检索命中的是"第二章 休假制度"里的那半页；如果整篇文档只有一个向量，检索命中的是"整篇文档"，大模型就要在上百页里找答案——约等于没检索。

@@idea 核心思路
分块（Chunking）把长文档切成**语义完整的小段（chunk）**，每个 chunk 单独向量化。这样：

```text
整份文档（100 页）                分块后（每个块独立向量）
┌──────────────────┐            ┌─────┐  chunk1: 第一章 总则
│  一个向量 = 检索  │     →      ├─────┤  chunk2: 第二章 休假制度
│  命中就是全文    │            ├─────┤  chunk3: 年假 XX 天……
└──────────────────┘            └─────┘  chunk4: ......
```

回答"年假几天"时，检索直接命中 chunk3，大模型只看一小段就能答准。**分块是 RAG 检索精度的地基**——块切得好不好，直接决定"能不能捞到对的那一段"。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 以为"块越小检索越准" | 太小（一句两句）语义不完整，向量表达失真；**块的大小要在"语义完整"和"粒度精细"之间平衡** |
| 把"分块"和"段落"划等号 | 段落是**作者视角**，分块要考虑**模型上下文窗口和检索粒度**。一个 3 千字的段落照样要再切 |
| 切完不保留块之间的上下文关系 | 相邻块语义相关，检索时**最好带上邻居**或记录原文档 id，回答才能引用"出自同一文档" |

@@point ④ 分块策略：四种切法各打什么场景
@@need 要解决什么
"切成小块"说起来简单，切法大有讲究：按标题切、按段落切、按固定字数切、还是按语义切？**不同文档结构适合不同切法**，项目用 `ChunkStrategy` 枚举统一管理。

@@idea 核心思路
四种策略，各管一类文档：

| 策略 | 怎么切 | 适合场景 | 特点 |
|---|---|---|---|
| **语义/结构切分** | 按文档结构（如 `##` 标题、分页符）切 | 有清晰层级的制度、手册 | 块之间语义内聚最好 |
| **段落切分** | 按自然段落切，长段再折 | 通用文档 | 简单，语义相对完整 |
| **固定大小切分** | 按字符数切（如 500 字一块），可带重叠 | 无结构的杂文、日志 | 简单粗暴、可控 |
| **句子切分** | 按句号/换行切 | 问答对、FAQ、条款 | 粒度最细，需后处理 |

项目里 `TextChunker` 支持按段落和固定大小两种主策略，并在分块时记录**来源文档、块序号**等元数据——这些是下一章入库和将来溯源的关键。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 一套策略打天下，所有文档都按固定 500 字切 | 制度手册有清晰二级标题，硬按字数切会把"第X条"劈进两个块。**有结构的文档先用结构切，无结构的才用字数切** |
| 选了结构切分却没提供"文档结构怎么识别" | 结构切依赖标题/分页等标记，纯文本流里没有这些标记时它退化成段落切。**选策略前先确认语料里有什么结构可用** |

@@point ⑤ 固定大小分块 + 重叠窗口：为什么"宁可多切一点"
@@need 要解决什么
按固定字数切块有个蛋疼问题：**语义可能在切缝处被劈断**——一句话上半句在块A、下半句在块B，两块各自都不完整，检索哪块都难命中，回答时上下文断裂。怎么补救？

@@idea 核心思路
答案是 **重叠窗口（overlap）**：相邻两块之间"借"一段文本。

```text
text: [.......................]
chunk1: [..............]
chunk2:        [..............]
chunk3:               [..............]
```

比如块长 500 字、重叠 50 字：块1 含 1-500，块2 从 450 开始到 950。**切缝处的语义被至少一个块完整包含**，检索命中率显著提升。代价是多占一点存储——但这点开销换检索质量，值。

要强调：重叠窗口是"小切口大收益"的工程细节，新手最容易忽略，但**少了它，固定大小分块在长句多的中文文档上几乎必然切坏语义**。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 重叠设太大（超过块长一半） | 相邻块几乎一样，冗余严重、检索结果高度重复。**经验值：重叠 10%-20%** |
| 中文按"字符数"硬切，切开多音字/生僻结构 | 中文分词比英文麻烦，硬切可能切碎词组；**有结构的文档优先用语义/段落策略** |
| 忘了记录"块来自哪个文档第几部分" | 没有来源元数据，将来无法回答"这个答案出自哪里"。**分块时同步写入 metadata** |

@@point ⑥ 分块参数怎么定：从"块大小"到"向量维度"的约束链
@@need 要解决什么
块到底多大合适？定 100 字太小、定 5000 字又太大……其实**块大小的上限不是拍脑袋，是被嵌入模型和检索语义共同约束的**。

@@idea 核心思路
一条完整的约束链：

```text
嵌入模型的最大输入长度（如 512/1024 token）
        ↓ 约束
单块字符数上限（超出会被截断，截断丢语义）
        ↓ 约束
重叠窗口大小（块长的 10%-20%）
        ↓ 再约束
块数与存储/检索量
```

所以定参顺序是：**先看嵌入模型支持多长 → 定块长上界 → 定重叠**。项目用 `TextChunker` 时把 max_chars、min_chars 提成配置参数，上层 `DocumentStore` 组装时传进来，改参数不改代码。

实践参考值：中文场景常见 300-800 字一块、重叠 50-150 字，具体要看语料类型微调。**没有万能值，有调整手段才是关键。**

@@point ⑦ 分块结果用什么承载：块对象与元数据
@@need 要解决什么
分块切出来的不只是"一堆字符串"。下游要存库、要检索、要追溯出处——它需要知道"这一块来自哪份文档、是文档里的第几块"。**如果只把纯文本递给下游，来源信息就丢了。**

@@idea 核心思路
项目用**块对象**承载"文本 + 元数据"，一个块是一个小结构体：

```python
@dataclass
class Chunk:
    text: str                  # 块文本（清洗后的）
    doc_id: str                # 来自哪份文档
    chunk_index: int           # 在文档里的第几块
    char_count: int            # 字符数（可验证参数是否生效）
    # 可扩展：页码、章节路径等
```

为什么要带这些：`doc_id` 是将来"答案出处"的身份证，`chunk_index` 支持跨块上下文（查第5块时顺带第4、第6块），`char_count` 帮你在调参时看到"max_chars 到底生效没有"。**分块不是终点，是被上下游使用的数据结构**——这也是下一章 `Document` 数据模型的直接前身。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 只把纯文本 list 传给嵌入层，不记来源 | 入库后检索只能拿到句子，不知道出自哪份文档——"可溯源"直接废掉，改起来要重灌全库 |
| 块对象字段随意加、结构不统一 | 下游解析块对象会到处 KeyError。**块的字段在 `Chunk` 数据类里统一声明**，别用裸字典 |

@@point ⑧ 入库前的完整流水线：解析 → 清洗 → 分块 → 备好元数据
@@need 要解决什么
单看每个工具都很简单，但**顺序和衔接才是工程的真功夫**：谁先谁后、什么状态交给哪个环节、中途失败怎么断。这一棒接不好，前面的功夫白费。

@@idea 核心思路
项目里这一段由 `DocumentStore`（下一章主角）编排，链路是：

```text
原始文件
   ↓ ① 解析（BaseParser：按扩展名路由）
解析文本（脏）
   ↓ ② 清洗（TextCleaner：删页眉页脚/页码/空行 + 合并空白）
干净文本
   ↓ ③ 分块（TextChunker：策略 + 重叠 + 元数据）
block 列表（每块带 doc_id、序号、来源）
   ↓ ④ 交给嵌入层，逐块向量化入库（下一章）
```

每一步都有自己的**失败出口**：解析失败（文件损坏）→ 记录错误并跳过，而不是整批崩溃；清洗完为空 → 说明文档没内容，警告；分块结果为空 → 同样要显式报错。**每一棒都要"检查上棒的质量"再往下传**，这正是清洗/分块这类管线的工程常识。
