@@why 这一章在解决什么问题

@@point ① docker-compose：把数据库变成"一条命令"
@@need 要解决什么
不装 Docker 也能装 Postgres，但你要处理版本冲突、开机自启、卸载残留、同事复现四个问题。用容器解决"基础设施可复现"，是团队工程的标配。
@@idea 核心思路
项目根目录的 `docker-compose.yml` 只干一件事：**声明并拉起两个基础设施服务**。
```yaml
# docker-compose.yml
services:
  postgres:
    image: postgres:16-alpine
    container_name: legal-postgres
    environment:
      POSTGRES_USER: legal_user
      POSTGRES_PASSWORD: <db_password>
      POSTGRES_DB: legal_db
    ports:
…（以下省略 18 行，完整代码见仓库对应位置）
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  pgdata:
  redisdata:
```
重点看三个设计：
- **`volumes` 持久化**：数据写进命名卷（pgdata/redisdata），`docker-compose down` 不会丢数据，只有 `down -v` 才清空——"重置数据库"很方便。
- **`healthcheck` 健康检查**：容器"起来了"不等于"能用了"，pg_isready / redis-cli ping 才是真活。第 4 章建表前可以等它 healthy。
- **端口映射**：`5432:5432` 让容器里的 Postgres 对本机 `localhost:5432` 可见——后续 Python 连接无需进容器。
@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| `docker-compose` 命令报 "command not found" | 老版本 docker-compose 是独立命令；确保 Docker Desktop 已启动且 `docker compose`（空格）可用，或安装 compose 插件 |
| 5432 端口被占用 | 本机已装过 Postgres；改 yml 里左侧端口如 `5433:5432`，并同步改 .env 的 DATABASE_URL |
| 容器重启后数据还在但连接失败 | 卷数据与镜像版本不兼容；`docker-compose down -v` 清卷重建（仅开发期可接受） |
| 镜像拉不下来/极慢 | 配置镜像加速器，或用 `docker pull` 先手动拉好两张镜像 |

@@point ② Python 3.14 虚拟环境：依赖隔离
@@need 要解决什么
系统 Python 是公共的，装一个包全家中毒（版本冲突、权限问题）。每个项目一个虚拟环境，等于给项目一个"独立小房间"。
@@idea 核心思路
Python 3.11+ 自带 `venv` 模块，不需要额外工具：
```bash
# 进入项目根目录（含 pyproject.toml 的地方）
python -m venv .venv

# Windows 激活（git-bash 下）
source .venv/Scripts/activate
# macOS/Linux
source .venv/bin/activate

# 验证
python --version   # 应显示 3.14.x
pip --version
```
激活后记住一个原则：**所有 `pip install` 只装进这个 .venv**，全世界互不污染。`.venv/` 目录要写进 `.gitignore`（几十 MB 不入库，凭 pyproject.toml 可再生）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 建了 venv 但 `python --version` 还是旧版本 | Windows 上直接输入 `python` 走的是 PATH 里的系统解释器；必须显式激活 venv（`venv/Scripts/activate`）或直接调用 `venv/Scripts/python.exe`，别靠"以为激活了" |
| 用 Python 3.14 装包报 "Failed building wheel" | 部分依赖还没有 3.14 的预编译轮子，源码编译在 Windows 缺工具链会失败；Web 服务项目建议锁 Python 3.11/3.12 这种轮子齐全的版本 |

@@point ③ pyproject.toml：一次性锁死全部依赖
@@need 要解决什么
"我这边能跑你那边不行" 90% 是依赖版本不一致。与其每个人手动 pip install 拼拼凑凑，不如在项目里声明一份**完整依赖清单**。
@@idea 核心思路
LegalMind 用 `pyproject.toml`（现代 Python 包管理标准，可被 pip/uv/pdm 通用）声明依赖，关键分组：
```text
[project]
name = "legal-mind-backend"
version = "1.0.0"
requires-python = ">=3.14"

dependencies = [
    "fastapi[standard]>=0.136",
    "uvicorn[standard]",
    "tortoise-orm[asyncpg]>=0.24",
    "asyncpg",
…（以下省略 9 行，完整代码见仓库对应位置）
    "psycopg[binary,pool]>=3.2",
    "sentence-transformers>=5.5",
    "redis>=8.0",
    "rank-bm25>=0.2.2",
    "python-multipart",
    "email-validator",
    "jieba",
]
```
安装方式：
```bash
pip install -e ".[dev]"     # 安装全部依赖 + 开发工具
```
版本带 `>=` 底线即可，不要锁死精确版本（生态迭代快）。如果想彻底复现他人环境，再生成 `uv.lock` / `poetry.lock`。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 锁了直接依赖，换台机器还是装出一堆不同版本 | `pyproject.toml` 只锁顶层依赖，传递依赖版本飘移；要可复现必须用 lockfile（uv/poetry 的 lock 文件），或 `pip freeze` 固定全量 |
| requirements.txt 和 pyproject.toml 同时维护，装漏装重 | 两处清单改一处忘另一处，环境时好时坏；统一只用一个入口（pyproject + lock），requirements 留给部署钩子 |

@@point ④ pydantic-settings：.env 自动加载
@@need 要解决什么
上一章看到 `.env` 里有十几项配置，代码里怎么读？手写 os.getenv 十几遍又容易漏默认值。用 `pydantic-settings` 让"配置类"自动从 .env 加载并对齐类型。
@@idea 核心思路
粗暴方案是 `os.getenv("DATABASE_URL")`，但类型、默认值、缺失提示全要手写。LegalMind 采用 Settings 类：
```python
# app/config.py
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8")

    DATABASE_URL: str = "postgresql://legal_user:<db_password>@localhost:5432/legal_db"
    REDIS_URL: str = "redis://localhost:6379/0"

    LLM_API_KEY: str = "sk-xxx"
…（以下省略 7 行，完整代码见仓库对应位置）
    RAG_TOP_K: int = 5
    RAG_SCORE_THRESHOLD: float = 0.7
    RERANK_ENABLED: bool = True

    SECRET_KEY: str = "<your-secret>"
    ACCESS_TOKEN_EXPIRE_MINUTES: int = 120

settings = Settings()
```
几个要点：
- `env_file=".env"`：启动时自动读 .env 文件，**同名环境变量优先于 .env**（方便生产环境注入）。
- 类型自动转换：`ACCESS_TOKEN_EXPIRE_MINUTES=120` 字符串会被转成 int 字段。
- 全项目 `from app.config import settings` 单例引用，一处定义全体生效。
@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 明明配了 .env 却读到默认值 | Settings 的 `env_file` 路径是**相对当前工作目录**的；确保从项目根目录启动 uvicorn |
| .env 里 Key 带引号 | `LLM_API_KEY="sk-xxx"` 含空格或特殊字符时必须加引号；**成对引号会被 python-dotenv 剥掉**，不会当成值的一部分；不要加引号 |
| 字段名大小写不匹配 | pydantic-settings 默认大小写不敏感匹配环境变量，但 .env 里建议全大写保持习惯 |
| extra="ignore" 缺失 | .env 里有多余的行走 pydantic 会报错；在 model_config 里加 `extra="ignore"` 容忍多余项 |

@@point ⑤ 验证链路：三步确认环境可用
@@need 要解决什么
环境搭完不能靠"感觉装好了"，要有一套**可重复的验证**，证明数据库真能连、Redis 真能通，为下一章的代码运行扫清路障。
@@idea 核心思路
启动容器后，依次验证三层：
```bash
# 1. 验证 Postgres（空库）
docker exec legal-postgres psql -U legal_user -d legal_db -c "\dt"
# 应返回：Did not find any relations（空库正常，表将在第 4 章由 ORM 建）

# 2. 验证 Redis
docker exec legal-redis redis-cli ping
# 应返回：PONG

# 3. 验证 Python 依赖可导入
python -c "import fastapi, tortoise, langchain, langgraph; print('deps ok')"
```
空库"没有任何表"不是错误——正说明还没人创建过表，Tortoise 建表在第 3 章做。如果你看到表了，往往是之前某次启动已建过。

@@point ⑥ 目录结构：后端工程的骨架长什么样
@@need 要解决什么
新项目最怕"文件乱放"。先规定好目录，后面代码永远知道往哪写、去哪儿找——这是工程化的第一习惯。
@@idea 核心思路
LegalMind 后端（legal_mind/backend）的标准布局：
```text
backend/
├── pyproject.toml           # 依赖清单
├── .env                     # 环境配置（不入 git）
├── app/
│   ├── main.py              # FastAPI 入口（下一章）
│   ├── config.py            # Settings 配置类
│   ├── dependencies.py      # JWT 依赖（第 5 章）
│   ├── models/              # Tortoise ORM 模型（第 4 章）
│   │   ├── user.py  case.py  chat.py  document.py
│   ├── api/                 # 路由层
…（以下省略 11 行，完整代码见仓库对应位置）
│   │   └── case_service.py
│   ├── utils/               # 工具
│   │   └── security.py      # 密码哈希 / JWT（第 5 章）
│   └── scripts/             # 一次性脚本
│       ├── build_index.py   # 案例切片建向量索引（第 6 章）
│       └── seed_cases.py    # 灌入种子案例数据
├── models/bge-small-zh/     # 本地嵌入模型权重（第 6 章）
└── docker-compose.yml
```
这个"按层分目录"的约定贯穿本书后续所有章节，任何代码文件都能在三秒内定位。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 启动报 `ModuleNotFoundError: app` | `from app.xxx` 依赖当前工作目录在项目根；在子目录里敲命令就会找不到包。统一从根目录跑 `uvicorn app.main:app`，别 cd 到 app 下 |
| 新建的子包忘了加 `__init__.py` | Python 3 有隐式命名空间包，本地能跑、打包/某些工具就崩；每个包目录补一个空 `__init__.py` |

@@point ⑦ 种子数据脚本 seed_cases.py：让系统"有东西可查"
@@need 要解决什么
RAG 检索没有语料就是空转。上线的案例由真实裁判文书导入，开发阶段用**种子数据**灌几条像样的案例，让检索有东西可捞、页面有内容可看。
@@idea 核心思路
`scripts/seed_cases.py` 把案例写进 cases 表，字段与第 4 章的 Case 模型一一对应：
```text
# 每条种子案例的形态（节选）
{
    "title": "张三与李四离婚财产纠纷案",
    "case_number": "(2024)京01民终1024号",
    "court": "北京市第一中级人民法院",
    "judgment_date": "2024-03-15",
    "case_type": "民事",
    "summary": "夫妻共同财产分割，房产归属争议……",
    "laws": ["民法典第一千零八十七条", "民法典第一千零六十二条"],
}
```
执行后输出：
```text
新增: 张三与李四离婚财产纠纷案
新增: 王某劳动仲裁案
新增: 李某交通事故赔偿案
✅ 种子数据插入完成
```
注意：**cases 表是 RAG 的"源头数据"**，第 6 章 build_index.py 会把这里的 content 切片向量化存进 ChromaDB——两个脚本是先后关系，别搞反。

@@point ⑧ .gitignore 与密钥卫生
@@need 要解决什么
`.env` 里有 LLM 密钥和数据库密码，一旦 push 到 GitHub 就是安全事故（Sk 密钥可被扫号工具秒发现）。项目从一开始就要立规矩。
@@idea 核心思路
项目根 `.gitignore` 至少要拦这些：
```text
.venv/
__pycache__/
*.pyc
.env
*.log
node_modules/
dist/
chroma_data/      # 向量库数据目录（可能很大且可再生）
```
三条纪律：
1. **`.env` 永远不进 git**，仓库里只放 `.env.example`（占位符版本，给队友照着填）。
2. 代码里**禁止出现真实密钥字面量**——真正的 Key 只存在于开发者本地 .env 或部署平台的环境变量里。
3. 如果不小心 push 了密钥，**立即去供应商控制台吊销该 Key 并重新生成**，不要只改仓库（历史记录里还有）。翻 GitHub 的扫号机器人几小时内就会抓走它。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| `.env`、`__pycache__`、`.venv` 被 git add 进去了 | 检查 `git status`，已提交就用 `git rm -r --cached` 移出跟踪再补 .gitignore；务必先确认仓库从未推过带密钥的提交 |
| 只写 `.env` 没写 `.env.example` | 新人/部署机不知道要配哪些变量；维护一个全占位符（sk-xxx 之类）的 `.env.example` 提交进仓库 |
