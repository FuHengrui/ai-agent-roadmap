@@sub 阶段 18 · 云原生开发环境与 DevOps 工具链　|　版本控制　|　难度 ★★★

@@why 这一章在解决什么问题
你在 dev 分支上开发新功能做到一半，线上突然出 bug 要紧急修复——**你手上的半成品不能上线，但线上又必须马上改**。没有分支的 Git 只能硬着头皮乱改；有了分支，master 这条主线可以永远是"干净可发布"的，任何实验、摸索都在别的分支上做。

这一章讲清分支的本质（一个"贴纸"模型，听完你会觉得超简单）、增删改查、合并，以及误删找回。

@@point ① 为什么需要分支：并行开发的时代
@@need 要解决什么
两个需求同时开工、一个功能做一半要中断、线上 bug 必须马上修——**所有开发都堆在一条主线上，谁也没法保证"主线随时能上线"**。分支就是给你"多条平行世界"。

@@idea 核心思路
分支允许你把工作**从主线上分离开**，互不影响：

```
master:  A --- B --- C          ← 主线永远干净可发布
                          \
dev:                        D --- E   ← 新功能在别的分支上开发，不污染主线
```

典型场景（也是一个完整的分支综合练习）：
1. 在 `dev` 分支开发新需求；
2. 突然有紧急 bug → 切回 `master`，从主线拉一个 `fix` 分支修复；
3. 测试通过 → 合并 `fix` 回 `master` 并推送上线；
4. 切回 `dev` **继续未完成的工作**——分支让"被打断"和"恢复"都无痛。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为分支是把文件复制很多份 | 不是！分支是一张"贴纸"（下一个知识点），创建分支**几乎不占空间、瞬间完成** |
| 不敢建分支，全挤在 master 上 | 这正是分支要解决的痛点；master 长期含"半成品"，线上发布全靠赌运气 |

@@point ② 分支的本质：一张贴在提交上的贴纸
@@need 要解决什么
"开分支是不是把整个项目复制一份？那不是要占好几份磁盘空间？"——理解分支本质之前，很多人对分支有这类误解。

@@idea 核心思路
**分支不是一个目录副本，它只是一个指针（贴纸），贴在某个 commit 上。**

```
         A --- B --- C        ← master 贴在 C 上
                        \
                          D --- E   ← 新建的 dev 贴在 E 上
```

- 每次 commit，当前分支这张"贴纸"就被撕下来，贴到**新的 commit** 上，同时 `HEAD` 跟着前进；
- 创建分支 `git branch cat`：就是**拿一张新贴纸，贴到当前 commit 的位置**，和 master 并排；
- 切换分支 `git checkout cat`：把 `HEAD` 指向 cat 这张贴纸；
- 之后在 cat 上 commit，cat 往前走，master 原地不动。

结论：**分支就是贴在 commit 上的贴纸，会随新提交前进；切换分支只是移动 HEAD，不复制任何文件。**

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 删了分支以为代码也删了 | 分支只是贴纸，**贴纸下的 commit 不会消失**；只要提交号还能找到，就能找回来（第⑨点） |
| 以为"创建分支后两边内容立刻不一样" | 创建瞬间两个分支指向**同一个 commit**，内容完全一样；是**各自的新提交**让它们分开的 |

@@point ③ 查看分支：git branch 的一眼扫
@@need 要解决什么
项目分支多了以后，你得知道：现在有哪些分支？我在哪个分支上？远程有哪些？——没有总览，管理全是瞎猜。

@@idea 核心思路

```bash
git branch            # 列出所有本地分支，当前分支前有 * 号
git branch -r         # 只列远程分支
git branch -a         # 本地 + 远程分支全部列出
```

当前分支在输出里带 `*` 星号，例如 `* master` 表示你此刻在 master 上——**提交前先确认人在哪条分支**，这是团队铁律。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 提交后找不到提交在哪 | 大概率发到了错误分支；在正确分支上合并回来或重新处理 |
| 分不清 branch 和 checkout | `git branch` 是**创建/查看**分支；`git checkout` 是**切换**分支（也可以创建+切换，见下一点） |

@@point ④ 创建分支：git branch 名字
@@need 要解决什么
新需求开工，需要一条独立分支——怎么"开新世界"？

@@idea 核心思路

```bash
git branch dev          # 创建名为 dev 的分支（贴纸贴到当前 commit）
git branch fix master   # 基于 master（而不是当前分支）创建 fix 分支
git checkout -b hotfix  # 创建 hotfix 分支并【立即切换过去】（创建+切换一步到位，最常用）
```

后面两条更常用：`git branch 名字 来源分支` 指定从哪条分支开；`git checkout -b` 创建即切换。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 创建分支后 `git branch` 显示新分支，但没切换 | 创建不会自动切换！`git branch dev` 后你**还在原分支**；要切换用 `git checkout dev` |
| 分支名带空格/特殊字符 | 分支名只能用字母、数字、下划线、横线等；带空格的会被拆成两个参数报错 |
| 在错误的分支上执行了 git branch dev | 新分支基于**当前所在分支**创建；想从别的分支开，要明确指定来源：`git branch dev 某分支` |

@@point ⑤ 切换分支：checkout / switch，切换时发生了什么
@@need 要解决什么
分支之间来回跳，得知道切换的本质动作，否则会出现"文件怎么突然变了"的惊慌。

@@idea 核心思路

```bash
git checkout dev        # 切换到 dev 分支
git switch dev          # 新版命令，同样功能（更语义化）
git checkout -b new     # 创建并切换
```

切换分支时 Git 主要做**两件事**：
1. **更新工作目录和暂存区**——把文件内容换成目标分支的版本（所以你会看到文件"瞬间变了"）；
2. **变更 HEAD 的位置**——HEAD 从指向 master 变成指向 dev。

这两个动作做完，你就在"另一个世界"里了。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 切换时提示 "Your local changes would be overwritten" | 当前分支有**未提交的改动**，切换会冲突；先 commit 当前改动，或先把改动暂存起来再切 |
| 切换后"文件消失了" | 文件在各分支本来就不一样（比如只在 dev 新建了文件），切到 master 自然看不到——切回 dev 就回来了，**没丢** |
| 切过去发现想要的旧文件不在 | 用 `git log -- <文件名>` 查它在哪个分支出现过，再决定怎么处理 |

@@point ⑥ 合并分支：git merge 把两边历史合流
@@need 要解决什么
dev 上功能开发完了，要把成果**合回主线**。合并就是：让目标分支拥有另一条分支的全部提交。

@@idea 核心思路

```bash
git checkout master     # 1. 先切到【要接收合并的分支】（目标分支）
git merge dev           # 2. 把 dev 合并进当前分支（master）
```

合并的两种结果：
- **快进（fast-forward）**：master 没动过、dev 领先 master → 直接把 master 贴纸"快进"到 dev 的位置，干净利落；
- **三方合并**：master 也有自己的新提交 → Git 找一个共同祖先，把两边改动合并成**一个新的合并提交**。

合并后：内容都齐了，被合并的分支（dev）作为"贴纸"没有利用价值了——**想删就删**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 没切到目标分支就 merge | 会把两个分支的合并方向搞反，合进错误的分支；**先 `git branch` 确认自己在哪** |
| merge 时冲突了 | 同一处两边都改了：手动解决冲突，`git add` + `git commit`（第十二章第八、九点） |
| 因为怕冲突干脆不合并 | 冲突是"信息差"的暴露，越拖越难合；**频繁小批量合并**才是减少冲突的正道 |

@@point ⑦ 合并冲突：两个分支改了同一处
@@need 要解决什么
dev 改了第 10 行，master 也改了第 10 行，合并时 Git 不知道听谁的——此时报错 CONFLICT，并生成带 `<<<<<<<` 标记的文件（和远程冲突同一套玩法）。

@@idea 核心思路

```bash
$ git merge b1
Auto-merging a.txt
CONFLICT (content): Merge conflict in a.txt
Automatic merge failed; fix conflicts and then commit the result.
```

1. 打开冲突文件，看到：

```bash
<<<<<<< HEAD
# master up
=======
# b1 up
>>>>>>> b1
```

2. **手动保留想要的（可以两边都要、删掉一边，或重写）**，删掉三行标记；
3. 重新提交：

```bash
git add a.txt
git commit -m "合并 b1：保留双方内容"
```

要点：解决冲突的核心是**手动**——Git 只负责"把两边的分歧摆到你面前"，拍板必须是人。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 冲突文件里有多个标记段 | 一次冲突可能不止一处；**以文件为单位逐段解决**，全部清掉标记后再提交 |
| 解决冲突时以为"选一边就万事大吉" | 有时两边都要（比如一个加了 import、一个改了逻辑）；只留一边可能编译不过 |
| 合并到一半想重来 | `git merge --abort` 撤销当前合并，回到冲突前状态 |

@@point ⑧ 删除本地分支：-d 与 -D
@@need 要解决什么
分支合并完就没用了，躺着只会让列表越来越乱。删除它是日常维护。但 Git 会"拦"你——分两种删除力度。

@@idea 核心思路

```bash
git branch -d dev      # 温和删除：只有【已合并】的分支才让删
git branch -D dev      # 强制删除：不检查是否合并，直接删（慎用）
```

- `-d` 遇到"还没合并"的分支会**报错拒绝**（错误信息会告诉你：如果确定要删，用 `-D`）；
- `-D` 无视提示强制删除——如果里面的提交没合并过，删了可能"暂时找不回"（第⑨点教你找回）。

这个"拦截"其实是保险丝：提醒你"这个分支的成果还没合回去，确定不要了？"

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| `-d` 报错 "not fully merged" 删不掉 | 正常保护；确认不需要就用 `-D`，或先合并再 `-d` |
| 删不了"正在使用"的分支 | 必须先切到别的分支才能删当前分支；会报错 "cannot delete branch checked out" |
| 以为删本地分支影响远程 | 不影响！远程分支要单独删（第⑩点） |

@@point ⑨ 误删未合并分支：贴纸撕了，commit 还在
@@need 要解决什么
`-D` 手一抖删了还没合并的分支——工作了几天的心血，是不是全没了？**不是。** 因为分支是贴纸，撕掉贴纸不影响它下面的 commit。找回的方法：拿一张新贴纸，贴回去。

@@idea 核心思路
找回原理：需要知道**原分支最后指向的提交号**。

```bash
git reflog                     # 1. 找到原分支最后指向的提交号（删除动作在 reflog 里有记录）
git branch new_dev b2323b      # 2. 用新名字建分支，指向那个提交号（这里是占位示例）
git checkout new_dev           # 3. 切换过去验证，文件都在
```

如果还记得提交号，直接 `git branch 新分支名 <提交号>` 也行；
如果不知道，reflog 里找 "Deleted branch dev (was xxxxxx)"——括号里的就是要找的提交号。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| reflog 也找不到（过期/换机） | 那就真找不回了；**重要工作勤提交、别太久不推远程**（推上远程等于双保险） |
| 以为"删除分支会把提交一起删掉" | 分支 = 指针，删除只删指针；提交对象还在仓库里（直到被垃圾回收） |
| 重新建分支用错了提交号 | 找回的是错版本；用 `git show 提交号` 先确认内容再贴 |

@@point ⑩ 删除远程分支：git push origin -d
@@need 要解决什么
本地分支删了，远程仓库里的同名分支还在（remote 会一直留着）。远程分支怎么删？用 push 的"删除指令"——推送一个"删除操作"出去。

@@idea 核心思路

```bash
git push origin --delete dev     # 删除远程分支 dev（新写法）
git push origin -d dev           # -d 是 --delete 的简写
```

处理的是"远程存在、本地已无价值"的分支。注意它和 `git branch -d` 删除的是**两个地方**的分支，互不影响。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 本地删了但远程还在 | 正常，两地独立；要同步删远程就执行上面的 push -d |
| 误删了远程分支 | 如果删除前的提交还在本地（或别人 clone 过），重新 push 分支回来；要快，赶在垃圾回收前 |
| 以为 `git remote rm` 能删远程分支 | `remote rm` 删的是"本地对远程的记录"；删远程分支必须用 push -d |

@@point ⑪ 分支综合练习：紧急修复的完整套路
@@need 要解决什么
把前面所有分支操作串成一次真实工作流：**开发到一半，线上紧急 bug 来了**——这是分支最有价值的场景，串一遍，你就真正会用分支了。

@@idea 核心思路

```bash
# 1. 开发中的日常工作
git branch dev                # 建开发分支
git checkout dev              # 切到 dev
# …写代码、git add、git commit…（在 dev 上继续）

# 2. 紧急 bug 打断开发
git checkout master           # 切回主线
git branch fix                # 从 master 开修复分支
git checkout fix              # 切到 fix
# …修复问题…
git commit -am "fix: 紧急修复 xxx"   # 提交修复（-am = 暂存已跟踪文件 + 提交）

# 3. 修复上线
git checkout master           # 切回主线
git merge fix                 # 把修复合进主线
git push                      # 推送到远程（线上代码更新）

# 4. 回到开发位
git checkout dev              # 切回 dev，继续未完成的功能
```

整个流程的关键：**主线永远只收"可上线"的代码**；开发中的半成品和紧急修复并行不悖。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| fix 分支忘了从 master 开 | 修的是"线上问题"，必须基于**当前线上版本（master）**；从 dev 开会把半成品带上去 |
| 合并完忘了切回 dev | 收尾检查：`git branch` 看你现在在哪；在错误分支上继续开发是常见事故源 |
| 修复完忘了 push | merge 只是本地合并，**push 之后线上/队友才看得到** |

@@summary
| 问题 | 答案 |
|---|---|
| 为什么要分支 | 并行开发、紧急修复不污染主线，主线永远可发布 |
| 分支本质 | 贴在 commit 上的"贴纸"（指针），随提交前进；创建几乎零成本 |
| 怎么建/看/切 | `git branch 名` 建；`git branch` / `-a` / `-r` 看；`git checkout 名` / `git switch 名` 切；`-b` 建+切 |
| 怎么合并 | 先切到目标分支再 `git merge 来源分支`；快进 or 三方合并 |
| 合并冲突 | 手动保留内容、删标记、add + commit；`git merge --abort` 可放弃 |
| 删分支 | `-d` 已合并才删；`-D` 强制；`git push origin -d` 删远程分支 |
| 误删找回 | 分支是贴纸，commit 还在；reflog 找提交号 → `git branch 新名 提交号` |

一句话记住本章：**分支 = 贴在 commit 上的贴纸，零成本创建、随手撕；master 别乱动，新功能上 dev/feature、紧急修复从 master 拉 fix，合完回主线再 push；删错分支不用慌，贴纸撕了 commit 还在，reflog 定位后一张新贴纸贴回去。**
