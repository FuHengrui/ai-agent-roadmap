@@h1 第一章　Spark 简介：为什么需要它
@@sub 阶段 13 · 大数据处理与分布式检索技术　|　难度 ★★☆

@@why 这一章在解决什么问题
你手里可能攒了几年的数据：网站的访问日志一天几亿条、电商订单表一次导出几十 GB、还有一堆"想算但算不动"的指标——比如"每个省份昨天卖得最好的商品 top 10"。用 Excel 崩，用 Python 跑一天，靠 SQL 单机数据库更是直接卡死。

**问题不是数据太多，而是你只有一台机器、一套单机工具。** 这一章介绍 Spark：一个把**成百上千台机器组织起来一起算**的分布式计算框架。你不需要先弄懂它内部多复杂，只需要搞清楚三件事：**它解决什么问题、凭什么比 Hadoop MapReduce 快、它和别的组件怎么分工**。搞懂这三件事，后面 17 章你才知道自己在折腾什么。

学完这一章，你能回答：**什么时候该上 Spark、它比老一代框架强在哪、一个完整的 Spark 生态由哪些成员组成**。

@@point ① 单机算不动的数据，怎么办
@@need 要解决什么
先正视痛点：假设你要统计"过去一年每天每小时的访问量"，原始日志 500 亿行。单机上，读一遍要几小时，聚合一次内存直接爆——你缺的不是更快的 CPU，而是**一种把多台机器当一台用的方法**。

@@idea 核心思路
思路就三个字：**分而治之**。把 500 亿行切成 1000 份，丢给 1000 台机器**同时算**，每台只算自己的 500 万行，最后把结果合并。

但"分而治之"说起来容易，真做有三个难关：

| 难关 | 不解决会怎样 |
|---|---|
| 任务怎么分 | 某台机器多干、某台闲着，整体速度被最慢的那台拖死 |
| 机器挂了怎么办 | 算到一半节点宕机，整个任务白跑 |
| 中间结果往哪放 | 每一层的输出都要存盘，光读写磁盘就比计算还慢 |

Spark 存在的意义，就是把这三大难关**封装成一套 API**——你只需写"算什么"，不需要管"怎么分、怎么容错、怎么传输"。这就是它叫"计算框架"的原因。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为"分布式=每台机器写自己的轮子" | 框架把切分/调度/容错/传输封装好了，你只写"算什么"；自己造轮子必然踩满三大难关 |
| 500 亿行一次性读进内存 | 数据是**分片流式**读的，不是一把梭全加载。说"内存装不下"说明还没理解分治 |
| 机器越多一定越快 | 任务切分不均=被最慢节点拖死（长尾）；还有通信开销，机器数要配数据量 |
| 把框架当黑盒不关心怎么分 | 第三四章讲任务切分（分区/Stage），现在先建立"分而治之"的直觉 |


@@point ② Spark 是什么：一个统一的分布式计算框架
@@need 要解决什么
市面上解决大数据问题的东西很多：Hadoop 的文件系统（存数据）、Hive（写 SQL）、Flink（实时流），到底哪个才是 Spark？你需要一个**一句话定位**，不然学完都不知道自己在学哪一层。

@@idea 核心思路
**Spark = 一个通用的、分布式的、内存优先的计算引擎**，可以这么拆：

| 关键词 | 含义 |
|---|---|
| 通用 | 批处理（一次算一大块）、流处理（边进边算）、SQL、机器学习都能干 |
| 分布式 | 跑在多台机器上，机器数可以动态加 |
| 内存优先 | 中间结果尽量留在内存里，不写磁盘——这是它快的关键（下一节细讲） |
| 计算引擎 | 它只管"算"，不管"存"——数据通常放在 HDFS、本地文件系统或各种数据库里 |

对比记住这句：**HDFS 是仓库（存数据），Spark 是加工厂（算数据），两者配合但互不依赖**。Spark 甚至可以只读本机文件来跑（Local 模式，后面第三章会用到）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为 Spark 是"数据库" | Spark 不负责存储，是纯粹的**计算引擎**。数据要自己先放好（HDFS/本地文件），Spark 只是读进来算 |
| 以为 Spark 是"Hadoop 的升级版" | Hadoop 是一整套（存储 HDFS + 计算 MR + 调度 YARN），Spark 只取代了其中"计算"那一块。存储和调度它俩还经常共用 |
| 一上来就想搭"真集群" | 学习阶段 Local 模式单机就能跑（见第三章），不用先买 10 台服务器 |

@@point ③ 为什么 Spark 快：内存计算与 DAG
@@need 要解决什么
"Spark 比 MapReduce 快 100 倍"这个说法到处传，但它到底快在哪？如果你只知道"它快"，露出一个具体问题时（"为什么我这比 MR 还慢"）就答不上来——你得知道快的**机理**。

@@idea 核心思路
快的原因有两条，一条管"少跑路"，一条管"少读盘"：

**① DAG 调度，减少重复计算。** MapReduce 的每个任务算完必须落盘，下一步再读盘重算；Spark 把一连串计算画成一张**有向无环图（DAG）**，能合并的步骤直接"管道式"衔接——上一个算完立刻传给下一个，不落盘。

**② 内存优先（cache），中间结果留在内存。** 同一个数据要被反复用（比如迭代算法），Spark 支持把中间 RDD 缓存到内存，下次直接用，不用再从磁盘/网络重新读。

打个比方：MR 是流水线上"每道工序都要把工件搬回仓库再取出来"，Spark 是"工人排成一排，工件直接在手里传"。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| "快 100 倍"是绝对值，一开口就当真 | 快主要针对**迭代/多阶段计算**；如果只是一次简单的 map+reduce，Spark 未必比 MR 明显快（还要看数据量）。说"快"时要带上场景 |
| 以为 Spark 永远不读磁盘 | Spark 的**最终结果**还是要写盘（除非你自己缓存了中间结果），它省的是**中间结果的反复落盘** |

@@point ④ 离线批处理与实时流处理：Spark 能干的两种活
@@need 要解决什么
你听到两个词容易懵：**批处理**（把一整天的数据晚上一起算）和**流处理**（数据来一条算一条）。它们的代码长得完全不一样，需求也不同——先分清"我该用哪种"，才不至于把 Spark 用错地方。

@@idea 核心思路
| 类型 | 典型场景 | 延迟要求 | Spark 里谁负责 |
|---|---|---|---|
| 批处理（离线） | 昨天全网站 PV/UV、月度报表、模型训练 | 小时/天级，能等 | Spark Core（RDD）+ SparkSQL |
| 流处理（实时） | 实时大屏、异常告警、风控拦截 | 秒级，不能等 | Spark Streaming（微批）/ Structured Streaming |

关键认知：**Spark Streaming 不是"真正的逐条实时"，而是"微批"**——把 1 秒内到的数据攒成一小批再算，延迟在秒级。够用但不适合毫秒级场景（那种选 Flink，后面不展开）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为流处理是"来一条算一条" | Spark Streaming 是**微批**（micro-batch）：按固定间隔（如 1s）收集一批再算。要毫秒级真流才考虑 Flink |
| 不知道"实时大屏"该用谁 | 需求是"每秒刷新、秒级延迟"选 Streaming；需求是"每天出报表"选批处理，别拿流处理框架硬套离线需求（成本更高更难维护） |

@@point ⑤ 兼容一切数据源：Spark 的读写生态
@@need 要解决什么
真实项目里数据不会好心全放在一个地方：日志在 HDFS、业务表在 MySQL、同事给了个 JSON、老板又要导出 CSV。如果每换一个源头就得学一套新框架，这框架就没法用。你要的是一个**统一的读写入口**。

@@idea 核心思路
Spark 提供统一的 `DataFrameReader/Writer` 抽象：**换数据源只换一个 `format(...)` 参数**，读进来统一变成 DataFrame/RDD，之后写同一套处理逻辑。

```text
spark.read.format("json").load("s3://bucket/logs/")
spark.read.format("jdbc").option("url", "jdbc:mysql://...").load()
df.write.format("parquet").save("hdfs://.../out")
```

支持的来源非常广：**HDFS / 本地文件、JSON/CSV/Parquet/ORC、JDBC（MySQL 等）、Kafka、Hive 表、Elasticsearch**……所以"数据在哪"从来不是选 Spark 的理由，"**算得动、算得快**"才是。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为 Spark 只能读 HDFS | 本机文件、MySQL、Kafka、各种云存储都能读。学的时候用本地文件最省事 |
| format 写错大小写/单词 | 比如把 `parquet` 写成 `Parquet` 一般没事，但 `csv` 别写成 `CSV` 之外的拼写，报 `IllegalArgumentException: 遇到 `Unsupported class file major version` 是**JDK 版本太新**（Spark 3.2.1 不认 17+），不是 format 写错；format 拼错报的是 `Unable to find data source`` 类错误时先检查 format 字符串 |
| 读完一个 10GB JSON 想直接 show | `df.show()` 默认只打印 20 行但**整个文件还是要全读完**，数据大时先 `limit(100).show()` 或直接 SQL 过滤后再看 |

@@point ⑥ Spark 核心组件一览：五兄弟
@@need 要解决什么
你会在各种教程里看到 Spark Core、SparkSQL、Spark Streaming、MLlib、GraphX 这五个名字，傻傻分不清。需要一张"谁管什么"的地图，否则下文一出现 SparkSQL 你就不知道它和"Spark"什么关系。

@@idea 核心思路
它们不是五个独立软件，而是**一个核心 + 四个高层库**，全部基于同一套分布式底层：

| 组件 | 管什么 | 你会不会用到 |
|---|---|---|
| **Spark Core** | 最底层：RDD、调度、内存管理、容错 | ★ 必学，是地基 |
| **SparkSQL** | 用 SQL 风格处理结构化数据（DataFrame） | ★ 必学，日常最常用 |
| **Spark Streaming** | 把流切成一团团微批处理 | ☆ 按需，实时场景用 |
| **MLlib** | 机器学习算法库（分类、聚类、推荐……） | ☆ 按需 |
| **GraphX** | 图计算（社交关系、路径分析） | ○ 用到再看 |

记住这句话：**你写的 `spark.sparkContext` 是 Spark Core，`spark.read` 是 SparkSQL，`StreamingContext` 是 Streaming**——同一个程序里它们共享一个集群，互不干扰。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为 SparkSQL 是"另一个框架" | 它是 Spark 的**内置模块**，不是独立软件。你在 SparkSQL 里读的数据，底层还是 RDD 那套分布式机制 |
| 以为学完 Spark Core 才算"入门" | 现代 Spark **90% 的场景用 DataFrame/SQL 就够了**，RDD 更多用于理解原理和底层自定义。两条线都要懂，但别陷进 RDD 出不来 |

@@point ⑦ Spark vs Hadoop MapReduce：正面比较
@@need 要解决什么
教材总把 Spark 和 MapReduce 放一起比，你也总听说"Spark 取代 MR"，但运行时却分不清它们的边界。需要一张**对照表**，遇到"为什么不用 MR"的问题能直接答出来。

@@idea 核心思路
| 维度 | MapReduce | Spark |
|---|---|---|
| 计算模型 | 严格的 Map→Shuffle→Reduce 两阶段 | DAG 任意多阶段，可复用中间结果 |
| 中间结果存储 | 必须写磁盘 | 优先内存，可缓存 |
| 迭代/多轮计算 | 每轮都重读磁盘，巨慢 | 内存里反复用，快几个数量级 |
| 实时性 | 只有批处理 | 批 + 微批流 |
| SQL/ML/图 | 要配一堆外部组件 | 内置 SparkSQL/MLlib/GraphX |
| 容错 | 靠重算 | 靠血缘（Lineage）重算 + 可选 Checkpoint |

结论：**MR 是"能算"，Spark 是"算得又好又快还全面"**。新项目直接选 Spark，MR 你只需要知道它存在即可。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 面试问"Spark 为什么快"只答"内存" | 完整答案：中间结果内存化 + DAG 多阶段复用 + 分区并行。单答内存会被追问"还有呢" |
| 以为 Spark 永远比 MR 快 | 小数据/单次扫描场景 MR 差距不大甚至更快；Spark 优势在**迭代/多轮/交互** |
| 把"Spark 是 MR 的升级版"背下来 | 它俩是**不同计算模型**（DAG vs 两阶段），不是版本关系。能画出两者数据流差异才算真懂 |
| 实时场景也推荐 MR | MR 只有批。要流就用 Spark Streaming / Flink，别拿 MR 硬顶 |


@@point ⑧ Spark 的三种部署形态：本地 / 独立集群 / YARN
@@need 要解决什么
"部署"这个词劝退了很多初学者——感觉要搭机房。实际上 Spark 能**从小到大**三种跑法：自己电脑上练手、两台机器组独立集群、接入公司已有的资源调度平台。先看一张全景，后面三章逐一实操。

@@idea 核心思路
| 部署模式 | 在哪跑 | 什么时候用 | 复杂度 |
|---|---|---|---|
| **Local** | 就你一台电脑（可以就是 IDE） | 学习/调试/小数据 | ★ |
| **Standalone** | Spark 自带的主从集群（Master+Worker） | 中小型独立集群 | ★★ |
| **YARN** | 跑在 Hadoop 的资源调度平台上 | 公司已有 Hadoop 生态，统一资源管理 | ★★★ |

另外还有 Mesos/Kubernetes 等模式，实战中 **Local 练手 + YARN 上线**是最常见组合。后面第三、四、五章分别把三种模式跑一遍，那时你对"部署"的理解会从"吓人"变成"就是改个 `--master` 参数"。

@@note info 小预告
Local / Standalone / YARN 三种模式**唯一的代码区别就是 `spark-submit --master` 参数或 `master("local[2]")`**——这可能是你之后很长一段时间里"部署"二字的全部含义。别怕。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 部署前以为要配一堆东西 | Local 一行 `spark-submit --master local[2]` 就能跑，先把程序逻辑跑通再谈集群 |
| Standalone 和 YARN 选错 | 有 Hadoop 生态/要统一资源管理→YARN；独立小集群、不想依赖 Hadoop→Standalone |
| `--master` 参数写错不报错但跑不动 | 拼错会被当用户程序参数吞掉。先 `spark-submit --help` 确认，再用 `--master local` 试底 |
| 学习阶段直接上集群 | 本地能跑通=逻辑没问题；集群失败大多是环境/资源问题，先本地再集群，别倒过来 |
