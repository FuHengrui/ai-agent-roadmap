@@sub 阶段 15 · Hermes-Agent 自我进化的超级智能体　|　平台实操　|　难度 ★★☆

@@why 这一章在解决什么问题
第四章里 Agent 花 20 分钟跑完"搜→总结→建站"整套流程。**下次你再让它做类似的事，它会从头再来一遍——不会更快、也不会更稳**。这浪费的不只是时间，更是"进化"的机会：一次做好的流程，为什么不能沉淀下来变成"肌肉记忆"？

**技能（Skill）就是干这个的**：把一套"该怎么做"的流程写成结构化文档，放进技能库，Agent 遇到同类任务时主动加载这份"操作手册"，照着做就不会跑偏、不用从零摸索。技能加记忆，才是"自我进化"的真正引擎。

学完这一章，你能回答：**技能为什么比提示词更可靠、SKILL.md 的完整结构和 frontmatter 怎么写、技能怎么安装/列举/删除、什么叫"渐进披露"、以及一个真实的天气预报技能长什么样**。这一章学完，你就能动手创建自己的第一个技能。

@@note info 学习提示
技能是"给 Agent 写操作手册"，最怕写得玄。本章抓住一条主轴：**SKILL.md 是核心**——它用 frontmatter（元数据）+ 正文（流程）讲清"什么时候用、怎么用"。目录只是它的壳，内容才是魂。

@@point ① 为什么是技能，而不是靠提示词
@@need 要解决什么
"告诉 Agent 怎么做"有很多种方式：每次在提示词里写一遍、写进 SOUL、或者写进 AGENTS.md——为什么 Hermes 偏偏搞了个"技能"机制？

@@idea 核心思路
对比一下四种"教 Agent"的方式，优劣立现：

| 方式 | 问题 |
|---|---|
| 每次在提示词里手写步骤 | 重复劳动，还容易漏步骤 |
| 写进 SOUL.md | SOUL 只该放人格（第 5 章），塞流程会污染身份 |
| 写进 AGENTS.md | 全局生效，但对"特定任务专用流程"太重、太啰嗦 |
| **技能（Skill）** | **按需加载**：只在任务匹配时载入手册，平时不占上下文 |

技能的三重优势：**可复用**（一次编写多次使用）、**可分享**（在网络上共享技能）、**按需加载**（渐进披露，省 token 不干扰日常对话）。这就是"进化"的载体——做过的优质流程沉淀下来，越用越多。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 想省事继续把流程写进提示词/SOUL | 提示词重复累赘、SOUL 污染人格；技能是正解，尤其复杂多步流程 |
| 以为技能必须自己写 | 可以安装社区技能（hermes skills install），也可以只写给自己用（~/.hermes/skills/） |
| 技能写得太啰嗦 | 技能是"手册"不是论文；步骤清楚、边界明确即可，太长反而稀释重点 |

@@point ② Skill 的本质：带元数据的结构化 Markdown 文件
@@need 要解决什么
技能到底长什么样？是脚本？是代码？还是一个文件夹？需要从物理形态上认识它。

@@idea 核心思路
**技能的本质是一个 Markdown 文件（SKILL.md）**，放在技能库目录里。它的"结构化"体现在：

```text
SKILL.md 文件 = frontmatter（元数据头） + 正文（怎么做的说明）
```

- **frontmatter**：`---` 包裹的 YAML 头，包含 name（技能名）、description（什么时候用、怎么用——**给 Agent 看的说明书摘要**）等字段；
- **正文**：Markdown 写的操作说明、流程步骤、示例。

物理落点：`~/.hermes/skills/` 目录（个人技能库），每个技能一个子目录。**安装网络技能也会落到这里**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为技能是 .sh/.py 脚本 | 主体是 **MD 文档**（必要时可附脚本，但核心是说明）；脚本只是文档里可能指引的帮手 |
| 以为 frontmatter 可有可无 | description 是 Agent **判断何时加载**技能的依据，写不好=技能永远不会被主动使用 |
| 找不到自己创建的技能 | 确认放在 ~/.hermes/skills/<技能名>/SKILL.md，目录名与 frontmatter 的 name 保持一致 |

@@point ③ frontmatter 元数据：技能的"身份证"
@@need 要解决什么
技能文件的头部（frontmatter）到底该写哪些字段？每个字段什么意思？写错会怎样？

@@idea 核心思路
以 SKILL.md 示例为骨架（文件名必须大写，Linux 区分大小写）：

```yaml
---
name: my-skill
description: 什么时候用、能做什么、怎么用（给 Agent 看的一段摘要）
---
```

核心字段两个：

| 字段 | 作用 | 写不好会怎样 |
|---|---|---|
| **name** | 技能的唯一标识（目录名一致） | Agent 无法索引/加载它 |
| **description** | 告诉 Agent"什么任务匹配这个技能、用它做什么" | description 太泛或缺失，Agent 永远不会主动调用它 |

建议描述格式（让 Agent 一眼明白）：**"当用户需要 <场景> 时使用本技能，它帮助 <结果>，使用方式 <要点>。"** 一条好的 description，胜过正文写一万字。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| description 写"这是一个帮我做事的技能" | 空话无法匹配任务场景；要写清"什么时候用"（如：当用户要求查询天气时） |
| name 和目录名不一致 | 加载会失败；**目录名=name 字段**是对齐铁律 |
| 正文一堆、frontmatter 空白 | 先写清楚 head（name+description），再写 body——head 才是被检索的入口 |

@@point ④ 正文：把"怎么做"写成步骤清晰的说明
@@need 要解决什么
frontmatter 是门牌，正文才是内容。正文写什么风格、什么结构，Agent 才能"照着做"？

@@idea 核心思路
技能正文是**面向 Agent 的操作说明**，风格要点：

| 正文要素 | 说明 |
|---|---|
| 步骤化 | 拆成清晰的执行步骤，别写散文 |
| 具体化 | 给出路径、命令、判断标准 |
| 示例化 | 关键的调用方式给示例代码块 |
| 边界化 | 写清"什么情况适用、什么情况不适用" |

以天气预报技能的正文为例：说明"使用什么 API、参数怎么填、返回怎么整理成回答、获取失败怎么办"——读完之后，**没做过天气任务的 Agent 也能照着完成**。这就是技能"把经验固化"的价值。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 正文写成"回忆录"（讲自己当时怎么做的） | 要写成"通用操作手册"，让任何 Agent 在没有你的经验时也能照做 |
| 步骤含糊（"解析返回数据"） | 要具体到"读取 JSON 的 result.temperature 字段"这个粒度 |
| 边界不写清楚 | Agent 拿不准就用错场景；写"适用于X，不适用于Y"防误用 |

@@point ⑤ 技能库的目录结构：两个目录 + 一个启用开关
@@need 要解决什么
技能不止一个，它们存放在哪？"已安装技能""启用技能""内置技能"这些说法对应什么物理位置？

@@idea 核心思路
两个目录 + 一个开关，各自角色：

| 目录 | 角色 | 内容 |
|---|---|---|
| `~/.hermes/skills/` | **已安装技能的库** | 所有可用技能的存放地 |
| `/usr/share/hermes/skills` | 系统级技能目录（随安装方式而定，普通安装一般用不到） | 随安装包自带/共享的技能 |
| `~/.hermes/config.yaml` 的 skills 配置 | **启用开关** | 已启用技能的列表 |

理解链路：**技能先 install 进库，再 enable 启用，才可被 Agent 使用**。库是"仓库"，配置是"上架的货架"——上架的才卖（加载）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为技能放进库=自动启用 | 还要在配置里 enable；install 后按提示启用，别漏这一步 |
| 把系统目录当个人目录改 | 系统目录归安装包管（升级会被覆盖）；个人技能一律放 ~/.hermes/skills/ |
| 技能"消失"了先怀疑被删 | 先查 config.yaml 的启用列表，经常是 enable 丢了不是文件丢了 |

@@point ⑥ 三组技能管理命令
@@need 要解决什么
安装、列举、删除技能的命令长什么样？有没有类似"应用商店"的机制？

@@idea 核心思路
三组核心命令：

```bash
hermes skills list              # 列出已安装的技能
hermes skills install <名字>    # 通过网络安装技能
hermes skills remove <名字>     # 移除已安装的技能
```

| 命令 | 用途 | 备注 |
|---|---|---|
| `hermes skills list` | 查看技能库现状 | 确认装了啥、漏了啥 |
| `hermes skills install <技能名>` | 从网络技能市场安装 | 装完注意安全扫描结果 |
| `hermes skills remove <名字>` | 卸载技能 | 删除 `~/.hermes/skills/` 下对应的子目录 |

再配合 `hermes skills create <名字>` 创建空白技能模板（有的话），就凑齐"查-装-建-删"全流程。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| install 后立即测试找不到技能 | 检查是否**启用**（config.yaml skills 列表）并**重启会话**让技能索引生效 |
| remove 名字写错提示失败 | 先用 `hermes skills list` 拿到准确名字再删 |
| 安装来源不明的技能 | 安装过程/使用前留意安全扫描；来源可疑就装到沙箱或拒绝（安全第一） |

@@point ⑦ 渐进披露：技能不占日常对话的"内存"
@@need 要解决什么
技能库可能装了几十个技能，如果每个技能的全文都常驻在系统提示词里，token 早就爆了。Hermes 怎么处理？

@@idea 核心思路
答案：**渐进披露（progressive disclosure）**。

机制拆解：

| 阶段 | 发生了啥 |
|---|---|
| 日常对话 | 只有技能**名称+一句话描述**出现在上下文（不载入正文） |
| 任务匹配 | Agent 判定当前任务命中某技能 → **按需加载**该技能的完整正文 |
| 任务结束 | 技能不常驻，只在使用时进入上下文 |

效果：**装 100 个技能，日常对话也只背 100 行摘要；用到哪个才把哪个的全文调入**。这就是"技能系统不拖垮长对话"的秘诀，也解释了为什么 frontmatter 的 description 那么关键——匹配靠的就是那几句话。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 对话里看不到技能内容就以为没装 | 渐进披露本来就**只展示摘要**；触发了对应任务才加载全文 |
| description 写太泛导致该用技能时没加载 | 描述要具体到任务场景词，匹配不上=技能永远沉睡在库底 |
| 以为多个技能可同时全文常驻 | 常驻的只有摘要；同一任务可能加载多个技能，但都是"用到才载" |

@@point ⑧ 技能安装的两条路径：网络 / 本地
@@need 要解决什么
除了 `hermes skills install <名字>` 从网络装，自己写的技能怎么让 Agent 用上？两条路径都要会。

@@idea 核心思路
两条路径殊途同归——都进技能库然后启用：

**路径 A：网络安装**
```bash
hermes skills install <技能名>   # 自动下载到 ~/.hermes/skills/
```

**路径 B：本地创建**
```text
1. 在 ~/.hermes/skills/ 下新建目录，如 taiyuan-weather/
2. 目录内创建 SKILL.md（frontmatter + 正文）
3. 确保 name 与目录名一致
4. 用 `hermes skills list` 确认已装，再到 `~/.hermes/config.yaml` 的 skills 列表里启用
```

天气预报技能就是路径 B 的实例：`~/.hermes/skills/taiyuan-weather/SKILL.md`，目录名=taiyuan-weather。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 手动建好的技能"不显示" | 检查三处：目录名=name 字段？文件是 SKILL.md？config.yaml 已 enable？ |
| 网络安装碰壁（网络/权限） | 退回本地创建：自己写一样可用，还能完全掌控内容 |
| 把 SKILL.md 直接丢在 skills 根目录 | 每个技能要**独立子目录**里放 SKILL.md，直接放根目录无法识别为独立技能 |

@@point ⑨ 实战拆解：天气预报技能完整示例
@@need 要解决什么
光有规则没有活例，还是不知道"好技能长什么样"。下面用一个完整的天气预报技能（太原），逐行解剖它的结构。

@@idea 核心思路
`taiyuan-weather/SKILL.md` 的真实结构（逻辑还原，非逐字）：

```markdown
---
name: taiyuan-weather
description: 当用户需要查询太原实时天气时使用。它使用和风天气 API 获取温度、湿度、
              风力和天气状况，并整理成简洁的中文回答。使用方式：先向用户询问城市
              确认（如已明确则跳过），再调用 API，最终以指定格式返回。
---
# 太原天气预报
## 查询流程
1. 确认城市（默认太原，可换城市则换）
2. 调用和风天气 API：请求示例 <curl ...>
3. 解析返回 JSON 的 temperature / text / humidity / wind 字段
4. 组装回答：<整理为 "城市+当前温度+天气状况+湿度+风力" 的中文一句话>
## 注意事项
- API Key 从环境变量读取，不写入代码或记忆
- 接口失败时重试一次，仍失败则告知用户"暂时无法获取"
```

**解剖这个示例的三点精华**：description 三件套（什么时候用/做什么/怎么用）齐全；正文步骤化+字段化；**API Key 从环境变量读取**——安全习惯直接写进流程。这就是"能直接照着跑"的技能。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把真实 API Key 写进 SKILL.md | 技能文件不该含凭据：从环境变量读取（示例就是这么教的），否则分享技能=泄漏密钥 |
| 正文只写"查天气"不写流程 | 要写"用什么 API、读哪些字段、怎么组装回答"，一次性还原全过程 |
| 技能写死只服务太原 | description 写"太原"而正文支持换城市会冲突；要么限定死，要么 description 写明"可换城市" |

@@point ⑩ 技能与工具集里 skills 的关系：管理工具 vs 内容仓库
@@need 要解决什么
上一章工具集清单里有个 "skills 工具集"，本章又讲"技能系统"，名字撞了——到底谁是谁？

@@idea 核心思路
两者是"开关"和"仓库"的关系，不是一套东西：

| 概念 | 是什么 | 位置 |
|---|---|---|
| **skills 工具集** | 一个开关：是否允许 Agent 加载技能 | 第六章工具集管理（/tools enable skills） |
| **技能系统** | 技能内容的存储与加载机制 | ~/.hermes/skills/ 技能库 |

理解链：**skills 工具集关着 → Agent 无论如何都不会加载任何技能；skills 工具集开着 → 技能库里的内容才可能被渐进披露加载**。所以调试技能时，第一件事是查 skills 工具集开没开。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 技能写了、装了、启用了但 Agent 就是不调用 | 先查 skills 工具集是否开启——这是最容易被忽略的前置开关 |
| 在 skills 工具集里找"技能内容" | 工具集里只有开关；内容在 ~/.hermes/skills/ 目录 |
| 把 skills list 和 /tools list 混看 | skills list=技能清单；/tools list=工具开关；两者用途不同，看错会误判 |

@@point ⑪ 技能应用的市场向思维：分享与被分享
@@need 要解决什么
技能的最大魅力在于生态：别人写的技能我能不能直接用？我的技能能不能给别人用？跨机器怎么带？

@@idea 核心思路
技能的**可移植性**是官方明说的优点：

| 场景 | 怎么做 |
|---|---|
| 用别人的技能 | `hermes skills install <名字>`，从网络技能库安装 |
| 分享自己的技能 | 把技能目录（SKILL.md）发布/拷贝给他人，对方放入自己的 ~/.hermes/skills/ 并启用 |
| 跨机器迁移 | 直接把 ~/.hermes/skills/ 整体拷贝到新机器即可（注意环境变量依赖） |

本质：**技能 = 一个可复制的知识单元**。正因为 SKILL.md 是纯 Markdown+约定结构，它天然可分享、可版本管理（把技能目录放进 git 也行）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 直接拷贝技能目录但缺依赖 | 技能正文里用到的 API Key/环境变量要一并说明（写进技能正文的"注意事项"）；只拷文件不够 |
| 安装社区技能不检查内容 | 任何"可执行流程"都有风险面：安装前扫一眼正文、别装来路不明的技能 |
| 以为技能只能官方渠道 | 技能是开放格式，个人、社区、官方都能做；关键是可信度自评 |

@@point ⑫ 从安装到实战的完整闭环
@@need 要解决什么
把本章所有动作串成一个"技能实战闭环"：从装一个技能到验证它真的被用起来，一共几步？

@@idea 核心思路
技能实战五步闭环：

```text
① 安装/创建   hermes skills install <名字>  或手动建目录+SKILL.md
② 检查入库    hermes skills list            确认已出现在技能库
③ 启用开关    config.yaml 的 skills 列表    确保 enable 且 skills 工具集开启
④ 触发验证    新会话里下达匹配任务（如"今天太原天气"）
⑤ 效果复核    观察 Agent 是否按技能正文的流程执行（API 调用/格式输出）
```

**关键提醒**：验证时开**新会话**——技能在会话开始时索引；老会话可能看不到新技能。闭环跑通，你就掌握了"技能的安装、创建、触发、验证"全套能力。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 在旧会话里测试永远不生效 | 新装/新改技能后**新开会话**再测（索引在会话启动时生成） |
| 触发测试的任务描述与技能 description 不匹配 | 用技能 description 里的场景词去下指令，匹配率最高 |
| 闭环里漏了"启用开关"一步 | 装库≠启用，四步缺二（enable+工具集）等于白装；把五步读一遍再测 |

@@summary
这一章你掌握了 Agent 的"肌肉记忆"系统：

| 拿到了什么 | 为什么要紧 |
|---|---|
| **技能=结构化 MD**：SKILL.md = frontmatter（name+description）+ 正文（流程） | 技能的本质形态，看破"技能=手册"不神秘 |
| **description 是关键**：写清"什么时候用、做什么、怎么用" | 渐进披露靠它匹配；description 差=技能永远睡大觉 |
| **三目录分工**：~/.hermes/skills/（库）+ 系统目录（共享）+ config.yaml（启用） | 装库≠启用≠可加载，三环节缺一不可 |
| **命令三件套**：`hermes skills list / install / remove` | 查、装、卸全流程，附 create 可建空模板 |
| **渐进披露机制**：日常只载摘要、命中任务才载全文 | 技能再多也不拖垮对话 token，理解"为何不常驻" |
| **天气预报实例**：description 三要素 + 步骤化正文 + API Key 走环境变量 | 一份"照着跑"的标准技能模板，安全习惯内建 |
| **五步实战闭环**：安装→入库→启用→新会话触发→效果复核 | 从装到验证的完整可操作流程 |

一句话记住本章：**技能=贴好说明书的操作手册——放在 ~/.hermes/skills/ 的 SKILL.md 里，description 写清楚什么时候用，新会话触发即生效；一次固化，终身复用。**
