@@why 这一章在解决什么问题
你部署好了集群，但真正要开始写数据处理代码时，第一个问题来了：**"数据"在 Spark 里到底长什么样？** 你手里是一堆文本文件、几百行日志，怎么把它们变成"能分布到 100 台机器上并行处理"的东西？直接丢给集群？显然不行。

学完这一章，你能：**说清 RDD 五大特性各自的意义，并用两种方式（并行化集合/读文件）创建出 RDD**。

@@point ① 为什么需要 RDD：数据要"分布"却要"像本地一样用"
@@need 要解决什么
让 100 台机器同时处理一份大数据，最麻烦的问题是：**数据散在各机器上，你怎么把它当"一个整体"来编程？** 如果让你自己写分布式程序，你得自己管理"哪块数据在哪台机器、怎么拆、怎么合并、某台机器挂了怎么办"——光想想就头大。你需要一个**让分布式数据用起来像本地集合一样自然的抽象**。

@@idea 核心思路
RDD 就是为这个而生的：**你看到的是一个"逻辑上的大集合"，Spark 在背后帮你管它是怎么被切成分区、放在哪台机器上的**。

```text
你的视角：              Spark 的视角：
rdd.map(...)            把 map 逻辑发到每个分区所在机器，每台只处理自己那部分
rdd.filter(...)         同理，分布式执行
rdd.collect()           各分区算完 → 汇总回来
```

就像你用 Python 的 `list` 一样写代码，但底层数据是分布在集群上的。**"分布"你几乎感觉不到**——这就是 RDD 存在的最根本理由：封装分布式细节，暴露统一 API。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为 RDD "装"着数据本身 | RDD 里封装的是**计算逻辑和数据的位置**，不是把所有数据都放到某个内存里。这也解释了为什么它能"无限大"——数据在磁盘/分布式存储上 |
| 以为"用了 RDD 就等于并行" | RDD 只是给了**并行计算的可能**（有分区）；真正并行度由分区数和资源决定，见内核章 |
| 想把 RDD 当普通数组 `rdd[0]` | RDD 没有下标访问！它面向"分布式处理"，取数据用 `first()/take(n)/collect()`（行动算子），这是和本地集合最大的使用差异 |

@@point ② RDD 定义：弹性、分布式、数据集
@@need 要解决什么
"RDD 是弹性分布式数据集"——九个字你背得下来，但每个词啥意思？拆开讲才能建立真正的理解，也不至于面试被问"弹性指什么"时卡壳。

@@idea 核心思路
RDD（Resilient Distributed Dataset）拆开看：

| 词 | 含义 |
|---|---|
| **Resilient（弹性）** | 数据既能放内存也能放磁盘，内存不够自动溢出到磁盘（StorageLevel 可配），不会因为内存小就崩 |
| **Distributed（分布式）** | 数据切成多个分区，分布在集群不同节点上 |
| **Dataset（数据集）** | 它是一个"数据集合"的抽象，里面装元素，像集合一样可遍历、可变换 |

讲义给出的完整定义：**RDD 是 Spark 中最基本的数据抽象，代表一个不可变、可分区、里面的元素可并行计算的集合**。

四个要点拆开：

| 要点 | 白话 |
|---|---|
| 不可变 | RDD 创建后不能改，想变只能产生**新的 RDD**（这保证了血缘链，故障时能重算） |
| 可分区 | 数据按分区存储，分区是并行计算的基本单元 |
| 元素可并行计算 | 每个分区独立计算，天然并行 |
| 计算逻辑封装 | RDD 记的是"怎么算"，不是"数据副本"（见下一知识点） |

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把"弹性"理解成"自动扩容" | 弹性指的是**存储弹性**（内存↔磁盘自由切换），不是集群扩缩容。词是同一个，别答错含义 |
| 以为 RDD 可变、能往里面 add | 不可变是 Spark 分布式容错的基石：只有不可变才能记录"计算链"，挂了按链重放。想"改"就生成新 RDD |
| 以为每个 RDD 都是数据快照 | RDD 大部分时候只是**计算逻辑**（惰性的），真正数据算出来发生在 Action 触发时——这正是后面惰性求值的基础 |

@@point ③ RDD 是"计算逻辑"不是"数据本体"
@@need 要解决什么
新手最容易的误解：创建 RDD 时数据就"进内存"了。但实际上：**`sc.textFile(...)` 只是登记了"从哪读、怎么读"**，一行数据都没读进来。为什么这样设计？理解这点，你会少困惑"为什么没执行"。

@@idea 核心思路
RDD 的本质是**对数据的描述（计算计划）**，而不是数据本身。看这个过程：

```python
# 这三行只是"登记计算计划"，没有真正读文件
lines = sc.textFile("data/logs.txt")
words = lines.flatMap(lambda l: l.split(" "))
pairs = words.map(lambda w: (w, 1))

# 直到这里（行动算子），Spark 才开始真正干活
counts = pairs.reduceByKey(lambda a, b: a + b).collect()
```

这个设计的好处：

1. **省内存**：计划堆积时数据不占内存，只有要结果时才计算
2. **可优化**：Spark 可以把多个转换合并成一条高效执行链（pipeline）
3. **可重放**：记录的"如何计算"就是血缘，出问题按图重算

关键认知：**RDD 是"菜谱"，不是"菜"**。你写转换算子是在写菜谱，`collect()` 才是把菜做出来。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 写了 `rdd.map(...)` 后立刻 print 没数据 | 完全正常：转换算子惰性执行。必须有行动算子触发。想 debug 中间结果 → `rdd.take(10)` |
| 以为创建 RDD 就全读进内存了 | `textFile` 只是记录路径，分区读取发生在 Action 时。这也导致"文件不存在"的报错可能延迟到 Action 才爆 |
| 想"看 RDD 里有啥"用 `rdd` 直接打印 | 打印出来的是 RDD 对象描述（分区数等），不是数据。要看数据必须 `take/collect/first` |

@@point ④ 五大特性总述：先记框架再逐个打透
@@need 要解决什么
Spark 源码里 RDD 有"五特性"，外面讲课都是这个框架。先给一张**总表**再逐个拆解——你之后看源码、答面试题、诊断性能都靠这张表。

@@idea 核心思路
| # | 特性 | 一句话 | 必修性 |
|---|---|---|---|
| 1 | **有分区** | 数据切块，分区是存储和计算的最小单元 | 必选 |
| 2 | **计算方法作用到每个分区** | 每个分片独立执行同一套函数 | 必选 |
| 3 | **RDD 之间有依赖关系** | 父 RDD → 子 RDD，构成 DAG，可容错重算 | 必选 |
| 4 | **KV 型 RDD 可有分区器** | 可按自定义规则把 key 分到指定分区 | 可选 |
| 5 | **分区尽量靠近数据** | 数据在哪台机器，计算就往哪台调度（本地性） | 可选 |

前三个特性每个 RDD 都有，后两个是可选增强。**记忆锚点**：`分区 + 计算 + 依赖 + 分区器 + 本地性`——正好对应"存哪、怎么算、怎么容错、怎么分、贴数据"五大问题。

@@point ⑤ 特性 1：RDD 是有分区的
@@need 要解决什么
"分区"是 Spark 里出现频率最高的词之一，但到底什么是分区？为什么非要有分区？本点用最直观的例子讲清：**分区 = 把一个逻辑大集合物理切成 N 块**。

@@idea 核心思路
分区（Partition）是 RDD 数据存储的最小单位。举例：一个 RDD 里有 `1,2,3,4,5,6`，切成 3 个分区：

```text
分区0: [1, 2]
分区1: [3, 4]
分区2: [5, 6]
```

用算子验证分区：

```python
# 创建时指定分区数
rdd = sc.parallelize([1,2,3,4,5,6], 3)
print(rdd.getNumPartitions())    # 3

# glom 展示每个分区里的数据
print(rdd.glom().collect())      # [[1,2], [3,4], [5,6]]
```

分区存在的意义：**并行度 = 分区数**。3 个分区就能被 3 个核/任务同时处理；分区越多，并行潜力越大（但太多调度开销也大）。理解分区，是你后面调优的第一把钥匙。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为分区数越多越快 | 分区数超过可用核数后会排队，还有调度开销。理想是"分区数 ≈ 核数 × 2~3" |
| 以为分区里数据一定均匀 | 默认 hash/范围分区可能不均，数据倾斜时某些分区任务慢——这是后面调优重点 |
| `getNumPartitions` 和看到的 Task 数对不上 | 某些算子执行时内部会重新分区（如 join/groupBy），看到的分区数以实际执行为准 |

@@point ⑥ 特性 2 与 3：计算作用到每个分区 + RDD 间有依赖
@@need 要解决什么
特性 2、3 解释了两个核心机制：**"怎么算"和"怎么容错"**。它们连在一起看才说得通：计算作用在分片上，才能并行；RDD 间有依赖（血缘），才能在节点挂了之后**按图重算**。

@@idea 核心思路
**特性 2：计算方法会作用到每个分区上。** 你定义的 map/filter 函数，会被 Spark 复制到每个分区所在的机器，**每个分区独立执行**。伪代码：

```text
for part in rdd.partitions:
    part.map(my_func)   # 每个分区都执行同一套函数
```

**特性 3：RDD 之间存在依赖关系。** 转换算子产生新 RDD 时，新 RDD 会记录"我是从哪个旧 RDD 来的、经过什么变换"：

```text
textFile ──flatMap──> words ──map──> pairs ──reduceByKey──> counts
（父RDD）              （子RDD）      （孙RDD）            （最终）
```

这条链叫**血缘（Lineage）**，价值是：**某个分区计算失败或节点挂了，Spark 可以顺着血缘找到父 RDD，只重算丢失的部分**——这是 Spark 容错的核心，也是"不可变"设计的回报。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为容错=把 RDD 复制多份 | Spark 默认**不复制数据**，靠血缘重算（更快更省空间）。缓存/Checkpoint 是另加的手段 |
| 依赖有宽窄之分还不清楚 | 详见内核章：窄依赖（父分区→一个子分区，不 shuffle）、宽依赖（父分区→多个子分区，要 shuffle）。特性 3 这里先知道"有依赖"即可 |
| 血缘链越长越担心 | 链长说明计算步骤多（正常）；但长链重算代价大，所以长链关键节点用 cache/checkpoint 打断 |

@@point ⑦ 特性 4 与 5：分区器与数据本地性（可选特性）
@@need 要解决什么
剩下两个特性"可选"，但实战中**数据倾斜、性能慢**的根因往往就在这里。宁可现在花 5 分钟理解，别等任务跑不动了才回头看。

@@idea 核心思路
**特性 4：KV 型 RDD 可以有分区器。** 当数据是 `(key, value)` 元组时，可以指定用什么规则决定"这个 key 进哪个分区"：

| 分区器 | 规则 | 用途 |
|---|---|---|
| `HashPartitioner`（默认） | `key.hashCode() % 分区数` | 通用，按键哈希散列 |
| `RangePartitioner` | 按键范围分段 | 排序、范围查询友好 |
| 自定义 Partitioner | 自己写函数返回分区号 | 特殊业务规则 |

```python
# 用分区器把数据按规则重分区
rdd = rdd.partitionBy(3, partitionFunc)   # 自定义规则
```

**特性 5：分区尽量靠近数据所在的服务器。** 初始 RDD 读 HDFS 文件时，Spark 会参考 HDFS 块的存储位置，**把分区规划在数据所在的节点上**——计算在本地读数据，不走网络。这就是"数据本地性（locality）"。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 自定义分区器返回值越界 | 返回的分区号必须 `0 <= n < 分区数`，越界直接报 `IllegalArgumentException`。讲义特意提醒：编号从 0 开始，别超总数 |
| 以为所有 shuffle 都默认 hash | reduceByKey/groupByKey 默认 HashPartitioner，但你可以用 `partitionBy` 改成自定义分区，控制数据落点 |
| 本地性总是 100%？ | 理想是"计算挨着数据"，但资源不够或 shuffle 后数据移动会导致部分任务变级（PROCESS_LOCAL/RACK_LOCAL）。UI 的 locality level 可见 |

@@point ⑧ 创建 RDD 的两条路：并行化集合 / 读文件
@@need 要解决什么
书上说 RDD 创建有两种方式：并行化集合、读取文件。但什么时候用哪种？为什么有 `makeRDD` 又有 `parallelize` 两个一样的？本点把创建这件事一次性讲清，附分区数选择的经验。

@@idea 核心思路
**方式一：并行化集合创建（把本地集合转 RDD）**

```python
# 把 Python/Scala 的本地集合变成分布式 RDD
rdd1 = sc.parallelize([1, 2, 3, 4, 5], 2)      # 指定 2 个分区
rdd2 = sc.makeRDD([1, 2, 3, 4, 5], 2)          # 等价，内部就是 parallelize
```

**方式二：读取文件创建（最常用）**

```python
rdd = sc.textFile("data/words.txt")                 # 读本地/分布式文件
rdd = sc.textFile("data/words.txt", minPartitions=3) # 指定最小分区数
rdd = sc.textFile("hdfs://node1:9000/input/")        # 读 HDFS 路径/目录
```

分区数怎么定（经验）：

- `parallelize`：默认用推荐并行度，可显式传分区数
- `textFile`：HDFS 文件默认按块数分（一个块≈128MB 一个分区）；`minPartitions` 是**最小**值，仅供参考

```text
结论：测试数据并行化集合；真实数据处理用 textFile。
makeRDD 只是 parallelize 的别名，别为了两个名字纠结。
```

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 知道 `textFile` 但不知道"默认分多少区" | HDFS 按块（128MB/块）分；本地文件按块大小估算，但总分区数有限制。想控制就显式传 `minPartitions` |
| 设了 `minPartitions=100` 实际出来 86 | 讲义明确讲过：**最小分区数是参考值，Spark 会按数据量自行调整**（不会为 1 字节文件硬造 100 分区）。这是正常行为不是 bug |
| 以为读目录必须逐个列文件 | `textFile("hdfs://.../input/")` 读**整个目录**下所有文件（会合并），用通配符可精细控制：`"input/*.txt"` |
| `parallelize` 与 `makeRDD` 纠结 | 完全等价，前者是原生 API，后者是 SparkContext 的便捷封装。用哪个都行，别当成两种机制 |
