@@point ① 需求先行：先想清楚要解决谁的什么问题
@@need 要解决什么
接到一个需求，最容易犯的错是**直接想功能**："要做登录、要做上传、要做列表……"

这样想出来的东西，功能都做了，用户却不一定用。因为**你从头到尾没问过：他到底卡在哪？**

@@idea 核心思路
需求文档的写法值得学，它**从头到尾没提一个技术名词**，都是人话。

第一步：说清「谁的什么痛」
> 开会容易，会后难。一场半小时的会，往往要再花二十分钟重听录音、整理纪要、一条条扒待办——既费时间，又容易漏掉关键事项和紧急任务。

第二步：把痛翻译成**用户故事**（不是功能清单）
> **作为**参会者，**我希望**上传录音后系统自动处理，**这样**我不用手动去转写、去总结。

注意这个句型：**「作为谁 + 我希望什么 + 这样我能得到什么好处」**。它强迫你回答"为什么"，而不只是"做什么"。

第三步：用户故事 → 功能需求

| 用户故事（要什么） | 功能需求（做什么） |
|---|---|
| 注册账号并安全登录，数据只属于我 | 5.1 账号系统 |
| 上传录音后自动处理，不用手动 | 5.2 录音上传 + 5.3 语音转写 |
| 随时看到摘要和待办清单 | 5.4 智能摘要与待办提取 |
| 紧急的事能被识别并及时提醒 | 5.5 紧急事项提醒 |
| 回看历史会议，知道处理进度 | 5.6 历史会议查询 |

**5 个用户故事 → 6 条功能需求**。这个过程就是"需求先行"。

第四步：明确**不做什么**（非功能需求）
> 异步处理：转写与分析较耗时，**必须后台处理，不能让用户在前端干等**。

这一句看着像技术细节，其实是**需求**——它规定了用户体验的底线。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 功能都做完了，用户却说"不好用" | 直接从功能清单开工，没回到"谁的什么痛" |
| 需求写着写着变成技术方案 | 把"要异步处理"当成需求，却没写"为什么必须快" |
| 做了一大堆没人要的功能 | 没做第四步——没定义"不做什么" |
| 需求一变就全盘返工 | 用户故事和技术方案混在一层，改一个牵动全部 |

@@point ② 账号系统：为什么会议内容必须私有
@@need 要解决什么
会议录音里有薪资、有人事、有还没公开的商业计划。**这是别人不能看的东西。**

"私有"不能靠"没人猜得到链接"来保证——那叫隐藏，不叫安全。**谁能看到哪条会议，必须由系统说了算。**

@@idea 核心思路
三个决定，每一个都在回答一个具体的担心。

**决定一：密码不能明文存**

就算数据库被人拖走了，也不能让人直接拿到密码。

```python
# bcrypt 单次哈希的密码上限是 72 字节，超出部分会被静默截断
_BCRYPT_MAX_BYTES = 72

def hash_password(plain_password: str) -> str:
    """用 bcrypt 对明文密码加盐哈希，返回可入库的字符串。"""
    pwd_bytes = plain_password.encode("utf-8")[:_BCRYPT_MAX_BYTES]
    hashed = bcrypt.hashpw(pwd_bytes, bcrypt.gensalt())  # 默认 cost=12
    return hashed.decode("utf-8")
```

三个词要理解：

| 词 | 意思 | 为什么需要 |
|---|---|---|
| **哈希** | 单向变换，**算不回去** | 加密能解回来，哈希不能——**系统自己也不知道你密码是什么** |
| **加盐** | 每个人用不同的随机值 | 否则两个人密码一样，存出来就一样，一张"彩虹表"能全破 |
| **cost=12** | 故意算得慢 | 正常登录慢几毫秒无感，暴力破解要慢几万倍 |

**决定二：登录后发一张"票"，服务端认票不认人**

```python
payload = {
    "sub": subject,                  # 用户 ID
    "iat": now,                      # 签发时间
    "exp": now + expires_delta,      # 过期时间
}
return jwt.encode(payload, settings.jwt_secret_key, algorithm=settings.jwt_algorithm)
```

票里**只放这三样**。不放用户名、不放权限、不放密码——因为票是存在浏览器里的，**谁拿到谁就能用**。

服务端验票时不能只有签名，还要校验有效期，并且**必须指定算法列表**：

```python
jwt.decode(token, settings.jwt_secret_key, algorithms=[settings.jwt_algorithm])
```

> **为什么 `algorithms` 要写成列表？**
> 这是防「算法混淆攻击」。如果允许 token 自己声明 `alg: none`，攻击者就能伪造任意用户的票。

**决定三：查数据时把"只能查自己的"写进查询条件**

```python
Meeting.filter(id=meeting_id, user=current_user).first()
```

别人的会议**根本查不出来**，直接 404。而不是"先查出来，再判断是不是自己的，不是就返回 403"。

> **为什么是 404 而不是 403？**
> 403 等于告诉对方"这条记录存在，只是你不能看"——**这本身就是信息泄露**（别人可以靠 403/404 的差别探出你有哪些会议 id）。
> 404 什么都不承认。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 用户改了密码，旧 token 还能用 | JWT 是无状态的，签发之后就吊销不了。要支持"踢下线"就得加 `jti` + 黑名单 |
| 输入不存在的用户名，登录**明显更快**返回 | 代码在用户不存在时短路了 bcrypt 校验。bcrypt 要算几十毫秒，这个时间差**能被测出来**，从而枚举账号 |
| 账号被管理员禁用，用户却卡在"所有操作都报错" | 后端返回 403，但前端拦截器**只处理了 401**，没有 403 分支，用户既没被登出也看不到原因 |
| token 存在 localStorage，被人注入脚本偷走 | localStorage 对页面里任何脚本都完全开放。更稳的是 httpOnly Cookie |

@@point ③ 上传：为什么必须「立刻返回」
@@need 要解决什么
转写一段 30 分钟的录音要几十秒到几分钟。

如果用户点完上传，请求就一直挂着等结果——**页面转圈、什么都不能干、网一断全白费**，后端还白白占着一个连接。

用户要的从来不是"等"，而是"**先去干别的，好了告诉我**"。

@@idea 核心思路
把「上传」和「处理」拆成两件事：

```
用户点上传
   │
   ├─ 立刻做（几十毫秒就返回）
   │    校验文件 → 落盘 → 建一条「处理中」的记录 → 返回 201
   │
   └─ 后台慢慢做（几十秒到几分钟）
        转写 → 提炼 → 改状态为「已完成」或「失败」
```

**这就是"异步"**。它不是技术炫技，而是把"用户的等待"从几分钟压到几十毫秒。

### 三步的顺序不能乱

```python
# 1. 先校验扩展名，生成安全的存储名
stored_name = generate_stored_filename(file.filename)
# 2. 再落盘（边写边累加校验大小）
written = await save_upload_file(file, dest, max_bytes)
# 3. 最后才建数据库记录
meeting = await Meeting.create(user=current_user, status="处理中", ...)
```

**为什么顺序重要**：如果先建了数据库记录、结果落盘失败，数据库里就留下一条**指向不存在文件**的孤儿记录。按这个顺序，前面的任何一步失败都不会留下垃圾。

### 磁盘文件名为什么要用 uuid

原始文件名 `第一季度经营分析会.mp3` 只用来**显示**。磁盘上真正存的名字是 `e9fae988ec7644babc6daabb6dfe47cb.mp3`。

三个理由：

| 防什么 | 不这么做会怎样 |
|---|---|
| **重名覆盖** | 两个人同时传 `会议.mp3`，后一个把前一个覆盖了 |
| **路径遍历** | 恶意文件名 `../../etc/passwd` 可能写到系统目录 |
| **信息泄露** | 光看文件名就知道谁传的、什么内容 |

所以代码里专门划了一条红线：**原文件名绝不参与磁盘操作**。

### 触发后台任务时，传 id 不传对象

```python
background_tasks.add_task(transcribe_meeting, meeting.id)
```

传的是数据库 id（一个整数），不是那个 ORM 对象。

**为什么**：后台任务跑在**另一个任务上下文**里，这时候原来那个 ORM 对象可能已经失效了。传 id，让它自己去查一次，最稳。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 传大文件失败后，磁盘上留下半个文件 | 落盘要**边写边校验大小**，并且异常时 `unlink(missing_ok=True)` 清理半成品，别先存完再 `stat()` |
| 磁盘被恶意撑满 | 先存完再判断大小，攻击者已经写进去几百 MB 了 |
| 用户上传 100MB 录音，进度条走完却报"音频过大" | **上传上限和转写上限没对齐**（本项目真实存在：上传允许 500MB，转写只吃约 7.5MB），而且这个限制只写在代码注释里，前端毫不知情 |
| 服务重启后，正在处理的会议永远停在「处理中」 | `BackgroundTasks` 是**进程内**的，不持久化、不重试。多进程部署或崩溃重启，在途任务直接丢失 |

@@point ④ 语音转写：把声音变成文字
@@need 要解决什么
录音是声音，系统后面要处理的是文字。中间必须有一步「语音转文字」。

这一步有个绕不开的选择：**自己在本机跑，还是调云服务？**

@@idea 核心思路
两条路的取舍：

| | 本地跑（如 Whisper） | **云服务（如 Qwen3-ASR）** |
|---|---|---|
| 要装什么 | 模型文件好几个 GB | 一个 API Key |
| 快慢 | 看你的机器，没显卡会很慢 | 快 |
| 花钱 | 不花钱 | 按量付费 |
| 隐私 | 数据不出本机 | **录音要传到别人服务器上** |

本项目选了云服务。**理由很实际**：不想为了一个功能去折腾几个 GB 的模型；而且会议录音本来就是短期素材，传出去的心理成本可以接受。

> 选本地还是云，**没有标准答案**。如果是医疗、法务这类敏感录音，就该选本地——**哪怕慢十倍**。

### 一个顺手的设计：一个 SDK 驱动两个云服务

项目用了两个不同厂商的服务：语音用阿里云百炼，大模型用 DeepSeek。

按理说要装两套 SDK。但这里只用了一个 `openai` 库——因为**两家都提供了「OpenAI 兼容接口」**。

```python
client = AsyncOpenAI(api_key=..., base_url=settings.asr_base_url)

client.chat.completions.create(
    model="qwen3-asr-flash",
    messages=[{"role": "user", "content": [
        {"type": "input_audio", "input_audio": {"data": data_url}}
    ]}],

```

**只改 `base_url`，其余代码一行不动**——这就是"兼容接口"的价值。

### 音频怎么送过去

音频被 **base64 编码**成一串文本，直接内联在请求里。

这样做省掉了一整套"对象存储"（先把文件传到 OSS，再把链接给模型）。代价是**不能太大**——base64 会让数据膨胀约 4/3，云端限制编码后 10MB，所以原始字节上限是：

```python
# Qwen3-ASR-Flash 单次输入上限：Base64 编码后不超过 10MB。
# Base64 膨胀比约 4/3，故原始字节数阈值取 10MB * 3/4。
_MAX_RAW_BYTES = 10 * 1024 * 1024 * 3 // 4
```

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 上传合法但转写失败，提示"音频过大" | 上传上限（500MB）和转写上限（约 7.5MB）**是两个没关联的数字**。用户在前端看到的提示还写着"不超过 500MB" |
| 转写时整个服务变卡，别的请求也慢 | base64 编码是**同步阻塞**操作（读整个文件 + 编码），跑在异步事件循环里会把其他请求全堵住。正确做法是丢到线程里执行 |
| 换了个模型就报 400 | 有些端点不支持某些参数，得留降级路径 |
| 录音传到了境外/第三方服务器，事后被追责 | 选云服务时没评估数据合规 |

@@point ⑤ 让 LLM 稳定吐出 JSON：四层容错
@@need 要解决什么
你要的是**结构化的数据**（一段摘要 + 一串待办），但大模型天生输出的是**自由文本**。

它会很客气地跟你说：

```
好的，我分析完了，结果如下：
```json
{"summary": "...", "todos": [...]}
```
```

这串东西你**没法直接拿去存数据库**。

@@idea 核心思路
对付它要有**四层防线**，一层比一层靠后。

### 第 1 层：API 级强制

```python
response_format={"type": "json_object"},  # 让服务端保证输出是合法 JSON
temperature=0.3,                          # 提炼任务用低温，减少格式漂移
```

`temperature` 越低，模型越"保守"、越不容易自由发挥。

### 第 2 层：手工清洗（应对"模型还是加了废话"）

```python
def _extract_json_object(text: str) -> dict:
    """处理顺序：
    1. 去除首尾空白
    2. 剥离 ```json ... ``` 代码块围栏
    3. 若仍不以 { 开头，截取首个 { 到最后一个 } 之间的子串
    4. json.loads
    """
```

第 3 步是关键——**它能从一堆废话里把 JSON 抠出来**。

### 第 3 层：字段级归一（单个字段脏了，不让整体失败）

```python
@field_validator("priority", mode="before")
@classmethod
def _normalize_priority(cls, v: object) -> str:
    # LLM 偶发输出 "P1"/"紧急"/"normal" 等，统一降级为「中」
    if v in ("高", "中", "低"):
        return str(v)
    return "中"
```

`mode="before"` 很重要：在类型校验**之前**先改写，避免直接校验失败。

### 第 4 层：结果级降级（什么该救、什么该弃）

| 情况 | 处理 | 为什么 |
|---|---|---|
| `summary` 为空 | **整体失败** | 摘要没有合理的降级值——没有摘要就没法交付 |
| `priority` 非法 | 降级为「中」 | 优先级猜错，比没有强 |
| 某条待办内容为空 | 跳过这一条 | 单条脏数据不值得毁掉整场会议 |
| `todos` 不是数组 | 当成空数组 | 至少有摘要 |

**这四层里最值得学的是第 4 层的分寸感**：
不是"一旦有脏数据就全部失败"（太严，一点小毛病就白干），
也不是"什么错都忍着"（太松，没摘要还标成成功）。
**能救的救，救不了的老实承认失败。**

### 顺带说：prompt 本身也是"防错设计"

```python
_SYSTEM_PROMPT = """你是会议纪要分析助手。请阅读会议转写文本，输出【严格 JSON】，不要输出任何额外说明或代码块标记。

输出格式（字段名必须完全一致）：
{"summary": "...", "is_urgent": true|false, "todos": [{"content": "...", "priority": "高"|"中"|"低", ...}]}

判定规则：
- priority：涉及硬截止日期 / 客户承诺 / 阻塞他人 / 高风险 = 「高」；常规推进事项 = 「中」；可选 = 「低」。
- todos 只提取有人需要执行的具体任务，不要把纯讨论/信息性发言列为待办；无任务时返回空数组 []。
- 所有字符串值用简体中文。"""
```

好的 prompt 有四个特征，这份都占了：

| 特征 | 这段里对应的话 |
|---|---|
| **给出完整骨架**，而不是描述字段 | 直接把 JSON 结构写出来 |
| **给判定准则，不给关键词** | "涉及硬截止日期/客户承诺 = 高"，而不是"看到'紧急'就标红" |
| **明确说"不要做什么"** | "不要把纯讨论/信息性发言列为待办" |
| **说清缺省值** | "未指明时用 null"、"无任务时返回 []" |

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 模型返回带 ```json 围栏，解析直接崩 | 没做第 2 层清洗 |
| 数据库里 `priority` 存着 `"P1"`、`"紧急"` 这种值 | 没做第 3 层字段归一 |
| 待办列表里全是"大家讨论了 xx"这种废话 | prompt 里没写"不要提取信息性发言" |
| 换了个模型就大面积失败 | 那个端点不支持 `json_object`，而第 2 层兜底写得不够好 |
| 模型偶尔编一个不存在的负责人 | prompt 里没强调"未指明时用 null" |

@@point ⑥ 事务边界：网络调用不能放在事务里
@@need 要解决什么
一场会议的结果有两部分：**摘要**（写在会议表）+ **待办**（写在待办表，可能好几条）。

如果摘要写成功了、待办写失败——数据库里就留下一个"**号称有摘要，其实待办全丢了**"的半成品。用户看到的界面是残缺的，而且没有任何报错。

@@idea 核心思路
用**数据库事务**保证原子性：**要么全成，要么全不成**。

```python
async with in_transaction():
    await Todo.filter(meeting=meeting).delete()   # 先清旧待办（幂等）
    meeting.summary = result.summary
    meeting.status = "已完成"
    await meeting.save()
    if result.todos:
        await Todo.bulk_create([...])
```

### 但有个关键决定：LLM 调用必须放在事务**外面**

```python
# ❌ 有问题的写法
async with in_transaction():
    result = await call_llm(...)      # 网络要几十秒
    await meeting.save()

# ✅ 正确的写法
result = await call_llm(...)          # 网络调用在事务外
async with in_transaction():          # 进事务后只做写库（毫秒级）
    ...
```

**为什么**：数据库事务开着的时候会**持有锁**。

你拿着锁去等一个几十秒的网络请求，别的请求全被堵在门外——**一个慢请求能把整个服务拖垮**。

这个错误在异步服务里**特别容易犯**，因为写起来只差一个缩进。

### 还有一处幂等设计

事务里**先删旧待办，再重建**。

```python
await Todo.filter(meeting=meeting).delete()
```

**为什么**：如果流水线被重复触发（用户手滑、或者以后加了重试功能），不清旧数据的话，待办就会**翻倍**。

这个模式叫**幂等**——同一个操作执行一次和执行十次，结果一样。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 平时正常，一有并发就变慢 | 长网络 IO 占着事务/行锁 |
| 重复触发后待办变成两份 | 没做幂等（先删后建） |
| 摘要有了，待办丢了 | 没包在同一个事务里 |
| 事务里调用了外部接口，接口超时把数据库连接也拖死 | 事务范围画得太大 |

@@point ⑦ 失败隔离：一场失败不能拖垮其他
@@need 要解决什么
后台处理**一定会失败**——网络抖一下、API 限流、文件损坏、模型抽风。

如果一场会议失败就让整个后台任务崩掉，那么**后面所有用户传的录音都排不上队**。

@@idea 核心思路
**每场会议一个独立的任务，异常在任务内部消化掉。**

```python
except Exception as e:  # noqa: BLE001 —— 单场失败隔离，任何异常都标记本场失败
    logger.exception("会议 meeting_id=%s 提炼失败", meeting_id)
    meeting.status = "失败"
    meeting.error_message = f"提炼失败：{e}"
    await meeting.save()
```

> **`except Exception` 平时是坏习惯，这里为什么是对的？**
> 因为它捕获之后**不让异常继续往上抛**——上游是"整个后台任务"，让它看到异常就会中断。
> 那行 `# noqa: BLE001`（告诉代码检查工具"我知道我在广泛捕获，别报警"）就是在**标记这是有意为之**。
> 注释里也写明了理由。**广泛捕获不是错，不写理由才是错。**

### 状态机：三态流转

```
上传 ──► 处理中 ──(转写OK + 提炼OK)──► 已完成
            │
            ├──(转写抛异常)──────────► 失败   error_message="转写失败：..."
            └──(提炼抛异常)──────────► 失败   error_message="提炼失败：..."
```

注意一个讲究：**转写成功后，状态仍然是「处理中」**，不改成别的中间态。

因为「完成没完成」由**整条流水线**决定，不由单个阶段决定。中间态越少，状态机越不容易乱。

### 但这里有三个真实的坑

**坑一：失败路径的保存没有二次保护**

如果那个异常**本身就是数据库连接断了**，那么 `await meeting.save()` 会**再抛一次**——而它不在任何 `try` 里。

结果就是："单场失败隔离"在最需要它的时刻失效了。

```python
# 更稳的写法
except Exception as e:
    logger.exception(...)
    try:
        meeting.status = "失败"
        await meeting.save()
    except Exception:
        logger.exception("连失败状态都没能写进去")
```

**坑二：进程崩溃 → 永久卡住**

`BackgroundTasks` 是**进程内**的。服务如果在处理中被重启，那场会议就**永远停在「处理中」**——没有任何机制能把它捞出来。

前端轮询 120 次（约 10 分钟）后会自动放弃，用户看到的是一个**永远转圈的界面**，没有任何说明。

**要解决它，得引入真正的任务队列**（Celery / RQ / arq），加上超时扫描——这是把项目从"能演示"推进到"能上线"必须跨的一步。

**坑三：错误信息直接回显给用户**

```python
meeting.error_message = f"提炼失败：{e}"
```

`e` 的底层可能是 SDK 的原始异常，里面**可能带着域名、请求 id，极端情况下甚至含密钥片段**。而这个字段会**原样显示在前端**。

正确做法：**详细写日志，返回泛化文案**。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 服务重启后会议永远转圈 | `BackgroundTasks` 不持久化，也没有恢复机制 |
| 用户看到一串英文堆栈 | `error_message` 直接回显了底层异常 |
| 数据库挂了之后，连"失败"都标不上 | 失败路径的 `save()` 没有二次保护 |
| 一场失败导致后面全堵 | 异常没有被隔离在单场任务内 |

@@point ⑧ 前端怎么知道处理完了：轮询
@@need 要解决什么
状态在后台悄悄变化（处理中 → 已完成），**但服务器不会主动告诉前端**。

前端怎么知道该刷新了？总不能指望用户自己按 F5。

@@idea 核心思路
**轮询**：前端每隔几秒问一次"好了没"。

看起来简单，但有个**关键选择**——用 `setTimeout` 链，**不要用 `setInterval`**：

```ts
// ❌ setInterval：不管上一次回来没有，每 5 秒发一次
setInterval(fetchStatus, 5000)

// ✅ setTimeout 链：上一次回来之后，才排下一次
async function tick() {
  attempts++
  await fn()                              // 等它返回
  timer = setTimeout(tick, interval)      // 再排下一次
}
```

**为什么这个区别是致命的**：

假设后端要 8 秒才返回，而轮询间隔是 5 秒——

| | 结果 |
|---|---|
| `setInterval` | 每 5 秒发一个请求，**请求越堆越多**，最后把浏览器和服务端一起拖垮 |
| `setTimeout` 链 | 上一次回来才排下一次，**天然自我节流**，永远只有一个请求在飞 |

### 还有三个角要堵

| 要堵的 | 怎么堵 | 不堵会怎样 |
|---|---|---|
| 无限轮询 | `maxAttempts = 120`（约 10 分钟）后停 | 后端永久卡在「处理中」，前端就永远请求下去 |
| 网络抖动 | 单次失败**不中断**，继续排下一次 | 地铁里网断一下，界面就再也不更新了 |
| 组件卸载后还在跑 | `onUnmounted(stop)` 自动清理 | 用户切走页面，后台还在傻傻发请求 |

### 停止条件由数据本身决定

```ts
const polling = usePolling(async () => {
  await store.fetchDetail(meetingId)
  const m = store.current
  if (!m) return false              // 404 / 无数据，停止
  return m.status === '处理中'      // 一旦进入终态，自动停
}, { interval: 5000, immediate: true })
```

**这行 `return m.status === '处理中'` 是整个设计最漂亮的地方**——不需要任何额外的业务判断，"什么时候该停"直接由数据回答。

而这个「机制」和「策略」是分开的：

| 文件 | 管什么 |
|---|---|
| `usePolling` | **机制**：间隔、次数上限、自动清理（任何轮询场景都能复用） |
| `useMeetingStatus` / `useListPolling` | **策略**：什么时候该轮询、什么时候停（只有十几行） |

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 接口慢的时候，请求越堆越多 | 用了 `setInterval` |
| 后端永久卡住，前端一直请求 | 没有 `maxAttempts` 上限 |
| 切走页面后还在发请求 | 忘了 `clearTimeout` |
| 列表页刷得太频繁，用户看着晃 | 详情页和列表页用了同一个间隔（应该分开：用户盯着看就 5 秒，列表 6 秒） |
| 每 5 秒拉一次**完整转写全文** | 轮询把不需要的字段也带回来了——转写文本可能上万字，而"处理中"的时候前端根本不显示它 |

@@point ⑨ 前后端的契约：让编译器帮你查错
@@need 要解决什么
后端说「处理中」，前端也得说「处理中」。

两边一旦对不齐——后端改成了 `processing`、前端还在等「处理中」——**界面就永远显示不出状态**，而且这种错**不报异常、只在界面上默默空白**，最难查。

@@idea 核心思路
**把同一个字符串贯穿三层，并且让编译器替你把关。**

| 层 | 怎么写 |
|---|---|
| 数据库 | 直接存中文 `"处理中"` |
| API 返回 | 原样是 `"处理中"` |
| TypeScript | **字面量联合类型锁死** |

```ts
// 后端 status / priority 为中文枚举字符串，用字面量联合类型锁死，杜绝拼写错误
export type MeetingStatus = '处理中' | '已完成' | '失败'
```

再配一张样式映射表：

```ts
const STATUS_META: Record<MeetingStatus, StatusMeta> = { ... }
```

**`Record<MeetingStatus, ...>` 是这里的精髓**：

TypeScript 会强制你为**每一个**状态都提供样式，**漏一个就编译不过**。

以后业务加了第四种状态「已取消」——**编译器会主动提醒你去补全所有地方**，而不是等你上线后收到用户反馈。

好处总结成两句：**零映射转换 + 编译期穷尽性检查**。

### 另一个契约上的讲究：列表和详情用不同的模型

| 模型 | 返回什么 | 为什么 |
|---|---|---|
| 列表项 | id、状态、文件名、时间 | 一个用户可能有几百场会议，**不能每条都带摘要和全文** |
| 详情 | 再加上摘要、待办、转写全文 | 只有点开某一场时才需要 |

**这个区分看起来小，但它是"接口设计"和"把数据库字段全扔出去"的分水岭。**

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 新增一个状态后，界面显示空白 | 忘了在样式映射表里加一条 |
| 列表页加载很慢 | 列表接口把摘要、转写全文也返回了 |
| 前端拼错状态字符串，界面静默不显示 | 没用字面量联合类型，编译器管不了 |
| 后端字段改名，前端不知道，直接白屏 | 契约只存在于两边的脑子里，没有写下来 |

@@point ⑩ vibe coding：CLAUDE.md 怎么写 ★
@@need 要解决什么
你用 AI 写代码，但它每次开工都要问一遍：

- 用 `pip` 还是 `uv`？
- 怎么启动？`python main.py` 还是 `uvicorn`？
- 数据库要先起吗？
- 有没有测试要跑？

**你不想每次都把项目重新解释一遍。** 而且它猜错了，你还得收拾。

@@idea 核心思路
`CLAUDE.md` 是**放在项目根目录、给 AI 看的"入职说明书"**。AI 每次开工前会自动读它。

它该写什么？六条原则：

| # | 原则 | 例子 |
|---|---|---|
| 1 | **写「怎么做事」，不写「这是什么」** | `Use uv for all dependency and run commands` |
| 2 | **明确禁止 > 模糊推荐** | `do not call pip/python directly` |
| 3 | **给地图，不给全文** | 目录树 + 每个文件一行用途 |
| 4 | **区分「已实现」和「计划中」** | 否则 AI 会把计划中的功能当 bug 修 |
| 5 | **指出「唯一真源」并声明优先级** | `docs/需求.md 是 scope 的 source of truth` |
| 6 | **写「为什么」，尤其「为什么不那样做」** | `compose 只定义 MySQL，应用跑在宿主机` |

**第 2 条最值钱。**

因为 AI 的默认行为就是 `pip install` 和 `python main.py`。你要**显式覆盖这个默认**——而"本项目使用 uv"这种陈述句**覆盖不了**，它照样会用 pip。

**记住这个判断标准：每一条都应该是祈使句或禁令，而不是描述句。**

### 一个真实的反面教材

这份 `CLAUDE.md` 有一节叫「项目状态」，它写的是：

> Early scaffolding. ... **No models, routes, or business logic yet.**
> `models.py` # Tortoise models (**placeholder — User/Meeting/Todo TBD**)

但实际上呢？**三张表全实现了、路由全写了、整条流水线都跑通了。**

也就是说——**这份说明书过期了**。

后果很具体：**一个只读 CLAUDE.md 的 AI，会以为数据模型还没写，然后动手去"实现"它——把已经写好的代码覆盖掉。**

> **过期的不如没有。** 这是所有写 CLAUDE.md 的人都会踩的坑，包括这个项目。
> 对策：把「项目状态」写成**实现进度表**（哪条需求做了、哪条没做），而不是"现在有哪些文件"——**进度表比文件清单更不容易过期**。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| AI 用 `pip install` 装依赖，把环境搞乱 | 没写明确的禁令（只写了"用 uv"这种描述句） |
| AI 覆盖了已经写好的文件 | 状态说明过期了 |
| AI 找不到该改哪个文件，到处乱翻 | 没有目录地图 |
| AI 自己发明需求，做了一堆没要的功能 | 没指出需求文档是唯一真源 |
| AI 把"计划中"的功能当成 bug 去"修复" | 没区分已实现和计划中 |
| CLAUDE.md 越写越长，最后没人看 | 把代码抄进去了。**它该是地图，不是全文** |

@@summary
这一章没有讲任何新语法，但它可能是整个阶段里最"实战"的一章。

你学到的是**一条完整的做事链路**：

| 步骤 | 关键问题 |
|---|---|
| **① 需求先行** | 先问"谁的什么痛"，再谈功能。用用户故事句型逼自己回答"为什么" |
| **② 私有与认证** | 哈希+加盐存密码、发 token 认票不认人、查询条件里带上"只能查自己的" |
| **③ 立刻返回** | 上传和处理拆开。用户不该为几分钟的计算干等 |
| **④ 云的取舍** | 本地还是云，比的是"折腾成本 / 速度 / 隐私"，没有标准答案 |
| **⑤ 四层容错** | 防住 LLM 的自由发挥。**能降级的降级，救不了的老实承认失败** |
| **⑥ 事务边界** | 网络调用放事务外。**别拿着数据库锁去等网络** |
| **⑦ 失败隔离** | 一场失败不能拖垮别人。但要注意进程崩溃和错误回显这两个坑 |
| **⑧ setTimeout 链** | 轮询的自节流。**上一次回来才排下一次** |
| **⑨ 契约锁死** | 让编译器替你查错，而不是靠人记 |
| **⑩ 给 AI 写说明书** | 禁令 > 推荐。**过期的不如没有** |

**如果只记一句话**：

> **好的工程不是"功能都实现了"，而是"每个决定都有理由，每个失败都有交代"。**
