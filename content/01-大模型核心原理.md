@@point ① 大模型是什么：AI 三十年的进化终点
@@need 要解决什么
新闻里一会儿"深度学习"一会儿"大模型"，好像每个都是新发明。但 AI 这个概念 1956 年就有了——**为什么最近十年突然杀出个"大模型"，还碾压了以前所有方法？**

如果你不知道 AI 经历了什么，就不知道大模型"大"在哪、为什么别的方法打不过它。

@@idea 核心思路
AI 的发展可以压缩成四个阶段，每一代都在解决上一代的痛点：

```text
规则驱动阶段（1950s-）    人写规则：如果……就……  → 规则写不完，世界太复杂
统计机器学习阶段（1990s-） 人喂特征：让算法学规律  → 特征靠人工设计，还是累
深度学习阶段（2012 起）    人喂数据：机器自己找特征 → 数据够了，但模型还不够大
大模型阶段（2018 起）      人给海量数据+算力       → 参数千亿级，全能选手出现
```

大模型的"大"具体大在四处：

| 维度 | 传统模型 | 大模型 |
|---|---|---|
| **数据** | 几万条样本 | 万亿级 Token（几乎整个互联网） |
| **算力** | 单张显卡 | 上万张 GPU 集群训练数月 |
| **参数** | 几百万 | 千亿级（如 685B = 6850 亿） |
| **泛化** | 只会干一件事 | 一个模型能写诗、编程、看病历 |

在上一阶段，深度学习已经能识别猫、下围棋；大模型在此基础上把"专才"变成了"通才"——**不再为每个任务单独训练模型，一个模型吃遍所有任务**，这就是它颠覆性的地方。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把大模型等同于"聊天机器人" | 聊天只是形态，底层是文本、图像、视频、语音全能的生成模型 |
| 以为"参数越多一定越强" | 参数大是必要条件，但训练数据质量、对齐调优同样决定好坏 |
| 问"大模型是哪年发明的" | 没有发明元年，是 Transformer 架构 + 数据 + 算力逐步演进的结果（2017 Transformer 论文是公认里程碑） |

@@point ② 大模型凭什么在今天爆发
@@need 要解决什么
Transformer 架构 2017 年就发布了，大模型却直到 2019-2022 才爆发。**中间到底发生了什么？缺了哪一环都成不了？**

很多同学以为"大模型 = 更深的神经网络"，照着这个思路自己调参数，结果训练极慢还不出效果——方向就错了。

@@idea 核心思路
大模型爆发是**三个条件同时到齐**才发生的，缺一个都起不来：

1. **硬件条件：GPU/TPU 的崛起**
   传统 CPU 是"单核很强"的通用处理器；GPU 天生适合"成千上万个小计算并行"——而神经网络就是海量小矩阵运算。一块 H 系列 GPU 有数万个计算核心，专门为矩阵乘法设计的 TPU 更狠。没有并行算力，千亿参数模型训练一次要几百年。

2. **算法条件：Transformer 架构**
   2017 年 Google 提出 Transformer，核心是**自注意力机制（Self-Attention）**：让模型在理解一句话时，能同时"看"到句中所有词并自己算出哪些词更重要。相比以前逐字读的 RNN（循环神经网络），Transformer 可以**并行处理**、还能捕捉超长距离的依赖关系——"虽然前面 500 个字没提北京，但我知道你还是在说北京的事"。

3. **数据条件：互联网带来的数据爆炸**
   大模型吃的是"整个互联网"——网页、书籍、论文、代码。ChatGPT 的训练数据包括 Wikipedia、书籍语料、网页爬虫数据等数万亿 Token。没有互联网，就没有足够的"教材"。

```text
        硬件（算力给足）
           ↓
算法（Transformer）+ 数据（互联网）  →  大模型
```

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为大模型是"更深的神经网络"随便加层数就行 | 参数量到千亿必须配 Transformer 结构，否则训练不收敛 |
| 自己训练大模型 | 个人/小团队练不动（成本千万级），正确姿势是"用开源模型微调/调用 API" |
| 混淆"训练"和"推理" | 训练=造模型（烧钱烧时间）；推理=用模型（一次几分钱）|

@@point ③ AI 产品家族：分析式 vs 生成式
@@need 要解决什么
"人脸识别的 AI"和"给你画图的那个 AI"都是 AI，但**绝不是同一种东西**。你不搞清楚它们的区别，就会用错工具、配错硬件、买错方案。

比如你想做一个"识别图片里有没有猫"的程序，却去买了个文生图模型——牛头不对马嘴。

@@idea 核心思路
按"AI 的输出是什么"，可以把主流产品分成两大类：

```text
AI 产品
├── 分析式（判别式）：输入 → 给出判断/分类/预测
│     视觉识别（人脸识别、目标检测：ResNet、YOLO）
│     语音识别（听写、翻译：Transcribe）
│     自动驾驶（识别路况、规划路线：Waymo、特斯拉、百度Apollo）
└── 生成式：输入 → 生成新内容
      大语言模型（对话、写代码：ChatGPT、DeepSeek、Qwen）
      图像/视频生成（DALL-E、Midjourney、Sora）
```

几个关键区别：

| 对比 | 分析式 | 生成式 |
|---|---|---|
| 任务 | 判断"这是什么" | 创造"没有的东西" |
| 输出 | 标签/分数/框 | 文本、图像、视频、音频 |
| 代表 | 安防人脸识别、质检 | ChatGPT、文生图、文生视频 |
| 数据要求 | 标注数据（要人工打标签） | 海量无标注数据（从互联网自学） |

**大语言模型（LLM）属于生成式**，它做的事情本质是"预测下一个字"：看到"今天天气真"，预测下一个是"好"。但就是这一个朴素机制，加上海量参数和训练，涌现出了理解、推理、创作的能力——这是 2020 年代 AI 最大的范式转变。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 拿大模型去做"图片分类" | 分类任务用专门的视觉模型（YOLO/ResNet）便宜又准 |
| 以为生成式模型是"查数据库" | 它是"概率生成"，所以会一本正经地编造（幻觉）|
| 把分析式 AI 淘汰掉 | 没有淘汰，识别、检测、推荐这些分析场景生成式并不擅长 |

@@point ④ AIGC 与 AGI：AI 现在走到哪一步了
@@need 要解决什么
新闻天天刷屏："AIGC 颠覆产业""AGI 即将到来"。你分不清这俩词，就不知道该**现在就上 AI 的船**，还是等"真正的 AI"出来再说。

@@idea 核心思路
两个词一字之差，一个在今天，一个在未来：

- **AIGC（AI Generated Content）**：AI 生成内容。就是**已经落地的现实**——写文案、画图、做视频、配音、写代码。它是对内容和创意生产方式的升级，今天所有 AI 应用基本都属于 AIGC 的范畴。
- **AGI（Artificial General Intelligence）**：通用人工智能。指**达到甚至超越人类水平**、能像人一样处理各种任务、拥有自我学习和思维能力的 AI。目前**还没有实现**，是终极目标。

它们的关系：**AIGC 是 AGI 路上的里程碑**——当 AI 能熟练生成文本、图像、视频、语音、代码，再把这些能力打通成"一个模型啥都会"，就是在向 AGI 迈进。

行业共识：当前正处于"大语言模型向多模态 AGI 迈进"的转折期。所谓**多模态**，就是模型不再只处理文字，而是把文字、图像、音频、视频统一理解——ChatGPT 能"看图说话"、通义千问能"听语音"就是多模态能力。AGI 很远，但这条路已经被 AIGC 铺开了。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为 AGI 已经实现、"AI 要取代人类了" | AGI 还是目标，现在的模型仍会犯错、有幻觉 |
| AIGC 和 AGI 混用 | AIGC=内容生成（现在），AGI=通用智能（未来） |
| 轻视 AIGC 的当下价值 | 不会取代人，但会用 AI 的人会取代不会用的人——现在就该学 |

@@point ⑤ 联网搜索与读文件：AI 怎么"知道"你的资料
@@need 要解决什么
模型训练数据有截止日期，你问它"今天北京天气"它答不上来——它"出生后"就没见过这些信息。

但你看 DeepSeek 明明能联网查新闻、上传一份 200 页的财报后它还能精准回答"Q2 毛利率是多少"。**它怎么突然"知道"了？** 如果你不懂这两个机制，就会误以为"模型什么都懂"，被幻觉带偏。

@@idea 核心思路
大模型的知识来自"训练时"，但有两个机制帮它**临时补充知识**：

**1. 联网搜索**
当模型判断"这个问题光靠脑子里的知识不够"时，它会：

```text
识别需求 → 生成搜索关键词 → 调用搜索引擎 → 把搜索结果拼进上下文 → 基于结果回答
```

所以它"知道"今天的新闻，不是记住了，而是**现场搜给你看的**。

**2. 读取文件（RAG——检索增强生成）**
你上传文档后，系统做的事情是：

```text
① 切片：把文档切成小块（chunk）
② 向量化：用 Embedding 模型把每块转成"数学向量"（语义坐标）
③ 建库：存入向量数据库
④ 检索：把你提的问题也向量化，找出语义最接近的几块
⑤ 生成：把这几块内容拼进提示词，让大模型基于它们回答
```

这套流程叫 **RAG（Retrieval-Augmented Generation）**，是目前企业知识库、AI 客服、私有资料问答的**标准架构**——因为大模型不能直接"读"你的 PDF，必须靠这套检索管道把相关内容喂给它。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为模型"记住了"你上传的文件 | 没有，它只是"本轮带上检索内容"回答，换个会话又忘了 |
| 文档没被正确切片/向量化 | 大文件不切片会超上下文；切片太小会丢语义 |
| 把联网搜索当默认功能 | 很多 API 场景默认关闭联网，需显式开启搜索工具 |

@@point ⑥ 记忆功能：AI 怎么记住你刚说的话
@@need 要解决什么
你跟 AI 说"我很喜欢简洁的回答"，它下一轮真变简洁了；你跟它聊了半小时，它还记得开头说的名字。**可它不是"无状态"的吗？怎么做到的？**

反过来，有时候聊着聊着它又"失忆"了，刚才交代的事全忘了——这又是为什么？

@@idea 核心思路
关键概念是**上下文窗口（Context Window）**：

```text
大模型本身不记任何东西（无状态）
但它每轮收到的 prompt  =  系统设置 + 历史对话（最近 N 轮）+ 你刚说的话
```

也就是说，**"记忆"是伪装出来的**：每次回答前，模型把之前的对话全部重发给自己当背景资料。上下文窗口就是它"一次能带上多少背景"的容量。

- 不同模型容量不同：常见 32K、128K，DeepSeek-V3.2 支持 256K，Qwen3 系列支持到 1M（约 100 万字）。
- 超过窗口的内容会被丢弃，所以你会看到它"忘了"很早以前的事。
- 这种"短期记忆"由开发者控制：想要更长的记忆，就用**记忆系统/RAG** 把重要信息存起来（产品层的长期记忆）。

```text
你:"我叫小王"
AI:"你好小王"
你:"我叫什么?"          ← AI 把前两轮一起发给模型，所以答"小王"
你:(过了500轮后)"我叫什么?"  ← 前两轮被挤出窗口，答不上来了
```

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 聊天到后面 AI "失忆" | 早期对话被上下文窗口挤掉了，属正常；重要信息要用摘要或记忆库保存 |
| 以为上下文=签个合同就永久记住 | 上下文是一次性的，下次会话什么都没有 |
| 对话越长越慢越贵 | 因为每轮都要把所有历史重发给模型，token 消耗随轮次增长 |

@@point ⑦ 全球 AI 现状与主流大模型全景图
@@need 要解决什么
DeepSeek、豆包、Kimi、GPT、Claude、Gemini……打开任何一篇 AI 文章都是一堆名字。**这些模型到底是谁家的、各有什么本事？哪些是国产的？** 没有全景图，你连"该用哪个"都无从谈起。

@@idea 核心思路
一张表看清当前主流玩家（覆盖文本、图像、视频、多模态等能力）：

| 模型 | 公司 | 国家 | 特点 |
|---|---|---|---|
| DeepSeek | 深度求索 | 🇨🇳 中国 | 开源、推理强、成本低 |
| Qwen（通义千问） | 阿里 | 🇨🇳 中国 | 开源+闭源双线，生态全 |
| GLM | 智谱 AI | 🇨🇳 中国 | 国产老牌，代码能力强 |
| Doubao（豆包） | 字节跳动 | 🇨🇳 中国 | 免费量大，C 端普及 |
| Hunyuan（混元） | 腾讯 | 🇨🇳 中国 | 多模态，微信生态 |
| Kimi | 月之暗面 | 🇨🇳 中国 | 长文本（上下文大） |
| GPT | OpenAI | 🇺🇸 美国 | 标杆，ChatGPT 开创者 |
| Claude | Anthropic | 🇺🇸 美国 | 对话/写作质量顶尖 |
| Llama | Meta | 🇺🇸 美国 | 开源先锋 |
| Gemini | Google | 🇺🇸 美国 | 多模态原生 |
| Grok | xAI（马斯克） | 🇺🇸 美国 | 实时信息、风格大胆 |

几个值得记住的格局判断：

- **国产模型已进入第一梯队**：DeepSeek、Qwen、GLM、Doubao 在全球排名中常年靠前，且**国内网络直接用、中文效果好、价格便宜**——对国内开发者来说，首选国产模型没有妥协感。
- **开源 vs 闭源是两条路线**：中国厂商（DeepSeek/Qwen/GLM）普遍开源 + 提供 API，全球开发者都能下载权重自己部署。
- **模型能力各有侧重**：没有"绝对第一"，看任务选模型——要推理数学选 DeepSeek-R1，要写文章选 Claude，要本土服务选 Qwen/豆包。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 只认识 GPT，不知道国产模型 | 国内开发建议先看通义千问、DeepSeek——中文好、合规、便宜 |
| 以为闭源就是"不能下""弱" | 闭源模型通常更强（GPT-5、Claude 系），取舍在成本与可控性 |
| 拿一张榜单当定理 | 榜单数据每月都变，看"你实际任务上的效果"才有意义 |

@@point ⑧ 开源 vs 闭源：怎么选
@@need 要解决什么
Llama、Qwen 这些模型**免费下载**，GPT、Claude 只能花钱调 API。那是不是"下载免费的自己跑"永远最优？很多人这么想，结果部署起来发现又贵又慢又难调——**开源和闭源的账，要算清楚**。

@@idea 核心思路
从六个维度对比：

| 维度 | 开源（Llama/Qwen/DeepSeek） | 闭源（GPT/Claude/豆包API） |
|---|---|---|
| **模型权重** | 公开，可下载 | 只开放 API，看不到权重 |
| **定制化** | 可微调、可私有化部署 | 只能靠提示词/参数微调 |
| **成本结构** | 部署成本自己扛（硬件+运维） | 按调用量付费，无硬件投入 |
| **性能上限** | 略低于同代闭源旗舰 | 通常最强（如 GPT、Claude 旗舰） |
| **维护** | 自己负责升级、监控 | 厂商维护，开箱即用 |
| **数据安全** | 数据不出内网 | 数据要发给第三方（有合规风险） |

**怎么选，看你的场景：**

```text
个人学习/小工具   → 直接调 API（百炼、DeepSeek API），省钱省事
企业处理敏感数据 → 私有化部署开源模型（Qwen-72B 等），数据不出内网
追求极致效果     → 用闭源旗舰 API（GPT/Claude/DeepSeek-V3.2）
要改模型逻辑     → 用开源模型微调（你有语料和算力的话）
```

一个常见误区：**"开源 = 免费"**。模型权重确实不要钱，但 70B 模型推理需要多张专业显卡，一个月电费+硬件折旧远超 API 调用费。个人用户 90% 的场景，调 API 都比自己部署划算。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为开源白嫖最省钱 | 部署 70B 级模型硬件成本数万元起，算总账才见分晓 |
| 数据敏感还盲目用国外闭源 API | 涉密数据走私有化开源或国产合规平台 |
| 混淆"开源模型"与"免费API" | 开源指权重可下载；厂商的 API 是另一回事（可收费） |

@@point ⑨ 看懂版本后缀：Max/Plus/Flash 都是什么
@@need 要解决什么
第一次打开百炼平台模型列表：`qwen3-max`、`qwen3-plus`、`qwen3-flash`、`qwen3-vl-plus`、`DeepSeek-V3.2-Exp`、`R1`……**看着都像"通义千问"，到底选哪个？** 选错要么慢要么贵要么不支持你要的功能。

@@idea 核心思路
**型号 = 品牌 + 能力分级 + 特性后缀**。以通义千问（Qwen）系列为例：

| 后缀 | 定位 | 适用场景 |
|---|---|---|
| Max | 旗舰版，能力最强 | 复杂推理、重要任务 |
| Plus | 高性能/均衡 | 多数业务场景（性价比选它） |
| Flash | 极速版，响应最快 | 实时对话、批量调用 |
| VL | 视觉语言（Vision-Language） | 识图、看图问答 |
| Omni | 全能多模态 | 文本+图像+音频+视频 |
| Realtime | 实时语音对话 | 语音助手 |

DeepSeek 系列的规则也类似：

| 后缀 | 含义 |
|---|---|
| Exp（Experiment） | 实验版，新能力尝鲜但不稳定 |
| Base | 基础版，未对齐，适合继续微调 |
| Distill / Specials | 蒸馏版，把大模型知识压缩进小模型，跑得快 |

选模型时除了"能力档位"，还要看三个**硬指标**：

- **上下文长度**：256K 还是 1M，决定能一次装下多少资料；
- **RPM / TPM**：每分钟请求数 / Token 数——并发高了会被限流；
- **参数量**：如 685B 指 6850 亿参数，越大一般越聪明也越贵。

```text
选型口诀：
任务简单量大 → Flash（快）
业务稳定执行 → Plus（均衡）
最难的任务 → Max（最强）
要处理图片 → 带 VL 的
```

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 只看参数不管价格 | 参数越大单位 token 越贵，能用 Plus 别用 Max |
| 选了个不支持图片的模型做识图 | 要看是否带 VL/通用多模态能力 |
| 忽略 RPM 限制导致批量任务报 429 | 先查该模型的 RPM/TPM 并发配额，任务做分批/限速 |

@@point ⑩ 本地跑还是云端调：硬件怎么选
@@need 要解决什么
热血上头想"自己训一个模型"或者"在自己电脑上部署 70B 大模型"——结果训练到一半电脑死机，或者推理慢得像聊天。**大模型对硬件的要求到底有多离谱？什么配置能跑什么模型？**

@@idea 核心思路
先分清三个硬件角色：

| 硬件 | 干什么 | 特点 |
|---|---|---|
| **CPU** | 任务调度、通用计算 | 单核强、并行弱 |
| **GPU** | 大规模并行矩阵运算（AI 主战场） | 数千核心，训练/推理主力 |
| **TPU** | Google 专用张量处理器 | 为神经网络定制，一般云上用 |

大模型推理最吃的是**显存（VRAM）**——模型参数要装进显存才能算。按参数规模，粗略对照：

| 模型规模 | 最低需要 | 实际建议 |
|---|---|---|
| 1.5B（小模型） | 8GB 内存 | RTX 3060（12GB）可流畅 |
| 7B（中等） | 16GB | RTX 4080（16GB） |
| 14B | 32GB | RTX 4090（24GB）勉强到瓶颈 |
| 32B | 64GB | 双 4090 交火 |
| 70B（Llama3-70B） | 140GB | 4×A100（80GB）|
| 671B（DeepSeek-V3 满血） | 1TB+ | 8×H200，成本千万级 |

记住这个逻辑就懂了：

```text
模型参数量 × 每个参数的字节数 ≈ 需要的显存
（FP16 格式下：70B × 2 字节 ≈ 140GB）
```

**结论很现实**：普通人自己部署，顶多跑 7B-32B 的中小模型；要跑满血旗舰、或想追求稳定效果，直接调云端 API 是唯一合理选项——这也是行业共识：**"本地部署"适合隐私敏感场景和有硬件预算的团队，其余一律走 API。**

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 看"内存 32G"以为能跑 32B 模型 | 显存≠内存，32B 模型要的是显卡显存不是内存 |
| 买消费卡跑 70B | 消费级显卡顶多 24GB，跑不动；要么量化要么上云 |
| 以为量化就是"作弊" | 量化（4bit/8bit）是标准做法，损失少量精度换能跑，个人玩家常用 |

@@point ⑪ 第一次调用大模型：百炼 + OpenAI SDK
@@need 要解决什么
聊天界面玩腻了，你想**在代码里调用大模型**——让它帮你批量处理文本、搭自己的 AI 产品。但第一步就被卡住：去哪申请 Key？用什么库？为什么教程里 `openai` 包能连"通义千问"？

其实**最快打通只需三步**，十几分钟就能跑出第一个"会回话的代码"。

@@idea 核心思路
用**阿里云百炼**平台（聚合了 Qwen、DeepSeek 等模型，国内直连）走通全流程：

**第 1 步：拿 API Key**
百炼控制台 → 开通模型服务 → 创建 API-KEY。这个 Key 就是你程序的"通行证"，**要像密码一样保管**。

**第 2 步：装 SDK**
OpenAI 出的 `openai` Python 库已是事实标准——绝大多数国产模型都兼容 OpenAI 协议，只需改一个 `base_url` 就能指到国内平台：

```bash
pip install openai
```

**第 3 步：写 10 行代码**
```python
from openai import OpenAI

# 密钥从环境变量读取，绝不写死在代码里（安全红线）
key = os.environ["DASHSCOPE_API_KEY"]

client = OpenAI(
    api_key=key,
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)

resp = client.chat.completions.create(
    model="qwen-plus",          # 换成你选的模型
    messages=[{"role": "user", "content": "你好，介绍一下你自己"}],
)
print(resp.choices[0].message.content)
```

跑完控制台打印出模型的回答，恭喜——**你已经完成了人生第一次程序化调用大模型**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 报 `401` 鉴权失败 | Key 填错或没开通对应模型服务，回百炼控制台核对 |
| 报 `Invalid base_url` | base_url 必须精确到版本路径 `compatible-mode/v1`，别漏 `/v1` |
| 把 Key 写进代码提交到 GitHub | 泄漏即被盗刷！始终用 `os.environ[...]` 环境变量注入 |

@@point ⑫ 请求体：你发给模型的消息结构
@@need 要解决什么
`client.chat.completions.create(...)` 里那些参数：`model`、`messages`、`role`、`content`、`stream`、`temperature`……**每个都是干嘛的？** 你以为自己在"调接口"，其实是在"组装给模型看的一封信"——装错了模型就看不懂。

@@idea 核心思路
一次调用，本质是**发给模型一份结构化的对话记录**。核心就三个字段：

```python
resp = client.chat.completions.create(
    model="qwen-plus",                      # 用哪个模型
    messages=[                              # 完整对话上下文（列表）
        {"role": "system", "content": "你是资深的Python导师，回答简洁专业。"},
        {"role": "user",   "content": "什么是列表推导式？"},
        {"role": "assistant", "content": "列表推导式是用一行代码生成列表的语法…"},
        {"role": "user",   "content": "举个例子？"},
    ],
    stream=False,                           # 是否流式返回
    temperature=0.7,                        # 随机性：0 稳定，1 创意，范围 [0,2)
    max_tokens=1024,                        # 最多生成多少 token
)
```

四种 `role` 的含义，就是"这封信的角色分工"：

| role | 角色 | 说明 |
|---|---|---|
| system | 系统设定 | 告诉模型"你是谁、什么风格、什么边界"，优先级最高 |
| user | 用户 | 你要问的话、你的指令 |
| assistant | 模型 | **模型上一轮的回复**——把它放回来，模型才知道"自己刚说过什么" |
| tool | 工具 | Function Calling 里工具执行后的结果（第 16 个知识点讲） |

两个最容易犯的错：

- **把私密设定写进 user**：user 消息模型可能不把它当"底线"，人设、规则必须放 system；
- **每次只发最新问题**：模型看不到历史，就答非所问——**上下文由你手动拼装**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 模型"忘记"了之前对话 | messages 只发了最新一条，把历史轮次也组装进去 |
| system 说了不听 | 检查是否把规则写进了 user；system 指令越具体越有效 |
| 代码里 temperature 传 2 | 合法范围是 [0,2)，超范围直接报错 |

@@point ⑬ 响应体：读懂模型的回答
@@need 要解决什么
请求发出去，返回一个巨大的 JSON 对象，你在里面翻来找去找"它说的话"——**到底哪个字段才是回答？** 更麻烦的是：开了流式（stream=True）之后，拿到的东西完全不是那么回事了。

如果读不懂响应结构，后面所有实战项目都会卡在这一关。

@@idea 核心思路
**非流式响应**（stream=False，默认）返回一个完整对象，结构如下：

```python
ChatCompletion(
  id="chatcmpl-...",
  choices=[
    ChatCompletionChoice(
      message=ChatCompletionMessage(
        role="assistant",
        content="列表推导式是…",   # ← 你要的回答在这里
      ),
      finish_reason="stop",        # stop=正常结束 / length=超长截断 / tool_calls=要调工具
    ),
  ],
  usage=CompletionUsage(
    prompt_tokens=25,              # 输入消耗的 token（计费依据）
    completion_tokens=120,         # 输出消耗的 token
    total_tokens=145,
  ),
)
```

取值就一行：`resp.choices[0].message.content`。

**流式响应**（stream=True）：不等全部生成完，**边生成边吐**，像打字机。拿到的不是完整对象，而是一个个分片：

```python
for chunk in resp:
    delta = chunk.choices[0].delta.content  # 每个 chunk 里的增量文字
    print(delta, end="")
```

两个必读的隐藏字段：

- **finish_reason**：`stop` 正常结束；`length` 说明被 max_tokens 截断了（答案不完整）；`tool_calls` 表示模型请求调用函数（第 16 点）。
- **推理模型专属 `reasoning_content`**：DeepSeek-R1 这类推理模型先"思考"再回答，思考过程单独放在 `reasoning_content` 字段，正文仍在 `content`。**想只显示答案，就取 content，别把思考过程抖出去。**

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 流式下取 `resp.choices[0].message.content` 报错 | 流式是 `delta` 累积，不是一次性 message；要么关流式要么逐片拼接 |
| 回答到一半断了 | 看 `finish_reason`：是 `length` 就把 max_tokens 调大 |
| 输出了"思考过程" | 推理模型记得区分 `reasoning_content` 与 `content` |
| 不知道花了多少钱 | 看 `usage` 的 token 数 × 单价 |

@@point ⑭ 实战一：多轮情感分析
@@need 要解决什么
你想做一个"评论情感分析"工具：把用户评价批量判成好评/差评/中性。单条判断简单，但实际场景是——**用户连着说很多条，还希望模型在上下文里持续分析**（比如："把这 3 条客服记录按情绪排序，第二条比第一条更愤怒，重点分析一下"）。

如果只发一条消息，模型没有上下文，会答得支离破碎。

@@idea 核心思路
一个完整的情感分析助手 = **强人设（system）+ 对话历史维护（messages 组装）**。先定义一个"舆情分析师"角色，再模拟多轮对话：

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["DASHSCOPE_API_KEY"],
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)

SYSTEM = """
你是专业的舆情分析师，擅长情感分析。
要求：
1. 判断每条文本的情感倾向：积极/消极/中性
2. 给出情感强度评分（1-10）
3. 提取核心情绪关键词
"""

# 模拟多轮对话：每轮把历史追加进 messages
messages = [{"role": "system", "content": SYSTEM}]

def chat(user_input):
    messages.append({"role": "user", "content": user_input})
    resp = client.chat.completions.create(
        model="qwen-plus", messages=messages, temperature=0.3,
    )
    reply = resp.choices[0].message.content
    messages.append({"role": "assistant", "content": reply})   # 关键：回填模型回复
    return reply

print(chat("这家店的奶茶味道不错，就是排队太久了。"))
print(chat("再帮我分析一下上一条中最核心的情绪矛盾点。"))
```

**多轮对话的秘诀就一行**：把模型的每条回复 `append` 回 `messages`，历史就攒住了。第二轮问"上一条的情绪矛盾点"，模型能看到第一轮的输入和输出——上下文连续了。

`temperature=0.3` 低一点，情感分析要**稳定可复现**，不需要模型灵感迸发。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 第二轮回答"没有上一条" | 忘了把 assistant 回复 append 回 messages，历史断了 |
| 情感判断忽好忽坏 | temperature 调低（0-0.5）；人设里写明评分规则 |
| 误判反讽（"太棒了，又加班"） | 高级用法：system 里加"注意反讽与语境"，或让模型先复述再判断 |

@@point ⑮ 实战二：图像识别与图像生成
@@need 要解决什么
文本模型玩溜了，你想**让 AI 看图**——比如上传一张产品照片让它写卖点文案；还想反过来**让它画图**——输入一段描述产出一张图。这两个需求分别用什么模型、什么接口？很多同学拿着纯文本模型硬试，模型只会说"我看不到图片"。

@@idea 核心思路
两个能力对应两套接口：

**1. 图像识别 —— 视觉语言模型（VL）**
选 `qwen-vl-plus` 这类带视觉能力的模型，把图片作为消息的一部分传过去：

```python
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["DASHSCOPE_API_KEY"],
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)

resp = client.chat.completions.create(
    model="qwen-vl-plus",
    messages=[{
        "role": "user",
        "content": [
            {"type": "image_url",
             "image_url": {"url": "https://example.com/product.jpg"}},
            {"type": "text", "text": "描述这张图片里的产品，并给出卖点建议"},
        ],
    }],
)
print(resp.choices[0].message.content)
```

关键点：**content 从字符串变成了一组内容的列表**，图片和文字并行放进 `content` 数组，模型就能"看图说话"。

**2. 图像生成 —— 文生图模型**
文本模型不产图，要用专门的生图模型（百炼的 `wanx-image` 系列等），并切换成另一套接口协议：

```python
import dashscope
from dashscope import MultiModalConversation

dashscope.api_key = os.environ["DASHSCOPE_API_KEY"]

resp = MultiModalConversation.call(
    model="wanx2.1-t2i-turbo",
    messages=[{
        "role": "user",
        "content": [
            {"text": "一只戴着贝雷帽的橘猫，水彩风格，浅色背景"},
        ],
    }],
    size="1024*1024",
    result_format="message",
    watermark=False,

print(resp.output.choices[0]["message"]["content"][0]["url"])  # 生成图的 URL
```

**别把两类接口搞混**：识图走 OpenAI 兼容协议；生图走 DashScope 原生协议（`dashscope` 包 / `MultiModalConversation`）。想看懂流程，先跑通识别，再试生成。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 文本框模型问"图片在哪" | 换了 `qwen-vl-plus` 才支持图片输入 |
| 图片 URL 传了报 400 | 图片地址必须公网可访问，本地路径/私有链接不行 |

@@point ⑯ 实战三：Function Calling 让模型调工具
@@need 要解决什么
模型再聪明也有死穴：**它没有"手"**。问"上海现在多少度"，它的训练数据里没有实时天气；问"帮我查下这个订单号"，它查不了数据库。

现实场景里 AI 必须**调用真实工具**才能完成任务。怎么让"只会生成文本"的模型，去"执行一个函数"？

@@idea 核心思路
答案叫 **Function Calling（函数调用）**——模型不执行代码，而是**自己判断"该调用哪个函数、传什么参数"，把请求说出来，由你的程序真正执行**。完整流程分两轮：

**第 1 步：告诉模型你有这些工具（tools 描述）**
```python
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市的实时天气",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名，如 北京"}
            },
            "required": ["city"],
        },
    },
}]

resp = client.chat.completions.create(
    model="qwen-plus",
    messages=[{"role": "user", "content": "北京今天天气怎么样？"}],
    tools=tools,                      # ← 把工具清单交给模型
)
```

**第 2 步：模型返回"工具调用请求"，你执行后把结果回传**
```python
# 模型没有直接回答，而是返回了工具调用请求
tool_call = resp.choices[0].message.tool_calls[0]
print(tool_call.function.name)        # get_weather
print(tool_call.function.arguments)   # {"city": "北京"}

# ★ 真正执行函数的是你，不是模型
result = get_weather(tool_call.function.arguments["city"])

# 把执行结果作为"tool"角色消息回传，模型基于结果组织最终回答
messages = [
    {"role": "system", "content": "你是天气助手"},
    {"role": "user", "content": "北京今天天气怎么样？"},
]
messages.append(resp.choices[0].message)                    # 带上 tool_calls 的原文
messages.append({
    "role": "tool",
    "tool_call_id": tool_call.id,      # ★ 必须配对，模型靠它识别是哪次调用
    "content": result,
})

final = client.chat.completions.create(model="qwen-plus", messages=messages, tools=tools)
print(final.choices[0].message.content)   # "北京今天晴，23℃，适合出门…"
```

三个灵魂要点：

1. **模型只负责"调度"，执行在你**：它吐出 `tool_calls`（哪个函数、什么参数），你的代码去真正运行；
2. **工具消息必须配对 `tool_call_id`**：模型按 ID 把结果和请求对应起来；
3. **tools 描述写得越清楚，模型调得越准**：函数名、参数说明就是给模型的"使用说明书"。

`finish_reason` 这时会是 `tool_calls`（呼应第 ⑬ 点）——看到它，就知道该去执行工具了。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 模型答非所问不调工具 | tools 描述太含糊，把函数职责、参数含义写清楚 |
| 报 `tool_call_id mismatch` | 回传的 tool 消息没带原 `tool_call.id`，必须原样配对 |
| 以为模型"自己执行了函数" | 它只是生成参数，执行是你的代码，日志要看清楚 |
| 多次工具调用 | 一个 assistant 消息可能有多个 tool_calls，逐个执行后全部回传 |
