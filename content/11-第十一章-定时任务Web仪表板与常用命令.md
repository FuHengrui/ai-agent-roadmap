@@point ① 定时任务：把"提醒我"变成"自动执行"
@@need 要解决什么
"每天早上 8 点给我推送今日摘要""每周末汇总本周进展"——这种**周期性**需求，靠手发消息会被遗忘，靠记忆不靠谱。定时任务就是为"无人值守的周期执行"而生的。

@@idea 核心思路
**定时任务（Cron Job）** 让 Hermes 在指定时间自动执行任务并（可选）推送结果。它与"对话"的本质区别：

| 维度 | 对话 | 定时任务 |
|---|---|---|
| 触发 | 你发消息 | 时间到（cron 表达式）自动触发 |
| 交互 | 实时多轮 | 无人值守，执行+（可选）投递 |
| 场景 | 一切即时需求 | 周期性/计划性需求 |

典型用例：每日摘要、周报汇总、监控提醒（配合 MCP 查 API）、内容定时发布。**它把"人力盯守"转换成"配置一次，永久生效"**——这正是"主动型伙伴"的第一块基石。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为定时任务要"每次对话里设置" | 一次 `/cron` 配置即持久；除非删除/禁用，否则周期一直生效 |
| 以为定时任务=提醒闹钟 | 它是**执行任务**（Agent 真实干活）不只提醒；"推送结果"只是可选项 |
| 任务不跑先怀疑 Agent 坏了 | 先查 Cron 是否启用/网关是否运行（第 ④ 点网关轮询）；大概率是运行条件没满足 |

@@point ② 三种调度模式：秒速/计划/条件
@@need 要解决什么
"定时"不只是"每个小时一次"——三种调度模式，它们适用场景完全不同。需要一次分清。

@@idea 核心思路
先界定三种调度模式：

| 模式 | 机理 | 适用 |
|---|---|---|
| **基于时间的调度** | 按 cron 表达式在指定时刻触发 | 每日/每周/每月定点任务（最常见） |
| **基于间隔的调度** | 按固定间隔（如每 30 分钟）触发 | 轮询类、频率稳定的任务 |
| **基于条件的调度** | 满足某条件时才触发（如某工具返回特定结果） | 监控类：网页变化、API 状态、阈值报警 |

选型口诀：**"定点用时间，均匀用间隔，看情况触发用条件"**。本阶段重点演示"基于时间的调度"（cron 表达式），后两种知道存在即可，需要时再查。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 所有任务都塞"基于时间" | 轮询类任务用间隔更合理；条件类任务用时间调度会空跑，三种模式各有位置 |
| 调度模式与"立即执行"混淆 | "立即跑一次"是手动触发（/cron run），与周期调度是两回事 |
| 学完只记模式名不记场景 | 背场景口诀：时间=定点、间隔=均匀、条件=看情况 |

@@point ③ /cron 命令：创建与管理的入口
@@need 要解决什么
怎么创建定时任务？命令长什么样？创建后还能改吗？

@@idea 核心思路
对话内斜杠命令 `/cron` 是定时任务的创建与管理入口（示例环境是一条用内网工具创建的 cronjob）：

```text
/cron                      # /cron add "0 8 * * *" "每天早上 8 点总结昨日消息"
# 创建时通常要提供：
#   触发方式：cron 表达式（如 0 8 * * * = 每天 08:00）
#   任务内容：要 Agent 执行的消息/指令
#   可选投递：是否把结果推送到某个会话
```

| 操作 | 途径 |
|---|---|
| 创建 | `/cron` 向导，或命令行：`hermes cron create "0 8 * * *" "任务内容"`、`hermes cron list|run|status` |
| 查看已有任务 | `/cron list` 类子命令 |
| 管理（暂停/删除/手动触发） | `/cron pause / resume / run / remove <id>` |

**cron 表达式速记**（5 段：分 时 日 月 周）：
- `0 8 * * *` = 每天 8:00
- `*/30 * * * *` = 每 30 分钟
- `0 9 * * 1` = 每周一 9:00

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| cron 表达式写错（6 段/7 段） | Hermes 用 **5 段**（分时日月周）；秒级用间隔模式，别往 cron 里塞秒 |
| 创建任务不带时间只看效果 | 先给表达式，再让向导生成；拿不准就先手动触发试跑再定周期 |
| 忘记"可投递结果"配置 | 不投递=执行了就完，你看不到结果；要"推送"就配置投递目标会话 |

@@point ④ 网关 60 秒轮询：定时任务"醒来"的机制
@@need 要解决什么
定时任务不是凭空执行的——总有个"闹钟"在看表。**"网关每 60 秒检查一次"**，这段机制怎么理解？跟定时任务的准确度什么关系？

@@idea 核心思路
**要点**：**线程在 60 秒间隔检查已调度的 cronjob 并触发它们**——也就是"在每 60 秒的网关线程中检查并触发"。

机制图解：

```text
网关持续运行（后台线程）
   └─ 每 60 秒扫描一次定时任务表
        ├─ 时间到了 → 触发对应任务执行
        └─ 没到     → 继续等下一个 60 秒
```

**两个推论**：① **网关必须保持运行**，定时任务才会被执行——关掉网关=任务全部休眠；② **触发精度是分钟级**（60 秒轮询粒度），要求"秒级准时"的场景不适用，计划精度到分钟即可。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 关掉网关后任务不跑，以为删了 | 任务还在，只是"闹钟没电"；重启网关即恢复（第 3 章重启铁律的又一应用） |
| 期望"8:00:00 整点执行" | 60 秒轮询会有秒级抖动；当作"8 点前后一分钟内"理解 |
| 多个任务同时到点互相挤 | 同一轮询周期内按序触发，密集任务建议错开分钟，避免排队延迟 |

@@point ⑤ 任务执行+结果投递：闭环的最后一环
@@need 要解决什么
任务执行完了，结果去哪？"跑完了没人看见"和"跑完自动送到手里"是两种体验，需要把投递配明白。

@@idea 核心思路
**定时任务 = 到点执行 + （可选）结果投递**：

| 环节 | 说明 |
|---|---|
| 任务内容 | 你给 Agent 的一段指令（执行什么） |
| 执行 | 到点 Agent 真实干活（搜索/生成/调 MCP...） |
| 投递（可选） | 把产出推送到目标会话（如你的微信群/QQ/飞书/CLI） |

典型配置思路（示例）：每日 8 点 → "汇总昨天 GitHub 仓库的 issues → 推送到我的微信群"。**任务不带投递=执行完沉默**；要"自动报告"就必须在创建时指定投递目标（呼应第 3 章各平台的会话）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 任务执行了但"什么都没发生" | 大概率没配投递/投递目标失效；确认任务配置里的 delivery 目标 |
| 投递目标写错平台 | 投递走**已接入**的平台会话（第 3 章）；平台没接好，投递自然失败 |
| 忘了投递可含"文件/链接" | 部分平台支持富推送；产物型任务可以推文件或链接而非纯文本 |

@@point ⑥ 定时任务的调试：先手动触发，再等周期
@@need 要解决什么
定时任务配置完，最怕"等到天荒地老才发现任务本身就有 bug"。怎么调试定时任务？

@@idea 核心思路
**调试铁律：先手动触发验证，再交给周期调度**：

```text
① 手动触发   /cron run <任务>（或向导里"立即执行"）
② 检查结果   任务内容对不对？投递到没到？
③ 修正      有 bug 就改任务内容/表达式/投递
④ 才启用周期 → 让 cron 按表达式接管
```

理由很直观：**手动跑一次=所见即所得**，把"任务本身的问题"与"调度的时机问题"分开排查。千万不要"配完就等"——等到点才发现任务内容错的，白白浪费一个周期。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 配完 cron 就等第二天看结果 | 先手动触发：10 秒内确认任务逻辑，而不是 24 小时后才发现错 |
| 手动跑成功但到点没跑 | 那就是调度环节问题：查网关运行、cron 表达式、时区 |
| 手动触发和周期触发结果不一样 | 周期触发时的环境（网关负载、平台状态）可能不同；以日志为准复盘 |

@@point ⑦ Web 仪表板：浏览器里的"控制面板"
@@need 要解决什么
命令行再好，"可视化总览"仍有不可替代的价值：任务、状态、日志一眼扫过去。Web 仪表板就是这块"玻璃窗"。

@@idea 核心思路
**Hermes 提供 Web 仪表板**，默认地址 `http://localhost:9119`（"dashboard" 用来可视化查看任务/logs 等；默认端口 9119）。

| 能力 | 说明 |
|---|---|
| 浏览器访问 | 打开 localhost:9119 即可（无需登录/简单鉴权，以实际版本为准） |
| 看什么 | 定时任务状态、运行日志、服务器状态等 |

价值：**诊断"任务到底跑没跑"的图形化入口**——比翻终端日志直观。用途与 `hermes mcp list`/`/cron list` 互补：命令是精确定位，仪表板是全局视野。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 打开 localhost:9119 空白/拒绝连接 | 仪表板是**独立进程**：先 `hermes dashboard` 把它起起来，再开页面 |
| 端口被占用 | 看一下 config.yaml/日志确认实际端口；被占用可换端口：`hermes dashboard --port 8080` |
| 只依赖仪表板不看命令输出 | 仪表板适合总览，深挖细节（具体报错）要回终端日志；两手都要 |

@@point ⑧ 常用命令全景：四大类收个总
@@need 要解决什么
十一个章节下来，命令散落各处。最后把它们收进"一张全景图"，随用随查。

@@idea 核心思路
把全书命令按用途分四大类（合并常用命令表与各章已学）：

**① 配置与信息类**
```bash

hermes tools              # 工具/工具集查看与配置
```

**② 技能与记忆类**
```bash

**③ 网关与集成类**

```

**④ 自动化与运维类**
```bash

hermes dashboard          # 打开 Web 仪表板（如提供）
```

记忆锚点：**"配置查、技能管、网关接、Cron 自动"**——四句话盖住全书命令主线。

@@trap 坑在哪

| 想一口气背完所有命令 | 只背四类锚点+每类 1 条代表命令；其余 `hermes --help` 现查 |
| 命令忘在后面章节翻找 | 保留本页"命令总表"当速查卡；比翻全书快 |

@@point ⑨ URL 与端口的"本地服务观"
@@need 要解决什么
第 4 章的 localhost:8080、本章的 localhost:9119——漫游期间反复出现端口号。它们背后的"本地服务观"值得统一理解。

@@idea 核心思路
这一切都是 **WSL 里的本地服务通过端口暴露、Windows 浏览器可访问**（第 2/4 章铺垫过）：

| 服务 | 地址 | 谁在用 |
|---|---|---|
| 案例前端页面 | http://localhost:8080 | 你（浏览器） |
| Hermes Web 仪表板 | http://localhost:9119 | 你（浏览器） |
| 其它本地工具服务 | 各自端口 | 视工具而定 |

三条规律：**① 默认只在本地（localhost）监听，外部机器访问不到——这是安全默认；② 端口被封/占用就改配置换端口；③ 服务没起=地址打不开，先保服务再谈页面**。以后遇到任何"本地端口打不开"，先按这三条排查。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 想从手机访问 localhost:9119 | localhost 只在本机；要跨设备访问需配置端口转发/公网地址（要公网访问还得 `--host 0.0.0.0`，并务必配好鉴权）（进阶操作，默认不做） |
| 端口冲突打不开 | 换端口 + 重启对应服务，别死磕同一端口 |
| 打不开先怀疑"防火墙" | 本地 localhost 一般与防火墙无关；先查服务是否真的在跑（ps / 端口占用） |

@@point ⑩ 自动化红线：无人值守不等于无人审查
@@need 要解决什么
定时任务让 Agent 无人值守地执行命令、推送消息——**这份"自主权"怎么给才安全**？需要建立自动化场景的安全边界。

@@idea 核心思路
"无人值守"解放了你，也意味着**脚本化的权限授予**。安全边界三原则：

| 原则 | 实践 |
|---|---|
| 任务内容只给"本来就会手动授权"的事 | 不会手动批准/approve 的活，别写进 cron |
| 危险操作留审批/避险机制 | 涉及删除、支付、发送的操作，任务设计成"先产出待办→等你确认"而非直接执行 |
| 投递目标可信 | 结果只推到可信会话；不把敏感结果推到公开群 |

**核心判断**：定时任务相当于"预先批准的授权书"——**你批准的是"到点自动执行"，而不是把安全审查全部豁免**。宁可任务产出"草稿"由你拍板，也不要全自动一把梭。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把 100% 自动的"删旧文件"写进 cron | 没人审批的破坏性操作风险巨大；自动任务以"只读/生成/提醒"为先，破坏性动作留人工 |
| 全自动任务跑出奇怪结果后追责 Agent | 先追任务设计：内容、投递、权限三处总有设计缺陷；改动前先手动验证 |
| 敏感内容推到公共群 | 投递目标选择小心翼翼；只读结论进群、完整数据留本地 |

@@point ⑪ 从"会用"到"会养"：日常运维四件套
@@need 要解决什么
阶段接近尾声，Hermes 不再只是"学完的软件"，而是"要长期养的伙伴"。日常怎么保养？

@@idea 核心思路
**日常运维四件套**（频率由低到高）：

| 周期 | 动作 | 命令/入口 |
|---|---|---|
| 每会话 | 确认网关在跑、平台消息正常 | 发条消息自测 |
| 每周 | 技能/记忆体检：删过时、补缺失 | hermes skills list / hermes journey |
| 每月 | MCP 与 Token 审计：不用的下线、过期的更新 | hermes mcp list + 平台后台 |
| 每季度 | 版本升级：跟进 hermes 更新，顺带回归 | 官方更新渠道 |

**"养"的本质：把第一阶段学的每样能力，变成定期维护的习惯**。进化不是装完就完，是"用+检+修"的循环——这正呼应"自我进化的超级智能体"里的"进化"二字。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
