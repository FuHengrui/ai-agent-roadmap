@@point ① 什么是 MCP：AI 世界的 USB-C
@@need 要解决什么
先理解"为什么现在每个 AI 工具都在提 MCP"——它解决了什么问题，凭什么值得学。

@@idea 核心思路
**MCP（Model Context Protocol，模型上下文协议）** 由 **Anthropic 在 2024 年 11 月底推出**，是一种开放标准，旨在**统一大模型与外部数据源和工具之间的通信协议**。

讲义给了一个非常形象的比喻：**MCP 可以被比喻为 AI 应用领域的 USB-C 接口**。

为什么是 USB-C？因为 USB-C 的特点是"**一个接口，万物可插**"：鼠标、硬盘、显示器、充电器，统统一个口搞定。MCP 同理——**不同数据源和工具（数据库、网页接口、脚本、天气、票务……）用同一套协议接入 AI，AI 就能即插即用地"认识外部世界"**。没有 MCP 之前，每个工具都要单独给 AI 写一套接入代码；有了 MCP，接入成本大幅下降，生态开始爆发。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把 MCP 当成某个具体产品 | MCP 是**协议/标准**（像 USB 是接口标准），不是具体软件；它约束"怎么接"，不限制"接什么" |
| 以为 MCP=API 调用 | API 是"点对点对接"，MCP 是"统一标准对接"；MCP 上层还有工具发现、权限等能力 |
| 记错出品方和时间 | Anthropic 推出、2024 年 11 月底；本阶段实战用的 MCP 服务来自模型广场（魔塔） |

@@point ② MCP 的核心作用：AI 的"读现实"能力
@@need 要解决什么
MCP 到底给 AI 带来了什么？用一句话+三个能力概括。

@@idea 核心思路
MCP 的本质是**为大模型提供"认知外部世界的能力"**，让它能安全、灵活地调用各类资源，完成更复杂的任务。三大核心功能：

1. **安全访问本地和远程数据源**——限制权限地读文件、读数据库、读远程数据；
2. **调用外部工具**——数据库、网页接口、脚本等；3. **在多个系统之间无缝对话和协作**——让不同系统通过 AI 串起来。

一句话：**MCP 就像 AI 和真实世界之间的桥梁，使 AI 拥有了"读取现实"的能力。** 没有它 AI 是"盲人"——只能输出训练时学过的内容；有了它，AI 可以"查现在几点、问天气、买票、看航班"。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把"MCP 三大功能"背成死知识点 | 记它的本质：**数据**（安全访问）+**工具**（调用执行）+**协作**（系统串联），全是"让 AI 有手有眼" |
| 以为 MCP 会让 AI 什么都能干、没边界 | 有边界：权限管理、沙箱、人工审核（Codex 的沙箱章节会细讲限制机制） |

@@point ③ MCP 的三个核心组件：Host / Client / Server
@@need 要解决什么
MCP 基于客户端-服务器模式，三个角色各司其职。这是理解 MCP 架构的关键地图。

@@idea 核心思路
MCP 由三个核心组件构成，分工如下：

| 组件 | 是什么 | 类比 / 职责 |
|---|---|---|
| **MCP Host（主机）** | 提供 AI 交互环境的应用，如 Claude Desktop、Cursor 等 | AI 的"**操作台**"：用户在主机里与 AI 对话，主机负责任务调度和用户指令解析 |
| **MCP Client（客户端）** | 在主机内运行的通信桥梁 | 将用户请求转化为**标准化的 API 调用（基于 JSON-RPC 格式）**，并管理服务器响应 |
| **MCP Server（服务器）** | 轻量级程序，暴露特定功能（文件读写、数据库查询、Web 搜索等） | 每个服务器**专注于单一资源类型**，模块化设计支持灵活扩展 |

流程示意：**用户 ↔ Host（操作台）↔ Client（翻译官，JSON-RPC）↔ Server（工具人，如天气/票务）**。多个 Server 可以像 U 盘一样插在一个 Host 上，即插即用。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| Host/Client/Server 混作一团 | 记忆锚点：Host=**你用的 App**（操作台），Client=**App 里负责通信的那层**（翻译官），Server=**提供能力的程序**（工具人） |
| 以为一个 Host 只能挂一个 Server | 一个 Host 可插多个 Server，这就是"MCP 广场"生态的基础 |
| 把 Trae 当 MCP Server | Trae 是 Host——你在 Trae 里用 AI，AI 通过 Client 调 Server（如高德 MCP） |

@@point ④ MCP 的两种通信机制：Stdio 与 Streamable HTTP
@@need 要解决什么
Host 和 Server 之间怎么"通话"？两种传输机制分别适用什么场景？

@@idea 核心思路
MCP 支持两种主要的传输方式：

**1. Stdio（标准输入输出）**

- 通过标准输入/输出流实现通信；
- 在**构建本地集成和命令行工具**时特别有用；
- 适合：本地跑的 Server，比如让你本机 AI 读文件、执行脚本。

**2. Streamable HTTP（官方推荐）**

- 使用 **HTTP POST 请求** 进行客户端到服务器的通信；
- 通过可选的 **Server-Sent Events（SSE）流** 实现服务器到客户端的通信；
- 适合：远程服务——比如云上的天气 API、票务 API，网络化的 MCP 服务大多用这种方式。

一句话：**本地小工具用 Stdio，远程网络服务用 Streamable HTTP（官方推荐）。**

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为两种传输可以混用 | 一个 Server 通常选定一种传输；配置时看服务方文档说明 |
| 本地 Stdio 服务挂了 | 确认启动命令和依赖正确；Stdio 服务用命令行启动，报错会打到终端 |
| 远程服务连不上 | 检查网络、URL 是否正确、是否需要鉴权（API Key）；对照服务方文档 |

@@point ⑤ 实战全景：智能旅行助手是什么
@@need 要解决什么
概念完毕，进入实战：我们要在 Trae 里做一个什么样的应用？

@@idea 核心思路
**智能旅行助手**是一款借助 **Trae IDE 集成高德地图 MCP、12306-MCP、Variflight-MCP** 等多个服务的智能应用。它能提供**一站式的出行规划服务**：

- **地图导航**（高德地图 MCP）
- **铁路票务查询**（12306-MCP）
- **航空航班信息查询**（Variflight-MCP/飞常准）

三个能力有机融合后，用户只要说一句"国庆七天，帮我安排杭州七日游"，AI 就能结合实时天气、景点余票、地铁公交、航班车次，输出**包含行程概览、每日详细时间表、交通指引、住宿餐饮、预算与行李清单的完整旅行计划**，甚至生成可视化网页。

它演示的正是本章开头那句话：**MCP = 让 AI 接上真实世界。**

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为这是"官方出品"的应用 | 它是讲义演示的**开发案例**，用 Trae + 三个 MCP 服务搭建，不是预装应用；你要照着做 |
| 三个 MCP 服务分不清 | 高德=地图/天气/导航；12306=火车票；飞常准（Variflight）=航班/天气/航班舒适度 |

@@point ⑥ 配置 12306 MCP：从魔塔 MCP 广场接入
@@need 要解决什么
第一个 MCP 服务怎么找、怎么配置？这里走的就是"标准姿势"。

@@idea 核心思路
配置 12306 MCP 的入口是**魔塔 MCP 广场**（https://modelscope.cn/mcp ）：

1. 打开魔塔 MCP 广场；
2. 找到 **12306-MCP 车票查询工具**；
3. 按广场指引获得 MCP 服务的接入方式（服务名/URL/命令行启动方式等）；
4. 在 Trae 的 MCP 配置入口中，把这个服务添加进来。

配置完成后，AI 就"会买票了"——至少能查车次、余票、票价等信息（实际操作以服务提供的工具能力为准）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 在广场找不到 12306-MCP | 用"12306"关键词搜索；魔塔广场服务会更新，以当日广场列表为准 |
| 配好后 AI 说"没有买票能力" | MCP 提供的工具范围因服务而异，区分"能查"与"能买"；先确认 Server 暴露了什么工具 |
| 复制接入信息出错 | 注意区分"远程 URL 模式"和"本地命令行模式"两种接入，别混用 |

@@point ⑦ 配置高德地图 MCP：地图、天气、导航全家桶
@@need 要解决什么
旅行助手最核心的地图能力，来自高德地图 MCP。它提供哪些工具？

@@idea 核心思路
**高德地图 MCP** 为旅行助手提供地图类能力，包括：

- **实时天气查询**——每日高低温、天气状况；
- **实时门票余量查询**——景点余票动态获取；
- **交通规划**——高德地铁/公交 API；
- **景点导航**——唤起高德地图 App/网页导航；
- **地图绘制**——展示景点位置、访问路线。

这些能力让旅行计划从"纸面攻略"升级为"实时可执行方案"：行程里可以直接带"门票余量柱状图"、"景点间路线连线"、"点名字唤起导航"。

配置方式与 12306 相同：在魔塔 MCP 广场找到对应服务并接入 Trae；接入后核对工具的激活情况。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 高德 MCP 需要 API Key | 部分 MCP 服务需要你自己的高德开放平台 Key；按服务文档申请并配置，注意 Key 保密 |
| 唤起导航在 PC 上行为不同 | 设计时做了设备适配：安卓/iOS 唤起 App、PC 跳网页版——验证时按设备分别测 |
| 热门景点余票接口数据延迟 | 数据以服务返回为准，提示词里可要求"动态获取并展示"，但别承诺实时性 |

@@point ⑧ 配置飞常准（Variflight）MCP：航班与天气
@@need 要解决什么
旅行还涉及"飞过去"——航班信息由飞常准提供。

@@idea 核心思路
**飞常准（Variflight）** 的服务器提供多种工具，支持：

- **查询航班信息**——航班动态、起降时间等；
- **天气数据**——目的地/出发地天气；
- **航班舒适度指标**——机型、准点等维度综合评估。

接入方式和前两者相同（魔塔 MCP 广场 → 接入 Trae）。三个服务齐了之后，助手能力矩阵完整：**12306 管铁路、高德管地图+天气+导航、飞常准管航班**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 三个服务只有两个能连上 | 逐个排查：服务是否上线、接入信息是否最新、是否需要额外授权；先跑通一个再连下一个 |
| 把航班舒适度和天气工具搞混 | 舒适度是"这趟航班坐着舒不舒服"（准点/机型），天气是"目的地天气情况"，是不同工具 |

@@point ⑨ Agent 提示词设计：把能力编排成"旅行规划师"
@@need 要解决什么
服务接好了，但 AI 怎么"知道"自己是旅行规划师、该按什么步骤输出？——靠提示词。

@@idea 核心思路
讲义用一份完整提示词把 AI 定位成"经验丰富的智能旅行行程规划师"。核心内容分两层：

**先给角色与能力清单**：

```text
你是一个经验丰富的智能旅行行程规划师，基于智能集成平台（MCP）开发，拥有以下能力：
- 实时天气查询（高德地图MCP）
- 实时门票余量查询
- 交通规划（高德地铁/公交API）
- 景点导航（高德地图唤起功能）
- 地图绘制（高德地图）
- 行程可视化（路线图、时间轴图、门票图表）
```

**再给输出结构（总体规划步骤）**，要求最终产出包含六个区：

1. **行程标题区**：目的地、旅行日期与天数、天气信息摘要；
2. **行程概览区**：按日期分区的行程简表（用图标标识景点/餐饮/交通/住宿）；
3. **详细时间表区**：时间轴/表格，含时间、地点、停留时间、门票价格与余票；
4. **交通信息区**：换乘点、地铁公交线路、预计时间、路线可视化；
5. **住宿与餐饮区**：酒店地址、入住退房时间、推荐餐厅、便利设施；
6. **实用信息区**：紧急电话、旅行提示、预算摘要、行李清单。

再配合网页生成要求（HTML5 + Font Awesome + Tailwind CSS + JavaScript、响应式、数字杂志风格、Mermaid 图表、高德地图 API 标点与路线）——一份完整可执行的 Agent 提示词就成型了。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 提示词写太泛（"帮我规划一下"） | 要按讲义格式写**角色+能力+六区结构+技术规范**，AI 才有据可依 |
| 提示词里承诺了 MCP 提供不了的数据 | 能力清单必须与实际接入的 MCP 工具一致，别让 AI"硬编"不存在的余票数据 |
| 一个提示词塞太多要求 | 分步下发：先"角色+能力+六区结构"，再"网页生成技术规范"，再"地图/图表细节"，AI 逐轮吸收更稳 |

@@point ⑩ 发起实战：一句话触发完整交付
@@need 要解决什么
提示词写好了，最后一步：怎么"用起来"？真实请求长什么样，预期产出是什么？

@@idea 核心思路
配置完成、提示词就位后，直接向 Trae 发出需求（讲义原文示例）：

> **国庆正好七天，请帮我安排一个旅行计划在杭州玩七天**

预期是 AI 调用已接入的三个 MCP 服务，产出：

- 结合实时天气/余票/车次/航班的**完整七日行程**；
- 按提示词要求的**六区结构**组织内容；
- 可预览/可打开的**可视化网页**（行程路线、时间轴、门票余量图表、地图标注）。

这就是一次"从需求到成品"的 Vibe Coding + MCP 组合交付：**你说人话（需求），AI 用 MCP（真实数据）+ 代码（网页）把事办了**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 请求后 AI 没调用 MCP | 确认 MCP 服务已接好且工具在线；提示词里明确"使用高德 MCP 查询天气"等指令，引导它调用 |
| 输出缺区块（没预算/没行李清单） | 提示词六区结构逐条核对；追问"请补充实用信息区和预算摘要" |
| 网页打不开/样式乱 | 检查网络链路（CDN 字体/图标库需外网）；用"在浏览器中打开"验证真实渲染 |
| 觉得"这不就是个聊天" | 核心差别在**数据真实**：MCP 让天气/余票/车次是"查出来的"而非"编出来的"，这是 Agent 应用的意义 |

@@point ⑪ 实战复盘：MCP 应用的通用套路
@@need 要解决什么
做完一个案例，把"做 MCP 应用"的方法论抽出来，以后任何工具都能套。

@@idea 核心思路
从智能旅行助手中可以提取出 MCP 应用的**四步通用套路**：

```text
第一步  选服务：在 MCP 广场（如魔塔 modelscope.cn/mcp）找目标服务
第二步  接服务：把 Server 接入 Host（Trae），核对工具是否在线
第三步  写提示词：角色 + 能力清单 + 输出结构 + 技术规范
第四步  发请求：用自然语言发起真实需求，AI 调 MCP 拿数据并产出成果
```

任何"AI + 外部数据/工具"的 Agent 应用，都可以套这四步。这也是阶段 15（Hermes-Agent）+ 阶段 16（Trae/Cursor/Codex）两条线的交汇点：**Agent 的"大脑"是模型，"手眼"是 MCP。**

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 每个新需求都从零摸索 | 沉淀模板：服务清单+提示词模板存到项目里（可用 Rules 固化），复用效率翻倍 |
