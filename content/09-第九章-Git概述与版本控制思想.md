@@why 这一章在解决什么问题
你有没有把文件存成"**最终版**""**最终版2**""**打死不改版**"？

改错一行代码想反悔，结果发现原来的版本早被覆盖了；和同学一起改同一个项目，改完互相全覆盖，谁也说不清哪个才是最新的。

这一章先把"版本控制"这四个字讲透：它是怎么来的、能解决什么问题、Git 和老的 SVN 有什么区别、代码在 Git 里是怎么流转的。**这一章不敲一行命令**，先把"为什么"想明白——后面五章全是围绕这些概念动手。

@@point ① 没有版本控制时，代码是怎么"丢"的
@@need 要解决什么
写代码最怕的不是报错，是**改坏了恢复不回来**。

你辛辛苦苦调好的功能，为了加个新需求改了十行，结果新需求没做出来，旧功能也回不去了。以前大家怎么"备份"？把文件复制一份改名——于是出现了 `论文最终版.doc`、`论文最终版2.doc`、`最终版3打死不改.doc`。文件一多，你自己都分不清哪个才是最新的。

@@idea 核心思路
版本控制解决的就是这件事：**自动替你保存每一次改动，随时能回到任意一个历史版本**。

它像一个"数据库"，完整保存项目的每一个快照（版本）；你想看某个旧版本，它还能告诉你**当前版本和上一个版本之间到底改了什么**。你只管提交，剩下的对比、找差异、回滚，都交给它。

还有个细节：项目是**多人协作**的，修改无法避免，我们不能接受"一人一份文件"，但又希望**每次更改都被记录**——这恰恰是版本控制的标准使用姿势。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为版本控制 = 网盘/云盘备份 | 网盘备份的是"最新的那份文件"，版本控制存的是**每一次改动**：一个是单张照片，一个是完整相册 |
| 手动复制文件当备份 | 人多手杂根本不知道哪个版本是真的；版本控制是系统化管理，不是多存几份 |

@@point ② Git 的身世：Linus 为什么亲手造一个版本控制工具
@@need 要解决什么
Linux 内核是全世界最大的开源项目之一，几千名开发者同时改一套代码。2005 年前后，Linux 内核在用的商业版本控制工具**不再免费**，社区面临选择：花钱买，或者自己造。Linus 托瓦兹（没错，就是造 Linux 的那个人）决定：**自己写一个**。

@@idea 核心思路
需求非常明确：这个工具必须**快**（内核代码量巨大）、**分布式**（开发者遍布全球，不能都挤在一台服务器上）、**能撑住超大项目**。

于是 2005 年 Git 诞生了。如今它已经是全世界使用最广的版本控制工具——几乎所有主流代码托管平台（GitHub、Gitee、GitLab）都是基于 Git 实现的。记住一条：**Git 是开源免费的**，任何个人和公司都能直接用。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把 Git 和 GitHub 当成一个东西 | Git 是**工具（软件）**，GitHub 是**托管平台（网站）**；就像"微信这个软件"和"微信上的人"不是一回事 |
| 以为 Git 只适合程序员 | 任何"要反复改、还要多人改"的文件都适合：论文、设计稿、配置、合同……Git 管的是文件版本 |

@@point ③ 集中式 SVN：一个服务器当"大本营"
@@need 要解决什么
在 Git 流行之前，主流方案是集中式版本控制，代表是 SVN。它解决了"改坏了回不来"的问题，但引入了一个新麻烦：**所有人都依赖那台中央服务器**。

@@idea 核心思路
SVN 的工作方式：一台服务器存着所有代码（大本营），所有人改代码前，得先从服务器**下载一份拷贝**到本地，改完之后**再传回服务器**。一切提交、还原、对比，都必须在"连得上服务器"的前提下进行。

优点也明显：代码一致性非常高，管理员能轻松掌控每个开发者的权限，适合人数不多的项目。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 服务器断网/宕机，开发直接停摆 | 集中式的固有缺陷：**断网 = 不能提交、不能还原、不能对比**，只能干等 |
| 所有人都往一台服务器写数据 | 服务器压力大、数据库容量暴涨，人一多就明显变慢 |

@@point ④ 分布式 Git：人人都有一个完整仓库
@@need 要解决什么
SVN"服务器一挂全组瘫痪"的问题怎么破？思路翻转一下：**与其让所有人共用一份代码库，不如让每个人本地都有一份完整的库**——这就是分布式。

@@idea 核心思路
在分布式版本控制里，**每个开发者本地都有一份完整的版本库**（含全部历史记录），不联网也能提交、能看历史、能回滚；"中央服务器"退化成**一个方便大家交换代码的公共仓库**，不再是唯一的命根子。

你推送（push）到远程、从远程拉取（pull），本质只是**同步**，不是"上传给服务器保管"。也正因为如此，Git 的**公共服务器压力和数据量都不会太大**，而且速度快、灵活，任意两个开发者之间都更容易解决冲突。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为"推送"是把代码上传给服务器保管 | 你本地本来就有完整版本库，push 只是把新提交**同步**给公共仓库；哪怕远程没了，本地历史也不丢 |
| 以为离线就不能工作 | 分布式恰恰是**离线友好**：提交、回滚全在本地完成，联网只在"和队友交换"时才需要 |

@@point ⑤ Git 和 SVN 怎么选：一张表看懂谁强谁短
@@need 要解决什么
面试和选型时最常被问：Git 和 SVN 到底差在哪？答不出"三句内说清核心差异"，说明你只是背过名字。

@@idea 核心思路
| 维度 | SVN（集中式） | Git（分布式） |
|---|---|---|
| 代码库 | 只有服务器一份 | 每人本地一份完整库 |
| 离线工作 | ❌ 断网基本瘫痪 | ✅ 照常提交、回滚 |
| 服务器压力 | 大（所有数据集中） | 小（只承担交换） |
| 分支 | 支持，但笨重 | 轻量、快，分支是核心玩法 |
| 权限管控 | 直接、易掌控 | 靠托管平台（GitHub/Gitee）实现 |
| 学习成本 | 低，符合直觉 | 高，不符合常规思维，**易学难精** |

一句话：**小团队、要权限管控、在同一个内网 → SVN 够用；多人异地协作、要灵活分支、要离线开发 → 选 Git**。今天的新项目几乎默认 Git。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为 Git 有"锁文件"机制 | SVN 靠锁文件防止冲突，Git 靠**合并**处理冲突——Git 更灵活，但也意味着冲突得自己解（第十二章讲） |
| 以为 Git 什么项目都完胜 | SVN 的权限管理更直接，传统企业环境仍有存量使用；不是无脑选 Git |

@@point ⑥ 四大区域：文件在 Git 里的"三个家 + 一个远方"
@@need 要解决什么
第一次敲 `git add`、`git commit`、`git push` 时肯定懵：文件到底在哪？为什么 add 完了还要 commit？为什么 commit 完了还要 push？

因为 **Git 把文件分成了几个不同的"房间"**，每一步命令就是把文件从一个房间搬到另一个房间。

@@idea 核心思路
```
┌────────────┐  git add  ┌────────────┐ git commit ┌────────────┐ git push ┌────────────┐
│  工作区     │ ────────► │  暂存区     │ ─────────► │  本地仓库   │ ────────► │  远程仓库   │
│ Workspace  │           │ Index/Stage│            │ Repository │          │  Remote    │
└────────────┘           └────────────┘            └────────────┘          └────────────┘
  你写代码的地方            临时存放改动              安全存放所有版本            队友能拿到的地方
```

- **工作区（Workspace）**：你平时写代码的文件夹，文件在这随便改；
- **暂存区（Index/Stage）**：一个"待提交清单"，把想提交的改动先装进去（它其实只是 `.git` 里的一个文件，保存即将提交的文件列表）；
- **本地仓库（Repository）**：安全存放所有已提交版本的地方，`HEAD` 指向最新放入仓库的版本；
- **远程仓库（Remote）**：托管在服务器上的仓库，比如 GitHub/Gitee，用来和队友交换，可以简单理解成项目组里专门用于远程数据交换的一台机器。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为 `git add` 就是提交了 | add 只是把文件放进**暂存区**，还没写进仓库；**commit 才算落库** |
| 以为 commit 后队友就能看到代码 | commit 只是存进**本地仓库**，要 **push** 到远程，队友才看得到 |

@@point ⑦ 基本工作流：一次提交的完整旅程
@@need 要解决什么
知道了四个区域，还要知道**日常最顺的流程**——先做什么后做什么，才不会出现"该提交的没提交、不该提交的提交上去了"。

@@idea 核心思路
标准的 Git 工作流三步：
1. **在工作区**创建、修改文件；
2. 用 `git add` 把要版本管理的文件放入**暂存区**；
3. 用 `git commit` 把暂存区的内容正式提交进**本地仓库**——这一步之后，这个版本才算"存档"了。

需要和队友共享时，再加第四步 `git push` 推到远程仓库。这四步是本阶段所有操作的总纲，后面每一章都是往这条主线上加细节。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 提交时把不该提交的东西（编译产物、密钥）也提交了 | 提交前先 `git status` 看一眼清单；配合 `.gitignore`（第十一章）把无关文件挡在外面 |
| commit 说明乱写"111""update" | 以后翻历史完全看不懂；习惯写"做了什么、为什么" |

@@point ⑧ Git 存的是快照，不是差异
@@need 要解决什么
很多第一次用 Git 的人会问：Git 是不是像"补丁大全"一样，每个版本只存改了多少？

这个理解不对，而且会影响你判断 Git 为什么快、为什么磁盘占用可控。

@@idea 核心思路
**Git 不保存文件前后变化的差异数据，它只关心文件整体是否发生了变化。**

每次提交时，Git 会给每个文件算一个校验和（用的 SHA-1 算法）：校验和变了 = 文件变了，就把这个文件的**新快照**存起来；校验和没变 = 文件没动，Git **复用上次的快照，不重复存**。所以哪怕你有一百个版本，没改过的文件其实只存了一份，Git 依然快、依然省空间。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为 Git 每个版本都复制一遍整个项目 | 没变化的文件只存一份（靠校验和判断），所以仓库不会无限膨胀 |
| 以为"版本差异"是 Git 存好的 | diff 是**事后用快照对比算出来**的，不是 Git 事先存了差异——理解这一点，看 diff 输出时才不会晕 |

@@summary
| 问题 | 答案 |
|---|---|
| 版本控制解决什么问题 | 自动保存每次改动的快照，随时回滚到任意历史版本，多人协作不互相覆盖 |
| Git 是谁造的、为什么造 | Linus 托瓦兹为 Linux 内核开发创造的免费开源分布式版本控制系统 |
| SVN 和 Git 的本质区别 | SVN 集中式、依赖服务器、离线瘫痪；Git 分布式、每人一份完整库、离线可用 |
| 四大区域是什么 | 工作区（写代码）→ 暂存区（临时装改动）→ 本地仓库（存档）→ 远程仓库（共享） |
| 基本工作流程 | 改文件 → git add → git commit → git push |
| Git 怎么存数据 | 存**快照**不存差异，用 SHA-1 校验和判断文件是否变了 |

一句话记住本章：**版本控制 = 给项目装时光机；Git = 分布式版时光机，人人本地都有一台；文件在工作区 → 暂存区 → 本地仓库 → 远程仓库四个房间之间流转，每一步命令就是搬一次家。**
