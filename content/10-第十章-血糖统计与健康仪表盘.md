@@why 这一章在解决什么问题
后端把统计算出来了，可患者要"一眼看懂"——数字堆成列表没人看。本章把**统计学结果可视化**：用 ECharts 把血糖趋势、健康评分、营养摄入变成仪表盘。本章解决三件事：**一是 ECharts 图表配置**（折线 + 阈值辅助线 + 仪表盘），**二是健康评分与风险色带的业务规则**（把 stats 转成 0-100 分），**三是前端数据流的组织**（Pinia store + axios 封装 + 多接口并行加载）。

关键认知：**图表不是"画得好看"，是"让关键阈值一眼可见"**——3.9/7.0/10.0 三条 markLine 辅助线，比任何文字都直观。

@@point ① 前端技术栈：Vue3 + Vite + Element Plus + ECharts
@@need 要解决什么
前端骨架用什么？为什么选这套组合？

@@idea 核心思路
package.json 依赖一览：

| 依赖 | 职责 |
|---|---|
| vue ^3.5 + vue-router ^4.5 | 组件化 SPA + 路由 |
| pinia ^2.3 | 全局状态管理（患者/血糖/饮食 store） |
| axios ^1.7 | HTTP 请求封装 |
| element-plus ^2.9 | UI 组件库（卡片/标签/表格） |
| echarts ^5.5 + vue-echarts ^7 | 图表 |

工程入口流程：`main.ts` 创建应用 → 注册 router/pinia → 挂载 App.vue；`vite.config.ts` 配 devServer 代理 `/api → http://localhost:8000`（解决跨域）；`npm run dev` 起 5173。

**前后端联调的双保险**：后端 CORS（allow_origins=["*"]）+ 前端 Vite 代理——两层都通才能请求成功。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| npm run dev 后请求 /api 404 | vite.config.ts 没配 proxy；代理目标必须指到后端 8000 |
| 环境变量 VITE_API_* 不生效 | .env 里 VITE_ 前缀自动注入；但本项目直接用相对路径 /api 走代理更简单 |

@@point ② axios 封装：统一 baseURL 与超时
@@need 要解决什么
几十个接口请求，每个都写 `http://localhost:8000/api/...`？超时、请求头怎么办？

@@idea 核心思路
```ts
// src/api/index.ts
import axios from 'axios'

const api = axios.create({
  baseURL: '/api',             // 相对路径，走 Vite 代理
  timeout: 60000,              // 60 秒超时（LLM 接口响应慢，必须放宽）
  headers: { 'Content-Type': 'application/json' },
})

export default api
```

要点：
- **baseURL='/api'**：所有请求自动加前缀，与后端 main_router 的 prefix 对应；
- **timeout=60000**：AI 接口（报告/对话）可能要 10-30 秒，60 秒超时是刚需——默认 0（不超时）反而容易挂死页面；
- 每个业务模块再包一层（`bloodSugarApi`/`dietApi`/`medicationApi`），类型安全、语义清晰：

```ts
export const bloodSugarApi = {
  stats: (patientId: number, days = 7) =>
    api.get<BloodSugarStats>(`/blood-sugar/patient/${patientId}/stats?days=${days}`),
}
```

公共 axios 实例 + 按模块的 API 对象，是中小型前端的标准组织法。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| LLM 接口超时报错 | timeout 太短；60s 起，视模型响应时间再调 |
| 请求路径写全域名 | 绕开代理直连可能被 CORS 拦；统一用 /api 相对路径 |

@@point ③ Pinia store：状态集中与复用
@@need 要解决什么
仪表盘、血糖页、报告页都要用同一份 stats 数据，怎么避免各页面重复请求？

@@idea 核心思路
Pinia store（如 `stores/bloodSugar.ts`）持有"患者、记录、统计"三块状态并在页面间共享：

```ts
// 伪代码，展示核心形态
export const useBloodSugarStore = defineStore('bloodSugar', {
  state: () => ({ records: [], stats: null }),
  actions: {
    async fetchRecords(patientId, days = 7) {
      const { data } = await bloodSugarApi.list(patientId, days)
      this.records = data
    },
    async fetchStats(patientId, days = 7) {
      const { data } = await bloodSugarApi.stats(patientId, days)
      this.stats = data
    },
  },
})
```

学习要点：
- `useXxxStore()` 在任意组件调用返回**同一实例**——仪表盘改了 records，血糖页自动拿到；
- actions 里发请求、改 state，组件只 `store.fetchStats()` 不碰 axios；
- 患者 store 管"当前患者是谁"，其他页面 watch 它变化自动刷新（仪表盘正是这么做的）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 每个页面自己发请求 | 数据不同步且重复请求；状态必须进 store |
| 切换患者后页面不更新 | watch currentPatient.id 变化重新 loadAll（Dashboard 的标准做法） |

@@point ④ 折线图 + 三条辅助线：血糖趋势
@@need 要解决什么
几十条血糖记录怎么展示才有意义？关键阈值怎么画上去？

@@idea 核心思路
utils/charts.ts 的 `getBloodSugarChartOption`：

```ts
series: [{
  type: 'line', data: data.values, smooth: true,
  markLine: {   // 关键！阈值辅助线
    data: [
      { yAxis: 3.9,  lineStyle: { color: '#E6A23C' }, label: { formatter: '低血糖 3.9' } },
      { yAxis: 7.0,  lineStyle: { color: '#67C23A' }, label: { formatter: '目标上限 7.0' } },
      { yAxis: 10.0, lineStyle: { color: '#F56C6C' }, label: { formatter: '高血糖 10.0' } },
    ],
  },
  areaStyle: { opacity: 0.1 },   // 渐变面积
}],
xAxis: { type: 'category', data: data.times },
yAxis: { type: 'value', name: 'mmol/L', min: 2, max: 16 },
dataZoom: [{ type: 'inside' }],
```

设计解读：
- **三条 markLine 只是「参考刻度」，不能当诊断线**：3.9 / 7.0 / 10.0 是**空腹**口径；餐后 2h 正常上限是 7.8、随机是 11.1。图上一律画同一组线，会和后端按 measure_type 算出来的达标率打架（图里绿区的空腹 8.0，后端判高血糖）。要么按类型分色画，要么在图注里写清「此图按空腹口径参考」；
- y 轴固定 2-16：避免自动缩放导致阈值线位置抖动、误导视觉判断；
- smooth + areaStyle：曲线圆滑、面积填充，观感更"健康管理"。

**图表规范的核心是"固定的医学参照系"**，不是默认的自动刻度——这直接关系到使用者对"高不高"的判断。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| y 轴自动缩放，阈值线位置每天不同 | 固定 min/max，让参照系稳定（本项目 2-16） |
| markLine 不显示 | ECharts 配置层级写错；series 里对象要有 yAxis 键 |
| 折线断点（缺数据） | 前端按时间序列补 null 或后端返回连续时间轴；本项目按记录序列直接画 |

@@point ⑤ 仪表盘（gauge）：健康评分可视化
@@need 要解决什么
"达标率 72%"缺乏冲击力——用仪表盘把 0-100 分直观呈现。

@@idea 核心思路
`getHealthScoreOption(score)` 用 ECharts gauge：

```ts
series: [{
  type: 'gauge', startAngle: 200, endAngle: -20, min: 0, max: 100,
  itemStyle: { color: score >= 80 ? '#67C23A' : score >= 60 ? '#E6A23C' : '#F56C6C' },
  progress: { show: true, width: 18 },   // 进度环
  pointer: { show: false },
  detail: { fontSize: 36, formatter: '{value}分' },
  data: [{ value: score }],
}]
```

色彩即结论：**≥80 绿、≥60 橙、<60 红**——扫一眼颜色就知道控制好不好，不用读数字。这与后端 risk_level（低/中/高风险）相呼应，但维度不同：一个是"达标率映射得分"，一个是"多因子风险判定"。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 仪表盘颜色与风险等级脱节 | 前端 score 色带 + 后端 risk 标签各自独立实现，业务上要口径对齐 |
| gauge 数值不动 | detail.formatter 模板字符串要写 `'{value}分'` 带花括号 |

@@point ⑥ 健康评分规则：达标率 → 得分
@@need 要解决什么
time_in_range（达标率）怎么换算成 0-100 分？规则在哪层定？

@@idea 核心思路
Dashboard.vue 里的 computed：

```ts
const healthScore = computed(() => {
  if (!bloodStore.stats) return 0
  const tir = bloodStore.stats.time_in_range
  if (tir >= 90) return 90
  if (tir >= 70) return 75
  if (tir >= 50) return 60
  return 40
})
const scoreTip = computed(() => {
  const s = healthScore.value
  if (s >= 80) return '血糖控制良好，继续保持！'
  if (s >= 60) return '血糖控制一般，注意饮食和用药。'
  return '血糖控制不理想，建议咨询医生。'
})
```

| 达标率 | 得分 | 文案 |
|---|---|---|
| ≥90% | 90 | 控制良好 |
| ≥70% | 75 | 控制一般 |
| ≥50% | 60 | 一般 |
| <50% | 40 | 不理想 |

拆解：**分段映射而非线性公式**——用 4 档阈值把"达标率"降维成"分数+文案"，简单明确、易测试。这是"前端业务规则"的典型位置：后端算 stats，前端做展示语义。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 规则在前端后端各写一遍 | 展示层规则放前端可接受，但**医学判定**（risk_level）必须后端统一，别两边算 |
| 无 stats 时 score=0 被误读 | 前端要配套"暂无统计"空态（el-empty），别让 0 分吓到患者 |

@@point ⑦ 多接口并行加载：Promise.all
@@need 要解决什么
仪表盘要同时拿血糖记录、统计、今日营养、用药——四个请求串行要等 4 倍时间？

@@idea 核心思路
```ts
async function loadAll() {
  const p = patientStore.currentPatient
  if (!p) return
  const pid = p.id
  await Promise.all([                    // 四个接口并行！
    bloodStore.fetchRecords(pid),
    bloodStore.fetchStats(pid),
    dietStore.fetchDaily(pid),
    medicationApi.list(pid).then(({ data }) => { medications.value = data }),
  ])
}
onMounted(loadAll)                       // 进入页面即加载
watch(() => patientStore.currentPatient?.id, loadAll)  // 切换患者重载
```

三个点：
- **Promise.all 并行**：四个独立请求一次并发，总耗时 ≈ 最慢的一个；
- **onMounted 初载**：进入仪表盘先拉数据；
- **watch 换患者重载**：当前患者切换，仪表盘自动刷新。

**聚合加载的关键纪律**：能并行的绝不串行；但共享状态（先选患者才有 pid）必须等依赖就绪。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 四个请求串行 await | 总耗时翻 4 倍；独立请求必须 Promise.all |
| 没有患者就 loadAll | 先判 `if (!p) return`，避免用 undefined.id 发请求 |
| 换患者不刷新 | 必须 watch patient_id；这是仪表盘最常见"数据不更新"根因 |

@@point ⑧ 从仪表盘反推架构：数据从哪来
@@need 要解决什么
看一眼仪表盘组件，它的每个数字分别来自后端哪个接口？

@@idea 核心思路
| 仪表盘块 | 数据 | 后端接口 |
|---|---|---|
| 血糖趋势图 | records | GET /api/blood-sugar/patient/{id}?days=7 |
| 健康评分 | stats.time_in_range → score | GET /api/blood-sugar/patient/{id}/stats |
| 血糖统计卡 | avg/达标率/趋势/风险 | 同上 stats |
| 今日用药 | medications | GET /api/medication/patient/{id} |
| 今日营养 | dailyNutrition | GET /api/diet/patient/{id}/daily |

**仪表盘是后端能力的"需求清单"**：它需要 stats（第六章）、daily 营养（第七章/第八章）、用药列表（第七章）——前后端契约完全由 /api 前缀对齐。学前端的最快路径：**从页面反查接口，理解"每块 UI 背后是哪段后端逻辑"**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| UI 有数据但和接口字段对不上 | 字段命名不一致（如后端 period_days vs 前端 count）；联调以接口响应为准 |
| 某个卡片一直空 | 对应接口报错（404/422/超时）被吞；看 Network 面板逐个排查 |
