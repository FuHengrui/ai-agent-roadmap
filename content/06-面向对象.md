@@h1 第六章　面向对象
@@sub 阶段 1 · 大语言模型基础与工程化实践　|　|　难度 ★★★

@@why 这一章在解决什么问题
前五章你已经能写出"能干活的程序"了。但你会发现一个问题：**代码一长就散架。**

数据在这个文件里，处理它的函数在那个文件里。改一个字段要翻三个地方。别人（或者三个月后的你）接手，得先花半天搞清楚"这个 `data` 到底是什么结构"。

**根本原因**：你一直在用"面向过程"的方式写代码——**数据和操作数据的逻辑是分开的**。

这一章要换个思路：**把"一类东西的数据"和"这类东西能做的事"打包在一起**，做成一个**类**。

比如"一条岗位"，它有 `title`、`city`、`salary`（数据），也能 `clean()`、`to_row()`（行为）。把这两者捆在一起，代码就有了**结构**。

**这一章是全阶段最长的一章，也是最容易学到一半就放弃的一章。** 但它是后面所有框架的地基——LangChain 里全是类，你看不懂类就没法学。

@@map 这一章在整个知识库里的位置
第五章：学会了封装"逻辑" —— 函数
**本章** ← 你在这里：把"数据 + 逻辑"打包成类，让代码有结构
第七章 异常机制 —— 类的方法出错了怎么优雅地报告
第八章 模块 —— 把一堆类拆到不同文件，并做一个完整项目
阶段终点 Novel 自动化生成系统 —— 一个真正用上"类 + 模块 + 异常"的实战项目
后续阶段 —— LangChain / Agent 全是类的世界

@@note info 这一章的学习方法
这一章的量，一口气看不完也记不住。**建议分三段**：

- **第一段（类的基础）**：类、对象、`__init__`、实例属性、方法——**这段必须扎实**，是全部后续的基础
- **第二段（封装与特征）**：私有属性、`@property`、继承、多态——**这段理解思想比分清语法重要**
- **第三段（进阶）**：`MRO`、特殊方法、设计模式——**第一遍看不懂很正常，先有个印象，用的时候回来查**

**别追求第一遍全懂。** 类这个东西，是"写多了自然通"的。

@@point ① 面向过程 vs 面向对象
@@need 要解决什么
这不只是语法区别，是**两种组织代码的思维方式**。选错了，项目越大越痛苦。
@@idea 核心思路
**面向过程**：关注"**步骤**"。我要做这件事，第一步干什么、第二步干什么。

```python
# 面向过程：数据和函数是分开的
job = {"title": "前端", "salary": "8-15K"}

def clean_salary(job):          # 要改数据，得把数据传进去
    raw = job["salary"]
    ...                          # 一长串处理
    return num

def format_job(job):
    clean_salary(job)            # 又要把数据传一遍
    ...
```

**面向对象**：关注"**谁来做**"。我要一个"岗位对象"，它自己知道怎么清洗自己的薪资。

```python
# 面向对象：数据和行为打包在一起
class Job:
    def __init__(self, title, salary):
        self.title = title
        self.salary = salary

    def clean_salary(self):      # 自己改自己的数据，不用传来传去
        ...

    def format(self):
        self.clean_salary()      # 直接叫自己的方法
        ...
```

**"设计者思维 vs 执行者思维"这个对比说得很到位**：

| 思维 | 关注点 | 类比 |
| **执行者思维**（面向过程） | 我要**怎么做**这件事 | 我自己去超市、挑菜、洗菜、炒菜 |
| **设计者思维**（面向对象） | 我该**让谁**去做这件事 | 我找厨师、洗菜工、采购员，各管一摊 |

**面向对象的核心价值：把"变化"关在盒子里。** 薪资解析规则变了？只改 `Job.clean_salary` 一个地方，别处不用动。
@@trap 什么时候该用哪个
**不是所有代码都该面向对象。** 一个 20 行的脚本，写个类反而是负担。

**判断标准**：
- **数据和行为紧密相关、而且会被复用** → 用类
- **一次性的计算 / 流程脚本** → 用函数就够了

**别为了"显得专业"而过度设计。** 要强调：面向对象是工具，不是信仰。

@@point ② 类与对象：模板与实例
@@need 要解决什么
"类"和"对象"这两个词天天混着说。**搞清它们的关系，这一章后面的内容才有立足点。**
@@idea 核心思路
**类是模板，对象是按模板造出来的具体东西。**

```cmd
#   类 Job（模板）                对象（实例）
#  ┌────────────────┐         ┌──────────────────┐
#  │ 属性：title     │  造 ──▶  │ title="前端"      │
#  │      city      │         │ city="昆明"       │
#  │      salary    │         │ salary=12000     │
#  │ 方法：clean()   │         └──────────────────┘
#  │      to_row()  │  造 ──▶  ┌──────────────────┐
#  └────────────────┘         │ title="后端"      │
#                             │ city="郑州"       │
#                             │ salary=15000     │
#                             └──────────────────┘
```

**类比**：类是"月饼模子"，对象是"印出来的月饼"。模子只有一个，月饼可以有很多个。

```python
class Job:                       # 类名用【大驼峰】
    """一条岗位记录。"""

    def __init__(self, title, city, salary):
        self.title = title
        self.city = city
        self.salary = salary

j1 = Job("前端", "昆明", 12000)     # 造对象 → 调用类，像调函数一样
j2 = Job("后端", "郑州", 15000)

print(j1.title)                  # 前端
print(type(j1))                  # <class '__main__.Job'>
print(isinstance(j1, Job))       # True
```

**对象的内存模型**——每个对象有自己的**属性字典**：

```cmd
#  j1 ──▶ ┌─────────────────────────┐
#         │ __class__ ──▶ Job 类对象 │
#         │ title  = "前端"          │
#         │ city   = "昆明"          │
#         │ salary = 12000          │
#         └─────────────────────────┘
```
@@trap 命名规范
| 对象 | 规范 | 例子 |
| **类名** | 大驼峰 | `JobItem`、`ChatBot` |
| 实例名 | 小写+下划线 | `job_item` |
| 不要用内置名 | 避开 | 别写 `class List:` |

**类名用大驼峰不是"风格偏好"，是让你一眼能区分"这是类还是变量"。**

@@point ③ 构造函数：`__init__`
@@need 要解决什么
造对象的时候，那些属性怎么设进去？**总不能造出来再一个个赋值。**
@@idea 核心思路
`__init__` 是一个**特殊方法**（名字前后各两个下划线），在**对象创建后自动调用**：

```python
class Job:
    def __init__(self, title, city, salary):
        self.title = title
        self.city = city
        self.salary = salary

j = Job("前端", "昆明", 12000)
#     ↑ 这一刻发生了什么：
#       1. Python 创建了一个空对象
#       2. 自动调用 Job.__init__(新对象, "前端", "昆明", 12000)
#       3. __init__ 把属性挂到 self 上
#       4. 返回这个对象，赋给 j
```

**`self` 是什么？** 就是**"这个对象自己"**。Python 调用方法时**自动把对象作为第一个参数传进去**：

```python
j.clean_salary()
# 实际执行的是 Job.clean_salary(j)，j 就是那个 self
```

**所以 `self` 不是关键字，只是个约定俗成的名字**（你写成 `this` 也能跑，但别这么干）。

**给属性设默认值**——用参数默认值就行：

```python
class Job:
    def __init__(self, title, city, salary=None):
        self.title = title
        self.city = city
        self.salary = salary or 0      # 没传就是 0
```

**`__init__` vs `__new__`**——这两个都值得知道，但你**实际只需要用 `__init__`**：

| | 什么时候调用 | 干什么 | 你要写吗 |
| `__new__` | **先**调用（造出空对象） | 创建对象本身 | ❌ 极少需要 |
| `__init__` | **后**调用（初始化） | 给对象挂属性 | ✅ **99% 的情况写这个** |
@@trap 忘写 self
```python
class Job:
    def __init__(title, city):        # ✗ 漏了 self
        ...
# TypeError: Job.__init__() takes 2 positional arguments but 3 were given
```
**报错信息里的"个数对不上"基本都是漏写或多写 `self`。** 记住：**实例方法的第一个参数永远是 `self`**。

@@point ④ 实例属性与内存分析
@@need 要解决什么
"为什么每个对象的 `title` 互不干扰？"——**搞清实例属性存在哪里**，后面理解类属性和继承才不糊涂。
@@idea 核心思路
**实例属性存在每个对象自己的 `__dict__` 里**——这是"每个对象独立"的根本原因：

```python
class Job:
    def __init__(self, title):
        self.title = title

j1 = Job("前端")
j2 = Job("后端")

print(j1.__dict__)     # {'title': '前端'}
print(j2.__dict__)     # {'title': '后端'}
j1.title = "改过了"
print(j2.title)        # 后端  ← 互不影响
```

**属性可以随时动态添加**（Python 的特色，也是隐患）：

```python
j1.level = "P5"        # 直接加，不用事先声明
print(j1.__dict__)     # {'title': '改过了', 'level': 'P5'}
```

**这很灵活，但也意味着：写错属性名不会报错。**

```python
j1.tilte = "前端"      # 拼错了
print(j1.title)        # 报 AttributeError —— 但错误发现在很远的地方
```

**`__slots__` 可以限制只能有哪些属性**（进阶技巧，知道有这回事就行）：

```python
class Job:
    __slots__ = ("title", "city", "salary")   # 只能有这三个属性
```
@@trap 三个容易踩的点
| 坑 | 说明 |
| **属性拼写错不报错** | 赋值时不存在会新建，取值时才报 `AttributeError` |
| `__dict__` 会占内存 | 每个对象一个字典，对象很多时开销可观。`__slots__` 能省 |
| 别在类里写可变默认值 | 和第五章的 `def f(lst=[])` 同理——**类属性用可变对象会被所有实例共享** |

@@point ⑤ 实例方法
@@need 要解决什么
"对象能做什么事"——方法就是**挂在对象上的函数**。
@@idea 核心思路
```python
class Job:
    def __init__(self, title, salary):
        self.title = title
        self.salary = salary

    def desc(self):                    # 实例方法：第一个参数是 self
        return f"{self.title} 薪资 {self.salary}"

    def raise_salary(self, pct):       # 可以有别的参数
        self.salary = int(self.salary * (1 + pct))
        return self                    # 返回 self 可以【链式调用】

j = Job("前端", 10000)
print(j.desc())                        # 前端 薪资 10000
j.raise_salary(0.2).raise_salary(0.1)  # 链式调用
print(j.salary)                        # 13200
```

**方法调用时的查找过程**：

```cmd
#  j.desc()
#    1. 在【对象自己】的 __dict__ 里找 desc      → 找不到
#    2. 去【它所属的类】Job 里找 desc           → 找到了
#    3. 把 j 作为 self 传进去，执行 Job.desc(j)
```

**几个有用的内置工具**：

```python
dir(j)                 # 看这个对象所有能用的属性和方法（**调试利器**）
isinstance(j, Job)     # True   判断类型（推荐）
hasattr(j, "title")    # True   有没有这个属性
getattr(j, "title")    # '前端'  动态取属性
vars(j)                # 等同于 j.__dict__
```
@@trap 方法没有重载
**Python 不支持方法重载**（同名方法写两遍，后面那个会覆盖前面那个）：

```python
class A:
    def f(self, x): ...
    def f(self, x, y): ...     # ✗ 第一行被覆盖，只剩下这个
```

**替代方案**：用默认值参数或 `*args`：

```python
def f(self, x, y=None):
    if y is None:
        ...
```

**这就是所谓的"方法的动态性"**——类的方法可以在运行时被替换（`A.f = 新函数`），很灵活，但别滥用。

@@point ⑥ 类属性 vs 实例属性
@@need 要解决什么
有些数据**所有对象都该共用一份**（比如"一共有多少个岗位对象"）。存在每个对象里就重复浪费了，而且统计不了。
@@idea 核心思路
**类属性写在类里、方法外**，属于类，所有实例共享：

```python
class Job:
    total = 0                     # ← 类属性

    def __init__(self, title):
        self.title = title        # ← 实例属性
        Job.total += 1            # 用【类名】访问类属性

j1 = Job("前端")
j2 = Job("后端")
print(Job.total)      # 2
print(j1.total)       # 2    实例也能读到类属性
```

**查找顺序和"遮蔽"**——这是关键：

```cmd
#  j1.total 的查找过程：
#    1. 先在【实例自己的 __dict__】找   → 有就用实例的
#    2. 没有 → 去【类】找              → 有就用类的
#    3. 还没有 → 去【父类】找           → ...
#    4. 都没有 → AttributeError
```

**危险的地方——"读"和"写"行为不一样**：

```python
j1.total = 99         # ✗ 这【不是】改类属性，而是给 j1 加了一个实例属性
print(j1.total)       # 99    （实例属性遮蔽了类属性）
print(Job.total)      # 2     （类属性没变）
print(j2.total)       # 2
```

| 操作 | 效果 |
| **读** `j1.total` | 实例有就返回实例的，没有就返回类的 |
| **写** `j1.total = x` | **永远创建/修改实例属性**，不会改类属性 |
| **改类属性** | 必须 `Job.total = x` |

**这就是"实例属性会遮蔽类属性"。** 想改类属性，一定要用 `类名.属性`。
@@trap 别用类属性存可变对象
```python
class Job:
    tags = []                  # ✗ 所有实例共享【同一个】列表

j1 = Job(); j1.tags.append("a")
j2 = Job()
print(j2.tags)                 # ['a']  ← 被污染了
```
**原因**：类属性只创建一次，所有实例读到的都是同一个列表对象。

**正确做法**：在 `__init__` 里建实例属性：

```python
def __init__(self):
    self.tags = []             # ✓ 每个实例一个
```

**这又是第五章"默认值参数别用可变对象"的同一个道理**——**可变对象一旦被共享，就会互相污染。**

@@point ⑦ 类方法与静态方法
@@need 要解决什么
有些方法**和"某个具体对象"无关**——比如"从一行 CSV 造出一个 Job 对象"。放在实例方法里没法调（还没对象呢）。
@@idea 核心思路
**三种方法对比**：

| 类型 | 装饰器 | 第一个参数 | 能访问什么 |
| **实例方法** | 无 | `self`（对象） | 实例属性 + 类属性 |
| **类方法** | `@classmethod` | `cls`（类） | 类属性（**不能访问实例属性**） |
| **静态方法** | `@staticmethod` | 无 | 都访问不了，就是个普通函数 |

```python
class Job:
    def __init__(self, title, salary):
        self.title = title
        self.salary = salary

    # 实例方法：操作【这个对象】
    def desc(self):
        return f"{self.title}: {self.salary}"

    # 类方法：常见用途是【替代构造函数】
    @classmethod
    def from_csv_row(cls, row):
        title, salary = row.split(",")
        return cls(title.strip(), int(salary))     # cls 就是 Job

    # 静态方法：就是个"放在类里的普通函数"，逻辑上和这个类相关
    @staticmethod
    def is_valid_salary(s):
        return isinstance(s, (int, float)) and s > 0
```

**用起来**：

```python
j = Job.from_csv_row("前端, 12000")      # 类方法：用【类】调用
Job.is_valid_salary(12000)               # 静态方法：也是用类调用
j.desc()                                 # 实例方法：用【对象】调用
```

**`cls` 的好处**：子类调用时，`cls` 会自动变成子类，这样 `from_csv_row` 对子类也管用。这就是"工厂方法"的雏形。
@@trap 什么时候用哪个
| 需求 | 用 |
| 要读/写 `self.xxx` | **实例方法**（99% 的情况） |
| 要造对象、或需要知道"是哪个类" | **类方法** |
| 逻辑相关但不需要类或对象的数据 | **静态方法**（其实也可写成模块级函数） |

**新手最容易犯的错**：所有方法都写成静态方法，结果类变成"函数包"——**那就失去面向对象的意义了**。

@@point ⑧ 私有属性与私有方法
@@need 要解决什么
你写了一个类给别人用，但**有些内部数据不该让外面随便改**——比如"薪资"必须经过清洗才能赋值，直接改就乱了。
@@idea 核心思路
**Python 没有真正的"私有"**，靠命名约定：

| 写法 | 名字 | 含义 |
| `self.name` | 公开 | 谁都能访问 |
| `self._name` | **单下划线** | "内部用，别碰"——**只是约定，不强制** |
| `self.__name` | **双下划线** | 触发"**名称改编**"，外面很难访问到 |

```python
class Job:
    def __init__(self, title, salary):
        self.title = title
        self.__salary = salary        # 私有

    def get_salary(self):
        return self.__salary

    def set_salary(self, v):
        if v < 0:
            raise ValueError("薪资不能为负")
        self.__salary = v             # 在这里做校验


j = Job("前端", 10000)
print(j.__salary)        # ✗ AttributeError
print(j._Job__salary)    # 10000   ← 其实还能这样绕过去（"名称改编"）
```

**"名称改编"（name mangling）**：`__salary` 被 Python 自动改名成 `_Job__salary`。**这不是加密，只是"不鼓励访问"。**

**为什么要有 `_` 和 `__`？** 因为 Python 的哲学是"**我们都是成年人**"——它相信你不会故意破坏封装，但也给你工具表达"这是内部的"。
@@trap 私有方法同理
```python
class Job:
    def __clean(self):        # 私有方法
        ...

j.__clean()                   # ✗ 访问不到
```
**但私有方法有个隐患**：子类里同名的方法不会覆盖父类的私有方法（因为名字被改编了）。继承相关的坑，见下一节。

@@point ⑨ @property：把方法变成"属性"
@@need 要解决什么
`j.get_salary()` 这种写法有点啰嗦，而且**调用者不该关心"这是存的还是算的"**。`@property` 让方法看起来像属性。
@@idea 核心思路
```python
class Job:
    def __init__(self, salary):
        self._salary = salary            # 内部存 _salary

    @property
    def salary(self):                    # 读的时候走这里
        """月薪（元）"""
        return self._salary

    @salary.setter
    def salary(self, v):                 # 写的时候走这里
        if v < 0:
            raise ValueError("薪资不能为负")
        self._salary = v


j = Job(10000)
print(j.salary)      # 10000           ← 像属性一样读，其实调了方法
j.salary = 12000     # ✓ 走 setter，会校验
j.salary = -100      # ✗ ValueError
```

**`@property` 的三大价值**：

| 价值 | 说明 |
| **调用者体验好** | `j.salary` 比 `j.get_salary()` 自然 |
| **可以加校验** | 赋值时自动检查，不用要求调用者记得调 `set` |
| **"计算属性"** | 没有存、每次算出来的也能当属性用 |

**计算属性的例子**——很适合这个场景：

```python
class Job:
    def __init__(self, salary_min, salary_max):
        self.salary_min = salary_min
        self.salary_max = salary_max

    @property
    def salary_avg(self):                # 不存在这个字段，是算出来的
        return (self.salary_min + self.salary_max) / 2

j = Job(8000, 15000)
print(j.salary_avg)     # 11500.0
j.salary_avg = 1        # ✗ AttributeError（没有 setter，就是只读的）
```
@@trap property 与私有属性的配合
**标准写法**是"**内部用 `_x` 存，对外暴露 `@property x`**"：

```python
self._salary = ...          # 存
@property
def salary(self): ...       # 读
@salary.setter
def salary(self, v): ...    # 写
```

**注意**：不要在同名的 property 里访问自己（`self.salary = x` 会无限递归），**一定要访问 `self._salary`**。

@@point ⑩ 三大特征：封装、继承、多态
@@need 要解决什么
前面学的都是零件。这一节把"面向对象到底好在哪"讲清楚——**三个特征就是三个不同维度的好处**。
@@idea 核心思路
| 特征 | 一句话 | 解决什么问题 |
| **封装** | 把数据和操作它的方法打包，隐藏内部细节 | **变化被关在盒子里**——改内部实现不影响外面 |
| **继承** | 子类自动拥有父类的能力，还能改写 | **避免重复**——公共部分写一次 |
| **多态** | 同一个调用，不同对象有不同行为 | **调用者不用关心具体是哪个类** |

**这三个不是三种语法，是三种"让代码好维护"的手段。**
@@trap 别为了用而用
**继承是最容易被滥用的。** 判断标准是"**是不是真的 IS-A 关系**"：

- `Dog` IS-A `Animal` ✅ 该继承
- `Car` HAS-A `Engine` ✅ **该用组合**（把 Engine 当属性），不是继承

**"组合优于继承"是业界的共识**——见下面第 ⑮ 点。

@@point ⑪ 继承与重写
@@need 要解决什么
你要做"多个招聘平台"，它们都有"打开页面、抓列表、抓详情"，只有"解析规则"不同。**总不能把公共部分抄三遍。**
@@idea 核心思路
```python
class BaseCollector:                     # 父类 / 基类
    def __init__(self, keyword):
        self.keyword = keyword

    def collect(self):                   # 公共流程，写一次
        self.open_page()
        urls = self.parse_list()         # ← 这一步交给子类
        return [self.parse_detail(u) for u in urls]

    def open_page(self):
        print("打开浏览器……")

    def parse_list(self):
        raise NotImplementedError        # 子类必须实现

    def parse_detail(self, url):
        raise NotImplementedError


class ZhaopinCollector(BaseCollector):   # 子类
    def parse_list(self):
        return ["u1", "u2"]              # 智联的解析方式

    def parse_detail(self, url):
        return f"智联详情:{url}"


class Job51Collector(BaseCollector):
    def parse_detail(self, url):         # 只重写需要变的部分
        return f"前程详情:{url}"

    def parse_list(self):
        return ["j1"]


ZhaopinCollector("前端").collect()       # 公共流程完全复用
```

**几个关键概念**：

- **`class 子类(父类):`** —— 括号里写父类
- **重写（override）**—— 子类定义同名方法，会覆盖父类的
- **继承所有成员**—— 属性、方法都能用
- **`object` 是所有类的根类**——`class A:` 等价于 `class A(object):`（Python 3 里默认继承 `object`）

**这个"父类定流程、子类填细节"的模式叫「模板方法模式」，是实战里最常见的继承用法。**
@@trap 重写不是"覆盖着玩"
子类重写父类方法时，**签名（参数）应该保持一致**，否则调用方会出错。

**另外**：如果只是想"在父类基础上加点东西"，别忘了用 `super()` 调父类（下一点）。

@@point ⑫ super() 与 MRO
@@need 要解决什么
子类重写方法时，**经常需要在父类的基础上扩展**，而不是完全替换。`super()` 就是干这个的。
@@idea 核心思路
```python
class BaseCollector:
    def __init__(self, keyword):
        self.keyword = keyword

class ZhaopinCollector(BaseCollector):
    def __init__(self, keyword, city):
        super().__init__(keyword)      # ← 先让父类把该做的做完
        self.city = city               # 再补充自己的

    def collect(self):
        print("智联：准备限速……")
        return super().collect()       # 在父类流程前后加东西
```

**`super()` 的好处**：不用硬写父类名。**改继承关系时不用到处改代码**，而且在多重继承下会按 MRO 顺序找。

**MRO（方法解析顺序）**——多重继承时，"同名方法到底用谁的"：

```python
class A:
    def f(self): print("A")
class B(A):
    def f(self): print("B")
class C(A):
    def f(self): print("C")
class D(B, C):
    pass

D().f()               # B     ← 先找 B，B 有就不找了
print(D.__mro__)      # (D, B, C, A, object)
```

**规则叫「C3 线性化」**，实际记忆用**"从左到右、深度优先、但不重复"**基本够用。

**怎么查？** `类名.__mro__` 或 `类名.mro()`。**遇到"这个方法到底是谁的"时，打一下 MRO 就清楚了。**
@@trap 多重继承的"钻石问题"
```python
class A:     pass
class B(A):  pass
class C(A):  pass
class D(B, C): pass      # 菱形继承
```
**A 的 `__init__` 会被调用几次？** 如果 B、C 都调了 `super().__init__()`，**在 C3 线性化下只会调一次**。这就是为什么**大家都用 `super()` 而不是硬写父类名**。

**但说实话**：多重继承很容易写出难懂的代码。**实战中 90% 的情况用单继承 + 组合就够了。**

@@point ⑬ 多态
@@need 要解决什么
"我有一堆不同平台的采集器，想用同一段代码处理它们"——**不用 if 判断类型，直接调同名方法**。这就是多态。
@@idea 核心思路
**多态就是"同一个调用，不同对象有不同表现"。**

```python
collectors = [
    ZhaopinCollector("前端"),
    Job51Collector("后端"),
]

for c in collectors:
    c.collect()      # ← 同一行代码，各自跑各自的实现
```

**为什么这很值钱？** 对比一下"没有多态"的写法：

```python
# ✗ 面向过程：每加一个平台就要改这里
for c in collectors:
    if c.platform == "zhaopin":
        collect_zhaopin(c)
    elif c.platform == "job51":
        collect_job51(c)
    elif c.platform == "boss":          # 每加一个都要改
        collect_boss(c)
```

**Python 的多态是"鸭子类型"**——**不看它是什么类，只看它有没有那个方法**：

```python
# 只要对象有 collect() 方法，就能这么用
# 完全不需要继承同一个父类！
for obj in anything:
    obj.collect()
```

**"如果它走起来像鸭子、叫起来像鸭子，那它就是鸭子。"**

**这意味着**：你的类不需要继承某个"接口"才能被统一调用——**只要有同名方法就行**。这比 Java 那套灵活得多。
@@trap 鸭子类型的代价
**灵活，但没有编译期检查。** 传错对象只有在**运行时**才会报 `AttributeError`。

**防御手段**：
- 用 `hasattr(obj, "collect")` 先判断
- 用类型注解 + `mypy` 做静态检查
- 用抽象基类（`abc.ABC`）声明"必须实现哪些方法"

@@point ⑭ 特殊方法与运算符重载
@@need 要解决什么
`print(job)` 打出来是 `<__main__.Job object at 0x...>`——**完全看不出是什么**。你想要的是 "前端/昆明/12000"。这就需要重写特殊方法。
@@idea 核心思路
**特殊方法 = 双下划线开头结尾的方法**，它们对应着 Python 的内置行为：

| 你写的方法 | 什么时候被调用 | 效果 |
| `__init__` | `Job(...)` | 构造 |
| **`__str__`** | `print(j)` / `str(j)` | **给人看的字符串** ← 最常用 |
| `__repr__` | 直接敲 `j` / 调试器里 | 给开发者看的（最好能"重建"对象） |
| `__len__` | `len(j)` | 长度 |
| `__eq__` | `j1 == j2` | 相等判断 |
| `__lt__` | `j1 < j2` | 比较（`sort` 也用它） |
| `__add__` | `j1 + j2` | 加法 |
| `__call__` | `j()` | 让对象能像函数一样调用 |
| `__del__` | 对象被回收时 | 析构（**别依赖它**） |

**最该写的是 `__str__`**——调试体验天差地别：

```python
class Job:
    def __init__(self, title, city, salary):
        self.title, self.city, self.salary = title, city, salary

    def __str__(self):
        return f"Job({self.title} / {self.city} / {self.salary})"

    def __repr__(self):                   # 调试时更严谨
        return f"Job(title={self.title!r}, city={self.city!r}, salary={self.salary})"


print(Job("前端", "昆明", 12000))    # Job(前端 / 昆明 / 12000)
```

**`__eq__` 和 `__lt__` 配合，能让对象直接排序**：

```python
class Job:
    def __init__(self, salary):
        self.salary = salary
    def __lt__(self, other):
        return self.salary < other.salary

sorted([Job(12000), Job(8000)])      # 自动按 salary 排
```
@@trap 写 __eq__ 别忘了 __hash__
```python
class Job:
    def __eq__(self, other):
        return self.title == other.title
```
**一旦重写 `__eq__`，对象的哈希值就变了，默认就不能放进 `set` 或当字典键了**（`TypeError: unhashable type`）。

**要放进去，得同时定义 `__hash__`**：

```python
def __hash__(self):
    return hash(self.title)
```

@@point ⑮ 继承 vs 组合
@@need 要解决什么
"我要让 Job 有'导出 Excel'的能力"——**是让 Job 继承一个 Excel 类，还是把 Excel 当属性？** 选错了类会越继承越乱。
@@idea 核心思路
**判断标准就一句话**：

> **IS-A（是一个）→ 继承；HAS-A（有一个）→ 组合。**

```python
# ✗ 错：Job 不是一个 Exporter
class Job(Exporter):          # 逻辑上说不通

# ✓ 对：Job 有一个导出器（或者说"用"它）
class Job:
    def __init__(self, exporter=None):
        self.exporter = exporter or ExcelExporter()

    def export(self, path):
        return self.exporter.write(self.to_rows(), path)
```

**为什么组合更好？**

| | 继承 | 组合 |
| 耦合度 | **高**（子类依赖父类所有细节） | 低（只依赖对方提供的接口） |
| 能换吗 | 运行时换不了 | **可以换**（换一个 exporter 就行） |
| 层级 | 容易越继承越深 | 扁平的 |

**"组合优于继承"是面向对象设计的经典原则。** 继承只在**真的 IS-A 且需要多态**时才用。

**一个实战判断**：如果你写 `class A(B)` 时觉得别扭、说不太清"为什么 A 是一个 B"，那基本就该用组合。
@@trap 继承层级别超过三层
```cmd
#  🐢 这种层级很难维护
#  Base → BaseCollector → BaseWebCollector → BaseJsCollector → ZhaopinCollector
```
**超过三层的继承，改父类时你根本不知道会影响谁。** 用组合拆平。

@@point ⑯ 设计模式：工厂与单例
@@need 要解决什么
"**将来可能要支持 BOSS、拉勾……我总不能每加一个平台就改一遍主流程吧？**" 设计模式就是前人总结的、针对这类问题的成熟解法。
@@idea 核心思路
**先说明**：设计模式不是"必须用"的东西，**过度使用反而让代码更难懂**。这里讲两个在采集类项目里**真的用得上**的。

**① 工厂模式——把"造对象"的过程封起来**

```python
class CollectorFactory:
    _registry = {
        "zhaopin": ZhaopinCollector,
        "job51":   Job51Collector,
    }

    @classmethod
    def create(cls, platform, **kw):
        klass = cls._registry.get(platform)
        if klass is None:
            raise ValueError(f"不支持的平台：{platform}")
        return klass(**kw)

    @classmethod
    def register(cls, name, klass):        # 新平台只需注册，不用改主流程
        cls._registry[name] = klass


c = CollectorFactory.create("zhaopin", keyword="前端")
```

**好处**：调用方不用知道类名，**加新平台只改注册表一处**。

**② 单例模式——保证"全局只有一个实例"**

```python
class Config:
    _instance = None

    def __new__(cls, *a, **kw):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._loaded = False
        return cls._instance

    def load(self, path):
        if self._loaded:
            return
        ...                              # 只真正读一次
        self._loaded = True


c1 = Config()
c2 = Config()
print(c1 is c2)          # True   ← 同一个对象
```

**什么时候需要单例？** 全局配置、日志器、数据库连接池——**"整个程序只该有一份"的东西**。

**更 Pythonic 的写法**是用模块——**Python 的模块天然就是单例**：

```python
# config.py
_settings = None
def get_config():
    global _settings
    if _settings is None:
        _settings = load()
    return _settings
```
@@trap 设计模式的正确态度
| 该用 | 不该用 |
| 你真的遇到了那个问题（"每加一个平台要改五处"） | "听说工厂模式很牛，先套上" |
| 团队里大家都懂这个模式 | 只有你懂，别人看得一头雾水 |

**记住**：**先写能跑的简单版本，等到"改起来真的痛"了再重构。** 提前套设计模式，是最常见的过度设计。
