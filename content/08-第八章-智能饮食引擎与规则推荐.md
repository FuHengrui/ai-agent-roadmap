@@why 这一章在解决什么问题
第七章只摸了 `diet_advisor` 的边，本章把它拆开看——**DietAdvisor 是"规则式 AI"的典型代表**：不用大模型，用静态医学规则（食谱库 + 阈值判断）就能给出合理的饮食建议。本章解决三件事：**一是 10 条糖尿病推荐食谱库的设计**，**二是营养汇总与语义化评判的逻辑**，**三是"结合当前血糖动态调整推荐"的分支逻辑**。

关键认知：**不是所有智能都要上大模型**。规则引擎零成本、零延迟、结果可解释——本项目用规则引擎做"基础推荐"，用大模型做"生成式建议"，两层互补。看懂 DietAdvisor 就懂了"轻量 AI"的设计思路。

@@point ① 规则引擎 vs 大模型：为什么用规则
@@need 要解决什么
饮食推荐是医疗场景，为什么不用大模型直接回答，而是先写死规则？

@@idea 核心思路
DietAdvisor 的设计取舍：

| 维度 | 规则引擎（DietAdvisor） | 大模型生成 |
|---|---|---|
| 成本 | 0（纯本地计算） | 按 token 计费 |
| 延迟 | 毫秒级 | 秒级 |
| 确定性 | 同输入同输出，可测试 | 可能飘 |
| 可解释性 | 推荐逻辑透明（GI 排序可见） | 黑盒 |
| 场景 | 高频基础推荐 | 个性化综合建议（报告/对话） |

本项目分工：**DietAdvisor 管"今天吃什么"的即时推荐（毫秒响应），LLM 管周报、对话（个性化表述）**。医疗建议还涉及责任边界——确定性规则更容易控风险。

学习价值：掌握"何时用规则、何时用模型"的判断力，比会调 API 更重要。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 什么都丢给大模型 | 高频低风险场景用规则，成本与延迟都失控 |
| 规则库写死但没人维护 | 规则库要"可增删"，推荐条目按餐次+GI 结构化存放 |

@@point ② RECOMMENDED_FOODS：静态食谱库设计
@@need 要解决什么
"推荐吃什么"的依据在哪？菜谱怎么组织才能被程序筛选？

@@idea 核心思路
10 条食物字典按"餐次"和"GI 值"两个维度组织：

```python
RECOMMENDED_FOODS: List[Dict] = [
    {"name": "燕麦粥", "calories": 150, "carbs": 27, "protein": 5,
     "fat": 3, "gi": 55, "meal": "早餐", "tip": "富含膳食纤维，升糖慢"},
    {"name": "水煮鸡蛋", "calories": 78, "carbs": 0.6, "protein": 6,
     "fat": 5, "gi": 0, "meal": "早餐", "tip": "优质蛋白质，几乎不含碳水"},
    {"name": "糙米饭", "calories": 220, "carbs": 46, "protein": 5,
     "fat": 2, "gi": 56, "meal": "午餐/晚餐", "tip": "比白米GI低，营养更丰富"},
    {"name": "苹果", "calories": 52, "carbs": 14, "protein": 0.3,
     "fat": 0.2, "gi": 36, "meal": "加餐", "tip": "低GI水果，适量食用"},
    ... # 共 10 条
]
```

数据结构设计要点：
- **meal 支持多值**：`"午餐/晚餐"` 用斜杠表达"两餐通用"——筛选时 `meal_type in f["meal"]` 就是子串匹配；
- **gi 是筛选键**：低 GI（≤55）代表升糖慢，是高血糖时的优先推荐；
- **tip 是展示文案**：同一条能同时服务"计算"（nutrition）与"展示"（前端卡片）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| meal 字段写成单值 | 午餐晚餐都吃的食物得复制两条；用 "午餐/晚餐" 一字段多值 |
| gi 填错档次算法就错 | GI 是排序/筛选依据，必须按食物成分表核实 |

@@point ③ 营养汇总：按天聚合与 or 0 防护
@@need 要解决什么
get_daily_nutrition 怎么把一天的多条记录汇总成"总热量/四素/平均GI"？

@@idea 核心思路
```python
async def get_daily_nutrition(self, patient_id: int, date_str: Optional[str] = None):
    if date_str:
        date = datetime.fromisoformat(date_str).replace(tzinfo=timezone.utc)
    else:
        date = datetime.now(timezone.utc)
    start_of_day = date.replace(hour=0, minute=0, second=0, microsecond=0)
    end_of_day = start_of_day + timedelta(days=1)
    records = await DietRecord.filter(
        patient_id=patient_id,
        eaten_at__gte=start_of_day,
        eaten_at__lt=end_of_day,     # 半开区间，避免次日记录混入
    ).all()
    total_calories = sum(record.calories or 0 for record in records)
    ...
    gi_vals = [r.gi_value for r in records if r.gi_value is not None]
    avg_gi = statistics.mean(gi_vals) if gi_vals else 0.0
    return {
        "date": date.strftime('%Y-%m-%d'),
        "meal_count": len(records),
        "total_calories": round(total_calories, 1),
        "total_protein": ..., "total_fat": ..., "total_carbs": ...,
        "avg_gi": avg_gi,
        "calorie_status": self._calorie_status(total_calories),
        "carb_status": self._carb_status(total_carbs),
        "records": [{"name": r.food_name, "calories": r.calories,
                     "meal": r.meal_type} for r in records],
    }
```

三个细节值得抄：
1. **可选日期**：`date_str` 为空用当前时间，前端可查任意历史日期；
2. **时间区间**：`[start, start+1天)` 半开区间，`__lt` 收尾防越界；
3. **防 None 双保险**：总量用 `or 0`，均值用 `if not None` 过滤——两种空值策略按语义选用。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 日期字符串格式不对 | `fromisoformat` 只认 ISO 格式 YYYY-MM-DD；前端必须规范传参 |
| 次日 0 点的记录被算进今天 | 结束端必须 __lt 而不是 __lte |
| avg_gi 把 None 当 0 | 过滤后求均值；0 会严重拉低真实 GI |

@@point ④ 热量与碳水语义化：两个状态判定函数
@@need 要解决什么
"1800 千卡"数字冷冰冰，怎么转成"适中/偏高"这种可读判断？

@@idea 核心思路
```python
def _calorie_status(self, total_calories: float) -> str:
    if total_calories < 1200:
        return "热量摄入偏低，可能营养不足"
    if total_calories <= 1800:
        return "热量摄入适中，建议维持"
    return "热量摄入偏高，可能营养过剩"

def _carb_status(self, total_carbs: float) -> str:
    if total_carbs < 100:
        return "碳水化合物摄入偏低，可能营养不足"
    if total_carbs <= 200:
        return "碳水化合物摄入适中，建议维持"
    return "碳水化合物摄入偏高，注意控制碳水"
```

规则表：
| 指标 | 偏低 | 适中 | 偏高 |
|---|---|---|---|
| 热量（千卡） | <1200 | 1200–1800 | >1800 |
| 碳水（克） | <100 | 100–200 | >200 |

**与模型层 status 完全同构**——"原始数值 → 语义分级"是贯穿全系统的模式：血糖阈值（low/normal/high）、GI 等级、BMI 分类、热量状态全是它。掌握一个就会全部。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 边界值 1200/1800 归属漂移 | <1200 偏低、≤1800 适中；边界写法与血糖 status 保持一致（左闭右闭） |
| 阈值硬编码 | 本项目写死在类里；若多处用可提升到常量区统一管理 |

@@point ⑤ recommend_meal：结合血糖的分支推荐
@@need 要解决什么
血糖 9.5 和血糖 6.0 时，推荐的食谱应该不同——怎么动态调整？

@@idea 核心思路
```python
def recommend_meal(self, meal_type: str, recent_bg: Optional[float] = None):
    # 1. 初筛：餐次匹配，或"加餐"通用食物
    suitable = [f for f in RECOMMENDED_FOODS
                if meal_type in f["meal"] or f["meal"] == "加餐"]
    # 2. 分支：高血糖 → 按GI升序取前4；否则取前5
    if recent_bg and recent_bg > 8.0:
        suitable = sorted(suitable, key=lambda x: x["gi"])[:4]
    else:
        suitable = suitable[:5]
    return suitable
```

分支逻辑：
- **血糖 >8.0（偏高/高）**：`sorted(key=lambda x: x["gi"])` 按 GI 升序排序，取 GI 最低的 4 条——**优先降糖**；
- **正常或无血糖数据**：取库中前 5 条默认推荐——**均衡优先**；
- `recent_bg` 来自路由：`BloodSugar ... first()` 患者最近一次血糖。

这就是"规则智能"的动态性：**同样问"午餐吃什么"，血糖不同答案不同**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| recent_bg 为 None 时崩溃 | `if recent_bg and recent_bg > 8.0` 短路判空再判值 |
| 按 GI 排序方向写反 | 高血糖要"最不升糖"的在前，必须升序（小 GI 在前） |
| 取前4前5的语义混淆 | 高血糖给更少选择（4）更聚焦；正常给5条更丰富 |

@@point ⑥ 引擎接口设计：同步方法不硬等数据库
@@need 要解决什么
为什么 get_daily_nutrition 是 async 而 recommend_meal 是同步方法？混用会怎样？

@@idea 核心思路
| 方法 | 是否 async | 原因 |
|---|---|---|
| get_daily_nutrition | ✅ async | 内部 await DietRecord.filter(...).all()，必须异步 |
| recommend_meal | ❌ 同步 | 纯内存计算（列表筛选+排序），无 I/O |
| _calorie_status / _carb_status | ❌ 同步 | 纯函数，无 I/O |

设计纪律：**有数据库/网络 I/O 才 async，纯计算必须同步**。路由调用时 `await diet_advisor.get_daily_nutrition(...)`（异步）与 `diet_advisor.recommend_meal(...)`（同步，但要保险可包 await）——**同步方法在 async 路由里直接调用即可**（不 await），不会有问题；反之同步方法里 await 才会炸。

另外注意明确边界：`recommend_meal` 在章节里的路由为 `recommend/{meal_type}`，接 `patient_id` 与 `meal_type` 从路径取，内部拿最近血糖——**引擎不自己连数据库**，数据由路由喂进来，保持纯函数可单测。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 在同步方法里 await | SyntaxError；纯计算函数不要标 async |
| 把 I/O 藏进同步方法 | 路由会卡事件循环；同步方法里绝不能碰 await 数据库 |
| 忘记区分调用语法 | async 方法用 await 调；同步方法直接调，别画蛇添足 |

@@point ⑦ 单例导出与路由接线
@@need 要解决什么
引擎写好后，路由怎么拿到这个"唯一实例"？

@@idea 核心思路
与 health_analyzer 完全相同的模式——文件底部实例化：
```python
diet_advisor = DietAdvisor()
```
路由引用：
```python
from app.core.diet_advisor import diet_advisor

@router.get("/patient/{patient_id}/daily")
async def get_daily_nutrition(patient_id: int, date: Optional[str] = Query(default=None)):
    patient = await Patient.get_or_none(id=patient_id)
    if not patient:
        raise HTTPException(status_code=404, detail="患者不存在")
    return await diet_advisor.get_daily_nutrition(patient_id, date)

@router.get("/recommend/{meal_type}")
async def recommend_meal(patient_id: int, meal_type: str):
    recent_bg = await BloodSugar.get_or_none(
        patient_id=patient_id).order_by("-created_at").first()
    return diet_advisor.recommend_meal(meal_type, recent_bg.value)
```

注意：示例代码里 `BloodSugar.get_or_none(...).order_by(...)` 这种写法**真实值得警惕**——`get_or_none` 返回单条记录的协程对象，再链 `.order_by()` 并不正确；若要"最近一次记录"，应写：
```python
recent_bg = await BloodSugar.filter(patient_id=patient_id) \
    .order_by("-measured_at").first()
```
并处理"无记录"的 None 情况。读代码要带着"它写对了吗"的眼睛。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| get_or_none 后链 order_by 报错 | get_or_none 语义是"取零或一"；链排序应改用 filter().order_by().first() |
| 无血糖记录时 .value 崩溃 | recent_bg 为 None 要判空：`recent_bg.value if recent_bg else None` |
| 忘给 diet_advisor 加括号 | 导入的是实例不是类；调用才 `diet_advisor.recommend_meal` |

@@point ⑧ 规则引擎的边界与升级路径
@@need 要解决什么
规则式饮食建议的天花板在哪？如何平滑升级到"更智能"的方案？

@@idea 核心思路
当前规则引擎的三个短板：
1. **食谱库固定 10 条**：不能覆盖更多菜品与个体差异；
2. **分支仅按血糖**：没有考虑 BMI、肾功能、过敏等个性化约束；
3. **没有对话能力**：只能"要一份推荐"，不能追问"为什么"。

升级路径（本项目之外的延伸思路）：
- **规则扩大**：食谱库增到几十条 + 病理约束过滤（肾病低蛋白）；
- **混合推荐**：规则引擎筛候选 → LLM 基于患者档案精调表述；
- **知识注入**：RAG 检索指南条目补充推荐依据（本阶段第十二章已经在对话侧做了类似事）。

**在架构上，DietAdvisor 面向接口（返回结构化 dict/List），升级实现不影响路由**——这就是引擎封装的红利。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 想加个性化又不重构 | 先从"喂更多参数"入手（如传 BMI），别推倒重来 |
| 期望规则引擎"懂对话" | 明确职责：规则给确定性建议，对话给生成式回答，各管一段 |
