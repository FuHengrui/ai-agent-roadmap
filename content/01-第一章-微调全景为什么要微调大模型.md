@@point ① 什么是大模型微调
@@need 要解决什么
先定义清楚"微调"这两个字，不然后面全是名词打架。你说"让模型更专业"，供应商说"这是精调"，同事说"这是 RAG"——其实它们根本不是一回事。

@@idea 核心思路
讲义定义很简单：**微调 = 在已有的大规模预训练模型基础上，用标注数据再训练，把模型往特定任务/场景上优化**。

三个关键词拆开看：

| 词 | 含义 |
|---|---|
| 已有预训练模型 | 别人（或你）已经花巨资训好的底座，如 DeepSeek-R1、Llama 3，你不需要从零训 |
| 标注数据 | 带正确答案/期望输出的数据，如"问 → 答"对、"病历 → 诊断"对 |
| 再训练 | 让模型在 Task 上更新参数，改变它的行为 |

和"从零训练"的区别就是一句话：**别人已经教会了它语言和常识，你只负责教它你这个行业的规矩**——成本差着几个数量级。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把"微调"和"从零训练"混为一谈 | 从零训练一个 7B 模型要几千张卡训几个月；微调只用普通单卡几个小时。微调的前提是**底座已经存在**——你没底座就先选一个开源模型，别自己从头练 |
| 把"微调"当"换了模型" | 微调后的模型还是同一个底座，只是参数变了。模型名、词表、架构都没变，变的是"它对某些输入的反应" |

@@point ② 为什么需要微调：三个真实理由
@@need 要解决什么
"预训练模型已经很强了，为什么还要花钱花时间微调？"——这个问题答不上来，你会在"微调"和"提示词工程/RAG"之间反复摇摆，白花几周。

@@idea 核心思路
讲义给了三个理由，本质是一条：**通用 ≠ 专用**。

| 理由 | 具体表现 |
|---|---|
| 提升准确率 | 直接问通用模型"这个工伤算几级"，它给你教材式回答，错不漏但也不对；微调后按你公司的口径答，答错率明显下降 |
| 适应特定场景 | 客服问答、代码生成、售后工单……每个行业有自己的话术、格式、禁忌，这些细节预训练模型没见过 |
| 减少计算成本 | 相比从零训一个同类模型，微调用的数据少、算力少、见效快 |

记住决策句：**当"给模型一个好 prompt"已经榨不出更多效果，或者你要的是稳定的行业级输出时，就该微调了。**

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 项目一遇到"模型答得不满意"就上微调 | 先问三个问题：prompt 写透了吗？RAG 检索喂了吗？数据量够吗（几百条很难）？**方案没穷尽就微调，是拿大炮打蚊子且容易过期**——模型一升级，微调成果可能归零 |
| 以为微调能"教会模型新知识" | 微调擅长改变**行为方式和风格**（话术、格式、口径），不擅长灌入大规模新事实——新知识该用 RAG/检索。硬把知识塞进微调，既慢又容易学歪 |

@@point ③ 全量微调：效果最好，代价也最高
@@need 要解决什么
微调不是只有一种玩法。最"实在"的做法就是把模型所有参数全部再训练一遍——你得知道它好在哪、贵在哪，才能判断自己扛不扛得住。

@@idea 核心思路
**全量微调（Full Fine-tuning）= 对模型全部参数进行训练**，让模型完全适配新任务。

讲义列的三个适用场景，就是它的"使用条件"：

| 适用条件 | 说明 |
|---|---|
| 需要彻底调整模型行为 | 法律、医疗等专业领域的大规模任务，光微调一小块不够 |
| 训练数据足够丰富 | 数据太少喂不动几亿个参数，学出来的全是噪声 |
| 计算资源充足 | 全参更新的显存成本=模型本身+优化器状态，7B 模型 bf16 全微调就要 60GB 显存起步 |

一句话评价：**全量微调 = 效果上限最高，但门槛也最高**。它不是"默认选项",而是"财大气粗且数据管够"时的选项。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| "反正卡够大，全量微调最稳" | 全量微调不仅费显存，还容易**灾难性遗忘**（把底座学好的通用能力冲掉）。数据不够精、任务不够专时，全量反而比高效微调更容易翻车 |
| 以为"全量微调 = 效果必然最好" | "最好"指潜力，不指必然。没喂够高质量数据，全量参数只会把噪声也学进去；LoRA 加了"参数少=正则化"的天然约束，小数据场景经常比全量更稳 |

@@point ④ 高效微调：只改一小块，省下大价钱
@@need 要解决什么
学生党一张 4060、公司测试机一张 3090，全量微调 7B 根本跑不动——但业务又确实需要调。高效微调就是为"卡不够、数据少、还要快"的场景发明的。

@@idea 核心思路
**高效微调（Efficient Fine-tuning）= 只训练模型的一小部分参数**（如插入的 Adapter 层、LoRA 层），其余参数冻结不动。

讲义给的高效微调适用场景，正好和全量的三个条件反着：

| 场景 | 为什么高效微调行 |
|---|---|
| 计算资源受限 | 训练参数少了 99%+，显存需求断崖式下降 |
| 需要快速适配多个任务 | 每个任务存"一小包适配器"即可切换，原始模型不动，一个底座挂 N 个任务 |
| 训练数据较少 | 参数少，学得动；数据少也不会把模型冲坏 |

底层逻辑：**大模型的"知识"在底座里，"风格/任务"藏在参数的一个低维方向里**——你只要调整那个方向，不需要重训整张网。这就是第三章 LoRA 的理论根基。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为高效微调"什么任务都能搞定" | 高效微调擅长**风格/口径/格式/任务适配**，对"模型根本不会的复杂推理能力"提升有限——能力缺口靠底座选择或更大模型，高效微调救不了 |
| 以为"高效微调=零风险" | 学习率、秩 r、数据质量照样能把它训坏；只是**翻车成本**比全量低，不是不会翻车 |

@@point ⑤ 高效微调家族：Adapter / LoRA / Prefix / Prompt
@@need 要解决什么
打开任何微调框架，都是一堆名词：Adapter、LoRA、Prefix-Tuning、Prompt-Tuning。不把这几兄弟认全，你连文档都看不懂，更别说选型。

@@idea 核心思路
讲义一句话总结了四兄弟，本质是**四种"塞可训练参数"的位置**：

| 方法 | 一句话原理 | 可训练的东西在哪 |
|---|---|---|
| Adapter | 在 Transformer 层之间插入小适配层 | 模型**内部**新加的几层小网络 |
| LoRA | 用低秩矩阵模拟权重增量（下章主角） | 每层权重旁边挂的两个小矩阵 |
| Prefix-Tuning | 在输入序列前加可训练的前缀向量 | **输入前**的一串虚拟 token |
| Prompt-Tuning | 用可训练的"软提示词"引导模型 | 输入开头的一段连续向量（比 Prefix 更小） |

共性是：**原始模型权重都不动，只增加/训练极小一部分参数**。区别在于挂载位置不同，适用任务侧重略有差异（Adapter 角色多样、LoRA 最通用、Prefix/Prompt 适合"轻量换风格"）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把 Prefix-Tuning 和 Prompt-Tuning 当成一回事 | Prefix 加在**每一层**的输入前（更像"前缀向量"），Prompt 只在**输入序列**开头加；前者参数更多、能力更强，后者参数极少、适合轻场景。写代码前先分清你调的是哪个 |
| 以为四选一随便挑就行 | 具体任务和框架里默认值不同：手写 LoRA 教程用 LoRA，LLaMA-Factory/Unsloth 默认也是 LoRA。**先学会 LoRA 一条主线走到底**，其他兄弟知道"存在且原理不同"即可，别贪多 |

@@point ⑥ 全量指令微调：让模型学会"听话"
@@need 要解决什么
同样是微调，普通微调教的是"这个领域怎么答对"，但有一种微调教的是"人类下达的一切指令怎么理解"——这是 ChatGPT 从"会说话的模型"变成"懂事的助手"的关键一步。

@@idea 核心思路
**全量指令微调（Full Instruction Tuning）= 用高质量"指令-回答"数据集训练模型的指令理解和执行能力**，让它擅长完成指令驱动的任务（对话生成、文本摘要、代码补全等）。

讲义给的两个核心机制：

| 机制 | 作用 |
|---|---|
| 用高质量的指令数据集训练 | 让模型从"见到问题就给一段话"变成"见到指令就按指令办事" |
| 结合监督学习（SFT）与强化学习（RLHF） | SFT 先教会"照做"，RLHF 再教会"做得好" |

它和"普通微调"最大的差别在**目标**：普通微调教"你懂行情吗"，指令微调教"你听人话吗"——所以指令微调出来的模型天然适合对话 AI、智能助手、搜索引擎。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为"指令微调 = 收集一堆问答喂进去" | 指令数据**质量** > 数量。低质指令会把模型教成"有问必答但没脑"；需要遵循特定格式（如 Alpaca 格式）并做清洗，这一章后面的数据准备就在处理这件事 |
| 以为"指令微调后，模型就懂所有任务了" | 指令微调提升的是**服从指令的通用能力**，具体领域的专业深度仍要靠针对该领域的微调去补——两者是叠加关系，不是替代关系 |

@@point ⑦ 指令微调 vs 普通微调：一张表看懂
@@need 要解决什么
"指令微调"和"普通微调"名字像、操作也像，都叫 fine-tuning。不把它们并排对比一次，你永远会在写数据时搞混：这份数据该按指令格式写还是按领域数据写？

@@idea 核心思路
讲义给了一张现成的对比表，直接背下来：

| 比较项 | 指令微调（Instruction Tuning） | 普通微调（Fine-tuning） |
|---|---|---|
| 目标 | 让模型更擅长**遵循人类指令** | 让模型**适应特定领域任务** |
| 训练方式 | 需要**高质量指令数据**（指令-回答对） | 使用**领域数据**（领域输入-期望输出） |
| 适用场景 | AI 助手、对话系统、问答 | 特定行业（如医疗、金融） |

速记：**指令微调练"耳朵"（听懂并执行指令），普通微调练"专业"（成为行业专家）**。实际项目经常两个都要——先用指令数据教它听话，再喂领域数据教它懂行（LLaMA-Factory 的 SFT 一条流水线都能做）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 拿"领域数据"当"指令数据"混用 | 指令数据必须包含**明确的指令/任务描述**（"把下面这段翻译成中文"），纯领域切片没有指令结构，模型学不到"服从指令"。格式不对，微调效果直接打折 |
| 以为"先指令后领域"顺序无所谓 | 顺序有讲究：通常是先通用指令（对齐听话能力），再领域微调（深耕专业）。反着来，领域知识可能冲掉指令能力，模型又变回"不听话的专家" |

@@point ⑧ 怎么选：全量微调还是高效微调
@@need 要解决什么
你已经认识了全量和高效微调，但回到真实项目还是会卡：**我到底该选哪种？** 这一节把决策条件固定成一张检查表，以后对着打勾就行。

@@idea 核心思路
把前面几节的条件汇总成决策漏斗：

```
你的任务是"彻底改变模型行为"？──────是──► 全量微调（行业级大规模任务）
        │否
你的数据足够丰富（万级以上高质量对）？─是──► 全量微调（有条件选）
        │否
你的显存/预算很紧张？───────────是──► 高效微调（LoRA/Adapter…）
        │否
要快速切换多个任务，底座还想复用？──是──► 高效微调
        │否（最终兜底）
─────────────────────────────► 先做 prompt 工程 / RAG，微调不是第一步
```

实操建议（本阶段的主线也按这个走）：

| 你的处境 | 推荐路线 |
|---|---|
| 学生、单卡、几百条数据 | 手写 LoRA（第 4~7 章）或 Unsloth（第 8~9 章） |
| 公司、项目要交付、怕折腾 | LLaMA-Factory WebUI（第 11~12 章） |
| 数据管够、卡管够、任务重大 | 全量微调，但这不在本阶段教程主线内 |

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| "先全量微调试试，不行再换 LoRA" | 顺序反了。全量微调烧的钱和调参成本是 LoRA 的几十倍，**先用 LoRA 跑通验证可行性，确认收益后再考虑全量放大**——这才是省钱的正路 |
| "别人说 LoRA 效果好，我就无脑 LoRA" | LoRA 的秩 r、作用模块、学习率都有讲究（第 6 章讲）。选型之后还有一整套调参活，别以为选完就完事 |

@@summary
这一章你实际拿到的是：

| 拿到了什么 | 为什么要紧 |
|---|---|
| **微调的定义与三个理由** | 能回答"为什么要花这个钱"：准确率、场景适配、成本远低于从零训练 |
| **全量 vs 高效的完整对比** | 全量=效果好代价高（数据多、卡够用）、高效=省资源灵活（Adapter/LoRA/Prefix/Prompt），决策漏斗直接套用 |
