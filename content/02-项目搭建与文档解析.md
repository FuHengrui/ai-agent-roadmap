@@point ① 工程骨架：为什么目录要按"能力"分，不能按"类型"分
@@need 要解决什么
第一次组织一个"前后端分离 + 多模块"的工程，最常见的死法是把所有文件平铺或者按"文件类型"分（`parsers/`、`models/`、`utils/`）。结果是一个功能要跨 5 个目录找文件，改一行代码牵连一片。**目录结构就是代码的骨架，一开始就要按"能力边界"定。**

@@idea 核心思路
项目采用 `src/` 布局，按"能力"而不是"文件类型"分包：

```text
rag_project/
├── src/                      # 后端源码
│   ├── api/                  # FastAPI 路由、请求/响应模型、依赖注入
│   ├── parsers/              # 文档解析（PDF/Word/MD/HTML → 文本）
│   ├── embeddings/           # 嵌入模型 + 向量存储
│   ├── llm/                  # 大模型封装 + RAG 提示词组装
│   ├── retrieval/            # 检索服务（配置 + 统一入口）
│   └── database/             # 文档元数据存储
├── frontend/                 # Vue3 前端（独立子工程）
├── tests/                    # 测试
├── data/                     # 演示数据/上传文件
├── pyproject.toml            # 依赖清单（uv 用）
└── .env                      # 密钥与配置（不进 git！）
```

为什么这样分：**一个改动的目标是"一个包"而不是"一堆文件"**。比如"换向量库"，你只需动 `embeddings/` 里的实现，`api/`、`llm/` 完全不受影响——这就是上一章"接口抽象"在目录层面的落地。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 按"类型"分目录（所有 `.py` 放一起） | 类型相同不等于职责相同，功能会散落；**按能力分，功能内聚，改动只动一个包** |
| 前后端不分目录、堆在一个项目 | 前端有自己的构建链（npm）和后端（pip）完全隔离；**分开才能各自独立开发部署** |
| 把上传的用户文件放进源码目录 | 上传文件是**运行时数据**，要和代码分离，放 `data/` 下，方便清空/备份 |

@@point ② 依赖管理：uv 一条命令装齐整个项目
@@need 要解决什么
一个项目几十个第三方依赖，`pip install` 一个一个装早晚翻车：版本冲突、装漏、换了机器装不上。**依赖必须"一次性声明、一键复原"。**

@@idea 核心思路
项目用 **uv**（新一代 Python 包管理器）管依赖，声明文件是 `pyproject.toml`：

```bash
# 一条命令装齐 pyproject.toml 里声明的全部依赖
uv sync

# 装好后用 uv run 跑任何脚本（自动用项目虚拟环境）
uv run uvicorn src.api.main:app --reload
```

uv 比 pip 快一个数量级，还能锁定精确版本（`uv.lock`），保证"你机器上跑的和我一样"。这是工程化最基本的一课：**不要靠"我记得装过 xxx"**。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| `uv sync` 装了依赖，但直接 `python xxx.py` 报 ModuleNotFoundError | uv 会把依赖装进**项目自己的虚拟环境**，直接调系统 python 当然找不到。统一用 `uv run python xxx.py` 跑 |
| 以为 `pyproject.toml` 只是"声明文件"，手动 `pip install` 一个个补 | 手动装的和声明的不一致，换台机器立刻暴露。**任何依赖都写进 pyproject.toml，重新 `uv sync`** |

@@point ③ 配置与密钥：`.env` 是唯一允许放密钥的地方
@@need 要解决什么
项目要接智谱/通义两家 API，就要配两个 Key。**Key 一旦写进代码或提交进 git，等于把钱包贴在代码里**——现实项目里就发现过真实 Key（`sk-...`）躺在 `.env` 里。企业项目的红线：密钥和配置必须和代码分离。

@@idea 核心思路
做法是 **`.env` 文件 + 环境变量读取**：

```text
# .env（真实文件，不进 git）
DASHSCOPE_API_KEY=sk-xxxx            # 通义千问（这里必须写你自己的）
ZHIPU_API_KEY=xxxx.xxxx              # 智谱 GLM（也必须是你自己的）
LLM_PROVIDER=zhipu                   # 默认用哪家
```

代码里一律用 `os.getenv()` 读，绝不硬编码：

```python
import os
api_key = os.getenv("ZHIPU_API_KEY")   # 读不到就报错，而不是默默用空 Key
```

配套动作：`.gitignore` 里把 `.env` 排除，同时提供 `.env.example` 作为"模板"（只留键名、值用占位符），新同事复制一份改名就能用。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 跟着示例抄，把示例 Key 直接用了 | 示例 Key 是**别人（原作者）的、可能还在生效**，抄了是在花别人的钱。一律换成 `os.environ[...]` 占位，用自己的 Key |
| 把 `.env` 提交进 git | 一旦推送，Key 就进了代码历史，删都删不干净。`git log` 里永久留存。必须立即从 git 移除并轮换 Key |
| 在代码里 `print` 或写日志打 Key | 日志也会泄露密钥。Key 只在"读取时"出现，之后只存在内存变量里 |

@@point ④ 解析器为什么要"统一接口"：BaseParser 抽象
@@need 要解决什么
四种格式的解析代码天然千差万别：PDF 要处理页、Word 要处理段落和表格、HTML 要去标签……**但上层（分块、入库）只关心"给我一段干净文本"，不关心你内部怎么解析。** 如果上层直接调用四种不同的解析函数，每加一种格式就要改一圈上层代码。

@@idea 核心思路
定义抽象基类 `BaseParser`，把"能解析成文本"这个能力契约锁死：

```python
class BaseParser(ABC):
    @abstractmethod
    def parse(self, path: str) -> str:
        """把一个文件解析成纯文本字符串。"""
        ...
```

每一个具体解析器都实现这个 `parse`：`PDFParser`、`WordParser`、`MarkdownParser`、`HTMLParser`。
上层代码永远只认识 `BaseParser.parse()`，从而：
- **加新格式** = 新写一个类继承 `BaseParser`，上层零改动；
- **换解析方案** = 替换对应类的内部实现。

这和第⑦点的"一切可替换"是同一个原则在解析层的一次具体应用。

@@point ⑤ PDF 解析：为什么选 Docling，不选"更轻"的方案
@@need 要解决什么
PDF 是文档库里最难的格式：有的是文字版、有的是扫描图片、有的一页里嵌套表格、有的页眉页脚一页一页重复。**Python 生态里 PDF 解析库有一堆，选错了要么表格乱、要么扫描件读不出字。**

@@idea 核心思路
这里先比对三种轻量方案，再给出进阶方案：

| 方案 | 特长 | 短板 | 本项目判断 |
|---|---|---|---|
| **PyMuPDF**（fitz） | 快，纯文本提取 | 表格、版面、扫描件处理弱 | 简单 PDF 够用 |
| **pdfplumber** | 表格提取不错 | 慢、版面复杂识别一般 | 表格场景可用 |
| **PyPDF2** | 最基础 | 功能弱，复杂文档残废 | 不推荐 |
| **Docling**（IBM） | 版面分析 + 表格 + 图片理解，面向**文档AI解析**的完整方案 | 依赖较重、首次要下模型 | ✅ **项目选用** |

选 Docling 的理由：企业文档多含复杂版面（双栏、表格、图片说明），**Docling 把版面、表格、阅读顺序都处理了，输出结构化的 Markdown**，正好喂给下一章的清洗分块。它是"解析能力"和"工程易用性"的平衡点。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 以为"PDF 解析 = 把文本拉出来" | 复杂文档要的是**版面结构**（哪是标题、哪是表格、阅读顺序），纯文本提取会乱序。扫描件还需要 OCR，那又是另一套 |
| 迷信"最快的库" | 快只是纯文本提取；要结构、要表格，"快的库"常常做不到，得按文档复杂度选 |
| 用 Docling 却不下模型文件 | Docling 首次运行要下载版面分析模型，**离线环境会直接失败**。生产部署要预下载好模型 |

@@point ⑥ Word 解析：python-docx 读段落和表格
@@need 要解决什么
Word 文档（.docx）不是纯文本：正文是一段一段的，**表格是独立结构**。用简单的 `open()` 打开会得到一堆乱码（docx 本身是个 zip）。需要一个按文档结构读取的库。

@@idea 核心思路
项目用 `python-docx`，它把 docx 文档按"段落 + 表格"两层读出来：

```python
from docx import Document

def parse(path: str) -> str:
    doc = Document(path)
    chunks = []
    # 按文档顺序遍历 body 里的段落和表格
    for item in doc.element.body:
        # 段落 → 取文本；表格 → 转成 Markdown 表格文本
        ...
    return "\n".join(chunks)
```

关键点：**表格不能丢**。Word 里大量信息是以表格存在的（产品参数、对比清单），如果只读段落，表格里的知识就全丢了。所以 WordParser 对表格单独处理，转成 Markdown 形式的表格文本（和上一章 `merge_tables` 的表格处理呼应）。

@@point ⑦ Markdown 与 HTML 解析：一个去标记、一个去标签
@@need 要解决什么
Markdown 和 HTML 都是为了排版加了很多"标记"：`#`、`**`、`<div>`、`<style>`…… **这些标记对检索毫无意义，还得不到什么"干净文字"。** 得把标记剥掉。

@@idea 核心思路
两个解析器思路一致——**剥离标记、保留正文语义**：

```python
# Markdown：把 md 语法转成纯文本（标题保留为文本行即可）
# 项目直接用 markdown 库渲染成 HTML 再用 HTML 的剥法；也可用正则去标记

# HTML：用 BeautifulSoup 解析，取可见文本
from bs4 import BeautifulSoup

def parse(path: str) -> str:
    with open(path, encoding="utf-8") as f:
        soup = BeautifulSoup(f.read(), "html.parser")
    for tag in soup(["script", "style", "nav", "footer"]):
        tag.decompose()          # 清掉导航、脚本、样式
    return soup.get_text("\n")   # 剩下的取纯文本
```

注意的坑：**要清理 `<script>`/`<style>`**——网页里这两块内容（JS 代码、CSS）不是正文，不删会当成知识入库，检索时全是噪音。

@@point ⑧ 表格处理：跨页表格为什么必须"先合并再入库"
@@need 要解决什么
企业 Word/PDF 里的大表格经常**跨页**：表头在第一页，数据在第二页，第三页又续。如果逐页提取，一个逻辑表格被劈成三段，语义直接碎掉——检索时"这个产品支持哪些接口"只能搜到半张表。**这是全文库里最容易出的暗病。**

@@idea 核心思路
项目提供 `TableProcessor`，做两件事：

| 处理 | 干什么 | 为什么 |
|---|---|---|
| **提取** | 从文档里识别出表格结构（行/列/表头） | 表格要在"表格语义"层面处理，不当普通文本 |
| **合并跨页表** | 检测"上一页表格头 + 下一页表格体"是同一张表，拼回去 | 保住一个逻辑表格的完整性，不让跨页切碎语义 |

合并的判断依据：**相邻页出现"同结构、已满宽度、上一页最后一行通常不带下边框"等特征**时，判定为同一张表。落库前把合并后的表转成 Markdown 表格文本，检索时才能按"行"命中。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 以为"表格也是文本，一起拉出来就行" | 表格的语义在**行列结构**里，拍平成文本会丢失"这是第几列"的信息。必须结构化提取后再转文本 |
| 不处理跨页表格 | 一个逻辑表被切碎，检索永远只能命中一半，**答案残缺但看着正常**，是最难排查的暗病 |
| 合并时把"格式相同"的相邻表误合并 | 判断要谨慎：不仅要相邻、结构相同，通常看上一页表尾特征。误合并会把两张无关的表拼一起，更糟 |

@@point ⑨ 解析器工厂：按扩展名自动路由，一行代码接入新格式
@@need 要解决什么
四种解析器写好了，但上层怎么知道"这个文件该用哪个解析器"？如果到处写 `if ext == ".pdf": ...`，加新格式就要改 N 处 if。**解析器的选择逻辑应该集中在一处，且能一行扩展。**

@@idea 核心思路
用 **工厂（Factory）模式 + 注册表**：解析器按扩展名注册，工厂按文件扩展名路由。

```python
# 注册（每个解析器模块里一行）
register_parser(".pdf", PDFParser)
register_parser(".docx", WordParser)
register_parser(".md", MarkdownParser)
register_parser(".html", HTMLParser)

# 使用（上层永远只调这个）
def parse_document(file_path: str) -> str:
    parser = create_parser(file_path)   # 工厂按扩展名查表
    return parser.parse(file_path)
```

**以后要加 `.txt` 格式**：写一个 `TxtParser(BaseParser)` + 一行注册，全系统自动支持。这就是第④点抽象接口的真正收益——新增能力是"加一物"，而不是"改十处"。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 用 `if/elif` 链判断扩展名 | 每加一个格式就要改工厂函数本身，且选择逻辑散落。注册表模式把"新增"变成"注册一行" |
| 扩展名不匹配就静默返回空文本 | 会得到"入库成功但内容为空"的脏数据。**不认识的文件类型应显式报错**，让调用方知道没解析成功 |
| 把 `.doc`（旧版 Word）和 `.docx` 混为一谈 | python-docx 只支持 `.docx`；老 `.doc` 要先转格式或用其他工具，注册表里用错解析器会直接抛异常 |
