@@why 这一章在解决什么问题
vLLM 不是唯一的部署方案，**Ollama** 也有一大批拥趸，还有 HuggingFace TGI、TensorRT-LLM 等玩家。技术选型时最常问的问题是：**vLLM 到底有哪些特性？它和 Ollama 比各自擅长什么？** 本章把 vLLM 的能力清单梳理清楚，并给出与 Ollama 的正面对比与选型结论。

上一章学习了 PagedAttention 与连续批处理原理。**本章看 vLLM 的完整特性清单、vs Ollama 的定位对比与使用场景**。下一章进入实操：环境要求、安装与模型下载。

@@point ① vLLM 的完整特性清单
@@need 要解决什么
vLLM 除了"快"，还具有哪些拿来即用的能力？

@@idea 核心思路
vLLM 演进至今的完整特性矩阵：

| 类别 | 能力 |
|---|---|
| 推理优化 | PagedAttention、连续批处理、量化支持（AWQ/GPTQ/FP8 等） |
| 模型能力 | 支持主流开源 LLM、多 LoRA 适配、多模态部分支持 |
| 服务化 | OpenAI 兼容 API、流式输出、前缀缓存 |
| 扩展性 | 张量并行（多卡）、分布式推理、与 Ray 协同 |
| 生产可用 | 监控指标、优雅降级、量化精度控制 |

核心定位：**面向"生产环境的模型服务"**——不是玩具 demo，而是能承接线上流量、可观测可扩展的引擎。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为 vLLM 只擅长"快" | 服务化、量化、并行、监控一站式也是 vLLM 的重要价值 |
| 忽略版本差异 | vLLM 迭代极快，特性支持以官方文档/版本说明为准 |

@@point ② OpenAI 兼容 API：生态即插即用
@@need 要解决什么
为什么 vLLM 要"兼容 OpenAI API"？这对用户意味着什么？

@@idea 核心思路
OpenAI 的 API 格式（`/v1/chat/completions`、`/v1/completions`、`/v1/models`）已成为 LLM 服务的**事实标准**。

vLLM 直接实现这一接口：

```
你的 OpenAI SDK / 调用代码
   ↓ 只需改 base_url
http://localhost:8000/v1   ← vLLM 服务
```

**收益**：所有为 OpenAI API 写的客户端（LangChain、OpenAI SDK、各类 Agent 框架）**零改动**切换到自部署模型。这让 vLLM 在企业内"无缝替换"私有化模型成为可能。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为兼容=功能完全一致 | 工具调用（function calling）等高级 OpenAI 能力视模型/版本而定，需验证 |
| 忘记改 base_url | 客户端默认打 OpenAI 官方域名，切 vLLM 必须先改 base_url |

@@point ③ 前缀缓存与流式输出
@@need 要解决什么
生产环境常用的两个"体验优化"能力 vLLM 有没有？

@@idea 核心思路
两个高价值特性：

1. **自动前缀缓存（Automatic Prefix Caching）**：模型频繁收到相同前缀（系统提示、few-shot 示例）时，**相同前缀的 KV 直接复用**，不再重复计算。

```
场景: 1000个请求都带同一系统提示
效果: 前缀部分 KV 缓存复用 → 首令牌延迟大降
```

2. **流式输出（Streaming）**：token 边生成边返回，用户不再"傻等完整回答"，体验像 ChatGPT 一样逐字出现——这是大模型服务的标配体验。

两者组合：企业级 Chat 服务延迟感知与吞吐优化的关键开关。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 前缀缓存开了一股脑复用 | 前缀完全相同才命中，微小差异（多一个空格）都可能错失命中 |
| 忽略流式与首令牌延迟 | 流式体验关键看 TTFT（首个 token 时间），前缀缓存与调度影响它 |

@@point ④ 量化支持：与阶段23 无缝衔接
@@need 要解决什么
上一阶段学的量化，在 vLLM 里怎么用上？

@@idea 核心思路
vLLM 内建**多种量化格式支持**，部署时直接选择：

- **AWQ / GPTQ**：4bit 权重量化，大模型省显存的主流方案。
- **FP8**：新一代 8bit 浮点量化，精度/收益平衡好。
- **INT8 / INT4 权重**：各类线性量化格式的运行时加载。

用法：加载模型时指定量化算法对应的模型权重文件（如 AWQ 量化版模型），vLLM 自动做反量化计算。**阶段23 的量化知识与这里无缝衔接**：先压缩好模型，再交给 vLLM 部署，压缩收益在服务端兑现。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为量化在 vLLM 里自动完成 | 模型需要先权重导出（AWQ/GPTQ 工具或现成量化权重），vLLM 负责运行时支持 |
| 量化与精度预期错配 | 4bit 带来的精度损失要在部署前用评测集验证，别上线后才发现 |

@@point ⑤ 多 LoRA 与多模态支持
@@need 要解决什么
一个服务要服务多用户/多任务，vLLM 怎么支持"一套底座、多套适配"？

@@idea 核心思路
**多 LoRA（Multi-LoRA）**：一个基础模型同时挂载多个 LoRA 适配器，请求时按需加载对应 LoRA：

```
服务: base + lora_A + lora_B + lora_C
请求: 指定用 lora_B → 仅该请求启用 lora_B
```

**价值**：企业多角色/多风格场景，不必为每个角色部署完整模型，**一套模型服务 N 个适配器**，省显存省成本。

vLLM 也逐步支持**多模态模型**（视觉语言模型等，视版本），让"图片+文本"输入的推理服务化成为可能。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为多 LoRA 能无限叠加 | 显存内需要预留 LoRA 权重空间，加载数量受显存与配置限制 |
| 忽略多模态的版本门槛 | 多模态按模型适配，选型前查 vLLM 官方支持矩阵 |

@@point ⑥ 与 Ollama 对比：定位完全不同
@@need 要解决什么
网上常拿 vLLM 与 Ollama 比，二者到底什么关系？

@@idea 核心思路
讲义明确给出对比定位：

| 维度 | vLLM | Ollama |
|---|---|---|
| 定位 | 高性能推理引擎（服务导向） | 本地模型管理器（易用导向） |
| 目标用户 | 开发者/运维/企业服务 | 个人开发者/桌面用户 |
| 核心优势 | 吞吐、并发、API 生态 | 一键安装、模型仓库、简单启动 |
| 生产化 | 强（监控/量化/并行） | 弱（偏个人使用） |
| 吞吐性能 | 高 | 中 |

**结论**：Ollama 适合"本机体验、快速验证"；vLLM 适合"线上服务、高并发生产"——两者不是替代关系，而是**不同阶段的工具**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 拿 Ollama 跑生产高并发 | Ollama 的设计重心不在吞吐与调度，压测后大概率输给 vLLM |
| 拿 vLLM 当桌面小工具 | vLLM 上手偏工程化，纯本机玩模型 Ollama 更省心 |

@@point ⑦ 分布式与扩展：单卡不够怎么办
@@need 要解决什么
模型太大单卡放不下、并发太高单机扛不住，怎么扩展？

@@idea 核心思路
vLLM 的扩展路径：

- **张量并行（Tensor Parallelism）**：把模型按权重维度切到多张 GPU 卡上，单卡放不下的大模型靠多卡拼起来（如 70B 模型 2~4 卡）。
- **多实例/横向扩展**：一台机多实例、多台机负载均衡，承接更大并发。
- 与 **Ray** 等分布式框架集成，编排推理集群。

选型参考：先算模型参数"重量"（如 7B FP16 ≈ 14GB），再按单卡显存决定并行度与部署拓扑。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 张量并行想加就加 | 并行度需整除层/头数且通信开销随卡数增长，卡数不是越多越快 |
| 忽略显存三件套 | 模型权重 + KV 缓存 + 激活都要显存，实际所需远超权重大小 |

@@point ⑧ 本章小结：一张选型决策表
@@need 要解决什么
面对 vLLM/Ollama 等方案，怎么快速拍板？

@@idea 核心思路
选型决策口诀：

```
个人本机体验      → Ollama（一键、快、轻）
企业私有化服务    → vLLM（吞吐、API、量化、并行）
生产高并发压测    → vLLM + 负载均衡 + 监控
模型太大单卡不够  → 张量并行 / 量化（4bit/FP8）
手上有 OpenAI 客户端 → vLLM 零改造接入（改 base_url）
```

无论选哪个，部署前都先回答：**并发预期、模型大小、显存预算、API 生态**——这四个问题锁定方案。

@@summary
这一章完成了 vLLM 的能力全景与选型对比：

| 主题 | 结论 |
|---|---|
| 特性矩阵 | 优化/量化/API/并行/监控一站服务 |
| OpenAI 兼容 | 改 base_url 即插即用，生态零改造 |
| 前缀缓存+流式 | 首令牌延迟大降，体验符合 ChatGPT 标准 |
| 量化支持 | AWQ/GPTQ/FP8，承接阶段23 成果 |
| 多 LoRA | 一套底座服务多个适配器 |
| vs Ollama | vLLM=生产服务，Ollama=本机体验 |
| 扩展性 | 张量并行+横向扩展+Ray |

一句话记住本章：**vLLM 是"生产级"推理引擎——内建 OpenAI 兼容 API（改 base_url 即插即用）、自动前缀缓存与流式输出、支持 AWQ/GPTQ/FP8 量化（正好承接阶段23）、多 LoRA 一套底座服务多个角色，还能张量并行多卡扩展；而 Ollama 主打"本机一键体验"，两者定位不同：个人快速验证用 Ollama，线上高并发生产服务用 vLLM，选型时先想清楚并发预期、模型大小、显存预算与 API 生态四件事。**
