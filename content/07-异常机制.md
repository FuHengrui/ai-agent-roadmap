@@why 这一章在解决什么问题
你的程序要抓 200 个页面。抓到第 137 个的时候，那个页面返回了 404——**程序直接崩了，前面 136 个白抓。**

这就是没有异常处理的代价：**一处小问题，毁掉全部工作。**

这一章要解决两件事：

- **"出错了怎么不崩"**——捕获异常，跳过坏的继续跑

**而且这一章有个更重要的观念转变**：**异常不是"敌人"，是"信息"**。它告诉你程序在哪、因为什么、走不下去了。

**新手看到报错就慌，老手看到报错就高兴**——因为报错是程序在帮你定位问题。学会读懂异常，你的 debug 速度会翻倍。

@@point ① 异常的本质
@@need 要解决什么
"错误"和"异常"是一回事吗？为什么有的错误程序能继续跑，有的直接崩？
@@idea 核心思路
**异常 = 程序运行时遇到的、无法继续正常执行的状况。**

它和"逻辑错误"不一样：

| 类型 | 例子 | 表现 |
| **语法错误** | `if x = 1:` | **根本跑不起来**，解释器直接拒绝 |
| **逻辑错误** | 循环条件写反了 | **能跑**，但结果不对——最难查 |
| **异常（运行时错误）** | `1/0`、文件不存在、网络超时 | **跑到那一行才崩** |

**异常的产生和传播**：

```cmd
#  def a() → 调用 b() → 调用 c() → c 里出错了
#
#   ┌─── c() 出错 ───┐
#   │ ZeroDivisionError │
#   └────────┬────────┘
#            │ c 没处理，往上抛
#   ┌────────▼────────┐
#   │  b() 也没处理    │
#   └────────┬────────┘
#            │ 继续往上抛
#   ┌────────▼────────┐
#   │  a() 也没处理    │
#   └────────┬────────┘
#            │ 抛到最外层
#            ▼
#     程序崩溃，打印 Traceback
```

**关键理解：异常会沿着调用链一层层往上抛，直到有人接住它。**

**调试的核心理念**：

> **不要猜，要定位。** 报错信息已经告诉你"文件、行号、什么错"了，**照着读比拍脑袋快十倍**。

**遇到报错的正确顺序**：

- **看最后一行**——错误类型和原因
- **看行号**——哪一行出的问题
- **看中间**——如果是多层调用，看是谁调用了谁
- **复现**——能稳定复现，才能稳定修好

@@trap 别急着改代码
新手最常见的坏习惯：看到报错，**不看内容，凭感觉改一处，再跑**。

**结果**：改了三处，错误变了，但不知道为什么——**反而更难查了。**

**正确做法**：先把报错读完，在心里说出"**它是在说：第 X 行的 Y 操作，因为 Z 失败了**"，然后再动手。

@@point ② try / except：接住异常
@@need 要解决什么
"这一行可能出错，但我不想让整个程序崩"——这就是 `try` 的用途。
@@idea 核心思路
```python
try:
    可能出错的代码
except 异常类型:
    出错了怎么办
```

```python
try:
    n = int(input("请输入数字："))
    print(10 / n)
except ValueError:
    print("你输入的不是数字")
except ZeroDivisionError:
    print("不能除以零")
```

**执行流程**：

```cmd
#  try 里的代码
#    ├─ 没出错 ──▶ 跳过所有 except，继续往下
#    └─ 出错了 ──▶ 从出错那行【立刻跳出】，去匹配 except
#                     ├─ 匹配上 ──▶ 执行对应的处理
#                     └─ 没匹配上 ──▶ 继续往上抛（还是崩）
```

**几个写法**：

```python
# 捕获具体类型（推荐）
try:
    ...
except ValueError:
    ...

# 捕获多种类型
except (ValueError, TypeError):
    ...

# 捕获所有异常（慎用！见下面的坑）
except Exception as e:
    print(f"出错了：{e}")

# 把异常对象拿到手
except ValueError as e:
    print(f"具体原因：{e}")
```
@@trap 别裸写 except
```python
try:
    do_something()
except:                 # ✗ 裸 except：什么都抓
    pass                # ✗ 而且吞掉了，连日志都没有
```

**这行代码是"灾难级"的**，因为它会：

| 问题 | 后果 |
| 抓住**所有**异常 | 包括 `KeyboardInterrupt`（Ctrl+C 都不管用了） |
| **什么都抓** | 连你代码里的拼写错误、逻辑 bug 也一起吞了 |
| `pass` 吞掉 | **出了问题一点痕迹都没有**，程序"静悄悄地错" |

**正确姿势**：

- **尽量捕获具体类型**（`ValueError`、`requests.Timeout`）
- **至少 `except Exception as e`** 并且**打印或记日志**
- **真的有理由忽略时，写清为什么**（注释）

@@point ③ 精确捕获：多个 except 的排序
@@need 要解决什么
不同错误该有不同的处理方式——**超时应该重试，404 应该跳过，JSON 解析失败应该记下来**。全都一样处理等于没处理。
@@idea 核心思路
**从上往下匹配，命中第一个就走**：

```python
try:
    resp = requests.get(url, timeout=10)
    resp.raise_for_status()
    data = resp.json()
except requests.Timeout:
    print("超时了，稍后重试")
except requests.HTTPError as e:
    print(f"HTTP 错误 {e.response.status_code}，跳过这条")
except ValueError as e:          # json 解析失败会抛 ValueError
    print(f"返回的不是合法 JSON：{e}")
except requests.RequestException as e:     # 兜底：其它网络问题
    print(f"网络错误：{e}")
```

**顺序很重要**——**子类异常必须写在父类前面**：

```python
except Exception:            # ✗ 放最前面，后面全都进不来
    ...
except requests.Timeout:     # 永远到不了这里
    ...
```

**为什么？** 因为 `requests.Timeout` 是 `Exception` 的子类，**第一个就把它抓走了**。

**记法**：**从最具体写到最宽泛，兜底的放最后。**
@@trap 异常继承关系
```
BaseException
├── SystemExit
├── KeyboardInterrupt        ← Ctrl+C，别抓它
└── Exception                ← 你该抓的都在这下面
    ├── ValueError
    ├── TypeError
    ├── KeyError
    ├── OSError
    │   └── FileNotFoundError
    └── ...
```

**实践建议**：**捕获 `Exception`，不要捕获 `BaseException`**——后者会把 Ctrl+C 和程序退出也吞掉。

@@point ④ else 与 finally
@@need 要解决什么
"**只有没出错时才做的事**"和"**不管出不出错都必须做的事**"——比如文件必须关闭、日志必须写。
@@idea 核心思路
**完整结构**：

```python
try:
    risky()              # 1. 试着做
except SomeError:
    handle()             # 2. 出错时做
else:
    success()            # 3. 【没出错】才做
finally:
    cleanup()            # 4. 【不管怎样】都做
```

**`else` 的用处**——把"我怀疑会出错的代码"和"只有成功才做的代码"分开：

```python
try:
    data = json.loads(text)        # 只有这行可能抛异常
except ValueError:
    print("JSON 格式不对")
else:
    process(data)                  # 这里出错就不是"解析失败"了
```

**如果把它们都塞进 `try`**，那 `process(data)` 里抛的 `ValueError` 会被误判成"JSON 解析失败"——**这是个很隐蔽的 bug**。

**`finally` 的用处**——**无论发生什么都要执行**：

```python
f = open("data.txt")
try:
    content = f.read()
finally:
    f.close()          # 即使 read 抛异常，文件也会被关掉
```

**`finally` 和 `return` 的顺序**（容易踩坑，值得单独记住）：

```python
def f():
    try:
        return "try 的返回值"
    finally:
        print("finally 一定会执行")

print(f())
# 输出：
# finally 一定会执行
# try 的返回值
```

**规则**：**`finally` 在 `return` 真正返回之前执行。** 但如果 `finally` 里也有 `return`，它会**覆盖**掉 try 里的返回值——这是很容易埋雷的写法，**别这么干**。
@@trap finally 里的 return 会吃掉异常
```python
def bad():
    try:
        raise ValueError("出错了")
    finally:
        return "没事"       # ✗ 异常被吞掉了

print(bad())     # 没事   ← 异常无声无息地消失了
```
**规则**：`finally` 里有 `return` 会**丢弃正在传播的异常**。这是 Python 里最阴的坑之一，**永远不要在 `finally` 里写 `return`**。

@@point ⑤ 常见异常汇总
@@need 要解决什么
报错类型就那么十来个。**认识它们，你就能一眼看出问题在哪。**
@@idea 核心思路
| 异常 | 什么情况 | 常见原因 |
| `SyntaxError` | 语法错 | 少括号、少冒号——**根本跑不起来** |
| `IndentationError` | 缩进错 | Tab 和空格混用 |
| `NameError` | 名字没定义 | 变量名拼错、用在了定义之前 |
| `TypeError` | 类型不对 | `"1" + 1`、参数个数不对 |
| `ValueError` | 值不合法 | `int("abc")`、解包数量不匹配 |
| `KeyError` | 字典键不存在 | `d["不存在的键"]` |
| `IndexError` | 下标越界 | `a[100]` |
| `AttributeError` | 属性/方法不存在 | 名字拼错、对象是 `None` |
| `ZeroDivisionError` | 除以零 | `10 / 0`、`10 % 0` |
| `FileNotFoundError` | 文件不存在 | 路径写错、文件被删 |
| `PermissionError` | 没权限 | 文件被占用、系统目录 |
| `ImportError` / `ModuleNotFoundError` | 导入失败 | 没装库、名字写错 |
| `UnboundLocalError` | 局部变量未赋值 | 第五章的作用域问题 |
| `RecursionError` | 递归太深 | 忘了终止条件 |
| `JSONDecodeError` | JSON 解析失败 | 模型返回了非 JSON 文本 |
| `requests.Timeout` | 请求超时 | 网慢、对方限速 |

**`AttributeError: 'NoneType' object has no attribute 'xxx'`** —— 这个报错**极其常见**，意思是"**你拿到的对象是 `None`**"。通常是某个函数没返回值，或者查询没找到。**看到 `NoneType` 就往前找"为什么这里是 None"。**
@@trap 读报错的固定套路
```cmd
#  TypeError: unsupported operand type(s) for +: 'int' and 'str'
#  └─类型──┘  └───────原因──────────────────────┘ └──具体──┘
#
#  翻译：在第 X 行，你让 int 和 str 相加了——不支持
#  修法：把其中一个转成另一个类型
```

**固定三步**：**看类型 → 看原因 → 看行号**。

@@point ⑥ raise 与自定义异常
@@need 要解决什么
有时候**不是"系统出错了"，而是"你的业务规则不允许"**——比如"薪资为负""平台不支持"。这时候该你主动抛异常。
@@idea 核心思路
**`raise` 主动抛出异常**：

```python
def set_salary(v):   # 这里演示主动抛异常，故意写成普通函数   # 方法第一个参数是 self，漏了后面 self.salary 就 NameError
    if v < 0:
        raise ValueError(f"薪资不能为负：{v}")
    self.salary = v
```

**抛出 → 上层可以选择捕获或不捕获**：

```python
try:
    set_salary(-1)
except ValueError as e:
    print(f"参数有问题：{e}")      # 参数有问题：薪资不能为负：-1
```

**自定义异常**——定义一个自己的异常类，让上层能精确区分：

```python
class CollectorError(Exception):
    """采集相关的错误基类。"""

class PlatformNotSupported(CollectorError):
    """不支持的平台。"""

class PageStructureChanged(CollectorError):
    """页面结构变了，选择器失效。"""


# 用起来
raise PlatformNotSupported(f"没有 {platform} 这个平台的适配器")
```

**为什么要自定义？三个理由**：

| 理由 | 说明 |
| **能精确捕获** | 上层可以只 `except PlatformNotSupported`，不受别的错误干扰 |
| **能带上下文** | 异常对象上可以挂额外信息（`e.platform`、`e.url`） |
| **能分层** | 都继承自 `CollectorError`，上层一句 `except CollectorError` 抓住所有采集问题 |

**带上下文的写法**（实战里很有用）：

```python
class PageStructureChanged(CollectorError):
    def __init__(self, url, selector):
        super().__init__(f"选择器失效：{selector} @ {url}")
        self.url = url
        self.selector = selector


try:
    parse(page)
except PageStructureChanged as e:
    print(f"页面改版了：{e.url}")
    save_snapshot(e.url)          # 把现场存下来，方便事后分析
```
@@trap raise 的正确姿势
| 写法 | 评价 |
| `raise ValueError("xxx")` | ✅ 带上原因 |
| `raise`（在 except 里） | ✅ **重新抛出当前异常**，保留原始 Traceback |
| `raise ValueError("xxx") from e` | ✅ **链式异常**，能看出"因为 e 才抛的这个" |
| `raise ValueError` | ⚠️ 不带说明，别人看不懂 |
| `raise "字符串"` | ❌ Python 3 不允许 |

**在 `except` 里想"记录一下再往上抛"，用裸 `raise`**：

```python
try:
    do()
except Exception:
    logger.exception("出错了")     # 先记录
    raise                          # 再原样抛出，不丢栈信息
```
**别写 `raise e`**——那样会**重置** Traceback，丢失原始出错位置。

@@point ⑦ with：自动管理资源
@@need 要解决什么
打开文件、开数据库连接、开网络会话——**这些资源必须关闭**，否则会泄漏（文件被占用、连接耗尽）。手动 `close()` 很容易忘，尤其是在异常发生时。
@@idea 核心思路
**`with` 保证"离开代码块时一定清理"，哪怕中间抛了异常。**

```python
# 老写法：三层 try/finally，很啰嗦
f = open("data.txt")
try:
    content = f.read()
finally:
    f.close()

# with 写法：一行搞定
with open("data.txt", encoding="utf-8") as f:
    content = f.read()
# 出了这一行，文件自动关闭——不管有没有出错
```

**为什么不用手动 close？** 因为 `with` 背后调用的是**上下文管理器协议**：

```python
class MyResource:
    def __enter__(self):
        print("获取资源")
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        print("释放资源")            # ← 一定会执行
        # 返回 True 会【吞掉】异常，一般返回 None/False 让它继续抛
```

**这段代码就是"上下文管理器"的约定**——`with` 进入时调 `__enter__`，退出时调 `__exit__`（**包括异常退出**）。

**多个资源可以一起管**：

```python
with open("in.txt", encoding="utf-8") as fin, \
     open("out.txt", "w", encoding="utf-8") as fout:
    fout.write(fin.read())
```

**实战里你会遇到的 `with`**：

```python
with open(path, encoding="utf-8") as f:        # 文件
with sqlite3.connect(db) as conn:              # 数据库
with requests.Session() as s:                  # 网络会话（连接复用）
with lock:                                     # 线程锁
```
@@trap 编码问题
```python
open("data.txt")                        # ✗ Windows 上默认 GBK，读中文/UTF-8 会乱码
open("data.txt", encoding="utf-8")      # ✓ 永远显式指定
```
**这条规则几乎无例外**：**读写文本文件时永远写 `encoding="utf-8"`。** 跨平台、跨机器都不会出问题。

@@point ⑧ traceback 与日志
@@need 要解决什么
程序跑一整晚，早上起来发现"中间挂了"。**光看控制台滚动输出根本查不出来。** 你需要把异常完整地记到文件里。
@@idea 核心思路
**`traceback` 模块**——把异常信息变成字符串：

```python
import traceback

try:
    do_something()
except Exception:
    traceback.print_exc()                    # 打印到屏幕（和崩溃时一样详细）
    detail = traceback.format_exc()          # 拿到字符串，可以写文件/发邮件
```

**只看 `print(e)` 是不够的**——`print(e)` 只有一行错误信息，**没有调用链**：

```python
# print(e) 的输出
division by zero

# traceback 的输出
Traceback (most recent call last):
  File "a.py", line 8, in <module>
    main()
  File "a.py", line 4, in main
    print(1 / 0)
ZeroDivisionError: division by zero
```

**差在哪？** **traceback 告诉你"怎么走到这一行的"。** 没有调用链，你只知道错了，不知道从哪来的。

**用 logging 记录**——比 print 更适合长期运行的程序：

```python
import logging

logging.basicConfig(
    filename="collector.log",
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
    encoding="utf-8",
)
log = logging.getLogger(__name__)

log.info("开始采集 %s", url)
try:
    ...
except Exception:
    log.exception("采集失败：%s", url)      # ← 自动带上完整 traceback
```

**`log.exception()` 是 except 块里最该用的方法**——它会自动把 traceback 一起写进日志。

**日志级别怎么选**：

| 级别 | 什么时候用 |
| `DEBUG` | 调试细节（"正在解析第 3 个 div"） |
| **`INFO`** | **正常的关键节点**（"开始任务""入库 2 条"） |
| `WARNING` | 异常但能继续（"超时，重试中"） |
| `ERROR` | 出错了，这件事失败了 |
| `CRITICAL` | 整个程序没法继续 |

**实战建议**：正常流程用 `INFO`，被捕获的异常用 `WARNING`，导致这条数据失败的用 `ERROR` + `log.exception()`。
@@trap 别用 print 调试长期程序
| print 的问题 | logging 的好处 |
| 没法分级，全是噪音 | 能按级别过滤 |
| 没法同时输出到屏幕和文件 | 能配多个 handler |
| 没有时间戳 | 自带时间戳 |
| 一行一行加、一行一行删 | 写完留着，调级别就行 |

@@point ⑨ 调试实战：PyCharm 的 Debug
@@need 要解决什么
有些 bug **看报错看不出来**——程序不崩，就是结果不对。这时候需要**让程序慢下来，一行一行看**。
@@idea 核心思路
**三种调试手段，从轻到重**：

| 手段 | 什么时候用 | 怎么做 |
| **print / log** | 快速确认"走到这了吗""值是多少" | 加一行，跑一遍 |
| **断点调试** | 逻辑复杂、要反复看 | 点行号左侧打断点，`Shift+F9` |
| **单步 + 观察** | 已经定位到大致范围 | `F8` 单步、`F7` 进函数 |

**PyCharm 调试的四个核心操作**：

| 快捷键 | 作用 |
| `Shift + F9` | **以调试模式运行** |
| `F8` | **Step Over**——执行这一行，不进函数 |
| `F7` | **Step Into**——进到函数里面 |
| `F9` | **Resume**——继续跑到下一个断点 |
| `Ctrl + F8` | 在当前行打断点/取消断点 |

**调试面板里能看什么**：

- **Variables**——当前作用域所有变量的值（**最有用**）
- **Watches**——盯住某个表达式，比如 `len(jobs)`、`job["salary"]`
- **Frames**——调用栈，能看到"我是从哪被调进来的"
- **Console**——可以在暂停时**直接敲代码**试探，比如 `jobs[0]`

**最实用的一招：条件断点。** 循环跑到第 500 次才出问题？右键断点 → 填条件 `i == 500`，程序只在那一轮停下。
@@trap 调试的三个心法
**① 二分定位法**——不确定哪一段出错，就在中间打个断点/加个 print，**把范围砍一半**，重复几次就找到了。比从头一行行看快得多。

**② 最小复现**——把出错的部分抽成一个 20 行的小脚本，去掉所有无关代码。**能最小复现，就离修好不远了。**

**③ 假设要能被证伪**——"我觉得是薪资解析的问题"不是假设。**"如果我把这行的 `raw` 打出来，应该看到 `8-15K`"** 才是——因为跑一下就知道对不对。

@@summary
这一章你实际拿到的是**四样东西**：

| 拿到了什么 | 为什么要紧 |
| **让程序活下去的能力** | `try/except` 跳过坏数据继续跑——这是"演示"和"能跑一整晚"的分界线 |
| **读报错的套路** | 类型 → 原因 → 行号，三步定位，不再慌 |
| **记录现场的能力** | `traceback` + `logging` 把异常完整写进文件，第二天早上能查 |
| **一套自己的异常体系** | 自定义异常 + 分层继承，让上层能精确区分"平台不支持"和"页面改版了" |
