@@why 这一章在解决什么问题
还没登录就能让系统调用大模型给你生成文书？不行——LLM 按 token 计费，一次裸奔请求就是一次白嫖。LegalMind 需要一个**账号体系**：注册、登录、签发"令牌"（JWT），并且让聊天、文书、案例检索这些接口**只认登录用户**。
本章把认证全链路做透：**bcrypt 密码哈希**（密码不存明文）、**JWT 签发与校验**（无状态令牌）、**FastAPI 依赖注入**（`get_current_user` 一插，任何路由自动鉴权）。学完本章，你会有四个接口（注册/登录）和一套"插拔式"的鉴权守卫，后面所有需要登录的接口加一个 `Depends(get_current_user)` 就完事。

@@point ① 密码存储：为什么必须哈希
@@need 要解决什么
"把密码原样存数据库"是新手最容易犯但后果最严重的错误——数据库一旦泄露，所有用户密码裸奔。存储时必须"单向变换"，让明文不可恢复。
@@idea 核心思路
不存明文，存 **bcrypt 哈希**。bcrypt 的特点是"慢哈希"（故意计算慢，让暴力破解成本极高）+ 自动加盐（同样的密码每次哈希结果不同）。
```python
# app/utils/security.py
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def get_password_hash(password: str) -> str:
    return pwd_context.hash(password)

def verify_password(plain_password: str, hashed_password: str) -> bool:
    return pwd_context.verify(plain_password, hashed_password)
```
- 注册时：`hashed_password = get_password_hash(raw)` 存入 User 表。
- 登录时：`verify_password(raw, user.hashed_password)` 返回 True/False。
- **绝不 reverse**：哈希不可逆，"忘记密码"只能重置不能找回。
@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| bcrypt 报 "password cannot be longer than 72 bytes" | bcrypt 输入上限；前端限制密码长度或升级 argon2 |
| 每次哈希结果不同 | 这是 bcrypt 的盐机制，verify 时不比对哈希值而是调 verify() |
| passlib 与 bcrypt 4.x 兼容报错 | 装 `bcrypt<4.1` 或换 `pwdlib`；常见坑，先查版本 |

@@point ② JWT：无状态令牌的组成
@@need 要解决什么
登录成功后，怎么让服务器"记住"你是谁？传统 Session 存在服务器内存/数据库，扩容麻烦；JWT 把用户信息直接签进令牌，服务器不存 session，验签即知身份——这就是"无状态认证"。
@@idea 核心思路
JWT 由三部分组成：**Header（算法） + Payload（载荷，含用户 id） + Signature（签名）**，形如：
```text
<Header:算法>.eyJzdWIiOiI8dXNlcl9pZD4iLCJleHAiOjE3MDAwMDAwfQ.<Signature:签名>
```
签发逻辑（python-jose）：
```python
# app/utils/security.py（续）
from datetime import datetime, timedelta
from jose import jwt
from app.config import settings

def create_access_token(data: dict, expires_delta: timedelta | None = None):
    to_encode = data.copy()
    expire = datetime.utcnow() + (expires_delta or timedelta(minutes=settings.ACCESS_TOKEN_EXPIRE_MINUTES))
    to_encode.update({"exp": expire})
    return jwt.encode(to_encode, settings.SECRET_KEY, algorithm="HS256")
```
核心点：
- **`sub`（subject）**：载荷里存用户 id——服务端验签后从 sub 拿 user_id 查库。
- **`exp`（expire）**：过期时间，服务端校验时自动拒绝过期令牌。
- **`SECRET_KEY`**：签名密钥，泄漏=任意伪造令牌，必须留在 .env。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为 JWT 是加密的，把手机号、住址塞进 payload | JWT 只是签名防篡改，payload 是明文 base64，谁都能解码；密钥只能放 uid、过期时间这类非敏感信息 |
| token 不设过期时间 | 泄露的 token 永远有效，等于把钥匙交出去；access token 短时效（15-60 分钟）必须配 exp，刷新用 refresh token |

@@point ④ 登录接口：校验密码 + 签发新令牌
@@need 要解决什么
登录和注册的差异只在"校验"这一步：注册是"不存在就建"，登录是"必须存在且密码对，否则拒绝"。
@@idea 核心思路
```python
class LoginRequest(BaseModel):
    username: str
    password: str

@router.post("/login")
async def login(req: LoginRequest):
    user = await User.get_or_none(username=req.username)
    if not user or not verify_password(req.password, user.hashed_password):
        raise HTTPException(status_code=401, detail="用户名或者密码错误")

    token = create_access_token({"sub": str(user.id)})
    return {"access_token": token, "token_type": "bearer",
            "username": user.username, "nickname": user.nickname}
```
注意两个安全细节：
- **`get_or_none`**：查不到返回 None，不会抛异常——一条 if 同时处理"用户不存在"和"密码错误"，**统一提示 401**，不泄露"这个用户名注册过"。
- 明文密码只存在于请求体，不进日志、不进响应。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 校验时把数据库的哈希和用户输入的明文直接比较 | 必须先 `verify(明文, 哈希)`，拿哈希去比明文永远不对；用 passlib 的 `verify` 校验，别自己写比较逻辑 |

- `HTTPBearer(auto_error=False)`：**不自动报错**，让 credentials 为 None 时走我们自己的 401 文案（而不是 Swagger 默认英文报错）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| Swagger 调试 Authorization 不生效 | HTTPBearer 的 token 通过 Authorize 按钮填，不是手动加 header（两路径二选一） |
| 改动 SECRET_KEY 后旧 token 全部失效 | 预期行为！SECRET_KEY 变了旧签名全废，记住别再换 |
| User.get_or_none(id=user_id) 报类型错 | JWT 的 sub 是 str，查 UUID 前要确保 ORM 自动转换；若不转先 `uuid.UUID(user_id)` |
| 接口没传 token 返回 401 但文案奇怪 | 检查 auto_error 设置，None 分支要自定义文案 |

@@point ⑥ 前端对接：令牌存哪、请求头怎么带
@@need 要解决什么
后端签发 token，前端要"存下并每次带上"。localStorage vs cookie、请求拦截器在哪加，这些对接细节决定登录态好不好用。
@@idea 核心思路
LegalMind 前端（第 10、11 章展开）的策略：
- **存储**：`localStorage.setItem('token', resp.access_token)`，同时存 user 对象（含 nickname）。
- **自动携带**：axios 请求拦截器统一加头：
```text
// api/client.js
client.interceptors.request.use((config) => {
  const token = localStorage.getItem('token')
  if (token) {
    config.headers.Authorization = `Bearer ${token}`
  }
  return config
})
```
- **401 统一处理**：响应拦截器遇 401 清 token 并跳登录页——token 过期时全局踢回登录，不用每个接口写一遍。
- **路由守卫**：`/chat`、`/documents` 页面 `meta: { requiresAuth: true }`，无 token 直接 redirect 到 /login。
这样"登录 → 存 token → 自动带 token → 过期自动踢回"整条链路前端零手工操作。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| token 存 localStorage，页面被 XSS 就全丢了 | localStorage 对任何脚本可见；敏感服务建议 httpOnly cookie 存储，或至少保证无第三方脚本注入面 |

@@point ⑦ 路由守卫与登录页跳转
@@need 要解决什么
就算 token 逻辑都对，用户手动输 URL 访问 /chat 也会直接进页面——必须在路由层挡住未登录访问，这就是"前端守卫"。
@@idea 核心思路
vue-router 的 `beforeEach` 全局守卫（第 10 章细讲，这里给结论）：
```text
router.beforeEach((to, from, next) => {
  const token = localStorage.getItem('token')
  if (to.meta.requiresAuth && !token) {
    next({ name: 'Login' })          // 没登录 → 去登录页
  } else if ((to.name === 'Login' || to.name === 'Register') && token) {
    next({ name: 'Home' })           // 已登录 → 别留在登录页
  } else {
    next()                           // 放行
  }
})
```
注意：**守卫只是体验优化，安全还得靠后端**——前端守卫可被绕过（改 localStorage），真正防住非法访问的是每个接口的 `Depends(get_current_user)`。

@@point ⑧ 整条认证链路验证
@@need 要解决什么
写完了不会验证等于白写。用 curl 快速走一遍"注册 → 拿 token → 带 token 访问受保护接口 → 不带 token 被拒"，确认整条链路真实可用。
@@idea 核心思路
```text
# 1. 注册（成功返回 token）
curl -X POST http://localhost:8000/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"demo","email":"demo@test.com","password":"<demo_password>"}'

# 2. 登录（返回新 token）
curl -X POST http://localhost:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"demo","password":"<demo_password>"}'

# 3. 不带 token 访问受保护接口 → 401
curl http://localhost:8000/api/chat/sessions
# {"detail":"未登录"}

# 4. 带 token 访问 → 正常返回
curl http://localhost:8000/api/chat/sessions \
  -H "Authorization: Bearer <上一步返回的access_token>"
# {"sessions":[]}
```
验证通过的标志：**第 3 步必须 401**（说明守卫生效），第 4 步空列表也正常（还没会话）。
