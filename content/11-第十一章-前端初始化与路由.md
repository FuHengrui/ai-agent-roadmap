@@point ② main.js：Pinia + Router 挂载顺序
@@need 要解决什么
main.js 是前端入口，它决定"全局有哪些能力"。挂载顺序有讲究：Pinia 必须在 Router 之前——因为路由守卫里要用 Pinia store（auth）判断登录态。
@@idea 核心思路
```python
import { createApp } from 'vue'
import { createPinia } from 'pinia'
import App from './App.vue'
import router from './router'
import './style.css'

const app = createApp(App)
const pinia = createPinia()

app.use(pinia)      // 1. 先 Pinia：让守卫能用 auth store
app.use(router)     // 2. 再 Router：守卫里访问 useAuthStore() 才有值
app.mount('#app')
```
**为什么必须先 Pinia 后 Router**：Vue Router 的全局前置守卫在**路由导航前**执行，守卫里要 `useAuthStore()` 判断登录态；而 `useAuthStore()` 必须等 Pinia 安装后才能工作（否则报 "getActivePinia was called with no active Pinia"）。顺序反了，前端直接白屏。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 报错 "getActivePinia was called with no active Pinia" | Pinia 还没安装就在守卫/组件外调 useAuthStore；把 `app.use(pinia)` 放到 `app.use(router)` 之前，且不要在 store 外提前调用 |

@@point ③ 路由表：五路由 + meta 元信息
@@need 要解决什么
应用有哪些页面？哪些登录才能进？路由表 + meta 一次性说清楚，守卫逻辑只认 meta。
@@idea 核心思路
`router/index.js`：
```text
const routes = [
  { path: '/', component: HomeView, meta: { requiresAuth: false } },
  { path: '/login', component: LoginView, meta: { requiresAuth: false, guestOnly: true } },
  { path: '/chat', component: ChatView, meta: { requiresAuth: true } },
  { path: '/documents', component: DocumentsView, meta: { requiresAuth: true } },
  { path: '/cases', component: CasesView, meta: { requiresAuth: true } },
  { path: '/:pathMatch(.*)*', component: NotFoundView },
]

const router = createRouter({
  history: createWebHistory(),
  routes,
})
```
- **meta.requiresAuth=true**：chat/documents/cases 三页必须登录。
- **meta.guestOnly=true**：login 页对已登录用户反而不该看到（登录了还看登录页？跳回首页）。
- 404 兜底路由 `/:pathMatch(.*)*`：输错地址给友好的 NotFound 页。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 404 兜底路由放在最前面，所有页面全变 404 | 路由匹配按顺序，`/:pathMatch(.*)*` 必须放在路由表最后；放在前面会吞掉所有真实路由 |

@@point ④ 路由守卫：beforeEach 三行逻辑
@@need 要解决什么
"没登录不能进 chat"怎么落地？全局前置守卫在每次导航前执行：读 meta → 查登录态 → 决定放行还是踢去登录页。
@@idea 核心思路
```text
router.beforeEach((to, from, next) => {
  const authStore = useAuthStore()
  const requiresAuth = to.matched.some((r) => r.meta.requiresAuth)

  if (requiresAuth && !authStore.token) {
    next({ path: '/login', query: { redirect: to.fullPath } })
  } else if (to.meta.guestOnly && authStore.token) {
    next('/')
  } else {
    next()
  }
})
```
三行核心逻辑：
- **requiresAuth 且无 token** → 踢到 /login，并带上 `redirect`（登录成功后自动跳回原页面）。
- **guestOnly 且已登录** → 去首页（别浪费登录页）。
- **其余** → 放行。
- 用 `to.matched.some()` 而非 `to.meta`：**子路由继承父路由 meta**，深层路由也能取到。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 直接读 `to.meta.requiresAuth`，嵌套路由永远 false | `to.meta` **已经合并了 matched 各级**的 meta（子路由会继承父级）；这里用 `to.matched.some(...)` 是为了显式、也能兼容老版本。原文说法反了。所以别写成「读到 `to.meta.requiresAuth`，嵌套路由永远 false」；用 `to.matched.some(r => r.meta.requiresAuth)` 逐级向上找 |
| 守卫里用 `next()` 处理完异步再 next，页面跳转错乱 | 现代 Vue Router 推荐直接 `return true / { path }` 替代 next；至少保证每次导航只调用一次 next |

@@point ⑥ axios 拦截器：自动带 token、统一 401 处理
@@need 要解决什么
每个请求都手动塞 `Authorization` 头？那是 1999 年。用 axios 拦截器：**请求发出前自动加 token；响应回来遇 401 统一踢去登录**。
@@idea 核心思路
`api/http.js` 的封装：
```python

// 请求拦截器：自动带 token
http.interceptors.request.use((config) => {
  const authStore = useAuthStore()
  if (authStore.token) {
…（以下省略 11 行，完整代码见仓库对应位置）
      authStore.logout()
      router.push({ path: '/login', query: { redirect: router.currentRoute.value.fullPath } })
    }
    return Promise.reject(error)
  }
)

export default http
```
- **请求拦截器**：所有请求自动带 `Bearer token`，业务代码零感知。
- **响应拦截器**：401 说明 token 失效/过期 → 清空登录态 → 跳登录页并记 redirect。
- **返回 `response.data` 解包**：业务代码拿到的直接是后端 JSON，不必每处 `.data.data`。
- 注意：**流式接口不能用 axios**（axios 不支持流式读取），聊天流用原生 fetch（第 10 章 SSEClient）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 拦截器里在模块顶层缓存 store 报错 | 拦截器运行在组件外，Pinia 实例可能没就绪；在拦截器函数内部再调用 `useAuthStore()`（拿到执行时的实例），别在模块顶层缓存 |
| 401 跳转造成死循环（登录页自己也发 401 请求） | 响应拦截器对 /login 相关请求或已处于登录页时跳过重定向，否则死循环白屏 |
