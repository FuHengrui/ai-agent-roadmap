@@h1 第十五章　Docker 概述与容器化思想
@@sub 阶段 18 · 云原生开发环境与 DevOps 工具链　|　容器化　|　难度 ★★★

@@why 这一章在解决什么问题
你在自己电脑上把程序跑通了，发给同学，他来一句："报错了，缺环境。"
你让他装 JDK，他说有；让他配 MySQL，版本不对；改配置改了半小时，还是起不来。
这就是经典的**"在我电脑上是好的"**——程序和它依赖的环境是两码事，光把代码发过去，环境没人帮你带。

Docker 的答案很暴力：**把程序和它需要的整个运行环境一起打包成一个"集装箱"，连锅带饭一起端走。**
这一章用大白话讲清楚：Docker 是怎么想的（集装箱思想）、它和虚拟机差在哪、以及镜像/容器/仓库三大核心概念。
读完你能回答一个关键问题：**"Docker 到底解决了什么，让全世界都在用它。"**

@@map 这一章在整个知识库里的位置
**上一章**：阶段 17 收官——MySQL 索引、事务、用户管理，数据库能力闭环
**本章** ← 你在这里：Docker 第一课——搞懂"容器化到底是什么"（纯概念，不敲命令）
**下一章**：镜像与容器基本操作——装好 Docker，亲手 pull 镜像、run 容器
**阶段终点**：会装、会用、会自定义镜像、会管网络、会发布——一套云原生交付能力

@@note info 学习提示
本章是**纯概念章，一个命令都不用敲**。学的时候别急着背定义，抓住三个问题：
① 环境为什么难复制？② 集装箱解决了什么？③ 镜像/容器/仓库各管哪一头？
想清楚这三件事，后面的命令操作全是水到渠成。

@@point ① 交付困境：为什么"在我电脑上是好的"
@@need 要解决什么
你写完一个 Java 项目，想让它跑在任何一台机器上。
难题在于：**程序只是冰山一角**，底下压着一大坨"看不见的依赖"——JDK 版本、Tomcat、MySQL、各类配置文件、环境变量。
这些依赖散落在系统里，靠一份"安装文档"根本无法保证每次装出来都一样：有人装错版本、有人漏一步、有人系统本来就装了别的东西。
**环境没法标准化复制，程序就跑不"稳"。**

@@idea 核心思路
传统做法是"程序 + 安装文档"，把装环境的活儿甩给使用者。
Docker 换成"程序 + 环境一起打包"：环境被提前做好、塞进一个文件里，使用者不需要懂安装细节，拿来就能跑。
就像外卖：你不关心后厨怎么做的，拿到手的是一份完整的餐。

```
  传统交付                       Docker 交付
┌──────────┐   → 接受方    ┌──────────────┐   → 接受方
│ 程序源码   │     慢慢折腾   │ 程序 + 依赖   │     直接跑
│ + 安装文档 │              │ + 环境 + 配置 │
└──────────┘              └──────────────┘
```

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为 Docker 是"把程序打包"，装环境的活还得自己干 | Docker 打包的是"程序 + 环境"整体，环境在**制作镜像**时已完成，使用者不再碰 |
| 以为装好 Docker 程序就能自动跑 | Docker 只是运输工具，还得有对应的镜像；下一章讲怎么拿镜像 |

@@point ② Docker 是谁：一个开源的应用容器引擎
@@need 要解决什么
要理解容器化，先认识提出这个方案的家伙是谁、它凭什么能统一"打包"这件事。

@@idea 核心思路
Docker 是一个**开源的应用容器引擎**，用 Go 语言编写，按 Apache 2.0 协议开源（可以自由使用、商用）。
它的 logo 是一头鲸鱼驮着集装箱：

```
        ~~~~
     ~~~~~~~~
   ~~~ 鲸鱼 ~~~   箱  箱  箱  箱   ← 每个箱子是一个容器
     ~~~~~~~~
        ~~~~
```

含义很直白：**鲸鱼（Docker 引擎）驮着一堆集装箱（容器），正在把货物（你的应用）运到任何地方去。**
"Docker"直译是"码头工人"，和"Container（集装箱/容器）"是一套码头隐喻——程序就是货物，Docker 就是那个搬货的码头工人。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为 Docker 是虚拟机、是云平台 | Docker 是"容器引擎"——它负责把程序装进标准容器运走，不是给你一台虚拟电脑 |
| 以为"开源"= 免费没保障 | Apache 2.0 有明确使用授权，是企业可以放心用的主流开源协议 |

@@point ③ 集装箱思想：标准化、可堆叠、互不影响
@@need 要解决什么
货运行业以前最头疼的事：货物形状千奇百怪，装卸慢、容易坏、运到哪都得单独设计搬运方式。
IT 行业也一样：每个程序的依赖、配置、运行方式各不相同，换台机器就要重新调一遍。

@@idea 核心思路
思路来自海运的**集装箱**：所有货物不管里面装什么，先塞进统一规格的钢制箱子。好处有三条——
**格式划一**（全世界的吊车都能吊）、**层层堆叠**（省空间）、**箱箱互不影响**（一个箱子坏了不连累别的）。
IT 借鉴了这套理念，于是有了"容器"（Container）这个词：
你的程序放进一个标准容器里，这个容器在开发机、测试机、服务器上长得一模一样，互相之间互不干扰——这才有了"环境一致"。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为"集装箱"能把程序直接塞进去就完事 | 程序要先做成镜像（装好环境与启动配置）才能装进容器；集装箱只管标准化运输，货物本身要事先打包好 |
| 以为"箱箱互不影响"= 容器之间数据天然共享 | 隔离指的是进程和文件系统互不干扰；想共享数据要靠第 17 章的数据卷，不是默认行为 |

@@point ④ 容器 vs 虚拟机：轻得不是一点半点
@@need 要解决什么
虚拟机也能"隔离环境"，凭什么 Docker 后来居上？
因为传统虚拟机**太重了**：每台虚拟机都要装一整个操作系统（几 GB），开机要几分钟，一台机器也开不了几个。

@@idea 核心思路
对照表（记住这几个数字就够面试用了）：

| 对比项 | 容器 Docker | 虚拟机 VM |
|---|---|---|
| 启动速度 | 秒级 | 分钟级 |
| 磁盘占用 | 一般 MB 级 | 一般 GB 级 |
| 性能 | 接近原生 | 弱于原生（多一层虚拟化开销） |
| 单机支持量 | 上千个容器 | 一般几十个虚拟机 |
| 隔离性 | 完全隔离 | 完全隔离 |

原因一句话：**虚拟机模拟了一整台电脑（含操作系统），容器只是把程序和依赖装进一个隔离的"进程房间"，操作系统仍然共用宿主机的。**

```
  虚拟机                              容器
┌────────────────┐              ┌────────────────┐
│ 应用A │ 应用B  │              │ 应用A │ 应用B  │
│ 来宾OS│ 来宾OS │              └──┬────┴───┬────┘
│ Hypervisor(虚拟化层)              │ 共享宿主 Linux 内核
└───────┬────────┘              ┌──┴─────────┴────┐
    物理机（每个OS占几GB）          │  docker 引擎      │
                                └────────────────┘
                                    物理机（只有一个OS）
```

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为容器是"更轻的虚拟机" | 虚拟机模拟整个硬件+系统，容器共享宿主内核、只隔离进程和文件系统——原理完全不同，见下一个知识点 |
| 以为容器隔离性和虚拟机一样 | 容器对进程/文件/网络都是隔离的，但安全边界级别不如虚拟机；对安全要求极高的场景才需要虚拟机 |

@@point ⑤ 虚拟化与 Docker：操作系统级虚拟化
@@need 要解决什么
上一张表说容器"共享宿主内核"，这到底算不算虚拟化？属于虚拟化里的哪一类？——先搞懂"虚拟化"本身。

@@idea 核心思路
先看"虚拟化"是什么意思。一套房子市场价 2000/月，怎么租得更贵？两个方案：
① 租给一个不差钱的租户，收 6000（一台机器跑一个大应用，资源浪费）；
② 把房子隔成 4 间，各收 1500（一台机器分给 4 个用户，物尽其用）——**这就是虚拟化：把一台电脑"分"给多个使用方。**

虚拟化分很多种：完全虚拟化、硬件辅助虚拟化、部分虚拟化、超虚拟机化、**操作系统虚拟化**。
Docker 的容器技术属于**操作系统虚拟化**——它不虚拟整台电脑，只在同一个操作系统里把"进程 + 文件系统"按容器隔开。
这也是它比虚拟机轻的核心原因：不装来宾系统、不改硬件。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把 Docker 归类成"硬件虚拟化" | 容器不模拟硬件、不装来宾系统，属于操作系统层虚拟化；这个归类在考试/面试里是常见送分点，别丢 |

@@point ⑥ 两句口号：Build, Ship and Run / Build once, Run anywhere
@@need 要解决什么
前面讲了一堆思想，用两句话总结 Docker 的终极目标，也让后面学习有个"北极星"。

@@idea 核心思路
**「Build, Ship and Run」——搭建、发送、运行。**
你在本地把环境搭好（Build），把成品打包发出去（Ship），在任何机器上一键运行（Run）。

**「Build once, Run anywhere」——搭建一次，运行到任何地方。**
一次构建出的镜像，不管到哪台机器都能跑，不用重装、不用调版本。

这两句话对应 Docker 的四大优势：**交付部署更快、资源利用更高、迁移扩展更容易、更新管理更简单。**
记住这两句口号，后面所有 Docker 操作都是它的具体实现。

@@point ⑦ 核心概念一：镜像（Image）——装好环境的"模板"
@@need 要解决什么
"环境一致"需要一个可以反复复制的成品。这个成品在 Docker 里叫什么？长什么样？

@@idea 核心思路
**镜像（Image）**就是那个成品——一个面向 Docker 引擎的**模板**，里面包含一个完整的文件系统（装好的程序、依赖、配置都在里面）。
它和"虚拟机镜像"类似，但体积小得多（因为共享宿主内核）。
关键特性：**镜像只读、不可变**。你拿同一个镜像创建容器，每次出来的环境都一模一样——这就是"可移植"的根基。

打个比方：**镜像 = 做蛋糕的模具**。模具本身不能吃，但用它烤出来的每个蛋糕都一样。
另一个说法：**镜像 = 类（模板），容器 = 对象（实例）**，面向对象思维直接复用。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为镜像能直接修改 | 镜像是只读的，改不了；想改环境请用 Dockerfile 重新构建（第 18 章），或在容器里改完再固化（不推荐） |
| 以为一个镜像只能开一个容器 | 一个镜像可以开无数个容器，互不影响；这就是"模板"和"实例"的关系 |

@@point ⑧ 核心概念二：容器（Container）——镜像跑起来的实例
@@need 要解决什么
镜像做好了，怎么让程序真正跑起来？镜像里装的是"静态的环境"，程序要动起来，需要一层"能改"的空间。

@@idea 核心思路
**容器（Container）就是镜像的运行实例**：镜像是只读模板，容器是它的"活体"。
容器可以启动、停止、删除；多个容器互不可见、互不干扰（隔离）。
记住一个公式：

```
容器 = 镜像（只读层） + 可读写层（最上面一层）
```

程序运行要写文件、要写日志、要存数据——这些都写在顶层的可读写层，不动下面的只读层。
所以同一个镜像能开出无数个互不影响的容器。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 以为改了容器里的文件，镜像也变了 | 改的是容器顶层的可读写层，镜像的只读层不动；每次用同一镜像开容器，都是"干净的" |
| 容器一删，写进去的数据也没了 | 可读写层跟着容器走；想让数据活下来，需要第 17 章的数据卷 |

@@point ⑨ 核心概念三：仓库（Repository）——镜像的"中央货架"
@@need 要解决什么
镜像要能"搭建一次、到处运行"，前提是能方便地分发——你做的镜像，别人怎么拿到？

@@idea 核心思路
**仓库（Repository）就是集中存放镜像的地方**，类似 Maven 的中央仓库（存 jar 包）、代码仓库（存代码）——Docker 只是把"存的东西"换成了镜像。
最大的公开仓库是 **Docker Hub**（Docker 官方），里面有海量现成镜像（centos、openjdk、tomcat、mysql……），下载即用。
国内也有镜像仓库提供更稳定的访问（如阿里云 ACR，第 20 章细讲）。

三个概念的关系一句话：**仓库里存镜像，镜像开出容器。**

```
             仓库 Repository（存放镜像，如 Docker Hub）
                     │
                     │ docker pull（下载）
                     ▼
              ┌──────────┐   docker run（运行）
              │  镜像 Image│ ───────────────────► 容器 Container
              │ (模板/只读) │        （每个容器 = 镜像 + 可读写层）
              └──────────┘
```

@@point ⑩ 三概念闭环：从仓库拉镜像，用镜像开容器
@@need 要解决什么
镜像、容器、仓库各说了一遍，但新手最容易懵的是**三者到底怎么配合**——先看一个完整小场景。

@@idea 核心思路
完整链路（先混个脸熟，命令下一章才敲）：

1. 在 Docker Hub（仓库）里找到要用的镜像，比如 `openjdk:11`；
2. `docker pull` 把它下载到本地——本地从此有了一份镜像（模板）；
3. `docker run` 用镜像**开一个容器**——程序开始跑；
4. 容器不够用？再 run 一个——同一镜像，多开几个都行；
5. 自己的应用也可以**做成新镜像推回仓库**，分享给别人。

同时也给你打个预防针：Docker 概念不复杂，但**上手有学习曲线**——命令多、参数多、报错信息不好看。
别指望一章全会，先跟着第 16 章把"拉镜像、跑容器"练熟，其他命令都是它的变体。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 三个概念记混，不知道谁是谁 | 套面向对象：镜像=类、容器=对象、仓库=类库（jar 包仓库）；想通这个一辈子不忘 |
| 以为镜像必须从零做 | 90% 的镜像仓库里有现成的，先 pull 后用，需要定制再走第 18 章的 Dockerfile |

@@summary 本章小结
| 问题 | 答案 |
|---|---|
| Docker 解决什么问题 | 环境不一致：把程序+环境打包成容器，一处构建、到处运行 |
| Docker 是什么 | 开源应用容器引擎（Go 语言、Apache 2.0），鲸鱼驮集装箱，码头工人搬货 |
| 集装箱思想是什么 | 标准化、可堆叠、互不影响，于是有了"容器" |
| 容器和虚拟机差在哪 | 秒级 vs 分钟级、MB vs GB、上千个 vs 几十个、共享内核 vs 模拟整机 |
| Docker 属于哪类虚拟化 | 操作系统级虚拟化 |
| 镜像 | 模板，只读，装好环境的成品 |
| 容器 | 镜像的运行实例 = 镜像 + 可读写层，隔离、可启停删 |
| 仓库 | 集中存放镜像的地方，最大的是 Docker Hub |
| 三概念怎么配合 | 仓库拉镜像 → 镜像开容器 → 新镜像推回仓库 |

一句话总结：**环境难复制所以有了"程序+环境"一起打包的容器；容器是操作系统级虚拟化，比虚拟机又轻又快；镜像（模板）→ 容器（实例）→ 仓库（货架）三者闭环，就是 Docker 的全部骨架。**
