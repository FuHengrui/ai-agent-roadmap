@@why 这一章在解决什么问题
**Vibe Coding 的终极问题：AI 改错了一堆代码，怎么无损回到"改之前"？AI 每次都要重新交代的偏好，能不能写成"长期记忆"让它永远记得？** 这一章是 Codex 的"工程化双件套"：**Git 代码管理**（初始化、提交、回滚、分叉、工作树）和**记忆扩展**（AGENTS.md、插件、Skills、MCP）。

学完这一章，你能回答：**Codex 怎么初始化 Git、代码回滚的三种姿势（checkout / reset --soft / reset --hard；分叉属于下面「平行实验」那一节）、工作树 worktree 与回滚的关系、AGENTS.md 是什么怎么用、插件能扩什么、Skills 与 MCP 分别是什么**。

@@point ① Git 初始化：一切回滚的前提
@@need 要解决什么
"AI 改错能回滚"的第一步是什么？——先把项目交给 Git 管起来。

@@idea 核心思路
**在 Codex 中初始化 Git**：让 Codex 项目进入版本控制状态，后续所有"提交/回滚/分叉"才有地基。

```bash
# 概念示例：在项目目录初始化 Git 仓库
git init

# 提交当前基线（"实验前快照"）
git add .
git commit -m "baseline: 开始 AI 改造前的基线"
```

**为什么必须做**：没有 Git 时的 AI 改动是"不可逆的赌注"；有 Git 后，每一次实验都有**检查点**可回。

建议节奏（Vibe Coding 铁律）：

```text
开工前 → 初始化 + 提交基线
每完成一个小里程碑 → 提交一次
AI 要动大手术前 → 再提交一次（保平安）
```

**和权限沙箱的分工**：沙箱防"危险操作偷偷执行"，Git 救"改错了想反悔"——**一个管入口，一个管出口**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 开始实验前没初始化 | 没基线就无法干净回滚；**先 init+commit 再让 AI 动手** |
| 一个大任务完成后才提交 | 里程碑粒度提交才有用；"完成才提交"=只有一个检查点 |
| 把 .git 目录删除当回滚 | 删 .git 丢全部历史；回滚用的是 checkout/reset（下一点） |

@@point ② 代码回滚：实验失败的后悔药
@@need 要解决什么
AI 改崩了怎么回到之前？Codex/Git 提供的回滚姿势有哪些？

@@idea 核心思路
Git 回滚的**三种常用姿势**：

| 姿势 | 命令（概念） | 用途 |
|---|---|---|
| **丢弃工作区改动** | `git checkout -- <file>` 或 `git restore <file>` | 只清「未暂存」的改动（已 `git add` 的要先 `restore --staged`，或 `reset --hard` 才真丢） |
| **软回退指针** | `git reset --soft HEAD~1` | 回退提交记录但**保留改动**在暂存区（改主意了想重做） |
| **硬回退** | `git reset --hard <commit>` | 彻底回到某提交，之后改动**全部丢弃**（慎用） |

**在 Codex 中操作**：直接对话命令让 Codex 执行回滚（或手动在终端执行）；回滚类命令属于**权限沙箱内需授权的操作**，确认后再执行。

**使用原则**：

- 只想丢掉"最近的烂活" → checkout/restore；
- 想重做最近一次提交 → reset --soft；
- 想彻底抛弃一段时间内的所有改动 → reset --hard（**先确认没有要留的东西**）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| reset --hard 后"我的修改没了" | hard 会**丢弃未提交/后续提交**；用前三次确认（要留的先 commit/stash） |
| 回滚了但 AI 再次执行同样操作 | 回滚≠防复发；把"别那么做"的约束写进 **AGENTS.md** |
| 对公共分支乱 reset | reset 改历史，**共享分支上慎用**；自己实验分支随便，公共分支用 commit 修复 |

@@point ③ 分叉与工作树：平行实验不打架
@@need 要解决什么
想让 AI 同时试两条方案（A 方案、B 方案），互不影响、可随时切换——怎么办？

@@idea 核心思路
**分叉（Fork/Branch）**：从当前状态分出一个**独立分支**，让 AI 在一个分支上实验，原分支保持不动。

```bash
# 概念示例：开分支做危险实验
git branch experiment/refactor-v2
git switch experiment/refactor-v2
# ……AI 在分支上随便改……
git switch main        # 随时切回主线
```

**工作树（Worktree）**：更彻底的平行——**同一个仓库开出多个工作目录**，各自独立 checkout 不同分支：

```bash
git worktree add ../proj-exp experiment/refactor-v2
```

**两种方式的定位**：

| 方式 | 特点 | 适合 |
|---|---|---|
| **分叉（branch）** | 同一目录切换分支 | 快速实验、切换查看 |
| **工作树（worktree）** | 多目录并行，互不干扰 | 多方案**同时**进行、需要并排对比 |

和 Codex 的关系：**外接 VSCode 打开的就是工作树**（上一章）；"新方案开新 worktree"让 AI 的实验与主线物理隔离，是**最安全的探索姿势**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 分支切来切去丢了现场 | 切分支前 **commit 或 stash**；未提交改动会跟着你走，容易乱 |
| 多个 worktree 装依赖 | worktree 只共享 `.git` 元数据，**node_modules 各装各的**、不会互相冲突；代价是重复安装、占磁盘 |
| 实验分支永不合并也不清理 | 实验完要么 merge、要么删分支，**别让分支长杂草** |

@@point ④ AGENTS.md：Codex 的长期记忆
@@need 要解决什么
每次开新对话都要重新交代"用中文注释、别动 utils 里那个函数、测试必写"——能不能写进文件一劳永逸？

@@idea 核心思路
**AGENTS.md** 是 Codex 的**项目记忆文件**——把项目的规则、约定、注意事项写进这个 Markdown 文件，Codex **在（重新）开始任务时自动读取**，作为行为准则。

**在项目根目录放置 AGENTS.md**，内容示例：

```markdown
# 项目约定
- 代码注释使用中文
- 不要修改 utils/legacy.js（历史遗留，改动风险高）
- 所有新功能必须附带测试
- 变量命名使用 camelCase
```

**为什么它这么好用**：

- **自动加载**：新会话无需重复交代；
- **上下文省 token**：规则常驻、对话不用反复粘贴；
- **团队共享**：所有用 Codex 的人共享同一套约定。

**善用三招**：①把"AI 常犯的错"写进去（防复发）；②把"本项目特殊约定"写进去（保一致性）；③把"危险区（别碰什么）"写进去（护底线）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| AGENTS.md 写太长塞爆上下文 | 写**要点**别写论文；长规则拆成"路径+条目"，能省则省 |
| 改了 AGENTS.md 但 Codex 没反应 | 新会话才会重新读取；**改完开新对话**验证生效 |
| 把所有通用偏好写进项目级 AGENTS.md | 通用偏好（全程中文等）可放**用户级规则**，项目级专注本项目专属约定 |

@@point ⑤ 插件与自动化：给 Codex 加装技能
@@need 要解决什么
Codex 默认能力不够用、重复流程每次手写——怎么扩展？

@@idea 核心思路
**插件（Plugin）/自动化扩展**：给 Codex 增加**工具与自动化能力**的机制。

典型用途（一种思路）：

- 扩展命令集：为 Codex 增加自定义命令（工作流类操作一键触发）；
- 自动化流程：把"构建→测试→提交"这类固定流程封装，Codex 一键执行；
- 集成外部工具：接入代码分析、部署脚本等第三方工具。

**插件形态的提示（重要）**：Codex 的插件通过在其环境中**注册/配置**使用；**安装前看清来源与权限**——插件可能包含执行能力，别装来源不明的。

```text
示例（概念）：定义一条自定义流程
build → test → lint → git commit
之后一句 "跑一遍流程" 即可触发
```

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 装了来路不明的插件 | 插件的执行能力=代码执行；**选官方/可信来源**，安装前看权限说明 |
| 插件和现有环境冲突 | 先备份配置再装；冲突时逐个排查/禁用 |
| 以为必须装插件才能用 Codex | 插件是"增强项"；基础能力（对话/搜索/计划）开箱即用 |

@@point ⑥ Skills 与 MCP：能力包与生态接入
@@need 要解决什么
Codex 的扩展生态里还有两个高频词：Skills 和 MCP。它们分别是什么？

@@idea 核心思路

**Skills（技能包）**

- 把特定领域的工作流/知识打包成**可复用的技能文件**（类似"招式"），Codex 按需调用；
- 与 AGENTS.md 的"规则"区别：Skills 更像"**做某类事的完整方法**"（如"帮我审查代码"按固定步骤来），规则是"**行为约束**"。

**MCP（Model Context Protocol，模型上下文协议）**

- 一套**开放协议**，让 AI 应用（如 Codex）**标准化地接入外部工具和数据源**（数据库、API、内部系统……）；
- 价值：**生态互联**——写一次适配，多个 AI 工具都能用；不再每个工具各写各的对接。

**三者的分工**（本阶段理解到这一层即可）：

| 机制 | 管什么 |
|---|---|
| **AGENTS.md** | 项目"规矩"（行为约束） |
| **Skills** | 某类任务的"招式"（方法流程） |
| **MCP** | 对外部工具/数据的"接口"（生态通道） |

**和阶段前文的呼应**：第 5 章 Trae 讲过 MCP 概念（三组件、两传输）——**MCP 是行业通用协议**，Trae、Codex 等都在用它接外部世界，这正是"知识库前后呼应"的点。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| AGENTS.md / Skills / MCP 三者混淆 | 记忆口诀：**规矩（AGENTS.md）、招式（Skills）、通道（MCP）** |
| 以为 MCP 是 Codex 独有 | MCP 是**开放标准协议**，多家 AI 工具支持；第 5 章 Trae 已涉及 |
| 一上来就追求全套扩展 | 先跑通基础闭环，再按需加 Skills/MCP；**扩展是手段不是目的** |

@@point ⑦ AGENTS.md 写作清单：该写什么、别写什么
@@need 要解决什么
AGENTS.md 到底写什么？写太多是"长篇文档"、太少又约束不住 AI——这里有一份明确的"适合/不适合"清单。

@@idea 核心思路
AGENTS.md 的内容边界有一条明确说明：

**适合写进去的内容**：
- 项目使用的包管理器、测试命令、构建命令；
- 修改代码后**必须执行的验证步骤**；
- **不能触碰的目录、密钥、生成文件或外部系统**（风险边界）；
- 团队约定的代码风格和提交前检查；
- 特定子目录的例外规则（如后端/前端/脚本目录各自的验证命令）。

**不适合写进去的内容**：
- 大段产品背景、历史会议纪要、完整 API 文档；
- 会频繁变化的临时任务列表；
- 密钥、账号、Token 或只能给人看的内部凭证（**红线：密钥绝不进规则文件**）；
- 可以通过命令自动发现的信息（例如完整文件树）。

**还可以让 AI 帮你写**：让 Codex"通读当前项目，把学到的项目信息保存到 AGENTS.md 文件里，用中文、格式清晰"——AI 自动沉淀项目知识。

**核心判断标准**：AGENTS.md 不是越长越好，它该写"**Codex 做事前必须知道的规则**"，而不是把所有项目文档复制进去。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把密钥/Token 写进 AGENTS.md | **绝对禁止**；密钥用环境变量/凭证管理，规则文件只写"不要触碰密钥文件" |
| AGENTS.md 越写越长 | 定期瘦身：超过"做事前必知"范围的移出；长文档放项目 docs，规则只做索引 |
| 写完发现 Codex 不守规则 | 检查是否**新会话**（AGENTS.md 在新对话自动读取）、内容是否具体可执行（"别乱改"这种空话无效） |

@@point ⑧ 插件与自动化实例：GitHub + Gmail 组合拳
@@need 要解决什么
插件和自动化到底怎么用？看一个完整的组合实战——让 Codex 自动"查 GitHub 项目 + 发邮件给自己"。

@@idea 核心思路
完整实例：

**插件是什么**：插件是**第三方服务器为 Codex 编写的软件包**，第三方把自己的能力用插件形式注入 Codex；目前 Codex 的插件市场已经非常丰富。**连接 GitHub、Gmail 等第三方服务时，需要进行授权操作。**

**组合实战流程**：

```text
1. 安装/连接 GitHub 插件（授权）
2. 安装/连接 Gmail 插件（授权）
3. 指令："用 /github 看本周关于 AI Agent 一个月内 star 数
   前 10 的开源项目，用 /gmail 把列表发邮件给我"
4. 追加自动化："把上述任务做成自动化，每周五下午 5 点半
   都发邮件给我"
```

- 第一步：插件提供**能力**（查 GitHub / 发 Gmail）；
- 第三步：**一条指令**同时驱动两个插件完成"查 + 发"；
- 第四步：**定期对话**实现自动化——把任务设为周期执行，无需手动触发。

**学习要点**：插件的价值=**把外部服务能力注入 Codex**；自动化的价值=**把固定任务交给定期对话**。两者配合，Codex 从"回答工具"变成"常驻自动化助手"。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 插件连接第三方服务时拒授权 | 授权是**必要步骤**（OAuth 类）；先明白"插件要读取什么、能干什么"再授权 |
| 自动化任务频率设错 | 定期对话先确认**触发时机**（周五 17:30 等）再落地；别用错周期造成骚扰 |
| 把"能查 GitHub"当成"能改你仓库" | 插件权限**按授权范围**；只授任务所需的最小权限，别图省事全给 |

@@summary
收官章，你集齐了 Codex 的"工程化双件套"：

| 拿到了什么 | 为什么要紧 |
|---|---|
| **Git 初始化**：init + 基线提交 | 一切回滚的地基；无提交不实验 |
| **三种回滚**：checkout（丢工作区）、reset --soft（退指针留改动）、reset --hard（彻底回退） | 改崩了有后悔药，且知道哪颗药配哪种病 |
| **分叉与工作树**：分支切实验、worktree 开平行工作目录 | 多方案并行互不打架，探索最安全姿势 |
| **AGENTS.md**：项目长期记忆，新会话自动读取 | 规则一次写入、处处生效、避免重复交代 |
| **插件与自动化**：自定义命令与流程封装 | 固定流程一键触发 |
| **Skills 与 MCP**：招式包与开放协议生态 | 规矩（AGENTS.md）、招式（Skills）、通道（MCP）三层扩展观 |

一句话记住本章：**Codex 的工程化靠 Git 兜底（初始化→提交→回滚→分叉/worktree 平行实验）、靠 AGENTS.md 记忆（规矩写进文件自动读）、靠插件/Skills/MCP 扩展（加招式、通外部）；至此，Trae、Cursor、Codex 三条 Vibe Coding 路线全线通关。**
