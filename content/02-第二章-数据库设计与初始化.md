@@sub 阶段 10 · 安康智慧健康管理平台（糖尿病AI健康助手）　|　2 课时　|　难度 ★★★

@@why 这一章在解决什么问题
上一章画完了系统蓝图，但系统要存"患者是谁、血糖多少、吃了什么、用了什么药"——这些数据得有个家。本章解决两件事：**一是设计 7 张业务表的结构**（字段、类型、约束、外键），**二是把建库 SQL 跑起来**，让 MySQL 里真的有这 7 张表。

关键认知：**后面所有章节（CRUD、统计、报告、AI 对话）都建立在表结构之上**。表设计错了，后面改起来伤筋动骨——比如血糖表没存测量时间，趋势分析就做不了；运动表没存运动前后血糖，bs_change 就是空中楼阁。所以本章是"地基中的地基"。

@@point ① 开发环境准备：小皮 + MySQL8 + Navicat
@@need 要解决什么
没有数据库服务，一切表设计都是纸上谈兵。先解决"MySQL 从哪来、怎么连"。

@@idea 核心思路
讲义用的是一套 Windows 经典组合：

1. **安装小皮工具（phpStudy）**：一键集成了 MySQL 8.0 等环境，比单独装 MySQL 再配服务省事很多。
2. **在小皮里安装并启动 MySQL 8.0 服务**：启动后小皮面板显示服务为绿色（运行中）。
3. **用 Navicat 连接 MySQL**：主机 localhost、端口默认 3306、用户名 root、密码按安装时设定（讲义示例为 root）。连接成功意味着数据库服务就绪。
4. **创建名为 `diabetes` 的数据库**：字符集 utf8mb4（支持中文），排序规则对应 utf8mb4_general_ci 即可。

> 小贴士：utf8mb4 是必须的。MySQL 的老 utf8 字符集存不了 4 字节的 emoji，而本系统会存聊天记录（患者可能发 emoji），用 utf8mb4 才能放心。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| Navicat 连不上 localhost | ① MySQL 服务没启动（回小皮启动）② 端口被占用（检查 3306）③ 密码不对（确认安装时密码） |
| 建库时字符集选错 | 用 utf8mb4 而不是 utf8；否则中文正常但 emoji 报错 |

@@point ② 七张表全景：一张 ER 图看懂
@@need 要解决什么
设计数据库前先把"有哪些表、表与表什么关系"画出来，避免边写边加字段。

@@idea 核心思路
本项目所有表都挂在患者主表之下——**患者是 1，其余 6 张业务表都是 N**（一对多）：

```
                    ┌─────────────┐
                    │  patients   │ 患者主表（1）
                    └──────┬──────┘
        ┌─────────┬───────┼───────┬─────────┬─────────┐
        ▼         ▼       ▼       ▼         ▼         ▼
┌────────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌──────────┐ ┌────────────┐
│blood_sugar │ │diet_   │ │medi-   │ │exercise│ │health_   │ │chat_       │
│ 血糖记录    │ │records │ │cations │ │_records│ │reports   │ │history     │
│            │ │ 饮食记录│ │ 用药记录│ │ 运动记录│ │ 健康报告  │ │ 对话历史    │
└────────────┘ └────────┘ └────────┘ └────────┘ └──────────┘ └────────────┘
```

命名规律：**业务表都以复数命名**（records、cations、history），与 Tortoise 模型 Meta.table 一一对应。看清楚这个星型结构，后面十章写 CRUD 时"查哪个表、join 谁"都一目了然。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 建表名用了单数（blood_sugar_record） | 与讲义/代码的表名不一致，迁移和查询会对不上；以 `baizhan_` / 讲义 SQL 中的表名为准 |
| 忘了建外键 | 后面用 ORM 关联查询会报「字段不存在」；建表 SQL 必须带 FOREIGN KEY |

@@point ③ 患者主表 patients：字段设计
@@need 要解决什么
患者是系统的主实体，字段要覆盖"基本信息 + 糖尿病特诊信息 + 紧急联系 + 医疗史"，AI 生成个性化建议全靠它。

@@idea 核心思路
```sql
CREATE TABLE IF NOT EXISTS patients (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    age INT NOT NULL,
    gender VARCHAR(10) DEFAULT '未知',
    diabetes_type VARCHAR(20) DEFAULT '2型',
    diagnosis_date DATE,
    height FLOAT,
    weight FLOAT,
    phone VARCHAR(20),
    emergency_contact VARCHAR(50),
    emergency_phone VARCHAR(20),
    medical_history TEXT,
    allergies TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

设计要点：

| 字段 | 为什么这么设计 |
|---|---|
| diabetes_type 默认 '2型' | 1 型/2 型治疗逻辑完全不同，AI 回答要区分；默认 2 型最普遍 |
| height/weight 为 FLOAT | 后面要算 BMI（体重kg/身高m²），必须存数值 |
| diagnosis_date 可空 | 确诊时间不一定填，留空 |
| medical_history/allergies 为 TEXT | 病史、过敏史可能很长，用大文本 |
| created_at/updated_at | 审计字段，updated_at 用于"最近什么改过" |

这段 SQL 也是后面 Patient 模型的"翻译蓝本"——**字段名、类型、默认值必须与模型一致**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 体重身高存成 VARCHAR | BMI 算不了或类型报错；数值必须 FLOAT |
| 没设默认值，建患者报 NOT NULL 错误 | gender / diabetes_type / created_at 等字段要么给 DEFAULT 要么设为可空 |

@@point ④ 血糖记录表 blood_sugar：核心指标表
@@need 要解决什么
血糖是整个系统的"心跳数据"，趋势分析、健康报告、AI 风险评估都以它为准。表设计必须支持这些分析。

@@idea 核心思路
```sql
CREATE TABLE IF NOT EXISTS blood_sugar (
    id INT AUTO_INCREMENT PRIMARY KEY,
    patient_id INT NOT NULL,
    value FLOAT NOT NULL,
    measure_type VARCHAR(20) NOT NULL,
    measured_at DATETIME NOT NULL,
    note TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (patient_id) REFERENCES patients(id) ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

| 字段 | 为什么这么设计 |
|---|---|
| value FLOAT | 血糖值，单位 mmol/L（如 5.6、9.2） |
| measure_type VARCHAR(20) | 测量类型：空腹 / 餐后2h / 睡前 / 随机，用于区分场景 |
| measured_at DATETIME | 测量时间——趋势分析、按天数统计全靠它 |
| FOREIGN KEY ... ON DELETE RESTRICT | 患者被删时，若还有血糖记录则**禁止删除**——保护医疗数据 |

> 约束语义：`ON DELETE RESTRICT` 表示"父记录有子记录时不让删父记录"；`ON UPDATE CASCADE` 表示"父记录 id 变了，子记录自动跟着变"。医疗场景用 RESTRICT 很合适——别让一条血糖记录突然失去主人。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 外键建不上，报 errno 150 | ① patients 表不存在 ② 类型不一致（patients.id 是 INT，血糖表 patient_id 也要 INT）③ 引擎/字符集不一致（都 InnoDB + utf8mb4） |
| 血糖值存成 INT | INT 存不了 5.6 这种小数；FLOAT |

@@point ⑤ 饮食记录表 diet_records：营养五要素
@@need 要解决什么
智能饮食管理要推荐食谱、算碳水、查 GI，所以每顿饭要记**营养五要素 + 餐次 + 时间**。

@@idea 核心思路
```sql
CREATE TABLE IF NOT EXISTS diet_records (
    id INT AUTO_INCREMENT PRIMARY KEY,
    patient_id INT NOT NULL,
    food_name VARCHAR(100) NOT NULL,
    calories FLOAT,
    carbs FLOAT,
    protein FLOAT,
    fat FLOAT,
    gi_value FLOAT,
    portion FLOAT DEFAULT 1.0,
    meal_type VARCHAR(20),
    eaten_at DATETIME NOT NULL,
    note TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (patient_id) REFERENCES patients(id) ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

| 字段 | 为什么这么设计 |
|---|---|
| calories / carbs / protein / fat | 热量、碳水、蛋白质、脂肪——每日营养统计就靠聚合这四列 |
| gi_value FLOAT | 升糖指数（Glycemic Index）：低 GI≤55、中 GI≤70、高 GI>70，AI 推荐食谱的排序依据 |
| portion FLOAT DEFAULT 1.0 | 份数/重量系数，同一食物吃 2 份时营养翻倍 |
| meal_type | 餐次：早餐/午餐/晚餐/加餐——食谱推荐按餐次筛选 |
| eaten_at | 进食时间——"当日营养统计"按 eaten_at 落在哪天来过滤 |

有了这张表，DietAdvisor 就能回答"你今天碳水超标了""你早餐应该换成低 GI 食物"。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 营养量没乘 portion | 吃 2 份却按 1 份统计，营养结果偏小；统计时记得乘 portion（或前端录入时就乘好） |
| gi_value 为 NULL 也被算平均 GI | mean 会跳过 None，但如果数据全是 None 就没法算；注意空值兜底 |

@@point ⑥ 用药记录表 medications：安全余量设计
@@need 要解决什么
用药管理要记录药名、剂量、频次、起止时间、是否在服、副作用——AI 才能提醒"别漏药、别重复用药"。

@@idea 核心思路
```sql
CREATE TABLE IF NOT EXISTS medications (
    id INT AUTO_INCREMENT PRIMARY KEY,
    patient_id INT NOT NULL,
    drug_name VARCHAR(100) NOT NULL,
    drug_type VARCHAR(50),
    dosage VARCHAR(50) NOT NULL,
    frequency VARCHAR(50),
    timing TEXT,
    start_date DATE NOT NULL,
    end_date DATE,
    is_active BOOLEAN DEFAULT 1,
    side_effects TEXT,
    note TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (patient_id) REFERENCES patients(id) ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

设计三要点：
- **dosage 用 VARCHAR 而不是数字**：因为剂量可能是"1片""0.5mg""睡前 12 单位"这种带单位的文本，数值化反而不灵活；
- **is_active BOOLEAN DEFAULT 1**：判断"现在是否还在吃"——停药的药不删（保留记录），只置 0，历史可追溯；
- **start_date 必填、end_date 可空**：正在吃的药没有停药日期，未来停用再填。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把 dosage 设计成 FLOAT | "12 单位胰岛素"这种带单位写法存不进去；VARCHAR 才是正确粒度 |
| 删掉停用的药 | 医疗记录要留痕；改 is_active=0 而不是 DELETE |

@@point ⑦ 运动记录表 exercise_records：前后血糖对比
@@need 要解决什么
"运动与血糖关系分析"要靠**运动前后的血糖差值**（bs_change），所以运动表必须留两个血糖字段。

@@idea 核心思路
```sql
CREATE TABLE IF NOT EXISTS exercise_records (
    id INT AUTO_INCREMENT PRIMARY KEY,
    patient_id INT NOT NULL,
    exercise_type VARCHAR(50) NOT NULL,
    duration_min INT NOT NULL,
    intensity VARCHAR(20) DEFAULT '中等',
    calories_burned FLOAT,
    performed_at DATETIME NOT NULL,
    blood_sugar_before FLOAT,
    blood_sugar_after FLOAT,
    note TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (patient_id) REFERENCES patients(id) ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

亮点：`blood_sugar_before` + `blood_sugar_after` 两列是**运动与血糖关系分析**的数据基础——ORM 层会用计算属性 bs_change = after - before，直观看到"跑了 30 分钟后血糖降了多少"，AI 就能评估运动方案是否有效。

其他字段注意点：intensity 默认 '中等'（低/中/高三档）；duration_min 是 INT（分钟）；calories_burned 是可空 FLOAT（烧了多少卡运动手环才知道）。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 漏掉 blood_sugar_before/after | 运动与血糖关联分析直接没了；建模时务必保留 |
| intensity 用中文存但忘记默认值 | 录入端没传时插入报错；DEFAULT '中等' 兜底 |

@@point ⑧ 报告表与对话表：health_reports + chat_history
@@need 要解决什么
最后两张表：健康报告（自动生成的周报/月报）和 AI 对话历史（RAG 问答上下文）。它们存储的是"系统生成物"而非"患者录入数据"。

@@idea 核心思路
```sql
-- 健康报告表
CREATE TABLE IF NOT EXISTS health_reports (
    id INT AUTO_INCREMENT PRIMARY KEY,
    patient_id INT NOT NULL,
    report_type VARCHAR(50) NOT NULL,
    period_start DATE NOT NULL,
    period_end DATE NOT NULL,
    avg_blood_sugar FLOAT,
    blood_sugar_std FLOAT,
    time_in_range FLOAT,
    summary TEXT NOT NULL,
    recommendations TEXT,
    risk_level VARCHAR(20) DEFAULT '低',
    generated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (patient_id) REFERENCES patients(id) ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 对话历史表
CREATE TABLE IF NOT EXISTS chat_history (
    id INT AUTO_INCREMENT PRIMARY KEY,
    patient_id INT NOT NULL,
    role VARCHAR(20) NOT NULL,
    content TEXT NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (patient_id) REFERENCES patients(id) ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

health_reports 的三个"AI 相关"字段：
- `avg_blood_sugar` / `blood_sugar_std` / `time_in_range`：统计引擎算出的数值指标；
- `summary`：人类可读的健康总结（统计引擎生成）；
- `recommendations`：LLM 生成的个性化建议；
- `risk_level`：低/中/高/极高——风险评估结果。

chat_history 要点：`role` 只有两个取值——`user`（患者）和 `assistant`（AI），一问一答成对落库；content 是 TEXT（对话可能长）。这张表让"AI 问诊有记忆"：下次回答可以带上历史。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| chat_history 存 role 用了其他值 | 后续 LLM 客户端按 role 判断 user/assistant 组装消息；非约定值会被跳过，回答丢历史 |
| report 表没存 period_start/end | 报告"哪段时间的数据"就无法追溯；两个日期都 NOT NULL |
