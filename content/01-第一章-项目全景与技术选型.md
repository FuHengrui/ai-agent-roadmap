```text
# 安康智慧健康管理平台 · 需求文档

## 一、要解决什么
糖尿病要天天管四件事：测血糖、管住嘴、按时吃药、坚持运动。
可现在这些记录散在纸质本子、不同 App 和脑子里：复诊时医生看不到全貌，通用建议「少吃多动」落不到自己身上，
复诊间隔几周，中间血糖飙了也没人管。这个项目要做的，是把这四类数据收进一套系统，再用 AI 把数据讲成人话。

## 二、给谁用
需要长期自我管理的糖尿病患者，以及帮他们看数据的家属。
典型场景：早上测完空腹血糖录一条；午饭前问「今天能吃什么」；周末生成一份周报，复诊时递给医生。

## 三、用户故事
1. 作为患者，我希望把每次血糖连同测量类型（空腹/餐后/随机）和时间记下来，这样趋势才算得出来。
2. 作为患者，我希望系统告诉我这条血糖算不算正常、近一周达标率多少、在升还是在降，这样我不用对着数字猜。
3. 作为患者，我希望记录三餐的热量、碳水和 GI，并让系统按我当前的血糖推荐今天吃什么。
4. 作为患者，我希望用药记录分得清「还在吃」和「已停药」，停掉的药历史也留着。
5. 作为患者，我希望运动前后各测一次血糖、系统算出降了多少，让我知道这个运动有没有用。
6. 作为患者，我希望一键生成周报/月报，里面有统计数字、AI 写的建议和风险等级。
7. 作为患者，我希望直接问「低血糖怎么办」，回答要引用医学指南，而不是模型自己编。

## 四、功能需求
### 4.1 患者档案
- 记姓名、年龄、性别、糖尿病类型、确诊日期、身高体重、紧急联系人、病史、过敏史。
- 身高体重用来算 BMI；BMI 和 BMI 分类是算出来的，不单独存。

### 4.2 血糖记录与统计
- 每次记录：血糖值、测量类型（空腹/餐后/随机）、测量时间、备注。
- 每条显示状态：低血糖 / 正常 / 偏高 / 高血糖；**正常上限按测量类型取不同值**，不能一套阈值套所有。
- 能查某患者最近 1~90 天的记录（最新在前），也能查这段区间的统计：平均值、最高最低、达标率、趋势（上升/下降/稳定）、风险等级（低/中/高）。

### 4.3 饮食记录与推荐
- 记录食物名、热量、碳水、蛋白质、脂肪、GI、份数、餐次、进食时间。
- 每条显示 GI 等级（低GI/中GI/高GI）；营养量按「一份」存，实际摄入乘份数。
- 能查某天的营养汇总：总热量、三大营养素、平均 GI，以及「偏低/适中/偏高」的评判。
- 能按餐次推荐食谱；**当前血糖偏高时只推低 GI 的几条，条数更少更聚焦**。

### 4.4 用药记录
- 记录药名、类型、剂量、频次、服用时间、起止日期、副作用。
- 能只看「正在吃的药」；停药的记录保留不删。

### 4.5 运动记录
- 记录运动类型、时长、强度、消耗热量、运动时间、运动前后血糖。
- 每条算出前后血糖差值，负值表示降糖。

### 4.6 健康报告
- 按周或按月生成：区间统计（平均血糖、标准差、达标率）+ 一段人话摘要 + 3~5 条建议 + 风险等级。
- 报告存的是生成那一刻的指标快照；之后新增记录不能改动历史报告。
- 能查某患者的历史报告，最新在前。

### 4.7 AI 问诊对话与医学知识库
- 患者发一句话，系统先判断问的是血糖、饮食、用药还是别的，再带上患者档案和近 7 天血糖概况去查医学知识，最后生成建议。
- 回复末尾附风险提示：高风险直接建议尽快就医；用户消息与 AI 回复都要落库，能按患者查历史对话。
- **风险等级必须由规则算出，不能让大模型自己判**。
- 知识库预置约 20 条糖尿病医学知识，覆盖血糖管理、低血糖、高血糖、血糖监测、饮食、运动、用药、并发症；每条带分类和来源，引用要标出来。

### 4.8 仪表盘
- 一页看到：血糖趋势图（带低血糖 / 目标上限 / 高血糖三条参考线）、健康评分、今日营养、今日用药。

## 五、非功能需求（同样是需求）
- **数字归规则、表述归模型**：统计、达标率、风险等级都由后端算好再交给 AI 组织语言，不让模型做算数。
- **口径只有一份**：模型里的状态判定和统计引擎的阈值必须同一套（按测量类型分档），不能一边说正常一边说偏高。
- **没数据别装**：查不到血糖数据就明确返回「数据不足」，不能拿 0 当正常、拿「低风险」当安全。
- **AI 挂了不拖垮页面**：模型调用失败返回一句友好提示，不把异常堆栈抛给用户。
- **不串号**：所有数据都挂在某个患者名下，查谁的数据由参数决定，不能串到别人的档案。
```


@@point ① 这个项目解决的真实痛点
@@need 要解决什么
先搞清楚"为什么要做这个系统"，后面的技术选型才有着落——技术是为痛点服务的。

@@idea 核心思路
糖尿病是典型的**数据密集型慢性病**：患者每天要监测血糖、记录三餐、按时用药、保持运动，但这些数据**散落在不同的 App、小本子和脑子里**。四大痛点：

| 痛点 | 具体表现 |
|---|---|
| 数据碎片化 | 血糖、饮食、用药、运动记录分散在不同 App 或纸质记录中，医生看不到全貌 |
| 缺乏个性化指导 | 通用建议（"少吃多动"）无法针对个人血糖波动规律给出精准方案 |
| 就医频次有限 | 复诊间隔数周或数月，中间的血糖异常难以及时干预 |
| 患者依从性差 | 缺乏持续的督促和反馈机制，坚持不下去 |

系统的解法：**AI Agent 技术整合多维数据 + RAG 挂载医学指南知识库 + LangGraph 编排多步 Agent 流程**，为每位患者生成个性化健康管理方案和实时咨询。

@@point ④ 技术亮点：这套系统"新"在哪
@@need 要解决什么
讲清楚 AI 健康助手与普通 CRUD 系统的分水岭，也是面试/答辩最值得讲的点。

@@idea 核心思路
四大技术亮点：

1. **LangGraph Agent 工作流**：把健康管理拆解为「症状分析 → 知识检索 → 方案生成 → 风险评估」多步节点，用**状态机**编排，每一步的输出都是下一步的输入，可观测、可干预。
2. **RAG 医学知识增强**：结合糖尿病医学指南、营养学知识库回答患者问题，**避免 LLM 幻觉**——模型不会凭空编造医学建议。
3. **个性化推荐**：基于患者历史血糖、饮食数据生成个性化饮食/运动/用药方案，不是通用模板。
4. **实时预警**：血糖异常自动触发预警通知（高/低血糖风险等级）。

价值点：**普通问答机器人是"一问一答"，这个系统是"问诊工作流"**——它先判断你问的是血糖还是饮食，再带上你的档案和数据去回答案。

│  exercise / health_report / chat              │
└───────┬──────────────────────────┬───────────┘
        │ Tortoise-ORM              │ 业务引擎
┌───────▼────────┐   ┌─────────────▼───────────┐
│   MySQL 8      │   │  AI 引擎层                │
│  7 张业务表     │   │  DietAdvisor（饮食推荐）   │
└────────────────┘   │  HealthAnalyzer（统计）    │
                     │  LLMClient（大模型封装）    │
                     │  RAGEngine（知识检索）      │

关键认知：**AI 不是散在各个路由里，而是集中在 core/ 层**，路由只负责收发 HTTP，业务逻辑全在引擎里——方便单独测试、单独替换模型。

目录按五层落地：入口 `main.py` / 配置 `config.py` / 数据 `models` + `schemas` / 接口 `routers` / 引擎 `app/core/`（五个引擎文件：`diet_advisor.py`、`health_analyzer.py`、`llm_client.py`、`rag_engine.py`、`langgraph_agent.py`）。

@@point ⑥ Agent 工作流：一图看懂问诊流程
@@need 要解决什么
系统的"大脑"是一套 LangGraph 工作流，必须先理解它的节点顺序，后面第十二章才能照着写。

@@idea 核心思路
Agent 工作流是一条流水线（Agent 工作流程图 / 时序图的文字化）：

```
用户消息
  │
  ▼
① classify（意图识别）→ 血糖 / 饮食 / 用药 / 其他
  │
  ▼
② load_context（患者档案）→ 姓名/年龄/BMI/病史 + 近7天血糖统计
  │
  ▼
③ retrieve（知识检索）→ 按意图去 ChromaDB 检索糖尿病医学知识
  │
  ▼
④ generate（方案生成）→ 患者档案 + 医学知识拼成 prompt，调 LLM 生成建议
  │
  ▼
⑤ assess_risk（风险评估）→ 根据血糖统计判断高风险/中风险，追加警告
  │
  ▼
最终回复 = AI 建议 + 风险警告
```

这套编排正是 LangGraph 的 StateGraph：**五个节点 + 一个共享状态对象（AgentState）**，串成有向图。现在只要有印象，第十二章会逐行实现。

@@trap 坑在哪
