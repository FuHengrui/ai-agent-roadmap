@@point ② vite.config.ts：代理解决跨域
@@need 要解决什么
前端 5173 直接请求后端 8000 是跨域，靠 proxy 把请求"看起来同源"转给后端——同时隐藏后端地址。

@@idea 核心思路
```ts
server: {
  port: 5173,
  proxy: {
    '/api': {
      target: 'http://127.0.0.1:8000',
      changeOrigin: true,
      rewrite: (path) => path.replace(/^\/api/, ''),   // 去掉 /api 前缀
    },
    '/login': {   // 登录接口直通
      target: 'http://127.0.0.1:8000',
      changeOrigin: true,
    },
  },
}
```

机制拆解（这是联调最容易懵的点）：
- 前端请求 `/api/v1/test/styles` → Vite dev server 收到 → **去掉 /api 前缀** → 转发给 `http://127.0.0.1:8000/v1/test/styles` → 后端路由正好匹配。
- 所以后端路由里**根本没有 /api 前缀**！- - rewrite 就是"前后端路径不一致的桥梁"。
- `/login` 单独配：登录页走 `/login`（未拼 /api），同样直通 8000。

⚠️ 联调必查：代理只在 **Vite dev server（开发模式）**生效；`yarn build` 后的静态文件没有代理，线上部署要用 Nginx 做同样的转发规则！

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 前端请求 404 但后端明明有这路由 | rewrite 没删 /api，后端看到 /api/v1/... 当然 404 |
| build 后接口全挂 | 生产环境没有 vite proxy；需 Nginx 配 location /api { proxy_pass http://127.0.0.1:8000; } 并同样去前缀 |
| 不配 proxy 直接 fetch 8000 | 跨域被 CORS 拦（第 5 章的 allow_origins 必须含 5173 才能直连） |

@@point ③ request.js：axios 实例与拦截器
@@need 要解决什么
几十个接口都要"带 token、统一解包、统一报错"——封装一个 axios 实例，业务代码最干净。

@@idea 核心思路
```js
const request = axios.create({ baseURL: '/api', timeout: 120000 })

// 请求拦截：自动带 token
request.interceptors.request.use(config => {
  const token = getCookie('accessToken')
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

// 响应拦截：统一解包
request.interceptors.response.use(
  res => {
    if (res.data.code === 200) return res.data.data   // 直接吐出 data
    return Promise.reject(new Error(res.data.message))
  },
  err => {
    const status = err.response?.status
    if (status === 401 || status === 403) {
      clearCookie('accessToken')
      window.location.href = '/login'   // 过期/无权限 → 登出
    }
    return Promise.reject(err)
  }
)
```

三件套的落地点：`baseURL: '/api'` —— 所有请求路径自动带 /api，配合 vite rewrite 直达后端；**业务代码永远写 `/v1/xxx`**，不带 /api 不带主机名。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| Authorization 头一直没带上 | 拦截器读的 cookie 名与登录写入的不一致（accessToken 拼写/大小写） |
| timeout 120000 仍超时 | AI 生成类接口耗时可能 >2 分钟（Coze 轮询+文生图），130s 内没回是"上游慢"而非前端问题，需给慢接口单独更长超时 |
| 401 后无限跳 /login 循环 | 登录接口本身返回 401（密码错）也会触发拦截器跳转；对 /v1/auth/login 请求路径加白名单判断 |

@@point ④ 登录页逻辑：调接口 → 存 token → 存用户
@@need 要解决什么
登录页是用户进入平台的第一关，也是"后端 JWT + 前端存储"的第一次握手。

@@idea 核心思路
```js
const onLogin = async () => {
  const res = await loginApi({ username, password })   // POST /v1/auth/login
  setCookie('accessToken', res.token, 7)               // 存 7 天，与后端 exp 一致
  userStore.setUser(res.user)                          // pinia 缓存用户信息
  router.push('/home')
}
```

要点：
- **token 存 cookie（7 天）与后端 exp=7 天对齐**——过期都过期，前端不用猜。
- 用户信息进 **Pinia**（内存态，刷新消失）——所以刷新后要从 token 或重新拉接口恢复身份。
- 密码错误（HTTP 401）→ 前端拦截器"清 token 跳登录"逻辑要**跳过当前页**，否则登录失败也被跳走（前端代码对 auth 接口做了豁免）。

@@point ⑤ 路由守卫：未登录拦截
@@need 要解决什么
用户直接敲 URL /home 访问受保护页怎么办？路由前置守卫统一把关。

@@idea 核心思路
```js
router.beforeEach((to) => {
  const token = getCookie('accessToken')
  if (to.path !== '/login' && !token) {
    return { path: '/login' }          // 未登录 → 踢回登录页
  }
  return true
})
```

守卫的职责只是"前端第一道门"（UX 层），**真正的安全还是后端鉴权**——前端守卫可以被绕过（改了 cookie 又怎样，后端 401/403 会兜底）。前端不做安全判断，只做体验判断。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 守卫写死"无 token 就跳登录"，内嵌到首页的 iframe 也跳 | 死循环或跳转目标错误；路由守卫要排除 /login 与静态资源路径 |
| 只靠前端守卫以为安全 | 守卫可绕过；安全底线在后端 Depends(get_current_user_id) |

@@point ⑥ 联调清单：登录 → 历史 → 素材全链路
@@need 要解决什么
前端各页面对应哪些后端接口？怎么一步步验证联调通过？一张对照表 + 验收步骤。

@@idea 核心思路
页面 ↔ 接口对照：

| 前端页面 | 后端接口 | 说明 |
|---|---|---|
| Login | POST /v1/auth/login | 拿 token |
| History | GET /v1/create/themes | 当前用户主题列表（DISTINCT） |
| Home 素材 | GET /v1/create/load?theme=xxx | 按主题加载全部板块/标题/文案 |
| CreatePublish | POST /v1/create/start | 提交主题开始生成 |
| CreatePublish | POST /v1/create/copy | 生成文案 |
| 详情/重试 | GET/POST /v1/create/title 相关 | 标题详情、重置、保存 |

验收顺序（联调必走）：
1. 登录成功，cookie 出现 accessToken；
2. 登录后访问 History 能看到自己生成的主题（空则显示空态）；
3. 发起一次 /start 生成（真实调 Coze，耗时约 1-3 分钟，前端 loading 要稳）；
4. 生成完成 → /load 回来 → 素材页出现板块与标题。

匹配口径：**接口全部带 /v1 前缀、路径与后端 include_router 的 prefix 拼接完全一致**——拼错一个字符就是 404。

@@point ⑦ 跨页面状态：Pinia 存什么、cookie 存什么
@@need 要解决什么
"登录状态"到底放哪？cookie vs Pinia 的边界是什么？刷新不丢的是什么？

@@idea 核心思路
| 载体 | 放什么 | 生命周期 |
|---|---|---|
| cookie（accessToken） | 登录令牌（唯一持久凭证） | 7 天，刷新不丢 |
| Pinia（userStore） | 当前用户信息（id/username） | 内存态，刷新即丢 |
| 后端数据库 | 真实业务数据（sections/titles/...） | 永久 |

设计铁律：**cookie 只放 token 这一个凭证**，其余状态尽量内存；刷新后 Pinia 丢失不影响业务——因为业务数据永远从后端拉。想"刷新保持登录"，靠的也只是 cookie 里 token 被拦截器继续带上。

@@summary 这一章你学到了什么
- 前端栈：Vue3 + Vite + Element Plus + Pinia + axios + puppeteer（发布用）
- vite proxy 跨域：/api → 8000 并 rewrite 去前缀；/login 直通；build 后需 Nginx 等价配置
- request.js 三件套：baseURL=/api、请求拦截带 Bearer、响应拦截按 code 解包 + 401/403 登出
- 登录链路：调接口 → setCookie(accessToken, 7) → pinia 存用户 → 跳 /home
- 路由守卫：前端 UX 门（未登录跳转），安全靠后端鉴权兜底
- 联调对照表：Login/History/Home/CreatePublish 对应接口路径必须与后端前缀严格一致
- 存储分工：cookie 只放 token（7 天），Pinia 存瞬时用户态，业务数据全走后端
- VITE_API_BASE：路径前缀可配置，密钥永不进 VITE_ 变量；改环境变量需重启

@@point ⑧ 前端环境变量：VITE_API_BASE 与请求根路径
@@need 要解决什么
baseURL 写死 '/api' 会带来一个部署难题：开发用 /api 走代理，生产可能用不同前缀/域名。环境变量把它变成可配置项。

@@idea 核心思路
项目在根目录提供 `.env` / `.env.development`（Vite 约定），定义：
```ini
VITE_API_BASE=/api
```
axios 创建时读取：
```js
const request = axios.create({
  baseURL: import.meta.env.VITE_API_BASE || '/api',
  timeout: 120000
})
```
- **import.meta.env** 是 Vite 暴露环境变量的唯一方式（VUE_APP_ 是 Vue CLI 时代的，别混用）；
- 改环境变量要**重启 dev server** 才生效；
- 生产构建时（`yarn build`）VITE_ 开头的变量会被静态替换进产物——所以**不要把任何密钥放 VITE_ 变量**（会进浏览器）。

边界认知：VITE_API_BASE 只是"路径前缀可配置"，真正解决跨域的还是 dev proxy（开发）与 Nginx（生产）两层转发，两者配合才完整。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| import.meta.env 拿到的都是 undefined | 变量没以 VITE_ 开头；或改完没重启 dev server |
| build 后 .env 里的密钥泄露在页面里 | VITE_ 变量会打包进前端产物——密钥必须只放后端 .env |
| Vue CLI 老项目照抄 VUE_APP_ 写法 | 框架不同命名不同，Vite 一律 VITE_ 前缀 |
