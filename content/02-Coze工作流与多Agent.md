@@h1 第二章　Coze 工作流、对话流与多 Agent
@@sub 阶段 4 · 低代码 Agent 平台实战　|　平台实操　|　难度 ★★★

@@why 这一章在解决什么问题
第一章你搭出来的 Bot 很强，但它有个**天花板**：它是一步步"对话"的。

想象一个需求："帮我把历史人物**诸葛亮**的生平做成一条完整视频，要有文案、配音、字幕、背景音乐。"——如果让 Bot 在对话里硬干，它会：先生成文案、再让用户等、再生成图片……用户得在旁边一直陪着，中间任何一步断了整条就废了。

**单轮对话撑不起多步骤、批量、有依赖关系的复杂任务。**

Coze 给出了三段式升级路线：

- **工作流（Workflow）**：把多步骤任务编排成固定流水线，自动执行、自动批量；
- **对话流（Chatflow）**：为"边聊边办"的场景做精细化流程控制；
- **多 Agent 模式**：一个用户请求，分给多个"专家 Agent"协作处理，最后汇总。

这一章解决的就是：**怎么把 Bot 从"单兵作战"升级成"多兵种协同的流水线团队"。**

@@goal 学到这儿就够了
能说清工作流补了 Bot 什么短板、对话流和普通 Bot 差在哪、什么时候该挂多 Agent，这章就算过了。

@@point ① 工作流：把"临场发挥"变成"固定流程"
@@need 要解决什么
如果你要的不只是聊天，而是**一条固定的业务流水线**（生成视频、批量处理、数据转换），让模型在对话里"临场发挥"太不可靠了：

- 步骤容易漏（生成了文案忘了配图）；
- 不能批量（一张张让用户等，早就烦了）；
- 不能重试（某一步失败，整段推倒重来）；
- 过程不可控（模型自由发挥，输出格式不稳定）。

这些都是"单轮对话"模式的先天短板。

@@idea 核心思路
**工作流（Workflow）**就是把任务拆成节点、按顺序连成线，让 Bot 像工厂流水线一样自动执行。

它解决的正是上面四个痛点：

- **固化流程**：每个节点做什么、用什么参数，提前画好；
- **批量处理**：批处理节点一次喂入数组，逐条执行；
- **条件控制**：分支节点根据条件走不同路径；
- **重跑与调试**：单节点可测、可一键重跑，不必全盘推倒。

Coze 的节点类型够覆盖绝大多数场景：

| 节点类型 | 干什么用 | 一句话记法 |
|---|---|---|
| **LLM 节点** | 调用大模型做文本生成/意图识别（可写系统提示词） | "写、读、判断的都找它" |
| **批处理节点** | 对传入的数组逐条处理 | "循环干活" |
| **代码节点** | 写 Python 做数据类型转换、逻辑计算 | "搬数据、做算术" |
| **插件节点** | 调用平台插件（生图、搜索、AI 生视频……） | "调外部能力" |
| **问题节点** | 工作流中途向用户提问，收集输入 | "等用户回答" |
| **分支节点（条件判断）** | 根据条件走不同分支 | "分岔路口" |
| **多 Agent 节点** | 启动 Agent 处理子任务 | "分活给专家" |

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 把工作流和普通 Bot 混着用 | 先想清楚：是多步骤固定任务就走工作流，是开放对话就人设+知识库 |
| 节点太多、线画得乱 | 只把"必须有顺序、有依赖"的步骤画成工作流，能并行的就并行 |
| 上来就想把整个 Bot 塞进工作流 | 工作流是"干一件确定的事"的工具，不是整个 Bot 的替代品 |

@@point ② 历史人物视频实战：先拆需求，再画流程
@@need 要解决什么
从"我会用工作流节点"到"我能做出一条视频"之间，横着一个最常见的错误：**不拆需求就开拖**。

用户说"做一条诸葛亮生平视频"，如果直接去画节点，你根本不知道该画什么节点、每个节点喂什么参数。

@@idea 核心思路
任何复杂任务，**第一步永远是拆解**。把"生成历史人物生平视频"拆成一条明确的流水线：

1. **生成文案**：LLM 根据人物名生成生平故事文案；
2. **生成图片提示词**：LLM 把文案拆成画面描述（一次多个）；
3. **批量生成图片**：批处理 + 文生图插件，一次出多张；
4. **生成视频提示词**：LLM 为每张图生成动态描述；
5. **批量生成视频**：AI 文生视频，图转视频；
6. **提取视频 URL**：从返回结果里取出可下载的地址数组；
7. **配音**：文本转语音，生成旁白音频；
8. **加字幕**：自动给视频配字幕；
9. **拼接**：多段视频拼成完整一条；
10. **加背景音乐**：配上 BGM 收尾；
11. **输出结果**：结束节点交给用户。

画出来就是一条从"输入人物名"到"输出成品视频"的单向流水线。**需求拆得越细，节点画得越准**——每个小步骤对应 1~2 个节点，工作流自然成型。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 直接开拖节点，画到一半发现漏了步骤 | 没先拆需求，边画边想 |
| 步骤画太粗（一个"生成视频"节点搞定一切） | 一个节点只干一件事，干不了的拆开 |
| 拆完又堆回单 LLM 节点 | 把拆好的步骤合并，等于白拆 |

@@point ③ 文案节点：LLM 把名字变成故事
@@need 要解决什么
流水线第一步：用户只输入"诸葛亮"三个字，但后面所有环节（配图、配音、字幕）都要基于**一条完整、连贯、有画面感的生平文案**。谁来完成从名字到文案的转换？

@@idea 核心思路
用 **LLM 节点**，写一个"生成历史人物生平故事文案"的提示词：

```text
你是专业的历史科普文案创作者。
用户输入：{历史人物名}
请生成 500 字左右的生平故事文案：
1. 开头引出人物时代背景与简介
2. 选取 3-5 个关键生平事迹，按时间顺序讲述
3. 结尾总结人物历史贡献
要求：语言生动、有画面感、适合配音。
```

关键点在于：**每次生成的故事要相对可控**——因为后面还会复用这段文案生成图片、配音。所以提示词里明确"结构固定、字数区间、适合配音"，而不是让模型放飞。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 文案太长，配音/字幕被迫截断 | 设定字数上限，配音按文案长度裁剪 |
| 文案结构每次都不一样 | 固定"开头-事迹-结尾"三段式，输出可预期 |
| 文案口语化差、像百科词条 | 提示词里明确"要生动、有画面感、适合配音口播" |

@@point ④ 批量生图：一组提示词配一组图片
@@need 要解决什么
文案是**一整段话**，但做视频配图需要**多张风格一致的画面**（每段故事一张）。总不能手工把文案拆成 5 段再让用户排队等 5 次生图。

需求是：**自动拆文案 → 一次生成 N 张配图。**

@@idea 核心思路
用两个节点接力：

1. **LLM 节点（生成图片提示词）**：把文案拆成多段，每段生成一句"古风插画风、电影感构图"的图片提示词，输出为**数组**；
2. **批处理节点 + 文生图插件**：数组每进来一项，就自动触发一次生图，结果仍是数组（一张图对应一段文案）。

关键在于**批处理节点**：给它喂一个数组，它会逐条执行内部逻辑，输出还是数组——这就是"批量"的真相：循环处理，而不是手写循环。

对提示词质量的要求值得记住：图片提示词要写明**风格（古风插画/写实/水墨）、内容主体、画面要素、色调**，这样批量出的图才风格统一。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 生成的图风格五花八门 | 图片提示词没统一风格前缀，每段自由发挥 |
| 批处理只跑了一条 | 输入没传成数组，或输出没配置数组类型 |
| 图数和文案段数对不上 | LLM 拆分结果不稳定，要在提示词里固定段数 |

@@point ⑤ 批量视频：图片动起来，还要"安全化"
@@need 要解决什么
图片有了，但视频平台对**历史人物的生成内容有安全要求**——空手生成历史名人视频，很容易触犯平台的"不得歪曲历史真实人物形象"类规则，轻则生成失败，重则账号受限。

同时：5 张图对应 5 条视频，又要**一条条手动等**吗？

@@idea 核心思路
两步走：

1. **LLM 节点做"提示词安全化"**：把图片提示词改写成安全的动态视频提示词。方法是"移除 → 弱化 → 重构"三步：

   - **移除**：去掉涉及真实历史人物身份/真实事件的描述；
   - **弱化**：把"再现某历史人物生平"降级为"古风人物场景"；
   - **重构**：用"山水、园林、书生遥望"等画面性语言重述，保留氛围不保留人物实名。

2. **批处理 + AI 文生视频插件**：把安全化后的提示词数组逐条生成视频，结果仍是数组。

这一步也提示了做低代码应用的心态：**平台能力（文生视频）+ 提示词工程（安全化）= 能用的效果。**卡住你的往往不是工具，而是如何组织输入。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 视频生成失败/被拒 | 提示词含真实人物名与真实事迹，未做安全化 |
| 视频内容与图片不匹配 | 视频提示词没参考图片信息（插件支持输入图时务必传入） |
| 只生成了一条 | 批处理输入输出的数组类型配置不对 |

@@point ⑥ 提取 URL：插件返回的是"对象"，我们要的是"地址"
@@need 要解决什么
文生视频插件返回的结果是一个**对象/数组嵌套结构**（每条不含下载地址，而是含 URL 的复杂对象）。但下一步拼接视频时，需要的是**纯 URL 字符串数组**。

类型对不上，流水线就断了。这是数据工程问题——**格式转换**。

@@idea 核心思路
两类节点搞定：

- **插件节点（如"米核 AI 剪映小助手"）**：调用 `get_url` 之类的工具，从视频对象里把可访问的 URL 提取出来；
- **代码节点**：写 Python 做最终的类型统一——比如示例里的 `objs_to_str_list`，把对象数组转成字符串数组：

```python
def main(params):
    results = params.get("results", [])
    # 将每项提取为 str 类型的 URL
    urls = [str(r["url"]) for r in results if r.get("url")]
    # 规范传输，避免可空类型问题
    return {"results": urls if urls else [""]}   # 注意别写成 [urls]，那会变成嵌套数组
```

> 小结一下：**LLM 管"内容生成"，插件管"能力调用"，代码节点管"数据类型与格式"。** 三者分工，别混着用。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 下游节点拿到的是 {} 而不是 URL | 没做字段提取，把整个对象传下去了 |
| 代码节点报类型错误 | 输入字段名和插件返回字段名对不上，先看插件返回结构 |
| 空数组导致下游报错 | 返回前做空值兜底（如 [""]），别让空数组穿透 |

@@point ⑦ 配音与字幕：让成品"能听能看"
@@need 要解决什么
视频画面齐了，但**没有旁白和字幕**——用户看一条默片，体验大打折扣。要求是：把文案转成语音，并给视频加上跟随文案的字幕。

@@idea 核心思路
两个插件节点接力：

1. **语音合成**（如"语音合成"功能）：输入文案 + 选择音色，输出**音频文件 URL**；
2. **视频处理插件**：
   - **VideoRemux**：转格式/分流处理；
   - **VideoAutoText**（自动添加字幕）：把文案/语音转文字后烧录成字幕，输入视频 URL + 文案，输出带字幕的视频。

这条链路的本质是**"文本 → 音频 → 烧录"三步**：文案既用于配音，又用于字幕，两条产线共用同一份文案数据。这种"一份数据多处复用"正是工作流的优势——**数据在节点间流动，而不是人手工搬运**。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 每条视频都要单独处理，慢 | 配音/字幕可批量：把 URL 数组喂给批处理 |
| 字幕时间轴对不上画面 | 输入的是"文案全文"而非逐句时序文本时，字幕工具会按语音自动对齐 |
| 音色选错，旁白像朗读 | 选叙事/解说类音色，别选客服/新闻腔 |

@@point ⑧ 拼接与背景音乐：流水线最后一公里
@@need 要解决什么
所有素材都齐了：N 段带字幕的视频 + 1 份旁白音轨 + 1 段背景音乐。**注意：旁白要先和分段视频合并（video_audio_merge），再整体拼接**——漏了这步，成片会只有 BGM 没人声。最后要把它们合成**一条完整成片**——手工剪辑是不可能的。

@@idea 核心思路
收尾四个节点：

1. **代码节点**：把"多段视频 URL"转成标准数组（和讲解 ⑥ 同一套路，`objs_to_str_list` 复用）；
2. **VideoConcat 插件**：按顺序把多段视频**拼接**成一条（顺序 = 数组顺序，所以文案顺序在源头就不能乱）；
3. **合并背景音乐**：
   - 背景音乐文件先上传到临时文件站（用 tmpfiles 这类服务拿到公网 URL）；
   - **video_audio_merge** 把视频与音乐合成；
   - 也可以直接插入"音乐/音效"媒体资源作为节点；
4. **结束节点**：把最终视频 URL 作为工作流输出，交给 Bot 回复给用户。

至此，**"诸葛亮生平视频"工作流完整跑通**：人物名 → 完整成片 URL。整套流程零手工、可批量、可重试——这是对话式 Bot 做不到的。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 拼接顺序乱了 | 数组顺序不可靠，源头拆分文案时就要保证顺序 |
| BGM 盖过旁白 | 合并参数里调音量平衡，先听再调 |
| 结束节点返回的是整个对象 | 结束节点只保留最终 URL 字段，输出格式要精简 |

@@point ⑨ 把工作流接入智能体：让用户觉得"在和 Bot 聊天"
@@need 要解决什么
工作流本身是**被动执行器**——用户没法直接"跟工作流说话"，只能在对话里等它跑完。而用户的心智是：**我在跟一个会做视频的助手聊天。**

要解决的问题：**怎么让"调用工作流"成为 Bot 的一种普通能力？**

@@idea 核心思路
三步接好：

1. **发布工作流**：在工作流右上角"发布"，打开"在工作流中的聊天中生效/可被 Bot 引用"；
2. **在 Bot 对话里引用**：Bot 添加该工作流作为能力（类似插件），并给它配置一个**库块触发描述**（LibraryBlock）——告诉模型"什么时候该调它、输入是什么、输出是什么"；
3. **在 Bot 人设中约束调用规则**：

```text
# 视频生成
当用户需要生成历史人物生平视频时：
1. 调用「历史人物视频工作流」，参数为人物名
2. 称呼用户、解释流程、"正在为您生成，大约需要几分钟"
3. 工作流返回视频链接后，将链接直接发给用户
```

这样用户打出"做个诸葛亮的视频"，Bot 自动识别意图 → 调工作流 → 等待 → 把成品链接发回来。**对话是外壳，工作流是内核。**

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| Bot 不主动调工作流 | 人设里没写触发条件，或库块描述写得含糊 |
| 调用了但参数没填 | 库块描述里要写清"参数=人物名，从用户对话中提取" |
| 工作流跑 3 分钟用户以为卡死 | 人设里安排"正在生成"的过程话术，并提前说明耗时 |

@@point ⑩ 对话流：边聊边办事的"流程大脑"
@@need 要解决什么
工作流适合"执行型"任务。但另一类场景它管不了：**智能助教**——学生问"Git 怎么撤销提交？"。

- 回答要**先判断**这个问题的意图（是命令类、概念类还是闲聊？）；
- 回答要**检索知识库**（不能空答）；
- 检索成功和失败要**走不同路径**（失败要引导转人工/换个问法）。

这些"边对话边决策"的逻辑，用普通 Bot 的提示词写不清，用固定工作流又太死。

@@idea 核心思路
**对话流（Chatflow）** = 面向对话场景定制的流程图：节点 + 判断 + 分支，但每一轮都可以"暂停、追问、再继续"。

对比一下三种形态：

| 形态 | 特点 | 适用 |
|---|---|---|
| 普通 Bot | 全自动，对话即答案 | 简单问答 |
| 工作流 | 固定流水线，无对话 | 多步骤执行任务 |
| **对话流** | 流程可分支、可追问，边聊边走 | 智能助教、多轮业务办理 |

核心差异一句话：**工作流是"跑一段程序"，对话流是"开一场有流程的对话"。**

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 对话流画成固定工作流 | 忘了加"意图识别 + 分支"，流程就死板了 |
| 每个分支都用 LLM 节点重写答案 | 复用同一个 LLM 节点，用不同条件输入区分 |
| 分不清对话流 vs 工作流 | 看**是否要按用户回答走多轮分支**：对话流适合可追问、分支多的场景；工作流是固定流程，虽然也能用「问题节点」中途收一次输入，但走不了多轮追问 |

@@point ⑪ 智能助教案例：意图识别 + 知识库双分支
@@need 要解决什么
给一个"智能助教"画对话流：学生随便提问，助教要**判断问题类型、按需检索知识库、失败时体面兜底**。这需要"先看到内容，再决定走哪条路"的能力——固定 Bot 做不到。

@@idea 核心思路
这里画一条主干：

1. **意图识别节点**：LLM 判断用户问题属于哪类——编程技术问题 / 课程内容咨询 / 闲聊 / 其他；
2. **分支/选择器**：按意图分流（如技术问题走"知识库检索"支路，闲聊直接回复）；
3. **知识库检索节点**：在课程知识库（**Agent常见问答.xlsx** 这类表格转成的知识库）中检索答案；
4. **RAG 判断节点**：检索结果与问题相关吗？
   - **成功分支**：LLM 基于检索内容组织回答；
   - **失败分支**：礼貌说明"我暂时没找到相关内容"，并引导用户换一种问法或转人工；
5. **结束节点**：输出最终回答。

这条流程有一个关键细节：**右侧分支形成的"半成品"（比如直接复述检索结果），不代表可以交付**——判断节点之后的两条路必须各自完整成文，别让用户看到半成品。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 意图识别分错类 | 提示词里给足意图类别定义 + 示例，别让模型自由发挥 |
| 知识库检索结果很烂还硬答 | RAG 判断节点没兜底，失败分支要"换问法/转人工" |
| 失败分支直接报错 | 失败也要说人话：引导 + 建议，别暴露技术错误 |

@@point ⑫ 多 Agent：一个 Bot 背后多个"专家"
@@need 要解决什么
"智能小助手"要同时扮演几个角色：**分配任务的调度员、催作业的班主任、答疑的助教、处理投诉的客服**。这些角色**知识不同（班主任管作业表、助教管知识库）、语气不同（班主任严厉、客服温和）、职责不同**——硬塞进一个 Bot 的人设，会互相干扰（班主任用客服口吻催作业就很怪）。

@@idea 核心思路
**多 Agent 模式**：把不同职责拆成独立 Agent，用一个"主 Agent"（分发任务 Agent）统一入口、按需求分发给对应专家，最后汇总返回。

拿智能小助手举例：

- **分发任务 Agent（总入口）**：识别用户请求属于哪类 → 发给对应 Agent；
- **班主任 Agent**：管作业提交/催缴/班级通知（可带专属人设"严格班主任口吻"）；
- **助教 Agent**：管技术答疑（接知识库）；
- **投诉专员 Agent**：管投诉建议（接到后**写数据表**留档，再回复用户）。

多 Agent 的核心价值：**每个 Agent 可以有自己独立的人设、知识库、工具、记忆**，互不污染；主 Agent 负责"把任务交给对的人"。就像公司分工：前台接单，各部门干活。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 所有活还堆在主 Agent 身上 | 主 Agent 只做"分发"，具体干活的必须下放到子 Agent |
| 子 Agent 回答风格混了 | 各子 Agent 独立设人设，别共用 |
| Agent 太多、互相套娃 | 2-4 个职责清晰的子 Agent 最稳，多了难调 |

@@point ⑬ 全局跳转条件：多 Agent 的"回家通道"
@@need 要解决什么
多 Agent 组队后有个新问题：学生被分发到"投诉专员"，投诉完**就出不来了**——接下来想问"下节课作业"，还是投诉专员在回（它不懂作业）。**子 Agent 之间互相"串门"、没有统一出口，整个体验就乱了。**

@@idea 核心思路
用**全局跳转条件（Global Jump Conditions）**给多 Agent 设置"回家通道"：

- 定义**全局条件**（如"学生询问课程/作业相关 → 跳回分发任务 Agent"）；
- 每个子 Agent 回答后都会**先检查全局条件**，命中就自动跳转到总入口，而不是留在当前 Agent 里继续硬聊；
- 这样多 Agent 团队就有了"**统一入口 + 统一出口**"，对话永远不会困在某个子 Agent 里。

配套操作：投诉专员接到投诉，把内容**写入数据表**（投诉记录表：学号、内容、时间、处理状态）——既留档，也让跳转后主 Agent 知道"这位同学反映过什么"。

一句话总结：**多 Agent 解决"谁来干活"，全局跳转解决"怎么回来"——两者缺一不可。**

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 子 Agent 答完就"失联" | 没配全局跳转，用户被卡死在子 Agent |
| 跳转条件写得太宽泛 | 条件会影响所有 Agent，写清楚触发边界 |
| 投诉没留档 | 建立数据表写入规则：字段、时机都要在提示词里定死 |

@@point ⑭ Coze 应用开发：从"聊天"到"带界面的 Web 应用"
@@need 要解决什么
到目前为止，用户都是**"打字聊"**。但很多需求是**表单驱动的**：比如"智能投资顾问"——用户要填一堆选项（资金量、风险偏好、投资周期），填完点个按钮，出推荐方案。

让用户在聊天框里打字填表？体验太差。**需要一个真正的界面。**

@@idea 核心思路
Coze 的**应用（App）**就是为此设计的：带 UI 的 AI 应用，可以搭建页面、写数据表、绑事件。智能投资顾问案例的四个组件：

1. **界面搭建**：页面放表单组件（客户基本信息、资金量、风险偏好、投资周期下拉等）+ 结果展示区；
2. **数据表**：创建业务数据表（客户信息表/产品推荐表），表单提交时写入；
3. **工作流输出产品推荐**：后端接一个"产品推荐"工作流（基于 XYZ 公司证券产品知识库与客户画像，输出推荐基金产品）——注意知识库素材（`XYZ公司证券产品介绍.md`）就是这类场景的输入；
4. **按钮事件绑定**：点"提交/生成推荐"按钮 → 触发工作流 → 结果填入界面。

这套组合拳的意义：**Coze 已经不只是在做聊天机器人，而是在做完整的 AI Web 应用**——前端界面、后端工作流、数据存储都由一个平台托管。这也是"低代码 Agent 平台实战"这一板块的落脚点。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 界面表单和工作流参数对不上 | 表单字段名要与工作流入参名保持一致 |
| 按钮点了没反应 | 事件绑定没配工作流，或工作流未发布 |
| 数据表当"界面变量"用 | 数据表是持久化存储，界面+工作流是计算，分层设计 |

@@point ⑮ 发布智能体：把 Bot 送到用户手里
@@need 要解决什么
Bot 做完了，它还在**开发环境里自嗨**——用户怎么用？

发布要回答：**发布到哪些渠道、以什么形式呈现在用户面前。**

@@idea 核心思路
Coze 的发布能力把"成品 Bot"分发到常用平台：

- **豆包 / Coze 商店**：官方渠道，一键上架（走审核）；
- **微信 / 抖音 / 头条 /QQ**：以小程序或服务号形态嵌入（需各平台配置）；
- **网页/API / SDK**：嵌入自家网站或 App（企业常用）；
- **团队共享**：发布到团队空间，成员直接使用。

发布前 checklist：

1. 人设、知识库、工作流、插件**全部经过测试**（先在自己里反复触发每个能力）；
2. 发布设置里选择**渠道**与**功能开放范围**；
3. 导出**发布记录**与**调试日志**——上线后监控用户实际触发情况，迭代优化。

至此板块闭环：**用低代码平台，把一个想法从"人设配置"一路带到"线上可用"。**

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 上线后 Bot 表现和本地测试不一致 | 发布版本与最新版本没对齐，发布前检查"用哪个版本上线" |
| 审核不通过 | 人设里含违规内容（敏感话题、夸大宣传），先自查 |
| 发布后没有监控 | 用数据模块看用户问题分布，反哺知识库补充 |

@@summary
这一章把 Bot 从"单兵"升级成了"军团"：

- **工作流**：把多步骤任务变成固定流水线（文案 → 成片），支持批量、重试、条件分支；节点 = LLM/批处理/代码/插件/问题/分支/多 Agent；
- **实战一条龙**：拆需求 → 文案 → 图片 → 视频（记得安全化提示词）→ 提 URL → 配音字幕 → 拼接加 BGM → 结束输出；
- **接回对话**：发布 → 库块描述 → 人设约束调用规则，让 Bot 变成"会调工作流的助手"；
- **对话流**：面向"边聊边决策"的场景，意图识别 + 知识库检索 + 成功/失败分支；
- **多 Agent**：各司其职的子 Agent + 分发总入口 + 全局跳转条件，组成"前台接单、后台分工"的团队；
- **应用与发布**：用界面 + 数据表 + 工作流搭 Web 应用，再发布到豆包/微信/网页等渠道。

到这一章为止，"低代码 Agent 平台实战"全部完成：**你能从零把一个 AI 想法，配置成一个可用的应用。**
