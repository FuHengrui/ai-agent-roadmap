@@point ① 血糖记录模型与 Schema
@@need 要解决什么
血糖记录长什么样？创建血糖记录时前端要传什么？

@@idea 核心思路
模型核心字段（第四章定义）：
- `patient`（外键）→ 这条血糖属于谁；
- `value`（Float）→ 血糖值 mmol/L；
- `measure_type`（CharField）→ 测量类型（空腹/餐后/随机）；
- `measured_at`（DatetimeField）→ 测量时间（不是录入时间！）。

Schema 三件套：Create 比患者版多带 `patient_id`，因为"创建记录必须指明属于哪个患者"：

```python
class BloodSugarBase(BaseModel):
    value: float
    measure_type: str
    measured_at: datetime
    note: Optional[str] = None

class BloodSugarCreate(BloodSugarBase):
    patient_id: int          # 患者版没有，这里必须有

class BloodSugarResponse(BloodSugarBase):
    id: int
    patient_id: int
    status: Optional[str] = None   # 计算属性，从模型 property 来
    created_at: datetime
```

注意字段分工：请求只需要 `patient_id`（外键的 ID 值），响应把 `patient_id` 回显并加上 `status`。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 创建血糖记录时装外键对象 | 请求里传 patient_id 数字即可；ORM 层自动完成关联，不要传嵌套对象 |
| status 在响应里为 null | Response Schema 没声明 status 字段或 from_attributes 没配 |

@@point ② 创建记录：先验患者再写入
@@need 要解决什么
不能让一条血糖记录挂在不存在的患者上——创建前怎么防御？

@@idea 核心思路
```python
@router.post("/", response_model=BloodSugarResponse)
async def create_record(data: BloodSugarCreate):
    patient = await Patient.get_or_none(id=data.patient_id)
    if not patient:                                  # ① 拿返回值判断，别只调用不接
        raise HTTPException(status_code=404, detail="患者不存在")
    record = await BloodSugar.create(**data.model_dump())  # ② 创建记录
    return BloodSugarResponse(
        id=record.id, patient_id=record.patient_id,
        value=record.value, measure_type=record.measure_type,
        measured_at=record.measured_at, note=record.note,
        status=record.status, created_at=record.created_at
    )
```

关键差异：患者模块直接 `Patient.create(...)`，血糖模块**先 query 一次患者**。虽然 `Patient.get_or_none` 的返回值没用，但这个"存在性检查"是数据完整性的第一道闸。

返回时**手动构造** BloodSugarResponse 而不是直接传 ORM 对象——虽然 from_attributes 也能转，但这里显式列出字段，把 `status`（计算属性）也带上了。显式构造在字段多时更直观。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 患者不存在也创建成功 | 忘了存在性检查；get_or_none 应结合判空（工程可加强为 404） |
| 忘带 status 字段 | 前端拿不到"这条记录健康状态"；Response 构造时把 record.status 放进去 |

@@point ③ 查询进阶：Q 表达式 + 双下划线过滤
@@need 要解决什么
"查患者 1 最近 7 天的血糖"——多条件组合过滤怎么写？

@@idea 核心思路
```python
from tortoise.expressions import Q

@router.get("/patient/{patient_id}", response_model=List[BloodSugarResponse])
async def get_records(patient_id: int, days: int = Query(7, ge=1, le=90)):
    await Patient.get_or_none(id=patient_id)
    # 近 N 天 = 含今天往前数 N 个自然日，起点是「N-1 天前的本地 0 点」
    # 别用 utcnow()：UTC 0 点 = 北京 8 点，会少算 8 小时；也别减 days（会多算一天）
    today = datetime.now().date()
    since = datetime.combine(today - timedelta(days=days - 1), datetime.min.time())
    records = await BloodSugar.filter(
        Q(patient_id=patient_id) & Q(measured_at__gte=since)
    ).order_by("-measured_at").all()
    ...
```

三个新语法逐个拆：
1. **Q 表达式**：`Q(patient_id=1) & Q(measured_at__gte=since)` 表示 AND 组合；ORM 需要多条件+同一个 filter 里做逻辑组合时用 Q；
2. **双下划线运算符**：`measured_at__gte=since` 是"大于等于"（Greater Than or Equal）；还有 `__lt`/`__lte`/`__contains` 等；
3. **倒序排序**：`order_by("-measured_at")` 负号 = 倒序，最新记录排最前。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 忘了双下划线写成 `measured_at_gte` | 字段名会变成"不存在的字段"报错；必须是 `字段名__运算符` |
| 查询结果不含当天 | 起始时间把时分秒清零后往前推 days 天；边界是"左闭"——含当天 0 点 |
| 排序字段写错没报错但顺序乱 | order_by 传的是字符串，"-measured_at" 顺序敏感，注意负号 |

@@point ④ Query 参数校验：days 的范围约束
@@need 要解决什么
days 是用户传的参数，传 10000 天怎么办？传负数怎么办？

@@idea 核心思路
FastAPI 的 `Query` 自带校验器：

```python
days: int = Query(7, ge=1, le=90)
```

- 默认值 7；
- `ge=1`：大于等于 1（不能查 0 天或负数）；
- `le=90`：小于等于 90（限制最长查询范围，防止拖垮数据库）。

越界请求直接返回 **422**，根本不会进到业务代码。这是"参数校验前置"的典型做法——**坏数据在门口就拦下**，比进库里再判省事得多。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 前端传 days=0 返回 422 | ge=1 拦截；前端传参时按 1-90 校验 |
| 忘了加 Query 包装 | 不带默认值的参数 FastAPI 会当必填路径/查询参数，语义变化 |

@@point ⑤ 更新与删除：refresh_from_db 的时机
@@need 要解决什么
更新血糖 value 后，status 变了，返回的数据要不要重新算？

@@idea 核心思路
（`BloodSugarUpdate` 的字段和 `BloodSugarCreate` 一样，照患者章那套 Create/Update/Response 三件套再补一个即可，这里只讲更新逻辑。）
```python
@router.put("/{record_id}", response_model=BloodSugarResponse)
async def update_record(record_id: int, data: BloodSugarUpdate):
    record = await BloodSugar.get_or_none(id=record_id)
    if not record:
        raise HTTPException(status_code=404, detail="记录不存在")

    update_data = data.model_dump(exclude_unset=True)
    for key, value in update_data.items():
        setattr(record, key, value)

    await record.save()               # ① 写回数据库
    await record.refresh_from_db()    # ② 从数据库重新加载！关键
    return BloodSugarResponse(... status=record.status ...)
```

`refresh_from_db()` 是本例的关键：save 之后内存里的对象可能还带着旧值，**重新从数据库加载**保证计算属性（status）基于最新数据。患者模块的 update 没调 refresh，因为患者没有"依赖快照的计算属性"；血糖有——这就是差异。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 更新 value 后 status 还是旧值 | 忘了 refresh_from_db()；属性在内存里没重新计算 |
| 患者模块可以省、血糖模块不能省 | 依赖模型当前内存状态的计算属性（status）必须 refresh；纯落库字段无所谓 |

@@point ⑥ HealthAnalyzer：统计引擎的职责
@@need 要解决什么
"近 7 天血糖怎么样"不该手写一堆循环——统计逻辑要收进一个可复用的引擎。

@@idea 核心思路
`app/core/health_analyzer.py` 的 HealthAnalyzer 类，提供了两个核心方法：

```python
class HealthAnalyzer:
    async def analyze_blood_sugar(self, patient_id: int, days: int = 7):
        '''统计函数：返回血糖分析结果字典'''
        since = datetime.combine(datetime.now().date() - timedelta(days=days - 1), datetime.min.time())   # 与列表接口同一口径：本地 0 点、含今天
        records = await BloodSugar.filter(
            patient_id=patient_id, measured_at__gte=since
        ).order_by('measured_at')
        if not records:
            return {'error': '暂无血糖数据', ...}
        values = [record.value for record in records]

        # 阈值必须按测量类型分：空腹 3.9~6.1、餐后 2h <7.8、随机 3.9~11.1
        # 用一套 3.9/10.0 套所有记录，会把空腹 8.5 判成"正常"，达标率虚高
        HIGH = {'fasting': 6.1, 'postprandial': 7.8, 'random': 11.1}
        LOW = {'fasting': 3.9, 'postprandial': 3.9, 'random': 3.9}

        def _normal(r):
            hi = HIGH.get(r.measure_type, BG_HIGH_THRESHOLD)
            lo = LOW.get(r.measure_type, BG_LOW_THRESHOLD)
            return lo <= r.value <= hi

        high_count = sum(1 for r in records if r.value > HIGH.get(r.measure_type, BG_HIGH_THRESHOLD))
        low_count = sum(1 for r in records if r.value < LOW.get(r.measure_type, BG_LOW_THRESHOLD))
        normal_count = sum(1 for r in records if _normal(r))
        return {
            'period_days': days, 'record_count': len(values),
            'avg': round(statistics.mean(values), 1),
            'min': round(min(values), 1), 'max': round(max(values), 1),
            'std': round(statistics.stdev(values), 2) if len(values) > 1 else 0.0,
            'high_count': high_count, 'low_count': low_count,
            'normal_count': normal_count,
            'time_in_range': round(normal_count / len(values) * 100, 1),
            'trend': self._calculate_trend(values),
            'risk_level': self._assess_risk(values, high_count, low_count)
        }

health_analyzer = HealthAnalyzer()   # 模块底部实例化单例
```

设计要点：
- **单例导出** `health_analyzer`：路由统一 import 这一个实例，逻辑只有一份；
- **无数据兜底**：records 为空返回带 `error` 字段的字典，不抛异常——调用方（报告/对话）看到 error 就知道「数据不足」。注意这时**字段不全**，响应模型里统计字段要给默认值或设成 Optional，否则空数据直接把接口打成 500；
- **阈值要分类型**：空腹 3.9~6.1、餐后 2h <7.8、随机 3.9~11.1（饭后本来就高，用同一套阈值会把餐后正常值算成偏高）。`BG_LOW_THRESHOLD`/`BG_HIGH_THRESHOLD` 只作为缺省兜底，且必须与模型层 `status` 的判定口径一致——否则会出现「达标率 100%、风险却是中风险」这种自相矛盾。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 统计逻辑写在路由里 | 报告、对话、仪表盘都要用同一套统计；不封装就只能复制三份 |
| 没有记录时统计崩溃 | 引擎必须无数据兜底：records 为空返回 error 字典，绝不抛异常 |
| 阈值代码两处写死 | 模型 status 与引擎阈值**必须查同一张表**（且都按 `measure_type` 分档：空腹 6.1、餐后 7.8、随机 11.1）；单写 3.9/10.0 会让空腹 8.0 一边判正常一边判偏高 |

@@point ⑦ 趋势与风险：只有统计还不够
@@need 要解决什么
平均值看不出"在变好还是变差"，风险等级才是医生和患者真正关心的结论。

@@idea 核心思路
趋势 `_calculate_trend(values)`：拿**最近 3 次平均**对比**早期平均**：
```python
def _calculate_trend(self, values):
    if len(values) < 3:
        return "数据不足"
    recent = values[-3:]
    earlier = values[:-3] if len(values) > 3 else values[:1]
    diff = statistics.mean(recent) - statistics.mean(earlier)
    if diff > 0.5:  return "上升"
    if diff < -0.5: return "下降"
    return "稳定"
```
判据：差 > 0.5 上升，< -0.5 下降，否则稳定；数据少于 3 条直接"数据不足"。

风险 `_assess_risk(values, high_count, low_count)`，三级判定：
```python
def _assess_risk(self, values, high_count, low_count):
    # 只吃「按 measure_type 判出来的超高/超低次数」，别再自己拍一个 avg 阈值，
    # 否则会出现「达标率 100%、风险却是中风险」这种自打脸
    if low_count >= 2 or max(values) > 16.7:
        return "高风险"
    if high_count >= 3:
        return "中风险"
    return "低风险"
```

| 规则 | 结论 |
|---|---|
| 低血糖 ≥2 次 **或** 最高值 >16.7 | 高风险 |
| 高血糖 ≥3 次（按各测量类型的上限判） | 中风险 |
| 其余 | 低风险 |

**先判高风险再判中风险**——要么短路要么救急，低血糖风险权重最高，优先级不能反。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 趋势判断的数据不足条件在哪 | len < 3 返回"数据不足"，别拿 1-2 条算趋势 |
| 风险等级优先级颠倒 | 必须高风险在前；低血糖场景算出"低风险"就是事故 |
| 硬编码 16.7/8.5 | 这些"医学刻度"要统一注释来源，别散落各处 |

@@point ⑧ 统计接口：路由→引擎的接线方式
@@need 要解决什么
前端仪表盘想看统计数据，怎么把统计结果以 API 形式吐出去？

@@idea 核心思路
```python
@router.get("/patient/{patient_id}/stats", response_model=BloodSugarStatsResponse)
async def get_stats(patient_id: int, days: int = Query(7, ge=1, le=90)):
    await Patient.get_or_none(id=patient_id)
    analysis = await health_analyzer.analyze_blood_sugar(patient_id, days)
    return BloodSugarStatsResponse(**analysis)
```

统计接口把路由层写得极薄：`**analysis` 把字典打散成关键字参数喂给 Schema 构造器。BloodSugarStatsResponse 的字段（period_days/record_count/avg/min/max/std/high_count/low_count/normal_count/time_in_range/trend/risk_level/error）正好与引擎返回键一一对应——**引擎出 dict，Schema 收 dict，中间零转码**。

这个"引擎返回结构化字典 → Schema 直接展开"的模式在后面报告、对话模块反复出现。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| `**analysis` 报多余关键字 | Schema 字段与字典键不完全一致；多一个少一个都会炸 |
| error 字段漏了 | 无数据时引擎返回带 `error` 的字典；响应 Schema 没定义这个字段，构造响应时会抛 `ValidationError`，最终是 **500** 而不是 422（请求体缺字段才是 422；多余的键 Pydantic 默认忽略） |
