@@why 这一章在解决什么问题
前两章你学会了两个"仓库"：向量数据库管语义、Elasticsearch 管关键词。但**光有仓库不够**——大模型自己不会去翻这两个仓库。你问它"我们公司的年假规定是什么"，它只会背那些"背过"的话，或者一本正经地编一段假规定给你。

@@point ① 大模型的三大致命伤：为什么"背课文"不够用
@@need 要解决什么
你调通了 API、会用提示词，模型答得挺像那么回事——但一追问公司内部细节，它就露馅：不是**答不上来**（知识只到训练截止日），就是**胡编乱造**（幻觉），更别提把你的私有文档喂给它时心里发毛（数据安全）。这三个问题每个都是产品级硬伤。

@@idea 核心思路
把大模型想象成一个**背书极好但没上过网、也没看过你公司文件的学生**，他有三个天生的坑：

| 痛点 | 人话解释 | 现实后果 |
|---|---|---|
| **知识有截止日期** | 训练数据是"过去"的，新政策、新产品概不知道 | 问 2026 年的新规，只能答 2025 年以前的 |
| **幻觉（一本正经胡说）** | 不知道答案时，会"顺着话头编"，而不是说不知道 | 回答看着专业，数据全是编的，**错了也自信** |
| **数据安全焦虑** | 模型见过你的私有数据才可能答对，但把私有数据喂进训练集谁也承担不起 | 企业文档、商业机密不敢碰 |

RAG 的思路很朴素：**模型不背了，改成"开卷考试"**——每次回答前，先从公司资料库里翻出相关段落，让模型"照着材料答"，答不上就说不知道。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 以为幻觉是"模型不够强"，换个更大的模型就好 | 幻觉的根因是**模型不知道却说知道**——它没有"我不知道"这个选项。换模型治不了，给它资料才治得了 |
| 把三个痛点当成三个独立问题 | 它们是一件事的三面：**知识不在模型脑子里**。所以别分别去修，一个 RAG 一起解决 |
| 以为"数据安全"只是合规要求 | 更现实的是**商业风险**：把公司文档喂进别人的训练集，等于把资产交出去 |

@@point ② RAG 是什么：三步流程
@@need 要解决什么
"开卷考试"听着简单，落成系统要怎么设计？模型一次只能接收一段文字（上下文窗口），**而你的资料库可能上百万字**——全部都塞进去不现实（超上下文、还贵）。RAG 给出了标准答案：只把"跟问题最相关的几段"捞出来给模型看。

@@idea 核心思路
RAG 全称 **Retrieval-Augmented Generation（检索增强生成）**，核心就三步：

```text
① 检索(Retrieve)  用户提问 → 从知识库(向量库/ES)检索出最相关的 Top-K 段资料
② 增强(Augment)   把资料 + 问题 + 指令 拼成一个 Prompt 送给大模型
③ 生成(Generate)  大模型只依据这段上下文作答，答不上就明说不知道
```

一个最小可用的 RAG Prompt 骨架：
```text
【系统指令】你是客服助手。请严格依据下面提供的资料回答问题；
            资料里没有答案，就回答"根据现有资料无法确定"。

【资料】
（这里放检索出的 Top-K 段：原文 + 来源）

【问题】
用户的提问

【回答】
```

看出门道了吗：**模型没变，变的是每次喂给它的"小抄"**。资料常换常新，模型不需要重新训练——这就是 RAG 最大的本钱。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| **以为"RAG 就是向量检索"** | 最常见的一个误解。向量检索只是第①步「检索」的**一种实现**——检索还可以是 BM25 关键词、混合检索。RAG 是**架构**，不是某一种检索技术 |
| 以为"把资料全塞进 Prompt 就行" | 资料库上百万字，全塞进去**超上下文窗口**，而且按 token 计费，**贵到不能用**。所以才要"先检索、只挑最相关的几段" |
| 把 RAG 当成"换个更长的上下文模型就不用做了" | 上下文再长也有限度，而且**长上下文里模型会"中间遗忘"**——塞得越多，关键信息越容易被忽略 |

@@point ③ RAG 的五大优势：为什么企业落地首选它
@@need 要解决什么
方案对比总得先列账本：同样是"让模型懂我的知识"，有微调、有 RAG、有纯提示词，为什么企业最后普遍选了 RAG？因为它在五个老板最关心的维度上全部占优。

@@idea 核心思路

| 优势 | RAG 的做法 | 对比 |
|---|---|---|
| **知识实时更新** | 资料进库 = 立即生效，改一个字分钟级可查 | 微调要重新训练，动辄几小时 |
| **可溯源、可信** | 每句回答都能指回"出自哪份文档"，方便追问"依据呢" | 模型自由发挥，错都不知道错哪 |
| **数据安全** | 私有数据只存在于本地检索库，**不进模型、不上训练** | 关键行业（金融/医疗）的合规刚需 |
| **成本低** | 只需给模型做推理，不用为每个领域花钱训练 | 微调大模型是百万级投入 |
| **可控衰减幻觉** | 资料里没有 → 模型能说"不知道" | 大幅缓解胡说八道 |

一句话总结：**RAG = 让模型只回答"你提供的事实"，不回答"它脑补的"**。对预算有限、业务多变、行业敏感的企业，这是性价比最高的路线。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| **以为上了 RAG 就"零幻觉"** | RAG 只是**大幅降低**幻觉，不是消灭。检索到**相似但不相关**的段落时，模型照样会顺着编。所以要配"引用来源"，让人能核对 |
| 以为"成本低"就是不用花钱 | 省的是**训练**的钱，但多了**检索服务 + 每次多送的上下文 token**。资料越长、检索段越多，单次成本越高 |
| 以为"知识实时更新"等于"改了文档立刻生效" | 改完源文档还得**重新分块、重新向量化、重新入库**。这一步通常要走批处理，不是分钟级——**要设计好更新流程** |

@@point ④ RAG 的典型应用场景：六类最成熟
@@need 要解决什么
学了理论总得知道它能干嘛。这里把 RAG 目前跑得最成熟的六类场景列出来——面试、立项、选型时你至少有话可说，也能反推"我的需求是不是 RAG 场"。

@@idea 核心思路

| 场景 | 典型例子 | 为什么非 RAG 不可 |
|---|---|---|
| **企业知识库问答** | 员工问"年假几天""报销流程"，答的永远是**最新版制度** | 制度月月改，模型背不过来 |
| **智能客服** | 社保政策、产品售前售后答疑，附带"政策原文第 X 条" | 需要政策级准确，不能自由发挥 |
| **私有数据问答** | 财报、合同、病历、刑事卷宗里的"找答案" | 数据绝不能出公司 |
| **跨语言/跨模态** | 英文论文检索出来，中文回答；图文混排材料 | 检索实体、生成语言，各司其职 |
| **个性化推荐** | "根据我的持仓解释这三条新闻对我的影响" | 检索个人上下文 + 生成解释 |
| **长文写作辅助** | 按公司规范起草周报/方案，自动引用规范条款 | 模板化、守规矩、可溯源 |

判断口诀：**问题答案"藏在你的资料里、且会变、且不能编"** → 这就是 RAG 的主场。

@@point ⑤ RAG 的工作原理：一条完整链路
@@need 要解决什么
前面是"三步流程"的粗框架。你真要落地，会发现中间每一步都有工程细节：文档怎么切、向量怎么存、检索完怎么拼 Prompt、太长的资料怎么截断……这里把完整链路铺开，作为后面两章的路线图。

@@idea 核心思路

```text
【离线：知识入库】
原始文档(PDF/Word/Markdown)
   → ① 解析：提取正文（pdfplumber / pymupdf）
   → ② 分块(chunk)：切成几百字的小段，带重叠(overlap)，防止语义腰斩
   → ③ 向量化：每段调 Embedding 模型 变成向量
   → ④ 入库：向量 + 原文 + 元数据(来源/页码) 存进向量数据库

【在线：问答】
用户提问
   → ⑤ 向量化：同一个模型把问题变成向量
   → ⑥ 检索：向量库 ANN 找出 Top-K 最相似的段落
   → ⑦ 组装：指令 + 段落 + 问题 拼成 Prompt（可做去重/截断/重排序）
   → ⑧ 生成：LLM 依据上下文作答
   → ⑨ 返回：答案 + 引用来源（让用户能点开原文核对）
```

**一个强烈建议**：第 ⑨ 步"给引用"一定要做——它既是可信度来源，也是排查"答错了"的抓手（答错时直接看引用了哪段）。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| **答错了就拼命调 Prompt** | **RAG 的瓶颈 80% 在检索，不在生成。** 该捞的资料没捞到，Prompt 写得再好也是巧妇难为无米之炊。先查"检索命中率"，再动 Prompt |
| **入库和提问用了不同的 Embedding 模型** | 两个模型把文字映到**不同的向量空间**，算出来的距离毫无意义——检索结果近乎随机。**必须用同一个模型**（这是最隐蔽的坑，因为程序不报错） |
| 以为 chunk 切得越大越好 | 太大 → 一段里混了多个主题，**检索不精准**，还挤爆上下文；太小 → **语义被腰斩**，捞出来半句话。要**按文档结构切**（标题/段落）并留重叠 |
| 只调 Top-K 数字，不动分块策略 | Top-K 和分块是**一起决定效果**的。分块不好，Top-K 调到 20 也只是多捞了几段垃圾进上下文 |

@@point ⑥ RAG 的演进谱系：标准 RAG 只是起点
@@need 要解决什么
你搜"RAG"，会看到一堆名词：Naive RAG、Advanced RAG、Modular RAG、Self-RAG、CRAG……第一次接触以为是什么高深黑科技。其实**它们是一条演进链**：每个新流派都是给前一代的某个环节打补丁。理解了这个谱系，你就不会再被名词唬住。

@@idea 核心思路

| 流派 | 给上一代打了什么补丁 | 人话 |
|---|---|---|
| **标准 RAG（Naive/Simple RAG）** | 最朴素的"检索→增强→生成"三步走 | 地基 |
| **多轮对话 RAG** | 查资料时"带上对话历史"，上下文更连贯 | 客服场景刚需：连着聊不串味 |
| **多路检索 RAG（HyDE / 多查询）** | 把问题改写/拆成多个角度，分头检索再合并 | 一个问题问得太糙，多问几句更准 |
| **混合检索 RAG** | 向量语义检索 + 关键词(BM25)检索合并去重 | 兼顾"意思近"和"词对得上"，上一章 ES 的活用 |
| **重排序 RAG（Rerank）** | 粗检 Top-50 → 排队模型精细重排 → 取 Top-5 | 粗筛快但糙，精排保证质量 |
| **自适应 RAG（Self-RAG / CRAG）** | 先自检"凭现有资料能不能答"，答不了就触发检索或"自我纠错" | 让 RAG 懂得**承认自己缺资料**，而不是硬答 |

演进主线一句话：**从"固定流程"走向"会自己判断"**——先跑通标准 RAG，再按痛点逐级加装。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| **一上来就要做 Self-RAG / CRAG** | 这些是给"已经跑通、且知道瓶颈在哪"的系统打补丁的。**标准 RAG 都没测过命中率就上自适应，等于在没地基的地方盖三楼** |
| 把所有流派当成"选一个" | 它们大多是**可叠加**的：混合检索 + 重排序 + 多轮对话可以同时用，各管一段 |
| 看名词就以为是什么黑科技 | 每个流派都是**给上一代某个环节打补丁**。看懂"补的是哪个环节"，名词就不唬人了 |

@@point ⑦ 混合检索：为什么不能只靠向量
@@need 要解决什么
第一章吹了向量检索，这里必须把它的短板也说透：向量检索对"语义"灵敏，但对**精确实体**迟钝——搜"iPhone16 512GB 12800元"，它可能召回一堆"苹果手机近期的价格分析"。购物搜索、法规条文这种"必须逐字对得上"的场景，向量独木难支。

@@idea 核心思路
**混合检索（Hybrid Search）** = 向量检索 + 关键词检索，结果合并去重：

| 检索路 | 代表算法 | 擅长 | 短板 |
|---|---|---|---|
| 向量路 | ANN（余弦相似度） | 语义改写、同义词、"我要找关于X的资料" | 精确词/数字/代码不敏感 |
| 关键词路 | BM25（ES 全文检索） | 术语、型号、编号、"精确命中" | 听不懂同义表达 |

工程做法（ES 里现成）：
```text
一次请求同时执行：
  match 查询（BM25 打分） + dense_vector kNN查询（余弦打分）
  ↓
两路分数按权重合并（0.5 * bm25 + 0.5 * cosine）→ 排序取 Top-K
```

**决策建议**：知识库内容以"规章制度、产品文档、FAQ"这种**术语密集、表述固定**为主 → 混合检索是标配；以"综述、散文、自然聊天资料"为主 → 纯向量也能跑。第一篇先把标准 RAG 跑通，再按效果决定加不加另一路。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| **把两路分数直接相加** | **最常见的实现错误。** BM25 的分数是无界的（0 到几十），余弦相似度是 0~1——直接相加，BM25 会**完全压过**向量路，等于白做。**必须先归一化再加权** |
| 权重拍脑袋设 0.5 / 0.5 | 权重得按语料调：术语密集的库该给 BM25 更高权重，口语化的资料该给向量更高权重。**没有万能比例** |
| 合并后忘了去重 | 两路很可能捞出**同一段**。不去重就会出现"同一段资料占掉好几个 Top-K 名额"，白浪费上下文 |
| 以为混合检索一定能提升效果 | 如果语料以自然语言为主，向量路本来就够用，**加 BM25 只会引入噪声**。要先测，别默认加 |

@@point ⑧ 重排序与检索质量：粗筛和精排两段式
@@need 要解决什么
向量库 ANN 检索快是快，但召回的结果**排序质量一般**——它按"向量距离"排的序，跟"和问题真的相关"之间还有差距。直接取 Top-5 喂给模型，经常出现"第 3 段其实比第 1 段更该被引用"的尴尬。怎么在"快"和"准"之间找到平衡？

@@idea 核心思路
业界标准答案：**粗检索 + 重排序（Rerank）两段式**。

```text
第一段（粗）：向量库 ANN 快速召回 Top-50   ← 要求快，宁可多捞
第二段（精）：Rerank 模型对 50 段逐条打相关分
              → 排序 → 只取 Top-5 进 Prompt    ← 要求准，宁可慢
```

为什么这招有效：
- ANN 的排序是"距离近似"，Rerank 是**真正的阅读理解打分**（cross-encoder），谁更相关它答得最准
- 粗筛只做 50 段的轻活，重排只做 50 段的细活，两者都便宜
- 语义检索的"召回率"和"精度"矛盾，靠两段式同时解决

效果经验值：加了 Rerank 的 RAG，答案质量普遍肉眼可见提升，代价是一次重排延迟（几十毫秒级）。**企业级 RAG 的默认配置**。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| **以为加了 Rerank 就能"无中生有"** | Rerank **只能在已经召回的候选里重新排序**。粗筛没捞到的资料，重排一万遍也排不出来——**粗筛的召回率是整条链路的天花板** |
| 粗筛只取 Top-5 再去重排 | 那重排就没意义了（就 5 段，挑不出花）。**粗筛要"宁可多捞"**（通常 50~100），精排才有得挑 |
| 把 Rerank 当成"另一种检索" | 它是**排序器**，不负责找新资料。检索和排序是两件事 |
| 只加 Rerank，不管分块和 Embedding 模型 | 前面两样错了，Rerank 只是把**错的候选**排得更整齐而已。**先保证召回是对的，再谈排序** |

@@point ⑨ RAG vs 微调：到底该选哪个
@@need 要解决什么
RAG 这么火，但还是会有人问："为什么不直接微调，让模型把我们的知识学进脑子里？"——这是落地选型的第一道判断题。选错了：数据量小去微调是杀鸡用牛刀，追求实时性却微调了是南辕北辙。

@@idea 核心思路

| 维度 | RAG | 微调(Fine-tuning) |
|---|---|---|
| 本质 | 每次回答前**查资料** | 把知识**写进模型参数** |
| 知识更新 | 改资料即生效，分钟级 | 要重新训练，按天计 |
| 溯源能力 | 每句可指回原文 | 无（模型"记住"了但说不出出处） |
| 数据安全 | 私有数据不出本地库 | 训练数据进了模型=风险敞口 |
| 成本 | 检索服务 + 推理费 | 训练算力 + 训练数据准备 |
| 适合 | 知识会变、要可溯源、数据敏感 | 模型"做事风格/能力"要变（调格式、练技能） |

**决策树：**
```text
你的目标是"让模型知道新知识"？          → RAG
你的目标是"让模型学会某种做事方式/格式"？  → 微调
知识需要频繁更新？                      → RAG（责无旁贷）
```

行业共识：**RAG 解决"知道什么"，微调解决"怎么表现"**。多数场景先 RAG；确实遇到"回答风格、工具调用格式"的需求，再叠加微调，两者也不是互斥的。

@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| **以为微调能"把知识灌进模型"** | 微调擅长学**形式**（说话风格、输出格式、工具调用姿势），**不擅长灌事实**。用微调灌知识，成本高、更新难，还会**灾难性遗忘**（学了新的忘了旧的） |
| 以为两者只能二选一 | 不互斥。**"RAG 管知识 + 微调管风格"** 是常见组合，各司其职 |
| 拿"哪个更便宜"当唯一标准 | 微调的贵不只在训练算力，**更贵在数据准备和迭代周期**（每次改都要重来一遍）。算总账时容易漏掉 |
| 知识更新频繁还想靠微调 | 制度月月改、产品周周上新——**微调根本追不上**，这是 RAG 的绝对主场 |

@@point ⑩ RAG 选型决策树 + 落地检查清单
@@need 要解决什么
理论学完，落地时第一件事是拍板：我的场景用标准 RAG 起步，还是直接上混合/重排序？以及上线前我最该盯住哪几个指标？把决策变成"查表题"。

@@idea 核心思路
**检索方案决策树：**
```text
你的资料是什么样？
├─ 术语密集、表述固定（制度/FAQ/产品文档）→ 混合检索（向量+BM25）
├─ 自然语言为主（聊天记录/文章/报告）     → 向量检索起步
└─ 对精度要求苛刻（法律/医学/金融）       → 向量 + 重排序（Rerank）
                    ↓
还有余量？ → 再多轮对话 RAG（客服场景必选）
           → 再激进点 → 自适应/自我反思 RAG（Self-RAG/CRAG）
```

**上线前必看的四个质量指标：**
| 指标 | 衡量什么 | 怎么测 |
|---|---|---|
| **检索命中率** | 该被捞出来的资料捞出来没 | 构造 20~50 条"问题→期望资料"测试集 |
| **答案准确率** | 模型照着资料答对了没 | 人工/模型判分标注 |
| **幻觉率** | 资料没有的它硬编了没 | 答案里抽查"非资料信息" |
| **引用准确性** | 答的内容是否真的来自所引文件 | 随机抽 10 条核对 |

**工程质量铁律**：RAG 系统的瓶颈 80% 在"检索"而不是"生成"——**检索捞不到对的资料，后面模型再强也是巧妇难为无米之炊**。先优化检索，再谈 Prompt。
