@@point ① Codex 是什么：OpenAI 的 AI 编程助手
@@need 要解决什么
Codex 一句话怎么定位？它和 ChatGPT 的 Code Interpreter、和 GitHub Copilot 有什么渊源？

@@idea 核心思路
**Codex 是 OpenAI 推出的 AI 编程助手**（产生于 ChatGPT 代码解释器的演进，直系前身是 2021 年的 Codex 模型——GitHub Copilot 初代就用它）。

它支持多种形态（详见第 ② 点）：**CLI、SDK、桌面应用、VSCode 扩展**——开发者可以选择**在熟悉的工具中使用**（VSCode/桌面）或**自由嵌入到自己的工作流程**（CLI/SDK）。

**核心思想**：把"对话式 AI"与"真实编程执行"结合——你在对话里下指令，Codex 在**本地（受控）执行**代码、命令，完成修改、搜索、重构等真实动作，而不是只"说"不"做"。

一个容易被忽视的点：**它面向的是"本地优先"的开发者工作流**，不像 Trae/Cursor 强绑某个 IDE——**用 CLI 版时，你的编辑器是谁都行**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 把 Codex 当成"IDE" | Codex 不是 IDE，是 **AI 编程 Agent 工具**；IDE 只是它的一个宿主（VSCode 扩展形态） |
| 以为 Codex 就是"ChatGPT 里跑代码" | ChatGPT 代码解释器是"云端对话环境"，Codex 更偏**本地 CLI/工程流**、配 Git/AGENTS.md 深度集成 |
| 和 Copilot 搞混 | Copilot=代码补全插件（GitHub/微软），Codex=OpenAI 的对话式 Agent 工具；起源有关联但产品不同 |

@@point ② 四种形态：CLI / SDK / 桌面应用 / VSCode 扩展
@@need 要解决什么
"四种形态"是 Codex 最大的特色之一。它们各自是什么？怎么用？选哪个？

@@idea 核心思路
Codex 的四种形态及选择建议：

| 形态 | 是什么 | 适合谁 |
|---|---|---|
| **CLI（命令行）** | 在终端中运行 Codex，与工作区对话 | 终端党、脚本化流程、远程/SSH 环境 |
| **SDK（开发包）** | 通过代码调用 Codex 能力，嵌入自己的应用 | 想做**自动化/流水线**的开发者、搞 AI 编程产品 |
| **桌面应用** | 独立应用窗口使用 Codex | 不依赖 IDE 的轻量用户体验 |
| **VSCode 扩展** | 在 VSCode 中安装 Codex，编辑器内使用 | VSCode 用户、想要"IDE+Agent"一体体验 |

**选择口诀**：想要"编辑器里一体化"→ VSCode 扩展；想"纯终端高效"→ CLI；想"写程序调用/自动化"→ SDK；想"独立窗口轻量用"→ 桌面应用。常见组合：**平时 VSCode 扩展，自动化脚本用 CLI/SDK**。

四种形态共享同一个 Codex 引擎与工作区模型，**办公/教学场景推荐先上手 CLI 或 VSCode 扩展**，最快形成闭环。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 四种形态选择困难 | 别纠结，**按你最常用的入口选一种**开始；底层引擎一致，之后可随时换形态 |
| 以为 CLI 版没有界面就不能用 | CLI 有交互式对话界面（TUI）；输入 `codex` 命令即进入 |
| 桌面应用和 VSCode 扩展重复装 | 不冲突，各自独立；资源有限时先装 VSCode 扩展（生产力最直接） |

@@point ③ Codex vs Trae vs Cursor：三条路线对比
@@need 要解决什么
三款工具都学完了（Trae/Cursor 已学、Codex 进来），它们到底怎么区分？什么场景用哪个？

@@idea 核心思路

| 维度 | Trae | Cursor | Codex |
|---|---|---|---|
| 出品方 | 字节跳动 | Anysphere（Cursor 团队） | OpenAI |
| 核心形态 | AI IDE（Chat/Builder 双模式） | AI 原生 IDE（Agent/Ask/Manual） | CLI/桌面/VSCode 扩展/SDK |
| 绑定关系 | 自有 IDE | 类 VSCode 生态 | **不依赖特定 IDE**（本地优先） |
| 特色能力 | 中文友好、国内直连、Builder 全自动 | AI 原生设计、多模型、内联智能 | Git 深度集成、AGENTS.md 记忆、沙箱权限 |
| 上手门槛 | 低（中文语境） | 中（VSCode 习惯） | 中高（命令行/工程概念） |

**选型参考**：求"开箱即用、中文环境"→ Trae；求"AI 与编辑器深度融合"→ Cursor；求"工程化 Agent、命令行自动化、可编程嵌入"→ Codex。**三者并存也合理**：日常写码用 Cursor/Trae，自动化脚本和重工程用 Codex。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 三选一纠结到不敢用 | 都装了也占不了多少；**主力一个、备用一个**，实战出真知 |
| 以为 Codex 的"不绑 IDE"=没编辑器 | 它有 VSCode 扩展形态；"不绑"意思是**你也可以用别的编辑器 + CLI** |
| 用 Codex 时套 Cursor/Trae 的习惯 | Codex 的流程（Git 提交、AGENTS.md、沙箱）不同；**按它的节奏来**，别硬搬 |

@@point ④ 前置软件：Git / Node.js / VSCode（.NET 运行时）
@@need 要解决什么
装 Codex 前，机器上要有什么"底子"？各自是干什么的？

@@idea 核心思路
讲义给出的 Codex 安装前置依赖：

- **Git**：版本控制工具，Codex 的 Git 集成功能（提交、回滚、分叉）依赖它；
- **Node.js**：Codex CLI/SDK 的运行时依赖之一（部分功能基于 Node 生态）；
- **VSCode**：安装 VSCode 扩展形态时的宿主编辑器（可配合扩展市场安装 Codex 扩展）；
- **.NET 运行时（备注）**：某些 Codex 桌面应用/相关组件依赖 .NET 运行时（与 Windows 生态相关，根据讲义提示按需安装）。

安装建议：**按官方文档的版本要求装**（Node 建议 LTS，Git 最新稳定版）。讲义配套资料里也提供了离线安装包（Codex Installer、Git、Node、VSCode 安装器）。

**验证装好了**：终端执行 `git --version`、`node -v` 确认版本号输出版本正常。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 只装 Codex 本体不装 Git | Git 集成功能不可用；**Codex 的代码管理章节全靠 Git**，必装 |
| Node 版本太老（如 v14） | 装 **LTS 版**；老版本可能和 CLI 依赖冲突，报错先查版本 |
| 装了前置没验证 | 终端跑 `git --version`、`node -v`，有版本号才算真装好（软件安装包给出了 Git/Node/VSCode 配套离线包） |

@@point ⑤ 创建工作空间：一个任务一个 Workspace
@@need 要解决什么
Codex 的"工作空间（Workspace）"是什么？为什么说它是 Codex 里的"家"？

@@idea 核心思路
**工作空间（Workspace）**是 Codex 的**任务工作区**——每个任务在独立的工作空间中执行，Codex 在其中读写文件、执行命令。

核心特点：

- **隔离性**：任务间互不干扰，不同项目的文件、环境隔离；
- **临时性**：工作空间内的环境可按需创建/清理（不用担心污染本机）——**默认临时工作空间**用完即走，**持久工作空间**可跨会话保留；
- **上下文集**：当前相关的文件、上下文、会话都在空间内呈现。

一个任务可以跟一个工作空间挂钩（"**一个任务一个空间**"，讲义强调的用法），完成后可清理或留存。

```text
命令行使用示例（概念演示）
codex "帮我写一个 Python 爬虫"
→ 进入/创建工作空间，Codex 在该空间内行动
```

**理解角度**：Workspace 就是"Codex 干活的那张桌子"——一张桌子只摆一个项目，干完收走，别和别的项目混在一起。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 所有任务共用一个空间 | 任务互相踩文件、踩依赖；**一个任务一个空间**，隔离干净 |
| 临时空间的东西"丢了" | 临时空间**用完即毁**；要留存的内容放到持久空间或用 Git 提交 |
| 把 Workspace 和"文件夹"混为一谈 | 工作空间有 Codex 的隔离/上下文/会话管理语义，**不是普通文件夹** |

@@point ⑥ CLI 安装三步：安装、登录、验证
@@need 要解决什么
CLI 形态怎么装？装完怎么确认能用了？

@@idea 核心思路
**CLI 安装三步走（讲义路线）**：

```bash
# 1. 安装 Codex CLI（Windows 环境按官方指引）
npm install -g @openai/codex

# 2. 授权认证（按提示登录/注册 OpenAI 账号，完成 CLI 授权）
codex login

# 3. 验证安装成功
codex --version
```

安装要点：

- 包名以官方文档为准（示例为 `@openai/codex`，如官方有更新路径以官网/讲义资料为准）；
- **SDK 授权登录**：开发者还可通过 SDK 注册/获取 API 凭证（用于程序化调用），具体凭据存放遵循官方最佳实践（环境变量/配置，不外泄）；
- 国内环境的网络、代理、镜像问题，按讲义资料里的说明处理（或使用离线安装包）。

**验证通过的标准**：`codex --version` 输出版本号，`codex login` 后提示已认证，即可进入下一章的功能学习。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| npm 安装超时/镜像问题 | 使用国内 npm 镜像（如 npmmirror）或走**讲义配套离线安装包**；别反复重试默认源 |
| 登录时页面打不开 | 确认网络与代理；按提示的 OAuth 链接在浏览器完成并回终端确认 |
| 出现"Command not found" | 检查 PATH 是否包含 npm 全局目录；重新打开终端再试 `codex` |
| 拿到授权/密钥直接贴进代码里 | **密钥不进任何文件**；用环境变量保存并妥善管理，绝不写入项目或聊天记录 |

@@point ⑦ 其他细节：桌面应用的额外说明
@@need 要解决什么
四种形态里，桌面应用有什么需要防坑的额外注意点？

@@idea 核心思路
讲义对**桌面应用**形态补充了几个实务细节：

- **安装与启动**：跟随官方安装引导，注意与 VSCode 扩展的协同（两者可共用账号与工作区）；
- **首次使用要点**：登录账号、确认工作空间与运行环境（Node/Git 可用性）；
- **界面结构**：包含对话区、工作区列表、历史任务等模块（不同版本界面有差异，以实际为准）；
- **常见问题**：登录失效、工作区无法访问、界面卡顿等——先查官方 FAQ 或讲义附注，多数可自行解决。

**规律总结**：四种形态的"账号登录→工作空间→对话执行"结构是统一的；**会了 CLI 就懂了大半，其他形态只是换壳换入口**。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 桌面应用与 CLI 重复登录 | 登录状态一般**按账号共享**；个别版本要求分别登录，按提示操作 |
| 盯着"四个形态"害怕学不完 | 记住底层统一结构（账号+空间+对话），**会 CLI 即会全** |
| 界面版本不同就慌 | 版本 UI 差异不影响核心概念；对着功能找入口即可 |

@@point ⑧ 初次打开 Codex：任务列表与项目归属
@@need 要解决什么
装好 Codex 后第一次打开，界面上的"任务、对话、项目"到底是什么关系？讲义第 5 页给了明确说明。

@@idea 核心思路
Codex 的界面组织（讲义原文要点）：

- **多工作空间并列**：创建多个文件夹作为工作空间，Codex 可**同时开启多个任务**，且任务列表非常友好；
- **任务状态标识**：每个任务都有状态标识——**进行中、等待批准、完成**（对应权限沙箱的交互：等批准的会挂起等你确认）；
- **项目归属对话**：可以选择**对话的项目归属**；选择"不使用项目"的对话将归类到**对话区域**。

**一句话理解**：Codex 的界面 = "工作空间/任务"（大容器）+ "对话"（上下文单元）——任务挂靠空间、对话挂靠任务（或独立于项目）。状态标识让你一眼看清**哪些任务在跑、哪些在等你**。

**与工作空间的关系**：这里的"多文件夹多任务"正是第 ⑤ 点"一个任务一个空间"的界面呈现——空间管隔离，任务管状态。

@@trap 坑在哪
| 现象 | 原因 / 怎么办 |
|---|---|
| 任务"等待批准"却以为卡死 | 等待批准=在**等你授权**（沙箱提权操作）；去任务里点批准它才会继续 |
| 对话和任务混在一起分不清 | 对话是交流记录，任务是执行单元；"不使用项目"的对话归对话区 |
| 一个空间堆多个任务 | 建议**一个空间一个任务**（第 ⑤ 点口诀）；多任务时状态标识会帮你区分谁在跑 |
