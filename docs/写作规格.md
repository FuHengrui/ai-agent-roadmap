# 写作规格

> 一份让 AI 稳定产出**结构化教学内容**的规格。
> 你把它连同参考资料一起交给 AI，它就能按同一个标准写下去，不会每章一个样。
>
> 全文 **692 行**，包含：三套章法（知识型 / 项目型 / 操作型）、@@ 指令语法、
> 知识点切分原则、禁止清单、自检清单，以及若干条**踩坑换来的规则**。

---

## 这份规格解决什么问题

用 AI 写长内容，最大的问题不是写不出来，是**写着写着就散了**：

- 风格每章都不一样
- 该讲的为什么被跳过，只剩是什么
- 越写越像流水账
- 让他别写密钥，他转头就把讲义里的真 Key 抄进去

**规格的作用就是把这些标准写死。** 规格写得越明确，产出越稳定 —— 这条后面有一整节血泪教训（第 2.4 节）。


> 这份文档是硬性要求，不是建议。**每一条都有原因，请照做。**
> 有任何一条做不到，先问清楚，不要自己发挥。

---

## 〇、先搞清楚这是什么

我们在做一套**面向初学者**的 AI 知识库。它不是课程讲义的搬运，是**重新组织过的知识**。

**唯一的判断标准：**

> 一个完全不懂的小白，读完这一章，**能不能说出「这个东西是为了解决什么问题」**。

说不出来 → 这一章不合格。

## 一、目录规则（★ 最重要，先看这条）

知识库**按课程阶段分目录**，每章一个 HTML。目录结构**不能改**：

```
建立知识库/
├── index.html                          ← 需求地图（总入口）
├── README.html                         ← 使用说明
├── assets/style.css                    ← 全站样式
│
├── 阶段01-大语言模型基础与工程化实践/
│   ├── 01-第一章-聊天机器人初体验.html
│   ├── 02-第二章-编程基本概念.html
│   └── ...
│
└── 阶段02-AI智能体Web系统构建实战/
    ├── 01-第一章-后端服务开发FastAPI.html
    └── 02-第二章-FastAPI进阶.html
```

### 为什么必须分目录

**章节号在每个阶段里都从「第一章」重新开始。**
如果全平铺在根目录，阶段 01 和阶段 02 都会产生 `01-第一章-xxx.html` —— **直接撞车。**

### 命名规范

| 层级 | 规范 | 例子 |
|---|---|---|
| 阶段目录 | `阶段NN-阶段名` | `阶段02-AI智能体Web系统构建实战` |
| 章节文件 | `NN-第X章-章名.html` | `01-第一章-后端服务开发FastAPI.html` |
| 源文件 | `NN-章名.md` | `01-后端服务开发FastAPI.md` |

**名字里不要出现：** 空格、`【】`、全角括号、`的补充`这种没编号的后缀。

## 二、内容怎么写（这是灵魂）

### 2.1 每一章必须有的六块

| # | 块 | 源文件指令 | 作用 |
|---|---|---|---|
| 1 | **这一章在解决什么问题** | `@@why` | 大白话开篇，从痛点切入 |
| 2 | **在全局框架里的位置** | `@@map` | 上一章 → 本章 → 下一章 |
| 3 | **知识点卡片** | `@@point` | 主体 |
| 4 | 本章小结 | `@@summary` | 拿到了什么能力 |
| 5 | 自测题 | `@@quiz` | 3–7 题 |
| 6 | 本章配套资料 | `@@links` | 讲义 / 源码 / 资料链接 |

**缺任何一块都算不合格。**

### 2.2 知识点卡片：需求先行（★ 最关键）

**这是这套知识库和普通教材唯一的区别。** 每个知识点必须先讲「它要解决什么问题」，再讲它是什么。

**❌ 反例（知识罗列型 —— 这样写就是废的）**

```markdown
@@point ① 列表
@@need 要解决什么
列表是 Python 中最常用的数据结构，用方括号表示。

@@idea 核心思路
列表可以存任意类型的数据，支持增删改查……
```

**问题**：`@@need` 里写的还是定义，不是需求。学生读完只记住了"列表是什么"，不知道"为什么要用"。

**✅ 正例（需求驱动型）**

```markdown
@@point ① 列表：一次装很多数据
@@need 要解决什么
上一章你学会了处理【一个】数据。但真实世界不会一次只给你一个——
你要处理 100 条招聘信息、一张成绩表。
如果只用上一章的知识，你得写 job1、job2……job100 一百个变量。这显然不行。

@@idea 核心思路
列表就是解决这个的：**一个变量装一串数据**，用方括号写：[1, 2, 3]。
它有序、能改、能装任意类型（这一点和 C/Java 的数组不同）。
```

**差别在哪**：正例先让学生**感受到痛**，再告诉他解药。

### 2.3 判断 `@@need` 写得好不好，问一句话

> **这段文字，能不能让一个不懂的人说出「哦，原来是为了解决这个」？**

- 能 → 合格
- 只是解释了"它是什么" → **重写**

### 2.4 卡片的四段

| 段 | 指令 | 必写吗 | 写什么 |
|---|---|---|---|
| 要解决什么 | `@@need` | **必写** | 需求。写不出来说明还没吃透 |
| 核心思路 | `@@idea` | 建议写 | 大白话讲原理，可打比方、配代码、画图 |
| 怎么做 | `@@how` | **可选** | **只有当"做法"是独立的一串步骤时才单列**；否则并进 `@@idea` |
| 坑在哪 | `@@trap` | **建议写，见下** | 常见报错与认知误解（用表格） |

**关于 `@@how`**：像"字符串有哪些常用方法"这种，思路和做法本来就是一件事，硬拆反而做作。**别为了凑四段而拆。**

#### ⚠️ 关于 `@@trap`：写多少？（2026-10-14 定的规矩）

**实测过两种极端，都不对：**

| 阶段 | 做法 | 问题 |
|---|---|---|
| 01–05 | 每个知识点都写（**100%**） | 抽查后确认**不是凑数**，是真坑。但覆盖率"恰好 100%"会让人怀疑 |
| 06 初稿 | 只在"要动手操作"的点上写（**0–17%**） | **太少了**。`RAG基础理论` 一个坑都没有，可惜 |

**结论：坑分两种（操作坑 / 认知坑），两种都值得写——下面细说。**

**覆盖率：每个知识点都要认真想一遍"这里有没有坑"。**

> ⚠️ **2026-10-14 修正（重要，一定要看完）**
>
> 上一版这里只写了"**不要按百分比写，覆盖率是结果不是目标**"。
> 结果**阶段 11 立刻掉到 15%**（12 章 96 个点只有 14 个坑）。
> 教训：**去掉具体数字，就会被读成"不用写了"。**
>
> 所以这一版把话说死：

### 规矩（照做，别自己发挥）

**1. 每个知识点，动手写之前先问一句：**

> **初学者在这个点上，最可能在哪里想岔、或者哪里最容易报错？**

**2. 想得出 → 写。** 大部分知识点都想得出——尤其是"要动手装/配/跑"的点。

**3. 想不出 → 跳过。** 但**必须是真的想过了**，不是懒得想。

**4. 期望值：`@@trap` 覆盖率 ≥ 70%。**

| 覆盖率 | 判定 |
|---|---|
| **70% 以上** | ✅ 正常（阶段 01–10 基本都在这个区间） |
| **40–70%** | ⚠️ 偏低，检查是不是漏了 |
| **40% 以下** | ❌ **基本可以确定是漏了**，除非整章都是"清单/列表"型内容 |

**例外**：像"项目全景""选型决策树""应用场景列表"这种**纯罗列**的章节，
可以低到 30–40%。**但整本书里这种章节是少数**——如果你发现
自己有好多章都"想不出坑"，那不是章节的问题，是**态度的问题**。

### 坑分两种，两种都要写

| 类型 | 什么时候有 | 例子（都来自实际章节） |
|---|---|---|
| **操作坑** | 要动手装/配/部署的点 | 「安装 ES 8 别被非 root 用户坑到」 |
| **认知坑** | 概念点，最容易想岔的地方 | 「以为参数越多一定越强」「以为 RAG 就是向量检索」 |

**认知坑优先**——操作坑网上能搜到，而"我以为是这样、其实是那样"这种，
**没人会主动告诉你**。

### 写不出来的两个自救办法

**① 先想"初学者会怎么错"**，而不是"这段代码会报什么错"。

> 例：「pydantic-settings 加载 .env」这个点，
> 代码本身没什么坑，但初学者会**把字段名大小写写错**、会**以为改了 .env 立即生效**、
> 会**把 .env 提交进 Git** —— 这三个都是真坑。

**② 回忆你（或讲义）真的踩过什么。**

> 讲义里老师特意提了一句"这里注意"，那通常就是个坑。
> 验收清单里让你"确认 xxx"的地方，**为什么需要确认？因为不确认就会错**。

### 表格写法

```markdown
@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 以为 X | 实际上是 Y，因为 Z |
| 报错 XXXX | 原因 YYY，这样解决：ZZZ |
```

## 三、禁止清单（★ 违反就是返工）

| # | 禁止 | 原因 |
|---|---|---|
| **0** | **★ 绝对不要写任何密钥、Token、密码的真实值** | **安全事故，见下方专条** |
| 1 | **不要照搬讲义原文** | 版权，而且学生要的是"你的话" |
| 2 | **不要写成"XX 是什么"的词典条目** | 那是教材，不是这个知识库 |
| 3 | **不要编造"坑"** | 假坑比没坑更糟。没把握就写「这里容易想当然」 |
| 4 | **不要直接抄讲义代码** | 要能让它独立跑起来，并讲清每段在干什么 |
| 5 | **不要出现个人信息** | 设备型号、账号、学习进度——这份东西要能分享给同学 |
| 6 | **不要放课程视频链接** | 课程 10/27 到期后全是死链 |
| 7 | **不要改目录结构** | 见第一节 |
| 8 | **不要用讲义里的图** | 那是人家的版权；要图就自己画（ASCII 图可以） |

### ⚠️ 关于第 0 条（密钥）—— 必须逐字执行

**已实测确认：课程自带的 demo 代码里就有真实密钥。** 例如某份讲义配套的
`.ipynb` 里直接写着：

```python
client = OpenAI(
    api_key="sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",   # ← 这是真实可用的 Key
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)
```

**这些是别人的（讲师的）Key，而且可能还在生效。** 一旦写进知识库并发布出去，
任何人都能拿去花别人的钱，**责任在你**。

#### 引用这类代码时，必须这样改

```python
# ✅ 正确：改成占位符，并告诉读者去哪里拿自己的
import os
client = OpenAI(
    api_key=os.environ["DASHSCOPE_API_KEY"],   # 从环境变量读，别写死在代码里
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)
```

#### 交稿前必须自查这几类字符串

| 模式 | 例子 |
|---|---|
| `sk-` 开头 | `sk-ddbcf305…` |
| `api_key="…"` / `api_key: …` | 任何非占位符的赋值 |
| `Bearer xxx` | 请求头里的 token |
| `eyJ….….…` | JWT |
| `password="…"` / `pwd: …` | 明文密码 |
| `.env` 内容 | 整块都不要 |

**占位符合法写法**（这些是安全的）：
`"你的 API Key"`、`"sk-xxx"`、`os.environ["XXX_API_KEY"]`、`"<从控制台复制>"`

**拿不准就问，别猜。**

## 四、知识点怎么切

**按「学生要解决的问题」切，不按「视频顺序」切。**

| 原则 | 说明 |
|---|---|
| 一个大章 → **8–16 个知识点** | 太少说明没消化，太多说明还在按视频列 |
| 一节视频可能只占半个知识点 | 别一对一映射 |
| 一个知识点 ≤ 一屏半 | 超过就该拆 |
| 编号用 ①②③… | 视觉上连贯 |

## 四之二、项目型章节怎么写（★ 另一种章法）

前面二、四节讲的是**知识型章节**——有讲义、有概念、按知识点切。

**但有些阶段是「项目实战型」**：不给讲义，只给一份**需求书 + 成品代码**。
比如阶段 03「Agent项目启蒙」，就只有一份会议系统的需求文档和源码。

**这两类章节写法不一样，别套错。**

### 核心区别

| | 知识型章节 | **项目型章节** |
|---|---|---|
| 材料 | 讲义 PDF（有讲解） | 需求书 + 代码（**没讲解**） |
| 讲什么 | 这个概念解决什么问题 | **这个需求为什么这么实现** |
| 知识点按什么切 | 按「学生要解决的问题」 | **按「需求」切，不按「模块」切** |
| 主要难点 | 把概念讲通俗 | **从代码里反推出工程取舍** |

### ⚠️ 最容易犯的错：写成代码导览

**❌ 反例（按模块切 → 变成"文件说明书"）**

```markdown
@@point ① auth.py 是干什么的
@@need 要解决什么
auth.py 负责用户认证相关的接口……

@@point ② models.py 是干什么的
@@need 要解决什么
models.py 定义了数据库模型……
```

**问题**：这是在**介绍文件**，不是在**讲知识**。读者读完只知道"有这么几个文件"，
**不知道为什么要这么设计**。

**✅ 正例（按需求切 → 讲工程取舍）**

```markdown
@@point ② 账号系统：为什么会议内容必须私有
@@need 要解决什么
会议录音里可能有薪资、人事、商业计划。这是**别人不能看的东西**。
所以"谁能看到哪条会议"必须由系统说了算，不能靠"没人猜得到链接"。

@@idea 核心思路
三个决定：
  · 密码**不能明文存** —— 数据库泄露时不能让人直接拿到密码
  · 登录后发一个**凭证（token）** —— 之后每个请求带着它，服务端认票不认人
  · 每条会议记录**都挂一个用户 id** —— 查的时候强制带上"只能查自己的"
```

**差别**：正例讲的是**"为什么必须私有 → 于是做了三个设计决定"**，代码只是这些决定的实现。

### `@@need` 在项目型章节里写什么

写**用户或工程上的真实痛点**，不写"这个文件实现了什么"。

| ❌ 这么写 | ✅ 该这么写 |
|---|---|
| `auth.py 负责认证` | 会议内容敏感，**不能被别人看到** |
| `pipeline.py 是处理流水线` | 转写一段 30 分钟录音要几十秒，**不能让用户干等** |
| `models.py 定义数据表` | 一场会议要记的东西很多，**散着放会乱、会丢** |

### 项目型章节必须有的内容

| # | 内容 | 为什么 |
|---|---|---|
| 1 | **需求从哪来** | 用户故事 → 功能清单，这是「需求先行」的示范 |
| 2 | **每个需求的技术取舍** | 「为什么异步不选同步」「为什么用云 ASR 不本地跑」 |
| 3 | **数据怎么组织** | 有哪些表、什么关系、**状态怎么流转** |
| 4 | **完整链路走一遍** ★ | 从「用户点一下」到「看到结果」，按时间顺序拆解每一步 |
| 5 | **工程规范** | `CLAUDE.md`、目录约定、依赖管理这些「元知识」 |

**第 4 条最重要。** 学习者最缺的就是「一件事从头到尾是怎么走通的」——
散着讲十个文件，不如把一条链路完整走一遍。

### 从代码反推「为什么」的方法

代码只告诉你**做了什么**，不告诉你**为什么**。找「为什么」的四个线索：

| 线索 | 在哪找 |
|---|---|
| **注释和文档** | `CLAUDE.md`、`README.md`、`docs/`、代码注释 |
| **配置项的存在** | 比如有 `APP_DEBUG`、`ACCESS_TOKEN_EXPIRE_MINUTES`，说明作者想过这些 |
| **「没做」的地方** | 没有测试、没有重试机制——**「没做」往往也是信息** |
| **反差** | 某处用复杂方案而别处很简单，说明这里有真实痛点 |

**找不到「为什么」就诚实写「这里看不出作者的意图」，不要编理由。**

### 知识点数量

**8–14 个**，通常一个知识点对应**一个需求**（或一组紧密相关的需求）。
按需求切超过 14 个，说明项目太大，**考虑拆成两章**。

### 追加的禁止清单（在第三节基础上）

- ❌ **不要写成文件说明书**（"xx.py 负责 xx"）
- ❌ **不要逐行讲解代码**（读者要设计思路，不是代码朗读）
- ❌ **不要把 `.env`、密钥、真实域名写进去** ← 安全事故
- ❌ **不要美化**。有 bug 如实说，有妥协如实说
- ❌ **不要贴超过 20 行的代码块**（超了就挑关键几行）

## 四之三、操作型章节怎么写（★ 装软件 / 点后台 / 配界面）

**判断标准**：这一节的内容，读者是不是**要照着"点"或"装"才能学会**？

- **是** → 按这一节写
- **不是**（纯讲概念、纯看代码）→ 按二、四节写

**典型场景**：装 IDE（Trae / Cursor / Codex）、配云服务器、在企业微信/钉钉/飞书后台建机器人、
Coze 里拖节点、WebUI 里改设置。

### ⚠️ 先说不能做的（版权 + 现实约束）

| 不做 | 原因 |
|---|---|
| ❌ 不放讲义里的截图 | 版权 |
| ❌ 不自己截图 | 费时间；而且截图里带**账号信息**（企业名、头像、工作空间名） |
| ❌ 不用 ASCII 画复杂界面 | 后台菜单树太深，画不准反而误导 |

**所以只能用文字——但文字可以写得很好用。下面是规矩。**

### 四条规矩（照做）

#### 1. 开头挑明"这是操作章"，并给出学法

**在 `@@why` 或 `@@note` 里，主动说明这一章的性质。**

```markdown
本章全是平台后台操作，没有复杂代码（**全文代码不到 20 行**）。
建议用**边看边点**的方式学：**开一个浏览器跟着步骤走，卡在哪一步就回看哪一步。**
```

**为什么要挑明**：读者一看到"全是点菜单"就会慌。**主动告诉他方法，比装作有图强。**

#### 2. 步骤要编号，每步写清「在哪 → 做什么 → 注意什么」

**❌ 反面**（读者会迷路）

```markdown
去后台把权限配一下，然后创建机器人。
```

**✅ 正面**

```markdown
1. 打开 **企业微信官网** → 用**管理员账号**登录
   （注意：不是手机端 App，机器人相关操作只在官网管理后台）
2. 进 **安全与管理 → 管理工具**，找到"智能机器人"
3. 选 **手动创建**，填名称和头像
```

**关键**：菜单路径要**用 `>` 连起来写全**，并且**点明容易走错的地方**。

#### 3. 关键节点给「检查项表」——让读者自己确认走对了

**这是最有用的一招。** 没有截图时，读者不知道"我现在这个页面对不对"。

```markdown
| 检查项 | 说明 |
|---|---|
| 账号权限 | 必须是管理员，**普通成员看不到"安全与管理"等后台菜单** |
| 企业状态 | 至少拥有一个企业（新建即可） |
| 登录入口 | 用**官网管理后台**登录，**不是手机客户端** |
```

#### 4. 把「找不到入口 / 点错地方」写进 `@@trap`

**这替代了截图的"防迷路"作用。**

```markdown
@@trap 坑在哪
| 现象 | 原因 |
|---|---|
| 手机 App 里翻不到"智能机器人" | 机器人创建在**官网管理后台**，不是在手机端操作 |
| 用普通成员账号登录，找不到后台菜单 | 权限不足，换管理员账号 |
| 附加任务漏勾"添加到 PATH" | `cursor .` 这个命令需要它；装完可在系统设置里补 |
```

**读者按文字找不到入口时，翻一下 `@@trap` 表，八成就有答案。**

### 一个例外：纯"下一步式"安装可以简写

像"下载 → 同意协议 → 选附加任务 → 安装"这种**向导式安装**，
菜单路径没什么可迷路的，**不用硬套上面四条**。但**要挑出真正要留神的那一步**：

```markdown
整体是"下一步"式安装，唯一要留神的是**附加任务勾选项**
（决定是否加入右键菜单/命令行）。
```

### 一句话总结

> **没有图，就用「说清在哪 + 让读者自查 + 把迷路写进坑」来补。**
> **主动承认"这章是跟着点的"，比硬讲好得多。**


### 正文支持的写法

| 想要 | 怎么写 |
|---|---|
| **小标题** | `#` / `##` / `###`（渲染成 h2/h3/h4，卡片里会压小字号） |
| 代码块 | 三个反引号 + 语言名 |
| 命令行 | 三个反引号 + `cmd`（`>` 开头当提示符，`#` 开头当注释） |
| 表格 | Markdown 表格，**分隔行可省** |
| 表格内换行 | 写 `<br>` |
| 粗体 / 行内代码 | `**粗体**` / 反引号 |

**关于小标题**：`#` 开头的行会被当标题——**但代码块里面的 `#` 不受影响**
（`# 这是注释`、ASCII 图的边框都安全），因为渲染时先处理代码块。
所以放心在正文里用标题，也在代码里写 `#` 注释。

**长知识点建议加小标题。** 一个知识点如果超过一屏，用小标题分段，
读者才好扫。而且正文里的 `###` 不会进右侧目录（那是给知识点用的），
所以可以放心多用。

### 要解决什么问题

一章有 10–16 个知识点，页面很长。**读者从头滚到尾很累**，而且：

- 想回看第 ③ 点，得滚半天
- 滚到一半**不知道自己看到哪了**、还剩多少
- 想找"那个讲 temperature 的地方"，只能 Ctrl+F

### 目标（做完应该达到的效果）

1. **每个章节页自动生成一份本页目录**，列出该页所有知识点
2. **点目录项能跳过去**
3. **往下滚的时候，目录里高亮当前所在的那一项**（这是关键——解决"我在哪"）
4. **目录要一直可见**（跟随滚动），不是滚上去就没了
5. **窄屏 / 手机上不挡内容**（收起或隐藏）

### 硬性约束

| # | 约束 | 原因 |
|---|---|---|
| 1 | **必须由 `tools/build_site.py` 自动生成** | 手写进 markdown 会漏、会和内容脱节；自动生成才能让**以后每一章都自带目录** |
| 2 | **不要改 `content/*.md` 的语法** | 15 个源文件已经写好了，不能因为加目录就让它们全部失效 |
| 3 | **不要改已有卡片的 HTML 结构** | 复用现成的锚点即可（见下） |
| 4 | **覆盖全部已有页面** | 改完要重新构建，13 个页面都要有目录 |
| 5 | **CSS 加到 `site/assets/style.css`** | 别写内联样式，保持全站统一 |

### 现成的条件（不用从零做）

**知识点卡片已经带 id 了**，`build_site.py` 生成的是：

```html
<div class="point" id="p1">
  <div class="head"><span class="no">1</span>① 需求先行：先想清楚要解决谁的什么问题</div>
  <div class="body">…</div>
</div>
```

所以目录只需要：
- 遍历 `#p1`、`#p2`… 拿到 `.head` 里的文字
- 生成 `<a href="#pN">` 列表
- 加一段 JS 做滚动高亮（`IntersectionObserver` 或 `scroll` 事件都行）

**不需要改卡片结构，也不需要给章节内容加标记。**

### 位置建议

现在的布局是两栏：`.sidebar`（左侧，全局导航）+ `.main`（正文）。

**建议加成三栏**：左侧全局导航不变，**右侧加一个固定的本页目录**。

```
┌──────────┬────────────────────────┬────────────┐
│ 侧边栏    │  正文                   │ 本页目录    │
│ （全局）  │                        │ （跟随滚动） │
│ 阶段1     │  第一章 xxx             │ ● ① 需求先行 │
│  第一章   │  …                     │   ② 账号系统 │
│  第二章   │                        │   ③ 上传    │
│ 阶段2     │                        │   …        │
└──────────┴────────────────────────┴────────────┘
```

**不要太长**：知识点标题可能很长，目录里**截断到 12–16 个字**，鼠标悬停显示全文。

**窄屏处理**：宽度不够时**直接隐藏**右侧目录（不要挤正文）。
