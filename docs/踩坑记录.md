# 一、和 AI 协作踩的坑（最值钱的部分）

## ⚠️ 坑 1：删掉具体数字，产量会崩

**这是最贵的一条教训，值得单独一节。**

**经过：**

`@@trap`（避坑记录）这条规矩，我最初写的是：

> **目标覆盖率：60–80%**

后来有一章覆盖率只有 38%，我判断那是合理的（那章是"项目全景"，大部分内容是清单式的，本身没坑）。于是我去改规格，想让它别那么死板，改成了：

> **不要按百分比写。覆盖率是「结果」，不是「目标」。**

**结果下一批内容的质量直接崩了 —— 覆盖率从 100% 掉到 15%。**

我查了文件修改时间，铁证如下：

```
规格改于        20:48
上一批内容      20:02–20:38   覆盖率 67%–100%
下一批内容      20:56–21:03   覆盖率 15%     ← 12 章全在这里
```

**教训：**

> **该给数字的地方必须给数字。**
>
> 想表达「别死守这个数字」，要写清「**在什么情况下可以低于它**」，
> **而不是把数字删掉**。
>
> **删掉数字 = 告诉 AI「这条不作数了」。**

**修法**：恢复成「期望值 ≥ 70%」，并**列出分级判定**：

| 覆盖率 | 判定 |
|---|---|
| 70% 以上 | ✅ 正常 |
| 40–70% | ⚠️ 偏低，检查是不是漏了 |
| 40% 以下 | ❌ **基本可以确定是漏了** |

**外加一条明确的例外**：「纯罗列型章节（场景列表、选型决策树）可以低到 30–40%」。

**改完之后**：同一批内容重做，覆盖率 **15% → 82%**。抽查确认新加的坑是真坑，不是凑数。

## 坑 2：覆盖率这个指标，两头都会翻车

**我在这上面栽了两次，方向相反：**

| 批次 | 覆盖率 | 问题 |
|---|---|---|
| 第一批 | 100% | 我怀疑是"为了凑格式硬编的" |
| 第二批 | 0–17% | **真的是漏了** |
| 第三批 | 15% | 又漏了（就是坑 1 造成的） |
| 修完之后 | 70–100% | ✅ 正常 |

**关键认识：覆盖率是「结果」，不是「目标」—— 但也不能没有目标。**

**两个方向都不能走：**

- ❌ **为了凑百分比编坑** → 编出来的比没有更糟（读者会照着错的做）
- ❌ **因为"看着没坑"就跳过** → 大部分知识点都是有坑的，只是你没认真想

**唯一的判断标准：**

> **这个知识点，初学者最可能在哪里想岔？或者哪里最容易报错？**
>
> 想得出 → 写。想不出 → **跳过，但必须是真的想过了。**

**另外，抽查的时候我确认了一件事：** 100% 覆盖率**不等于**凑数。有时候每个点真的都有坑。所以要**抽内容看**，不能只看数字。

## 坑 3：让 AI 写代码示例，它会把真密钥抄进去

**我在自己整理的讲义里，抓到了 4 个真实的 API Key。**

来源是课程配套的 demo notebook —— 老师写示例时把 Key 直接写在代码里了。整理的时候如果不过脑子，就会原样抄进知识库，然后**跟着开源仓库一起公开**。

**这些 Key 是别人的、而且可能还在生效。** 公开出去，全世界都能拿去花别人的钱，**被追责的是你**。

**所以 `check_content.py` 里最重要的一项就是密钥扫描**，每次构建都跑：

```python
KEYPATS = [
    ("sk-开头的Key",   re.compile(r"sk-[A-Za-z0-9]{16,}")),
    ("api_key 硬编码",  re.compile(r"api[_-]?key\s*[=:]\s*[\"'][^\"']{12,}[\"']", re.I)),
    ("Bearer token",   re.compile(r"Bearer\s+[A-Za-z0-9._\-]{20,}")),
    ("JWT",            re.compile(r"eyJ[A-Za-z0-9_\-]{10,}\.[A-Za-z0-9_\-]{10,}\.")),
    ("明文密码",        re.compile(r"(?:pass(?:word)?|pwd)\s*[=:]\s*[\"'][^\"']{4,}[\"']", re.I)),
]
```

**要排掉合法占位符**（`"你的 API Key"`、`os.environ["XXX"]`、`sk-xxx`），否则会满屏误报。

**正确的写法：**

```python
# ✅ 从环境变量读
api_key = os.environ["DASHSCOPE_API_KEY"]
```

**而且要写进规格的禁止清单**，不能指望 AI 自觉。

## 坑 4：AI 会在 git 历史里留东西，删不掉

**这条是"泄密"的隐藏渠道。**

如果你不小心把密钥 / 讲义截图提交上去，**后面再 commit 一次删掉文件是没用的 —— 历史里还在**，`git log` 一翻就出来。

**两种处理：**

- `git filter-repo` 重写历史（会改掉所有 commit hash，协作的话很麻烦）
- **另起一个干净仓库**（推荐）

**所以正确做法不是"清理现有文件夹再提交"，而是"新建仓库，只把干净的文件拷进去"。**

---

## 坑 5：别把课程原文和链接一起开源

整理的时候会有很多**中间产物**散在目录里，一不小心就跟着提交了：

| 东西 | 为什么不能传 |
|---|---|
| 讲义 PDF | 版权 |
| 讲义提取出的正文 / 截图 | 版权 |
| 课程大纲 `.doc` | 版权 |
| **课程链接表（含视频 URL）** | ← **这个最容易被忽略** |

**我这次就差点中招**：`_资料索引/` 里存着一张链接表，**342 行里有 307 条是课程视频链接**。知识库正文里一条视频链接都没有（规格里禁止了），**但它躺在旁边那个文件夹里**。

**所以 `.gitignore` 要显式排掉这些目录**，别指望自己记得。

# 二、内容质量踩的坑

## 坑 6：容易写成"文件说明书"，而不是讲知识

写"项目型"章节（只给需求书 + 成品代码）时，最自然的写法是**按文件讲**：

```markdown
@@point ① auth.py 是干什么的
@@need 要解决什么
auth.py 负责用户认证相关的接口……
```

**读者读完只知道"有这么几个文件"，不知道为什么要这么设计。**

**改法：按「需求」切，不按「模块」切。**

```markdown
@@point ② 账号系统：为什么会议内容必须私有
@@need 要解决什么
会议录音里可能有薪资、人事、商业计划。这是**别人不能看的东西**。
所以"谁能看到哪条会议"必须由系统说了算，不能靠"没人猜得到链接"。
```

**差别**：正例讲的是"**为什么必须私有 → 于是做了三个设计决定**"，代码只是这些决定的实现。

## 坑 7："坑"要写认知坑，不要只写报错

**两类坑，价值差很多：**

| 类型 | 例子 | 价值 |
|---|---|---|
| **操作坑** | `EXPOSE 8080` 写了但连不上 → `-p` 才是开门 | 中（搜一下能搜到） |
| **认知坑** ★ | 以为 `RAG` 就是向量检索 → 向量只是检索的一种实现 | **高** |

**为什么认知坑更值钱：**

> 操作坑，遇到了一搜就有；
> **但"我以为是这样、其实是那样"—— 没人会主动告诉你，你只会在踩了之后才知道。**

**所以规格里明确了优先级：优先写认知坑。**

---

## 坑 8：抽象知识点没法"先体验"，得换个办法

一开始我想让每个知识点都"先让读者痛一下"（比如先跑一段慢代码，让他等 30 秒）。但有些知识点**根本没法体验** ——

比如「密码不能明文存」，总不能让他真被泄露一次。

**解法：用「先做错一次」代替「先体验痛苦」。**

给他一段"明文存密码"的代码，让他自己查数据库，看到密码原样躺着 → "这也太不安全了" → 再讲哈希。

**原则不变：先让他看见，再讲道理。**

---

## 坑 9：没有截图时，怎么讲"点哪个按钮"

有些章节讲的是可视化后台操作（建机器人、配通道），**但截图有版权不能用**。

干巴巴写步骤，读者会迷路。**解法三条：**

**① 开头就挑明**

```markdown
本章全是平台后台操作，没有复杂代码（全文代码不到 20 行）。
建议用**边看边点**的方式学：开一个浏览器跟着步骤走，卡在哪一步就回看哪一步。
```

**主动承认没图，并给出替代学法 —— 比装作有图强得多。**

**② 关键节点给「检查项表」**

```markdown
| 检查项 | 说明 |
|---|---|
| 账号权限 | 必须是管理员，普通成员看不到"安全与管理"等后台菜单 |
| 登录入口 | 用官网管理后台登录，不是手机客户端 |
```

让读者**自己确认走对了**，而不是靠看图比对。

**③ 把"找不到入口"写进坑**

```markdown
| 现象 | 原因 |
|---|---|
| 手机 App 里翻不到"智能机器人" | 机器人创建在**官网管理后台**，不是在手机端操作 |
```

**读者按文字找不到入口时，翻一下这张表，八成就有答案。**

**一句话：**

> **没有图，就用「说清在哪 + 让读者自查 + 把迷路写进坑」来补。**

## 坑 10：一套规格不能打天下

**知识型、项目型、操作型，三种章节的写法完全不同。**

| 类型 | 材料 | 知识点按什么切 | 最容易犯的错 |
|---|---|---|---|
| **知识型** | 有讲义、讲概念 | 按「学生的问题」切 | 写成词典条目 |
| **项目型** | 需求书 + 成品代码 | **按「需求」切，不按模块切** | 写成文件说明书 |
| **操作型** | 界面 / 安装流程 | 按操作步骤切 | 没有图，读者迷路 |

**我一开始只有一套规格，写到项目型章节时立刻跑偏。** 后来才补了另外两套。

# 三、技术踩的坑

## 坑 11：`adb pull` 拉不了含中文名的目录

**现象：**

```
adb: error: failed to create directory 'C:\.\章\': Illegal byte sequence
```

**第一次尝试**：以为是目标路径有中文 → **改成纯英文路径，还是炸**。
因为**源目录里面的 `代码` / `文档` 也是中文**，adb 建这些子目录时一样失败。

**第二次尝试**：用 Windows 自带的 `tar.exe` 解压。**文件名全乱码：**

```
Agent项目启蒙  →  Agent椤圭洰鍚
代码          →  浠ｇ爜
```

试着用 `name.encode('gbk').decode('utf-8')` 逆变换救回来 —— **只救回 2 个，另外 3 个救不回来**（部分字节不是合法 GBK 前导字节，解压工具走了回退路径）。

**✅ 正解：**

```bash
# 1) 手机上用 tar 打包成【英文名】的包
adb shell "cd '/sdcard/...' && tar -cf /sdcard/_pull.tar '要拉的中文目录'"

# 2) 拉这个纯英文名的包
adb pull /sdcard/_pull.tar C:\temp\_pull.tar
```

```python
# 3) 用 Python 的 tarfile 解压 —— 它对 UTF-8 文件名的处理是正确的
with tarfile.open(TMP_TAR, "r:*", encoding="utf-8") as tf:
    tf.extractall(dest)
```

**两个附带发现：**

- **`adb exec-out` 管道二进制在 PowerShell 里会被破坏**，别用
- **别用 Windows 的 `tar.exe` 解中文名压缩包**
- **打包时别压缩** —— 如果内容是 `.exe` / `.zip` 这类早已压缩的文件，gzip 一遍几乎不减小体积，纯浪费手机 CPU

## 坑 12：Markdown 表格没写分隔行，会让解析器死循环

自己写 Markdown → HTML 的渲染器时，如果只认「表头 + `|---|---|`」格式的表格，
遇到**作者没写分隔行**的表格就会卡住不前进 —— **程序直接挂死**。

**修法两条：**

1. 把连续的 `|` 开头行都当表格，分隔行**有则过滤、无则不管**
2. **段落分支必须加兜底 `i += 1`**，防止任何未识别的行导致死循环

**第二条是保命的，不管解析什么格式都该加。**

## 坑 13：`<div>` 不保留换行

做代码块样式时用了 `<div class="cmd">`，结果**多行内容被挤成一行**。

`<pre>` 自带 `white-space: pre`，`<div>` **没有**。

**修法**：`.cmd { white-space: pre; }`

## 坑 14：Word 的超链接域，网址在前、文字在后

从 `.doc` 大纲里抽链接，按直觉写「文字 + `HYPERLINK "网址"`」—— **一条都抽不到**。

**真实结构**（Word FIELD）：

```
\x13  HYPERLINK "网址"  \n _blank  \x01  \x14  显示文字  \x15
域开始                                    域分隔           域结束
```

**正确正则：**

```python
re.compile(r'HYPERLINK\s+"([^"]+)"[^\x13\x14\x15]{0,60}?\x14([^\x13\x15]{0,140})\x15')
```

## 坑 15：编辑 Word 别用 COM 自动化

做另一个项目（写论文）时，我用 Word COM 打开 docx 更新目录，结果：

- `Documents.Open` **挂死**
- 加看门狗 → 发现是 **LibreOffice 占着文件**
- 被占用时 Word 弹的对话框被 `DisplayAlerts=0` 压掉了，所以**看不到提示，只看到卡住**
- 最后改走临时副本才绕开

**更好的做法**：用**内置的 LibreOffice 命令行**转换和渲染，别碰 COM。

**但要注意**：LibreOffice 的排版**和 Word 不完全一致**（缺字体会导致文字度量变化）。所以：

- 结构检查、批量转换、快速预览 → LibreOffice 够用
- **要确认"在 Word 里最终长什么样" → 必须在 Word 里看**

## 坑 16：从手机拉资料前，先看看插了几台设备

`adb pull` 报：

```
adb: error: failed to get feature set: more than one device/emulator
```

**原因**：同时插着两台手机。**所有 adb 命令都会失败。**

**修法**：`adb -s <设备序列号> pull ...`，别让它自己猜。
